# 前端长会话内存优化（同一个会话聊很久后单 tab 占用 800MB+）

**背景（使用者反馈）**：在 Chrome 里同一个会话连续聊很久之后，该 tab 的内存占用涨到 800MB 以上，
刷新后回落。目标是把长会话的稳态占用压到可接受范围（目标：纯文本长会话 < 300MB，
含图片附件时 < 400MB），同时不改变任何交互口径。

**范围**：只动前端（`frontend/src`、`frontend/vite.config.ts`、`frontend/index.html`），
不涉及后端接口与 `shared` 契约。**零新增依赖**（沿用本仓从 P0-1-30 起的纪律）。

---

## 一、先量再改：怎么确认是哪一类在吃内存

Chrome DevTools → **Memory**：

| 观测 | 结论 | 对应本文 |
|------|------|----------|
| Heap snapshot 里 `Detached HTMLElement` / `Detached Text` 很多 | DOM 没被回收（长列表常驻 + 反复重挂） | P2 / P3 / P4 / P5 |
| Heap snapshot 里 `string` 占大头 | Markdown 源码 / 渲染结果 / 工作区正文堆积 | P3 / P4 / P5 |
| 以上都不多，但任务管理器显示占用很高 | **图片解码缓存**（位图不进 JS 堆） | P1 |
| 只在 Code 模式（工作区面板）明显 | 文件树 + 编辑器 + 每文件两份正文 | P4 |

判定顺序建议：先看“有没有图片附件”（P1 是唯一可能单独造成几百 MB 的一项），
再看 Code 模式是否开着（P4），最后看纯文本长会话（P2 / P3 / P5）。

---

## 二、根因与改法（按收益排序）

### P1 · 图片：`<img>` 没有懒加载，浏览器解码的是原图（收益最大、风险最小）

**现状**

- `features/chat/MessageList.tsx` 的用户附件缩略图：`<img src={fileContentUrl(...)}>`，
  没有 `loading` / `decoding` / `width` / `height`；
- `features/chat/ChatInput.tsx` 的 26×26 附件 chip 同理；
- CSS 只把**显示**尺寸限到 120×120（`app.css` `.msg__attachment-image img`）与 26×26
  （`.attachment-chip__thumb`），**解码尺寸仍是原图**。

**为什么这是最大的一块**：一张 4000×3000 的 JPEG 解码后约 48MB 位图（4 字节/像素），
不进 JS 堆、不进 heap snapshot，但在任务管理器里实实在在地算在这个 tab 上。
历史里 10 张照片 ≈ 480MB —— 与“800MB”这个量级完全吻合，且与“聊得久”强相关
（附件是历史消息的一部分，滚动回来就一直被缓存着）。

**改法**

1. 所有消息流 / 输入区的图片加 `loading="lazy" decoding="async"`，并把
   `width` / `height` 显式写成语义尺寸（CSS 已固定，这里只是让浏览器在布局前知道盒子大小，
   避免“先按原图尺寸撑开、再缩回去”的抖动）。
2. 保留 `title` / `alt` 行为不变（文案口径不动）。

**边界**：这条只保证“视口外的图片不被解码 + 解码不阻塞渲染”，**不减小原图字节**。
真正的根治要后端按 `width` 参数出缩略图（本批不做，记入“后续可选”）：
`/api/files/:id/content` 加 `?w=`（接口契约变更，需与后端一起排期）。

### P2 · 流式期间整棵消息列表都重渲染

**现状**：`useChatStream` 每收到一个 `delta` 帧就把这一轮写进 store
（`stores/chatStream.ts#apply`），`ChatPage` 的 `messages` 依赖 `streamViews` 变化 ⇒
`MessageList` 整个 `map` 重跑 ⇒ 历史上每一条 `AssistantMessage` / `UserMessage`
都重新执行函数体（`react-markdown` 对**历史**消息虽然 `text` 没变，但父组件重渲染会重新走一遍
元素树构建）。目前只有 `ToolCard` 是 `memo` 的。

**改法**

1. 给 `AssistantMessage`、`UserMessage`、`OpeningMessage`、`ThinkingBlock`、
   `CitationCard`、`ArtifactCard`、`StreamingStatusLine` 套 `memo`；
2. 输入回调（`onRegenerate` / `onRecall` / `onResend` / `onRecallSteer`）在 `ChatPage` 里
   必须引用稳定 —— 现状已经是 `useCallback`，但 `openRecall` 之外的 lambda 需要改成 `useCallback`，
   否则 `memo` 会被新函数引用击穿；
3. **前提**：`view` 的引用必须稳定。历史侧 `messageToViews` 已经在 `ChatPage` 里 `useMemo`
   缓存（`messagesQuery.data` 不变则引用不变），所以历史消息在流式期间天然不会重渲染。

**收益**：流式期间每帧的工作量从“O(历史消息数)”降到“O(1)”（只有当前那一轮变化）。

### P3 · 思考块与 Markdown：折叠的内容仍挂在 DOM，且每帧全量重解析

**现状**

- `ThinkingBlock`：`<div className="think__body">{text}</div>` 无论折叠与否都在 DOM 里
  （`<details>` 只是隐藏），长思考（几万字）全程占着文本节点；同时 `charCount(text)` 每次渲染
  都 `[...text].length`（对几万字是 O(n) 展开成数组）。
- `AssistantMarkdown`：流式期间每个 `delta` 都触发一次 `react-markdown` **全量解析 + 全量重建
  元素树**；长回答（几万字）时这是流式期间 CPU 与临时对象的主要来源。

**改法**

1. `ThinkingBlock`：折叠时**不渲染正文节点**（`open ? <正文/> : null`），只在用户展开后挂上；
   字数用 `text.length` 近似或缓存（改为 `useMemo(() => [...text].length, [text])`，
   避免每次渲染重算）—— 仍然如实报“字”。
2. `AssistantMarkdown`：流式期间**按块增量解析** —— 只把“已完成的前缀”（最后一个空行之前）
   交给 `react-markdown`，末尾那段不完整的块按纯文本渲染。这样：
   - 已稳定的部分不随新字符重解析；
   - 末尾块每帧只解析一小段（最多几百字）；
   - 收尾后一次整篇解析，与历史一致。
   判据放在 `AssistantMarkdown` 内部（`streaming` 布尔入参），不改任何调用方契约。
3. 消息**不在视口附近**时，用 `content-visibility: auto` + `contain-intrinsic-size`
   让浏览器跳过整棵子树的样式/布局（纯 CSS，无需 JS 测量）—— 这是 P5 虚拟滚动的“轻量版”，
   能拿到大部分收益且零风险。

### P4 · 工作区（Code 模式）每打开一个文件就留两份正文，且关标签不清

**现状**

- `WorkspacePanel` 的 `docs: Record<path, { text, baseText }>`（两份字符串/文件），
  `closeFile` 只改 store 的开标签列表，**不清 `docs`**；
- `useQuery(['workspace-file', conversationId, activePath])` 每打开一个文件就留一份完整正文在
  query 缓存里，`gcTime` 用全局默认（5 分钟，但会话一直在用就一直活着）；
- `<CodeMirrorEditor>` 挂在“当前激活文件”上，但切换标签时**卸载重建**（`docKey` 变化 → 组件
  仍是同一个实例、`value` 走 effect 替换），撤销栈被清空是对的；问题在 `docs` 里那些
  **已经关掉的标签**的正文一直留着。

**改法**

1. `closeFile` 之后同步：
   - 从 `docs` 里删除该路径的草稿；
   - `queryClient.removeQueries({ queryKey: ['workspace-file', conversationId, path] })`。
2. `WorkspacePanel` 卸载 / 切会话时，把 `docs` 整份清掉（会话级临时状态不该跨会话累积）。
3. `docs` 只保留**当前打开的标签**（`openPaths`）里的路径 —— 新增一个小函数
   `pruneDocs(docs, openPaths)`，在 `openPaths` 变化时裁剪一次，避免“删了标签但没走 closeFile”
   的路径（例如 agent 侧删文件时 store 的 `closeFile` 只关标签）。
4. 给 `['workspace-file']` 查询设 `gcTime: 60_000`，别让整份文件在缓存里躺十几分钟。
5. CodeMirror 编辑器：保持“只渲染当前标签”不变（本来就是），但给外层容器加
   `content-visibility: auto` 不适用（编辑器可见即需要），跳过。

### P5 · 查询缓存与历史窗口化

**现状**

- `useConversationMessages` 是无限查询，翻过的每一页都永久留在 `QueryClient` 里；
- `queryClient.ts` 没设 `gcTime`（默认 5 分钟），活跃查询永不回收；
- `messages` 数组无上限增长（虚拟滚动做之前，DOM 也随之增长）。

**改法（不引入新依赖）**

1. `queryClient.ts`：`gcTime: 5 * 60_000` 显式化（行为与默认一致，但把口径写在明处），
   同时对 `['conversation', id]` 这类历史查询保留默认即可 —— 真正的问题是“页数”，见下条。
2. **P5a（本批做）**：`ChatPage` 增加一个“历史上限”窗口 —— 渲染用 `messages` 最多保留最近
   `HISTORY_RENDER_LIMIT`（默认 120 条）**视图**，更早的部分折叠成顶部一条
   “更早的消息已折叠（点此展开）”的占位，点开后在本次会话内保持展开。
   - 数据层不丢（query 缓存仍持有），只是渲染上限；
   - 配合 P3 第 3 条的 `content-visibility`，即使展开也不会一次性把整棵树算进布局；
   - 判据放在一个纯函数里（`features/chat/messageWindow.ts`），可被无依赖档断言。
3. **P5b（后续）**：真·虚拟滚动（变高列表）。这需要测量每条消息高度（或用户“跳到底部”时重新
   测量），属于独立一批；本批不做，理由：变高虚拟滚动与“贴底跟随”“流式长高”两套逻辑耦合，
   风险明显高于 P5a 的渲染上限。

### P6 · 次级项

| 位置 | 问题 | 改法 |
|------|------|------|
| `ConvRail` 会话行 | 60s tick + 任意 `rounds` 变化都会让整列重渲染；每行还 `items.find(...)` | 抽出 `ConvRow` 并 `memo`；分组结果按 `(group, streamingIds)` 缓存 —— **本批只做 memo + 索引 Map** |
| `ArtifactPreviewDrawer` | 预览过的文本（最多 1MB）与 iframe 在关闭后仍留在 DOM/state | 关闭时 `destroyOnClose` 语义：`open=false` 时清 `text` 状态（已有的 effect 已处理取数，但没有清 `ready` 的正文） |
| `vite.config.ts` | 生产 `sourcemap: true`，chunk 的 `.map` 2～3MB，Chrome 加载后 source map 也占内存 | 改为 `sourcemap: 'hidden'`（仍可上传给错误监控，但浏览器不会自动拉取） |
| `styles/webfonts.ts` | 一次拉 6 个 Google 字体文件（含 Noto Sans SC 大子集），字体数据也计在 tab 上 | Archivo / IBM Plex 只保留真正用到的字重（700/800、400/500/600 已是全部），把 **Noto Sans SC 移除**（中文本来就由系统字体承接，见该文件头） |
| `MessageList` 用户附件 | `formatSize` 每次渲染重算 | 无害，跳过 |

## 四、验收

1. `pnpm --filter @doubulea/frontend typecheck` 通过；
2. `node --import tsx scripts/verify-chat-sse.mjs` / `verify:chat-home` / `verify:artifact-panel`
   等无依赖档全部通过（渲染窗口函数另有断言）；
3. 手工验收（Chrome）：
   - 同一会话连续 100 轮 + 滚动到底：tab 内存（Chrome 任务管理器）应显著低于改造前；
   - 流式期间 DevTools Performance 录制：每帧的重渲染工作不再随历史条数线性增长；
   - 思考块折叠状态下，Elements 面板里**没有**正文文本节点；
   - Code 模式关掉标签后，Memory 快照里不再有该文件的两份正文；
4. **回归重点**：工具卡在正文内的插入位置（`remarkInlineBlocks` 的偏移口径）、
   思考段与工具卡的内联顺序、流式光标、`重新生成` 的收词、贴底跟随。
