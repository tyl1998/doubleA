## 一、先量再改：现状盘点（本方案的事实基础）

平台**此前从未做过界面多语言**。

| 位置 | 规模（实测，非注释文案） | 性质与处置 |
|---|---|---|
| `frontend/src` | **约 5,800 处 / 109 个文件** | 纯界面文案（JSX label / message / 空态 / 错误提示 / 标签表），**必须外置** |
| `shared/src` | **约 850 处 / 23 个文件** | 一半是 `*_LABELS` 标签表（前端直接渲染，**是问题**）；一半是 zod 校验消息（初测 **246 处**，末批复扫为 **359 处**；随 `data.fields` 回给前端，**也是问题**） |
| `backend/src` | 约 6,000 处，其中**用户可见仅 ~320 条 `AppError` 消息** | 余下为日志（318 行，运维面不必译）、OpenAPI 注释（311）、给 LLM 的工具描述（不属界面） |

三个实测锚点：

- `frontend/src/app/AppProviders.tsx:20` —— AntD locale **硬编码** `import zhCN from 'antd/locale/zh_CN'`，`:49` 直接传给 `ConfigProvider`，没有第二语言可选。
- `shared/src/errors.ts:63` —— `DEFAULT_MESSAGE_BY_ERROR_CODE` 是**中文硬编码**的错误码兜底文案（`frontend/src/api/client.ts:23` 消费它）。
- `shared/src/cron.ts`、`memory.ts`、`modelProvider.ts` 等**十余张 `*_LABELS`** 前后端共用（`backend/src/services/memory.service.ts`、`openapi/openV1Spec.ts` 也在消费），前端渲染其中一部分。

**"依注释里的中文计数"会严重高估工作量**：本仓注释极重（前端注释中文 28,854 处 ≈ 非注释的 5 倍），改造口径**只算非注释文案**。

## 二、被否掉的方案（记录理由，避免反复）

| 备选 | 否决理由 |
|---|---|
| 引 `i18next` / `react-intl` / `lingui` | ① 本仓前端依赖刻意"极简"（唯二的非极简依赖是 AntD 与 CodeMirror 家族）；② 这些库的 key 是**字符串**，漏译要到运行时才炸 → 正是本仓"错了不会报错"的高危类型；③ 运行时体积与首屏成本；④ 平台只有 2 语言、无复数/性别等复杂规则，库能力绝大部分用不上 |
| 由后端按 `Accept-Language` 返回本地化文案 | 与既有架构冲突：本仓**已有**一层"错误码 → 用户文案"的收口（`frontend/src/app/feedback.ts` = 唯一出口，`06` §六 纪律 28），后端返回本地化正文会造出**第二份文案真相**；且 `*_LABELS` 这类枚举标签本就在前端渲染 |
| locale 存服务端（用户偏好列） | 界面语言不改变任何服务端行为；为一个纯展示偏好加列 + 端点 + 迁移，与 `themeMode`（纯客户端）的口径不一致 |
| 一次性把 109 个前端文件全抽 key | 整个前端不可验收（改动面 = 全栈），违反本仓"一批一验、可回滚"的节奏 |

## 三、定案

### 3.1 运行时：自研 typed、零新依赖

新增 `shared/src/i18n/`（口径同自写 `shared/src/cron.ts`：纯函数、零依赖、前后端共用、可无依赖验收）：

```
shared/src/i18n/
  messages.zh.ts    ← key 全集真相（zh 是默认语言，其 key 集合即契约）
  messages.en.ts    ← Record<MessageKey, string> 约束 ⇒ 漏译 = 编译期报错
  index.ts          ← LOCALES / Locale / MessageKey / translate()
```

**三条硬约束**：

1. **key 类型从 zh 推出**：`type MessageKey = keyof typeof zh`；`en` 声明为 `Record<MessageKey, string>` ⇒ **漏一个 key 就编译不过**（不是运行时 warning）。多一个 key 同样报错（`Record` 不允许超出）。这是选"自研 typed"而非 i18n 库的**核心理由**。
2. **`translate(locale, key, params?)` 是纯函数**：不读 `window`、不读 localStorage、不 import 前端模块 ⇒ 后端与零依赖验收脚本都能直接跑。
3. **占位符**：`{name}` 形式（与既有 `renderNotifyTemplate` 的 `{{task}}` 刻意区分，避免与"通知模板"混为一谈）；缺失参数**原样保留**占位符（不抛错、不静默吞）。

### 3.2 locale 来源与持久化：纯客户端偏好

- 存储键 `doubulea.locale`，取值 `'zh' | 'en'`，缺省/非法 ⇒ 回落 `'zh'`。
- **口径与 `stores/ui.ts#themeMode` 完全对齐**：localStorage + 隐私模式异常吞掉 + `<html lang>` 同步（对应 theme 的 `<html data-theme>`）。
- `initLocale()` 在 `main.tsx` 的 `render` **之前**调用（与 `initThemeMode()` 同处），避免首帧语言闪动。
- **不进服务端**：无 per-user 列、无端点、无迁移。

### 3.3 切换入口

- **会话栏底部**（`frontend/src/features/chat/ConvRail.tsx` 的 `.convrail__foot`）：与配色切换按钮并列的一枚语言切换（`中 / EN`）。
- **头像菜单**（`frontend/src/app/UserMenu.tsx`）：菜单项「界面语言 / Display language」。
- 两处都是纯客户端调用 `setLocale()`，**不做路由跳转、不刷新页面**（`useT()` 订阅 store，切换即重渲染 —— 与配色切换同款）。

### 3.4 AntD 与 dayjs 联动

- `app/AppProviders.tsx`：删掉写死的 `zhCN`，改为按当前 locale 从**映射表**取（`zh_CN` / `en_US`）。
- dayjs：`dayjs.locale(currentLocale)` 在 locale 生效时调用（`dayjs/locale/zh-cn`、`dayjs/locale/en` 按需 `import`）。
- **一处来源**：映射表只写在 `AppProviders.tsx` 邻近（`app/locale.ts`），别处不要再写一次 AntD locale 判据。

### 3.5 `shared` 标签表与后端错误码如何收口（★ 本次最大的一处架构决定）

**方向 = 前端主译，后端只回 code + 参数。**

| 对象 | 处置（本批） | 后续 |
|---|---|---|
| `shared/*_LABELS`（十余张） | **保留中文**（前/后端仍在消费，动它牵一发动全身）；前端新增 i18n 层按 `label.<表名>.<值>` key 覆盖 | 逐表迁移，迁完一张在 `03` §九 划掉一张；全部迁完后这些表退化为"zh 兜底"或直接删除 |

#### 3.5a 收口结论（末批，P1-23 第十批）

四件都落在"**前端主译、后端只回 code + 参数**"这一条主轴上，没有引入第二种口径：

1. **标签表**：`shared` 里**还剩下 1 张前端在渲染的表** —— `SANDBOX_BUILD_PHASE_LABELS` 之外的都已有 `*_KEY`（见 §九 的核对）。本批补齐了两处漏网的**消费方**（`pages/settings/ProviderKeySection.tsx`、`components/VisibilityBadge.tsx` 改用 `PROVIDER_CREDENTIAL_MODE_KEY` / `ASSET_VISIBILITY_KEY`），并收口了 `components/*` 余下的三处纯中文组件（`TransferOwnershipModal` / `AssetUserPicker` / `AudiencePicker`，用户 2026-10-26 实测反馈"智能体转让弹窗没有中英文"）。
   - `SANDBOX_BUILD_PHASE_LABELS` **已于 2026-10-27 迁完**（收尾 ①，结论见 §3.5d）：契约改为 `phase` + `detail`，前端按 `SANDBOX_BUILD_PHASE_KEY` 拼句；`phaseLabel` 降级为 `@deprecated` 且后端不再更新。
2. **`describeCron` 多收 `locale`**（选"纯函数多收 locale"这一档，不选"返回结构化片段"）：`shared/src/cron.ts` 因此多一个依赖 `./i18n/index.js`（同 `document.ts`），但仍是纯函数；`cron.desc.*` 七条 zh 与旧内联中文**逐字一致**，由 `backend/scripts/cron-regression.ts` 的 E1/E1b 与 `verify:i18n` G3 双守。

#### 3.5d 构建进度的阶段文案：**已迁**（2026-10-27，收尾 ①）

原结论是"不迁"（后端拼好 `phaseLabel` 下发，前端直接显示）。**该结论已于 2026-10-27 作废**：契约改成
`phase` + `detail` 两个字段，由前端按 `SANDBOX_BUILD_PHASE_KEY` 取译文再拼成一句人话。

**契约形状（`shared/src/runtime.ts#sandboxBuildJobSchema`）**

| 字段 | 形态 | 说明 |
|---|---|---|
| `phase` | `z.enum(SANDBOX_BUILD_PHASES)` | 阶段（粗粒度，只前进） |
| `detail` | `z.string().nullable()` | 当前阶段的细节（组件名 / `RUN` 概要）；没有时 `null` |
| `phaseLabel` | `z.string().optional()` **`@deprecated`** | 后端**不再更新**；仅为兼容旧前端保留，将随下个版本删除 |

**为什么保留 `phaseLabel` 而不是直接删**：一次性删会让"新后端 + 旧前端"（灰度期）拿到 `undefined`，
那一行变成空白。保留但不更新 = 旧前端退化成"只显示阶段名"，不会崩。

**落点**

- 中文真相仍是 `SANDBOX_BUILD_PHASE_LABELS`（**不删**：后端日志与回归用它），孪生 `SANDBOX_BUILD_PHASE_KEY`
  （`label.buildPhase.*`）；`verify:i18n` G1 与 `runtime-build:regression` ① 都逐表守"两边不漂移"。
- 拼句走字典 `runtime.buildPhaseWithDetail`（zh 与旧 `phaseLabel` 逐字一致：`{phase}（{detail}）`）。
- 前端唯一渲染点 `features/chat/RuntimeSelect.tsx#buildPhaseText`；`detail` 为空时**不产出** `(null)`。
- 守门：`verify:i18n` **F12** 断言 `RuntimeSelect.tsx` 源码里不再出现 `phaseLabel`。

**同族的 `sandboxVariantLabel` 仍未迁**（属于"后端算好的显示名"，与 `runtime.label` 一起改才划算），
记入 §六 已知边界。

**为什么不给 `ApiError` 加 `locale` 字段**：`ApiError.message` 的契约就是"可直接展示的文案"。
再加一份 locale 等于让同一份数据有两种形状（页面到底信哪个？）。代价是**构造期快照** ——

**`api.sse.issueLine` 为什么也进字典**：那行 `[chat] … 事件被忽略：…` 只进控制台，
但它同样会出现在 en 用户的 DevTools 里。进字典的收益是"排查时读得懂"，成本是一条 key。

`verify:i18n` 的 `isAllowedChineseLine` 对它做**整行字面量白名单**（不是整文件放行）。

**守门**：F 账本 +5 文件（共 111）；新增 **H6** —— 断言 `api.*` 命名空间不少于 13 条、en 下逐条不含汉字、

**`parseSseFrame` 的 locale 参数带默认值 `'zh'`**：它是纯函数、且已有大量零依赖断言直接调它。
给必填参数会逼着改几十处断言，而默认值让"忘了传"退化成中文（zh 是默认语言，与产品一致）。

#### 3.5g 失败通知的文案判定：**已修正**（2026-10-27）

**修的是什么**：收尾 ④ 把前端自造的文案（`api/client.ts` 的网络层自造句、`useChatStream.ts`

#### 3.5h 后端 `AppError` 细节消息：**已迁**（2026-10-27，收尾 ⑤）

**规模**：`backend/src` 里带中文的 `AppError` 调用点 **400 处 / 242 条去重模板**（含 31 处纯字面量拼接）。

**做法：双写，而不是把 `message` 换成 key**

| | 改写前 | 改写后 |
|---|---|---|
| `AppError.message` | 中文正文 | **仍是中文正文**（`appMsg` 在构造期按 zh 渲染） |
| 日志 / `documents.error_msg` | 中文 | **逐字不变** |
| HTTP 信封 | `{code, msg, data}` | `{code, msg, data, msgKey?}` |
| SSE `error` 帧 | `{code, message}` | `{code, message, msgKey?}` |
| en 界面 | 退化成 `error.<CODE>` | **按 `msgKey` 显示真译文** |

为什么不把 `message` 直接换成 key：`message` 同时是**日志**与 `documents.error_msg` 的真相。
换成 `@app.m000` 等于把运维可见的报错变成一串编号 —— 那是净损失。

**为什么是「包裹调用点」而不是「按中文反查翻译」**：后者拿已经插值完的中文去正则匹配模板，
参数里一旦含有模板定界符就会张冠李戴，而且**不会报错**。`appMsg('app.m116', { p0: id })`
让 key 与参数都由调用点显式给出，结构上不可能猜错。
