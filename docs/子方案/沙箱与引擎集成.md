## 三、引擎选型定案（`01` 决策 3 的落点）

### 1. 选型结论

| 项 | 定案 |
|----|------|
| 引擎 | **Pi**（`earendil-works/pi`），**唯一默认引擎** |
| 许可 | **MIT** ⇒ `01` 决策 3 挂的"引擎许可与 API 服务条款需通过内部商用合规确认"**因选型而消解**，只剩常规的开源使用登记 |
| 接入形态 | **直连 `pi --mode rpc`**（JSONL over stdio），自写薄桥 |
| ACP | **不做适配器、只借接口形状**（见 3） |
| 模型 | BYOK：Pi 用自己的 provider 配置指向**我方模型池**的 baseURL（§五 3） |

### 2. 为什么不走 ACP 适配器

社区有现成适配器（Zed ACP Registry 里的 `pi-acp`，另有 `@curxor/pi-acp`、`pi-acp-zz`）。**不选它做实现**，三条都是硬理由：

1. **拿不到 `thinking` 增量** —— `pi-acp` 的 README 明写 "Assistant streaming is currently sent as `agent_message_chunk` (**no separate thought stream**)"。而思考过程是我方**需求 10/28 明确要**的事件。走适配器 = 要么砍需求，要么绕过适配器再取一次。
2. **拿不到 extension UI** —— §七 的双向提问通道靠 Pi 的第 4 类 RPC 记录；`pi-acp` 的功能清单里没有它的转发条目。
3. **拿不到全量 usage** —— `pi-acp` 只上报上下文占用 ⇒ 会直接踩 `01` 决策 20 的"TaskAgent 计量允许 token 为空"这条**兜底**，把"可以填满"降级成"只能留空"。

★ 直连**不增加自研量**：Pi 的 RPC 协议是**官方文档化**的（`docs/rpc.md`，包内导出 `rpc-types.ts`，官方给了 `RpcClient` 示例），不是逆向出来的。而且它把关键路径上的**单人 MVP 依赖**去掉了 —— 一个我们无法回滚的第三方。

### 3. ACP 当作"接口形状"而不是"实现"

编排器内部仍按 ACP 的语义分层：

```
initialize（握手/能力确认）
  → session/new（建会话：模型、工作目录、系统提示词）
  → session/prompt（派活）
  → 事件流（delta / thinking / tool_call / usage）
  → session/cancel（停止）
```

这样**将来真换引擎时，改的是"桥接实现"而不是"编排层"** —— `01` 决策 3 想要的"引擎可换"这条缝保住了，只是缝的位置从"外挂适配器"挪到了"我方桥的接口边界"。

### 4. 三条硬门槛的结论

| 门槛 | 结论 | 落点 |
|------|------|------|
| **模型池三协议** | 我方 = `OPENAI_COMPAT` / `OPENAI_RESPONSES` / `ANTHROPIC_MESSAGES`。✅ **2026-09-26 P0-3-4 关闭（→ §十三 待决 1）**：pi 三条**都有**对应实现（`dist/api/{openai-completions,openai-responses,anthropic-messages}.js`，它的 `api` 取值就是这三个名字）⇒ **不需要"不支持任务型 Agent"的收窄判定**。映射表唯一落点 = 后端 `sandbox/spec.ts#piApiForProtocol`；容器侧只照抄 api 名 | ✅ P0-3-4 已定 |
| **MCP 绑定** | ✅ **可以绑** —— 走**后端代理**（§七）。TaskAgent 是 Agent，`01` 需求 7"Agent 绑知识库 + MCP server"对它同样成立；上一轮讨论过的"收窄绑定"**作废** | P0-3-9b |
| **会话恢复** | **不挂持久卷**。每轮把**我方自己的消息历史**重放给新起的 Pi，而不是持久化 Pi 的 session 文件。理由：与"事件即真相、历史读库"的既有口径一致（`02` §六），少一个持久化面，且不与"空闲 30min 回收"打架 | P0-3-5 |

## 四、容器与网络

### 1. 会话即容器

- 粒度：**一个 `conversations` 行 ⇒ 一个容器**（`01` 决策 6）。同一会话的多轮消息**复用同一个容器**；容器不存在（首次 / 已被回收）则新建后**重放历史**（§三 4）。
- 命名与标记：容器与卷一律带 label `doubulea.role=sandbox`、`doubulea.conversation=<id>`、`doubulea.startedAt=<iso>`。⚠️ **孤儿清道夫（§九 2）完全依赖这组 label**，漏打一个就等于清道夫看不见它。
- **落库**：创建/回收同样写 `sandboxes` 表（`02` §三 已有：`id, conversation_id, container_id, status(CREATING|RUNNING|RECYCLED|FAILED), image, created_at, last_active_at`）。⚠️ `container_id` 只是**留痕与排障用**；**"哪些容器是我们的"以 label 为准、不以这张表为准** —— 后端崩在"容器已建、行还没写"之间时，表里没有它，而 label 在。两处都要有，但判据只能有一个。
- ✅ **P0-3-2 落地（`backend/src/sandbox/spec.ts` 是这组契约的唯一落点）与两条实测**：① **`OpenStdin: true` 且刻意不设 `Tty`** —— 否则容器**起来就死**（引擎要靠 stdio 说话）；② ★ **`docker rm -v` 删不掉具名卷**（实测 `docker rm -f -v` 之后 `docker volume ls --filter label=…` 里那个卷**还在**）⇒ **回收必须两步**（容器 → 显式 `volume rm`），指望 `-v` 顺手清干净会得到"账本说回收了、卷还堆着"。另：`Mounts` 落在 `HostConfig` 而非创建参数的顶层（`docker inspect` 亦然）。
  ⚠️ **本批容器的 `NetworkMode: 'none'` 是临时取值** ⇒ §四 2 / §四 3 的全部安全项留给 **P0-3-3**（改点集中在 `buildSandboxContainerSpec` 的**同一处** `HostConfig`）。

### 2. 资源与文件系统（`01` 需求 31）

| 项 | 配置 | 理由 |
|----|------|------|
| rootfs | `--read-only` | 引擎与工具链全在镜像里；容器**不该能改自己** |
| work 卷 | 具名卷，挂 `/work`，**读写**，上限见 §二 | 产物唯一落点 |
| `/tmp` | `tmpfs`，`nosuid,nodev,noexec`，上限见 §二 | 引擎与三方库都要写临时文件；给 tmpfs 保证"用完即消" |
| 用户 | **非 root**（镜像内建 `agent` 用户） | 与 `--cap-drop ALL` 配套，缺了它 cap-drop 的意义减半 |
| capabilities | `--cap-drop ALL` + `--security-opt no-new-privileges` | 沙箱内**没有任何**需要特权的能力 |
| 限额 | mem / cpu / pids 见 §二 | `01` 需求 31"资源限额" |
| 网络 | 见 3 | **两条出口，其余默认拒绝** |

> ⚠️ **work 卷不能做成 `tmpfs`**。上一轮讨论里一度倾向"内存为主"，但 work 卷若用 tmpfs，验收场景（产出 CSV 汇总表）的大产物会直接把容器内存顶掉。正确分工：**内存限额管"引擎+工具链的运行足迹"，work 卷管"产物体积"**，两者配额分开。

> ✅ **2026-09-26 P0-3-3 落地实测**（表内七项全部落进 `spec.ts#buildSandboxContainerSpec` 的**同一处 `HostConfig`**；真 Docker 29.4.0 / OrbStack，容器内逐条取证）：
> - `ReadonlyRootfs: true` ⇒ 容器内写 `/` 与 `/usr` 得 **EROFS**（写 `/work`、`/tmp`、`$HOME` 正常）。
> - `CapDrop: ['ALL']` + `SecurityOpt: ['no-new-privileges']` ⇒ 容器内 `/proc/self/status` 的 `CapEff=0000000000000000`。
> - `Memory` **必须同时给 `MemorySwap` 且两者相等**（只给 `Memory` 时 swap 不受限，内存限额形同虚设）；实测 `memory.max=268435456`（= 256MB 探针值）。`NanoCpus` / `PidsLimit` 同理（实测 `pids.max=64`）。
> - ★ **两处 tmpfs**：`/tmp`（`rw,nosuid,nodev,noexec,size=…`）与 **`$HOME`**（= `/home/agent`，**本批新增**）。⚠️ **`$HOME` 那处必须带 `uid`/`gid`** —— 实测不带时新目录属 `root:root`，agent 写自己的 HOME 得 **`EACCES`**（第一版就是这个形态）；加 `uid=10001,gid=10001,mode=0755` 才正常。两处额度都取 `SANDBOX_TMPFS_MB`。
> - **用户 = 非 root 由"镜像断言"守住**：建容器前 `inspectImageUser` 读镜像 `Config.User`，非 root 才继续（**不是**靠命令行 `-u` 运行期覆盖 —— 镜像本身若烤成 root，`docker exec` 等旁路仍可能是 root）。实测容器内 `uid=10001`。

### 3. 网络：两条白名单，其余默认拒绝（`01` 决策 6 / 需求 31）

容器**必须**能出网（引擎要调 LLM），所以 `network=none` 不成立。但"能出网"不等于"能随便出网"：

| # | 放行目的 | 归类 | 说明 |
|---|----------|------|------|
| ① | **模型池 baseURL**（各 Provider 的公网地址） | 公网，经 egress 代理 | `02` §七 原文 |
| ② | **后端沙箱代理**（`SANDBOX_CALLBACK_PORT`） | **内网，不经代理** | ★ 本次新增 —— `02` §十 网络一列已同步回写。这是 §七 MCP 代理的通道 |

**实现要点**

- 容器放在**专用 internal bridge**，**不用默认 `bridge`**：默认 bridge 上容器能摸到宿主所有监听端口（含 13000 公网口、PG、Redis、MinIO），那是比"能出公网"更严重的暴露面。
- 出口② 落成**独立 listener**：同一进程内**第二个 Fastify 实例**，只挂 `/api/sandbox/*`，绑在专用 bridge 的网关地址上。⇒ 容器**摸不到任何业务 API**（登录、会话、管理端点全不在这个 listener 上）。
  - 若第二实例成本偏高，可退化为"同一实例 + `iptables` 只放行该端口 + token 校验"，但**必须显式记下这个退化**，不要默默选它。
  - ✅ **2026-09-26 P0-3-3 定案：不退化** —— 采用独立 Fastify 实例（`sandbox/listener.ts`）。理由：退化方案里的 `iptables` 限源**在 macOS/OrbStack 上根本验不了**，且把"沙箱专用"与"公网"两条面混在一个实例里，**任何一条路由挂错 listener 都是静默扩大暴露面**。本批**只交付通道**，端点本体（`/api/sandbox/*`）属 **P0-3-9b**。
- 专用 bridge 的网关地址是容器眼里后端的地址，通过**容器环境变量**下发给桥扩展（`SANDBOX_BACKEND_URL`），**不做 DNS 猜测、不做兜底**（与 `06` §六 第 27 条"服务间地址必须唯一事实来源 + 显式失败"同款纪律）。✅ 落地即此形态，只是把"网关地址"收进 `SANDBOX_BACKEND_URL`（留空时后端自动取「网关 + `SANDBOX_CALLBACK_PORT`」）。
- egress 代理只做**域名/前缀白名单**，不做内容检查；代理本身不属于 P0 的加固范围（`02` §十 已把 `docker.sock` 列为已知 trade-off，本条同族：**写清边界，不假装**）。

> ⚠️ **两处必须实测，不许假设**：① 专用 bridge 上容器到网关地址是否真能通（不同 Docker 版本 / OrbStack 对 `bridge` 网关与 `iptables` 的处理有差异）；② `--storage-opt size=` 是否真的生效（`docker inspect` 看 `HostConfig.StorageOpt`，**且要真写超一次看它拒绝**）。两条都进 P0-3-3 的验收项。
>
> ✅ **2026-09-26 P0-3-3 实测结论**：
> - ① ★ **internal 网络上容器到不了 macOS 宿主**（`ENETUNREACH` —— bridge 网关是 OrbStack 的 Linux VM，**不是 macOS**），**但到 Docker 宿主（= 网关地址）可达**：后端起 listener 后容器侧实测 **200**。⇒ 出口② 的设计在**生产**（后端与 Docker 同宿主）成立；**macOS 本机**需显式中转（把 `SANDBOX_BACKEND_URL` 指到一个与沙箱网络**双宿**的中转、`SANDBOX_LISTEN_HOST` 填 `0.0.0.0`）。此实况已写进 `sandbox/network.ts` 文件头与 `README`。同一实验里还确认：internal 网络**公网不可达**（`EAI_AGAIN`）—— 这正是"白名单只剩代理一条路"的正面取证。
> - ② **`--storage-opt size=100m` 被守护进程直接拒绝**（`docker: Error response from daemon: --storage-opt is supported only for overlay over xfs with 'pquota' mount option`）⇒ **不写进创建参数**（写进去会导致**建容器这一步就失败**），改走 §九 1 的降级方案。
> - 另：专用 bridge 建网时若相邻网段被占（先前探针留下的网络没删）会报 `Pool overlaps with other one on this address space`（403）—— `network.ts` 的幂等创建 + 归属断言正是为了让这类"名字被占了"的情况**大声失败**而不是默默挂上去。

## 五、镜像：三层结构 + toolkit 预烘焙

### 1. 为什么分层（而不是烤成一整块）

改一层不必重建全镜像；且同一只读层在宿主上**只有一份**，10 个容器共用（§九 1 的磁盘账本全靠这个）。

| 层 | 标签 | 内容 | 变更频率 |
|----|------|------|---------|
| **base** | `doubulea/sandbox-base:<ver>` | Node 运行时 + **pin 版本的 pi** + 桥扩展 + 非 root 用户 + 只读层里的 pi 配置 | 跟 pi 版本 |
| **toolkit** | `doubulea/sandbox-toolkit:<ver>` | 验收与常见任务所需的**全部**依赖：`python3` + `pandas` / `numpy` / `openpyxl`、`jq`、常用 CLI | 跟需求 |
| **workspace** | 不是镜像 | 每会话的 work 卷（可写层 + 卷） | 每会话 |

### 2. ★ toolkit 必须构建期预烘焙（这条解的是一个死结）

egress 白名单只放行模型池出口 ⇒ 容器内 `pip install pandas` / `npm i` **必然失败**；而验收场景「分析这份 CSV 出汇总表」**恰恰要 pandas**。

⇒ **判据**：**验收场景与已知任务类型所需的一切依赖，必须在构建期进 toolkit 层；运行期安装一律不做、也不为它开任何出口。**

配套两条：

- **`toolkit` 层要能被验收反向校验**：镜像构建的最后一步跑一遍"依赖自检"（`python3 -c "import pandas"` 等），缺一个就让 build 失败 —— 否则症状是"镜像 build 成功、派活时才发现少个库"，而那时错误只会以一条含糊的引擎 stderr 出现。
- 新增依赖 = **重建 toolkit 层 + 改版本号**，不是运行时补。

### 3. 模型接入（BYOK，指向我方模型池）

- 后端按 `agent.model_id` 解析 → 解密 Provider Key → 以**容器环境变量**注入（`02` §七 2.5）。
- Pi 的 provider 配置走 **只读层里的配置文件 + 环境变量**，不落在 work 卷。
- ⚠️ **Key 进入容器环境是已知暴露面**（`02` §七 原文口径：容器单会话独占 + 无其他出口 + 结束即回收，风险可接受）。本文补两条**硬约束**：
  1. Key **不得出现在 work 卷的任何文件里**，尤其 **Pi 的 session 文件**（它在可写区）。⇒ P0-3-4 必须**实测**：把一轮对话跑完，`grep` 整个 work 卷找 Key 片段；若 session 文件里带上了，**session 目录改挂 tmpfs**。
  2. Key **不得进日志**（含桥的调试日志与引擎 stderr 转发）。日志里那几行按 `backend/src/infra/logger.ts` 的脱敏口径处理，但**新增的容器 stderr 转发路径要单独过一遍**。

#### ✅ 2026-09-26 P0-3-4 落地（本节三条从"设计口径"变成"有落点的约定"）

**① 六个容器环境变量**（后端 `sandbox/spec.ts#SANDBOX_LLM_ENV` 是唯一清单，**零新增宿主 env**）：

| 变量 | 必需 | 内容 |
|------|------|------|
| `DOUBULEA_LLM_API_KEY` | ✔ | Provider **明文 Key**。★ 只被引用、**不落盘** |
| `DOUBULEA_LLM_BASE_URL` | ✔ | 模型池地址，**已按 pi 的语义归一**（见 ③） |
| `DOUBULEA_LLM_API` | ✔ | pi 的 api 名（`openai-completions` / `openai-responses` / `anthropic-messages`） |
| `DOUBULEA_LLM_MODEL` | ✔ | 上游 model id |
| `DOUBULEA_LLM_PROVIDER` | | provider id，缺省 `doubulea`（`SANDBOX_PI_PROVIDER_ID`）⇒ **P0-3-5 用它拼 `--model doubulea/<modelName>`** |
| `DOUBULEA_LLM_LABEL` | | 显示名（进 `models[].name`）。空串 = **不写这个键**（不是写空值） |

支持 `${NAME}` / `$NAME` 环境插值（`dist/core/resolve-config-value.js`），而 **`baseUrl` / `api`

`"apiKey": "${DOUBULEA_LLM_API_KEY}"`，**pi 在请求期自己从 `process.env` 取**。
它顺带让"配置能不能被 agent 读到"这件事不再重要（读到也没有值）。
⚠️ 落点 `infra/sandbox/base/gen-models.mjs`，**由 entrypoint 在播种之后、`exec pi` 之前调用**
（agent-dir 必须可写 ⇒ 不可能烤进只读种子）；脚本末尾有一条**自检**：序列化结果里出现 Key 明文
⇒ `exit(1)` ⇒ **容器起不来**（这条约束刻意做得不靠自觉：破了就是启动失败，而不是某天在某份磁盘上被发现）。
⚠️ 未注入必需项时**跳过**（退出码 0）—— 镜像要能直接 `docker run` 起来手工调试。

**③ ⚠️ `baseUrl` 语义按 api 而不同，归一在后端做**：我方 `llm/client.ts` 是字符串拼接

### 4. 镜像里的具体落法（P0-3-1 落地时补记，含实测到的上游实况）

> 本节记的是**已落到代码里的形态**（`infra/sandbox/**`），不是设计意向。写在这里是为了让
> P0-3-2/3/4 知道"哪些已经定死、别改"，以及"哪几件事必须先实测"。

**① 版本只有一个来源**：`infra/sandbox/versions.mjs`（Node 基线 / **pin 版 pi** / base·toolkit 两条层版本号 / npm registry）。构建入口是 `pnpm sandbox:build` ⇒ `infra/scripts/sandbox-build.mjs`，它把这些值变成 `--build-arg` 与 `-t`。⚠️ 两个 Dockerfile 里这些 ARG **刻意没有有意义的默认值**：手敲 `docker build` 会在第一道断言上大声失败（唯一事实来源 + 显式失败，`06` §六 27）。**改镜像内容 = 改层版本号 + 重建**（§五 2 的纪律）；不这么做，宿主上会同时留着新旧两个 tag，"上次构建的"与"这次跑的"就此分叉。
  ✅ **P0-3-4 把两层都推到 `:2`**（base 新增 `gen-models.mjs` + entrypoint 多一步；**toolkit 一行没改，但它 `FROM` base** ⇒ 一起推）⇒ 已重建、末步自检全绿；`SANDBOX_IMAGE` 应改指 `doubulea/sandbox-toolkit:2`（漏改的症状是"容器里没有 `models.json`、引擎不知道调哪个模型"，**不报错**）。

**② pi 配置 = 「只读种子 + 运行期播种」两步**（★ 构建期实测逼出来的形态，不是设计推演）：

- **种子** = `/opt/pi/agent`（环境变量 `PI_AGENT_SEED`）：镜像里烤好、**根属主 + 0755/0644 ⇒ `agent` 可读不可写**（配置属于镜像、不属于会话）。里面**没有 `auth.json`** —— Key 一律走容器环境变量（§五 3）⇒ "凭据只在进程环境里、不落盘"。⚠️ **P0-3-4 起运行期多一份配置**：播种后由 `gen-models.mjs` 在可写 agent-dir 里生成 `models.json`，**它也只有 `${DOUBULEA_LLM_API_KEY}` 引用**（值在进程环境里）—— 见 §五 3 的 P0-3-4 落地小节。
- **运行期 agent-dir** = `/tmp/pi-agent`（`PI_CODING_AGENT_DIR`）：由 **entrypoint 播种**（`cp -an`，幂等）之后再 `exec pi "$@"`。入口形态变成 `tini -- /opt/pi/entrypoint.sh`。
- ⚠️ **为什么必须两步 —— 构建期实测**：镜像构建时跑 `pi --help` 拿到
  `Warning: Invalid settings file /opt/pi/agent/settings.json: EACCES: permission denied, mkdir '/opt/pi/agent/settings.json.lock'`
  ⇒ pi **读** settings.json 时会**先在同目录加一把锁**，加不上就把整份 settings 判为 **invalid 并整体忽略**（不是"跳过这一项"）⇒ `sessionDir` / `defaultProjectTrust` / `enableInstallTelemetry` 三个键**全部静默失效**，而症状会伪装成"会话写不进去""headless 弹信任提示"，排查方向完全指不到这里。
  ⚠️ 顺带一条教训：base 层那句 `pi --help > /dev/null` **把这条警告吞掉了**，是在 toolkit 自检里复现才看见的 ⇒ 自检里留了一对**反例 + 正例**的断言（拿只读种子当 agent-dir **必须**报 `Invalid settings file`；播种后**必须**不报）。
- 这条同时解释了**为什么不能靠"把种子 chmod 放宽"来修**：P0-3-3 起 rootfs 是只读的（`--read-only`），放宽一样没用 ⇒ **播种那一步在那时必然存在**，本批先把它做实。
- `settings.json` 只放三个键，每个都有理由：

| 键 | 值 | 为什么 |
|---|---|---|
| `sessionDir` | `/tmp/pi-sessions` | agent-dir 里的默认位置在可写区（`/tmp/pi-agent/sessions`）也没问题，但**显式**指到 `/tmp/pi-sessions` 更清楚、且顺带满足 §五 3 的硬约束 1（**Key 不可能落进 work 卷**）。§三 4 已定"会话不持久化、每轮重放我方历史" ⇒ 它本来就是一次性的。⚠️ **P0-3-4 仍要实测**（见 §十三 待决 6） |
| `defaultProjectTrust` | `"never"` | §六 4 坑 3 的"headless 不弹 trust 提示"改用**设置**解决（上游 `settings.md` 明说它**只能在 agent-directory 里设**），比命令行传 `-na` 更不易漏 —— 而且 `/work` 里的 `.pi/` 是**引擎自己会写出来的**（它有 `write` 工具）⇒ 这条不是空防 |
| `enableInstallTelemetry` | `false` | 上游默认 `true` 会做匿名安装/更新上报与 provider 归属头；出口白名单里没有它要去的地方，留着只制造失败噪声 |

**③ 非 root 用户的 uid 固定 10001**：Docker 首次把**空具名卷**挂到已存在目录上时会复制该目录的**属主** ⇒ 镜像里先建好 `/work` 并 `chown agent`，具名卷才天然可写。uid 浮动会在"换台机器"时变成"卷是我的、容器里的 agent 写不进去"（§四 2）。

**④ 入口形态 = `ENTRYPOINT ["/usr/bin/tini","--","/opt/pi/entrypoint.sh"]` + `CMD ["--mode","rpc"]`**（脚本内播种后 `exec pi "$@"`，不残留中间进程）：参数留成 CMD ⇒ **P0-3-2 用 dockerode 建容器时直接覆盖 `Cmd`**（`--model` / `--no-session` …）即可，不必绕过 ENTRYPOINT。`tini` 用于 PID 1 僵尸回收（pi 会反复起 bash）；⚠️ **它必须只透传 stdout/stderr** —— RPC 通道就是 pi 的 stdout，任何给 stdout 加前缀的 init 都会把 JSONL 打坏（§六 1）。

**⑤ toolkit 的两条"刻意不装"**（与"只有两条出口"配套，`selfcheck.sh` 里有**反向断言**守着）：不装 **pip**（装了就会有人去试 `pip install`，然后在 egress 上失败得莫名其妙）、不装 **curl/wget**。依赖自检以 `agent` 身份跑，并**真做一次** csv→汇总→xlsx 往返（只 `import pandas` 会漏掉"只缺 `openpyxl`"那一类）。

**⑥ 实测到的上游/本机实况（不是推测）**：

- pi 的 `engines` 是 **`>=22.19.0`**，`bin` = `pi`（`dist/bundle/cli.js`），MIT。`node:22-bookworm-slim` 当前给的是 **22.23.3**；base 层里有一条断言把"Node 被降到 22.19 以下"变成**构建期失败**（镜像标签是浮动的，不能只靠它）。
- 装 pi 只有 **`npm install -g --ignore-scripts`** 这一条上游写法（上游 `containerization.md` 就是它）⇒ 本仓 pnpm 的 `allowBuilds` 纪律在这里**不适用**：镜像内用 npm 装全局包，不走 pnpm。
- ⚠️ **本机实况**：`docker` CLI 找凭据助手时只看 **PATH** ⇒ 用 `/usr/local/bin/docker` 而 PATH 里没有 `~/.orbstack/bin` 时，报的是 `error getting credentials - err: exec: "docker-credential-osxkeychain": executable file not found in $PATH` —— 一个与"构建失败"毫不相干的错。`sandbox-build.mjs` 已把该目录补进子进程 PATH。

**⑦ 两处留给 P0-3-3 的实测**（同时登记进 §十三 待决 7/8）：

- **代理怎么注入 pi**：上游把 `httpProxy` 归为"**只能在 agent-directory 设置里设**"，而我们的 agent-dir 是**只读烤进镜像**的（②）⇒ P0-3-3 落 egress 出口① 时**必须先确认 pi 认不认 `HTTPS_PROXY` 环境变量**。不认的话只剩两条路：烤一份固定值（**违反"服务间地址唯一事实来源"**）、或启动时写进一个可写的 agent-dir（与 ② 冲突）—— 这是个必须做实验的设计岔路。
  - ✅ **2026-09-26 P0-3-3 关闭（→ §十三 待决 7）**：**pi 认环境变量** —— 源码级证实镜像内 pi 装的是 `undici.EnvHttpProxyAgent`，它自己读 `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`；pi 的 `httpProxy` 设置只是 `process.env.HTTP_PROXY ??= <值>`。⇒ **不必往只读 agent-dir 烤值**，直接走容器 `Env`。落点 = `spec.ts#sandboxEgressEnv()`（`NO_PROXY` 里带上出口②的 `host:port`，否则代理会试图把回调也转发出去）。

  - 🟡 **2026-09-26 P0-3-3 部分收口（→ §十三 待决 8）**：本批已给 `/tmp` 与 `$HOME` 各一个 tmpfs（额度都取 `SANDBOX_TMPFS_MB`），但 **session 文件的实际体积与 Key 是否落进它仍未实测** —— 那属 **P0-3-4**（同一批要做"Key 不进 work 卷 / 不进 session 文件"的实测）。

### 4. ★ 四条坑（必须进 P0-3-5/6 的坑预判）

1. **stdout 必须按 `\n` 切字节流，不许用 Node 的 `readline`。** Pi 官方点名警告：`readline` 会在 `U+2028` / `U+2029` 上当行边界切开，而这两个字符**在 JSON 字符串里是合法内容**。我们的桥是 TS，正好会踩。
2. **完成信号是 `agent_settled`，不是 `agent_end`。** 后者之后还可能跟重试、上下文压缩、跟进动作；拿它当"这轮结束"会**提前落库**，症状是"回答少了一截，但历史里看着是完整的"。
3. **headless 模式不弹 trust 提示** ⇒ 必须显式传 `--no-approve`（或 `--approve`），别指望默认能挡住项目级扩展。
4. **镜像里预烘焙 pin 版本的 pi**，**绝不在运行时 `npm i`** —— 否则直接撞上 egress 白名单（§五 2）。

#### ✅ 2026-09-26 P0-3-5 落地（桥从"设计口径"变成"有落点的实现"）

**① 桥的底座 = 复用容器主进程的 stdio（`attach`），不 `exec`。** 镜像 `ENTRYPOINT` 是
`tini -- entrypoint.sh`，脚本收尾 `exec pi "$@"` ⇒ **pi 就是容器主进程**；P0-3-2 建容器时给的
`OpenStdin: true` / `StdinOnce: false` 正是给这条连接留的。落点 `docker.ts#attachSandboxStdio()`：
`container.attach({ stream, stdin, stdout, stderr, hijack: true })` + **`modem.demuxStream`**。
⚠️ 用 `exec` 会得到"容器里两个引擎"（主进程白等、我们连的那个死了容器还活着），与"会话即容器"直接矛盾。
⚠️ 本仓容器 **`Tty: false`**（P0-3-2 实测）⇒ Docker stdio 是 **8 字节头（流号 + 大端长度）** 的多路复用
格式，**不解复用直接读 ⇒ 每条记录都解析失败**（而报错现场离真因隔着两层）。

**② 分帧只认 `LF` —— 坑 1 的落法。** `jsonl.ts#createJsonlDecoder()`：只按 `0x0a` 切、行尾剥**一个**
可选 `CR`（`0x0d`）、空行不产出、跨 chunk 的多字节字符交 `StringDecoder`；**半条记录上限
`PI_RPC_STDIO_MAX_BYTES`（8MB，代码常量不进 env）** ⇒ 超限抛 `JsonlRecordTooLargeError`
（带上已缓冲字节数）。**`node:readline` 一次都没用**（坑 1 点名的那两个字符在 JSON 字符串里合法）。

**③ 收尾判据 = `agent_settled` —— 坑 2 的落法，外加"订阅先于派活"。** 上游 `docs/rpc.md` 明写
`Subscribe before sending a prompt to avoid missing a fast completion` ⇒ `bridge.ts#armSettled()`
**先造 Promise 并把等待者登记进 `#settleWaiters`，再 `await send(prompt)`**（反过来写，极快的收尾必丢）。
断开回调**先 `decoder.flush()` 处理完残留字节，再宣告 `engine-exited`** —— "说完 `agent_settled` 就退出"
是引擎常态，不 flush 会丢掉最后那一帧。

**④ ⚠️ 配不上号的应答：丢弃 + WARN（与上游刻意不同）。** 上游 `rpc-client.js#handleLine` 把配对失败的
response 混进事件流，我方**不跟**：桥的消费者是 `map.ts`（P0-3-6），收到来源不明的记录只会造出无主的卡。
同理**非 JSON 行 / 非对象记录一律不派发**。⭐ 与 ② 合起来是同一条纪律：**能进事件流的每一条都必须可解释**。

**⑤ 失败与收尾都必须是"可解释的终态"，不许挂住。** `SandboxRpcError.code` 六种
（`closed` / `engine-exited` / `timeout` / `write-failed` / `too-large` / `rejected`）；命令
`RPC_REQUEST_TIMEOUT_MS`(30s)、一轮由调用方给 `timeoutMs`；`abort()` 后给
`ABORT_SETTLE_GRACE_MS`(15s) 让引擎把 `agent_settled` 说完。`close()` **幂等**，只 `detach()`
**不碰容器**（`StdinOnce: false` ⇒ 断开不关容器 stdin，pi 原地等下一次 attach —— 这是"复用容器"的前提）。
⚠️ 刻意**不 `await` drain**：写进 socket 缓冲即可返回（**将来若要发带图片的 prompt（P1），这条要重看**）。

**⑥ 引擎 stderr 进后端日志、绝不进 SSE（§六 3 末行的落法）。** `#appendStderr` 先
`redactSecret(text, secret)` 脱敏 —— secret 取自 `readSandboxLlmApiKey()`（**只读容器 `Config.Env` 里那一条、
唯一用途就是脱敏**，读不到返回 `undefined` 不抛）—— 再保尾 **8KB**（诊断信息永远在最后），默认 `debug` 级。
⚠️ **取不到 Key 时脱敏是"尽力而为"**，不是保证。

**⑦ 建容器时覆盖 `Cmd`（P0-3-4 末行兑现）。** `spec.ts#piRpcArgv(modelName)` 给出
`--mode rpc --provider doubulea --model <modelName> --no-approve`（provider id = `SANDBOX_PI_PROVIDER_ID`；
`--no-approve` 是坑 3 的落法）；`manager.ts` 建容器时传 `cmd: piRpcArgv(llm.modelName)`
（**用 `modelName` 不是 `modelId`** —— 前者才是上游认的名字）。镜像 `CMD` 的默认值**仍然保留** ——
手工 `docker run` 调试照旧能起来。

**⑧ 4 个数值常量（§二 表已登记，零新增 env）**：`PI_RPC_STDIO_MAX_BYTES`(8MB) /
`RPC_REQUEST_TIMEOUT_MS`(30s) / `ACTIVITY_TOUCH_INTERVAL_MS`(30s，`touchSandbox` 的节流) /
`ABORT_SETTLE_GRACE_MS`(15s)。`touchSandbox` 仍是 `last_active_at` 的**唯一写入口**，
桥只负责"有事件就刷、但别每条事件都刷"。

**⑨ 取证状态（⚠️ 按 `06` §六 第 30 条，写清取证方式）**：纯函数 + 协议层确定性核查 **25 项 ALL PASS**
（`/tmp` 临时脚本，**不进仓库**；A 组分帧矩阵含 `U+2028` / `U+2029` 两条反例，C 组用一对内存
`PassThrough` 替掉 docker attach）⇒ 证明的是**协议层**行为，**不是**真 Docker 上的 stdio。
**真链路（`attach` + `demuxStream` 对着真容器）与"真跑一轮对话"仍属人工**，本批**未做**；
`README`「沙箱引擎桥（P0-3-5 起）」一节给了可照抄的手工取证步骤。

### 5. ✅ 2026-09-26 P0-3-6 落地（映射 + 编排：从"有通道"到"能派活"）

**① `map.ts` 只做"形状翻译"，编排层做"累积 + 派发"。** `map.ts` 的输入是一条 `PiSessionEvent`、
输出是 `{events, usage, snapshot?, toolRecord?, known, anomaly?}` —— 它**不认识** DB / Redis /
SSE 连接 / Docker（唯一的运行期 import 是 `orchestrator/chatContext.ts` 的两个纯函数
`summarizeToolInput` / `truncateToolResult`），因此可以**不连任何依赖**地逐条核查。

**② ★ 四类"认识但不发"（每一条都有反例，别顺手补上）。**

| 不发的事件 | 反例（补上会怎样） |
|------------|------------------|
| `agent_end` | 它之后还可能跟自动重试 / 溢出恢复 / 上下文压缩 / 跟进动作 ⇒ 拿它当收尾会**提前落库**（症状："回答少了一截，但历史里看着是完整的"）。真正的收尾判据是 `agent_settled`，而且它由 `bridge.ts#runTurn` **直接消费**，根本不到本层 |
| `message_update` 的 `toolcall_*` | 它是"模型**打算**调这个工具"，而卡片表达的是"这个工具**正在跑**"（`tool_execution_*`）。两处都发会造出**两张卡**，而它们的 `callId` 相同 ⇒ 前端按 id upsert 时状态来回跳 |
| `tool_execution_update`（`partialResult`） | 卡片的取值域是"一进一出"的三态（`RUNNING` → `SUCCESS`/`ERROR`），**没有"中间进度"这一态** |
| `queue_update` / `thinking_level_changed` / `session_info_changed` / `entry_appended` | 会话内部状态类，界面上**没有对应的卡** |

**③ ★ 可解释性 = 两个可核查的出口。** `known: true` = 这条引擎事件在映射表里有条目（含上面
"刻意不发"那一类）；`known: false` = 引擎发了我们**没写过**的事件名（版本漂移）⇒ 编排层只留痕。
另有一条 `anomaly`：**认识这条事件、但它的载荷用不了**（如 `tool_execution_start` 缺
`toolCallId`）⇒ 必须留一条 warn，否则症状是"**引擎明明干活了、界面上什么都没有、日志里也什么
都没有**"（本仓最难查的一类）。两条都不进事件流，区别只在"要不要留痕" —— 这与 §六 4 坑 4
后面那句是同一条纪律：**能进事件流的每一条都必须可解释**。

**④ ⚠️ `tool_execution_end` 不带 `args` ⇒ 同一张卡的两帧必须共用一份摘要。**
pi 的字段表里只有 `toolCallId` / `toolName` / `result` / `isError`，而前端按 `callId` **upsert**
⇒ end 帧若给空摘要，会把 start 帧已经显示出来的"参数"那一行**抹掉**。落法 = 映射器内一小块
`callId → {inputSummary, args}` 记忆（`TOOL_SUMMARY_MEMO_LIMIT = 200` 是**防呆上界**：正常路径
"记一条删一条"，上界只在**工具执行中途被打断**（end 永不到来）时兜底 —— 桥与容器同寿命，
没有上界的 Map 会随轮数缓慢长）。同一个记忆顺带给**落库那份**补 `arguments`（完整入参
**只留档、不上线**：SSE 帧由 `toolCallRecordSchema.omit({arguments:true})` 派生 ⇒ 两处**只差
这一个字段**）。

**⑤ 编排循环（`orchestrator/taskAgent.ts`）的三条实现判据。** ① **订阅必须早于派活**
（`onEvent` 挂在 `runTurn` **之前** —— 与 §六 4 坑 2 的"订阅先于派活"是同一条推理）；
② **累积同步 / 发帧串行**（桥的事件回调是**同步**的、而 `emit` 是**异步**的 ⇒
`assistantText` / `toolRecords` / `usage` 在回调里**同步**记，"发出去"进一条串行队列；
`void emit(...)` 会同时丢掉帧顺序与错误）；③ **usage 口径 = 同一 turn"覆盖"、跨 turn"相加"**
（引擎的 `message_update.usage` 是 **latest cumulative** ⇒ 后一帧盖掉前一帧。⚠️ **P0-3-12 订正**：
这里原先只写了"覆盖不是相加"，**只对了一半** —— 一个 turn = **一次模型请求**，"覆盖"只在**同一个**
turn 内成立；多轮派活落在同一条账上时要**相加**（`turn_start`/`turn_end` 划边界 + `sumUsages`）
⇒ 照原口径实现时多轮工具循环**只留了最后一轮的 token**，实现见 §十「✅ P0-3-12 落地」）。

**⑥ ★ 落库判据 = "这一轮真的发生过"，唯一例外 `lock-lost`。** 与 `chatBot.ts` 同一条，
且实现在 `orchestrator/persist.ts`（**只留一处**）：能落库的只有"派过活"与"用户**排队时**
点了停止"两种；"没发生过"（拿不到沙箱 / 本轮模型不可用 / 建容器失败）**不落库** ——
留一条"只有问题、永远没有答案"的记录会让用户以为自己问过却被丢了。⚠️ `lock-lost` ⇒
一个字都不写（那时可能已有**另一个流**在写同一份历史）。

**⑦ 失败码 → 出口：两个纯函数，别在映射层再发明一套**（P0-3-5 传下来的口径 ②）。
★ **两者的出口其实是同一个：流内 `error{code}` 帧** —— 这点容易想错，P0-3-6 专门核实过：
`producer` 是 `streamChatReply` 在 **`reply.hijack()` 之后**才调用的（那里要先把互斥锁 / 心跳 /
停止轮询挂上）⇒ 编排层抛的 `AppError` 一定被出口层的 `catch` 接住、走 `SseChannel#fail`
⇒ `error` 帧（HTTP 早已是 200 的 SSE）。**JSON 信封只属于"在 `streamChatReply` 之前就抛"的
那一类**（未登录 / 参数 / 会话不是我的 / 会话只读 / 缺凭据 —— 全在 `assertConversationSendable`
里），这与 `chatBot.ts` 的并发闸 `AppError.busy` 是**同一条路径**。于是"选哪个工厂"的唯一作用
= **选 `error` 帧里的 `code`**（前端按它取文案）+ `message`：
`QUEUE_TIMEOUT`⇒`BUSY` / `NOT_CONFIGURED`⇒`INTERNAL` / `MODEL_NOT_AVAILABLE`⇒`CONFLICT` /
`CONVERSATION_NOT_FOUND`⇒`CONFLICT` / `CREATE_FAILED`⇒`INTERNAL`；
引擎侧 `engine-exited`/`closed`/`rejected`⇒`UPSTREAM_ERROR`、`timeout`⇒`UPSTREAM_TIMEOUT`、
`aborted` **不可达**。
⚠️ **pi 的原文只进日志、绝不进 SSE**（`02` §十）；⚠️ `ABORTED` **不是失败**而是"用户在排队时
点了停止" ⇒ 按**中断**收尾（落库 + `done{STOPPED}`），否则用户自己的动作会被显示成系统故障。

## 七、MCP：走后端代理（本轮定案）

### 1. 定案与它的边界

**TaskAgent 可以绑 MCP server，但容器内的引擎永不直连 MCP。** 所有 MCP 调用经一条**容器 → 后端**的内网通道，由后端**带着该会话发起者的凭据**去调，结果回传容器。

**这条路线顺带把三扇原以为要打开的门重新关上了**：

| 原以为要开的门 | 走后端代理后 |
|----------------|-------------|
| 凭据进容器 | ❌ 不需要 —— **凭据全程在容器外**（比直连更好） |
| egress 上按会话开公网洞 | ❌ 不需要 —— 容器→后端是**内网**；公网出口仍然只有模型池那一条 |
| 放弃危险判定与确认流 | ❌ 不需要 —— 调用必经后端，**判定与确认重新变成拦得住的** |

### 2. 调用链

```
Pi 里的 mcp_* 工具（由桥扩展注册）
  → handler 里 fetch POST {SANDBOX_BACKEND_URL}/api/sandbox/mcp/call
     头：X-Sandbox-Token: <per-container token>
     体：{ serverAlias, toolName, arguments }
  → 后端（沙箱代理 listener）
     a. 校验 token → 解析出 {conversationId, userId, agentId}
     b. 用 serverAlias 换回 serverId（§七 4）
     c. 校验：该 server 是否真的绑在 agentId 上（防越权，§七 6）
     d. 危险判定（§七 5）→ 需要则走确认流
     e. 调既有 executeMcpToolCall（P0-2 的编排，带 **userId 的凭据**）
     f. 结果原样回给扩展
  → 扩展把结果交回 Pi → 模型继续
```

★ 关键复用点：**`e` 那一步就是 P0-2 已经做完的那个执行器**（凭据注入 / 危险判定 / elicitation / 结果整形全都在里面）。§七 只需要"把入口接上"，**不重写任何 MCP 逻辑**。

### 3. 三条通道要素

| # | 要素 | 落法 |
|---|------|------|
| ① | **内网通道** | §四 3 的出口② |
| ② | **per-container token** | 建容器时 `randomBytes(32)` → 同时写进容器环境变量（`SANDBOX_TOKEN`）与 Redis `sandbox.token:{token}` → `{conversationId, userId, agentId}`。**TTL = 容器寿命**，容器回收时显式删。⚠️ 没有它，**任何容器都能冒充某个会话去调后端**（还能顺带用别人的 MCP 凭据） |
| ③ | **Pi 扩展 `mcp-bridge`** | 预烘焙进 base 层。启动时拉工具清单（下面 4）、注册工具、`handler` 里做上面那次 `fetch`。⚠️ 扩展**不含任何凭据**，它只有一个 token 和一个内网地址 |

### 4. 工具清单下发与命名（含唯一反查点）

- 容器启动后，扩展调 `GET /api/sandbox/mcp/tools` ⇒ 后端按 `agentId` 的绑定拉各 server 的 `tools/list`（**走 P0-2-5 的缓存**）⇒ 返回**已重命名**的工具清单。
- **命名规则**：`mcp_<alias>_<toolName>`，其中 `alias` 由后端**按会话内序号分配**（`s1` / `s2` …）。
- 后端同时把映射 `{ s1 → serverId, s2 → serverId, … }` 写 Redis `sandbox.mcp:{conversationId}`。
- ★ **唯一反查点**：桥（`map.ts`）收到容器侧的 `tool_call` 事件后，**用这张映射**把 alias 解回 `serverId` 填进 `tool_call.serverId`。
  ⚠️ **不要靠"工具名 slug"反推 server** —— slug **刻意不唯一**（P0-2-11 已定案），反推会指错 server，而症状只是"卡片上显示的 server 名不对"，不会报错。alias 由本次会话分配、映射由后端持有，唯一且可回滚。
- **一张卡**：容器侧事件与代理侧**只发一条 `tool_call`**（以容器侧事件为准）。代理端点**不额外发卡**，它只在需要时发 `confirm`（§七 5）。

### 5. 危险判定落在哪 —— ★ 多了一处落点

`02` §9.9 的判定原本**只算在 `toOpenAiTools`**（把 MCP 工具转成 LLM 工具时，供 ChatBot 用）。**容器路径不经过那一步**（Pi 的工具是扩展注册的）。

⇒ 代理端点（`proxy.ts` 的 `d` 步）必须**独立判一次**：

- **复用 `shared` 的危险判定纯函数**，`02` §9.9 那张判定表仍然是唯一契约。
- **不要**把判定搬出 `toOpenAiTools`、也**不要**在代理侧另写一份 —— 两处调用**同一个纯函数**，各自在自己的入口调。
- 判决与 ChatBot 完全一致：**只有 `readOnlyHint === true` 且未声明 `destructiveHint === true` 才安全，其余（含读不出注解、非布尔值）一律进确认**。

### 6. 安全约束（三条，都要在代理端点里做）

1. **token ⇒ 会话是唯一身份**：`conversationId` / `userId` / `agentId` 全从 token 解析，**请求体里不带**（带了也不信）。
2. **只能调"这个 agent 绑定的" server**：`serverAlias` 换成 `serverId` 后要校验绑定关系。否则一个会话能拿 token 去调**平台上任何** MCP server。
3. **危险调用串行化**：同一会话同时来的危险调用**串行**（后一个等前一个结束）或直接拒绝。理由：确认槽 `chat.confirm:{id}` 与 `/active.pendingConfirmId` 是**单槽**的，一轮里并行问两次会让后一个覆盖前一个（`orchestrator/sse.ts` 已有注释记着这个坑）。

### 7. 这条路的两个好处，值得单独记住

- **对用户**：TaskAgent 与 ChatBot 的 MCP 体验**一致** —— 同一套凭据页、同一张确认卡、同一族错误文案。用户在两边看到的不是两套东西。
- **对平台**：MCP 的**所有**安全能力（凭据不落容器、危险判定、确认、审计留痕）都还在，因为它们全在**调用必经的那一段**上。

### 8. ✅ 2026-09-27 P0-3-9b 落地（代理端点本体 + 容器侧扩展真实现）

**一句话定案**：★ **容器里的引擎永不直连 MCP** —— 所有调用经内网 `POST /api/sandbox/mcp/call` 由后端带**会话发起者**凭据代调 ⇒ 凭据不进容器、公网出口仍只模型池、危险判定拦得住。（本节 1~7 的**设计一字未改**，9b 是**落地**。）

**★ 本批只"把入口接上"**：端点算完身份 / 越权 / 危险判定之后，调的是 **P0-2 已有的 `executeMcpToolCall`**；另外三处（`isDangerousTool` / `toDescription` / `askConversation`）也都是复用**同一个实现** ⇒ **一行 MCP 协议代码都没写**。

**新增 3 个文件**：`sandbox/token.ts`（per-container 令牌）、`sandbox/mcpMap.ts`（`alias ⇄ serverId` 的**唯一**存与取 + 命名与反查纯函数）、`sandbox/proxy.ts`（两个端点 + 危险判定的**第二落点** + 按会话串行）。

**两条端点**：`GET /api/sandbox/mcp/tools`（清单）与 `POST /api/sandbox/mcp/call`（调用）—— **都不套统一信封**（失败形态 `{error:{code,message}}`），**404 例外**（"路径写错"由 listener 的 `setNotFoundHandler` 统一给信封，与"端点自己判定的失败"是两件事）。⚠️ 两条端点**不在公网 listener 上**，只在出口② 那个独立实例上。

**落地口径（对着上面 1~7 逐条）**：

| 设计条目 | 落地做法 |
|---|---|
| 3 ② per-container token | `sandbox/token.ts`：`generateSandboxToken` / `bindSandboxToken` / `resolveSandboxToken` / `revokeSandboxToken`；★ **签发点在建容器之前**（`manager.ts`；容器一起来 pi 就加载扩展并拉清单，晚一步就是一次 401，而扩展那边看起来像"后端不可达"）；两个方向同写同删（`sandbox.token:{token}` + `sandbox.convToken:{conversationId}`，Redis 没有"按值查键"所以必须两个键）；**建失败与回收都撤销** |
| 3 ③ 扩展 `mcp-bridge` | 由**空壳 → 真实现**（`infra/sandbox/base/pi-agent/extensions/mcp-bridge/index.ts`）；`session_start` 拉清单 + `registerTool`；handler 里做那次 `fetch`。⚠️ 扩展仍**不含任何凭据**，只有 token 与内网地址 |
| 4 清单与命名（唯一反查点） | `ensureSandboxMcpCatalog()` = "**已发布就原样读回**"（每个容器一份**快照**）；`GET /tools` 与编排层预热**共用**它 ⇒ 容器注册的名字与后端反查用的表**必然同源**（两边各算一次会有 alias 漂移窗口，症状只是"卡片上 server 名不对"、不报错）；别名 `s1`/`s2`… 按 `(name, id)` 升序分配；★ **唯一反查点** = `mcpMap.ts#resolveSandboxMcpTool`，⚠️ **不靠 `slug` 反推**（它刻意不唯一） |
| 5 危险判定的第二落点 | `proxy.ts` 独立判一次，但**复用同一个 `isDangerousTool`**（`02` §9.9 的表仍是唯一契约）+ 走 §八 2 的 `askConversation`；⚠️ **`NO_CHANNEL` 与 `REJECTED` 必须分得开**、`ChatStoppedError` **接住但不并进 `REJECTED`**，安全默认**拒绝执行** |
| 6 ① token ⇒ 唯一身份 | `conversationId`/`userId`/`agentId` 全从令牌解析，**请求体里不带**（带了也不信） |
| 6 ② 只能调"这个 agent 绑定的" server | 越权 ⇒ **403**（`serverAlias` 换成 `serverId` 后校验绑定关系） |
| 6 ③ 危险调用串行化 | `proxy.ts#withConversationSerial`：**只串危险那一段**（非危险调用不占队）；队尾是自己是才 `delete`（否则 `Map` 会长住每个会话 id） |

★ **4xx 与 200 的分界线 = 「能不能调」vs「调了之后怎样」**：方法 / 令牌 / 体 / 别名 / 归属 / 清单属**状态码**（401 / 400 / 404 / **403** / 409），而"用户没确认 / 凭据没配 / 上游挂了 / 工具自报错"属**响应体 `{isError, text}`（恒 200）** —— 后者模型必须读得到才能向用户解释，做成 4xx 只会让它看到一句"请求失败"。

**容器侧扩展的三条上游约束**（来自 pi `docs/extensions.md`；⚠️ 本仓 `infra/**` 不在任何 tsconfig 的 include 里，**改扩展靠上游文档 + `npm view` 查依赖，没有类型可查**）：① **工厂里不许起进程 / socket / 定时器**（`pi list` 会加载扩展但不启动会话）⇒ 只读 env、只挂 handler，网络请求全在 `session_start`；② ★ **`throw` 才是"这一趟失败了"**（上游原话："Returning an object does not mark it as an error."）⇒ 后端回的 `{isError:true, text}` **必须抛**，否则卡片显示成功、模型也看不出失败；③ **不调 `ctx.ui.notify`** —— RPC 下的 UI 通知走另一条子协议，而我们的桥**没接它**（只会多一条"不认识的事件"）⇒ 报错只走 **stderr**（后端把容器 stderr 收进日志）。

**★ 一处对本文的订正**：3 ② 原写"**TTL = 容器寿命**"，实现改成 **滑动 12 小时**（`SANDBOX_TOKEN_TTL_SEC = 12 * 3600`，同 `sandbox.mcp:{id}` 的 `SANDBOX_MCP_MAP_TTL_SEC`）—— 理由：Redis 的 TTL 是**绝对过期**，而"容器寿命"没法直接表达；滑动续期让**活跃容器**的令牌只要在用就不会过期，容器真被回收时再**显式 `revokeSandboxToken`**。⚠️ 续期失败**只 warn**（不该让一次本来能跑的调用失败）。

**⚠️ 镜像层 → 3（`base` / `toolkit` 两条版本线都 +1）**：`:2` 里的扩展只是个**空壳**，宿主上留着旧 tag 的症状最隐蔽 —— "模型从来不调 MCP 工具"，而后端日志**一条错都没有** ⇒ 端测前**必须** `pnpm sandbox:build` 重建（本机换源）。

**未变的契约**：两条端点的路径 / 请求体形状 / 身份来源 / 401 不回显细节 —— 一条都没改（本批是**落地**，不是改约定）；§七 5 的危险判定表**一字未动**（第二落点用的是**同一个纯函数**，判决口径逐字一致）。

## 八、跨请求提问原语（★ 结构性增量）

### 1. 问题：现在没人能从"另一个请求"提问

现状（P0-2-10 落地形态）：

- `awaitConfirm` 是 **`SseChannel` 的实例方法**，用 `this.#conversationId` 读写确认槽并往**这条响应流**里写 `confirm` 帧。
- `activeChannel` 是 `streamChatReply()` 里的一个**局部 `const`**。
- 跨请求能拿到的只有 Redis 上的三样：`chat.stop:{id}`（信号）、`chat.confirm:{id}`（**应答槽**）、`chat.active:{id}`（快照）。

⇒ **`/confirm` 能跨请求"回答"，但没有任何东西能跨请求"提问"。** 而 §七 的代理端点正好是一条**独立的 HTTP 请求**，它需要向会话的 SSE 流提一个问。

### 2. 落法：活跃通道注册表（**只做取实例，不做判据**）✅ 2026-09-26 P0-3-6b 已落地

- `orchestrator/sse.ts` 增一个模块级 `Map<conversationId, SseChannel>`：`new SseChannel(...)` 之后**注册**，`dispose()` 所在 `finally` 里**注销**。
- 增一个导出：`askConversation(conversationId, question): Promise<ConfirmDecision>` —— 实现就是"查表 → 调该通道的 `awaitConfirm`"。
  ⚠️ **落地时把返回类型改成了四值**：`AskConfirmOutcome = ConfirmDecision | 'NO_CHANNEL'` —— 理由见 6 ①（下同）。
- ⚠️ **两条纪律，缺了会出静默坏事**：
  1. **注册表不是"谁是主人"的判据。** 主人判据仍然是 Redis 的活跃流锁（`chat.active:*`）。注册表只回答"这个 id 的通道实例在不在本进程里"，两者**不要混成一个真相源**。
  2. **查不到通道 = 危险调用直接拒绝执行**（回一条"无法确认 ⇒ 未执行"的结果），**不是静默放行、也不是当成功**。安全默认拒绝：查不到只可能是因为流已经结束（那这轮本来也该结束）。**非危险工具不依赖注册表**，照常执行。
- ⚠️ **单实例限制**：注册表是**进程内**的。若将来横向扩容，容器与 SSE 流可能不在同一实例上 ⇒ 必须先把 §四 3 的后端地址与本节一起改成"按会话路由"。⇒ 与 §九 1 的"配额作用域 = 单实例"**同一条扩容前提**，写在一处。
  ⚠️ 补一句落地时的判据：**扩容时不能只是把 `Map` 换成 Redis** —— "提问"的重心是"往哪一条响应流写 `confirm` 帧"，那不可能跨进程。

### 3. 这一个原语服务两类发起者

| # | 发起者 | 提问内容 | P0 范围 |
|---|--------|---------|---------|
| ① | **平台**（沙箱 MCP 代理，§七 5） | "任务里即将执行"某危险工具，确认/取消 | **P0-3 必做**（`01` 决策 22 的强制确认在容器路径上的唯一落点） |
| ② | **引擎**（Pi extension UI） | 引擎主动问：要不要这么干 / 选哪种方案 | 见 4 |

### 4. `source` 不新增枚举值（刻意）

`confirm` payload 的 `source` 仍是 `PLATFORM` / `SERVER` 两值：**沙箱代理发起的确认 = `PLATFORM`**（它确实是"平台在强制确认一个危险工具"）。

⚠️ **不要为了"读起来更清楚"而加第三个值 `SANDBOX`**：`03` §六 已定"`source` 只决定那行说明文案、不是两种卡片"，而"这是任务页还是对话页"前端**本来就由 Agent 类型知道**。加一个值 = 一次无收益的契约增量 + 前端多一条永不走到却必须维护的分支。

### 5. 引擎提问与"逐工具确认"的关系（一句话判据）

> **只有"跨出容器边界"的动作才需要确认卡。**

- 容器内的 `bash` / `read` / `write` / `edit` —— 只碰**自己的临时工作区**，破坏面已被容器边界框死（只读 rootfs + 临时卷 + 两条出口白名单 + 结束即回收）⇒ **不做**逐工具确认。（另外两条实情：Pi 没有内置权限系统，拦不住；沙箱里几乎每个动作都是写操作，逐个弹卡等于把"派活"退化成"逐步审查"。）
- 经 §七 出去的 MCP 调用 —— **跨边界，要走**确认（`01` 决策 22）。
- 将来新增任何"能碰到容器外"的动作，照这条判据补确认，**不必在沙箱里另造一套**。

★ 这条判据同时解释了"引擎主动提问"为什么和"逐工具确认"不一样：**前者是引擎主动发起的请求（有通道就接得住），后者是平台去拦引擎（拦不住）**。两者长得像，机制完全不同。

### 6. ✅ 2026-09-26 P0-3-6b 落地（三处实现口径 + 一条仍未接线的路）

落点只有 `backend/src/orchestrator/sse.ts` 两处增量：模块级 `Map<conversationId, SseChannel>`（构造后**登记**、`dispose()` 所在 `finally` 里**注销**）+ 导出 `askConversation()`。**零新增 env、零新增常量、零 HTTP 面。**

| # | 口径 | 理由（不这么做会怎样） |
|---|------|----------------------|
| ① | ★ 出口是**四值**：`AskConfirmOutcome` = `ConfirmDecision` 加 `'NO_CHANNEL'` | 上面 2 的纪律 ② 只说"要拒绝"，没说"**怎么把拒绝表达出来**"。若把它折进 `REJECTED`，回给模型的话就变成"用户已取消"——把**我们的状态问题**说成**用户的决定**，模型会向用户复述一件没发生过的事。四值让"没问成"是一个**独立的、必须显式处理**的结局 |
| ② | **注销按身份撤销**（表里那个位置还是自己时才删） | 锁有 TTL（`sse.ts` 文件头 ③）⇒ 锁一过期，同一会话就可能有**第二条流**拿到锁、建出第二个通道并覆盖登记；此时老通道的 `finally` 若直接 `delete(id)`，删掉的是**新通道**的登记 —— 此后该会话的危险工具会**全部**答 `NO_CHANNEL`，**没有任何报错**。与 `releaseConversationLock` 的"按归属释放"是同一条纪律 |
| ③ | **中断照旧抛出**（`ChatStoppedError`，= `signal.reason`），不并进那四种结局 | 用户停止 / 断连 / 锁丢失是"**这一轮结束了**"，不是"确认的结局"（与 `ConfirmDecision` 的既有口径逐字一致）⇒ `askConversation` **不接**，由代理端点自己接住、按"未执行"回给引擎（属 P0-3-9b） |

**顺序也有一条**：登记紧跟构造（在 `channel.start()` 之前）、注销排在 `dispose()` **之前**；两者都是同步调用、中间没有 `await` ⇒ **不存在"表里有、通道已死"的可观测窗口**（`askConversation` 里那句 `channel.closed` 因此只是纯保险，失败方向也只能是"拒绝"）。

⚠️ **仍未接线的一条路：发起者 ②（引擎主动问）**。那类请求走 pi 的另一条 RPC 子协议（**RPC-only events**，不是 `AgentSessionEvent`），而 `bridge.ts` 对"非 response 记录"一律扇给映射层、映射层只把它算成 `known:false`（**只留痕、不派发**，是 P0-3-6 刻意定的口径）⇒ **本批交付的是一个"有通道就接得住"的原语，还没有任何东西把引擎的提问递进来**。要接通需另立批次（谁接住它、用什么事件名，本仓目前没有契约）。P0 范围内**必须**的只有发起者 ①（平台强制确认），它属 P0-3-9b。

## 九、生命周期：回收 / 排队 / 自愈

### 1. 磁盘账本（`01` 需求 29 的"省空间"半边）

- **只读层全机共用一份**：Docker 分层天然就是"共享书架"，10 个容器跑同一镜像，磁盘上只读层只有 1 份，每个容器多一个很薄的可写层 + 一个 work 卷。
- **可写层必须有配额**（§二 `SANDBOX_WORK_VOLUME_MB`）。⚠️ 若 `--storage-opt` 实测不支持，**降级方案必须明确写成"定期 `du` 巡检 + 超限告警 + 人工介入"**，不要假装有配额。
  - ✅ **2026-09-26 P0-3-3：降级方案已落地**（实测 `--storage-opt size=` 被本机守护进程直接拒绝，且它管不到具名卷，见 §四 3 与 §十三 待决 2）——`reaper.ts#auditWorkVolumes()` 每轮对账时读一次 `GET /system/df`（**一次拿全场卷体量**，不逐卷 inspect）→ 按 label 过滤出"我们的" → `findOversizedWorkVolumes(volumes, limitMb)` → **超限只 WARN、不删**；读数进 `ReaperStats.lastVolumeAudit`。⚠️ 无 `RUNNING` 行时**直接跳过**（省一次 `df`）。
- **产物立刻出容器**：一轮结束就扫卷 → 传对象存储 → （本轮结束时不删容器，但）容器回收时产物已经在外面。**产物留在容器里的时间是分钟级**。
- ⚠️ **两个最经典的静默泄漏**（进 P0-3-2 坑预判）：
  1. **`docker rm` 必须带 `-v`** —— 不带就会留下匿名卷，越堆越多，是 Docker 上"磁盘悄悄满"的头号原因。**每个容器用到的卷都具名**（少一次"这卷是谁的"的考古）。
     - ⚠️ **2026-09-25 P0-3-2 实测更正**：**`docker rm -v` 删不掉具名卷** —— `-v` 只清匿名卷，具名卷（我们的 work 卷就是具名卷）**会留下来**。所以"靠 `-v` 顺手清干净"这条**不成立**，回收**必须两步**：先 `rm` 容器、再显式 `volume rm`。这条已在 `manager.ts#recycleSandbox` 落地（`06` §五 P0-3-2 决定六同款记录）。
  2. **`docker build` 的 layer cache 只增不减** ⇒ 每个镜像 tag **只留 pin 的那一个** + 定期 prune。

### 2. ★ 孤儿回收器（**不是优化，是必需项**）

后端启动时（+ 周期）扫一遍带 `doubulea.role=sandbox` label 的容器与卷，把**没有对应活会话**的清掉。

- 为什么必需：**后端崩一次就必然留下容器**。没有清道夫它们会一直占着槽位不释放 ⇒ **10 个并发名额被静默吃掉**，症状是"**明明没人用却在排队**"。这是最容易被当成玄学 bug 的一处。
- 对应地，**排队队列项也要能自愈**：Redis 里的排队项对应的是前端那条 SSE 流，流一断排队项就是孤儿 ⇒ 要 TTL + 启动时清理。
- ✅ **P0-3-2 落地（`backend/src/sandbox/reaper.ts`）—— 以及"两条判据为什么要分开"**：
  · **启动对账 `reconcileOnBoot()` 清掉全部**（**不是**"清没有活会话的"）：理由与 §九 4 同源 —— **引擎是后端进程的子进程**，进程一死容器就没有对话者了，那是一个"活着但没人能跟它说话"的容器，复用只会得到"发消息没反应" ⇒ **一律重建、不复用**。顺带一个免费收益：名额册是**进程内**的、启动时天然为空 ⇒ "清空容器"让**账面与实际在重启后自动一致**。
  · **周期对账 `reapOrphans()` 只清"没有活会话的"**：判据 = 会话 `ACTIVE` **∩** 账本有活体行（`RUNNING`，或 `SANDBOX_CREATE_GRACE_SEC` 宽限期内的 `CREATING`）。**容器与卷共用同一个活会话集合** —— 给容器一套判据、给卷另一套，迟早分叉出一个"容器删了卷留着"的**稳定泄漏**；特别地，**标签读不出来的对象也会被删**（它们占着磁盘与名额，却谁也认领不了）。
  · **空闲回收 `reapIdleSandboxes()` 是另一条路**：判据 `sandboxes.last_active_at < now - SANDBOX_IDLE_TTL_MIN`。一个连跑 40 分钟、期间一直在输出事件的容器**不会**被回收（每来一个事件都会 `touchSandbox()`）；建出来就没动静的才会 —— 那正是要的语义。⚠️ **该列必须由 JS 侧写**：本仓 PG 会话时区非 UTC 时 Prisma 对 `timestamptz` 有偏移（`02` §3.1 的"已知问题"），写偏了阈值就整体偏移一个时区。
- **实测（真 Docker 29.4.0 + 真 PG + 真 Redis，P0-3-2）**：预置 2 容器 + 2 卷（一个指向真会话、一个指向不存在的会话）+ 一条超宽限期的 `CREATING` 行 + 一个过期排队项 ⇒ 启动对账 `containers 2/2`、`volumes 2/2`、`removalFailures 0`；紧接着一轮周期对账 `removedContainers 1 / removedVolumes 1`（★ **真会话那个被正确保留**）、`staleCreatingRows 1`、`queuePruned 1`；空闲回收 `candidates 1 / reaped 1`；终态带 label 的对象**全零**。⚠️ 取证方式是**脚本驱动模块**（P0-3-2 没有任何入口能创建沙箱），证明的是"模块在真 Docker 上的行为"，**不是**端到端功能。

### 3. 并发配额的作用域（★ 现在就把语义写死）

- **`SANDBOX_MAX_CONCURRENCY` 的语义 = "单个后端实例"**，不是"整个平台"。
- P0 是单机单实例 ⇒ 两者是同一件事、看不出差别。但**一旦横向扩容**：计数在 Redis 是全局的，而**容器是本机的** —— 槽位可能由实例 A 持有、容器却在实例 B 的宿主机上，B 挂掉时 A 手里的槽位不会自动释放。
- ⇒ 与 §八 2 的注册表同一条前提，写进 `02` §七：**扩容前必须先改配额作用域与孤儿回收归属。**

### 4. 三种"高可用"档位与我们的取舍

| 档 | 内容 | P0 取舍 |
|----|------|---------|
| **1 · 进程级自愈** | 不恢复运行中的沙箱，靠既有口径兜底（"事件即真相 + 历史读库" ⇒ 后端重启 / 容器意外退出后用户刷新看到历史，那一轮标失败或中断，**直接重发**）；孤儿回收器；排队项 TTL | **必做** |
| **2 · 会话级续跑** | 持久化 Pi session + work 卷，从中断处接着跑 | **不做**，写成路径。理由：立刻与"省磁盘 / 控复杂度"打架，而 TaskAgent 任务通常是分钟级、重跑成本可接受；"会话即容器 + 空闲 30min 回收"这个设计**本身就承认状态是易失的**。真要做，正确做法是"**用我们自己的历史重放给一个新容器**"（历史本来就要存），不是持久化引擎状态 |
| **3 · 主机级** | 单机 docker daemon，主机挂了沙箱全丢；`docker-socket-proxy` 本身也是一个单点 | **写清边界，别假装**。P0 是单机部署 ⇒ 在 `02` / `README` 里作为**已知边界**写明，**不要**在 P0 引入集群调度（会把 P0-3 工期直接翻倍） |

★ **面向用户的"高可用"主要靠"快速让出槽位"，不是靠扩容。** 上限 10 打满时不是报错，而是**排队 + 位次可见**（`01` 需求 29、`03` §六 的 `queued` 卡）。所以真正要盯的指标是"**回收是否可靠**"和"**排队位次是否算得准**"，比"能不能横向扩容"重要得多。

### 5. 停止（P0-3-8）✅ 2026-09-26 已落地

`POST /api/conversations/:id/stop`（`02` §4.8 已定：**不设独立 tasks stop 端点**，按会话类型内部分流）的沙箱分支：

1. 向引擎发中断（`session/cancel` 语义）→ 等 `agent_settled` 或超时。
2. **已生成内容照常落库**（`01` 决策 15：停止即中断，已生成部分保留，可直接追问）。
3. 产物收集**仍然执行**（用户点停止通常正是因为他已经拿到想要的东西了）。
4. 容器**回收**（§九 2 的具名卷一并 `-v` 删）。

## 十一、产物收集与交付

### 1. 扫描判据 = "**这一轮新出现或修改的**文件"

容器启动时对 work 卷做一次基线快照（路径 + mtime + size），一轮 `agent_settled` 后对照 ⇒ **只上报变化的**。

⚠️ 不做基线对照的话，第二轮会把第一轮的产物**再报一次**，症状是"产物列表里同一个文件出现两份、时间还不一样"。

### 2. 过滤规则（都要有日志，不静默丢）

| 规则 | 处理 |
|------|------|
| 隐藏文件 / 隐藏目录（`.` 开头） | 跳过 |
| 超过 `ARTIFACT_MAX_FILE_MB` | 跳过 + 告警 |
| 总数超过 `ARTIFACT_SCAN_MAX_FILES` | 截断 + 告警 |
| 引擎自身的工作文件（按目录白名单/黑名单排除） | 跳过。⚠️ 名单要**显式列在配置里**，不要写死一串 magic path |

### 3. 上传与落库

工作卷扫 → 对象存储 → 建 `artifacts` 行 → 发 `artifact` 事件（`shared/src/sse.ts` 已有形状）。**顺序不能反**：先建行会出现"列表里有个文件、点下载才发现对象不存在"。

### 4. 保留期（★ 本文第一次定这个数）

- 产物文件：`ARTIFACT_RETENTION_DAYS`（默认 **7 天**），过期由**周期性清理**删除（对象存储 + `artifacts` 行）。
  ⚠️ 不定这个数，**产物就是一个只涨不跌的口子** —— `01`/`02` 只定了下载链接 30min，那是"链接"的时效，不是"文件"的寿命。
- 下载链接：`ARTIFACT_DOWNLOAD_TTL_MIN`（**30 分钟**，沿用 `02` §4.8）。
