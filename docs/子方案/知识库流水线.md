## 二、参数总表（施工唯一依据）

|------|--------|----------|------|
| `chunk_size` | **512** | **字符（近似）** | 非 token。bge-m3 上限 8192 token，512 字符远在其内，安全 |
| `chunk_overlap` | **64** | 字符 | 约 12.5% 重叠，防止边界切断语义 |

| `retrieval_config.score` | **0.3** | 0–1 | 向量路相似度下限（cosine 相似度） |
| `retrieval_config.mode` | `HYBRID` | `HYBRID` \| `VECTOR` \| `FULLTEXT` | **B9 定案**：三值枚举，默认 HYBRID |
| `rrf_k` | **60** | 常数 | RRF 平滑常数，见 §六 |
| `rrf_vector_weight` | **1.0** | ≥0 | 向量路权重 |
| `rrf_fulltext_weight` | **1.0** | ≥0 | 全文路权重 |
| `empty_text_threshold` | **50** | 字符 | 解析后正文字符数低于此值 → FAILED("疑似扫描件")，见 §五 |

| `PIPELINE_CONCURRENCY` | **2** | 并发任务数 | 02 §二已定；onnx 走 worker_threads |

## 三、文本流水线总览

```
上传（multipart）
  │
  ├─ ① 入库登记：documents 行 status=PARSING，原始文件 → S3（file_key）
  │    content_hash = sha256(文件字节) —— 覆盖重建的判重依据
  │
  ├─ ② 入队：Redis List  push pipeline:jobs  {docId, kbId, contentHash, mode: NEW|REBUILD}
  │       ⚠️ `contentHash` 是 P0-1-17 的实现增量：下面的幂等规则要求比对它，
  │          而 worker 手里只有一个"当前值" ⇒ 不带投递时刻的 hash 就无从判断"变过没有"
  │       ⚠️ 队列键默认 `pipeline:jobs`，可用 `PIPELINE_QUEUE_KEY` 换（隔离共用同一 Redis 的消费方）
  │
  └─ Pipeline Worker（进程内，PIPELINE_CONCURRENCY=2 并发）
       │
       ├─ ③ 解析   → 纯文本 + 结构元数据（标题层级/页码）    §四-1
       ├─ ④ 空文本检测 → < empty_text_threshold 则 FAILED    §五
       ├─ ⑤ 分块   → chunks[]（策略可插拔）                  §四-2
       ├─ ⑥ embedding（worker_threads，批 32）               §四-3
       ├─ ⑦ 入库   → 事务写入 chunks（含 vector + 全文索引）  §四-4
       └─ ⑧ 收尾   → documents.status=READY, chunk_count=N
```

**幂等**：每个 job 携带 `docId`；worker 取到 job 先校验 `documents.status`。若已是 READY 且 `content_hash` 未变 → 跳过（防重复投递）。
P0-1-17 把这条落成**四道**（只写"已是 READY"一道不够，前三道都是"文档变了"）：
① **同进程在飞去重**（同一文档的两个 job 被连着取走时只处理一次）② 文档已删除 ③ job 的 `contentHash` 与当前行不符（投递之后被重新上传过 ⇒ 这个 job 描述的是旧内容）④ 已是 `READY`。
四道全跳过时**一个字节都不写库**；反过来 `PARSING`/`FAILED` 且 hash 相符的 job **会真的重新处理** —— 于是"重投同一个 job"就是可用的重试手段。

**失败**：任一步抛出 → `status=FAILED, error_msg=可读原因`；`POST .../retry` 重新入队。
⚠️ 状态机由 `shared` 的 `DOCUMENT_STATUS_TRANSITIONS` 定义：`PARSING → READY | FAILED`、`FAILED → PARSING`、`READY → PARSING`（重传/重建）；**刻意不允许 `READY → FAILED`**（过期 job 不得把已成功的文档打回失败）与 `FAILED → READY`（重试必须有可见的 `PARSING` 中间态）。⚠️ 另：worker 读行/写状态本身失败（如 PG 不可用）时**不写状态**——那是"我们查不了"，不是"文档坏了"；文档停在 `PARSING`，靠重投恢复。

## 四、各环节实现

### 4-1 解析（四格式）

| 格式 | 库 | 产出 | 要点 |
|------|-----|------|------|
| PDF | `unpdf` | 每页文本 + 页码 | 页码写入 `meta.page`；逐页检测空文本（混合型扫描件识别） |
| docx | `mammoth` | 纯文本 + 标题层级 | **仅 docx**；.doc 在上传前置校验拦截 |
| Markdown | 原生 | 文本 + 标题层级 | 按 `#` 层级记录到 `meta.headingPath` |
| TXT | 原生 | 文本 | 编码嗅探（UTF-8 / GBK），失败尝试 iconv |

**上传前置校验**（`POST /api/knowledge-bases/:id/documents`）：

1. 扩展名 ∈ {pdf, docx, md, txt}；**`.doc` 直接拒绝**，返回可读提示"请另存为 .docx 后重传"（决策 10）
2. MIME 与扩展名交叉校验（防改名绕过）
3. 大小 ≤ `UPLOAD_BODY_LIMIT`（默认 100MB）
4. 同 KB 内 `content_hash` 已存在 → 走**覆盖重建**分支（§七），不新建文档行

**`.doc` 拦截的两种时点**（都做，双保险）：

- 前端：`accept` 白名单 + 选择 .doc 时立即提示，不发请求（省一次往返）
- 后端：路由层校验扩展名，非白名单直接 400（前端拦截可能被绕过）

### 4-2 分块（策略可插拔 · B8 配套）

```ts
interface ChunkStrategy {
  name(): string;                              // 'hybrid' | 'fixed'
  split(text: string, meta: DocMeta, opt: ChunkOpt): Chunk[];
}
```

**`hybrid`（默认）** — 保结构、控长度：

```
1. 若文本含标题结构（docx 标题 / md # / PDF 大字号段）：
   → 先按标题切成 Section[]
2. 每个 Section 内按段落（\n\n）累积：
   - 累到 chunk_size（512 字符）→ 封块，回退到最近的句末边界（。！？.!?）
   - 尾块 < chunk_min（50）→ 并入前块
3. 相邻块加 chunk_overlap（64 字符）重叠
4. 每块记 meta：{ headingPath: [...], page: n, seq: k }
```

**`fixed`** — 纯定长滑窗，用于结构混乱的文本（如 OCR 残留、长表格转文本）：直接按 512 字符切，64 重叠，不做边界回退。

**为什么默认 hybrid**：内部知识库主体是**制度手册 / 技术文档**这类结构强、段落规整的材料，按标题+段落切能让每个 chunk 语义自洽，检索命中率高；而 fixed 在结构强的文本上会把一个完整条款切成两半。两者都保留，是给结构异常的材料留退路——这是「可插拔」的实际意义，不是为将来预留抽象层。

**小文档特例**：全文 ≤ `chunk_size` 时**不切块**，整篇作为 1 个 chunk（避免"200 字的通知"被切成 2 块还带重叠）。⚠️ 判在**全文**而不是"每个 Section"：一份 200 字、带 3 个标题的通知按 Section 判会变成 3 块（每块 60 余字），与本节的原意相反。反过来全文超阈值时，Section 仍按"装得下就整块装"处理 —— 这正是 hybrid 与 fixed 的区别（保结构）。

**落地口径（P0-1-18 实现时定案，细节见 `issue_fix/问题记录-P0-1-18-空文本检测+分块.md`）**：

| 议题 | 定案 | 为什么（不这么做会怎样） |
|------|------|------------------------|
| 策略接口签名 | `split(source: ParseResult, opt: ChunkOptions)`（文档写的是 `(text, meta, opt)`） | 标题层级只在 `blocks` 里，`text` 是它的派生。只给 `text` 会让 hybrid 退化成 fixed（拿不到标题、也拿不到页码） |
| Section 切分 | 按"**连续**同名标题"切，不按 `headingPath` 分组 | 同一文档里两个 `## 考勤`（中间隔着别的标题）是常态；分组会把它们并到一起 ⇒ **chunk 顺序与原文不一致**，而顺序错乱在检索层几乎发现不了（片段读起来通顺，只是位置不对） |
| 句末边界集合 | `。！？.!?` + **`\n`** | 段落末尾本身就是最自然的切点，而 blocks 之间以 `\n\n` 连接。少了 `\n`，"一段正好超长"的文档只能退化成硬切 |
| 回退下界 | 最近的边界若落在 `chunk_min` 之前 ⇒ **硬切在 `chunk_size`** | 这一大段几乎没有句读（长表格转文本、无标点 OCR 残留）时，"回退"只会切出几十字的碎块 |
| 重叠范围 | **仅同一个 Section 内**（不跨 Section） | 跨 Section 的重叠会把两段不相干的内容缝在一起（一个的结尾 + 另一个的开头），命中后读起来语义断裂 |
| 块长上界 | 普通块 ≤ `chunk_size + chunk_overlap`；**尾块合并后**的末块可达 `chunk_size + chunk_overlap + chunk_min` | 尾块并入前块是"宁可贵一点也不要碎片块"的刻意取舍，上界放宽是它的代价（写在这里免得被当成 bug） |
| `chunk_min` 来源 | **代码常量** `DEFAULT_CHUNK_MIN_CHARS = 50` | §十一 的配置增量表里没有 `CHUNK_MIN_DEFAULT`，`knowledge_bases` 也没有对应列 ⇒ 加变量属于自己发明契约。要可配先改本节与 §十一 与 schema |
| 切片单位 | 全部建在 `[...text]` 的**码点**数组上 | `text.slice()` 会劈开代理对（`'😀'.length === 2`），产出非法字符串且**本层毫无报错**（下游 embedding 才炸） |
| 块的不变式 | 每块都是 `parsed.text` 的**逐字子串**（重叠也是取前块尾部） | §九 的"引用片段与原文一致可核对"以它为前提；破了则引用无法核对 |
| meta 的页码 | 取**块起点所在段**的页码（用段内偏移反查，不含重叠前缀） | 一个 Section 可能跨页（PDF）；"整块用 Section 首页"会把页码全说成第 1 页；用重叠前缀定位则会说成上一块所在的页 |

### 4-3 embedding

```ts
// 复用 02 §八 的 EmbeddingProvider 抽象
const batches = chunkBy(chunks, 32);           // chunk_embed_batch=32
const vectors = await Promise.all(batches.map(b => provider.embed(b)));
```

- **onnx 推理走 `worker_threads`**（02 §二已定），避免 CPU 密集阻塞在线请求
- 单条 < 500ms 为验收底线（01 §四性能）
- provider `name()` 随每个 chunk 落库到 `meta.embeddingName`，用于换模型检测（§八）
- 失败重试：单批失败重试 2 次（指数退避 1s/3s），仍失败则整文档 FAILED

**落地口径（P0-1-19 实现时定案）**：

- **重试落在"批"粒度，且因此必须由流水线侧切批**：`EmbeddingProvider.embed()` 内部自己会按
  `batchSize` 循环切批 ⇒ 它看到的永远是"一次调用"。要兑现本节的"**单批**失败重试 2 次"，
  只能由 `pipeline/index/writer.ts` **先按 `EMBEDDING_BATCH_SIZE` 把文本切好、每次只喂一批**
  （provider 的内部循环于是只跑一轮），重试边界才与"批"对齐。
- **一批最终仍失败 ⇒ 整篇 `FAILED`**（不做"跳过这批继续"）。跳过会留下"有块没向量"的坏数据：
  那些 chunk 在检索里**永远排不上号**（`<=>` 对 NULL 是 NULL），而界面上一切正常 ——
  这种"看不见的缺失"比整篇失败难查得多，而整篇失败是**可见且可重试**的。
- **失败文案是给用户看的**：`文本向量化失败（已重试 2 次）：…`。这一环最常见的故障是"配置缺项 /
  上游不可达 / 维度不符"，必须让人看出是**环境或上游**的问题，否则他会去重传一个没问题的文件。
  上游回显的内容（401 的 `Authorization`）由 `llm/upstream.ts` 统一脱敏（P0-1-12 的坑）。

### 4-4 入库（DDL 与索引）

**B2 已定案：chunks 单表不分区**（分区表无法建全局 HNSW）。02 §三的表定义至此落实为 DDL：

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_bigm;

CREATE TABLE chunks (
  id          uuid PRIMARY KEY,                  -- uuid(7)，见 02 §3.1
  doc_id      uuid        NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  kb_id       uuid        NOT NULL,
  seq         int         NOT NULL,
  content     text        NOT NULL,
  embedding   vector(1024),
  meta        jsonb       NOT NULL DEFAULT '{}',
  created_at  timestamptz NOT NULL DEFAULT now()
);

-- 向量路：HNSW，cosine 距离
-- ⚠️ 迁移里的实际写法多一个 `WHERE kb_id IS NOT NULL` 谓词 —— 它**不是业务过滤**
--    （kb_id 是 NOT NULL 列，谓词恒真、覆盖全部行），而是"让 Prisma 看不见这条它表达不了的索引"
--    的手段：认不出的索引会被 `migrate dev` 判成多余对象并生成 DROP INDEX。
--    详见 06 P0-1-14 落地要点 1。
CREATE INDEX idx_chunks_embedding ON chunks
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64)
  WHERE kb_id IS NOT NULL;

-- 全文路：pg_bigm GIN（中文 bigram，LIKE '%词%' 可走索引）
-- ⚠️ 算子类**必须**显式写：text 没有默认 GIN 算子类，省掉它不是"静默建错"而是直接报错
CREATE INDEX idx_chunks_bigram ON chunks USING gin (content gin_bigm_ops);

-- 过滤路：按库/文档定位
CREATE INDEX idx_chunks_kb   ON chunks (kb_id);      -- 落地为 chunks_kb_id_idx（Prisma 命名）
CREATE INDEX idx_chunks_doc  ON chunks (doc_id, seq); -- 落地为 chunks_doc_id_seq_idx
```

> **落地口径（P0-1-14 订正，以 `backend/prisma/schema.prisma` 与 `migrations/0002_knowledge/` 为准）**：
> ① 三张表的主键是 **`uuid(7)`** 而不是本段草稿原先写的 `bigserial` —— `02` §3.1 定了"一律 uuid(7)"，
> 且 `agent_components.ref_id`（P0-1-5 已落 `UUID`）将来要指向 `knowledge_bases.id`；
> ② 普通索引由 Prisma 声明并管理（故名字是 `chunks_kb_id_idx` / `chunks_doc_id_seq_idx` /
> `documents_kb_id_created_at_idx`），只有上面两条特殊索引是手写 DDL；
> ③ `chunks.embedding` 在 Prisma 侧声明为 `Unsupported("vector(1024)")?`（**可空**才能让 Prisma 省略它），
> 读写一律走手写 SQL；`chunks.id` 也就由客户端生成 ⇒ 批量插入必须自带 id 数组。

> **落地口径（P0-1-19 实测订正 —— 写入语句换了形态）**：
> 上面那段 `INSERT ... SELECT unnest(...)` 要求"**自带 id 数组**"，而 `chunks.id` 的口径是
> `uuid(7)`（`02` §3.1），并且 **P0-1-16 已定案"不手搓 uuid7"**（实测 `crypto.randomUUID({version:7})`
> 在 Node 22.22 上静默返回 v4）⇒ `uuid(7)` 在本仓**只有 Prisma 的 `@default` 一个实现**，
> 要拿它就必须走 Prisma 的写入路径。实际落地为（`backend/src/pipeline/index/writer.ts`）：
>
> ```sql
> -- 一个事务里三步，每批 200 行：
> DELETE FROM chunks WHERE doc_id = $1;                        -- 先删后建（§七 的取舍）
> INSERT INTO chunks (id, doc_id, kb_id, seq, content, meta)   -- 由 Prisma 的 createManyAndReturn 执行，
>   VALUES ...;                                                -- id 由 @default(uuid(7)) 客户端侧生成
> UPDATE chunks AS c SET embedding = v.emb::vector             -- 手写 SQL 回填向量
>   FROM unnest($1::uuid[], $2::text[]) AS v(id, emb) WHERE c.id = v.id;
> ```
>
> 代价：多一条 `UPDATE`（一条 SQL 一批，不是 N 条）。收益：**id 只有一个来源**，
> `uuid(7)` 这条不变式不会被"加第二个实现"。验收里有 **"id 的版本位必须是 7"** 一条专门守它。
> 向量以**文本数组**（`[0.1,0.2,…]`）传入再 `::vector` 转换，而不是 `vector[]` ——
> 后者需要驱动层先认识 pgvector 类型，而 `文本::vector` 是官方路径（P0-1-20 的 `embedding <=> $1` 同款）。
>
> **`meta` 的实际形状**：`{ headingPath: string[], page: number | null, embeddingName: string }`。
> `seq` 不重复放进 `meta`（它是独立列，两处存会漂）；`embeddingName` **每行都存一份**
> （而不是只存文档级）：换 embedding 模型时要能分辨"哪些行是旧模型产的"，那正是 §八 重建路径的输入。

**为什么 `gin_bigm_ops` 而不是 tsvector**：PG 内置 parser 按空格/标点切词，中文整句会成为一个 token，`to_tsvector` 对中文基本命不中（A2 结论）。pg_bigm 用 2-gram 建倒排索引，查询写成 `content LIKE '%关键词%'` 即可走索引，无需分词器。**代价**：`LIKE` 查询的召回是"字面包含"，对同义改写无能为力——这部分由向量路补足，这也正是双路存在的理由。

**写入事务**：同一 `doc_id` 的 chunk 全量插入放在**单事务**内（先 `DELETE FROM chunks WHERE doc_id=?` 再批量 `INSERT`），保证覆盖重建不产生孤儿 chunk（需求 17 的验收要点）。批量插入用 `INSERT ... SELECT unnest(...)` 拼多值，单批 200 行。

## 五、空文本检测（B11 → 需求 16 验收要点）

```
解析完成 → textLen = 所有页/段正文的字符总数（去空白后）
  ├─ textLen < empty_text_threshold(50)
  │    → documents.status = FAILED
  │      error_msg = "解析结果内容过少（<50 字符），疑似扫描件或空白文档，
  │                   本系统暂不支持图片型 PDF，请上传可复制文本的文件"
  │    → 不产生任何 chunk；原始文件保留（便于用户核对）
  └─ textLen ≥ 50 → 继续分块
```

**为什么放在解析后而非上传前**：上传时无法知道内容量，只能解析后判。**为什么不判"per 页"**：多页文档常有封面/目录页本身近乎空白，按页判会误杀正常文档；按**全文总量**判更稳。

**混合型文档的降级**：若**部分页**有文本、部分页是扫描图（PDF 常见），全文总量通常 ≥ 阈值 → 正常入库，但仅有文本的页进入检索。此时在文档列表页给一条提示（`chunk_count` 明显低于页数时的弱提示），不阻塞流程。

**落地口径（P0-1-18 定案）**：

- **文案里的数字取实测值**，不把 50 写死：阈值来自 `EMPTY_TEXT_THRESHOLD`（可配），写死的话管理员调到 200 之后用户看到的报错仍说"少于 50"，他会改成一个 60 字的文件重传、再失败一次。实际文案：
  `解析结果内容过少（有效字符 {实测}，不足 {阈值} 个），疑似扫描件或空白文档；本系统暂不支持图片型 PDF，请上传可复制文本的文件。`
- **判据是 `<` 而不是 `<=`**：有效字符**恰好等于**阈值即通过（验收有"恰好达标通过 / 少一个字符失败"这一对边界断言，且用例内容按**当前阈值**生成 —— 阈值可配，写死 50 的实现会被它抓出来）。
- **它是独立阶段（④），且必须排在分块（⑤）之前**：顺序反了会先白切一遍再判失败；且"块数为 0 却报句子级错误"会把排查方向带偏。验收用**产物的缺席**取证（重跑阶段数组时 `ctx.chunks === undefined` 而 `ctx.parsed !== undefined`）。
- **失败不删原文件**：用户要能下载回去核对"我传的到底是不是扫描件"（比"猜"有用得多）。

## 六、混合检索与 RRF 融合（B1 定案 + 需求 18）

### 6-1 双路检索

```sql
-- 向量路：cosine 距离 → 相似度
SELECT id, 1 - (embedding <=> $1) AS vscore
FROM chunks
WHERE kb_id = ANY($2) AND embedding IS NOT NULL
ORDER BY embedding <=> $1
LIMIT $3;                      -- $3 = topK * 3（取候选池，融合后再截断）

-- 全文路：pg_bigm LIKE
SELECT id, bigm_similarity(content, $1) AS fscore
FROM chunks
WHERE kb_id = ANY($2) AND content LIKE '%' || $1 || '%'
ORDER BY fscore DESC
LIMIT $3;
```

**候选池放大 3 倍**：融合需要足够的双路候选才有意义，直接各取 topK 会让 RRF 退化成"两路小数量的机械交替"。最终输出仍截断到 `topK`。

**查询预处理**：

- 向量路：query 原样 embed（bge-m3 对中文短查询表现好，不做改写）
- 全文路：query 去停用词、去标点后作为 `LIKE` 子串；**长 query 截断到 64 字符**（过长子串几乎不可能字面命中）
- **`mode` 分流**：`VECTOR` 只走向量路，`FULLTEXT` 只走全文路，`HYBRID`（默认）双路

**落地口径（P0-1-20 定案，`backend/src/services/retrieval.ts`）**：

| 项 | 口径 | 为什么 |
|----|------|--------|
| "去停用词"**只剥句首/句尾** | 剔标点（全部）→ 反复剥两端的提问脚手架（"请问…是多少"）→ **不删中间的停用词** | LIKE 要的是**连续子串**：把"报销的标准"里的"的"删掉会变成"报销标准"，而正文写的是"报销的标准" ⇒ **本来能命中的反而命中不了**，与初衷相反。脚手架本来就只在两端 |
| **不剥否定词** | "不 / 没 / 非" 等一律保留（"不含税"→"含税"是语义反转） | 召回率低只是少几条，语义反转是答错 |
| 标点一律剔除 | `[\p{P}\p{S}\p{C}\s]` | 顺带把 `%` / `_` 干掉 —— 它们是 **LIKE 的通配符**，留着会让"字面包含"静默变成模式匹配（`5%0` 会命中"5…0"）。**不需要再叠一层转义**（多一层转义就多一处会漏的地方） |
| 截断单位是**码点** | `[...text].slice(0, 64)` | `slice()` 会把 64 切在 32 个代理对上，产出非法字符串且本层无报错 |
| `score` **只作用于向量路** | 过滤放在候选池**之后**（距离单调 ⇒ 两种顺序等价） | `bigm_similarity` 与 cosine 量纲、分布都不可比，套同一个阈值是两套量纲混用 |
| SQL **不加第二排序键** | tie-break（同分按 id 升序）在 JS 侧做 | `ORDER BY embedding <=> $1, id` 会让 HNSW 退化（HNSW 只支持单键距离排序）⇒ P0-1-14 的索引取证白做 |
| 候选池 `topK × CANDIDATE_POOL_FACTOR` | 倍数是**环境级**（§十一 未定义为 KB 级参数） | 融合需要足够的双路候选，直接各取 topK 会让 RRF 退化成"机械交替" |
| `kb_id = ANY($2::uuid[])` | 保持本节的形状，单库端点传一个元素的数组 | F 包的对话编排要一次查 Agent 绑定的多个库，届时只改调用方、SQL 不动 |

> ⚠️ **全文路只适合短查询**（P0-1-20 实测的边界）：它是字面子串匹配 —— 一句自然语言长问句
> 即使截断到 64 字符，那 64 个字符也**几乎不可能**连续出现在正文里（实测：截断后的问句命中 0 条，
> 而"从原文里取 64 字子串当 query"命中 1 条）。**长问句请用 `HYBRID`/`VECTOR`**；试查页要给出这句话，
> 否则用户会在 `FULLTEXT` 下看到空结果从而怀疑索引坏了。


### 6-2 RRF 融合（B1 定案）

双路原始分不可比（cosine 相似度 vs bigram 相似度，量纲与分布完全不同），因此**不比较分数，只比较排名**：

```
RRF_score(d) = w_vector  × 1 / (rrf_k + rank_vector(d))
             + w_fulltext × 1 / (rrf_k + rank_fulltext(d))

rrf_k = 60（默认）
```

- `rank_x(d)` = 文档 d 在第 x 路结果中的位次（从 1 开始）
- 只在一路出现的 d：另一路项记 0（**即"缺失即无贡献"**，不惩罚、不补位）
- 融合后按 `RRF_score` 降序 → 截断 `topK`

**一个反直觉但正确的结果**（下表即实测值，k=60、权重 1.0）：只在单路拿到第 1 名的 chunk（0.0164），会**输给**在两路都排中游/第 1 的 chunk（向量第 1 + 全文第 4 = 0.0320；两路都第 1 = 0.0328）。这不是 bug，而是 RRF 的设计意图——**双路共同认可比单路极端高分更可信**。这正是混合检索相比单路的价值所在。

| 情形 | 算式（k=60，w=1.0） | 分值 |
|------|--------------------|------|
| 两路都第 1 | `1/61 + 1/61` | **0.0328** |
| 向量第 1 + 全文第 4 | `1/61 + 1/64` | **0.0320** |
| 只在向量路第 1（另一路缺席） | `1/61 + 0` | **0.0164** |
| 只在全文路第 3 | `0 + 1/63` | **0.0159** |

> ⚠️ **数值订正（P0-1-20 实测）**：本节原先写的"向量第 1 + 全文第 4 = **0.0323**"是纸上推的，
> 实测为 **0.0320**（`1/61 + 1/64`）。已按实测订正，并把这三个数值写成断言
> （`verify:app` 的"RRF 融合公式"用例）—— 文档里的数字与代码里的公式从此互为守门。


**`rrf_k=60` 的来历**：这是 RRF 论文的常用默认值，作用是压平头部差距——k 小则第 1 名与第 2 名权重差悬殊，k 大则趋于均匀。60 在「既要突出头部、又不让单路结果独裁」之间取平衡。内部知识库场景无需精调，先用默认值。

**为什么不用分数归一化加权**：归一化需要一个可靠的分数分布假设，而两路分数分布随 query 长度、KB 内容变化剧烈，归一化系数会失效。RRF 只用排名，对分数分布不敏感——这是选它的核心原因。

**检索测试页要展示什么**（需求 18 "看双路得分"）：rag 调试需要看到每一路各自的判断，因此返回结构按**单路分 + 融合名次**并列：

```jsonc
// POST /api/knowledge-bases/:id/search     （请求体：{ query, topK?, mode? } —— 只有这三项）
{
  "items": [
    {
      "chunkId": "01a0c289-6738-715c-a10c-ef95c1286bf9",  // chunks.id 是 uuid(7)，不是自增整数
      "docId":   "01a0c289-6738-715c-a10c-ef95c1286bf8",  // 引用卡要能跳回文档
      "docName": "报销制度.docx",
      "seq": 3,
      "page": null,                  // PDF 才有页码（§十三 待决事项 1：P0 只给 meta.page）
      "headingPath": ["第三节"],     // 引用卡显示"在哪一节"
      "snippet": "出差住宿标准为每晚上限 500 元",   // 命中位置前后各 80 字符的**原文**（不加工、不加省略号）
      "vectorScore": 0.82,           // 向量路原始相似度，未命中为 null（不是 0）
      "vectorRank": 1,
      "fulltextScore": 0.31,         // bigram 相似度，未命中为 null
      "fulltextRank": 4,
      "rrfScore": 0.0320,            // = 1/(60+1) + 1/(60+4)

    }
  ],
  "mode": "HYBRID",                  // 本次**生效**值（请求可覆盖 topK/mode，且不落库）
  "topK": 5,
  "rrfK": 60,                        // 取该库快照；展示 rrfScore 时必须同时显示它（否则分数不可比）
  "candidatePool": 15,               // = topK × CANDIDATE_POOL_FACTOR
  "elapsedMs": 187,
  "vectorPathSkipped": false,        // 机器可判的"这次没走向量路"（§八 的降级）

```

> 前端检索测试页在原设计（双路得分）基础上**新增「融合排名」列**（B1 修订要求）。
> `§九` 的"对外只给融合分"指的是**引用卡**（F 包的 `citations` 事件）；试查页要看到每一路各自的
> 判断，故本端点把双路原始分一并出口 —— 两者不冲突，别把试查页当成引用对象的形状。

## 七、覆盖重建（需求 17 / 决策 13）

```
POST /api/knowledge-bases/:id/documents/:docId/reupload
  ↓
1. 新文件写 S3 → 新 file_key
2. 同事务内：
   a. DELETE FROM chunks WHERE doc_id = :docId     ← 旧 chunk 立即清理
   b. UPDATE documents SET status='PARSING', error_msg=NULL,
        content_hash=<new>, file_key=<new>, chunk_count=0
3. 入队 pipeline:jobs {docId, mode: REBUILD}
4. worker 走标准流程（解析→检测→分块→embedding→入库）
```

**语义**：同文档重传 = 替换，**不新建 documents 行**（决策 13"覆盖重建"）。文档 id 稳定 → 引用、绑定均不受影响。

**关键取舍：先删后建，中间存在检索空窗。**

- 窗口时长 = 一次流水线耗时（大 PDF 可达分钟级）
- 此期间该文档的 chunk 数为 0，检索自然不返回它——**不报错，只是暂时查不到**
- 为什么不"先建后删"（双份共存再切换）：双份期间同一内容会有两份 chunk 同时被检索到，引用出现重复文档名，比空窗更糟且更难向用户解释
- 缓解：文档列表页在 `PARSING` 状态显式提示"更新中，暂不参与检索"

**`content_hash` 相同的重传**：视为用户误操作，直接返回 200 + "内容未变化，已跳过"，不触发流水线。

**落地口径（P0-1-19 定案）**：

- **`file_name` 也一并更新（对本节列清单的刻意补全）**：上面 `UPDATE` 的列只列了
  status / error_msg / content_hash / file_key / chunk_count。但 `file_name` 在本仓还承担
  下载端点的 `Content-Disposition` 文件名 ⇒ 旧名留着就会**说谎**（列表显示旧名、下载得到新内容），
  而用户没有任何别的入口改名（只能删掉重传，那会丢掉本文档要保的稳定 id）。
- **`unchanged` 的"三个没做"要能被验收分辨**：不落新对象、不删旧 chunk、不入队。
  取证方式是**删得掉证据**的那几条 —— chunk 行 `id` 逐字不变（重写过就会换新 id）、
  文档 `updated_at` 逐字不变、`kb/{kbId}/` 下的对象数不变、队列深度 0。
  只断言"内容还在"是验不出"重写了一遍"的。
- **响应契约**：`{document, unchanged}`，与上传的 `{document, deduplicated}` **字段名刻意不同**
  （前者答"这一篇没变"、后者答"库里已有同样内容"）。提示文案走 `shared` 的
  `REUPLOAD_UNCHANGED_HINT`，前后端共用同一句。
- **`reupload` 的入队失败无法整次回滚，只能如实告知**：上传能回滚是因为行是它刚建的；
  这里旧 chunk 删了就回不来。故失败时返回"内容已替换但入队失败，请点重试"，
  **不伪装成"什么都没变"**（那会让用户以为旧内容还在）。
- **状态守卫**：`READY`/`FAILED`/`PARSING` 三种在库状态回到 `PARSING` 都合法（状态机表里
  `READY → PARSING` 正是"覆盖重建"这条转换），但服务层仍走一次
  `canTransitionDocumentStatus` 守卫 —— 真进来了说明状态值与状态机脱节了，宁可 409 也不写坏那行。

## 八、换 embedding 模型的重建路径（B3 定案 · P1）

`vector(1024)` 是 DDL 写死的，换模型（如 bge-m3 → 1536 维模型）会导致维度不匹配。**不做 `ALTER COLUMN`**（大规模改写向量列会长时间锁表），走**新表切换**：

```
① 检测：EmbeddingProvider.name() 与 chunks.meta.embeddingName 不一致
   → 所有 KB 标记「需重建」

② 新建：chunks_v2（同构表，embedding vector(<新维度>) + 同名索引）

③ 双写：流水线同时写 chunks（旧，保留可检索）与 chunks_v2（新）
   —— 只在重建窗口期双写；存量文档按重建队列逐个重跑

④ 切换：全部文档重跑完成 → 检索指向切 chunks_v2（配置开关，非代码发布）

⑤ 弃旧：观察一个版本周期 → DROP TABLE chunks；把 chunks_v2 改名回 chunks
```

**降级路径（维度不匹配时的第一反应）**：在 `chunks_v2` 就绪前，检索遇到维度不匹配**不报 500**，而是：跳过该 KB 的向量路 → 若 `mode=HYBRID` 则**仅用全文路返回**并附警告；若 `mode=VECTOR` 则明确提示"该知识库使用的 embedding 模型已变更，请等待重建完成"。

**P0 只做①④的开关骨架**，②③⑤ 是 P1「重建索引」需求的实现——但探测与告警要在 P0 就位，否则换模型时会静默出错。

**落地口径（P0-1-20 定案 —— 降级路径已进检索服务，`backend/src/services/retrieval.ts`）**：

| 情形 | `HYBRID` | `VECTOR` | `FULLTEXT` |
|------|----------|----------|------------|
| 库快照 `embedding_model` ≠ 当前 provider `name()` | **跳过向量路 + `warnings` 告警**（`vectorPathSkipped=true`），全文路照常返回 | **409** + 可展示原因 | 不受影响（这条路根本不碰 embedding） |
| 服务端 embedding 未就绪（配置缺项 / 本地模型未就位） | 同上（跳过 + 告警） | **500** + 配置缺项清单 | 不受影响 |

- **一个库里的两种"不能走向量路"必须分开报**：模型变了是"**这个库**要重建"（业务动作），
  未就绪是"**这台机器**没配好"（运维动作）。合成一条会让用户去重做一个治不好的动作 ——
  对应 `shared` 的两条常量 `VECTOR_PATH_SKIPPED_MODEL_CHANGED` / `VECTOR_PATH_SKIPPED_NOT_READY`。
- **`VECTOR` 模式不能"降级成空结果"**：返回 `items: []` 会被读成"库里没有相关内容"——
  那是一句假话，而用户没有任何线索能推翻它。故明确报错。
- **降级不静默**：`vectorPathSkipped` 是给机器判的布尔，`warnings` 是给人看的文案
  （让前端去匹配文案是最脆的一种契约）。
- ①② 的**探测**（`embeddingModelChanged` 三态）在 P0-1-15 已就位（列表/详情投影里就能看到
  "这个库需要重建"），本批把**检索路径**接上；④ 的"检索指向切表"仍属 P1。

## 九、引用格式（需求 19 / 决策 12）

```
chunk → 引用对象
{
  docName: "报销制度.docx",
  snippet: <命中片段原文>,
  score:   <RRF_score>              // 对外只给融合分，不给双路原始分
}
```

**规则**：

- `snippet` = 命中位置前后各取 **80 字符**窗口的原文，**不加工、不摘要**（决策 12"命中原文片段，可展开核对"）
- 长 chunk（512 字符）不做整块返回，只给窗口 —— 引用卡要的是"核对依据"，不是"整段内容"
- 未命中任何 chunk → **不产生引用卡**，且后端在 system prompt 里明确禁止编造引用（需求 14 验收要点）
- 同一文档多个 chunk 命中 → 各生成独立引用（不合并），用户能看到命中在不同位置

> 引用如何进入 LLM 上下文、如何随 SSE 的 `citations` 事件下发：见 02 §五（事件契约）与 §六（编排）。

## 十、异步队列与并发（承接 02 §二）

| 项 | 方案 |
|----|------|
| 队列载体 | Redis List `pipeline:jobs`（`LPUSH` 入队 / `BRPOP` 消费） |
| 并发上限 | `PIPELINE_CONCURRENCY=2`（02 §二已定），worker 内信号量控制 |
| 任务粒度 | 1 个 job = 1 个文档（含全部 chunk） |
| 重试 | 文档级重试（`POST .../retry`）；批级内建 2 次退避重试 |
| 失败隔离 | 单 job 失败不影响其他 job；error_msg 落库供前端展示 |
| 进程形态 | **进程内** worker（不单独部署），onnx 推理走 `worker_threads` |
| 演进路径 | 若 CPU 争抢明显 → 拆独立 worker 进程，**Redis 队列协议不变**（02 §二预留） |
| 重建队列 | 整库重建（P1）复用同一队列，job 带 `mode: FULL_REBUILD` 与 KB 级标记 |

**为什么用 List 而非 Stream**：任务无多消费者组需求、无需 ack 语义（失败已落库），List 的 `BRPOP` 最简单够用。引入 Stream 会带来 consumer group 管理的额外复杂度而无对应收益。

## 十二、验收清单（对应 01 需求行）

| 需求 | 验收动作 | 通过标准 |
|------|---------|---------|
| 15 KB CRUD | 建库（设 topK/阈值）→ 改名 → 删库 | 删除时级联清 chunks 与 S3 原文件 |
| 16 文档上传 | 传 pdf/docx/md/txt 各 1 → 观察状态 | 状态 PARSING→READY；**传扫描件 → FAILED 且提示"疑似扫描件"**；传 .doc → 拒绝并提示另存为 .docx |
| 16 失败可重试 | 造一个失败文档 → 重试 | 重试后转 READY，chunk 正确入库 |
| 17 覆盖重建 | 同文档传 v2 | 文档 id 不变；`SELECT count(*) FROM chunks WHERE doc_id=?` **无重复、无孤儿**；检索返回 v2 内容 |
| 18 检索测试 | 输中文 query | 双路得分 + **融合排名**均可见；中文能命中（证明 pg_bigm 生效，非空结果） |
| 19 引用格式 | 对话提问命中 | 引用卡显示"文档名 + 原文片段"，片段与原文一致可核对 |
| 性能 | 单条 embedding | < 500ms（01 §四） |
| 性能 | 检索 | < 500ms（01 §四） |

**一个必测的坑**：`mode=FULLTEXT` 单独跑一次中文 query。若这个用例返回空，说明 pg_bigm 索引未生效（最可能是建索引时用了默认 `gin_ops` 而非 `gin_bigm_ops`），此时"混合检索"实际只剩向量单路——这正是 A2 要防的问题。

**验收结论（P0-1-21 实测，包 D 收口）**：上表 8 行**逐行有据** —— `pnpm verify:kb-package` 一行一组
（11 项断言，需 PG + Redis + MinIO，自起语义型假 embedding 上游），原始输出见
`issue_fix/问题记录-P0-1-21-知识库包验收.md`。逐行结论与**取证方式**：

| 行 | 结论 | 取证方式（关键那条） |
|----|------|---------------------|
| 15 KB CRUD | ✅ | 建库（设 `topK`/阈值）→ 改名（`retrievalConfig` 不被顺带改动）→ 删库后 `chunks` 与 **S3 对象**都清零（按前缀 `listObjectsV2` 复核） |
| 16 文档上传 | ✅ | 四格式各 1 篇：上传恒 `PARSING` → **用列表端点观察到转 `READY`**，且 `chunk_count` **等于 `chunks` 表行数**、每块都有向量；扫描件（空白 PDF）→ `FAILED` + 「疑似扫描件」；`.doc` → 400 + 「请另存为 .docx 后重传」 |
| 16 失败可重试 | ✅ | 上游 500 → `FAILED`（原因可读）→ 修好后 `POST /retry` → 立刻 `PARSING` → `READY`，chunk 正确入库 |

| 18 检索测试 | ✅ | 中文 query 的 `vectorScore/vectorRank` + `fulltextScore/fulltextRank` + `rrfScore/finalRank` 六列同时可见；命中那一篇两路都排第 1，`rrfScore = 2/(k+1)` |
| 19 引用格式 | ✅ | 每一条 `snippet` 都是**它自己那块正文的逐字子串**（从库里取原文比对）且含命中的词；`docName` 与库里一致 |
| 性能 | ⚠️ 部分 | 检索：自报 `elapsedMs`（8ms）与墙钟（12ms）都 < 500ms ✅；**单条 embedding < 500ms**：本档量的是"HTTP + 解析 + 校验"的**固定开销**（1ms，假上游在 localhost），**真实模型推理时延要等 `LOCAL_EMBEDDING_RUNTIME_MODULE` 就位**（§十三 待决事项 2 / `06` §七 待决事项 2）才能量 |
| §十二 必测的坑 | ✅ | `mode=FULLTEXT` 单独跑中文 query **非空**（名次 1、`vectorScore` 为 `null`）；索引**可用性**本身由 `verify:knowledge` 的三条 EXPLAIN 断言守着（关掉更便宜的退路看它现不现身） |

## 十三、待决事项

|---|------|------|------|
