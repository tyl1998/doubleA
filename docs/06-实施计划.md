## 二、开工前置核对（2026-09-20 实测）

施工前必须确认的事实，避免中途发现环境不支持：

| 项 | 实测结果 | 结论 |
|----|---------|------|
| Node | v22.22.2（受管）/ v20.20.2（系统） | 用受管 22，`engines` 锁 `>=22` |
| pnpm | 12.4.2（经 corepack，**须用系统 node 启动**：`<npm_prefix>\nodejs\node.exe ...corepack\dist\pnpm.js`） | ✅ 可用；受管 node 下 pnpm shim 失效，需在脚本里固定启动方式 |
| pnpm 配置文件 | **pnpm 12.x 不读 `.npmrc`** —— 配置唯一入口是 `pnpm-workspace.yaml` | ⚠️ 所有设置写进 `pnpm-workspace.yaml`（camelCase） |
| pnpm 构建脚本白名单 | 实际采纳的键是 **`allowBuilds`**（映射），标准键 `onlyBuiltDependencies` 无效；未放行会让 install **报错退出** | ⚠️ 加原生依赖时在此登记 |
| pnpm 目录符号链接 | **静默失败**：Windows 未开开发者模式 → `symlink(…,'dir')` 不报错、只留空目录 | ⚠️ 已用 `nodeLinker: hoisted` + `paths`/`alias` + `prepare` 补 junction 三层解决 |
| Docker | 29.4.0 + Compose v5.1.1，`desktop-linux` context 正常 | ✅ PG/Redis/MinIO 可真实拉起 |
| Git | 2.53.0.windows.2 | ✅ |
| 本机 Bash | Git Bash **缺 coreutils**（无 `ls`/`head`/`tail`/`dirname`/`grep`） | ⚠️ 施工脚本一律走 Node/PowerShell，不依赖 shell 工具链 |
| pgvector + pg_bigm 镜像 | 官方 `pgvector/pgvector` **不含 pg_bigm** | ⚠️ 必须自建 PG 镜像（P0-1-2 落此项） |

## 二·补、构建与部署分离约定（2026-09-20 定案）

用户诉求：**前后端能独立构建、独立部署**。本项目的实现方式（与 `02` §十二 部署形态联动）：

| 项 | 后端 | 前端 |
|----|------|------|
| 构建 | `pnpm --filter @doubulea/backend build` → `backend/dist` | `pnpm --filter @doubulea/frontend build` → `frontend/dist`（纯静态） |
| 运行形态 | Node 进程，容器化（`backend/Dockerfile`） | 静态资源，Nginx / CDN / 对象存储托管（`frontend/Dockerfile` 可选） |
| 部署位置 | 内网服务器，需访问 PG / Redis / MinIO / Docker daemon | 可与后端**不在同一台机器**，只需能调后端 API |
| 依赖服务 | `infra/docker-compose.yml` 起 PG / Redis / MinIO（不含 app） | 无 |
| 共享代码 | `shared/`（编译期内联，**运行期零耦合**） | 同左 |

**关键说明**：
- 前端产物是**纯静态**（Vite build），部署时不需要 Node 运行时，也不需要知道后端在哪台机器（通过构建期 `VITE_API_BASE_URL` 或运行期同源反代决定）。
- 后端**不负责托管前端静态资源**（`02` §十二 原写「app 容器含前端静态资源」是单容器简化形态；独立部署时改为前后端各自部署，用网关按路径分流 `/api` → 后端、`/*` → 前端）。
- 两者唯一必须一致的只有**接口契约**，由 `shared/` 在编译期强制保证。

### 3.0 仓库最终形态（先定死，后面所有路径都以此为准）

**形态决策：单仓 + pnpm workspace；前后端平级分离。**

> **为什么不分两个仓库（2026-09-20 已讨论并定案，不再重开）**：
> 用户诉求是「前后端**独立构建、独立部署**」——这个诉求 monorepo 已完整满足：`pnpm --filter` 分包构建，前后端各自产出 `dist`，可分别部署到不同机器/容器/静态托管，运行期零耦合。**分仓需要额外解决的问题（50 个端点 + 10 个 SSE 事件的契约同步）在本项目里代价高于收益**：SSE 是流式契约，类型漂移不会立刻暴露，属于最难查的一类缺陷；而分仓带来的收益（多团队各自独立发布、各自走审批）在本项目（内部工具、单人/小团队）拿不到。故维持单仓，仅把目录整理为平级清晰形态。
> 若将来后端要开放给其他系统消费，届时再引入 OpenAPI 生成类型（`@fastify/swagger` → `openapi-typescript`），作为**增量**加上，不影响当前结构。

**独立构建 / 独立部署的实现方式**（写进各包 `package.json` 的 scripts）：

```powershell
pnpm --filter @doubulea/backend  build      # 只构建后端 → backend/dist
pnpm --filter @doubulea/frontend build      # 只构建前端 → frontend/dist
pnpm --filter @doubulea/backend  dev        # 只起后端开发服务
```

> **⚠️ 本机两处非默认设置（P0-1-1 代价）：**
> 1. `pnpm-workspace.yaml` 里 `nodeLinker: hoisted` —— 本机 pnpm 无法建目录符号链接（Windows 未开开发者模式，且失败时静默），isolated 布局下各包 `node_modules` 只剩空目录。
> 2. `infra/scripts/link-workspace.mjs` + 根 `prepare` —— 把 `backend|frontend/node_modules/@doubulea/{shared}` 补成 junction，保证运行期可解析。
>
> 若 CI 或其他机器上符号链接正常，这两项都会自然失效/跳过，**代码无需改动**。

**三个分离要点**：
1. **业务代码 vs 基础设施**：`infra/` 独立成目录，compose 与镜像定义不散在根。
2. **后端 vs 前端**：平级两个目录，各有 `package.json` / `tsconfig.json` / `Dockerfile`，可 `cd` 进去独立安装、构建、启动。
3. **共享契约单独一层**：`shared/` 是编译期依赖，构建时内联进各自产物，**运行期不产生耦合**——前端部署到 CDN、后端部署到内网，互不影响。

### 4.0 三条全局口径（先定死，13 步都按它走）

1. **传输与协议只做一种**：**Streamable HTTP** + 协议 **2025-06-18**（本仓的**设计目标**）。
   `stdio` 传输 = **P2**（不做）、OAuth 2.1 = **P1**（不做）。但 **`auth_type` 列与 `oauth_config` 列先建出来**
   （表结构一次到位），免得 P1 再改表 —— 与 P0-1-23"`ref_id` 是多态外键、目标表分批到齐"是同一手法：
   **接口留位、能力不做**。
   ⚠️ **P0-2-1 实测订正（协议版本这件事的真相）**：官方 SDK 1.30.1 把请求的版本**写死**在
   `LATEST_PROTOCOL_VERSION` = **`2025-11-25`**（`client/index.js#connect` 的 `params.protocolVersion`），
   **没有 setter**，也没有"请求哪个版本"的入参。所以正确的口径不是"我们请求 2025-06-18"，
   而是 **"请求最新、接受降级、把协商结果留痕"**：
   · 服务端回 `2025-06-18` ⇒ SDK 接受，并 `transport.setProtocolVersion(它)`，
     此后**每个**请求都带 `mcp-protocol-version: 2025-06-18`（= 与设计目标一致，这条路径有断言）；
   · 服务端回一个**不在 SDK 支持集内**的版本 ⇒ SDK 抛裸 `Error` ⇒ 我们翻成 502 并在消息里列出支持集；
   · 握手时把「请求版本 / 协商版本 / 是否落回设计目标」记进 **info 级日志**（"留痕"的落点就是它）。
   ⇒ **P0 的硬要求收窄为一条：服务端回的版本必须落在 SDK 支持集内；落到 `2025-06-18` 时行为与设计一致。**
   这也意味着**"协议版本"不是我们可控的配置项**，所以 §4.3 的环境变量里**没有**它。
2. **用到的是 MCP 的一小片能力**：客户端侧只走 `initialize` / `tools/list` / `tools/call`；
   另外**支持服务端反向发起的 `elicitation/create`**（我们是应答方）。其余（resources / prompts /
   sampling / roots）**P0 一律不用**，也不要在 SDK 上顺手开出来。
3. **凭据的形态是"注册者定义模板、每个使用者填自己的值"**（`02` §九，核心定制点）。
   由此推出**两条硬约束**（后面的步骤都会被它们约束）：
   · **值永不回填**（任何响应体都不得含明文，`01` 决策 7 + `02` §九 不变式）；
   · ⇒ 因此 **`PUT` 凭据的语义只能是"只更新提交里出现的 key"（合并），不能是"整体替换"** ——
     整体替换在"值不可回填"的前提下会把用户没填的那些 key **静默清空**。**这条与 P0-1 的
     `agent_components`（整体替换）刻意相反**，理由写在 P0-2-4。

### 4.2 权限（MCP 一族：server 走行级判定、凭据走 `user_id`）

> ⚠️ **本节在 P0-2-12 改过一次**：原口径是"`/api/mcp/**` 一律登录即可，`mcp_servers` **没有 owner 列收窄**"
> （P0-2-2 的"第五族"，`01` 决策 22"全员可注册"的直接推论）⇒ **server 的改/删已收窄到注册者 + ADMIN**，
> 与 `03` §25 的"（`/mcp` 页面的操作按钮按 `canEdit`）"对齐。**建/看、测试、工具列表仍全员可用**。

**建/看一律"登录即可"**（与 knowledge-bases 同族）；**改/删 = 注册者 + ADMIN**（与 `agents` 同族，
判据 `shared#canEditMcpServer`）。⚠️ **凭据那几条路径的收窄不在角色上、而在 `user_id` 上**：
`GET/PUT/DELETE /api/mcp/credentials/**` 只能操作**自己**的凭据（`where:{serverId, userId}`），
**ADMIN 也没有后门**（与会话第四族同源：表里有没有 owner 列是判据）。⇒ 新表 `mcp_credentials`
必须有 `user_id` 且**每条查询都要带它**。

⚠️ **两个"凭据"别混（P0-2-12 起）**：`mcp_servers` 的**注册者**决定"**这台 server 能不能用**"
（测试 / 工具列表用它那份凭据），而**每个使用者**决定"**我这次调用能不能成**"（`tools/call` 用自己那份）。
两条判据各自独立、都要成立（§4 的 9.6 ① 与 `02` §9.3）。

| 资源 | 端点 | 谁能用 | 判据 |
|------|------|--------|------|
| server · **建/看** | `GET/POST /api/mcp/servers` | **全员（登录即可）** | 无 owner 列收窄（不变） |
| server · **改/删** | `PATCH/DELETE /api/mcp/servers/:id` | **注册者 + ADMIN** | `mcp_servers.created_by` ⇒ `shared#canEditMcpServer`（⚠️ **P0-2-12 起**，403） |
| server · **测试/工具** | `POST /:id/test`、`GET /:id/tools` | **全员（登录即可）** | **无角色判据** —— 它们是"使用"不是"编辑"，且**用注册者凭据**连上游 |
| 凭据 | `GET /api/mcp/credentials`（列表 = 我的 + 未配置清单） | 登录即可，**但只回我的** | `where:{userId}` |
| 凭据 | `PUT/DELETE /api/mcp/credentials/:serverId` | 登录即可，**但只能动我的** | `where:{serverId, userId}`，他人的 serverId 不是 404（server 是公开的）而是"写我自己的那份" |

⚠️ **为什么"测试"不给注册者专属**：它**不写任何人的东西**（只刷新 server 级的 `tool_cache` 与 `status`），
用的是**注册者**的凭据 ⇒ 让谁点都不串用户。收窄它只会造出"server 建完就没人能测了"（注册者离职/停用）。
**删除除外**：`DELETE` 会连带删掉**所有人的凭据**（`ON DELETE CASCADE`）⇒ 必须归注册者。

### 4.3 新增数据与契约（一次列清，避免每步临时发明）

- **表**：`mcp_servers` / `mcp_credentials`（`02` §三 已定义）。
  ⚠️ **`mcp_servers` 要补两列**（`02` §三 原文没有，P0-2 定案）：`slug`（**创建时从 `name` 生成、
  之后不变**的派生名，用于工具名前缀 —— 改名不改工具名是**刻意**的，见 P0-2-5）与 `updated_at`。
  ⚠️ **`mcp_credentials.values_enc` 的形态定案**（⚠️ **P0-2-4 落地时按"逐 key"收口，本节原写"整对象一个信封"已订正**）：
  该列是一个 JSON 对象 `{ <key>: "v1.<iv>.<tag>.<ct>" }` —— **每个 key 各自一个信封**（复用 `infra/crypto.ts`），
  **AAD = `mcp-credentials:{serverId}:{userId}.values_enc.{key}`**（含 serverId + userId + key，
  **刻意不含行 id**：写入走 `upsert`，加密那一刻还没有行）。逐 key 而非整对象，是为了让"**合并语义**"
  （只动提交里出现的 key）在密文层面也成立 —— 整对象加密的话，改一个 key 就得重写全部密文。
  绑定到 `(server, user, key)` 才是"把密文粘到另一格上解不开"的唯一保证（P0-1-10 的绑定层断言同款）。
  完整口径见 `02` §9.5。
- **信封形态（MCP 一族；⚠️ 本节原写的"第五族"是 P0-2-2 的叫法，P0-2-12 改/删收窄后 server 已与 `agents` 同族、凭据仍与 `conversations` 同族 —— 历史行里的"第五族"按历史记号读）**：`GET /api/mcp/servers` = `{items,total,offset,limit}`；
  `GET /:id/tools` = **裸 `{tools:[…], fetchedAt, cached}`**（`?refresh=1` 的三种出口见 P0-2-5）；
  `POST /:id/test` = **恒 200** + `{ok, tools?, error?}`（理由同 §六 第 17 条"探活端点自身是请求成功"）。
  ⚠️ **凭据三条的信封**（⚠️ **P0-2-4 订正，以 `02` §4.7 为准**）：`GET /api/mcp/credentials` = **裸 `{items, unconfigured}`**
  （**两面一起给、刻意不分页**）；`PUT /:serverId` = **裸 `McpCredentialItem`**；`DELETE /:serverId` = `{serverId, serverName}`。
  ⚠️ **凭据的读接口只回 `key` + `hasValue`，不下发值、也**不下发掩码****（P0-2-4 定案 —— 本节原写的
  "掩码只在值长度 ≥ 8 时给首尾各 2 字符"**已作废**）：那是每个人自己的令牌，下发掩码收益为零，
  而风险是把它塞进一个更多人能读到的通道（与 Provider Key 的 `apiKeyPreview` 刻意相反：
  那个是管理员配的一份、掩码用于"确认没配错"）。
- **环境变量（新增 3 个，登记 `infra/.env.example` + `infra/.env`）**：

  `MCP_CONFIRM_TIMEOUT_SEC`（确认等待上限，默认 120 —— `01` §3.6 的验收要点"取消后流程可继续"要靠它可注入才能验）、
  `MCP_TOOL_LIMIT`（单个 server 进 function 列表的工具数上限，默认 64，超限**截断并告警**）。
  ⚠️ 其余都是**代码常量**（轮次上限 10、超时 120s 的语义边界），不进 env。

| 决定二 | ★ **启动对账与周期对账的判据刻意不同**：**启动清掉全部** —— 理由不是"省磁盘"，而是**引擎是后端进程的子进程**（P0-3-5），进程一死容器里就没有对话者了，"活着但没人能跟它说话"，一律重建不复用（与 `子方案③` §九 4 "不恢复运行中的沙箱"逐字一致）；**周期只清"没有活会话的"** —— 判据 = 会话 `ACTIVE` ∩ 账本有活体行（`RUNNING`，或宽限期内的 `CREATING`）。宽限期专治"正在建"那一瞬，绝不能被误判成孤儿 |
| 决定三 | ★ **排队用 ZSET 而不是 List**（与 `pipeline/queue.ts` 刻意不同）：score = **入队时刻 epoch ms** ⇒ `ZRANK` 给位次（"1 = 下一个"）、`ZREMRANGEBYSCORE` 给**单项 TTL**，而这个 TTL **同时是等待预算**（"等了 10 分钟"的请求本来也不该再等）。认领队首**刻意不用 Lua**：先 `ZRANK` 判是不是我，再 `ZREM` 并把**返回值**当判据（只有"自己删自己那条"一种写者，够原子）。`ZADD NX` 保位次 ⇒ 重试不退到队尾 |
| 决定四 | ★ **配额作用域 = 单实例**（进程内**具名**名额册，`registry.ts` 刻意不 import 任何东西 ⇒ 可进"无依赖档"）。崩溃即归零 ⇒ 与"启动对账清空容器"配合，**账面与实际在重启后自动一致**（这是选"进程内计数"的主要理由之一）。⚠️ **扩容前必须先改配额作用域与孤儿回收归属** |
| 决定五 | **名额只在两个时刻变动**（拿到 / 回收），**失败路径必须还名额**：`createSandbox` 抛错后 `slots.remove()`；否则每失败一次漏一个槽位，且**重启才恢复**（症状"明明没人用却在排队"）。同理**队列非空时不允许直通**（否则后来者插队、FIFO 破功），且"队空判定"与 `tryAdd` 之间**没有 await**（放一个进来就是经典超发竞态） |
| 决定六 | ★ **两处"实测逼出来"的硬事实**（都写进了注释，别再靠推演）：① `OpenStdin: true` 且**不设 `Tty`** —— 否则容器起来就死；② **`docker rm -v` 删不掉具名卷** ⇒ 回收**必须两步**（容器 → 显式 `volume rm`），指望 `-v` 顺手清干净会得到"账本说回收了、卷还堆着"。另：`Mounts` 属 `HostConfig` 而非顶层（`@types/dockerode` 的类型逼出来的修正，`docker inspect` 里它也确实在 `HostConfig.Mounts`） |
| 决定七 | ⚠️ **本批内自洽修掉一处跨批次时区问题**（详见"已知问题"行）：`createSandbox` 的 `createdAt` **显式由 JS 侧写入**（不用 DB 的 `@default(now())`）⇒ 沙箱的两处时间判据（宽限期、活体窗口）全部落在 **JS 侧时区空间**，`SANDBOX_CREATE_GRACE_SEC` 的语义由此才是它字面上的值 |
| 参数 | **新增 4 项且都真消费**：`SANDBOX_QUEUE_KEY`(`sandbox:queue`) / `SANDBOX_QUEUE_TTL_SEC`(600) / `SANDBOX_REAP_INTERVAL_SEC`(60) / `SANDBOX_CREATE_GRACE_SEC`(120)；含**跨字段校验** `SANDBOX_CREATE_GRACE_SEC > SANDBOX_REAP_INTERVAL_SEC`（宽限期短于对账间隔 = 每轮都可能在"正在建"时误杀）。另：`SANDBOX_IDLE_TTL_MIN` 由 P0-3-1 的"只登记不消费"转为**真正消费**（空闲回收的唯一判据） |
| 一次实测 | 后端以 `LOG_LEVEL=info SANDBOX_REAP_INTERVAL_SEC=5 SANDBOX_IDLE_TTL_MIN=1 SANDBOX_CREATE_GRACE_SEC=30` 在**真 Docker（OrbStack 29.4.0）+ 真 PG + 真 Redis** 上跑，逐项取证：① **启动对账** `containers: 2/2`、`volumes: 2/2`、`removalFailures: 0`（预置 2 容器 + 2 卷后重启后端，`docker ps -a --filter label=…` 与 `docker volume ls --filter label=…` **都变空**）；② **周期对账一轮 tick**：扫到 `containers 2 / volumes 2` ⇒ `removedContainers 1 / removedVolumes 1`（★ **真会话那个被正确保留**）、`staleCreatingRows 1`、`rowsRecycled 0`、`queuePruned 1`、`removalFailures 0`，另有一条"清理了过期的沙箱排队项"WARN；③ **空闲回收**：`candidates 1 / reaped 1` + `沙箱已回收 reason=idle rows=1 slots=0/10`；④ **终态**：带 label 的容器与卷**全零**，账本两行分别是 `FAILED`（`errorMsg` = "创建未完成（超过宽限期未见容器就绪）"）与 `RECYCLED`。⚠️ 取证方式是**脚本驱动模块**（本批没有 HTTP 入口），证明的是"模块在真 Docker/PG/Redis 上的行为"，**不是**端到端功能 |
| 已知问题 | ⚠️ **跨批次（本批发现并记录，未做全局修）**：`infra/.env` 的 `TZ=Asia/Shanghai` 传给了 PG 容器 ⇒ 会话时区非 UTC，而 `@prisma/adapter-pg` 读写 `timestamptz` **各偏一个时区偏移且往返恒等**。本机实测（`DATABASE_URL` 指向本机 PG）：原始 SQL 写 `'2026-01-01 00:00:00+00'` ⇒ Prisma 读回 `2026-01-01T08:00:00Z`（**读 +8**）；Prisma 写 JS `2026-02-01T00:00:00Z` ⇒ 物理值 `2026-02-01 00:00:00+08` = `2026-01-31T16:00:00Z`（**写 -8**），读回又是 `2026-02-01T00:00:00Z`（**往返恒等**）。**后果**：凡「JS 侧时间」与「DB 侧生成时间（`@default(now())` / SQL `now()`）」进**同一个比较**处整体偏 8 小时；**纯 JS 侧比较不受影响**（所以平时看不出来，往返恒等）。全局修法 = 连接串加 `options=-c TimeZone=UTC` **并**把"由 JS 侧写过"的 datetime 列一次性 +8h 迁移 ⇒ **另立批次**，见 §七 待决 8 与 `02` §三 的"已知问题" |
