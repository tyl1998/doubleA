## 二·补、构建与部署分离约定（2026-09-20 定案）

用户诉求：**前后端能独立构建、独立部署**。本项目的实现方式（与 `02` §十二 部署形态联动）：

| 项 | 后端 | 前端 |
|----|------|------|
| 构建 | `pnpm --filter @doubulea/backend build` → `backend/dist` | `pnpm --filter @doubulea/frontend build` → `frontend/dist`（纯静态） |
| 运行形态 | Node 进程，容器化（`backend/Dockerfile`） | 静态资源，Nginx / CDN / 对象存储托管（`frontend/Dockerfile` 可选） |
| 部署位置 | 内网服务器，需访问 PG / Redis / MinIO / Docker daemon | 可与后端**不在同一台机器**，只需能调后端 API |
| 依赖服务 | `infra/docker-compose.yml` 起 PG / Redis / MinIO（不含 app） | 无 |
| 共享代码 | `shared/`（编译期内联，**运行期零耦合**） | 同左 |

**关键说明**：
- 前端产物是**纯静态**（Vite build），部署时不需要 Node 运行时，也不需要知道后端在哪台机器（通过构建期 `VITE_API_BASE_URL` 或运行期同源反代决定）。
- 后端**不负责托管前端静态资源**（`02` §十二 原写「app 容器含前端静态资源」是单容器简化形态；独立部署时改为前后端各自部署，用网关按路径分流 `/api` → 后端、`/*` → 前端）。
- 两者唯一必须一致的只有**接口契约**，由 `shared/` 在编译期强制保证。

### 3.0 仓库最终形态（先定死，后面所有路径都以此为准）

**形态决策：单仓 + pnpm workspace；前后端平级分离。**

> **为什么不分两个仓库（2026-09-20 已讨论并定案，不再重开）**：
> 用户诉求是「前后端**独立构建、独立部署**」——这个诉求 monorepo 已完整满足：`pnpm --filter` 分包构建，前后端各自产出 `dist`，可分别部署到不同机器/容器/静态托管，运行期零耦合。**分仓需要额外解决的问题（50 个端点 + 10 个 SSE 事件的契约同步）在本项目里代价高于收益**：SSE 是流式契约，类型漂移不会立刻暴露，属于最难查的一类缺陷；而分仓带来的收益（多团队各自独立发布、各自走审批）在本项目（内部工具、单人/小团队）拿不到。故维持单仓，仅把目录整理为平级清晰形态。
> 若将来后端要开放给其他系统消费，届时再引入 OpenAPI 生成类型（`@fastify/swagger` → `openapi-typescript`），作为**增量**加上，不影响当前结构。

**独立构建 / 独立部署的实现方式**（写进各包 `package.json` 的 scripts）：

```powershell
pnpm --filter @doubulea/backend  build      # 只构建后端 → backend/dist
pnpm --filter @doubulea/frontend build      # 只构建前端 → frontend/dist
pnpm --filter @doubulea/backend  dev        # 只起后端开发服务
```

> **⚠️ 本机两处非默认设置（P0-1-1 代价）：**
> 1. `pnpm-workspace.yaml` 里 `nodeLinker: hoisted` —— 本机 pnpm 无法建目录符号链接（Windows 未开开发者模式，且失败时静默），isolated 布局下各包 `node_modules` 只剩空目录。
> 2. `infra/scripts/link-workspace.mjs` + 根 `prepare` —— 把 `backend|frontend/node_modules/@doubulea/{shared}` 补成 junction，保证运行期可解析。
>
> 若 CI 或其他机器上符号链接正常，这两项都会自然失效/跳过，**代码无需改动**。

**三个分离要点**：
1. **业务代码 vs 基础设施**：`infra/` 独立成目录，compose 与镜像定义不散在根。
2. **后端 vs 前端**：平级两个目录，各有 `package.json` / `tsconfig.json` / `Dockerfile`，可 `cd` 进去独立安装、构建、启动。
3. **共享契约单独一层**：`shared/` 是编译期依赖，构建时内联进各自产物，**运行期不产生耦合**——前端部署到 CDN、后端部署到内网，互不影响。

  3. **bcrypt 用原生包且不需要编译器**：`bcrypt@6.0.0` 自带 `prebuilds/`（darwin-arm64 / win32-x64 / linux-x64 glibc+musl 都有），`node-gyp-build` 只负责挑平台文件 —— 但仍**受 `allowBuilds` 管辖**，不登记会 `ERR_PNPM_IGNORED_BUILDS` 失败退出（§六 第 22 条）。本机实测 cost 12 ≈ **225ms/次**
  4. **⚠️ `DUMMY_PASSWORD_HASH` 必须是"结构合法"的摘要**：实测 bcrypt 6 对结构非法的摘要（如 `'not-a-hash'`）`compare` **立刻返回 false（0ms）**、不抛错 —— 那样等时比较**完全失效**。故该常量由 `bcrypt.hash(随机串, 12)` 生成（60 字符、cost 12），供 P0-1-7 在"账号不存在"路径上跑一次以对齐耗时；`verify:app` 里已加断言守住它的形态
  5. **超长密码显式拒绝，而不是让它被静默截断**：bcrypt 只处理前 **72 字节**，`"a"×72+"x"` 与 `"a"×72+"y"` 会被判成同一密码。`hashPassword` 按**字节**（不是字符，中文/emoji 一字多字节）判断超限并抛 `RangeError`；**校验侧刻意不做长度判断** —— 否则超长输入的登录会走另一条报错分支，等于泄露密码长度特征。密码策略的长度上限放 P0-1-7 的路由层
  6. **会话令牌刻意不签名**（推翻"Cookie 要签名"的直觉）：值是 32 字节 CSPRNG 随机串（43 字符 base64url），**身份的真相在 Redis**；签名只能证明"这串没被改过"，而改成一串无对应键的随机值同样会被判无会话 → 签名不增加任何安全属性，只多一个要轮转的密钥
  7. **会话「半衰期滑动续期」**：值里存 `renewedAt`，只有已用掉的有效期过半才重写 `session:{sid}` —— 若"每请求都续"等于每个请求一次 Redis 写（登录后前端会并发若干初始化请求），收益只是把过期点往后推几秒。实测：半衰期前**值不变**、过半后值变且 TTL 变长、到期后读不到（`verify:session` 用 TTL=2s 的独立会话验的）
  8. **`user.status` 校验缓存的是「整份快照」而不是只缓存 status**：`auth-user:{userId}` → `{id,username,role,status,mustChangePassword}`（TTL 默认 60s）。只缓存 status 的话其余字段每请求仍要回库，等于没缓存；`role` 是 `requireAdmin` 要用的、`mustChangePassword` 是 P0-1-7 首登闸门要用的。**不含 `passwordHash`**（§六 第 7 条 密钥零下发）
  9. **坑预判落地为「写侧必须主动失效」**（`invalidateUserSnapshot(userId)`，P0-1-8 的启停/改角色/重置密码都要调）：不调则窗口内仍放行；调用则**立即** 401。缓存只兜底"有人直接在库里改状态"。该函数写失败**故意向上抛**，与 `writeUserSnapshot` 的"写失败只告警"刻意相反 —— 失效是正确性要求，缓存只是性能优化。同理：**删用户**也只在窗口过后才被发现（脚本第 10 项专门等过窗口再断言）
  10. **「会话存储不可用」映射成 500 而不是 401**：Redis 挂了是服务端依赖故障，不是"你的凭据不对"——映射 401 会把所有在线用户踢回登录页（还以为是会话过期），运维也只看到 401 而非 5xx，容易把依赖事故当鉴权问题查。同时**「无 Cookie」这一条刻意不碰 Redis**，故依赖不可达时它仍是 401（匿名/探测请求不该打在依赖上）。这两条在 `verify:app` 的有/无依赖两种模式下都有断言（degraded → 500 INTERNAL，本机 → 401）
  11. **鉴权失败一律自毁会话**：会话不存在/过期 → 401 + 清 Cookie；用户已删 → 401 + 删会话键 + 清 Cookie；`status=DISABLED` → 401「账号已停用」+ 自毁。客户端那枚 Cookie 已无意义，留着只会让每个请求重复走一遍失败路径
  12. **`requireAuth`/`requireAdmin` 是装饰器而非插件**：`decorateRequest`/`decorate` **必须直接调用**（走 `register` 只装饰该插件作用域，根作用域的路由拿不到 —— `installErrorHandler` 同款坑）；只有 `@fastify/cookie` 是用 `register` 进的队列（在 `onRequest` 阶段解析，早于路由的 `preHandler`）。`request.auth` 默认值用 `null` 而非 `undefined`
  13. **新增 3 个环境变量**（`infra/.env.example` + `02` §十一 已同步）：`SESSION_TTL_HOURS`（12）、`USER_STATUS_CACHE_TTL_SEC`（60）、`SESSION_COOKIE_SECURE`（留空 = 跟随 `NODE_ENV`，生产 true）。生产显式关掉会启动 WARN —— 内网若确实 HTTP 直连，带 `Secure` 的 Cookie 会被浏览器**直接丢弃**，症状是"登录成功却立刻未登录"，比明文传输更难排查
  14. **Cookie 名不做成环境变量**（`doubulea_sid` 常量，写在 `plugins/session.ts`）：同域名下前后端各配一个名字，"登录成功但仍未登录"会变成最难查的一类问题。且登录与登出共用**同一份选项对象** —— 属性（path/secure/sameSite）不一致时浏览器不会覆盖旧 Cookie，表现为"点了登出还是登录态"
  15. **`@fastify/cookie` 的类型口径**：该包是 `export =`（CommonJS）形态，**import 不到** `CookieSerializeOptions` 这个名字；选项对象的类型改从 `Parameters<FastifyReply['setCookie']>[2]` 取，既绕开命名空间问题，又让 `satisfies` 真的校验属性名与取值
  16. **验收脚本分两档**（§六 第 6 条纪律）：`verify:app` 增补**不需要依赖**的断言（密文/密码/初始密码/未登录出口），新增 `verify:session`（**需要真实 PG+Redis**）验会话行为；后者自造带随机后缀的临时 ADMIN/MEMBER 用户并在 `finally` 里删净（含 Redis 键）—— 实测跑完 `users` 无 `verify-session-%` 残留、Redis 键为空。脚本把 `LOG_LEVEL` 收敛到 `error`（否则几十条"应当失败"的请求 warn 会淹掉断言结果），要看细节用 `LOG_LEVEL=debug pnpm verify:session`
  17. **依赖**：backend 加 `bcrypt@^6.0.0`（install 脚本 `node-gyp-build` → 需 `allowBuilds`）、`@fastify/cookie@^11.1.2`（无 install 脚本），devDep `@types/bcrypt`；根新增 `pnpm verify:session` 转发

  4. **重置密码的两个连带动作**（文档没写、但不做就是"重置没生效"）：① `invalidateUserSnapshot` —— 否则该用户**在线的**会话不会被首登闸门拦住（最长 60s 空档）；② **清登录失败计数** —— 现实中重置密码往往正因为对方连错 5 次被锁，不清计数的话重置完还要再等 10 分钟。验收里两条都有专门用例（含"连错 5 次 → 429 → 重置 → 新密码**立即**能登录"）
  5. **密码痕迹的检查要分两层**（写验收时差点自相矛盾）：**值/哈希**（`passwordHash`/`password_hash`/`$2b$`/明文）在任何响应里都不许出现；而 `initialPassword` 这个**键名**在建号/重置的响应里本就该出现，只有列表/详情类响应才要求它也不出现。混在一个清单里会让"正确实现"被判失败
  6. **Prisma 唯一冲突的处理要两道**：先 `findUnique` 查一次（给出可读的「用户名已存在」），再在 `create` 上 `catch` 唯一约束错误（并发下的兜底）。错误码判定用**鸭子类型**（`error.code === 'P2002'` / `'P2025'`）而不是 `instanceof PrismaClientKnownRequestError` —— 后者的错误类来自生成物的内部路径，跨模块/跨构建产物做 `instanceof` 容易因"两份类对象"而失效，错误码字符串反而是稳定契约。实测：**大小写不同的同名**（`Verify-Users-Created-X` vs `verify-users-created-x`）同样 409 —— 归一化真的生效了
  7. **分页的两条硬要求**：① **稳定排序**（`username` 升序 + `id` 兜底），否则翻页会重复/漏项；② 用 `$transaction([findMany, count])` 取"当页 + 总数"，否则两者可能来自不同快照，分页器看着会错位。验收里断言"limit=1 的两页互不重复、total 稳定、按 username 升序"
  8. **建号返回 `200` 而不是 `201`**（口径记录，免得下批或前端以为是漏了）：`02` §四 的错误出口口径是「`code` 是唯一契约，HTTP 状态码是辅助信号」，成功侧同理用 `200` + `code=0`，不在本项目引入 201 这种"要前端多一个分支"的差别
  9. **首登闸门会拦住"首登态的 admin"调用户管理**（接线注意点）：闸门白名单只有 `/api/auth/{login,logout,me,password}`，`/api/users` 不在其中 —— 所以**种子脚本造的"首登改密态 admin"必须先改密才能建号**（P0-1-9 的门槛 1 正是这个顺序）。验收脚本里"操作者"账号因此必须建为非首登态，否则整批断言会全线 403
  10. **`initialPassword` 进日志脱敏清单**（`infra/logger.ts` 的 `LOG_REDACT_PATHS`）：代码里已经只记 id/username，但"顺手 log 整个响应对象"时它是最容易被带出去的字段 —— 契约层"只在响应里出现一次" + 日志层"出现也打码"，两道都留
  11. **新增产出**（计划外但绕不开）：`shared/src/user.ts`（前后端共用契约：`UserListItem`/建号/改角色/分页 schema/`initialPasswordResultSchema`，前端 `/admin/users` 页直接用）、`envelope.ts` 补 `OffsetPage<T>` 与 `offsetPageOf()`（通用分页 schema 工厂，模型池/知识库列表也会用）、`scripts/verify-users.mjs`
  12. **依赖与变量**：**零新增依赖、零新增环境变量**

  5. **种子脚本的 `console` 需要 ESLint 例外**（`eslint.config.mjs` 的脚本 override 加了 `**/prisma/seed.ts`）：业务代码禁 console 是为了"日志必须走 pino（带 requestId + 脱敏）"，而种子脚本是 **CLI**，stdout 就是它的接口。安全侧没有放松：`LOG_REDACT_PATHS` 早已含 `initialPassword`（P0-1-8 加），"顺手 log 整个对象"仍会被打码
  6. **「端到端」的关键是换掉传输层**：前四个脚本都走 `app.inject`（跳过 HTTP 传输层：`Set-Cookie` 序列化、Cookie 回传、连接复用、bodyLimit…都在那一层）。本脚本 `spawn` 真实进程并用 `fetch` 打 `http://127.0.0.1:<独立端口>`，全程无测试后门 —— 因此"它能跑通 ⇔ 用户 curl 能跑通"。实测两种方式行为**完全一致**（含 403/429 文案），但这是验出来的、不是假设的
  7. **门槛 3 的"业务 API"本仓还没有**（`/api/agents` 是 E 包），若照字面找一个"业务 API"只能拿到永远 403 的路径。替代判据 = **用 403 的文案区分两条本质不同的 403**：改密前是闸门文案「首次登录必须修改密码后才能使用其他功能」，改密后是权限文案「该操作仅限管理员」。断言"改密后 msg 必须不再含'修改密码'"即等价于"闸门已放行 + 权限判定生效"；E 包落地后可升级为直接 200
  8. **验收脚本的两条工程经验**：① **子进程端口先探再用** —— 起进程前先 `fetch(/health)`，有应答就报错退出（否则请求会打在一个陌生服务上，症状是莫名的 404）；默认端口取 **13099**，刻意不占用户的 13000。② **"跑完干净"写成断言** —— 清理不是 finally 里的尽力而为，而是「停服务 → 清 Redis → 按 `verify-e2e-` **前缀**扫账号 → 断言残留账号 0 / 各 `login-fail:*` 与 `session:*` 均不存在」（按前缀而不是内存清单：跑到一半崩了内存清单就丢了）。本次实测清 3 个账号 / 7 个会话键
  9. **手工走查会留下"不可用状态"，收尾必须复位**（流程约定，下次端测照做）：先 `SEED_RESET_PASSWORD=1 SEED_ADMIN_PASSWORD=… pnpm db:seed` 拿到已知密码，但走查第 ⑤ 步会把 admin 的密码改掉并置 `mustChangePassword=false`；若就此收工，用户拿到的是"密码已不是我告诉你的那个"的环境。故走查后必须：`SEED_RESET_PASSWORD=1 … pnpm db:seed` 复位 + 删掉走查期间建的账号 + 清 Redis 键

#### P0-1-10 Provider 管理  `[✓]` 2026-09-21
- **内容**：`routes/modelProviders.ts` + `services/model.service.ts` 前半 —— CRUD（`02` §4.3）；`api_key` 写入即 AES-256-GCM 加密落 `api_key_enc`；**读接口一律脱敏**（返回 `sk-****abcd` 形态或 `hasKey: true`，绝不下发明文，`01` §3.2 验收要点）；`type ∈ {CHAT, EMBEDDING}`；`enabled` 开关。
- **产出**：`backend/src/routes/modelProviders.ts`、`backend/src/services/model.service.ts`
- **前置**：P0-1-5（表）、P0-1-6（crypto）
- **验收**：创建带 Key 的 provider → 查询返回**不含**明文 Key；数据库 `api_key_enc` 是密文；PATCH 不传 Key 时原 Key 保持不变
- **坑预判**：PATCH 的三态语义（缺省不动 / null 清空 / 有值写入）→ 参考参考项目 `update_endpoint` 同款三态，前端不易误清空
- **落地要点**（12 条，详见 `02` §4.3 契约增量 与 §10.2）：
  1. **出口只有一个 `toItem`**：`api_key_enc` 会被查出来（要算掩码），但只能经它变成 `hasKey` + `apiKeyPreview`；`verify:app` 里有一条**键级断言**（输出形态的键集合不得含 `apiKey`、也不得含任何带 `enc` 的键），防"以后有人顺手 select 出去"。
  2. **掩码规则**（`maskApiKey`，纯函数放 shared）：≥16 → `前3+****+后4`；8~15 → `****后4`；<8 → `****`。掩码是**解密后**取首尾生成的，所以"能看到掩码"顺带证明密文解得开。
  3. **掩码取的是首尾而不是"额外存一段尾巴"**：多存一份尾巴等于把 Key 的尾巴明文落库，反而多一个泄露面。
  4. **AAD 绑定到记录**：`providerKeyAad(id)` = `model-providers:{id}.api_key_enc`，写/读两侧共用同一函数（单点，防写读用错）。收益：密文被粘到另一条记录上就解不开（实测：粘过去后该条 `hasKey:true` 但预览降级为 `****`）。
  5. **建 Provider 必须用事务**：AAD 含 `id`，而 `id` 由 Prisma 在 create 时生成 → 只能"先落行拿 id，再加密写回"。两条独立语句中间失败会留下"建好了但 Key 没写进去"的 Provider，而调用方看到失败会重试再建一个。PATCH 不需要（id 已知）。
  6. **解密失败不掀桌**：预览降级 `****` + warn，`hasKey` 仍 true。否则主密钥一换，列表接口整页 500，管理员连"哪个 Provider 的 Key 坏了"都看不到。
  7. **三态的实现落点**：契约层用 `.nullable().optional()`（**不加 `.default()`**），服务层 `undefined → {}`、`null → { apiKeyEnc: null }`、字符串 → 写入密文。空串被契约拒掉（400，文案直接说"要清空请传 null"）。
  8. **最强的那条验收是"密文逐字不变"**：PATCH 改名后比对库里的密文与改前**完全相同**（不是"重新加密了一次"，否则 IV 变化会让它不同）—— 这条能抓出"每次 PATCH 都重写 Key"的实现。
  9. **`baseUrl` 归一化去尾斜杠**：将来拼 `/chat/completions` 不能出现 `//`（有的网关当 404）。只在契约层做一次 transform，前后端对"存下来的到底是什么"无分歧。同时只允许 http(s)，其它 scheme 一律拒（这个值会被后端拿去发请求，放宽等于放大 SSRF 面）。
  10. **改 type 的守卫**：`model_providers.type` 与 `models.type` 冗余 → 有模型时改 type 一律 409（同值 PATCH 放行）。级联改模型的 type 会静默改变"已绑定 Agent 的模型类型"，比报错更糟。
  11. **删除的前置检查**：`agents.model_id` 是 `ON DELETE RESTRICT`，有模型被 Agent 引用时删 Provider 会撞外键抛 500 → 先数一遍（`agents: { some: {} }`）再 409。⚠️ **软删的 Agent 仍占外键**，计数刻意不按 `deletedAt` 过滤，否则"提示说能删、删下去却 500"。
  12. **`name` 不做查重**：表上没有唯一约束（`02` §三），服务层刻意不造一条"看起来唯一、并发下不唯一"的规则；要唯一性应先加约束再改代码。

  2. **拆路径，且按"用途"而不是按"角色"分投影** —— 这是本批最要紧的一条。管理列表 `GET /api/models`（仅 ADMIN，含停用项、`agentCount`、分页）vs 可选列表 `GET /api/models/available`（登录即可，只含 `enabled` 且 Provider `enabled` 的，精简投影）。若按角色分：`03` §4.2 的智能体编辑页里 **ADMIN 的模型下拉会看到停用模型**，直接违反 `01` §3.2「无效模型创建 Agent 时不可选」（ADMIN 也要建 Agent）。故 `03` §116 的 `GET /api/models?type=CHAT` 已同步改为 `/api/models/available?type=CHAT`。

  5. **zod v3：`required_error` 与自定义 `errorMap` 互斥**，同时给会在**模块加载期** `throw`（`typecheck` 完全查不出来，进程 import 就死）。"必填"文案改由 `errorMap` 分派 `invalid_type` 产出；verify:app 有一条断言守着这句文案。
  6. `maxContext` 三态（同 Provider 的 `apiKey`）：缺席不动 / `null` 清空 / 数字设置；缺省落 `NULL`。

  12. 模型**没有**对 `providerId` 的 `PATCH` 迁移能力，也没有"按 Provider 名排序"——管理页分组交给前端，服务层排序键保持与分页结果可解释（`createdAt asc, id asc`）。

  5. **SSE 帧会被 TCP 切碎**：按行缓冲、与网络分片解耦；验收脚本**故意把一帧拆成两次 `write`**（`data: {"cho` + `ices":…`）。
  6. **六类差异一并收敛**：保活帧（`choices: []` / 只有 role 的首帧 / `:` 注释行）、思考增量（`reasoning_content` 与 `reasoning` 两种写法）、`delta.content` 是数组、忽略 `stream:true` 的实现（按非流式降级）、畸形帧（跳过 + 计数 + warn，不丢整条回答）、`200` 里藏 `{error}`（显式抛 502，否则表现为"答了个空"）。
  7. **⚠️ 中断必须在每帧之前显式查一次信号**（本条是**跑验收才暴露**的实现 bug）：一帧才几十字节，网关常把整个响应塞进一个 TCP 包 → "abort 让网络读失败"根本不生效，症状是**"点了停止，回答还在往外冒"**。第一版就是这么写错的，被"中断后只应有 1 块增量"这条断言抓住。
  8. **⚠️ 超时守卫只能有"一个控制器 + 可重装的计时器"**（同上，第二个被验收抓出的实现 bug）：最初给"到响应头"与"流内空闲"各建了一个 `AbortController`，结果**流内空闲那个压根没接到 `fetch` 上** —— 计时器照常触发、标记照常置位，而读流的 `for await` 纹丝不动，症状是"配了 300ms 超时，脚本挂到天荒地老"（第一次跑 verify:llm 直接超时被 SIGTERM）。

  10. **`rawFinishReason` 保留上游原值**（`stop`/`length`/…），不在这层归一化成 `COMPLETE|STOPPED|ERROR` —— 归一化是 SSE 层（`02` §5.1）的职责，且会丢掉 `length`（被 `max_tokens` 截断）这种对上层有决策价值的信息。
  11. **密钥零下发的落点是"脱敏"**：上游 401 的 body 常回显 `Authorization`，所以**任何**进日志/错误消息的响应片段都先过 `redactSecret()`；日志只用 `describeTarget()`（id/名字/hasKey），绝不整体序列化 target。验收里有两条断言专门盯它（错误消息不含明文 Key；`remote-models` 响应体不含 `Bearer`）。
  12. **"拉上游模型列表"的两种"不"是刻意的**：**不要求 Provider 启用**（换 Key 后先探一次是正常诊断）、**不要求配 Key**（`GET /models` 在很多自建实现上免鉴权，本地 vLLM/llama.cpp/ollama 兼容层都属此类 —— 与 `resolveChatTarget` 要求的 424 相反）。与"只读"配套：验收断言"探完模型条数一条没变"。
  13. **三种返回形态归一 + 去重 + 按 id 排序**：标准 `{data:[…]}` / `{models:[{name|model}]}` / 裸数组；`items` 上限 500 且**显式**给 `truncated` + 真实 `total`（不做静默截断）。上游 404 时文案直接说"该实现可能不提供模型列表，请手工录入"。

  > 实测 `gin_bigm_ops` 的 `opcdefault = false`）。所以真实风险不是"静默建错"，而是"报错文案不点破该写哪个算子类" ——
  > 容易误判成"pg_bigm 没编进镜像"。断言因此不止于"索引存在"：还查 `indexdef` 逐字含 `gin_bigm_ops`、
  > 且全文路的 `LIKE` 真能命中它（见验收脚本与 `issue_fix`）。
- **落地要点**：
  1. **⚠️ 本批最大的坑不在坑预判里：手写 DDL 会被 Prisma 判成"多余对象"而生成 `DROP INDEX`**。P0-1-5 的 messages 分区结论（"Prisma 会主动跳过分区子表，无需处理"）**不能外推**到这里。实测 `migrate dev --create-only` 只要 schema 有任何别的改动就会生成：
     ```
     -- DropIndex
     DROP INDEX "idx_chunks_bigram";
     -- DropIndex
     DROP INDEX "idx_chunks_embedding";
     ```
     即"下一个批次动 schema 时，两条索引被**静默删掉**、检索退化成全表扫描"（P0-2 加 MCP 表时必炸）。两条处置不同：
     · **`idx_chunks_bigram` —— 在 schema 里声明**（Prisma 能表达）：`@@index([content(ops: raw("gin_bigm_ops"))], type: Gin, map: "idx_chunks_bigram")`。三个参数都不是可选的：`ops` 补算子类、`type: Gin` 否则按 btree 生成、`map` 否则每次 diff 都想把它改名成 `chunks_content_idx`（实测）。
     · **`idx_chunks_embedding` —— 藏进"部分索引"**：Prisma 7 没有 `Hnsw` 索引类型（`type: Hnsw` 报 Unknown index type），也没有 `WITH (m, ef_construction)` 的语法位置，于是迁移里建成**部分索引** `... WITH (m = 16, ef_construction = 64) WHERE kb_id IS NOT NULL`。Prisma **忽略带 `WHERE` 谓词的索引**（实测：普通 btree 与**表达式索引**都会被它检出并 DROP，唯独部分索引不看）。该谓词恒真（`kb_id` 是 NOT NULL 列）⇒ 索引内容与全量 HNSW 等价；且它被向量路的 `kb_id = $2` **蕴含** ⇒ 规划器照常使用。
     · **代价与守门**：这两个机制一旦失效（升级 Prisma/PG 后行为回退），后果是静默的。故 `verify:knowledge` 里有三条断言盯着：`migrate diff --exit-code` 必须为 **0**、HNSW 的 `indpred` 必须仍是 `(kb_id IS NOT NULL)`、以及两条路 `EXPLAIN` 真的命中各自索引。
     · 换 Prisma 版本前**先重跑这三条**（与 P0-1-5 的"升级前重跑分区探针"同一纪律）。
  2. **`chunks.embedding` 用 `Unsupported("vector(1024)")?`**（可空是硬要求）：Prisma 不认识 pgvector 类型，该列不进生成的 client ⇒ chunks 的写入/检索一律手写 SQL（P0-1-19 的 `INSERT ...   3. **主键类型把 `子方案①` §4-4 的草稿改掉了**：草稿写 `bigserial`，但 `02` §3.1 已定案「一律 `uuid(7)`」，且 `agent_components.ref_id`（P0-1-5 已落 `UUID`）将来要指向 `knowledge_bases.id` —— 不改就永远指不上。本批按 `02` §3.1 统一 `uuid(7)` 并同步改了 `子方案①` §4-4（**两张文档对同一条 DDL 给出不同口径属于文档腐烂，必须消掉其一**）。代价：`chunks.id` 由客户端生成，P0-1-19 的手写 INSERT **必须自带 id 数组**（已写进 P0-1-19 的坑预判）。

  6. **`documents` 的索引只加一条**（`@@index([kbId, createdAt(desc)])`）：既服务列表，`kb_id` 前缀也服务 §4-1 第 4 条的判重查询（单库千级文档下前缀+过滤够用）。**刻意不加** `UNIQUE(kb_id, content_hash)` —— 唯一约束会把 §七"同内容重传 → 200 内容未变化，已跳过"这条**业务语义**变成 409，与文档口径冲突。
  7. **三个新列的"为什么"写进了 schema 注释**：`content_hash` 是 sha256 十六进制的 64 字符（覆盖重建判重 + P0-1-17 worker 幂等的一半）、`chunk_count` 默认 0 而非 null（`PARSING` 就是"当前 0 个可用 chunk"）、`documents.file_key` 是 S3 键（删库时服务层负责连带清 S3）。

  9. **`EXPLAIN` 断言的写法值得单独记一笔**：小表上 PG 会**理性地**选 `chunks_kb_id_idx` + 排序（或 kb_id 索引 + 过滤）而不是 HNSW/GIN —— 那是成本模型正确的判断，不是索引坏了的信号。要验的是"这条索引**能不能**服务这个查询形状"，手法是关掉更便宜的退路（`enable_seqscan=off`，向量路再加 `enable_sort=off`）看它是否现身：**方向单向有效** —— 不可用的索引永远不会出现在计划里，"现身"即证明可用；反过来"没现身"不构成反证。全文路刻意去掉 `kb_id` 限定（留着它 GIN 就不露头）；且**不能**关 `enable_bitmapscan` —— GIN 的常规用法正是 Bitmap Index Scan。

  1. **解析是异步的：上传只做到 `PARSING`，本批刻意不做同步解析**（worker/队列是 P0-1-17）。上传 = 前置校验 → 落 S3 → 建 `PARSING` 行。验收里"四格式各传 1 篇均能解析出文本 + meta"验的是**解析器本身**（模块级真跑四个夹具生成的文件），**不是**"上传后立刻可检索"。切分理由是职责干净：同步解析会让 P0-1-17 退化成"把已经做完的事再异步做一遍"，且队列/幂等/重试的入口会有两个。

  1. **新增环境变量 `PIPELINE_QUEUE_KEY`（默认 `pipeline:jobs`）**：队列是"**被消费**"的资源，而 `REDIS_URL` 是共享的。两个进程（跑着的 dev server 与验收脚本、或同机两套部署）用同一条队列时，"谁取走 job"是随机的 —— 症状不是报错而是"验收时好时坏"。故键可配：`verify-pipeline` / `verify-documents` 一律注入 `verify:*` 前缀的独立键，`verify:e2e` 起的一次性进程也换键。（`docs/02` §十一 与 `infra/.env.example` 已登记。）
  2. **阻塞读必须走独立连接**（`infra/redis.ts#createRedisConnection`）：`BRPOP` 在返回前会占住整条连接，若复用会话单例，队列一空闲就会把 `/api/auth`、`/health` 与所有会话读写一起钉住 —— 而且**只在队列空闲时**才明显（有 job 时 BRPOP 立刻返回，一切正常），是最难联想的一类症状。验收里有一条专门盯它：BRPOP 挂起期间共享连接的 `PING` 必须 < 500ms 返回。收尾用 `disconnect()` 而不是 `quit()`：调用它的时机恰恰是 BRPOP 还挂着的时候，`quit` 会一直等下去（卡满退出宽限）。

  4. **幂等四道**（§三 只写了第 ④ 道）：① **同进程在飞去重**（同一文档的两个 job 被连着取走时只处理一次；本进程只有一个阻塞消费者，"取走 → 登记"之间没有窗口，故这条是**确定性**的，不靠运气）② 文档已删 ③ hash 不符（旧内容的 job）④ 已是 `READY`。四道全跳过时**一个字节都不写库**（验收断言 `updated_at` 逐字不变 **且** 阶段执行次数仍为 1）。反过来：`PARSING`/`FAILED` 且 hash 相符的 job **会真的处理** —— 这正是"重投能把文档救回来"的机制。
  5. **状态机的唯一定义在 `shared`**（`DOCUMENT_STATUS_TRANSITIONS` + `canTransitionDocumentStatus`）：`PARSING→{PARSING,READY,FAILED}`、`FAILED→PARSING`、`READY→PARSING`（重传/重建）。**刻意不允许 `READY→FAILED`** —— 那是"过期 job 把已成功的文档打回失败"的唯一形态，用户看到的是"内容明明能用却报失败"，且**无法自愈**（重投会被 READY 幂等规则跳过）。这条不变式没有任何 HTTP 路径能验到它（worker 是唯一写者），故在 `verify:app` 里用纯函数矩阵守着。
  6. **写状态一律走 CAS**：`updateMany({ where: { id, status: from } })` —— 非法转换**只告警不写**，且 `from` 取当前状态而不是硬写 `'PARSING'`；于是"上一次转换没成功"会自然导致下一次转换被判非法并拒绝写入（宁可这次白跑，也不越级写）。`count === 0` 表示状态已被别的写者改过，本进程不覆盖。
  7. **失败要区分"文档的问题"与"基础设施的问题"**：阶段抛错 → `FAILED` + `error_msg`；而**读行/写状态本身就失败**（PG 挂了）→ 不写状态、只记日志 —— 把"我们查不了"写成"这个文档坏了"，会让用户去重传一个其实没问题的文件。代价是文档停在 `PARSING`，正是重试入口覆盖的场景。
  8. **`error_msg` 是给用户看的** ⇒ 文案纪律：每条都按"用户能不能照着做点什么"写（如「原文件读取失败：对象存储里找不到《重试.pdf》，请重新上传该文档」），bucket / S3 键 / 堆栈只进日志。阶段抛出 `AppError` 的消息被原样采用；非 `AppError`（编程错误）加「内部错误：」前缀并截断 300 字。
  9. **上传与入队是同一件事的两半**：入队失败必须把"① 登记"**整个回滚**（删行 + 删对象）。只留 ① 的后果最坏 —— 那行永远是 `PARSING`、没有任何人会消费它，而用户重传还会被判重命中跳过（连新行都不建）⇒ 界面上出现"上传成功、永远转圈、重传也没用"的文档。验收用**子进程注入死 Redis** 做 A/B 对照：真 Redis 那次必须成功（证明探针本身是通的，否则"失败"可能是别的原因造成的假通过）。
  10. **worker 的生命周期归进程入口，不进 `buildApp()`**：它是"进程级后台组件"而 not"HTTP 应用的一部分" —— 放进 `buildApp()` 会让所有走 `app.inject` 的契约验收（`verify:app`）被迫连 Redis，还会莫名开始消费队列里的任务。`index.ts` 在 listen **成功之后**才 start（绑定失败就没必要开始消费），优雅退出时**先** stop 再关连接（否则 worker 会拿着已关闭的连接继续处理，日志里出现一堆假故障）。
  11. **阶段数组 + 可注入（`stages.ts`）**：本批阶段只有 `load-source` 与 `parse`（④ 空文本检测与 ⑤ 分块属 P0-1-18，⑥ embedding 与 ⑦ 入库属 P0-1-19）；`startPipelineWorker({ stages })` 让验收能塞一组慢速假阶段，从而**确定性**地观测并发闸与幂等（E 组：8 个 200ms 任务，峰值并发恰为 2，总耗时 ≥ 4 轮）。这就是"骨架"的具体含义：后两批各插一个阶段，worker 的并发/幂等/失败处理**一行都不用改**。另外 `parse` 阶段**再跑一次** `detectFormat`：上传时校验的是客户端发来的字节，这里读到的是**存储里的字节** —— 验收里"对象被换成文本 ⇒ FAILED 且原因是「文件内容与扩展名不符」"正是它（顺带证明阶段跑的是真逻辑而不是桩）。
  12. **⚠️ 本批的 `READY` 还不是"可检索"**：解析成功即置 READY，而 `chunk_count` 仍是 0、chunk 一行也没有（⑥⑦ 属 P0-1-19），空文本检测也还没做（⑤ 属 P0-1-18）⇒ 这个中间态下"扫描件"（解析出 0 字）同样会变 `READY`。验收把 `chunkCount === 0` 写在明处，避免下一个人把它当 bug。
  13. **可观测**：`getPipelineWorkerStats()`（`running` / `concurrency` / `stages` / `inFlight` / `peakInFlight` / `processed` / `failed` / `skipped` 按原因分组）。它既是"并发没超过上限、也没白跑"的断言依据，也是将来运维面板或 `/health` 的雏形（本批**刻意未**接进 `/health`，那不是本批的范围）。
- **坑预判取证**：⚠️ 预判**成立**（"List 无 ack ⇒ 不能假设队列必达"）：`BRPOP` 取走即出队，worker 在 `finally` 之外崩溃时那个 job 就没了。本批把"补救"做成**协议层成立**的事 —— `PARSING`/`FAILED` 且 hash 相符的 job 会被真的重新处理，于是"重投同一个 job"就是可用的重试手段（验收 F 组：对象丢失 → `FAILED` → 补回对象 + 重投 → `READY`，`error_msg` 被清空）。P0-1-19 的 `POST .../retry` 只是给这件事加一个端点与权限，机制已就位。

  8. **小文档特例判在"全文"而不是"每个 Section"**：一份 200 字、带 3 个标题的通知若按 Section 判会变成 3 块，而验收原句要的是"恰好 1 个 chunk"。反过来全文超阈值时，Section 仍按"装得下就整块装"处理 —— 这正是 hybrid 与 fixed 的区别（保结构）。
  9. **句末边界集合比文档多一个 `\n`**：段落末尾本身就是最自然的切点，而 `blocks` 之间就是以 `\n\n` 连接的；少了它，"一段正好超长"的文档只能退化成硬切。另设**回退下界 = `chunk_min`**（最近的边界落在 `chunk_min` 之前说明这一大段几乎没有句读，如长表格转文本，此时回退只会切出碎块，不如按长度硬切）。
  10. **重叠只发生在同一个 Section 内**，且 meta 反查页码用**段内偏移（不含重叠前缀）**：跨 Section 的重叠会把两段不相干的内容缝在一起；用重叠前缀定位页码则会把这一块说成上一块所在的页。

- **坑预判取证**：⚠️ 预判**成立**且验收把它钉住了 —— `chunk_size` 的单位是**字符（码点）**，不是 token、也不是 UTF-16 长度。`fixed` 用 `text.slice()` 就会**劈开代理对**（`'😀'.length === 2`），产出非法字符串且**本层毫无报错**（下游 embedding 才炸）；本批所有切片一律建在 `[...text]` 的码点数组上，验收有一条专门的"600 个 emoji 按 `fixed` 切，每块逐码点都是 `😀`"。另外两条实测补充：① `'😀'.length` 与 `[...str].length` 的差异已在 P0-1-16 用 `countChars` 钉过，本批沿用同一口径（`chunkSize`、`charCount`、`chunkMin` 三处必须同源，否则会出现"提示 0 字符却又不判空"这类自相矛盾）；② **PDF 夹具必须折行**：单条超长 `Tj` 会超出 `MediaBox`（612pt 宽），而 pdf.js 只提取**页面框内**的文本 ⇒ 内容被**静默截断**（实测 561 字的单行只析出 85 字）。这不是实现问题，但会让"分块/阈值"类断言拿到假数据，已写进 `issue_fix`。

- **落地要点**（11 条，细节见 `issue_fix/问题记录-P0-1-19-入库+覆盖重建+失败重试.md`）：
  1. **阶段数组到本批才完整（八步）**：`load-source → parse → detect-empty-text → chunk → embed → index`。至此 `READY` 的含义才是**"可检索"**（`chunks` 表有行、每行都有向量、`chunk_count` 与之一致）。仍差的是**检索端点本身**（P0-1-20）与文档列表端点（P0-1-21）。
  2. **插 ⑥⑦ 时 `worker.ts` 一行未改** —— 阶段数组买到的东西兑现了：P0-1-18 插入 ④⑤ 时只改了 `JOB_DOCUMENT_SELECT`（阶段间的数据契约），本批连它都没动（`chunks`/`vectors`/`embeddingName` 全在上下文里流转）。
  3. **⚠️ 写入路径刻意偏离 `§4-4` 草稿的 `INSERT ... SELECT unnest(...)`**：草稿要求"自带 id 数组"，而 `chunks.id` 的口径是 `uuid(7)`（`02` §3.1），且 P0-1-16 已定案**不手搓 uuid7** ⇒ `uuid(7)` 在本仓只有 Prisma 的 `@default` 一个实现。故实际做法是 **Prisma 建行（拿 id）→ 手写 `UPDATE ... FROM unnest(...)` 回填向量**，两步在**同一事务**里。代价是一条额外的 `UPDATE`（一条 SQL 一批，不是 N 条），换来"id 只有一个来源"。**验收里有一条"id 的版本位必须是 7"**专门守它 —— 那条断言是唯一能抓住"某天有人换成自搓 id"的东西。
  4. **事务的边界是"删 + 建 + 回填"三步一起**：`DELETE WHERE doc_id` → `createManyAndReturn` → `UPDATE ... unnest`。中途失败必须回到"旧的那一份"或"没有"，不能出现半新半旧 —— `§七` 的"无重复、无孤儿"在代码层面就是这一条。验收除了数条数，还查了**全库孤儿**（`LEFT JOIN documents ... WHERE d.id IS NULL` 必须为 0）。
  5. **embedding 的重试落在"批"粒度**（`§4-3` 的"单批失败重试 2 次，退避 1s/3s"）：provider 的 `embed()` 会自己按 `batchSize` 切批，它看到的永远是"一次调用" ⇒ 本层先把文本按 `EMBEDDING_BATCH_SIZE` 切好、每次只喂一批，重试边界才与"批"对齐。**一批仍失败 ⇒ 整篇 FAILED**（跳过这批写进去的向量缺失是**看不见**的坏数据：那些 chunk 永远排不上号，而界面上一切正常）。
  6. **`chunk_count` 只在 ⑦ 成功之后才写**（P0-1-18 的反面）：worker 用 `ctx.chunkCount`（= 真实写入行数）落那一列，验收同时断言它与 `chunks` 表行数**逐行一致**、且**没有 `embedding IS NULL` 的行**。
  7. **覆盖重建的三个"没做"**（`content_hash` 相同时）：不落新对象、不删旧 chunk、不入队。取证方式要能分辨"没做"与"做了但结果相同" —— **chunk 行 id 逐字不变**（重写过就会换新 id）、文档 `updated_at` 逐字不变、对象数不变、队列深度 0。
  8. **⚠️ `file_name` 也一并更新（对 `§七` 列清单的刻意补全）**：`§七` 的 `UPDATE` 只列了 status / error_msg / content_hash / file_key / chunk_count。但 `file_name` 在本仓还承担 P0-1-21 下载端点的 `Content-Disposition` 文件名 —— 旧名字留着就会**说谎**（列表演示旧名、下载下来的字节却是新文件），而用户没有任何别的入口改名（只能删掉重传，那会丢掉文档 id）。已同步写进 `子方案①` §七 的落地口径。
  9. **覆盖重建与上传的"入队失败"补偿**能力**不对称，且必须如实说明**：上传能整次回滚（行是它刚建的）；重建做不到 —— 旧 chunk 删了就回不来。故重建的入队失败处理是"如实报告 + 指向可用的恢复手段"（`POST .../retry`），而不是伪装成"什么都没变"。这也是 `retry` 必须**放行 `PARSING`** 的原因之一（见下一条）。
  10. **`retry` 的状态口径**：`FAILED` 常规重试 / **`PARSING` 放行**（这是"worker 崩了、入队丢了"的**恢复入口**，P0-1-17 就是照这个口径设计的；若因"看起来正在处理"就 409，卡住的文档将没有任何出路）/ `READY` **409**（没有东西可重试，回 200 会让用户以为在重新处理）。并且**在端点里就把 FAILED 翻成 PARSING 并清 `error_msg`**（CAS：`updateMany where status='FAILED'`）—— 交给 worker 翻的话，用户点完按钮会有一段"点了没反应"的空窗。
  11. **旧 S3 对象在"改行之后、入队之前"删**：此时 `documents.file_key` 已指向新对象，旧对象已是孤儿；放在入队之后则"入队失败提前返回"会把清理一并跳过、泄漏一个对象。

- **落地要点**（11 条，细节见 `issue_fix/问题记录-P0-1-20-双路检索+RRF融合.md`）：
  1. **两条路各自"与独立 SQL 等价"是唯一能证明分数不是编出来的手段**：验收里把端点返回的向量/全文名次与分数，跟**独立跑一遍同形状 SQL**（不走任何业务代码）逐条对照。只断言"非空 + 有六列"时，一个"按 seq 排序"的假实现照样全绿。
  2. **`mode`/`topK` 可在单次请求里覆盖，且**不落库****：检索测试页的价值就是"同一 query 试三种模式"（`03` §4.3），每次去 PATCH 库配置会**污染**别人的检索口径；`score`/`rrfK`/`weights` **刻意不可覆盖**（它们是"这个库的口径"）。验收有一条断言"覆盖之后库里的 `retrieval_config` 逐字不变"。
  3. **参数来源各归其位**：`rrfK` / `score` / `weights` / `topK` / `mode` 取**该库的快照**（建库时来自 `RRF_K` / `RETRIEVAL_*` 等环境值），而 `candidatePool = topK × CANDIDATE_POOL_FACTOR` 取**环境级**（`子方案①` §十一 没把它定义成 KB 级参数）。验收注入 `RRF_K=77` / `CANDIDATE_POOL_FACTOR=5` 两个**非默认特征值**并断言响应回显 —— 沿用默认值的话，"读了配置"与"写死 60/3"分辨不出来（P0-1-15 的同款手法）。
  4. **两级 tie-break 放在 JS 里，不写进 SQL 的第二排序键**：`ORDER BY embedding <=> $1, id` 会让 HNSW 退化（HNSW 只支持单键距离排序 ⇒ 变成"索引扫描 + 显式排序"），P0-1-14 的索引取证就白做了。做法是 SQL 保持 `§6-1` 的单键形状，取回候选池后在 JS 里按 `(score, id)` 稳定排序。`fuseRrf` 的同分也按 `chunkId` 升序（uuid7 时间有序 ⇒ 等价于"先入库的优先"，不引入文档没有的偏好）。
  5. **相似度下限（`retrieval_config.score`）落在池之后过滤**：距离单调 ⇒ "最近的 N 条里过线的"与"过线的里面最近的 N 条"是同一集合，而这样能少传一份 20KB 的向量字面量。**只作用于向量路**（`bigm_similarity` 与 cosine 不可比，给它套同一个阈值是两套量纲混用）。
  6. **`%` 与 `_` 必须在 query 预处理阶段就剔掉**：全文路是 `content LIKE '%' || $1 || '%'`，needle 里留着 `%` 就从小小的"字面包含"变成模式匹配（`5%0` 会命中"5…0"）。剔除标点顺手解决它，**不需要再叠一层转义**（多一层转义就多一处会漏的地方）。验收用"正文里有 5 和 0 但永不相邻"的夹具做判别（两种实现的期望值不同，这条断言才有判别力）。
  7. **对 `§6-1` "去停用词"的收窄：只剥句首/句尾的提问脚手架，不删中间的停用词**。LIKE 要求**连续子串** —— 把"报销的标准"里的"的"删掉会变成"报销标准"，而正文写的是"报销的标准"，于是**本来能命中的反而命中不了**，与初衷相反。脚手架（"请问…是多少"）本来就只在两端。保守是刻意的：**不剥"不/没/非"**（"不含税"→"含税"是语义反转，比召回率低严重得多）。
  8. **`snippet` 不加工、不加省略号**：`§九` 明确"不加工、不摘要"，而本批验收有一条"片段与原文一致可核对" ⇒ 加了省略号的字符串**不再是原文的子串**，那条验收就永远做不成（`§六` 的示例 JSON 里写的 `"……出差住宿标准为……"` 属展示层，省略号由前端按需加）。三条分支都有断言：命中居中（±80 完整窗口）／命中贴边（在 0 处裁剪）／字面未命中（取块首窗口，向量路命中时没有"命中位置"可取）。
  9. **`§八` 的降级路径本批就位**（原文要求"P0 只做①④的开关骨架，但探测与告警要在 P0 就位"）：库快照的 `embedding_model` ≠ 当前 provider 的 `name()` ⇒ **`HYBRID` 跳过向量路 + 告警**（附 `warnings` 文案与 `vectorPathSkipped` 布尔），**`VECTOR` 明确 409**（没有可退的路，返回空数组会被读成"库里没有相关内容"）。两种原因分开报：**模型变更**（业务要重建）与**未就绪**（运维要修）—— 合成一条会让用户去重做一个治不好的动作。
  10. **`null` 与 `0` 是两件事**：没走/没命中的一路必须是 `null`（不是 0）—— 前者前端显示 `—`，后者显示 `0.000`。这条写进了契约与断言（zod 的 `.nullable()` 而不是 `.default(0)`）。

     **不按 `updatedAt` 排**：覆盖重建会改它，一篇正在重建的文档会在用户翻页时"跳到最前面"。
  2. **库不存在 → 404，而不是空列表**：`{items: [], total: 0}` 会让前端分不清"库没了"与"库里没文档"
     （前者该跳回列表页、后者该显示上传引导）。验收同时断言 401 / 400 / 404 三条前置。
  3. **列表项与上传响应共用同一套投影**，并有**键集合断言**：同一份数据在多个出口出现不同形状，
     是前端最容易踩的坑（也防"以后有人顺手把 `file_key` / `content_hash` select 出去"）。
  4. **下载是本仓唯一不返回 JSON 信封的端点**：成功回字节流，**失败仍然是信封**（404/500 是 JSON）
     ⇒ 客户端要按状态码分支而不是永远 `json()`。这条写进了路由注释与 README。
  5. **`statObject` 在 `getObject` 之前**：`getObject` 对不存在的键**不在 `await` 时抛错**（错误发生在
     读流时）⇒ 只调它的话响应头已经发出去了，客户端看到的是"下载到一半断了"。先 `stat` 才能
     在发头之前干净地回 404（顺带拿到 `Content-Length`）。⚠️ 两者之间仍有 TOCTOU 窗口，
     那时只能断流 —— **不假装能回 JSON**。
  6. **"行还在但对象没了"是 404 + 另一句文案**（"原始文件已不在存储中…请重新上传"），且**不动数据库**：
     它与"文档不存在"是两件不同的事，用户该做的动作也不同。
  7. **`Content-Disposition` 双写（RFC 6266/5987）+ 头注入防护**：`filename="<ASCII 回落>"` 给老客户端、
     `filename*=UTF-8''<百分号编码>` 给中文名；**CR/LF 必须删掉**（响应头注入）、引号/反斜杠/路径分隔符
     一律替换。这些是纯函数，验收在无依赖档逐条断言（含 `'`/`(`/`)`/`*` 这几个
     `encodeURIComponent` 会放过、而 RFC 5987 **不认**的字符）。
  8. **下载的 `Content-Type` 表与上传白名单刻意分开**（前者"唯一确定"，后者是"允许客户端声明哪几种"
     的多选白名单），代价是可能漂移 ⇒ `verify-app` 有一条"下载类型必须落在该扩展名的上传白名单里"的
     跨表一致性断言。文本类型**显式带 `charset=utf-8`**（不带时浏览器猜编码，中文会乱码）。
- **包 D 收口**：`子方案①` §十二 的 8 行**逐行有据**（`verify:kb-package` 一行一组），
  `02` §4.6 的知识库端点表**全部落地**（CRUD / upload / reupload / retry / delete / list / download / search）。
  **⚠️ 仍不是浏览器可端测的里程碑**：§七 待决事项 7 的第二个端测点（P0-1-30 浏览器首站）与
  知识库界面（P0-1-35）都还没做 ⇒ 本批之后**用户可以在命令行里跑完整条链路**（建库 → 上传 →
  看列表 → 检索 → 下载），但浏览器里还是占位页。

- **落地要点**（9 条，细节见 `issue_fix/问题记录-P0-1-23-组件绑定.md`）：
  1. **「校验」必须排在「删除」之前 —— 顺序本身就是正确性**（本批最要紧的一条）。

     而库里的绑定已经没了。取证方式**不是**看状态码，而是看旧行的 **`id` 是否逐字不变**
     （`agent_components.id` 是 uuid7、插入时生成 ⇒ "重写了一遍但内容相同"也会换 id，一验就出来）。
  2. **整体替换的语义包含"清掉不在提交集合里的行"**，包括**手工塞进库的脏行**（`ref_id` 是多态外键、没有 FK，

     用户下次保存组件绑定，它就被清掉了。

     若每次都删了重建，`agent_components.id` / `created_at` 会被**无谓刷新** —— P0-1-10 已为同类问题立过规矩
     （"带随机 IV 的密文逐字不变"）。判等是**集合语义**（换顺序提交不算改动），验收里有一条就用"换顺序再提交一次"取证。
  4. **`createMany({ skipDuplicates: true })` 只兜并发**（`ON CONFLICT DO NOTHING`）：两个同时到达的相同 `PUT`
     会在插入时撞 `@@unique(agentId, componentType, refId)`，跳过即得正确结果，而不会把一次双击变成 500。
     payload **内**的重复项由 schema 拦（否则那才是真的"静默掩盖调用方 bug"）。
  5. **不动 `agents.updated_at`**（上一批回写的坑预判，本批**已用断言钉死**）：`updated_at` 同时是 `/api/agents`

     + 列表里两者的相对顺序不变。

     而界面显示"保存成功"。与 `guideQuestions` 用 `[]` 表达清空是同一套口径 —— 清空只有一种写法。
  7. **重复项的 400 用 `superRefine` + `addIssue({ path })`，path 精确到 `['components', 1, 'refId']`**：
     上一批在 `.refine()` 上踩过"path 是空串、只能遍历 message 找"，本条是**同族问题的正面写法**；
     前端能因此高亮到具体那一行。两档验收里都有断言，且**刻意放在一起对照**。
  8. **刻意不设条数上限**：可绑的知识库数量本身没有业务上限，加一个"看起来合理"的数字，
     会把"有 60 个库想全绑上"变成做不到的事（P0-1-11 的教训：自己发明约束会把合法配置挡在门外）。报文大小由 `bodyLimit` 兜。
  9. **响应是同一套 `AgentItem` 投影**（不是只回一个 `components` 数组）：组件绑定只是这个资源的一部分，

## 六、施工纪律（本项目的固定约定）

> 这些是跨批次反复生效的规则，写在一处，避免每批重复解释。

| # | 约定 | 出处 |
|---|------|------|
| 1 | **文档先于代码**：需求变更先改 `01`，再改 `02`/`03`，最后改本文与代码 | 项目既有工作方式 |
| 2 | **状态回写**：每批做完立即回写本文状态列，不攒着写 | 参考项目实践 |
| 3 | **缺陷归档**：踩坑写进 `issue_fix/问题记录-<批次>-<主题>.md`，本文只留一行指针 | 同上 |
| 4 | **参数唯一来源**：所有数值常量（chunk_size / topK / rrf_k…）以 `子方案①` §二 参数总表为准，代码里不硬编码散落 | `子方案①` |
| 5 | **schema 单一事实**：zod schema 定义在 `shared/`，前后端共用（含表单校验） | `03` §一 |
| 6 | **渲染单一路径**：流式与历史用同一套组件，不做两套 | `03` §六 |
| 7 | **密钥零下发**：Provider Key / MCP 凭据只在后端解密，任何响应体不得含明文 | `02` §九 不变式 |
| 8 | **计算值实测**：文档或注释里出现的具体数值（如 RRF 示例）写完用脚本算一遍 | 参考项目踩坑 |
| 9 | **不依赖本机 shell 工具链**：脚本用 Node/PowerShell（本机 Git Bash 缺 coreutils） | 本文 §二 实测 |
| 10 | **提交粒度 = 批次**：一批一提交，消息里带批次号（`P0-1-7: 认证接口`） | 便于回滚 |
| 11 | **`install` 成功 ≠ 依赖可用**：每批动完依赖后必须跑 `pnpm -r typecheck && pnpm -r build`；出现 `Cannot find module` 先查 `node_modules` 里的目录**是不是空的** | P0-1-1 坑 3 |
| 12 | **pnpm 配置只写 `pnpm-workspace.yaml`**（`.npmrc` 在本机不生效）；新增原生依赖需登记 `allowBuilds` | P0-1-1 坑 1/2 |
| 13 | **`.ps1` 脚本一律纯 ASCII**（注释用英文）：Windows PowerShell 5.1 对**无 BOM** 文件按系统 ANSI 读取，中文会乱码并可能触发语法错误；仓库统一无 BOM，故不给 `.ps1` 加 BOM | P0-1-2 坑 5 |
| 14 | **Go 模板（`{{…}}`）传参前必须先赋值给变量**：`--format '{{if …}}'` 会被 PowerShell 5.1 误判为嵌套脚本块，直接语法错误 | P0-1-2 坑 4 |
| 15 | **SQL 自检脚本：DDL 与校验必须同会话执行**（`TEMP TABLE` 是会话级），且用 `psql -q` + 只取最后一行（`-c` 多语句会带出命令标签） | P0-1-2 坑 6 |
| 16 | **zod 变量默认值要防「`.env` 空串」**：`KEY=` 得到的是空字符串而非 undefined，只在 schema 外层挂 `.default()` 会被 preprocess 绕过并报 `Required` —— 统一走「空 → 默认值」的前置收口；必填项则相反，把空串当缺失才符合直觉 | P0-1-3 坑 1 |
| 17 | **探活/健康检查端点恒返 200**，依赖状态放进 body（`ok`/`degraded` + 逐项 `checks`）；每项探活必须带超时。理由：探活端点自身是「请求成功」，依赖抖动映射成 5xx 会让网关把整个服务摘掉。需要 status code 形式的 readiness 时另开端点 | P0-1-4 坑 3 |
| 18 | **错误出口的状态码**：领域错误按错误码映射表出码；**框架错误保留 Fastify 原始状态码**（415/413 压成 400 会丢客户端处理依据）。另：错误处理代码自身不得读未校验的字段，否则 500 会掩盖真实错误 | P0-1-4 坑 5 |
| 19 | **Fastify v5 装配**：传 pino 实例用 `loggerInstance`（会把 `FastifyInstance` 按实例类型参数化，需断言成 `FastifyBaseLogger`）；`disableRequestLogging`/`requestIdLogLabel` 已废弃，改用 `logController: new LogController({…})` | P0-1-4 坑 6 |
| 20 | **Prisma 7 的接入形态是"三件套"，缺一不可**：① generator 必须是 `prisma-client`（旧的 `prisma-client-js` 将被移除）且 **`output` 必填**；② 连接串写在 **`prisma.config.ts`**（`schema.prisma` 的 `datasource.url` 已废弃），且 **必填 `@prisma/adapter-pg` 驱动适配器**（v7 不再有内置连接池）；③ 生成物放 `backend/generated/prisma`（gitignore），因此 **`build`/`typecheck` 必须先 `prisma generate`**，否则 tsc 找不到模块 | P0-1-5 坑 1~3 |
| 21 | **Prisma CLI 配置里自己加载 env，不复用 `src/config.ts`**：迁移只需要 `DATABASE_URL`，若继承应用侧 zod 全量校验，会出现"只想跑 migrate 却因为没配 S3 而失败"。配套：把不需要连库的命令（`generate`/`validate`/`format`/`version`）列入白名单，缺 `DATABASE_URL` 时其余命令**大声失败**并说明怎么修 —— 这样 CI 的 install/build 阶段无需注入任何数据库变量 | P0-1-5 坑 4 |
| 22 | **新增带 install 脚本的依赖必须登记 `allowBuilds`**：P0-1-5 加 `prisma`（自带 `preinstall`）与 `@prisma/engines`（自带 `postinstall`）时，未登记直接以 `ERR_PNPM_IGNORED_BUILDS` **报错退出**。规矩与 esbuild 相同，但这次是"一次要登记两个包" | P0-1-5 坑 5 |
| 23 | **手写 DDL 前先做反向探针**：`prisma migrate diff` 对"多余对象"是敏感的（多一张表立刻报 `DROP TABLE`），因此可以用「故意造一个多余对象/故意加一列」来判定 Prisma 到底把什么当成自己的管辖范围。P0-1-5 靠这招证伪了"分区表会被重建"的预判，避免了启用 `experimental.externalTables` 带来的静默不一致 | P0-1-5 坑 6 |
| 24 | **对外可见的结构变更要落到 `02` §三**：本批给各表补 `updated_at`、给 `agents` 补 `deleted_at`、定唯一约束与外键删除语义，均属"契约增量"，必须同步回写设计文档而不是只留在 `schema.prisma` | P0-1-5 落地要点 7 |
| 25 | **「能人工端测了就要主动说」（用户定的准则）**：每到一个**用户自己能在浏览器/命令行里亲手跑通一条完整链路**的里程碑，主动、明确地告知用户 —— 给出①启动命令与确切地址（含本机端口避让）②该测哪几条路径 ③已知未完成的边界（别当 bug）④现在还不能验什么。**不要攒到整批做完才汇报**；里程碑没到就直说"还不能"，并给出最早可端测的那一步及其前置链。本项目已识别的端测里程碑见 §七 待决事项 7 | 用户 2026-09-21 明确指定 |
| 26 | **「每批手改一次」的标识必须进收尾动作**：`backend/src/index.ts` 启动信封里的 `step` 属此类，P0-1-7/8/9 **连漏三批**（启动日志一直报「P0-1-6」，冒烟时无法从日志判断跑的是哪一版代码）。对策：该行写"每批必改"注释 + 收尾清单加一条 + 冒烟时把这一行当核对项。凡引入新的"跨批次手改字符串/清单"都照此办理 | P0-1-9 坑 11（2026-09-21 用户启动端测时发现） |
