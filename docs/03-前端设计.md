# 内部 Agent 工作台 — 前端设计

> 配套：`01-整体需求与实施步骤.md`、`02-后端设计.md`（SSE 契约以 02 第五节为准）。
> 技术结论：React + TypeScript，与后端同仓 monorepo 共享类型。自包含设计。

## 一、技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| 框架 | React 18 + Vite + TypeScript | 轻、快、无重脚手架 |
| UI 库 | Ant Design 5 | 表格/表单/弹窗全齐，内部工具效率优先 |
| 路由 | React Router 6 | — |
| 服务端状态 | TanStack Query | 列表/详情的缓存、失效、重试 |
| 客户端状态 | Zustand | 轻量；SSE 流式状态单独建模 |
| Markdown | react-markdown + remark-gfm（**代码高亮暂缓**，见 §4.1 增量） | 消息渲染 |
| SSE | fetch + ReadableStream 自实现 | 需要 POST body + 自定义头，原生 EventSource 不够 |
| 类型 | `@shared/types`（monorepo 内部包） | **直接导出 zod schemas**（前端表单校验复用同一份 schema，而非仅生成 TS 类型） |

## 三、全局布局

```
┌────────────────────────────────────────────────────────┐
│ Logo   智能体  知识库  MCP  任务        [头像▾ 改密/登出] │
├────────────────────────────────────────────────────────┤
│                      页面内容                            │
└────────────────────────────────────────────────────────┘
```

- 「管理」入口仅 ADMIN 可见（用户/模型池/用量），折叠在头像菜单或独立导航项
- 对话页（/chat）为全屏布局：**保留 Logo（点击回首页）与头像菜单（改密/登出）**，其余导航项收纳进「工作台」下拉入口——避免用户对话中途配凭据/查知识库时无路可走（全隐藏会形成导航孤岛）

**P0-1-34 落地增量（全屏布局 / 导航不孤岛）**

- **专注判据只有一个来源**：`app/nav.ts#isFocusPath(pathname)`（`pathname.startsWith('/chat/')`）。`AppLayout` 据此走 `<div className="shell shell--focus">`，该分支**不渲染左侧导航轨**（`.rail`）。⚠️ 只收顶栏而不收轨等于**一个像素都没省**，而症状是"布局看着没错、只是没变大"——所以"全屏"的定义是**两头都收**，只留 Logo + 「工作台」下拉 + 头像菜单。
- **「工作台」下拉的内容与侧栏/顶栏同源**（`visibleNavItems(role)`，`adminOnly` 在同一处过滤）：三种布局形态不会出现"某一处忘了某个角色该看到什么"。实现是 AntD `Dropdown` + `group`。
- **下拉里放的是"按角色过滤后的全部导航项"，不是"挑几个次要项藏"**：`04-评审报告` 第 2 条否掉的正是后者 —— 那是另一种形式的导航孤岛（用户找不到入口，只是换了个理由）。

**P0-1-36 落地增量（管理入口落地成两条导航项）**

- 「管理」在 P0-1-30~35 期间是**一条**占位项（`AD → /admin/users`）；本批拆成两条**真导航项**：`US 用户管理 → /admin/users`、`ML 模型池 → /admin/models`（`app/nav.ts` 的 `adminOnly: true`，`serial` 记作 `S-07 · 用户管理` / `S-07b · 模型池`）。
- ⚠️ **`adminOnly` 的过滤只有一个执行点**（`visibleNavItems(role)`）⇒ 侧栏 / 顶栏 / 对话页的「工作台」下拉三处同时正确；**不要**在某个布局里再写一次 `role === 'ADMIN'` 判断，那会造出第二份真值。
- 「用量统计」（`/admin/usage`）是 P1，**本批不给导航项**（同「任务」）—— 导航里出现一个进去是空页的入口，比没有入口更糟。

## 四、核心页面详设

### 4.1 对话页（最重页面）

```
┌────────────┬─────────────────────────────────────────┐
│ 会话侧栏     │  Agent 名 + 类型标签        [任务中心入口] │
│ + 新会话    ├─────────────────────────────────────────┤
│ 会话列表     │            消 息 流                      │
│ (最近活跃)   │  用户气泡 / 助手 Markdown                 │
│            │  [思考▾] [工具卡片] [引用卡] [产物卡]       │
│            │  [确认卡：确认/取消]                       │
│            ├─────────────────────────────────────────┤
│            │  [📎] [输入框................] [停止/发送] │
└────────────┴─────────────────────────────────────────┘
```

**消息流渲染规则**

| 消息元素 | 渲染 | 交互 |
|---------|------|------|
| 开场白 | 会话首条用户消息前，Agent 开场白纯文本气泡（不解析 markdown） | 新会话态展示（无 conversationId 进入时即展示，首条消息发送时才创建会话）；TaskAgent 同理 |
| 助手文本 | Markdown（代码高亮/表格/复制） | 流式追加；消息 hover 显示**复制全文**按钮 |
| 思考过程 | 灰底可折叠块，流式时默认展开 | 完成后自动折叠 |
| 工具卡片 | 图标 + 工具名 + 参数摘要 + 状态灯（运行/成功/失败） | 点击展开完整入参/出参；失败卡片显示原因；"需配置凭据"卡片带跳转按钮 |
| 引用卡 | 文档名列表 + 展开 snippet 原文 | 完成时随 citations 事件出现 |
| 产物卡 | 文件名 + 大小 + [预览] [下载] | 预览打开 4.6 |
| 确认卡 | 工具名 + 入参摘要 + [确认] [取消] | 阻塞输入区；120s 倒计时 |
| 引导问题（P1） | 开场白下方可点击列表 | 点击**填入输入框**（可编辑后发送），不直接发送 |
| 排队提示 | "沙箱并发已满，排队第 N 位" | queued 事件驱动 |

**会话侧栏**：会话项 hover 浮出 [重命名][删除]；重命名行内编辑；删除走分级确认（见 §七全局交互规范）。

**P0 隐藏项**：📎 附件按钮（P1）、[任务中心入口]（P1）——P0 版式图中不渲染。

**输入区状态机**

```
idle → streaming（发送→SSE建立）
输入约定：Enter 发送 / Shift+Enter 换行；streaming 中允许继续输入但发送禁用
streaming: 按钮变 [停止]；confirm 到达 → 锁输入显示确认卡
停止时序：点[停止] → POST /stop → 等 done{STOPPED} 收口；5s 未收口才 abort fetch，随后拉历史对齐
CONFLICT（同会话并发发送）→ toast "该会话正在生成中"
停止/完成 → idle
断线 → 顶部黄条提示，点击黄条=立即拉取历史对齐；
        TaskAgent 断线先查 GET /active（排队位次/当前工具）恢复进度视图，再拉历史
```

**TaskAgent 差异**：消息流同构（工具卡片 kind=SANDBOX）；右侧/下方多一个**产物面板**（artifact 事件驱动，列出文件+预览入口）；断线重连先查 `/active` 恢复进度（见输入区状态机）。

**P0-1-32 落地增量（对话页骨架 + SSE 客户端）**

- **路由落地形态**：`/chat/:agentId/:conversationId?`（与 §二 一致）。只带 `agentId` = **新会话态**（展示开场白，**首条消息发送成功后才创建会话**）；发送成功即用 `replace` 把 `conversationId` 写进 URL —— 于是刷新后仍停在同一会话、历史用同一套组件重画（这是"刷新后形态一致"能验的前提）。**会话侧栏属 P0-1-34**：本批没有"在会话之间切换"的入口，从列表页进来永远是**新会话态**。
- **开场白**：取 `agent.openingRemarks`，**只在"一条消息都没有"时**渲染（恒在最前，且此时它是唯一一条）；为 `null` / 空串时退化为空态文案。**纯文本气泡、不解析 Markdown**（§4.1 表第 1 行），与助手正文走的是两个渲染分支。
- **助手正文**：`react-markdown` + `remark-gfm`（表格 / 删除线）。**不渲染原始 HTML**（保持库默认不解析，模型输出里的 `<script>` 之类不进 DOM）。⚠️ **语法高亮本批不给**，与 §一 选型表的"代码高亮"是一处**已记录的差异**：高亮库会显著增大前端产物，而单块体积已在 vite 告警线附近 ⇒ 与 `manualChunks` 一起在 **P0-1-36** 定；代码块现在按等宽样式渲染，**不是忘了**，要补只需接在 `AssistantMarkdown` 一处（`components.code` 的渲染器）。
- **贴底跟随（新增口径，本批端测抓到真缺陷后定案）**：流式期间内容每帧长高时，**仅当用户贴着底部**才自动滚到底；用户主动上翻历史后**不打断他**。"是否贴底"必须**在 `scroll` 事件里记录**（容差 120px）—— 在 effect 里现算只能拿到"内容已经长高之后"的距离，永远判成"不在底部"（症状：回答在视口外一帧帧长出来，而滚动条纹丝不动）。
- **七种卡片的数据源成熟度**：`delta` / `thinking` / `citations` / `error` 四类本批**有真实数据源**并已端测；`tool_call` / `confirm` / `artifact` 三种组件**已就位但暂无数据源**（工具调用与产物属 P0-3），`queued` 同理（产生方是沙箱并发闸）—— 属"提前把形状建好"，不是缺失。
- **消息流容器层级**：`.stream`（滚动容器）**只能有一层**，`padding` 与滚动都归它；消息列表自身不再包一层同名容器（两层会叠加 padding 并产生嵌套滚动容器，且**不会报任何错**，只有 `document.querySelectorAll('.stream').length` 看得见）。

**P0-1-33 落地增量（输入区状态机 + 停止 + 断线）**

- **状态机落地成五个状态**（`03` §4.1 原文只点名三个：`idle` / `streaming` / `confirm`）。另外两个是**必须分开的空窗**，合进 `idle` 会各造成一个真事故：
  · `sending` —— 从"按下发送"到"store 里出现这一轮"之间（先建会话、再建流）。这段窗口里没有一个"进行中的轮次"，若判成 `idle`，用户再按一次 `Enter` 会**再建一个会话**（`submit` 清空草稿是异步的 React 状态更新，两次回车读得到同一份草稿）；
  · `stopping` —— 点过停止、正在 5s 窗口里等 `done{STOPPED}`。此轮在归约层**仍是 `streaming`**，若只有三态，按钮会停在「停止」，用户以为没点上而反复点。
  优先级：`confirm` > `stopping` > `streaming` > `sending` > `idle`（顺序即正确性，四条都有真实错法）。全部判据在 `features/chat/composerState.ts`（纯函数，逐状态被无依赖档断言）。
- **`confirm` 锁输入**按原文实现（`canType:false`）；`streaming` 则**输入不禁、只禁发送**（原文那一行）。发送键与按钮**同源**判据（`isSubmitKey`：`Enter` 发送、`Shift+Enter` 换行、**`isComposing` 时一律不发送**——中文输入法候选词也用 Enter 确认）。
- **停止时序**（原文五行）由 `features/chat/stopController.ts` 实现，**四条路径**：`settled`（窗口内等到收口 ⇒ **不 abort**）/ `settled-locally`（5s 未收口 ⇒ abort 兜底 + 客户端侧标"已停止"）/ `stop-request-failed`（`POST /stop` 自己失败 ⇒ **不等窗口**、直接 abort + 对齐，否则用户看到的是"点了没反应的按钮"）/ `nothing-to-stop` / `already-running`（幂等，重复点不重复 POST）。窗口是**注入参数**（默认 5000，`03` 点名的 5s）⇒ 验收能注入 30ms 真跑到这条规则，而不是等 5 秒或读代码相信。
- **停止后拉历史对齐**：三条收尾路径都会调 `align()`。它先取"对齐前的历史"，重拉之后按**助手消息条数是否增加**判断服务端存没存：存了 ⇒ 丢掉流式版本（否则同一轮渲染两遍）；没存 ⇒ **保留**（本地那份是唯一副本）。`done` 那条路仍走 `done.messageId` 精确让位（P0-1-32 的规则），两条规则分工见 `ChatPage.tsx` 文件头。
- **断线黄条住在 store 里、不挂在轮次上**（`stores/chatStream.ts`）：点黄条 = 对齐，而对齐的结论之一就是"丢掉流式轮次"——黄条若跟着轮次走，它会在用户点它的同一瞬间消失，用户看不到"对齐完成"这个动作。三条路径会亮它（连接中断 / 停止超时 / 停止信号没发出去），共**一句文案**（`streamErrors.ts`），具体线索（错误码、超时）走 `extra` 一行。它是**整条可点的 `<button>`**（键盘可达），不是 `<div onClick>`。
- **失败分两个通道**（`errorSource` 落在轮次上）：`'server'`（流内 `error` 事件，含 `CONFLICT`）⇒ **toast + 消息流内错误卡**（§五 原文）；`'client'`（读流失败 / 连接中断）⇒ 错误卡 + **黄条**、**不弹 toast**（三处同时喊同一件事会把黄条那句"点此对齐"淹掉）。
- **`CONFLICT` 专用文案「该会话正在生成中」只许有一处写法**（`features/chat/streamErrors.ts`）：P0-1-32 时它只在 `ErrorCard` 里，本批 toast 也要说 ⇒ 搬到一处、两个消费方共用。服务端那句更长（`'该会话正在生成中，请等当前回答结束或先停止它'`）作说明行，短句作标题；跨包一致性由验收档 J3 守着（前端短句必须是后端原文的子串）。
- **`/active` 有了第一个真消费方**：TaskAgent 的断线对齐先查 `GET /active`（原文那一行），且**它失败就当没查**（不因为"恢复进度"这一步失败而让"对齐历史"整体失败）。⚠️ 进度视图的两个字段（`queuedPosition` / `currentTool`）在 P0 阶段**没有产生方**（沙箱属 P0-3）⇒ 实际恒为 `null`、文案退化成"服务端仍在生成这一轮"。"恢复进度视图"的完整形态（位次/当前工具上屏）等 P0-3。
- **`POST /:id/stop` 的响应契约**（`{id, signaled}`）P0-1-26 就写在 `shared/src/sse.ts` 里了；本批是它第一个前端消费方（**不要**在 `conversation.ts` 里再写一份同名 schema —— 本批真的这么干了，`tsc` 的 `TS2308` 当场拦下）。

**P0-1-34 落地增量（会话侧栏 + 全屏布局）**

- **侧栏一行的三个"只能有一个来源"**（全部判据在 `features/chat/conversationList.ts`，零依赖纯逻辑）：① **顺序**只能来自服务端（`lastMessageAt desc` + `nulls:'first'`）—— 前端分组只做**切片归属、一列都不动**（`conversationList.ts` 里没有一处 `sort(`，由验收档 K10 守）；在前端再排一次就出现了**第二份排序口径**，而它与服务端的 offset/limit 分页会打架（症状："翻到第二页时同一条又出现一次"）。② **"生成中"** 只能来自流 store 的 `streamFor` —— `conversations` 表**没有**这个列，真值只在 Redis 的活跃锁上（**不能**用 `status` 猜）。③ **"当前是哪条"** 只能来自**路由参数**（用 store 或局部 state 记"我选了哪条"会出现两份真值，浏览器后退 / 粘贴链接 / 刷新三种进入方式都会让它们分叉）。
- **状态灯是三态，不是原型上的四态**：`design/chat.html` 写了「生成中 / 已完成 / 已失败 / 已停止」，落到本项目只有三个有**数据来源** —— `run`（生成中，流 store）/ `warn`（只读保留，`status === 'FINISHED'`，只由"Agent 被软删"产生）/ `idle`（其余）。「已失败」「已停止」是**单轮回答**的结局、不是会话的状态，也没有接口能回答"这个会话的最后一轮失败了"（`/active` 只回答"现在有没有在跑"）⇒ 编一个出来就是造假数据。文案做成"**色 + 字**"两重表达（只靠颜色在色觉障碍与暗色主题下读不出状态）。
- **分组与读数**：两个分组标题（今天 / 更早），**空组不出现**；分组的参考时刻是 `lastMessageAt ?? createdAt`（刚建的会话 `lastMessageAt` 是 `null`，而服务端把它排在最前 ⇒ 拿 `null` 去算分组会让侧栏顶部空一截、而"刚新建的那条"掉到下半部分）；时间读数五档（`刚刚` / `N 分钟前` / `N 小时前` / `昨天 HH:mm` / `MM-DD HH:mm`），分档按**日历日差**而不是 24 小时差（23:50 的消息在 00:30 看会被整除成"今天"，而它其实是**昨天**的 —— 症状是分组标题下少一条，读数看着却完全正常）；`null` ⇒ 「还没有消息」（**不拿 `createdAt` 冒充** `lastMessageAt`）。侧栏带 60s 的"现在"节拍器（`useMinuteTick`），否则读数不会自己更新。
- **行内重命名**：唯一校验 `normalizeTopicDraft`（`trim()` 后非空 / 长度按**码点** ≤ `CONVERSATION_TOPIC_MAX_CHARS` / `unchanged`），三条与后端 `renameConversationBodySchema` **逐条对齐**（**同一个常量**、**同样按码点** —— 用 JS 的 `.length` 会让一个 emoji 算两个字符，于是前端拦下后端明明接受的标题）；**没改动不发 PATCH**（省一次请求，也避免把 `updatedAt` 无谓推进）；未命名会话**预填空串**而不是「新会话」（那个词是**回落文案**、不是它的名字，预填它会让用户存出一个真叫"新会话"的标题）。
- **删除走"级联删除"那一档**（§七）：Modal + `tag--danger` 红色危险按钮 + 明示影响范围 + **输入「删除」逐字确认**（`isDeleteConfirmed` **不做 `trim()`** —— "顺手去掉空白"会让"逐字确认"变成一句空话）。⚠️ **给不出消息条数**：`GET /:id/messages` 是**游标分页**、只回 `{items,nextCursor,hasMore}`（没有 `total`），而 `deletedMessages` 是 **`DELETE` 的响应字段**（删完才拿得到）⇒ 如实写「**全部消息**」，真数放进**删除成功的提示**（与 `DeleteAgentModal` 处置"会话数取不到"同一口径：不造假）。**生成中删除是允许的**（后端就不按 `status` 拦 —— 用户要能清理自己的历史），前端不额外禁用，只如实告知"这一轮不会落库、本地这条流会被收掉"。
- **⚠️ 本批新识别出的静默风险：切会话串台**。P0-1-32/33 的对话页一次只有一个会话，"一个轮次槽 + 能随手切换"就成了真问题 —— 在 A 里发消息、没等收口就切到 B，B 的页面上会看到 **A 的增量一帧帧长出来**（渲染读的是 store 里那唯一的轮次）。两端处置：**看得见** ⇒ 状态机加第六态 `elsewhere`（占位符与提示行都说"另一个会话正在生成"）；**拦得住** ⇒ `send` 里加 `BUSY` 闸门，且**排在 `createConversation` 之前**（排在后面的话，用户在新会话态点发送会先**凭空建一个空会话**、再被告知发不出去）。
- **`elsewhere` 的优先级排在 `sending` 之后**（全序 `confirm > stopping > streaming > sending > elsewhere`，**顺序即正确性**）：`sending` 是"我自己这一轮正在起"，比"别人在跑"更贴近用户此刻的手指，两者同时成立时占位符该说的是前者。
- **侧栏不做请求**：改名/删除都走 `api/conversations.ts` 的 hooks（§六："组件内不写请求"）；侧栏只向页面要三样东西（`onSelect` / `onNew` / `onDeleted`）—— 它**不认识 URL 长什么样**，导航是页面的事。
- **一处 `shared` 契约的连带改动**：`CONVERSATION_TOPIC_MAX_CHARS = 255` 提为公开常量（`renameConversationBodySchema` 的 `.max()` 改为引用它），前端的 `maxLength` 与提交校验都读它 —— "255"不许在两处各写一遍（验收档 K8 守同源）。

- 文档表格：文件名 / 状态（解析中 spinner、完成 ✓、失败 ✗+原因）/ chunk 数 / 更新时间 / 操作（覆盖重传、重试、下载原始文件、删除）
- 检索测试抽屉：输入 query → 结果表（内容片段 / 向量分 / 全文分 / RRF 融合排名 / 命中库）

> **P0-1-35 落地增量**（本批连带把 `/knowledge` 列表页与三个弹窗一起落地，详见 `06` P0-1-35 与 `issue_fix/问题记录-P0-1-35-*.md`）：
> ① **⚠️ `.doc` 是唯一一条"必须留在 `accept` 里"的扩展名** —— 它是后端明确拒收的格式，但"选了立即提示"这条验收只有在**系统选择器放它进来**时才可能触发；`accept` 只写四个白名单会让 `.doc` 在选择器里是灰的、用户根本选不中 ⇒ 提示代码是**死代码**。定案：`UPLOAD_ACCEPT_ATTRIBUTE` 由 `[...UPLOAD_EXTENSIONS, LEGACY_DOC_EXTENSION]` 派生（**故意含 `.doc`**），拦截交给纯函数 `screenPickedFiles()`，且 `Upload` 的 `beforeUpload` **必须 `return false`**（否则 AntD 会**自己再发一次**上传，"前端已拦下"变成"还多传了个垃圾请求"）。
> ② **状态三态的展示口径**：`PARSING` 行给 spinner + `shared` 的「暂不参与检索」提示、`READY` 绿、`FAILED` 红 + `errorMsg`（原因**必须显示**，`06` 验收原文第 2 条）。**片数量只在 `READY` 显示数字**（非 `READY` 一律 `—`，判据用 `isDocumentSearchable`，**不显示 0**）。副标题**只放扩展名** —— `documents` 表没有 `size` 列、接口也不回，编一个"1.2 MB"就是造假。
> ③ **行内操作是矩阵不是固定四项**：`PARSING` = 下载 ✅ / 覆盖重传 ❌（后端 409）/ 重试 ✅（**唯一的恢复入口**）/ 删除 ✅；`READY` = **不给重试**（后端 409）；`FAILED` = 四项全给。两种状态下的"重试"说明**不是同一句**（`RETRY_HINT` 两分支），把它们都渲染成可点会让用户点了必然失败。
> ④ **轮询是纯函数 + 明确的终止条件**：`documentRefetchInterval(items)` —— 本页有 `PARSING` ⇒ `DOCUMENT_POLL_INTERVAL_MS`（2s），全部终态 / 空 / `undefined` ⇒ **`false`**。判据只有这一处来源（api 层**不自己判** `PARSING`）。页面把"每 2 秒自动刷新，全部解析完即停"写在表尾明处。
> ⑤ **⚠️ 三处"看着该有、其实拿不到"的数字一律不显示**：全库 **chunk 总数**（列表接口只回 `documentCount`）；文件 **size**（见 ②）；检索结果的**「命中库」**（库是**路径参数**、恒等于当前库名、零信息量 ⇒ 这一列改名**「来源文档」**，有页码给页码、否则给块号）。
> ⑥ **`null` 与 `0` 是两个意思**：未命中的一路后端回 `null`（**不是 0**）⇒ 显示 `—`；"恰好 0 分"显示 `0`。**两个量级要两套小数位**：RRF 融合分在 0.03x ⇒ **四位**小数（两位会把一屏结果全显示成 `0.03`）、相似度 0.8x ⇒ 两位；名次未命中给 `—` 不给 `#0`。
> ⑦ **检索测试抽屉的 `mode`/`topK` 默认是"跟随该库配置"**（`undefined`/`null` 表示），**不预选 `HYBRID` / `10`** —— 预选会让用户永远观察不到"库级配置到底生效没有"。结果区顶部回显**服务端生效值**（mode/topK/rrfK/candidatePool/elapsedMs/命中数），让"我改的配置真的生效了"有可见证据；"向量路被跳过"的横幅**引用服务端 `warnings[0]` 原文**（不重写）。
> ⑧ **三态与局部合并**：改库的请求体**只在值真的变了才带键**（没改就不发请求；**清空描述 ⇒ 显式 `description: null`**，少写会让"删掉的描述刷新后又回来"）；检索配置是 jsonb **局部合并**、逐键比较，⚠️ **两个权重必须成对带**（schema 要求同时给 `vector`/`fulltext`）；**建库时分块参数留空 = 不带这两个键**（服务端用环境默认值快照），前端不填 `512/64` 冒充"我选过了"。
> ⑨ **⚠️ 下载是全仓唯一不套信封的端点** ⇒ `requestBlob` 必须按**响应形状**分支（`content-type` 含 `application/json` ⇒ 走信封抛 `ApiError`；否则回 `{blob, fileName}`），**不能按状态码判**；文件名 **`filename*`（RFC 5987 三段式）优先于 `filename`**（中文名只有 `filename*` 是对的，取错会拿到 `%E5%8F%98...` 乱码名）。
> ⑩ **删除分级沿用 §七**：文档删除 = `Popconfirm`；**删库 = 级联那一档**（`tag--danger` + **输入库名逐字确认**、**刻意不 `trim`**、失败不关弹窗）。**删库能给条数、删会话给不出** —— 详情接口回 `documentCount`/`agentCount` ⇒ 弹窗如实写"将删除 N 篇文档"；`agentCount > 0` 时**不禁用删除、而是先给错误提示 + 指路智能体列表**（否则用户点下去只拿到一句 409）。这与 P0-1-34 删会话「只能写『全部消息』」是**同一原则、两种处境**。
> ⑪ **一处原型口径纠正**：`design/kb-detail.html` 库级检索配置卡上的「不落库 · 每次请求传入」**写反了** —— 库级配置**是落库的**（`retrieval_config` jsonb），"每次请求传入"说的是**检索测试抽屉里那个可覆盖的** `mode`/`topK`。
> ⑫ **权限沿用 `02` §4.6：`/api/knowledge-bases/*` = 登录即可**（与模型池的 ADMIN **相反**）⇒ 列表页**不做任何角色过滤**（MEMBER 看到同一个库列表是刻意的不对称，不是漏鉴权）。

> **两处与本节初版的差异**（P0-1-30/32 落地时定案）：
> ① **错误码→文案映射层不在 `api/`，而在 `app/feedback.ts`** —— 它是"用户可见文案"的唯一出口（`06` §六 第 28 条），放在 `app/` 与导航/路径常量同级更符合"界面口径收在一处"的意图；`api/client.ts` 只负责把响应变成 `ApiError`（带 `code` / `fields` / `retryAfterSec`）。

- 组件内不写请求，全部走 api 层 hooks

**P0-1-36 落地增量（十条例逐条落实，两条 admin 页是执行样本）**

> 本批的验收门槛第 4 条就是"本节 10 条落实"，所以逐条点名**落在哪个文件/哪条断言**上；表中"删除分级"的缺席项（用户无删除、模型删除走哪一档）在下面第 2 条说明。

1. **创建/编辑形态**：用户（6 字段）/ Provider（5 字段）/ 模型（5 字段）**三者都用弹窗**（`UserFormModal` / `ProviderFormModal` / `ModelFormModal`）；同一实体创建与编辑**同形态、同组件**（靠 `mode` 区分），与 `03` 原表一致。⚠️ 编辑态里 `username` 恒只读 —— 后端 `updateUserBodySchema` **只接 `status`/`role`**，给个能改的框等于让用户白填一次再被静默丢掉。
2. **删除分级确认**：Provider 删除走**级联那一档**（`DeleteProviderModal`：`Tag tag--danger`「级联删除」+ 列出"将同时删除 N 个模型" + **输入 Provider 名称逐字确认** + 红色危险按钮），因为它会连带删掉它名下的模型；**模型删除走普通那一档**（`Popconfirm`）。⚠️ **用户列表刻意没有删除** —— `P0-1-9` 只给了"启停"，没有 `DELETE /api/users/:id`，界面上**不放假按钮**（同 P0-1-35「界面上有数字 ≠ 能拿到这个数字」的反向：**没有能力就不摆入口**）。
3. **保存语义**：三个表单都是显式保存；**"什么也没改" ⇒ 按钮给出"没有需要保存的改动"且不发请求**（`buildCreateUserBody` / `buildProviderUpdateBody` / `buildModelUpdateBody` 在无改动时返回 `null`，"不发请求"这个决定**只有这一处来源**）；失败停留弹窗不关（逐字段错误挂在表单上）。
4. **反馈通道**：成功/失败都走 `app/feedback.ts`（**错误码→文案的唯一出口**）；本批**没有新增任何一处就地写文案** —— `App.tsx` 的三条 admin 路由与其余页面共用同一个 `message`/`notification` 封装。
5. **二级页动线**：本批两页都是**一级页**（导航项直达，无详情页）⇒ 不涉及面包屑；`/admin/users`、`/admin/models` 的导航项来自 `app/nav.ts` 的**同一处**（`adminOnly: true`），侧栏/顶栏/「工作台」下拉三处同源。
6. **表格规范**：操作列固定右侧、**文字链按钮**（AntD `Button type="link"`，⚠️ **不自己发明 `.linkish` 类** —— P0-1-35 的教训：自写外观类会被 AntD 的 cssinjs 按特异度打平）、危险操作红色、**删除放最后**（模型表：`编辑 / 启用停用 / 删除`；用户表：`编辑 / 停用启用 / 重置密码`，无删除项）。⚠️ **模型表另外改了一处形态**：Provider 列用 **`rowSpan` 把相邻同 Provider 的行合并**（`providerGroupSpans()`，成组呈现），因为"一个 Provider 下挂几个模型"是本页的主要读数；**因此刻意不开客户端排序**（`sorter` 一个都没挂）—— 排序会让同 Provider 的行不再相邻，`rowSpan` 的合并立刻变成**错的**（症状是"行高串位"，但代码不报错）。
7. **列表三态**：两页复用 P0-1-31 的 `ListStates`（`TableSkeleton` / `ErrorState` 带重试 / `EmptyState` 带引导按钮），每页各出现一次；`useAdminUsers` / `useAdminModels` 都带 `keepPreviousData`（翻页不闪空）。
8. **文案词表**：界面上不认识"provider"这个英文 —— 一律写「模型服务商」；模型、用户、状态词（启用/停用）都用中文。⚠️ 「Key」是唯一保留的英文词（它是**用户在自己厂商后台看到的那个名字**，译成"密钥"反而对不上）；`Key 只进不出`这条口径的界面表达是「已配置 · `sk-****abcd`」。
9. **键盘约定**：Enter 提交 / Esc 关闭弹窗与抽屉，全按 AntD 默认行为（**不额外接管**）；**唯一一处显式例外**是 `InitialPasswordModal`（`keyboard={false}` + `closable={false}` + `maskClosable={false}`）—— 它是**初始密码的唯一一次明文展示**，误触关掉就再也拿不回来了，所以它**刻意不响应 Esc**（"敲一次密码 → 手一抖按了 Esc → 账号废了"不是可以接受的代价）。
10. **窄屏边界**：两页都只保证 1024px 以上可用（复用已有的媒体查询），不做窄屏专门适配。

两条**跨页面的口径收敛**（本批顺手做的，避免同一判断出现第二份实现）：
- **"输入名称/词逐字确认"的判断抽成 `app/confirm.ts#isTypedConfirmMatch`**（P0-1-36 前已有三处各写一遍：智能体删除、会话删除、知识库删除；本批的 Provider 删除是**第四个消费方**）⇒ 转成一个共享纯函数，四处改为委托；它**刻意不做 `trim`**（多一个空格不算）。
- **模型池的三条缓存互不相干但必须一起失效**：`['admin','model-providers']` / `['admin','models']` / `['models','available','CHAT']`（第三个是**智能体编辑页的模型下拉**用的）⇒ 全部收进 `api/modelPool.ts#invalidateModelPoolViews()` 一处；漏掉第三个的症状是"改了模型池，智能体编辑页的模型下拉还是旧的"（黄条都不弹，纯静默）。
