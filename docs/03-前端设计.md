# 内部 Agent 工作台 — 前端设计

> 配套：`01-整体需求与实施步骤.md`、`02-后端设计.md`（SSE 契约以 02 第五节为准）。
> 技术结论：React + TypeScript，与后端同仓 monorepo 共享类型。自包含设计。

## 一、技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| 框架 | React 18 + Vite + TypeScript | 轻、快、无重脚手架 |
| UI 库 | Ant Design 5 | 表格/表单/弹窗全齐，内部工具效率优先 |
| 路由 | React Router 6 | — |
| 服务端状态 | TanStack Query | 列表/详情的缓存、失效、重试 |
| 客户端状态 | Zustand | 轻量；SSE 流式状态单独建模 |
| Markdown | react-markdown + remark-gfm（**代码高亮暂缓**，见 §4.1 增量） | 消息渲染 |
| SSE | fetch + ReadableStream 自实现 | 需要 POST body + 自定义头，原生 EventSource 不够 |
| 类型 | `@shared/types`（monorepo 内部包） | **直接导出 zod schemas**（前端表单校验复用同一份 schema，而非仅生成 TS 类型） |

## 三、全局布局

```
┌───────────────┬─────────────────────────────────────────┐
│ Logo   ⌷ 收起 │ 工作台 / 智能体           [浅色] [头像▾] │
├───────────────┼─────────────────────────────────────────┤
│ ▣ 智能体       │                                         │
│ ▣ 知识库       │                                         │
│ ▣ MCP         │              页面内容                    │
│ ▣ 会话产物     │                                         │
│ ▣ 我的凭据     │                                         │
│ …  ADMIN 两项  │                                         │
│ ●  S-02 · …   │                                         │
└───────────────┴─────────────────────────────────────────┘
（左侧栏 = 图标 + 文字，可收起为仅图标；顶栏 = 快捷页面导航（面包屑））
```

- **左侧栏**承载**全部导航项**（图标 + 文字），并带**收起 / 展开**开关；「管理」入口仅 ADMIN 可见（用户/模型池，`adminOnly`）
- **顶栏**是**快捷页面导航**（面包屑 `工作台 / 模块 / 细节`），不再放全局文字导航 —— 全局导航唯一入口就是左侧栏
- 对话页（/chat）**也用同一套外壳**（左侧栏 + 顶栏面包屑），面包屑是 `工作台 / 智能体 / <智能体名>`。⚠️ 改版前那套"对话页专注布局（隐藏左侧栏 + 「工作台」下拉）"**已取消**（用户要求：发起对话后仍保留侧边导航）。

**布局改版（左侧栏 + 顶栏面包屑；本次）**

- **左侧栏**：每项 = 图标（按 `NavItem.code` 认领，映射在 `AppLayout`）+ 文字（`nav.ts#NAV_ITEMS` 的 `label`）；默认展开（`--rail-open-w`），点开关收起为仅图标（`--rail-w`，与改版前同宽）。序列号在**展开态横排、收起态竖排**。**权限过滤仍只有一个执行点** `visibleNavItems(role)`。
- **顶栏面包屑**：静态前缀由 `nav.ts#crumbBaseForPath(pathname)` 推出（`工作台 / <模块>`），二级页的**细节段**（知识库名 / 智能体名 / 占位页标题）由页面用 `app/crumbContext.ts#usePageCrumb` 上报 —— 那些名字来自查询数据、路径里没有。有细节段时前缀各段渲染成链接，否则末段即当前页。
- ⚠️ **页面不再自带面包屑**（`.crumb` 只在 `AppLayout` 一处渲染）：`verify-admin-ui.mjs` 的 J12 守着"管理页不再出现 `className=\"crumb\"`"。这消除了改版前"每页各写一遍面包屑"的重复，也不会再出现"某一页忘了写面包屑"。
- ⚠️ **对话页不再有"专注布局"**：`nav.ts#isFocusPath` 与「工作台」下拉（`WorkspaceMenu`）已删除；所有页面统一"左侧栏 + 顶栏面包屑"。移动端左侧栏仍是底部横条，对话页一屏高**多扣 56px**（否则横条盖住输入区）。

**P0-1-34 落地增量（全屏布局 / 导航不孤岛）—— ⚠️ 已被"布局改版（2026-09-30）"取代，以下为历史记录**

- **专注判据只有一个来源**：`app/nav.ts#isFocusPath(pathname)`（`pathname.startsWith('/chat/')`）。`AppLayout` 据此走 `<div className="shell shell--focus">`，该分支**不渲染左侧栏**（`.rail`）。⚠️ 只收一处等于导航没收敛，而症状是"布局看着没错、只是没变大"——所以"全屏"的定义是**左侧栏收起 + 顶栏只留面包屑与「工作台」下拉**。
- **「工作台」下拉的内容与左侧栏同源**（`visibleNavItems(role)`，`adminOnly` 在同一处过滤）：两种布局形态不会出现"某一处忘了某个角色该看到什么"。实现是 AntD `Dropdown` + `group`。
- **下拉里放的是"按角色过滤后的全部导航项"，不是"挑几个次要项藏"**：`04-评审报告` 第 2 条否掉的正是后者 —— 那是另一种形式的导航孤岛（用户找不到入口，只是换了个理由）。

**P0-1-36 落地增量（管理入口落地成两条导航项）**

- 「管理」在 P0-1-30~35 期间是**一条**占位项（`AD → /admin/users`）；本批拆成两条**真导航项**：`US 用户管理 → /admin/users`、`ML 模型池 → /admin/models`（`app/nav.ts` 的 `adminOnly: true`，`serial` 记作 `S-07 · 用户管理` / `S-07b · 模型池`）。
- ⚠️ **`adminOnly` 的过滤只有一个执行点**（`visibleNavItems(role)`）⇒ 左侧栏一处同时正确；**不要**在某个布局里再写一次 `role === 'ADMIN'` 判断，那会造出第二份真值。
- 「用量统计」（`/admin/usage`）已于 **P1-7** 落地（§4.8）⇒ **补上导航项** `UT · 用量统计`（`adminOnly: true`）；此前因"点进去是空页"刻意不进导航。

## 四、核心页面详设

> ⚠️ **多机透明（P1-14 核心 / P1-9 · R9，2026-10-12）**：**前端零改动**。前端仍只连一个**同源** `/api`（`api/client.ts`）；是否落到多台后端、哪条请求必须粘性（`/chat`、`/stream`、`/regenerate`、`/workspace*`）由**路由网关**（`backend/src/router/*`，生产 = nginx/网关入口；dev 无网关，Vite 直连唯一后端）按会话目录透明处理。前端**不感知**实例数，也不需要为工作区/流做任何特殊处理。

### 4.1 对话页（最重页面）

```
┌────────────┬─────────────────────────────────────────┐
│ 会话侧栏     │  Agent 名 + 类型标签        [任务中心入口] │
│ + 新会话    ├─────────────────────────────────────────┤
│ 会话列表     │            消 息 流                      │
│ (最近活跃)   │  用户气泡 / 助手 Markdown                 │
│            │  [思考▾] [工具卡片] [引用卡] [产物卡]       │
│            │  [确认卡：确认/取消]                       │
│            ├─────────────────────────────────────────┤
│            │  [📎] [输入框................] [停止/发送] │
└────────────┴─────────────────────────────────────────┘
```

**消息流渲染规则**

| 消息元素 | 渲染 | 交互 |
|---------|------|------|
| 开场白 | 会话首条用户消息前，Agent 开场白纯文本气泡（不解析 markdown） | 新会话态展示（无 conversationId 进入时即展示，首条消息发送时才创建会话）；TaskAgent 同理 |
| 助手文本 | Markdown（代码高亮/表格/复制） | 流式追加；消息 hover 显示**复制全文**按钮；**最新一条回答**额外显示「重新生成」（P1-3） |
| 思考过程 | 灰底可折叠块，流式时默认展开 | 完成后自动折叠 |
| 工具卡片 | 图标 + 工具名 + 参数摘要 + 状态灯（运行/成功/失败） | 点击展开完整入参/出参；失败卡片显示原因；"需配置凭据"卡片带跳转按钮。⚠️ P0-2-11：原因显示 `errorCode` + `shared` 默认文案；「去配置凭据」是**三条判据**（`status=ERROR` **且** `errorCode=NEED_CREDENTIAL` **且** `serverId` 非空） |
| 引用卡 | 文档名列表 + 展开 snippet 原文 | 完成时随 citations 事件出现 |
| 产物卡 | 文件名 + 大小 + [预览] [下载] | 预览打开 4.6 |
| 确认卡 | 工具名 + 入参摘要 + [确认] [取消] | 阻塞输入区；倒计时**读服务端 `expiresAt`**（"120s"是**服务端**的超时、前端不另起一个，P0-2-11）；到点停在「已超时」+ 两键禁用、**卡不自己撤** |
| 引导问题（P1） | 开场白下方可点击列表 | 点击**填入输入框**（可编辑后发送），不直接发送 |
| 排队提示 | "沙箱并发已满，排队第 N 位" | queued 事件驱动 |

**会话侧栏**：会话项 hover 浮出 [重命名][删除]；重命名行内编辑；删除走分级确认（见 §七全局交互规范）。

**P0 隐藏项**：📎 附件按钮（P1）、[任务中心入口]（P1）——P0 版式图中不渲染。

**输入区状态机**

```
idle → streaming（发送→SSE建立）
输入约定：Enter 发送 / Shift+Enter 换行；streaming 中允许继续输入但发送禁用
streaming: 按钮变 [停止]；confirm 到达 → 锁输入显示确认卡
停止时序：点[停止] → POST /stop → 等 done{STOPPED} 收口；5s 未收口才 abort fetch，随后拉历史对齐
CONFLICT（同会话并发发送）→ toast "该会话正在生成中"
停止/完成 → idle
断线 → 顶部黄条提示，点击黄条=立即拉取历史对齐；
        TaskAgent 断线先查 GET /active（排队位次/当前工具）恢复进度视图，再拉历史
```

**TaskAgent 差异**：消息流同构（工具卡片 kind=SANDBOX）；右侧/下方多一个**产物面板**（artifact 事件驱动，列出文件+预览入口）；断线重连先查 `/active` 恢复进度（见输入区状态机）。

**P1-6 方案 A 落地增量（后台运行可被实时观察）**：定时任务到点/「立即执行」时后端在**后台**跑一轮，帧发进**帧总线**；对话页挂 `useConversationWatch`（`GET /:id/stream` 只读订阅）把帧喂进**同一个** `chatStream` store ⇒ 用户打开那个会话窗口就能实时看到内容，不必等落库。三条约束：① **与本页自己发起的那一轮互斥**（`streamFor === conversationId` 时不订阅，防同一帧画两遍）；② 观察流**迟到先补帧**（后端总线缓冲本轮已发帧）；③ 收到 `done`/`error` 后**以落库历史为准**（刷新消息/产物并清掉观察轮次）。观察是长连（没运行只发心跳），收尾不关连接，下一次运行接着用。⚠️ 总线**进程内**（P0 单实例）。

**P0-1-32 落地增量（对话页骨架 + SSE 客户端）**

- **路由落地形态**：`/chat/:agentId/:conversationId?`（与 §二 一致）。只带 `agentId` = **新会话态**（展示开场白，**首条消息发送成功后才创建会话**）；发送成功即用 `replace` 把 `conversationId` 写进 URL —— 于是刷新后仍停在同一会话、历史用同一套组件重画（这是"刷新后形态一致"能验的前提）。**会话侧栏属 P0-1-34**：本批没有"在会话之间切换"的入口，从列表页进来永远是**新会话态**。
- **开场白**：取 `agent.openingRemarks`，**只在"一条消息都没有"时**渲染（恒在最前，且此时它是唯一一条）；为 `null` / 空串时退化为空态文案。**纯文本气泡、不解析 Markdown**（§4.1 表第 1 行），与助手正文走的是两个渲染分支。
- **助手正文**：`react-markdown` + `remark-gfm`（表格 / 删除线）。**不渲染原始 HTML**（保持库默认不解析，模型输出里的 `<script>` 之类不进 DOM）。⚠️ **语法高亮本批不给**，与 §一 选型表的"代码高亮"是一处**已记录的差异**：高亮库会显著增大前端产物，而单块体积已在 vite 告警线附近 ⇒ 与 `manualChunks` 一起在 **P0-1-36** 定；代码块现在按等宽样式渲染，**不是忘了**，要补只需接在 `AssistantMarkdown` 一处（`components.code` 的渲染器）。
- **贴底跟随（新增口径，本批端测抓到真缺陷后定案）**：流式期间内容每帧长高时，**仅当用户贴着底部**才自动滚到底；用户主动上翻历史后**不打断他**。"是否贴底"必须**在 `scroll` 事件里记录**（容差 120px）—— 在 effect 里现算只能拿到"内容已经长高之后"的距离，永远判成"不在底部"（症状：回答在视口外一帧帧长出来，而滚动条纹丝不动）。
- **七种卡片的数据源成熟度**：`delta` / `thinking` / `citations` / `error` 四类本批**有真实数据源**并已端测；`tool_call` / `confirm` / `artifact` 三种组件**已就位但暂无数据源**（工具调用与产物属 P0-3），`queued` 同理（产生方是沙箱并发闸）—— 属"提前把形状建好"，不是缺失。
- **消息流容器层级**：`.stream`（滚动容器）**只能有一层**，`padding` 与滚动都归它；消息列表自身不再包一层同名容器（两层会叠加 padding 并产生嵌套滚动容器，且**不会报任何错**，只有 `document.querySelectorAll('.stream').length` 看得见）。

**P0-1-33 落地增量（输入区状态机 + 停止 + 断线）**

- **状态机落地成五个状态**（`03` §4.1 原文只点名三个：`idle` / `streaming` / `confirm`）。另外两个是**必须分开的空窗**，合进 `idle` 会各造成一个真事故：
  · `sending` —— 从"按下发送"到"store 里出现这一轮"之间（先建会话、再建流）。这段窗口里没有一个"进行中的轮次"，若判成 `idle`，用户再按一次 `Enter` 会**再建一个会话**（`submit` 清空草稿是异步的 React 状态更新，两次回车读得到同一份草稿）；
  · `stopping` —— 点过停止、正在 5s 窗口里等 `done{STOPPED}`。此轮在归约层**仍是 `streaming`**，若只有三态，按钮会停在「停止」，用户以为没点上而反复点。
  优先级：`confirm` > `stopping` > `streaming` > `sending` > `idle`（顺序即正确性，四条都有真实错法）。全部判据在 `features/chat/composerState.ts`（纯函数，逐状态被无依赖档断言）。
- **`confirm` 锁输入**按原文实现（`canType:false`）；`streaming` 则**输入不禁、只禁发送**（原文那一行）。发送键与按钮**同源**判据（`isSubmitKey`：`Enter` 发送、`Shift+Enter` 换行、**`isComposing` 时一律不发送**——中文输入法候选词也用 Enter 确认）。
- **停止时序**（原文五行）由 `features/chat/stopController.ts` 实现，**四条路径**：`settled`（窗口内等到收口 ⇒ **不 abort**）/ `settled-locally`（5s 未收口 ⇒ abort 兜底 + 客户端侧标"已停止"）/ `stop-request-failed`（`POST /stop` 自己失败 ⇒ **不等窗口**、直接 abort + 对齐，否则用户看到的是"点了没反应的按钮"）/ `nothing-to-stop` / `already-running`（幂等，重复点不重复 POST）。窗口是**注入参数**（默认 5000，`03` 点名的 5s）⇒ 验收能注入 30ms 真跑到这条规则，而不是等 5 秒或读代码相信。
- **停止后拉历史对齐**：三条收尾路径都会调 `align()`。它先取"对齐前的历史"，重拉之后按**助手消息条数是否增加**判断服务端存没存：存了 ⇒ 丢掉流式版本（否则同一轮渲染两遍）；没存 ⇒ **保留**（本地那份是唯一副本）。`done` 那条路仍走 `done.messageId` 精确让位（P0-1-32 的规则），两条规则分工见 `ChatPage.tsx` 文件头。
- **断线黄条住在 store 里、不挂在轮次上**（`stores/chatStream.ts`）：点黄条 = 对齐，而对齐的结论之一就是"丢掉流式轮次"——黄条若跟着轮次走，它会在用户点它的同一瞬间消失，用户看不到"对齐完成"这个动作。三条路径会亮它（连接中断 / 停止超时 / 停止信号没发出去），共**一句文案**（`streamErrors.ts`），具体线索（错误码、超时）走 `extra` 一行。它是**整条可点的 `<button>`**（键盘可达），不是 `<div onClick>`。
- **失败分两个通道**（`errorSource` 落在轮次上）：`'server'`（流内 `error` 事件，含 `CONFLICT`）⇒ **toast + 消息流内错误卡**（§五 原文）；`'client'`（读流失败 / 连接中断）⇒ 错误卡 + **黄条**、**不弹 toast**（三处同时喊同一件事会把黄条那句"点此对齐"淹掉）。
- **`CONFLICT` 专用文案「该会话正在生成中」只许有一处写法**（`features/chat/streamErrors.ts`）：P0-1-32 时它只在 `ErrorCard` 里，本批 toast 也要说 ⇒ 搬到一处、两个消费方共用。服务端那句更长（`'该会话正在生成中，请等当前回答结束或先停止它'`）作说明行，短句作标题；跨包一致性由验收档 J3 守着（前端短句必须是后端原文的子串）。
- **`/active` 有了第一个真消费方**：TaskAgent 的断线对齐先查 `GET /active`（原文那一行），且**它失败就当没查**（不因为"恢复进度"这一步失败而让"对齐历史"整体失败）。⚠️ 进度视图的两个字段（`queuedPosition` / `currentTool`）在 P0 阶段**没有产生方**（沙箱属 P0-3）⇒ 实际恒为 `null`、文案退化成"服务端仍在生成这一轮"。"恢复进度视图"的完整形态（位次/当前工具上屏）等 P0-3。
- **`POST /:id/stop` 的响应契约**（`{id, signaled}`）P0-1-26 就写在 `shared/src/sse.ts` 里了；本批是它第一个前端消费方（**不要**在 `conversation.ts` 里再写一份同名 schema —— 本批真的这么干了，`tsc` 的 `TS2308` 当场拦下）。

**P0-1-34 落地增量（会话侧栏 + 全屏布局）**

- **侧栏一行的三个"只能有一个来源"**（全部判据在 `features/chat/conversationList.ts`，零依赖纯逻辑）：① **顺序**只能来自服务端（`lastMessageAt desc` + `nulls:'first'`）—— 前端分组只做**切片归属、一列都不动**（`conversationList.ts` 里没有一处 `sort(`，由验收档 K10 守）；在前端再排一次就出现了**第二份排序口径**，而它与服务端的 offset/limit 分页会打架（症状："翻到第二页时同一条又出现一次"）。② **"生成中"** 只能来自流 store 的 `streamFor` —— `conversations` 表**没有**这个列，真值只在 Redis 的活跃锁上（**不能**用 `status` 猜）。③ **"当前是哪条"** 只能来自**路由参数**（用 store 或局部 state 记"我选了哪条"会出现两份真值，浏览器后退 / 粘贴链接 / 刷新三种进入方式都会让它们分叉）。
- **状态灯是三态，不是原型上的四态**：`design/chat.html` 写了「生成中 / 已完成 / 已失败 / 已停止」，落到本项目只有三个有**数据来源** —— `run`（生成中，流 store）/ `warn`（只读保留，`status === 'FINISHED'`，只由"Agent 被软删"产生）/ `idle`（其余）。「已失败」「已停止」是**单轮回答**的结局、不是会话的状态，也没有接口能回答"这个会话的最后一轮失败了"（`/active` 只回答"现在有没有在跑"）⇒ 编一个出来就是造假数据。文案做成"**色 + 字**"两重表达（只靠颜色在色觉障碍与暗色主题下读不出状态）。
- **分组与读数**：两个分组标题（今天 / 更早），**空组不出现**；分组的参考时刻是 `lastMessageAt ?? createdAt`（刚建的会话 `lastMessageAt` 是 `null`，而服务端把它排在最前 ⇒ 拿 `null` 去算分组会让侧栏顶部空一截、而"刚新建的那条"掉到下半部分）；时间读数五档（`刚刚` / `N 分钟前` / `N 小时前` / `昨天 HH:mm` / `MM-DD HH:mm`），分档按**日历日差**而不是 24 小时差（23:50 的消息在 00:30 看会被整除成"今天"，而它其实是**昨天**的 —— 症状是分组标题下少一条，读数看着却完全正常）；`null` ⇒ 「还没有消息」（**不拿 `createdAt` 冒充** `lastMessageAt`）。侧栏带 60s 的"现在"节拍器（`useMinuteTick`），否则读数不会自己更新。
- **行内重命名**：唯一校验 `normalizeTopicDraft`（`trim()` 后非空 / 长度按**码点** ≤ `CONVERSATION_TOPIC_MAX_CHARS` / `unchanged`），三条与后端 `renameConversationBodySchema` **逐条对齐**（**同一个常量**、**同样按码点** —— 用 JS 的 `.length` 会让一个 emoji 算两个字符，于是前端拦下后端明明接受的标题）；**没改动不发 PATCH**（省一次请求，也避免把 `updatedAt` 无谓推进）；未命名会话**预填空串**而不是「新会话」（那个词是**回落文案**、不是它的名字，预填它会让用户存出一个真叫"新会话"的标题）。
- **删除走"级联删除"那一档**（§七）：Modal + `tag--danger` 红色危险按钮 + 明示影响范围 + **输入「删除」逐字确认**（`isDeleteConfirmed` **不做 `trim()`** —— "顺手去掉空白"会让"逐字确认"变成一句空话）。⚠️ **给不出消息条数**：`GET /:id/messages` 是**游标分页**、只回 `{items,nextCursor,hasMore}`（没有 `total`），而 `deletedMessages` 是 **`DELETE` 的响应字段**（删完才拿得到）⇒ 如实写「**全部消息**」，真数放进**删除成功的提示**（与 `DeleteAgentModal` 处置"会话数取不到"同一口径：不造假）。**生成中删除是允许的**（后端就不按 `status` 拦 —— 用户要能清理自己的历史），前端不额外禁用，只如实告知"这一轮不会落库、本地这条流会被收掉"。
- **⚠️ 曾经的静默风险"切会话串台" —— P1-19 已由"多流"根治**。P0-1-32/33 的对话页一次只有一个会话，而 store 只有**一个轮次槽** ⇒ 在 A 里发消息、没等收口就切到 B，B 的页面上会看到 **A 的增量一帧帧长出来**。当时的处置是**拦住**（状态机第六态 `elsewhere` + `send` 的 `BUSY` 闸门），代价是"**只要 A 还在跑（TaskAgent 动辄数分钟），B 就一直发不出消息**"（用户报的"切过去卡住"）。**P1-19** 把 `stores/chatStream.ts` 改成**按会话存**（`rounds[conversationId]` / `disconnects[conversationId]`，`begin`/`apply`/`fail`/`reset` 都带 `conversationId`）⇒ 各会话互不覆盖、也不串台，"另一条流在跑"不再是拦阻条件：`elsewhere` 状态、`streamingId` 与 `send` 里的 `BUSY` 闸门**一并删除**，闸门（`createSendGate`）、`sending`/`stopping` 标记与 abort 控制器都**按会话**各一份（在 B 里发消息不会掐掉 A 那条）。新的不变量：`ConvRail` 的"生成中"灯取**正在生成的会话 id 集合**（`streamingIdsOf`），可能同时点亮多条。
- **侧栏不做请求**：改名/删除都走 `api/conversations.ts` 的 hooks（§六："组件内不写请求"）；侧栏只向页面要三样东西（`onSelect` / `onNew` / `onDeleted`）—— 它**不认识 URL 长什么样**，导航是页面的事。
- **一处 `shared` 契约的连带改动**：`CONVERSATION_TOPIC_MAX_CHARS = 255` 提为公开常量（`renameConversationBodySchema` 的 `.max()` 改为引用它），前端的 `maxLength` 与提交校验都读它 —— "255"不许在两处各写一遍（验收档 K8 守同源）。

**P0-2-11 落地增量（确认卡接真数据源 / 工具卡"去配置" / 历史工具卡还原）**

- **确认卡的倒计时读的是服务端的绝对时刻**：`ConfirmCard` 的输入只有 `expiresAt`（`confirm` 事件的 payload，`02` §9.10），`remainingSeconds(expiresAt, now)` **每秒用 `Date.now()` 重算**、不做本地递减 —— 前端自己另起一个 120s 的后果是"界面说还没到、服务端已按取消处理"，而用户看到的是"我点了确认但什么都没发生"。卡**不自己撤销**：到点后读数停在「已超时」、两个按钮 `disabled`（那正是此时的事实），撤卡的判据在服务端。
- **`source` 只决定那行说明文案**（`confirmSourceHint`）：`PLATFORM` 与 `SERVER` 的按钮、应答端点完全一致 ⇒ 它是**判别字段**，不是两种卡片。
- **答复后的收卡是一个本地动作**：答复走独立于流的 `POST /:id/confirm`，服务端**不会**为此发事件 ⇒ `chatStream` store 上有 `clearConfirm()`，页面在 `.finally` 里调；这期间两个按钮都 `disabled`（防连点拿到 `applied:false`）。⚠️ 文案上与"失败"划清界限：`applied:false` 是**幂等忽略**（重复 / 迟到 / 已超时），不是错误（`confirmIgnoredNote`）。
- **工具卡的「去配置凭据」走唯一的路径构造点** `app#credentialsPath(serverId)`。
- **失败卡的理由显示 `errorCode` + `shared#DEFAULT_MESSAGE_BY_ERROR_CODE` 的默认文案**（`errorCodeLabel`）：手上有的是**字符串**错误码，而 `describeError` 只接受错误对象 ⇒ 拿它渲染会掉进兜底显示"服务内部错误"。
- **历史里的工具卡能还原**（P0-2-8 定型、本批接回）：`messageToView` 走 `pickToolCalls(content.tool_calls)` —— **逐项过 schema、坏项丢弃**（一项坏不该让整轮渲染不出来），且 **`arguments` 刻意不带上来**（那是含凭据值的完整入参，只进库）。

**P0-3-11 落地增量（任务型对话页：产物面板 + 预览弹层接进来）**

- **版式图从两栏变三栏**：`.chat--with-panel`（原型 `design/chat.html` 的第三列）**只对 `agent.type === 'TASK_AGENT'` 加**。判据是 `artifactPanelModel.ts#showArtifactPanel(agentType)`，**不是 CSS、也不是"有没有产物"** —— 类型在创建时定死（`02` §3.2"创建后不可改"）而"有没有产物"不是；用后者会让面板在第一次派活之前完全不存在、派活之后凭空出现，用户会以为自己触发了什么。`undefined`（agent 还没读到）按"不显示"处理：先渲染再撤掉会让 `grid-template-columns` 变一次、中栏宽度跳一下。
- **⭐ 面板清单是两个来源在一处的合流，而这两个来源从来没有同时齐过**：`GET /api/conversations/:id/artifacts`（**"刷新后产物还在"的唯一出口**，带 `createdAt`）只在"这一轮结束、列表被重取之后"才含新产物；流里的 `artifact` 事件此刻就在手上，却**没有 `createdAt`**。合流点 = `artifactPanelModel.ts#mergeArtifactPanelItems(persisted, streamed)`（零依赖纯逻辑，进无依赖档）。
- **⚠️ 合并的顺序不是排版偏好，是"两个来源的排序口径要一致"**：服务端列表是 `created_at desc`（最新在前），而 `artifact` 事件是**产出顺序**（旧 → 新）⇒ 直接拼接会得到"上半段旧→新、下半段新→旧"的清单 —— **不报错、也不重复**，只是"刚生成的那个"掉在中间，而用户找的就是它。故流式那一段必须**倒序**放在最前。去重按 `artifactId` 且**保留服务端那一份**（它有 `createdAt` ⇒ 面板上那行才能从"刚生成"变成真正的时间读数）。
- **⭐ 产物卡的两个按钮（P0-1-32 的 disabled 形态）在本批解禁**，而**「预览」不是每张卡都有**：判据是 `previewAvailability()`（内部调 `shared#previewKindOf` + 两个体积常量）⇒ `none` 类型（zip / pptx / 未知；⚠️ **docx、xlsx 自 P1-16 起不再属 `none`** —— 它们走独立的 `docx`/`xlsx` 形态 + 服务端渲染出口 `/api/artifacts/:id/render`）与**超限**的产物**都不渲染按钮、只给下载**（`子方案④` §九 的两条验收点是**同一条规则的两种情形**）。刻意**不做成"置灰的预览按钮"**：能力有无是事实、不是"暂不可用"（§4.5 口径）—— 给 zip 一个永远点不开的「预览」，用户会以为是自己用错了。
- **「下载」的实现收在 `components/ArtifactPreview/useArtifactDownload.ts` 一处**：本批让下载有了**第二个**入口（卡片 + 弹层标题栏），抄一份的代价不是那六行，而是 §六 那句"同一口径两处写必有一处先腐烂"（成功/失败文案与"在飞时禁用"的判据会分叉，且**不报任何错**）。
- **「谁在预览」住在 `stores/artifactPreview.ts`，不逐层传**：弹层必须住在页面级（产物面板与消息流是 `.chat` 下的**两个兄弟列**，弹层要在两列之上），而"点预览"的动作发生在**四个层级之下**（`ChatPage → MessageList → AssistantMessage → ArtifactCard`），中间两层是纯展示组件。⚠️ 与 `stores/ui.ts` 的"服务端数据不进 zustand"不冲突：存的不是服务端数据（不缓存、不去重），而是"用户此刻打开了哪一张"这个纯客户端选择。
- **`ArtifactCard` 多了个可选的 `timeText`**：面板那一格写 `8.4 KB · 刚生成`（`design/chat.html`），消息流里的卡（§4.1 那一行）只有 `8.4 KB` —— 两种读数**不是同一个来源**（面板有 `createdAt`、流式产物没有）。故时间读数做成**可选入参**，而不是让卡片自己判"我在哪一列"。⚠️ 同一条纪律：`ArtifactCard` **不 import** `artifactPanelModel.ts`（那个纯逻辑档是面板的）。
- **`total` 取服务端给的数、不拿 `items.length` 冒充**：列表一页最多 100 条，拿它当"共 N 个"会在超过一页时说谎；拿不到就**什么都不说**（`artifactPanelOverflowNote`，与 P0-1-34 的"给不出就留白，别编"同一条）。
- **列表拉失败不遮挡事件那一路**：两个来源的可用性互相独立（`GET /artifacts` 挂了，本轮事件产出的那些**照样在手上**）⇒ 失败是**一条提示 + 重试**，不是把整个面板换成错误态（后者会让用户以为"产物都没了"，而他刚刚明明看见它们出现）。
- **`useMinuteTick` 从 `ConversationSidebar` 提到 `features/chat/useMinuteTick.ts`**：产物面板是第二个"相对时间会自己走"的界面 ⇒ 节拍间隔（60s）只有一处来源，两处界面共用（对外行为逐字未变、只挪位置，P0-1-36 抽 `isTypedConfirmMatch` 同款手法）。
- **1280px 断点下第三列 `display: none`**（原型同款；窄屏上它会把消息流挤到 700px 以下）。⚠️ 「能预览产物」这条能力**没有消失** —— 消息流里的产物卡仍带 [预览][下载]。⚠️ 本批在 `app.css` 里新建这条断点**刻意住在 base 规则之后**（同特异度由源码顺序决定，搬到文件前那个「响应式」块里会被覆盖掉 —— 那个块里已有一处这样的坑，见 `06` §五 P0-3-11 的待决 ③）。
- **`useChatStream` 收尾多失效一次产物列表**：与消息历史、侧栏列表并列（"这一轮真的发生过 ⇒ 库里可能多了几行"）。非 TaskAgent 时那个查询**根本没建**（`enabled: false`）⇒ 空转、不多打请求。

**P1-3 落地增量（重新生成：重跑最新一轮、替换原回答）**

- **入口挂在"最新一条助手回答"上**（§4.1 渲染表第 2 行）：判据（`ChatPage#regenerable`）= 有会话 + 没有流在跑 + 历史最后一条是 `ASSISTANT` + 能往前找到它回答的那条 `USER`。⚠️ **不挂在用户消息上**：被替换的是"回答"，而用户消息上已有「撤回/修改重发」。
- **渲染时必须把"正在被替换的那一轮"暂时收起**（`messageModel.ts#dropLastRound`）：后端重新生成 = **撤掉上一轮 + 重跑同一段正文**，前端此刻同时持有旧轮次（历史）与新轮次（流式 store）两份数据 ⇒ 不收起来就会**重复渲染用户气泡与两份回答**。收起判据 `round.kind === 'regenerate'`（`StreamRound` 新增 `kind`，默认 `'send'`）。
- **⚠️ "对齐 effect"必须先于收起判断用未收起的历史**：收尾后靠"历史里出现了 `done.messageId` 那条"让流式版本让位（文件头那一段）。若拿**收起后**的历史去判，新落的那一轮也在被收起之列 ⇒ 永远匹配不到、流式版本永不让位（症状：同一轮既在历史里、又在流式里，且永远不会自愈）。故页面同时持有 `allHistory`（服务端原样，用于对齐与模型回显）与 `history`（收起后，用于渲染）。
- **抽 `useChatStream#performStream`，`send` 与 `regenerate` 共用**：开一轮 → 读流 → 三类失败处置 → 收尾失效三棵查询（历史/侧栏/产物）这套逻辑**只写一处**；两者只在"谁开流"（`streamChat` / `streamRegenerate`）与"要不要先建会话"（`send` 会、`regenerate` 不会）上不同。不抽的话重新生成很容易漏掉某一处失效（症状：重新生成后侧栏排序不动、或产物面板停在旧数）。
- **它是 `send` 的近亲但不是同一个**：`regenerate` 不接收草稿、不建会话、不做正文长度校验（正文来自历史那条消息）；`modelId` 沿用当前选择器 ⇒ "换个模型重跑"= 选好模型再点重新生成。**不新增 SSE 事件**：后端跑的是同一条 `/chat` 链路，前端仍是同一套归约与卡片。

- 检索测试抽屉：输入 query → 结果表（内容片段 / 向量分 / 全文分 / RRF 融合排名 / 命中库）

> **P0-1-35 落地增量**（本批连带把 `/knowledge` 列表页与三个弹窗一起落地，详见 `06` P0-1-35 与 `issue_fix/问题记录-P0-1-35-*.md`）：
> ① **⚠️ `.doc` 是唯一一条"必须留在 `accept` 里"的扩展名** —— 真 OLE2 `.doc` 仍是后端拒收的格式，但"选了立即提示"只有在**系统选择器放它进来**时才可能触发；`accept` 只写四个白名单会让 `.doc` 在选择器里是灰的、用户根本选不中 ⇒ 提示代码是**死代码**。且 **P1-12 起 `.doc` 可能是 HTML/MIME（MHTML）导出件、本可正常解析**，更不该被选择器过滤。定案：`UPLOAD_ACCEPT_ATTRIBUTE` 由 `[...UPLOAD_EXTENSIONS, LEGACY_DOC_EXTENSION]` 派生（**故意含 `.doc`**），拦截交给纯函数 `screenPickedFiles()`，且 `Upload` 的 `beforeUpload` **必须 `return false`**（否则 AntD 会**自己再发一次**上传，"前端已拦下"变成"还多传了个垃圾请求"）。
> ①·补 **⚠️ P1-12 起 `.doc` 的拦截分两层**：`screenPickedFiles()` 在**扩展名层放行 `.doc`**（不再按扩展名拒）；命中 `.doc` 时组件读**文件头**（`item.slice(0, LEGACY_DOC_PROBE_BYTES)`）走 `screenLegacyDocContent()` → `sniffLegacyDocHead()`（**镜像后端 `detectFormat` 的嗅探**：OLE2 魔数 / RTF / MIME 头 / HTML 标记 / 其它）—— HTML/MHTML 放行、真 OLE2/RTF/其它才落 `LEGACY_DOC` 并给"请另存为 .docx"。⚠️ 前端这份只是**提前提示**，判错最坏是多一次往返、由后端给出准结论（与 `extensionOf` 同一取舍）；文件头读取是异步的，用序号 ref 只认最后一次选择。
> ② **状态三态的展示口径**：`PARSING` 行给 spinner + `shared` 的「暂不参与检索」提示、`READY` 绿、`FAILED` 红 + `errorMsg`（原因**必须显示**，`06` 验收原文第 2 条）。**片数量只在 `READY` 显示数字**（非 `READY` 一律 `—`，判据用 `isDocumentSearchable`，**不显示 0**）。副标题**只放扩展名** —— `documents` 表没有 `size` 列、接口也不回，编一个"1.2 MB"就是造假。
> ③ **行内操作是矩阵不是固定四项**：`PARSING` = 下载 ✅ / 覆盖重传 ❌（后端 409）/ 重试 ✅（**唯一的恢复入口**）/ 删除 ✅；`READY` = **不给重试**（后端 409）；`FAILED` = 四项全给。两种状态下的"重试"说明**不是同一句**（`RETRY_HINT` 两分支），把它们都渲染成可点会让用户点了必然失败。
> ④ **轮询是纯函数 + 明确的终止条件**：`documentRefetchInterval(items)` —— 本页有 `PARSING` ⇒ `DOCUMENT_POLL_INTERVAL_MS`（2s），全部终态 / 空 / `undefined` ⇒ **`false`**。判据只有这一处来源（api 层**不自己判** `PARSING`）。页面把"每 2 秒自动刷新，全部解析完即停"写在表尾明处。
> ⑤ **⚠️ 三处"看着该有、其实拿不到"的数字一律不显示**：全库 **chunk 总数**（列表接口只回 `documentCount`）；文件 **size**（见 ②）；检索结果的**「命中库」**（库是**路径参数**、恒等于当前库名、零信息量 ⇒ 这一列改名**「来源文档」**，有页码给页码、否则给块号）。
> ⑥ **`null` 与 `0` 是两个意思**：未命中的一路后端回 `null`（**不是 0**）⇒ 显示 `—`；"恰好 0 分"显示 `0`。**两个量级要两套小数位**：RRF 融合分在 0.03x ⇒ **四位**小数（两位会把一屏结果全显示成 `0.03`）、相似度 0.8x ⇒ 两位；名次未命中给 `—` 不给 `#0`。
> ⑦ **检索测试抽屉的 `mode`/`topK` 默认是"跟随该库配置"**（`undefined`/`null` 表示），**不预选 `HYBRID` / `10`** —— 预选会让用户永远观察不到"库级配置到底生效没有"。结果区顶部回显**服务端生效值**（mode/topK/rrfK/candidatePool/elapsedMs/命中数），让"我改的配置真的生效了"有可见证据；"向量路被跳过"的横幅**引用服务端 `warnings[0]` 原文**（不重写）。
> ⑧ **三态与局部合并**：改库的请求体**只在值真的变了才带键**（没改就不发请求；**清空描述 ⇒ 显式 `description: null`**，少写会让"删掉的描述刷新后又回来"）；检索配置是 jsonb **局部合并**、逐键比较，⚠️ **两个权重必须成对带**（schema 要求同时给 `vector`/`fulltext`）；**建库时分块参数留空 = 不带这两个键**（服务端用环境默认值快照），前端不填 `512/64` 冒充"我选过了"。
> ⑨ **⚠️ 下载是全仓唯一不套信封的端点** ⇒ `requestBlob` 必须按**响应形状**分支（`content-type` 含 `application/json` ⇒ 走信封抛 `ApiError`；否则回 `{blob, fileName}`），**不能按状态码判**；文件名 **`filename*`（RFC 5987 三段式）优先于 `filename`**（中文名只有 `filename*` 是对的，取错会拿到 `%E5%8F%98...` 乱码名）。
> ⑩ **删除分级沿用 §七**：文档删除 = `Popconfirm`；**删库 = 级联那一档**（`tag--danger` + 红色危险按钮 + 明示影响范围 + 失败不关弹窗；**已去掉逐字输入确认**）。**删库能给条数、删会话给不出** —— 详情接口回 `documentCount`/`agentCount` ⇒ 弹窗如实写"将删除 N 篇文档"；`agentCount > 0` 时**不禁用删除**：后端会**自动解绑**（2026-10-08 起删库不再 409），弹窗只**提示**"删除后会解除 N 个智能体绑定"。这与 P0-1-34 删会话「只能写『全部消息』」是**同一原则、两种处境**。
> ⑪ **一处原型口径纠正**：`design/kb-detail.html` 库级检索配置卡上的「不落库 · 每次请求传入」**写反了** —— 库级配置**是落库的**（`retrieval_config` jsonb），"每次请求传入"说的是**检索测试抽屉里那个可覆盖的** `mode`/`topK`。
> ⑫ **权限沿用 `02` §4.6：`/api/knowledge-bases/*` = 登录即可**（与模型池的 ADMIN **相反**）⇒ 列表页**不做任何角色过滤**（MEMBER 看到同一个库列表是刻意的不对称，不是漏鉴权）。
>
> **P1-5 落地增量（重建索引·整库 + 换模型入口）**：
> ⓪ ★ **换模型是唯一入口、也是重建的唯一触发点**（用户 2026-10-01 反馈：不要独立的「重建索引」按钮）：Embedding 模型下拉不再只出现在"创建"形态；编辑时选另一个模型即显示 `EMBEDDING_MODEL_CHANGE_REBUILD_HINT` 告警，**保存成功后自动调用 `POST /:id/rebuild`**（有文档时），用户一步完成"换模型 → 重建"。判据是纯函数 `isEmbeddingModelChanged`。⚠️ **保存动作同时兜住"模型池里被改名"的情形**：当 `kb.embeddingModelChanged === true`（快照与当前模型不一致）时，**即使本次没改任何字段、点「保存」也会触发重建** —— 因为详情页没有独立按钮，这是该状态唯一的触发入口。

> · **注册/编辑弹窗的模板编辑器**是**行编辑**：key / label / **受控下拉的注入位置**（三个值，来自 `shared#CREDENTIAL_INJECT_LOCATIONS`，不出现裸英文）/ 移除按钮；`key` 列错误报在**行内**，数量超限报在**表单级**。⚠️ **校验不重写** —— 直接调 `shared#validateCredentialSchema`（四条语义规则后端已有一份），前端只把 `path[index,'key']` 还原成"哪一行哪一列"。
> · **编辑态的"没改就不发"**（⚠️ **2026-10-17 修订**，原判据有 bug）：`buildServerUpdateBody` 对模板用**整体结构判等**（`credentialSchemaEquals`：对象键序无关 —— jsonb 往返会重排键；**行序有关** —— 顺序即界面顺序）—— `label`（参数提示）/ `placeholder` / `required` / 行序的任何差异**都要提交**。❗旧判据（key 级的 `diffCredentialSchema`）只回答"已存凭据受什么影响"，拿它当"改没改"的判据会把**只改参数提示的编辑静默丢弃**（保存"成功"、重开弹窗还是旧文案）。改 label 这类文案级改动也**不会**误弹"影响了 N 份凭据"：那条提示由服务端按 key 级 diff 计算，空 diff ⇒ `null`。零改动 ⇒ `null` ⇒ 提示「没有需要保存的改动」、不发 `PATCH`。保存成功若带 `credentialSchemaImpact`，用 `credentialImpactHint` 说一句人话：⚠️ 结尾**恒**有"已填的值不会被自动清理"，且**绝不出现"已清理 / 已删除"**（那是承诺，本仓只做提示）。
> · **新建不带 `authType`**（那是服务端派生的展示字段），空模板**照提交 `[]`**（"这台 server 不要用户填东西"的明确写法）。
> · **一页一条权限说明**：`/api/mcp/servers/*` 是**建/看/调用登录即可**（⚠️ **P0-2-12 起改/删收窄到"所属人 + ADMIN"**；⚠️ **2026-10-16 起「测试」也收窄到"所属人 + ADMIN"**）⇒ 页面上明写"任何人登录后都能**注册 / 调用**，但**「测试连通 / 编辑 / 删除」只有所属人或管理员**"，**不做角色过滤**（能改不能改**由服务端给的 `canEdit` 决定**）。

> **P0-2-12 落地增量（所属人）**：
> · **表格从一个"名称副行"里挪出一列**：新增 **「所属人」列**（`dataIndex: 'creatorName'`，服务端给的是**昵称优先、回落用户名**）—— 名称列的副行**去掉**了原来那句"由 {createdBy} 注册"（那是 uuid，对用户没有用）。列标题的 `title` 属性写清"**连通测试与工具列表都用这位的凭据；调用工具注入的是你自己的凭据**"（这一行同时是"我该找谁 / 我该配什么"的答案，比页脚那段话更靠前）。
> · ⚠️⚠️ **操作列按服务端给的 `canEdit` 渲染，前端不许自己算**：`server.canEdit ? ### 4.6 文件预览（概要，详见子方案④）

| 格式 | 方式 |
|------|------|
| MD | react-markdown 渲染（消毒） |
| HTML | sandbox iframe（禁 script）+ CSP |
| 图片 | 直出 |
| CSV | 解析为虚拟滚动表格 |
| PDF | 浏览器原生 viewer |

预览统一为抽屉/全屏弹层，带下载按钮。

> **P0-3-0b 落地增量（以 `子方案/文件预览.md` 为准，本表照旧只作概要）**：
> · ⚠️ **"图片 | 直出"要读成"除 SVG 之外的图片直出"**：`image/svg+xml` 归 **HTML 那一路**（iframe + 双隔离）—— SVG 是能带脚本的文档，`<img>` 里安全、但"在新标签页打开"就会以**我们的源**执行。
> · ⚠️ **"CSV 解析为虚拟滚动表格"里的解析器是自写的 RFC 4180 纯函数**（不引第三方 CSV 库），好处是它能进**无依赖验收档**逐条断言（引号内换行、`""` 转义、CRLF…）；表格用 AntD `Table` 的 `virtual`（5.x 自带，不加依赖）。
> · **格式分派只看 `artifacts.mime`**（`shared#previewKindOf`），**不看 `file_name` 的扩展名** —— 引擎可以把 `evil.html` 命名成 `x.png`，而 `mime` 是后端扫描时定的那一个。**前后端用同一个函数**（前端选渲染器 / 后端上响应头），不可能分叉。
> · **预览内容是后端代理**（`GET /api/artifacts/:id/content`，`inline`），不是对象存储的签名 URL —— 这样 HTML/SVG 的隔离头（CSP `sandbox`）才加得上。图片 / PDF 直接把这个 URL 交给 `<img>` / `<iframe>`（**不 fetch、不进 JS 堆**）；MD / CSV 才 `fetch().text()`。
> · **体积闸门有两种，界面上要能说出原因**：值超过上限时**不出现「预览」按钮**（不是置灰、也不是点进去转圈），右侧给一句"文件较大，请下载查看"；`previewKindOf` 返回 `none` 的格式给"该格式不支持在线预览"。
> · **弹层落点 `components/ArtifactPreview/`**（本节 §六 `components/` 里那个"**预览器**"就是这个目录），含五个渲染器 + `artifactPreview.ts`（**零依赖纯逻辑**：分派/CSV 解析/三处截断读数/两个 URL 的构造 —— URL 只在这一个文件里拼，别处不许拼字符串）。
> · **MD 预览复用 `features/chat/AssistantMarkdown`**（与助手正文同一套组件，`06` §六 第 6 条的单一渲染路径）；但要多传一个 `components.img` 覆盖：**外链图片不自动加载**（实测 `react-markdown@10.1.0` 会把 `![](http://…)` 原样保留 ⇒ 会真的发起外网请求，是 MD 一路唯一的残留风险）。**这是预期行为**，别当 bug。
> · **两种"取不到"要分开显示**：体积超限（不给预览）／会话过期或无权（401 的 JSON 被 `<img>` 吃成"裂图"）—— 后者要有 `onError` 兜底文案，否则用户看到的只是一块空白。

> **P0-3-10 落地增量（五种格式预览；以 `子方案/文件预览.md` 为准，本表照旧只作概要）**：
> · **落地的是"预览能力"本身**：后端 `GET /api/artifacts/:id/content`（**响应头分派**，见 `02` §4.8）+ `shared#previewKindOf` 分派判据 + 前端 `components/ArtifactPreview/`（弹层 + 渲染器 + `artifactPreview.ts` 纯逻辑）。⚠️ **「预览」按钮的接入点不在这批** —— 产物面板与对话页里谁把 `artifactId` 交给弹层属 **P0-3-11**，`ArtifactCard` 上那两个按钮仍是 P0-1-32 的 disabled 形态（"不提供点不通的入口"）。
> · **渲染器是六个不是五个**（对 `子方案④` §七 1 的一处**偏离**，理由写在 `TextPreview.tsx` 文件头）：`previewKindOf` 的 `text` 一族里除 MD 与 CSV/TSV 外还有 `text/plain` 与 `application/json`，后两种**不能**交给 Markdown 渲染器（react-markdown 会折叠连续换行、也会吃掉 JSON 里的缩进与特殊字符）⇒ 补一个 `<pre>` 的 `TextPreview`。**五个格式不变**，多出来的是 `text` 那一路的余量。
> · **MD 复用了 `AssistantMarkdown`**，但多传一个 `components.img`：`AssistantMarkdown` 为此新增了一个**可选**的 `components` 属性（默认不给 ⇒ 对话正文行为一字未变）。覆盖内容是"外链图片改成可点击的链接 + 一句说明" —— 白名单只有 `data:image/` 与同源 `/api/…`。⚠️ **这是预期行为**：引擎产出的 MD 里带外链图时，预览里看到的是链接而不是图（别当 bug）。
> · **HTML 那一路有两道隔离，第一道在响应头**（iframe 的 `sandbox=""` 只在被嵌进 iframe 时生效；"在新标签页打开"或把 URL 贴进地址栏时，只剩响应头的 CSP `sandbox` 还在）。因此本批**没有**任何"前端自己加 CSP"的写法 —— 那是后端的事，且它**不支持 `<meta>`**。
> · **两种"不给预览"的文案刻意不同**：`previewKindOf` = `none` ⇒ "该格式不支持在线预览"；体积超限 ⇒ "文件较大（X，超过上限 Y），请下载查看"。合成一句"暂时无法预览"会让人去做一件治不好的动作（反复刷新）。
> · **三处截断的读数报的是截断前的数**（行 / 列 / 单元格），且**只在真的截断了时**才出现那行读数 —— 报"共 5000 行"等于对用户说谎。CSV 解析是自写的 RFC 4180 纯函数，**不引第三方库**（它要进无依赖验收档逐条断言）。
> · **新增无依赖验收档 `pnpm verify:artifact-preview`**（`frontend/scripts/verify-artifact-preview.mjs`，26 项 / 七组：分派矩阵、CSV 逐分支、三处截断、体积闸门边界、两个 URL、**源码级守门**（`/api/artifacts/` 在 `frontend/src` 下恰好一处）、严格 UTF-8 解码）。

> **P0-3-11 落地增量（接入点已就位：产物面板 + 卡片上的「预览」）**：
> · **「预览」按钮的接入点已定案**（P0-3-10 那条"属 P0-3-11"**已作废**）：产物卡上的按钮改成 `previewAvailability(artifact).available === true` 才渲染（`none` 与**超限**都只给下载 —— §九 的两条验收点是同一条规则）；点击只做一件事：把产物放进 `stores/artifactPreview.ts`，由 `ChatPage` 订阅并渲染本节的弹层。

```
│                 │      │             │          │     │ 编辑 删除│
└───────────────────────────────────────────────────────────────┘
```

**字段与交互**
- 「新建 / 编辑」弹窗（`TaskFormModal`）：任务名 / 目标智能体（**ChatBot 与 TaskAgent 都可选**）/ 指令 / cron（含常用周期预设）/ 启用开关。**编辑时目标智能体不可改**（换智能体请删了重建）。
- cron 字段是**组合框**（AntD `AutoComplete`）：既能直接手填，也能从常用周期里选（选中即填入），还带输入过滤。**输入后即时解析**：给出一句话描述（`describeCron`，只认常见形状）+ **接下来 3 次执行时间**（`nextCronRuns`，权威读数）。合法性用 `shared#isValidCron`（与后端同一份解析器）即时校验；错误文案来自 `shared`。时区 = **服务器本地时区**（弹窗说明写明）。
- 「立即执行」**不跳转**：这一轮是**后台跑**、不会往页面推流（`emit` 是空 sink），跳过去只会看到一个空会话 —— 故改为一句提示"已开始运行，完成后可点「最近会话」查看"。列表**按 `lastRunStatus` 轮询**（有「运行中」就每 3s 重拉，跑完自动翻成成功/失败），避免停在"运行中"；同一任务已在跑 ⇒ 后端 409，页面弹错误通知。
- 「启用」开关直接 `PATCH enabled`；「最近会话」跳那次运行的会话；「删除」走 `Popconfirm` 二次确认（会话/产物保留）。
- 「**允许执行危险工具（MCP 破坏性操作）**」开关（`autoApprove`，默认开）：定时任务无人值守、没有第二个人能确认 ⇒ 由任务 owner 决定策略（开 = 自动放行、关 = 一律拒绝）。
- **通知渠道**（`01` 场景 1）：弹窗里「通知渠道」下拉（不通知 / 企业微信群机器人 / 飞书自定义机器人 / 通用 webhook）。**联动**：选「不通知」时整块隐藏「webhook 地址 / 签名密钥」；「签名密钥」只在飞书时出现。地址与密钥**加密存储、不回显**（编辑时留空 = 保持不变；要停用就把渠道改成「不通知」）。还提供**通知模板**输入框（可选）：用 `{{task}}/{{time}}/{{status}}/{{result}}` 占位符自定义消息，留空用内置默认。列表里有一列「通知」显示已配的渠道。任务跑完会**自动推送结果**（带 任务名/时间/状态；各渠道按自身渲染 —— **企微 markdown、飞书卡片、通用 webhook 纯文本**）；智能体也可用 `send_notification` 工具**主动发消息**（内容由模型决定，只带任务名标题、不带时间状态）。
- 空态：一个智能体都没有时，引导先去建一个（`/`）。

## 七、全局交互规范（14 页面共用，前端开工前定稿）

> 目的：所有页面一套操作模式，避免各自实现后体验割裂。本节为评审回写新增（04-评审报告第七节）。

| 规范 | 约定 |
|------|------|
| 创建/编辑形态 | 字段 ≤6 的实体用**弹窗**（KB、MCP server、用户、模型）；字段多/分区表单用**独立页**（Agent）；同一实体创建与编辑同形态 |
| 删除分级确认 | 普通删除（文档/凭据/server）= Popconfirm；**级联删除（Agent/会话）= Modal + 红色危险按钮 + 明示影响范围**（如"将同时删除 N 个会话"） |
| 保存语义 | 显式保存按钮；失败停留页面 + 标注未保存区块（不静默部分成功）；成功 message + 返回列表 |

| 二级页动线 | 统一面包屑/左上返回（列表名 → 详情）；浏览器后退兜底 |

| 文案词表 | 界面统一"智能体"（不与"Agent"混排）；创建实体/新建会话/注册 server 等动词按 01 需求表用语 |

**P0-1-36 落地增量（十条例逐条落实，两条 admin 页是执行样本）**

> 本批的验收门槛第 4 条就是"本节 10 条落实"，所以逐条点名**落在哪个文件/哪条断言**上；表中"删除分级"的缺席项（用户无删除、模型删除走哪一档）在下面第 2 条说明。

1. **创建/编辑形态**：用户（6 字段）/ Provider（5 字段）/ 模型（5 字段）**三者都用弹窗**（`UserFormModal` / `ProviderFormModal` / `ModelFormModal`）；同一实体创建与编辑**同形态、同组件**（靠 `mode` 区分），与 `03` 原表一致。⚠️ 编辑态里 `username` 恒只读 —— 后端 `updateUserBodySchema` **只接 `status`/`role`**，给个能改的框等于让用户白填一次再被静默丢掉。
2. **删除分级确认**：Provider 删除走**级联那一档**（`DeleteProviderModal`：`Tag tag--danger`「级联删除」+ 列出"将同时删除 N 个模型" + **输入 Provider 名称逐字确认** + 红色危险按钮），因为它会连带删掉它名下的模型；**模型删除走普通那一档**（`Popconfirm`）。⚠️ **用户列表刻意没有删除** —— `P0-1-9` 只给了"启停"，没有 `DELETE /api/users/:id`，界面上**不放假按钮**（同 P0-1-35「界面上有数字 ≠ 能拿到这个数字」的反向：**没有能力就不摆入口**）。
3. **保存语义**：三个表单都是显式保存；**"什么也没改" ⇒ 按钮给出"没有需要保存的改动"且不发请求**（`buildCreateUserBody` / `buildProviderUpdateBody` / `buildModelUpdateBody` 在无改动时返回 `null`，"不发请求"这个决定**只有这一处来源**）；失败停留弹窗不关（逐字段错误挂在表单上）。
4. **反馈通道**：成功/失败都走 `app/feedback.ts`（**错误码→文案的唯一出口**）；本批**没有新增任何一处就地写文案** —— `App.tsx` 的三条 admin 路由与其余页面共用同一个 `message`/`notification` 封装。
5. **二级页动线**：本批两页都是**一级页**（导航项直达，无详情页）⇒ 不涉及面包屑；`/admin/users`、`/admin/models` 的导航项来自 `app/nav.ts` 的**同一处**（`adminOnly: true`），侧栏/顶栏/「工作台」下拉三处同源。
6. **表格规范**：操作列固定右侧、**文字链按钮**（AntD `Button type="link"`，⚠️ **不自己发明 `.linkish` 类** —— P0-1-35 的教训：自写外观类会被 AntD 的 cssinjs 按特异度打平）、危险操作红色、**删除放最后**（模型表：`编辑 / 启用停用 / 删除`；用户表：`编辑 / 停用启用 / 重置密码`，无删除项）。⚠️ **模型表另外改了一处形态**：Provider 列用 **`rowSpan` 把相邻同 Provider 的行合并**（`providerGroupSpans()`，成组呈现），因为"一个 Provider 下挂几个模型"是本页的主要读数；**因此刻意不开客户端排序**（`sorter` 一个都没挂）—— 排序会让同 Provider 的行不再相邻，`rowSpan` 的合并立刻变成**错的**（症状是"行高串位"，但代码不报错）。
7. **列表三态**：两页复用 P0-1-31 的 `ListStates`（`TableSkeleton` / `ErrorState` 带重试 / `EmptyState` 带引导按钮），每页各出现一次；`useAdminUsers` / `useAdminModels` 都带 `keepPreviousData`（翻页不闪空）。
8. **文案词表**：界面上不认识"provider"这个英文 —— 一律写「模型服务商」；模型、用户、状态词（启用/停用）都用中文。⚠️ 「Key」是唯一保留的英文词（它是**用户在自己厂商后台看到的那个名字**，译成"密钥"反而对不上）；`Key 只进不出`这条口径的界面表达是「已配置 · `sk-****abcd`」。
9. **键盘约定**：Enter 提交 / Esc 关闭弹窗与抽屉，全按 AntD 默认行为（**不额外接管**）；**唯一一处显式例外**是 `InitialPasswordModal`（`keyboard={false}` + `closable={false}` + `maskClosable={false}`）—— 它是**初始密码的唯一一次明文展示**，误触关掉就再也拿不回来了，所以它**刻意不响应 Esc**（"敲一次密码 → 手一抖按了 Esc → 账号废了"不是可以接受的代价）。
10. **窄屏边界**：两页都只保证 1024px 以上可用（复用已有的媒体查询），不做窄屏专门适配。
