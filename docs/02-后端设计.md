> 配套：`01-整体需求与实施步骤.md`（需求与决策基准）、`03-前端设计.md`。
> 技术结论：TypeScript / Node.js 单体。本文为自包含设计，不依赖任何既有系统。

## 一、技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| 运行时 | Node.js 22 + TypeScript 5 | 单语言栈；ACP 引擎适配器生态是 TS |
| Web 框架 | Fastify | 轻量、TS 原生、SSE/流式友好、插件体系够用不过度 |
| ORM | Prisma 7（Rust-free 客户端 + `@prisma/adapter-pg` 驱动适配器） | TS 生态最顺的 schema→类型链路；v7 起连接池改用底层 `pg`，与探活池同源，少一层黑盒（接入形态见 `06` §六 第 20 条） |
| 数据库 | PostgreSQL 16 + pgvector + pg_bigm | 业务数据 + 向量 + 中文全文一库承担（PG 内置 parser 不支持中文分词，以 bigram 补位；详见 §三/§十二） |
| 缓存/队列 | Redis 7 | 停止信号、会话、异步流水线队列（List/Stream） |
| 对象存储 | MinIO（S3 协议） | 原始文档 + 任务产物，文件不进库 |
| 容器调度 | dockerode（Docker SDK） | TaskAgent 沙箱生命周期 |
| MCP | 官方 TS SDK，协议 2025-06-18 | Streamable HTTP client、elicitation、OAuth 2.1 |
| LLM 接入 | OpenAI 兼容 client（自定义 baseURL） | 模型池全部走兼容协议，多 provider 零适配 |
| embedding | 双模式：onnxruntime-node（bge-m3 int8，默认）+ OpenAI 兼容 API | 配置切换，见第八节 |
| 文档解析 | unpdf（PDF）/ mammoth（**仅 docx**）/ 原生（md/txt） | .doc 不支持，上传时明确提示另存为 .docx |
| 校验 | Zod | 请求校验 + 共享类型 |
| 日志 | pino（结构化 JSON） | — |
| 工程形态 | pnpm monorepo（backend / frontend / shared） | DTO 一处定义前后端共用 |

## 二、架构总览

```
┌─────────────────────────────────────────────────────┐
│                  Fastify API 层                       │
│   路由 / 鉴权(Session) / Zod 校验 / SSE 出口          │
├─────────────────────────────────────────────────────┤
│                    服务层（领域）                      │
│  auth │ user │ model │ agent │ conversation │        │
│  knowledge │ mcp(+credentials) │ task │ file │ usage │
├─────────────────────────────────────────────────────┤
│                   编排层（核心）                       │
│  ChatBotOrchestrator：RAG 循环 + 工具调用循环          │
│  TaskAgentOrchestrator：沙箱管理 + ACP 桥接           │
│  SSE 归一化出口：两条链路 → 同一套事件                 │
├─────────────────────────────────────────────────────┤
│                  基础设施层                           │
│  LLMClient │ EmbeddingProvider │ MCPClient 池        │
│  DockerSandbox │ Pipeline Worker(文档流水线)          │
│  PG(Prisma) │ Redis │ S3 │ pino                     │
└─────────────────────────────────────────────────────┘
```

单体单进程；仅文档流水线 worker 作为**进程内异步任务**（Redis 队列驱动，不单独部署）。

流水线资源约束：并发上限 2（`PIPELINE_CONCURRENCY`），onnx 批量推理走 `worker_threads`，避免 CPU 密集任务（大 PDF 解析 / embedding 批量推理）阻塞在线请求；若仍出现明显争抢，演进路径为拆独立 worker 进程（Redis 队列协议不变）。

### 3.1 实现口径（P0-1-5 起，第一批 7 张表已落地）

> 已落地范围：`users` / `model_providers` / `models` / `agents` / `agent_components` /
> `conversations` / `messages`（见 `backend/prisma/schema.prisma` 与迁移 `0001_init`）。
> 其余表按 `06` 的批次顺序在 P0-1-14（知识库）与 P0-2/P0-3（MCP / 沙箱 / 产物）落地。

| 项 | 口径 | 理由 |
|----|------|------|
| 主键 | 一律 `uuid(7)`（Prisma `@default(uuid(7))` + `@db.Uuid`） | 时间有序 → 直接适配 `beforeId` 游标分页；不像自增键那样暴露业务量；不需要额外的分布式 id 方案 |
| 命名 | Prisma 侧 camelCase，库侧 snake_case（`@map`/`@@map`）；PG 枚举类型名亦 snake_case（`user_role` 等） | 与本节列名逐字对齐，`psql` 排查时不需心算转换 |
| 时间列 | `timestamptz(3)`；`created_at` 带 DB 默认 `CURRENT_TIMESTAMP`，`updated_at` 由 Prisma `@updatedAt` 维护（**无** DB 默认） | 分区按绝对时间切，必须带时区；毫秒精度足够，且与 JS `Date` 精度一致 |
| 外键删除 | `provider→models` 为 `CASCADE`（模型离开 provider 无意义）；`agents.model_id` / `agents.created_by` / `conversations.*` 为 `RESTRICT`（不允许被动消失）；`messages→conversations`、`agent_components→agents` 为 `CASCADE` | 「谁能带走谁」一次性写清楚，避免后续批次各自猜 |
| `agent_components.ref_id` | **多态外键，刻意不建 FK**（KNOWLEDGE→`knowledge_bases.id`，MCP→`mcp_servers.id`） | 一列不能同时指向两张表；引用完整性交服务层（`02` §4.4 的 PUT 全量替换），且两张目标表本批尚不存在 |
| `messages` 主键 | `(id, created_at)` 复合主键 | PG 硬性要求**分区键必须包含在主键/唯一约束内**。代价是 `findUnique` 要用复合键 `where: { id_createdAt: { id, createdAt } }`；业务上不亏 —— §4.5 的消息分页本来就带 `conversationId` 且按 `createdAt` 排序 |
| `messages` 索引 | `(conversation_id, created_at DESC)` 建在**父表**上一次 | 分区索引自动落每个分区，且**对后续 attach 的新分区同样生效**（已实测断言） |
| 分区窗口 | 迁移用 `ensure_messages_partition(月份)` 动态建「上个月 ~ 未来 12 个月」；续期脚本 `pnpm db:partitions`（幂等） | 写死日期会在窗口外用尽时让对话写不进去；向前留 1 个月覆盖数据回填/时钟偏差 |
| DEFAULT 分区 | **不建** | 它会把「新月份 attach 成正式分区」变成会失败的操作（分区约束被破坏时 PG 拒绝 attach，须停机搬数据），换来的是把"缺分区"从**立刻报错**（`no partition of relation "messages" found for row`）变成静默吞掉的假安全感 |
| `users.username` | 唯一但**大小写敏感** | 「登录时忽略大小写」由 P0-1-7 的服务层做归一（写入前统一小写），不引 `citext` 以免 Prisma 的 `@db.` 映射复杂化 |

分区说明：messages / usage_records 按月分区；**chunks 不分区**（分区表无法建全局 HNSW 索引，百万级以内单表 + HNSW 性能足够）。中文全文检索用 pg_bigm（bigram GIN，`LIKE '%词%'` 可走索引），不用 tsvector（PG 内置 parser 对中文无效）。换 embedding 模型的重建路径：新建 chunks_v2 → 流水线双写 → 切换检索指向 → 弃旧表（详见子方案①）。

> **`messages` 分区已落地（P0-1-5）**：`PARTITION BY RANGE (created_at)` + 复合主键 `(id, created_at)`，
> 分区由 `ensure_messages_partition(月份)` 动态建、由 `pnpm db:partitions` 续期，落地口径见 §3.1 表。
> Prisma 侧**照常当普通模型管理**（不启用 `experimental.externalTables`）—— 实测其内省能正确识别分区关系，
> `migrate dev` 不会重建该表，坑预判见 `06` §七 待决事项 1 的关闭记录。
> `usage_records` 到 P1 落地时按同一套路（分区键入主键 + 动态窗口 + 续期脚本）。

> **子方案①已完成**：`子方案/知识库流水线.md` 落实了本节的 DDL（含 `gin_bigm_ops` / HNSW 参数）、参数总表（chunk_size=512 **字符**、mode 三值枚举）、RRF 融合公式（k=60）、空文本检测阈值（50 字符）、覆盖重建"先删后建"语义与换模型重建五步路径。

## 四、API 设计

约定：`{ code, msg, data }` 包裹，`code=0` 成功（该格式适用于 JSON API，SSE 流与文件下载除外）；除登录外均需会话；`(A)` = 仅 ADMIN。列表分页：messages 用游标（`beforeId/limit`），其余列表 offset/limit（默认 20），小型选择器列表（模型/KB）可全量返回。

**错误出口的状态码（P0-1-4 定案）**：`code` 是唯一契约，HTTP 状态码是它的辅助信号，两条规则：

1. **领域错误**（`AppError`）→ 按 `shared/src/errors.ts` 的 `HTTP_STATUS_BY_ERROR_CODE` 出状态码（`VALIDATION`→400、`CONFLICT`→409、`NEED_CREDENTIAL`→424…）。
2. **框架错误**（Fastify 自己抛的）→ **保留其原始状态码**（415 不支持的媒体类型、413 请求体过大、408 超时…），只把 `code` 归类。把这些压成 400 会丢掉客户端的处理依据（前端要按 413 提示「文件太大」）。
   同时：**5xx 的原始 message 一律不透传**（可能是 SQL 片段/路径/堆栈），响应体只给通用文案，详情进日志（§十）。
3. **字段级明细**：校验失败时 `data.fields = [{path, message}]`，`path` 带请求部位前缀（`body.username` / `querystring.limit`），前端据此定位输入框。注意 Fastify 按 `params → body → querystring → headers` 顺序校验且**任一处失败即短路**，故一次响应只报得出第一处失败的部位。

### 4.1 认证

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/auth/login | `{username, password}` → `data` = AuthUser + Set-Cookie 会话 |
| POST | /api/auth/logout | 注销会话（幂等）；`data` = null |
| GET | /api/auth/me | 当前用户（含 mustChangePassword） |
| POST | /api/auth/password | 改密 `{oldPassword, newPassword}`（旧密码校验，首登强制走这里） |

> 首登强制改密期间（`must_change_password=true`），除 `/auth/password`、`/auth/me`、`/auth/logout` 外所有 API 一律 403。

**契约增量（P0-1-7 起）**

- `AuthUser` = `{ id, username, nickname, role, mustChangePassword }`（定义在 `shared/src/auth.ts`，前后端共用）；login / me / password 三者的 `data` 同构，**都不含任何密码字段**。`nickname` 可为 null（前端回落到 username）；刻意不含 `status`（能拿到它就一定是 ACTIVE）。
- **用户名大小写不敏感**：写入与查询前都过 `normalizeUsername()`（去空白 + 转小写），DB 侧仍是大小写敏感的唯一约束。
- **密码策略**（写入侧，login 不套）：8–64 字符**且** ≤72 字节（bcrypt 硬上限，中文按 3 字节计）。超限 → 400 `VALIDATION`，`data.fields[{path: 'body.newPassword'}]`。
- **失败态与状态码**（口径固定，前端按此写分支）：

| 情形 | 结果 |
|------|------|
| 密码错误 / 账号不存在 | 401 `UNAUTHORIZED` + 「用户名或密码错误」——**文案逐字相同且耗时对齐**（不泄露账号是否存在） |
| 连续失败达 5 次后的第 6 次起 | 429 `BUSY` + 「账号已锁定，请 N 分钟后重试」+ `data.retryAfterSec`（锁定期内正确密码同样 429） |
| 账号已停用（**密码正确时**） | 401 `UNAUTHORIZED` + 「账号已停用，请联系管理员」（密码错误时仍只给通用文案） |
| 改密时旧密码错误 | 400 `VALIDATION` + `data.fields[{path: 'body.oldPassword', message: '当前密码不正确'}]` |
| 首登未改密访问其它 API | 403 `FORBIDDEN` + 「首次登录必须修改密码后才能使用其他功能」 |

**首登闸门的实现口径（P0-1-7）**：挂在**根级 `preHandler`**，拦「除上述四个白名单路径外所有 `/api/**`」（白名单逐条显式列出，不用前缀匹配）。它**不依附于 `requireAuth`** —— 没有鉴权钩子的公共 `/api/**` 路由同样会被拦；反过来，**无 Cookie 时闸门直接放行**，不给匿名请求增加会话存储调用。停用/会话失效仍由 `requireAuth` 出 401，闸门只负责 403。

### 4.2 用户 (A)

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/users | 列表（`?offset=&limit=`，默认 20 / 上限 100） |
| POST | /api/users | 建号（返回初始密码，仅此一次明文） |
| PATCH | /api/users/:id | 启停 / 改角色 |
| POST | /api/users/:id/reset-password | 重置密码（同上） |

**契约增量（P0-1-8 起）**

- `UserListItem` = `{ id, username, nickname, role, status, mustChangePassword, createdAt }`（定义在 `shared/src/user.ts`）；列表响应为 `{ items, total, offset, limit }`（`02` §四：非消息列表用 offset/limit）。排序固定为 `username` 升序、以 `id` 兜底（**分页必须有稳定顺序**，否则翻页会重复/漏项）。
- **建号**：`{ username, nickname?, role? }` → `{ user, initialPassword }`。`role` 缺省 `MEMBER`；用户名先按 §4.1 的口径归一化（去空白 + 转小写）再存，且**不允许含空白字符**（会被抄错的用户名不该被创建出来）；`nickname` 空串按"未填"处理（存 null）。**初始密码由服务端生成**（18 字符、无易混字符），调用方不能指定。
- **初始密码的生命周期**：只在建号/重置密码**那一次响应**的 `data.initialPassword` 里出现，之后任何列表/详情接口都不再带（`02` §十 不变式）；日志侧也在 `LOG_REDACT_PATHS` 里打码。建号与重置都把该用户置为 `mustChangePassword=true`。
- **改角色/启停**：`{ status?, role? }`，**至少给一个**（缺省字段不动；两态，不需要 `null` 表达清空）。
- **不能操作自己**：停用、降级、重置自己的密码 → `409 CONFLICT`。理由：本系统只有 ADMIN 能进 `/api/users`，管理员把自己停用/降级后没有任何入口能改回来（`06` P0-1-8 坑预判「防 admin 自锁」）；重置自己也一并拒绝 —— 本人有 `/api/auth/password` 可自助改密，让"新初始密码只在响应里闪一次"这种路径少一条。
- **重置密码的连带动作**：① 失效该用户的快照缓存（否则他在线的会话不会被首登闸门拦住）；② **清掉登录失败计数** —— 现实中"重置密码"往往正是因为对方被锁在外面（连错 5 次），不清计数的话重置完仍要再等最多 10 分钟，看着就是"重置没生效"；③ 不吊销其已有会话（没有按用户反查会话的索引，见 §10.1），但配合①后那些会话会立刻被闸门赶到改密页。
- **状态码**：成功一律 `200`（信封的 `code=0` 是唯一契约，状态码是辅助信号 —— 与 §四 的错误出口口径一致，此处不引入 201）；`401` 未登录 / `403` 非 ADMIN（或首登未改密被闸门拦）；`404` 目标不存在（含 `:id` 不是合法 UUID 时的 `400`）；`409` 用户名已存在（含大小写变体）、操作自己；`400` 参数校验失败（带 `data.fields`）。

**第一个账号从哪来（种子脚本口径，P0-1-9 起）**

`/api/users` 要求调用者是 ADMIN，因此系统里的**第一个 ADMIN 由种子脚本产生**，不由任何 API 产生：

- 命令：`pnpm db:seed`（= `db:generate && tsx prisma/seed.ts`；前置 `pnpm infra:up && pnpm db:deploy`）；
- 产出：一个 `ADMIN` + 一个 `MEMBER`，**两者都是 `mustChangePassword=true`（首登改密态）**——
  与"admin 建号"完全同构，所以 **admin 也必须先改密才能建号**（首登闸门白名单不含 `/api/users`）；
- **幂等是安全属性**：默认「不存在才建，已存在则跳过且绝不改密码」，覆盖密码要显式
  `SEED_RESET_PASSWORD=1`（并把该账号打回首登改密态）。否则每次 `db:seed` 都会把
  已自行改过密码的人锁在门外，而症状（401）与"密码记错"无法区分；
- 初始密码在种子脚本 stdout 上**只打印一次**（与建号响应同一语义：交付而非记录）；
- 变量（可选，不进 `AppConfig`，只在种子脚本进程内生效）：
  `SEED_ADMIN_USERNAME`(admin) / `SEED_ADMIN_PASSWORD`(随机 18 位) / `SEED_ADMIN_NICKNAME`(系统管理员) /
  `SEED_MEMBER_USERNAME`(member) / `SEED_MEMBER_PASSWORD`(随机 18 位) / `SEED_MEMBER_NICKNAME`(示例成员) /
  `SEED_RESET_PASSWORD`(空)。开关一律走**环境变量**（根 script 经 `pnpm --filter` 会吞掉额外参数）。

### 4.3 模型池 (A)

| 方法 | 路径 | 说明 |
|------|------|------|

**契约增量 · Provider（P0-1-10 起）**

- `ModelProviderItem` = `{ id, name, baseUrl, type, enabled, hasKey, apiKeyPreview, modelCount, createdAt, updatedAt }`（定义在 `shared/src/modelProvider.ts`）；列表响应为 `{ items, total, offset, limit }`（默认 20 / 上限 100）。排序固定 `createdAt` 升序、以 `id` 兜底（Provider 数量极少，按录入顺序展示最直观；分页仍需稳定顺序）。
- **Key 有进无出**：`apiKey` 只出现在请求方向（`POST`/`PATCH` 的 body）。响应方向**永远没有** `apiKey` / `apiKeyEnc` 之类字段，只有 `hasKey`（布尔）与 `apiKeyPreview`（`sk-****abcd` 形态的掩码）。前端表单据此把"已配置"渲染成掩码 + "重新设置"，**不回填输入框**（`01` §3.2 验收要点「Key 不回显明文」）。
- **掩码口径**：明文长度 ≥ 16 时给 `前3 + **** + 后4`；8~15 只给 `****后4`；< 8 一律 `****`。掩码由后端**解密后**取首尾生成 —— 也就是说"能看到掩码"本身证明密文可解（主密钥没配错）。
- **存储形态**：`api_key_enc` 是 `v1.<iv>.<tag>.<ct>`（base64url，无填充）的 AES-256-GCM 密文，主密钥来自 `CREDENTIAL_MASTER_KEY`（§十）。密文**绑定到记录**：加密用 AAD `model-providers:{id}.api_key_enc`，因此密文被粘到另一条记录上就解不开。⚠️ 代价：**加密必须发生在拿到 `id` 之后**，故建 Provider 用事务（先落行拿 `id`，再写入密文），见 §10.2。
- **`apiKey` 的三态（PATCH）**：不带该字段 = **不动原 Key**；`null` = **清空**；字符串 = **写入新 Key**。**空串被拒（400）** —— 只留两条明确的路，避免"到底清没清"的歧义。这一条最容易被写成"每次 PATCH 都重新加密"，从而在"改个名字"时把 Key 悄悄抹掉（或把密文无谓改写）。
- **`baseUrl` 契约**：必须 `http://` 或 `https://` 开头且是合法 URL（拒绝其他 scheme：这个值最终会被后端拿去发请求，放宽 scheme 等于放大 SSRF 面），长度 ≤ 2048；**尾部斜杠会被归一化去掉**（否则将来拼 `/chat/completions` 会出现 `//`，有的网关当 404）。
- **`type` 的守卫**：`model_providers.type` 与 `models.type` 冗余，故 Provider 下**已有模型时不允许改 type** → `409`（同值 PATCH 放行）。替代方案（级联改所有模型的 type）会静默改变"已绑定 Agent 用的是哪类模型"，不采用。
- **删除语义**：`models.provider_id` 是 `ON DELETE CASCADE`，但 `agents.model_id` 是 `ON DELETE RESTRICT` —— 因此**当 Provider 下有模型被 Agent 引用时，删除会被前置检查拦成 `409`**（而不是撞外键抛 500）。Agent 软删（`agents.deleted_at`）仍占着外键，计数刻意不按 `deletedAt` 过滤，否则会出现"提示说能删、删下去却 500"。
- **状态码**：成功一律 `200`（不引入 201/204）；`401` 未登录 / `403` 非 ADMIN（或首登未改密被闸门拦）；`404` 目标不存在；`400` 参数校验失败（`data.fields`）；`409` 有模型时改 type、有模型被 Agent 引用时删除。
- **名称不做唯一约束**：`model_providers` 上没有 `name` 唯一索引（§三），同名的两个 Provider 靠 `id` 区分。服务层刻意不造一条"看起来唯一、并发下不唯一"的查重规则；需要唯一性时应先加约束再改代码。

**`/health` 的语义（P0-1-4 定案）**：

- **HTTP 恒 200**，依赖状态放在响应体里：`data.status ∈ {ok, degraded}` + `data.checks[]`（每项含
  `target / ok / latencyMs / detail`）。理由：探活端点自身是「请求成功」——它确实给出了结论；把某个
  依赖抖动直接映射成 5xx 会让网关/负载均衡把**整个后端**摘掉（本机只停 Redis 时后端其实还能服务大部分接口）。
  若将来上 k8s 需要 status code 形式的 readiness，另加 `/health/ready`（返 503）更清楚，不把两种语义塞进同一端点。
- 每项探活**必须带超时**（`HEALTH_TIMEOUT_MS`，默认 2s），单项失败只降级、不整体报错：
  `detail` 要能直接告诉运维「为什么」（如 `connect ECONNREFUSED 127.0.0.1:16379`）。
- 推荐运维口径：`jq '.data.status'` 判整体；`jq '.data.checks[] | select(.ok==false)'` 定位到具体依赖。

## 五、SSE 协议（前后端唯一契约，双链路归一化）

`POST /api/conversations/:id/chat`，请求体 `{ content, attachmentFileIds?[] }`，响应 `text/event-stream`。

### 5.1 事件全集

| event | data | 说明 |
|-------|------|------|
| `delta` | `{ text }` | 助手回答文本增量 |
| `thinking` | `{ text }` | 思考过程增量（可折叠渲染） |
| `tool_call` | `{ callId, toolName, serverName, kind: MCP\|SANDBOX, status: RUNNING\|SUCCESS\|ERROR, inputSummary, output? }` | 工具调用卡片；同一 callId 多次推送 = 状态机流转 |
| `confirm` | `{ confirmId, toolName, inputSummary }` | elicitation：前端弹确认卡，用户答复走 `/confirm` 接口，流挂起等待 |
| `citations` | `{ items: [{ docName, snippet, score }] }` | 本轮知识库引用 |
| `artifact` | `{ artifactId, fileName, size, mime }` | TaskAgent 产出文件 |
| `queued` | `{ position }` | 沙箱并发满，排队中 |
| `ping` | `{ ts }` | 心跳（每 15–25s 一次，空闲期保活）；前端静默忽略；防止排队/确认挂起/长任务静默期被网关断连 |
| `done` | `{ messageId, finishReason: COMPLETE\|STOPPED\|ERROR, usage: { tokensIn, tokensOut } }` | 流结束 |
| `error` | `{ code, message }` | 错误（流终止） |

### 5.2 语义规则

- **事件即真相**：前端渲染只依赖事件流；持久化由后端在 `done` 时整条落库（含 tool_calls/citations/artifacts 结构），历史拉取直接读库，**不做 SSE 重放**
- **会话互斥**：Redis 锁 `chat.active:{conversationId}`；持锁期间同一会话再次发送返回 `error{code: CONFLICT}`（防双标签页并发写乱历史）
- **心跳**：空闲期（排队/confirm 挂起/引擎长静默）每 15–25s 推送 `ping`；部署前提：网关 `proxy_read_timeout ≥ 120s` 且关闭响应缓冲
- **停止**：`stop` 写 Redis key `chat.stop:{conversationId}`（TTL 60s），编排循环每个可中断点检查；中断后推送 `done{finishReason: STOPPED}`
- **confirm 挂起**：确认等待上限 120s，超时按取消处理
- **断线**：前端断线重连后先查 `/api/conversations/:id/active` 获取进度（在流/排队位次/当前工具），再调消息历史接口补齐（事件流不重放；历史不含进行中消息，进行中状态由 active 提供）
- **两条链路同构**：ChatBot 的 MCP 工具与 TaskAgent 的沙箱工具（bash/read/write 等）都映射为 `tool_call`（`kind` 区分）；引擎侧事件在编排层完成映射（详见子方案③）

```
    system = agent.system_prompt

    → delta / thinking 持续透传
 4. 工具循环：LLM 返回 tool_call 时
    a. 该工具属于某 MCP server？

 5. done：整条消息落库 + usage_records 计量
```

## 十、安全设计

| 项 | 方案 |
|----|------|
| 会话 | HttpOnly + SameSite=Lax Cookie + Redis 存储（登出即毁）；每请求校验 user.status（60s TTL 缓存），停用账号立即失效（实现口径见 §10.1） |
| 密码 | bcrypt(cost 12)；初始密码一次性展示 |
| 凭据/Provider Key | AES-256-GCM，主密钥仅环境变量注入 |
| HTML 产物预览 | 仅 sandbox iframe（无 script 权限）+ CSP，详见子方案④ |
| 文件下载 | 签名 URL + Content-Disposition: attachment |

| Docker socket | app 容器挂载 docker.sock 为**已知 trade-off**（等效宿主 root）；建议经 docker-socket-proxy 收敛暴露的 API 面 |

### 10.1 会话实现口径（P0-1-6 起落地）

**Cookie**

| 项 | 取值 | 说明 |
|----|------|------|
| 名 | `doubulea_sid` | 常量，不做成环境变量（前后端各配一个名字会造成"登录成功仍显示未登录"） |
| 值 | 43 字符 base64url（32 字节 CSPRNG） | 会话令牌，**不签名** —— 身份真相在 Redis，签名不增加安全属性（详见 06 P0-1-6 落地要点 6） |
| 属性 | `HttpOnly` + `SameSite=Lax` + `Path=/` + `Max-Age=SESSION_TTL_HOURS` | 登出与登录必须用**同一份**选项，否则浏览器不覆盖旧 Cookie（症状：点了登出还是登录态） |
| `Secure` | 跟随 `SESSION_COOKIE_SECURE`，默认 = `NODE_ENV === 'production'` | 内网 HTTP 直连时必须显式置 `false`（否则浏览器丢弃 Cookie），生产置 false 会启动 WARN |

**Redis 键**

| 键 | 值 | TTL |
|----|----|-----|
| `session:{sid}` | `{userId, renewedAt}` | `SESSION_TTL_HOURS`（默认 12h）；**半衰期滑动续期**（已用掉一半才重写，避免每请求一次写） |
| `auth-user:{userId}` | `{id, username, role, status, mustChangePassword}`（**不含 `passwordHash`**） | `USER_STATUS_CACHE_TTL_SEC`（默认 60s） |

**失效语义（写侧责任）**：`user.status` 与角色变化**必须**由写侧调 `invalidateUserSnapshot(userId)` 主动失效缓存（P0-1-8 的启停 / 改角色 / 重置密码），否则最坏要等一个缓存窗口才生效；缓存只兜底"有人直接在库里改状态"的场景。该函数写失败**向上抛**（与"写缓存失败只告警"刻意相反）—— 失效是正确性要求，缓存只是性能优化。

**鉴权出口编码**（`requireAuth` 的四个结论，避免各处自行发明）：

| 情形 | 结果 |
|------|------|
| 无 Cookie | `401 UNAUTHORIZED`，**不访问 Redis**（匿名/探测请求不该打在依赖上） |
| 会话键不存在 / 已过期 / 用户已删 / `status=DISABLED` | `401`；**一律自毁**（删会话键 + 清 Cookie）；停用额外给出「账号已停用」文案 |
| 会话存储（Redis）不可用 | `500 INTERNAL` —— 依赖故障 ≠ 凭据不对；映射 401 会把在线用户全踢回登录页，运维也看不到 5xx |
| 已登录但非 ADMIN 访问 `(A)` 端点 | `403 FORBIDDEN` |

### 10.2 Provider Key 的存储口径（P0-1-10 起落地）

> 实现：`backend/src/services/model.service.ts`（唯一的读写点）+ `backend/src/infra/crypto.ts`（算法）。

| 项 | 取值 |
|----|------|
| 落库列 | `model_providers.api_key_enc`（`TEXT`，可为 `NULL` = 未配置） |
| 算法 | AES-256-GCM，密文形态 `v1.<iv:12B>.<tag:16B>.<ct>`，各段 base64url 无填充（§十） |
| AAD（附加认证数据） | `model-providers:{id}.api_key_enc` —— 由 `providerKeyAad()` 单点生成，写/读两侧共用 |
| 出口 | 只有 `hasKey` + `apiKeyPreview`（掩码）。**任何响应体都不含密文或明文** |

**三条要点**

1. **加密依赖 `id`，所以建 Provider 必须用事务**：`id` 由 Prisma 在 `create` 时按 `uuid(7)` 生成，
   而 AAD 里含 `id` —— 只能"先落一行拿 `id`，再用它加密写回"。若拆成两条独立语句，
   中间失败会留下"建好了但 Key 没写进去"的 Provider，而调用方看到失败会重试再建一个。
   PATCH 路径不需要事务（`id` 已知）。
2. **解密失败不掀桌**：主密钥换过/密文坏了时，`apiKeyPreview` 降级为 `****` 并留 warn，
   `hasKey` 仍为 `true` —— 语义准确（Key 还在，只是本进程解不开），且列表接口不会整页 500，
   管理员至少能看到"哪个 Provider 的 Key 坏了"。
3. **不要"防重解密"缓存**：`apiKeyPreview` 每次读都由服务端解密一次，成本可忽略（毫秒级），
   换来的是"读路径无副作用"（密文不会被读操作改写）与"换主密钥后立刻反映真实状态"。
   ⚠️ 反过来说：**PATCH 不传 `apiKey` 时必须一个字节都不写**，否则密文会被无谓重写
   （IV 变化 → 验收里"密文逐字不变"这条会失败）。

## 十二、部署形态

```
docker compose:
  app        （本后端 + 前端静态资源，单容器；挂 /var/run/docker.sock）
  postgres   （自建镜像：pgvector + pg_bigm；数据卷；pg_dump 定时备份 cron）
  redis      （数据卷；AOF everysec——重启不丢 session 与队列）
  minio      （数据卷）
  挂载卷：/models/bge-m3-int8（local embedding 模式时）
```

- app 容器需访问宿主 Docker daemon（沙箱调度）
- 网关/反向代理（如 nginx）：`proxy_read_timeout ≥ 120s` + `proxy_buffering off`（SSE 前提，配合 §五心跳）
- 无其他外部依赖；embedding 默认本地，纯内网可整体运行
- 升级：镜像替换 + Prisma migrate；回滚 = 回退镜像（schema 向前兼容一个版本）
