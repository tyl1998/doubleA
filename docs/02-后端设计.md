单体单进程；仅文档流水线 worker 作为**进程内异步任务**（Redis 队列驱动，不单独部署）。

流水线资源约束：并发上限 2（`PIPELINE_CONCURRENCY`），onnx 批量推理走 `worker_threads`，避免 CPU 密集任务（大 PDF 解析 / embedding 批量推理）阻塞在线请求；若仍出现明显争抢，演进路径为拆独立 worker 进程（Redis 队列协议不变）。

**文档流水线 worker 的实现口径（P0-1-17 定案）**：

- **生命周期归进程入口 `index.ts`**（`listen` 成功后 `startPipelineWorker()`，优雅退出时**先** `stopPipelineWorker()` 再关连接），**不进 `buildApp()`** —— 它是"进程级后台组件"而非 HTTP 应用的一部分；放进 `buildApp()` 会让所有走 `app.inject` 的契约验收被迫连 Redis，还会莫名开始消费队列里的任务。
- **队列键可配**：`PIPELINE_QUEUE_KEY`（默认 `pipeline:jobs`）。队列是"**被消费**"的资源而 Redis 是共享的 —— 两个进程用同一条队列时"谁取走 job"是随机的，症状是"时好时坏"而不是报错；改键即可隔离消费方（验收脚本一律注入独立键）。
- **阻塞读走独立连接**：`BRPOP` 在返回前占住整条连接，复用会话单例会在"队列空闲时"把 `/api/auth`、`/health` 与所有会话读写一起钉住（有 job 时看不出来）⇒ 队列用 `createRedisConnection()` 另开一条，收尾用 `disconnect()`。
- **写状态一律走 CAS 且受状态机约束**：`documents.status` 的合法转换见 `shared` 的 `DOCUMENT_STATUS_TRANSITIONS`（`PARSING → READY | FAILED`、`FAILED → PARSING`、`READY → PARSING`）；**刻意不允许 `READY → FAILED`** —— 那是"过期 job 把已成功的文档打回失败"的唯一形态，且重投也救不回来。写入用 `updateMany({ where: { id, status: from } })`，非法转换只告警不写。
- **幂等四道**（`子方案①` §三 只写了"已是 READY 且 hash 未变"这一道）：同进程在飞去重 / 文档已删 / `contentHash` 与 job 不符（旧内容的 job）/ 已是 `READY`。四道全跳过时**一个字节都不写库**；`PARSING`/`FAILED` 且 hash 相符的 job 会**真的重新处理** —— 这就是"重投同一个 job 能把文档救回 `READY`"（List 无 ack 的补救口，P0-1-19 的 `POST .../retry` 只是给它加端点）。
- **失败要区分两类**：阶段抛错 → `FAILED` + `error_msg`（**给用户看的中文可操作提示**，技术细节只进日志）；读行/写状态本身就失败（PG 挂了）→ 不写状态只记日志（把"我们查不了"写成"这个文档坏了"会让用户重传一个没问题的文件）。

**流水线阶段的实现口径（P0-1-18 增量；P0-1-19 补齐 ⑥⑦）**：

- **阶段序列是插拔点**，现在是六步：`load-source → parse → detect-empty-text → chunk → embed → index`（= `子方案①` §三 的 ③~⑦，⑧ 是"收敛状态"由 worker 做）。**顺序不可换**：④ 必须在 ⑤ 之前（否则扫描件先白切一遍再判失败，且"块数为 0 却报句子级错误"会把排查方向带偏）；⑤ 必须在 ⑥ 之前（embedding 的输入就是块）；⑥ 必须在 ⑦ 之前且**只此一次**（向量与块是同一条记录的两半，分开写会出现"有块没向量"或"有向量没块"）。**至此 `READY` 才等于"可检索"。**
- **阶段要用的 KB 参数由 worker 一次联表带出**（`JOB_DOCUMENT_SELECT` 的 `kb` 片段：`chunk_size` / `chunk_overlap` / `retrieval_config`），**不让阶段各自再查一遍库** —— 三个阶段各查一次就是"同一份数据、三种读法"的开端。`splitStrategy` 一律经 `shared` 的 `normalizeRetrievalConfig()` 补默认值（jsonb 可能缺键），**不在业务代码里再写一次 `??`**。
- **分段与分块的正确性靠纯函数守**：`pipeline/chunk/` 刻意**不 import `config`/logger** ⇒ 无依赖档（`verify:app`，可进 CI）能直接断言它。三条最容易静默做错的：**单位是码点**（`[...text]` 切片，`text.slice()` 会劈开代理对且本层无报错）、**Section 按"连续同名标题"切**（按 `headingPath` 分组会让 chunk 顺序与原文不一致，而这在检索层几乎发现不了）、**每块都是原文的逐字子串**（P0-1-20 的"引用片段与原文一致"以它为前提）。
- **`chunk_min`（50）是代码常量，不是环境变量也不是 KB 列**：`子方案①` §十一 的配置增量表里没有它 ⇒ 加一个变量属于自己发明契约。它同时被用作"句末回退"的下界（最近的边界落在它之前 ⇒ 硬切，免得切出碎块）。
- **embedding 的重试落在"批"粒度**（`§4-3` 的"单批失败重试 2 次、退避 1s/3s"）：`EmbeddingProvider.embed()` 自己会按 `batchSize` 切批、看到的永远是"一次调用" ⇒ 由 `pipeline/index/writer.ts` 先按 `EMBEDDING_BATCH_SIZE` 切好、每次只喂一批，重试边界才与"批"对齐。**一批仍失败 ⇒ 整篇 `FAILED`**（跳过这批会留下"有块没向量"的坏数据：那些 chunk 在检索里永远排不上号，而界面上一切正常）。
- **⚠️ 入库不是 `INSERT ... SELECT unnest(...)`，而是"Prisma 建行 + 手写 `UPDATE ... unnest` 回填向量"**（对 `§4-4` 草稿的刻意偏离）：草稿要求"自带 id 数组"，而 `chunks.id` 的口径是 `uuid(7)`（§3.1），且 P0-1-16 已定案**不手搓 uuid7** ⇒ 该值在本仓只有 Prisma 的 `@default` 一个实现，必须走 Prisma 的写入路径才拿得到。两步（建行、回填向量）在**同一事务**里，批量仍是每批 200 行。`embedding` 是 `Unsupported` 列，只能由手写 SQL 写 —— 这是全仓唯一一处手写 SQL 的地方，集中在 `pipeline/index/writer.ts`。**验收里有一条"id 的版本位必须是 7"**守住这条不变式。
- **`chunk_count` 只在 ⑦ 成功之后才写**（P0-1-18 曾刻意留空）：worker 用 `ctx.chunkCount`（= 事务里真实的写入行数）落那一列，读取端可据此判断"这篇能不能检索"。
- **写入是"同一 doc 的 chunk 集合整次替换"**：`DELETE WHERE doc_id` → 建行 → 回填向量，全在一个事务里 —— 中途失败必须回到"旧的那一份"或"没有"，不能半新半旧（`§七` 的"无重复、无孤儿"）。

### 3.1 实现口径（P0-1-5 起，第一批 7 张表已落地）

> 已落地范围：`users` / `model_providers` / `models` / `agents` / `agent_components` /
> `conversations` / `messages`（见 `backend/prisma/schema.prisma` 与迁移 `0001_init`）。
> 其余表按 `06` 的批次顺序在 P0-1-14（知识库）与 P0-2/P0-3（MCP / 沙箱 / 产物）落地。

| 项 | 口径 | 理由 |
|----|------|------|
| 主键 | 一律 `uuid(7)`（Prisma `@default(uuid(7))` + `@db.Uuid`） | 时间有序 → 直接适配 `beforeId` 游标分页；不像自增键那样暴露业务量；不需要额外的分布式 id 方案 |
| 命名 | Prisma 侧 camelCase，库侧 snake_case（`@map`/`@@map`）；PG 枚举类型名亦 snake_case（`user_role` 等） | 与本节列名逐字对齐，`psql` 排查时不需心算转换 |
| 时间列 | `timestamptz(3)`；`created_at` 带 DB 默认 `CURRENT_TIMESTAMP`，`updated_at` 由 Prisma `@updatedAt` 维护（**无** DB 默认） | 分区按绝对时间切，必须带时区；毫秒精度足够，且与 JS `Date` 精度一致 |
| 外键删除 | `provider→models` 为 `CASCADE`（模型离开 provider 无意义）；`agents.model_id` / `agents.created_by` / `conversations.*` 为 `RESTRICT`（不允许被动消失）；`messages→conversations`、`agent_components→agents` 为 `CASCADE` | 「谁能带走谁」一次性写清楚，避免后续批次各自猜 |
| `agent_components.ref_id` | **多态外键，刻意不建 FK**（KNOWLEDGE→`knowledge_bases.id`，MCP→`mcp_servers.id`） | 一列不能同时指向两张表；引用完整性交服务层（`02` §4.4 的 PUT 全量替换），且两张目标表本批尚不存在 |
| `messages` 主键 | `(id, created_at)` 复合主键 | PG 硬性要求**分区键必须包含在主键/唯一约束内**。代价是 `findUnique` 要用复合键 `where: { id_createdAt: { id, createdAt } }`；业务上不亏 —— §4.5 的消息分页本来就带 `conversationId` 且按 `createdAt` 排序 |
| `messages` 索引 | `(conversation_id, created_at DESC)` 建在**父表**上一次 | 分区索引自动落每个分区，且**对后续 attach 的新分区同样生效**（已实测断言） |
| 分区窗口 | 迁移用 `ensure_messages_partition(月份)` 动态建「上个月 ~ 未来 12 个月」；续期脚本 `pnpm db:partitions`（幂等） | 写死日期会在窗口外用尽时让对话写不进去；向前留 1 个月覆盖数据回填/时钟偏差 |
| DEFAULT 分区 | **不建** | 它会把「新月份 attach 成正式分区」变成会失败的操作（分区约束被破坏时 PG 拒绝 attach，须停机搬数据），换来的是把"缺分区"从**立刻报错**（`no partition of relation "messages" found for row`）变成静默吞掉的假安全感 |
| `users.username` | 唯一但**大小写敏感** | 「登录时忽略大小写」由 P0-1-7 的服务层做归一（写入前统一小写），不引 `citext` 以免 Prisma 的 `@db.` 映射复杂化 |

分区说明：messages / usage_records 按月分区；**chunks 不分区**（分区表无法建全局 HNSW 索引，百万级以内单表 + HNSW 性能足够）。中文全文检索用 pg_bigm（bigram GIN，`LIKE '%词%'` 可走索引），不用 tsvector（PG 内置 parser 对中文无效）。换 embedding 模型的重建路径：新建 chunks_v2 → 流水线双写 → 切换检索指向 → 弃旧表（详见子方案①）。

> **`messages` 分区已落地（P0-1-5）**：`PARTITION BY RANGE (created_at)` + 复合主键 `(id, created_at)`，
> 分区由 `ensure_messages_partition(月份)` 动态建、由 `pnpm db:partitions` 续期，落地口径见 §3.1 表。
> Prisma 侧**照常当普通模型管理**（不启用 `experimental.externalTables`）—— 实测其内省能正确识别分区关系，
> `migrate dev` 不会重建该表，坑预判见 `06` §七 待决事项 1 的关闭记录。
> `usage_records` 到 P1 落地时按同一套路（分区键入主键 + 动态窗口 + 续期脚本）。

> **子方案①已完成**：`子方案/知识库流水线.md` 落实了本节的 DDL（含 `gin_bigm_ops` / HNSW 参数）、参数总表（chunk_size=512 **字符**、mode 三值枚举）、RRF 融合公式（k=60）、空文本检测阈值（50 字符）、覆盖重建"先删后建"语义与换模型重建五步路径。

## 四、API 设计

约定：`{ code, msg, data }` 包裹，`code=0` 成功（该格式适用于 JSON API，SSE 流与文件下载除外）；除登录外均需会话；`(A)` = 仅 ADMIN。列表分页：messages 用游标（`beforeId/limit`），其余列表 offset/limit（默认 20），小型选择器列表（模型/KB）可全量返回。

**错误出口的状态码（P0-1-4 定案）**：`code` 是唯一契约，HTTP 状态码是它的辅助信号，两条规则：

1. **领域错误**（`AppError`）→ 按 `shared/src/errors.ts` 的 `HTTP_STATUS_BY_ERROR_CODE` 出状态码（`VALIDATION`→400、`CONFLICT`→409、`NEED_CREDENTIAL`→424…）。
2. **框架错误**（Fastify 自己抛的）→ **保留其原始状态码**（415 不支持的媒体类型、413 请求体过大、408 超时…），只把 `code` 归类。把这些压成 400 会丢掉客户端的处理依据（前端要按 413 提示「文件太大」）。
   同时：**5xx 的原始 message 一律不透传**（可能是 SQL 片段/路径/堆栈），响应体只给通用文案，详情进日志（§十）。
3. **字段级明细**：校验失败时 `data.fields = [{path, message}]`，`path` 带请求部位前缀（`body.username` / `querystring.limit`），前端据此定位输入框。注意 Fastify 按 `params → body → querystring → headers` 顺序校验且**任一处失败即短路**，故一次响应只报得出第一处失败的部位。

### 4.1 认证

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/auth/login | `{username, password}` → `data` = AuthUser + Set-Cookie 会话 |
| POST | /api/auth/logout | 注销会话（幂等）；`data` = null |
| GET | /api/auth/me | 当前用户（含 mustChangePassword） |
| POST | /api/auth/password | 改密 `{oldPassword, newPassword}`（旧密码校验，首登强制走这里） |

> 首登强制改密期间（`must_change_password=true`），除 `/auth/password`、`/auth/me`、`/auth/logout` 外所有 API 一律 403。

**契约增量（P0-1-7 起）**

- `AuthUser` = `{ id, username, nickname, role, mustChangePassword }`（定义在 `shared/src/auth.ts`，前后端共用）；login / me / password 三者的 `data` 同构，**都不含任何密码字段**。`nickname` 可为 null（前端回落到 username）；刻意不含 `status`（能拿到它就一定是 ACTIVE）。
- **用户名大小写不敏感**：写入与查询前都过 `normalizeUsername()`（去空白 + 转小写），DB 侧仍是大小写敏感的唯一约束。
- **密码策略**（写入侧，login 不套）：8–64 字符**且** ≤72 字节（bcrypt 硬上限，中文按 3 字节计）。超限 → 400 `VALIDATION`，`data.fields[{path: 'body.newPassword'}]`。
- **失败态与状态码**（口径固定，前端按此写分支）：

| 情形 | 结果 |
|------|------|
| 密码错误 / 账号不存在 | 401 `UNAUTHORIZED` + 「用户名或密码错误」——**文案逐字相同且耗时对齐**（不泄露账号是否存在） |
| 连续失败达 5 次后的第 6 次起 | 429 `BUSY` + 「账号已锁定，请 N 分钟后重试」+ `data.retryAfterSec`（锁定期内正确密码同样 429） |
| 账号已停用（**密码正确时**） | 401 `UNAUTHORIZED` + 「账号已停用，请联系管理员」（密码错误时仍只给通用文案） |
| 改密时旧密码错误 | 400 `VALIDATION` + `data.fields[{path: 'body.oldPassword', message: '当前密码不正确'}]` |
| 首登未改密访问其它 API | 403 `FORBIDDEN` + 「首次登录必须修改密码后才能使用其他功能」 |

**首登闸门的实现口径（P0-1-7）**：挂在**根级 `preHandler`**，拦「除上述四个白名单路径外所有 `/api/**`」（白名单逐条显式列出，不用前缀匹配）。它**不依附于 `requireAuth`** —— 没有鉴权钩子的公共 `/api/**` 路由同样会被拦；反过来，**无 Cookie 时闸门直接放行**，不给匿名请求增加会话存储调用。停用/会话失效仍由 `requireAuth` 出 401，闸门只负责 403。

### 4.2 用户 (A)

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/users | 列表（`?offset=&limit=`，默认 20 / 上限 100） |
| POST | /api/users | 建号（返回初始密码，仅此一次明文） |
| PATCH | /api/users/:id | 启停 / 改角色 |
| POST | /api/users/:id/reset-password | 重置密码（同上） |

**契约增量（P0-1-8 起）**

- `UserListItem` = `{ id, username, nickname, role, status, mustChangePassword, createdAt }`（定义在 `shared/src/user.ts`）；列表响应为 `{ items, total, offset, limit }`（`02` §四：非消息列表用 offset/limit）。排序固定为 `username` 升序、以 `id` 兜底（**分页必须有稳定顺序**，否则翻页会重复/漏项）。
- **建号**：`{ username, nickname?, role? }` → `{ user, initialPassword }`。`role` 缺省 `MEMBER`；用户名先按 §4.1 的口径归一化（去空白 + 转小写）再存，且**不允许含空白字符**（会被抄错的用户名不该被创建出来）；`nickname` 空串按"未填"处理（存 null）。**初始密码由服务端生成**（18 字符、无易混字符），调用方不能指定。
- **初始密码的生命周期**：只在建号/重置密码**那一次响应**的 `data.initialPassword` 里出现，之后任何列表/详情接口都不再带（`02` §十 不变式）；日志侧也在 `LOG_REDACT_PATHS` 里打码。建号与重置都把该用户置为 `mustChangePassword=true`。
- **改角色/启停**：`{ status?, role? }`，**至少给一个**（缺省字段不动；两态，不需要 `null` 表达清空）。
- **不能操作自己**：停用、降级、重置自己的密码 → `409 CONFLICT`。理由：本系统只有 ADMIN 能进 `/api/users`，管理员把自己停用/降级后没有任何入口能改回来（`06` P0-1-8 坑预判「防 admin 自锁」）；重置自己也一并拒绝 —— 本人有 `/api/auth/password` 可自助改密，让"新初始密码只在响应里闪一次"这种路径少一条。
- **重置密码的连带动作**：① 失效该用户的快照缓存（否则他在线的会话不会被首登闸门拦住）；② **清掉登录失败计数** —— 现实中"重置密码"往往正是因为对方被锁在外面（连错 5 次），不清计数的话重置完仍要再等最多 10 分钟，看着就是"重置没生效"；③ 不吊销其已有会话（没有按用户反查会话的索引，见 §10.1），但配合①后那些会话会立刻被闸门赶到改密页。
- **状态码**：成功一律 `200`（信封的 `code=0` 是唯一契约，状态码是辅助信号 —— 与 §四 的错误出口口径一致，此处不引入 201）；`401` 未登录 / `403` 非 ADMIN（或首登未改密被闸门拦）；`404` 目标不存在（含 `:id` 不是合法 UUID 时的 `400`）；`409` 用户名已存在（含大小写变体）、操作自己；`400` 参数校验失败（带 `data.fields`）。

**第一个账号从哪来（种子脚本口径，P0-1-9 起）**

`/api/users` 要求调用者是 ADMIN，因此系统里的**第一个 ADMIN 由种子脚本产生**，不由任何 API 产生：

- 命令：`pnpm db:seed`（= `db:generate && tsx prisma/seed.ts`；前置 `pnpm infra:up && pnpm db:deploy`）；
- 产出：一个 `ADMIN` + 一个 `MEMBER`，**两者都是 `mustChangePassword=true`（首登改密态）**——
  与"admin 建号"完全同构，所以 **admin 也必须先改密才能建号**（首登闸门白名单不含 `/api/users`）；
- **幂等是安全属性**：默认「不存在才建，已存在则跳过且绝不改密码」，覆盖密码要显式
  `SEED_RESET_PASSWORD=1`（并把该账号打回首登改密态）。否则每次 `db:seed` 都会把
  已自行改过密码的人锁在门外，而症状（401）与"密码记错"无法区分；
- 初始密码在种子脚本 stdout 上**只打印一次**（与建号响应同一语义：交付而非记录）；
- 变量（可选，不进 `AppConfig`，只在种子脚本进程内生效）：
  `SEED_ADMIN_USERNAME`(admin) / `SEED_ADMIN_PASSWORD`(随机 18 位) / `SEED_ADMIN_NICKNAME`(系统管理员) /
  `SEED_MEMBER_USERNAME`(member) / `SEED_MEMBER_PASSWORD`(随机 18 位) / `SEED_MEMBER_NICKNAME`(示例成员) /
  `SEED_RESET_PASSWORD`(空)。开关一律走**环境变量**（根 script 经 `pnpm --filter` 会吞掉额外参数）。

### 4.3 模型池 (A)

| 方法 | 路径 | 说明 |
|------|------|------|
| GET/POST/PATCH/DELETE | /api/model-providers[…/:id] | Provider 管理（Key 写入加密，读脱敏） |
| GET | /api/model-providers/:id/remote-models | **拉取上游实际提供的模型列表**（仅 ADMIN；只读探测、不落库，P0-1-12） |
| GET/POST/PATCH/DELETE | /api/models[…/:id] | 模型管理（`(A)` 仅 ADMIN） |
| POST | /api/models/:id/test | 连通测试（P1） |
| GET | /api/models/available?type=CHAT | 全员可选模型列表（登录即可；建 Agent 用） |

> ⚠️ 最后一行原写作 `GET /api/models?type=CHAT`。P0-1-11 落地时改为**子路径** —— 同一条
> `GET /api/models` 不能既做管理列表又做全员可选列表：Fastify 对"同路径同方法注册两次"会在
> **启动期**抛 `FST_ERR_DUPLICATED_ROUTE`（已实测）。而"按调用者角色决定返回哪套投影"更糟：
> ADMIN 也要建 Agent，那样 **ADMIN 的模型下拉里会出现停用模型**，直接违反 `01` §3.2
> 的「无效模型创建 Agent 时不可选」。详见下面「契约增量 · 模型」。

**契约增量 · Provider（P0-1-10 起）**

- `ModelProviderItem` = `{ id, name, baseUrl, type, protocol, enabled, hasKey, apiKeyPreview, modelCount, createdAt, updatedAt }`（定义在 `shared/src/modelProvider.ts`）；列表响应为 `{ items, total, offset, limit }`（默认 20 / 上限 100）。排序固定 `createdAt` 升序、以 `id` 兜底（Provider 数量极少，按录入顺序展示最直观；分页仍需稳定顺序）。
- **Key 有进无出**：`apiKey` 只出现在请求方向（`POST`/`PATCH` 的 body）。响应方向**永远没有** `apiKey` / `apiKeyEnc` 之类字段，只有 `hasKey`（布尔）与 `apiKeyPreview`（`sk-****abcd` 形态的掩码）。前端表单据此把"已配置"渲染成掩码 + "重新设置"，**不回填输入框**（`01` §3.2 验收要点「Key 不回显明文」）。
- **掩码口径**：明文长度 ≥ 16 时给 `前3 + **** + 后4`；8~15 只给 `****后4`；< 8 一律 `****`。掩码由后端**解密后**取首尾生成 —— 也就是说"能看到掩码"本身证明密文可解（主密钥没配错）。
- **存储形态**：`api_key_enc` 是 `v1.<iv>.<tag>.<ct>`（base64url，无填充）的 AES-256-GCM 密文，主密钥来自 `CREDENTIAL_MASTER_KEY`（§十）。密文**绑定到记录**：加密用 AAD `model-providers:{id}.api_key_enc`，因此密文被粘到另一条记录上就解不开。⚠️ 代价：**加密必须发生在拿到 `id` 之后**，故建 Provider 用事务（先落行拿 `id`，再写入密文），见 §10.2。
- **`apiKey` 的三态（PATCH）**：不带该字段 = **不动原 Key**；`null` = **清空**；字符串 = **写入新 Key**。**空串被拒（400）** —— 只留两条明确的路，避免"到底清没清"的歧义。这一条最容易被写成"每次 PATCH 都重新加密"，从而在"改个名字"时把 Key 悄悄抹掉（或把密文无谓改写）。
- **`baseUrl` 契约**：必须 `http://` 或 `https://` 开头且是合法 URL（拒绝其他 scheme：这个值最终会被后端拿去发请求，放宽 scheme 等于放大 SSRF 面），长度 ≤ 2048；**尾部斜杠会被归一化去掉**（否则将来拼 `/chat/completions` 会出现 `//`，有的网关当 404）。
- **`type` 的守卫**：`model_providers.type` 与 `models.type` 冗余，故 Provider 下**已有模型时不允许改 type** → `409`（同值 PATCH 放行）。替代方案（级联改所有模型的 type）会静默改变"已绑定 Agent 用的是哪类模型"，不采用。
- **`protocol` 与 `type` 是两件事**（P0-1-37）：`type` 是**用途**（CHAT / EMBEDDING），`protocol` 是**上游怎么说话**。取值 `OPENAI_COMPAT`（默认）/ `OPENAI_RESPONSES` / `ANTHROPIC_MESSAGES`，三者的请求路径、鉴权头与报文形状都不同（映射表见 §6.1）。约束：
  - **`type = EMBEDDING` 的 Provider 只接受 `OPENAI_COMPAT`** → `400`（字段级错误，`path` 指向 `protocol`）。embedding 只有一条 OpenAI 兼容的路，放行别的值只会造出"配了 Anthropic 协议的向量库"这种一建就失败的组合。
  - **改 `protocol` 刻意不加"有模型就 409"的守卫**（与改 `type` 刻意相反）：改 `type` 会让 `model_providers.type` 与 `models.type` 冗余冲突，而改 `protocol` **不动任何数据形状**、只换调用方式 —— 协议填错了本来就该能改。
  - **新列有默认值** ⇒ 既有行全部落在 `OPENAI_COMPAT` 上，改造前后的行为**逐字一致**（`verify:llm` 既有用例一条不改也必须全绿）。
- **删除语义**：`models.provider_id` 是 `ON DELETE CASCADE`，但 `agents.model_id` 是 `ON DELETE RESTRICT` —— 因此**当 Provider 下有模型被 Agent 引用时，删除会被前置检查拦成 `409`**（而不是撞外键抛 500）。Agent 软删（`agents.deleted_at`）仍占着外键，计数刻意不按 `deletedAt` 过滤，否则会出现"提示说能删、删下去却 500"。
- **状态码**：成功一律 `200`（不引入 201/204）；`401` 未登录 / `403` 非 ADMIN（或首登未改密被闸门拦）；`404` 目标不存在；`400` 参数校验失败（`data.fields`）；`409` 有模型时改 type、有模型被 Agent 引用时删除。
- **名称不做唯一约束**：`model_providers` 上没有 `name` 唯一索引（§三），同名的两个 Provider 靠 `id` 区分。服务层刻意不造一条"看起来唯一、并发下不唯一"的查重规则；需要唯一性时应先加约束再改代码。

**契约增量 · 模型（P0-1-11 起）**

- **两套投影，按路径分，不按角色分。** 这是本批最要紧的一条：
  - `ModelItem` = `{ id, providerId, providerName, providerEnabled, modelName, label, type, maxContext, supportsVision, enabled, agentCount, createdAt, updatedAt }`（`shared/src/model.ts`）——`GET /api/models`（**仅 ADMIN**），响应 `{ items, total, offset, limit }`。
  - `ModelOption` = `{ id, providerId, providerName, modelName, label, type, maxContext, supportsVision }` —— `GET /api/models/available`（**登录即可**），响应 `{ items }`（不分页）。
  - `ModelOption` **刻意不含** `enabled`（按定义只含"能选的"，再下发一个恒为 `true` 的字段只会诱使前端写 `if (option.enabled)` 这种永远为真的分支）、也不含 `agentCount` 与时间戳（管理口径）。
  - 为什么不按角色决定投影：`03` §4.2 的智能体编辑页用同一份列表渲染下拉，ADMIN 也要建 Agent。按角色分会**让 ADMIN 看到停用模型**，违反 `01` §3.2。路径分则与 `/api/users`、`/api/model-providers` 的摆法一致——资源根的 `(A)` CRUD 在根路径，视图型子集走子路径。
- **`available` 的 `type` 必填**（`CHAT`/`EMBEDDING`），不是可选。它的唯一用途是填"选模型"的下拉，而对话与向量不可互换：给个默认值等于允许"忘了传"的调用方把 CHAT 模型塞进向量库（不报错，只静默产生垃圾向量）。⚠️ zod v3 里 `required_error` 与自定义 `errorMap` **互斥**，同时给会在**模块加载期** `throw`（`typecheck` 查不出来）→ "必填"文案由 `errorMap` 分派 `invalid_type` 产出。
- **`available` 的三个过滤条件缺一不可**：`models.enabled = true`（门槛原文）、`provider.enabled = true`（"Provider 被停用"是同一个"用不了"的另一种形态，只筛前者会给出"能建 Agent、一发消息就失败"的模型）、`type = ?`。排序 `providerId asc, modelName asc, id asc`（`providerId` 是 uuid7 时间有序，等价于"按 Provider 录入顺序"，天然分组；同请求两次结果**逐字相同**）。
- **不分页**：模型池由管理员人工维护（量级"几十"）。刻意**不**加一个静默 `take` 上限——那会让"某几个模型从下拉里消失"变成没人能查的幽灵 bug。将来若出现批量导入把量级推到几百，应先补分页再放量。
- **管理列表的过滤**：`type?` / `providerId?` / `enabled?`（`?enabled=false` 是字符串，契约层 `transform` 成布尔）+ `offset`/`limit`（默认 20 / 上限 100）。排序 `createdAt asc, id asc`（与 Provider 同口径）；管理页要按 Provider 分组由前端做，不在这里按关联字段排序。
- **`maxContext` 三态（PATCH）**：不带 = **不动**；`null` = **清空**；数字 = 设置。与 Provider 的 `apiKey` 同款口径——合并成 `.default(null)` 的话"改个别名"会把上下文长度顺手抹掉。上限 1000 万（挡"把 token 数填成字节数"这类量级错）；建模型时缺省落 `NULL`。
- **`model_name` 拒内部空白**（trim 后 `/^\S+$/`）：上游 model id 从不含空格（`gpt-4o-mini` / `us.anthropic.claude-…` / `bge-m3` / `qwen2.5:7b`），从文档粘来的常见脏数据是尾随空格/换行（会被 trim 吃掉）；真夹了空格放行下去只会在第一次调上游时变成 404，排查成本高得多。`label`（别名）可中文。
- **刻意不校验「`type` 必须等于 Provider 的 `type`」**：`schema.prisma` 的 `@@unique([providerId, modelName, type])` 注释已明确"同一型号名可能既提供 chat 又提供 embedding（如 bge 系列的兼容端点）"是**合法**的。加一条"必须一致"会把那种配置挡在门外，属自己发明约束。
- **三条新守卫**（与 P0-1-10 两条同族：先查、说人话、别让 500 说话）：
  - **改 `providerId`** → `409`（同值放行）。它**在契约里**（不是被 zod 静静剥掉）——正是为了把"想迁移"这种无效意图变成显式报错，而不是返回 200 让人以为改成功了。理由：迁移会静默改变"已绑定 Agent 走的是哪个上游"；真要迁移应新建一条再改绑 Agent，每一步都可见。
  - **改 `type` 时该模型被 Agent 引用** → `409`（同值放行）。CHAT/EMBEDDING 不可互换，改了等于让已上线的智能体静默换一类模型（下一次发消息才暴露）。
  - **唯一冲突**：建/改撞上 `(providerId, modelName, type)` → `409`（先查给文案 + `catch P2002` 兜并发窗口），且**失败不得有副作用**（库里原值逐字不变）。
- **删除语义**：`agents.model_id` 是 `ON DELETE RESTRICT` → 有 Agent 引用时 `DELETE /api/models/:id` 前置检查后 `409` 并给出引用数。⚠️ `ModelItem.agentCount` 与这条守卫**同口径**：**含软删的 Agent**（`agents.deleted_at` 非空照样占外键），按 `deletedAt` 过滤会出现"界面说能删、删下去 500"。
- **状态码**：成功一律 `200`；`401` 未登录 / `403` 非 ADMIN（或首登未改密被闸门拦）；`404` 模型或 Provider 不存在；`400` 参数校验失败（`data.fields`）；`409` 三条守卫。

**契约增量 · 拉取上游模型列表（P0-1-12 起）**

- `GET /api/model-providers/:id/remote-models`（**仅 ADMIN**）→ `RemoteModelListResult` = `{ providerId, providerName, baseUrl, total, truncated, items: [{ id, ownedBy, created }] }`（`shared/src/modelProvider.ts`）。
- **为什么要有它**：模型池里的 `modelName` 本来全靠管理员手敲，敲错一个字符要等到第一次发消息才以 404 暴露。这是"OpenAI 兼容实现基本都提供"的**通用**端点（用户 2026-09-21 提出），把上游真实型号列给管理页，由管理员自己挑（自动化增删不做：上游清单里常混着一堆不能用的 —— embedding、图像、老版本）。
- **只读探测、不落库**：它不改任何数据。验收里有一条断言守着这件事（调完之后该 Provider 下的模型条数一条没变）。
- **两种"不"是刻意的**（与 `resolveChatTarget` 的口径相反）：
  - **不要求 Provider `enabled`**：这正是"换 Key 后先探一次再启用"的诊断动作；
  - **不要求配 Key**：`GET /models` 在许多自建/内网实现上免鉴权（本地 vLLM / llama.cpp / ollama 兼容层）。没配就不带 `Authorization` 头去探，能不能成由上游决定 —— 这样"用不了"与"该实现不支持列表"能被区分开。
- **三种返回形态都归一**（缺口在实现层就不让它露头）：标准 `{object:'list',data:[…]}`、`{models:[{name|model}]}`（llama.cpp 系）、裸数组 `[…]`；条目字段 `id|name|model` 取第一个非空，`owned_by|created_at` 兼容命名，**去重**（同一型号被不同 owner 列两次）后按 `id` 升序（顺序不稳定时前端列表会自己抖）。
- **不做静默截断**：`items` 上限 500 条，超出时 `truncated: true` 且 `total` 仍是上游真实条数。
- **`404` 的文案要可执行**：不是所有 OpenAI 兼容实现都有 `/models`，命中 404 时直接说"该实现可能不提供模型列表，请手工录入模型名"，而不是甩一个"上游返回 404"。
- **错误映射**：上游非 2xx → `UPSTREAM_ERROR`(502) + `data.upstreamStatus`；超时 → `UPSTREAM_TIMEOUT`(504)；Provider 不存在 → `404`；密文解不开 → `500`（**不**降级成"没配 Key"——那会让人误判成"换个 Provider 就行"）。⚠️ 上游 401 的响应体常回显 `Authorization`，**任何进错误消息/日志的响应片段都必须先脱敏**（见 §6.1）。
- **密钥零下发照旧**：这条响应里没有 `apiKey` / `apiKeyEnc` / `hasKey`，也没有 `Bearer` 形态的串（`verify:app` 有一条键级断言守着）。

### 4.4 Agent

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/agents | 列表（全员，含是否可编辑标记） |
| POST | /api/agents | 创建 |
| GET | /api/agents/:id | 详情（含组件绑定） |
| PATCH | /api/agents/:id | 编辑（创建者或 ADMIN） |
| DELETE | /api/agents/:id | 删除（**软删**：会话转只读保留、组件绑定解除） |
| POST | /api/agents/:id/copy | 复制（P1） |
| PUT | /api/agents/:id/components | 整体替换组件绑定（全量提交，避免增量 diff） |

**契约增量 · Agent（P0-1-22 起；组件绑定写侧 P0-1-23 起）**

上表七条路由中**已落地六条**（列表 / 创建 / 详情 / 编辑 / 删除 / **组件整体替换**），
`POST …/copy` 属 **P1**（验收里有一条"它必须 404"守着，防"顺手实现"）。
权限一列：前五条由 P0-1-22 落地，`PUT …/components` 由 P0-1-23 落地，**用的是同一套行级判定**。

**① 权限：全员可建可看可用；创建者 + ADMIN 可编删**（`01` §3.3 决策 18）。

| 资源 | 建 | 看 | 编 / 删 | 落点 |
|------|----|----|---------|------|
| `/api/models`、`/api/model-providers` | ADMIN | ADMIN | ADMIN | `(A)` 端点 |
| `/api/knowledge-bases` | 登录 | 登录 | 登录（**无 owner 列**） | 全员共享资源 |
| **`/api/agents`** | 登录 | 登录 | **创建者 + ADMIN** | `agents.created_by` 列 |

判据是 `02` §三 里**有没有 owner 列**。⚠️ 行级收窄**不通过路由的 `requireAdmin` 实现** ——
那样会把"创建者本人也改不了自己的东西"变成事实。五条路由的 `preHandler` **一律只用 `requireAuth`**，
判定落在 `shared` 的 `canEditAgent`（**唯一实现**，服务端与验收脚本共用）：
`deletedAt === null && (role === 'ADMIN' || createdBy === viewer.id)`。
两条反向守卫必须成对存在：**MEMBER 改他人 → 403** 与 **ADMIN 改他人 → 200**
（只验前者的话，一个"仅创建者"的实现会全绿）。

**② 唯一一套 `AgentItem` 投影**：列表 / 详情 / 创建 / 编辑的响应用**同一个 schema**（键集合有断言）。
与知识库"一套投影"同款理由：同一份数据在多个出口出现不同形状，是前端最容易踩的坑。
两个非表列字段及其理由：

- **`canEdit`** —— 列表对全员可见，前端据此决定"编辑/删除"按钮是否可点；
  服务端**不依赖它**做鉴权（每次请求重新判）⇒ 不把"能不能"与"允不允许"混成一个字段。
- **`modelAvailable`**（`models.enabled && model_providers.enabled`）—— 绑定的模型**现在**还能不能用。
  与知识库的 `embeddingModelChanged` 同族：没有它，管理员停用一个模型后，所有绑了它的智能体在界面上
  都"看着正常"，直到用户发消息才炸。

组件绑定**只给 `{componentType, refId}`、刻意不带目标名**（`mcp_servers` 表要到 P0-2 才建，
给不出 MCP 侧的 name；"只有知识库有名字"的不对称投影比"都没有名字"更难用）。名字由前端从各自的
列表端点映射 —— 建/改页面本来就要拉那些列表来渲染多选框。`config` 列**不进契约**（`§三` 标为
"P0 不写"，下发一个恒为 `null` 的字段只会诱使前端写永远走不到的分支）。

**③ 删除是软删，且是"三件事一个事务"**：`deleted_at = now()` + 删 `agent_components` +
该 Agent 的 `conversations` 全部 `status → FINISHED`（只读保留，消息与产物都不删）。

⚠️ **只打标记的实现会让被绑的知识库永远删不掉**（`kb.service.ts` 的删库守卫数的是
`agent_components`），而界面上那个智能体已经"没了" —— 这是最隐蔽的一种坏法。
取证方式是一条链：「绑 KB → 删 KB 得 409 → 软删 Agent → **同一个 KB 立刻删得掉（200）**」。

顺序：**先 CAS 打软删标记，再解绑、再转只读** —— 并发双击时第二条拿到 `count === 0` 直接 404，
此时还没改任何别的东西，抛错回滚等于什么都没发生。
响应带 `{id, name, removedComponents, finishedConversations}`：后两个数**数的是真的被改的行**
（`ACTIVE` 的那些），供 `03` §七 的级联确认框显示"将同时影响 N 个会话"。

软删之后**对谁都不再可编辑**（`canEditAgent` 返回 false），详情 / 编辑 / 再删一律 **404**（不是 403）
—— 留一个"看起来还能改"的页面等于诱导用户去改一条作废记录。历史会话显示智能体名要靠
**join 出来的快照**（不走本投影、不受软删过滤）。

⚠️ 软删的 Agent **仍占** `agents.model_id` 的引用（`ON DELETE RESTRICT`）⇒
`ModelItem.agentCount` 与模型删除守卫**刻意不按 `deletedAt` 过滤**（有跨批次一致性断言守着）。

**④ 绑定模型校验三条**（与 `GET /api/models/available?type=CHAT` **逐条对应**）：
存在 + `type=CHAT` + 模型与所属 Provider **都启用**。四种失败各有**可执行**的文案：

| 情况 | 状态码 | 文案指向的动作 |
|------|--------|----------------|
| 模型不存在 | 404 | 前端拿着旧下拉数据（多半模型被删了） |
| 是 `EMBEDDING` 模型 | 409 | 说清两者不可互换，请选对话模型 |
| 模型停用 | 409 | 去**模型池**启用这个模型 |
| Provider 停用 | 409 | 去启用那个 **Provider** |

⚠️ **刻意不复用 `model.service.ts` 的 `resolveChatTarget()`**：那是"**调用上游**"的前置
（要求 Provider 已配 Key，否则 424 `NEED_CREDENTIAL`），而"绑定"是**配置动作** —— 绑一个还没配 Key
的模型完全合法（Key 可以稍后补）。拿 424 拦住等于逼管理员先配 Key 才能建智能体。

**⑤ 换绑校验只在 `modelId` 真的变了时做**（同值放行 = 幂等）。若"传了就校验"，则当绑定的模型事后被停用时，
用户连**改个名字**都保存不了（每次提交都撞 409），而唯一走得通的出路（换模型）恰是他没想做的事 ——
症状是"这个智能体改不动了"。此时靠 `modelAvailable: false` 让界面给出提示。

**⑥ 请求体口径**：

- 四个文本字段（`description` / `icon` / `systemPrompt` / `openingRemarks`）**三态**：
  **不带 = 不动 / `null` = 清空 / 值 = 设置**，`.nullable().optional()` 且**绝不加 `.default()`**
  （P0-1-10 / P0-1-11 的同款坑）。
- `guideQuestions`：`undefined` = 不动、`[]` = 清空（"清空"**天然可表达**，故不叠 `null` 分支
  —— 两种"清空"写法并存的话前端迟早只处理其中一个）。条数上限 10、单条 200 字符，**只做防误操作**。
- `name` 最长 128；`systemPrompt` 最长 10000、`openingRemarks` 最长 2000。
  ⚠️ `systemPrompt` / `openingRemarks` **刻意不 `trim()`**（与 name/description 相反）：
  它们是多行自由文本，"先空一行再写角色设定"是常见写法，`trim()` 会把它悄悄改掉而用户看不见。
- `icon` 本批是**一个字符串**（emoji 或图片 URL，`VARCHAR(255)`），不是文件引用 ——
  P0-1 没有文件上传端点；将来真做上传时存进去的变成 URL，**契约不用改**。
- `type` **可传但不可改**（不同值 → 409，同值 → 200）。放进 schema 正是为了
  **把静默 no-op 变成显式报错**（不在 schema 里的话 zod 会把多余键剥掉，调用方以为改成功了）。
- `modelId` 必填（创建时）且是 UUID；`PATCH` 的 body **至少要有一个字段**，否则 400。
- 创建一律 **200**（信封 `code=0` 是唯一契约，**不引入 201**，与其余建接口同口径）。

**⑦ 读取端唯一兜底点 `normalizeGuideQuestions(raw) → string[]`（永不抛错）**：
`guide_questions` 是 jsonb，DB 默认值 `[]` 只在"INSERT 时不带该列"才生效 —— 手工插的行、
直接改库的行、将来导入的行都拿不到它；而前端的行为是 `.map()` 渲染引导气泡，
拿到数字或 `null` 就是**白屏**且报错指不到那条脏数据。**只做类型收敛、不做截断**
（读时悄悄丢条目 = 界面少了几条而用户永远不知道）；条数上限只在**写入口**拦。

**⑧ 列表排序是 `updatedAt desc, id desc`**（`agents` 的
`@@index([deletedAt, updatedAt(sort: Desc)])` 即为此建）。与其余四个列表的口径对照：

| 列表 | 排序 | 理由（**触发源**决定） |
|------|------|------------------------|
| `/api/users`、`/api/models`、`/api/knowledge-bases` | `createdAt asc` | 稳定分页，都是"长期不变的台账" |
| `/api/knowledge-bases/:id/documents` | `createdAt desc` | 文档"边用边传"，刚传的要在第一条 |
| **`/api/agents`** | **`updatedAt desc`** | `updated_at` **只被用户自己的编辑改** ⇒ 刚编辑完的排最前是期望行为 |

⚠️ 文档列表**不能**照抄这一条：它的 `updated_at` 会被**后台流水线**改（用户没动手）。
组件整体替换（`PUT …/components`）只写 `agent_components`、**不动** `agents.updated_at`
（P0-1-23 已落地，验收里有两条断言守着：库里 `updated_at` 逐字不变 + 列表相对顺序不变），
所以"解绑即生效"不会顺手把某个智能体弹到列表顶部。

**⑨ 组件绑定的写侧（P0-1-23 定案）**：`PUT /api/agents/:id/components`，**整体替换**。

请求体只有 `components`，**必填**（清空显式传 `[]`）。省略若被当作"清空"，前端某次忘带字段
就会**静默解绑全部**而界面显示"保存成功"。元素是 `{componentType, refId}`，`refId` 必须是 UUID
（列是 `@db.Uuid`，放非 uuid 过去只会变成一个 DB 500）；**payload 内的重复项直接 400**，且 `path`
精确到 `['components', N, 'refId']`（`superRefine` + `addIssue({path})`，前端能高亮到那一行
—— `.refine()` 只能给空 path，见 ⑥ 的同款坑）。**刻意不设条数上限**：可绑的库数量本身没有业务上限。

| 情况 | 状态码 | 语义 |
|------|--------|------|
| 智能体不存在 / 已软删 | 404 | 与详情同口径 |
| 不是创建者也不是 ADMIN | 403 | 行级判定（`canEditAgent`），**不是** `requireAdmin` |
| 引用的知识库不存在 | 404 | 文案带上是哪个 id |
| 含 `MCP` 引用 | 400 | **P0-1 阶段明确拒绝**，文案指向 P0-2 |
| `components` 缺失 / 非数组 / 重复项 / 坏 uuid | 400 | 字段级 `data.fields[{path, message}]` |

四条实现口径（**每一条都有验收断言**，细节见 `issue_fix/问题记录-P0-1-23-组件绑定.md`）：

1. **「校验」必须排在「删除」之前** —— 这是本端点唯一的"顺序即正确性"。
   先清空再校验的实现在"引用了不存在的库"这条路上会**删光旧绑定再报错**：请求失败、
   用户没有任何理由认为它改动了什么，而绑定已经没了。取证看**旧行的 `id` 是否逐字不变**
   （`id` 是 uuid7、插入时生成 ⇒ 重写一遍也会换 id）。
2. **集合相同就不写库**（幂等、零副作用）：保存按钮每次都发 `PATCH` + `PUT`（`03` §4.2 第 5 条），
   每次删了重建会无谓刷新 `id` / `created_at`。判等是**集合语义**（换顺序提交不算改动）。
   `createMany({skipDuplicates: true})` 只兜**并发**下的唯一索引冲突（双击不该变成 500）。
3. **整体替换的语义包含"清掉不在提交集合里的行"**：`ref_id` 是多态外键（没有 FK），
   直接 `INSERT` 是合法的 ⇒ 手工塞进去的脏行会在用户下次保存时被清掉。
4. **不动 `agents.updated_at`**（理由见 ⑧），也**不动 `documents` / `chunks`**：
   绑定只是"下次对话时多检索几个库"，不是一个需要重建的动作。

⚠️ **`MCP` 为什么在 P0-1 被拒**：`mcp_servers` 表属 **P0-2**，当前没有 server 列表端点
⇒ 用户**不可能选出一个真实 server**，收到的 MCP 引用必然是伪造/过期 uuid，写进去就是
"永远修不好的孤儿绑定"（`kb.service.ts` 文件头 ④ 定性的最难查的一类）。放行换不来任何可用能力。
**P0-2 接回方式**：同一处 `assertComponentRefsBindable` 从"无条件拒绝"改成"存在性校验"，接口形态不变。
前端（P0-1-35）的 MCP 多选框在此之前**没有数据源**，要以空态渲染。

上表九条路由中**已落地八条**：Agent 会话列表 / 新建 / 重命名 / 删除 / `/active` /

仍缺一条：`POST /:id/confirm` 属 **P0-2**（它的前置是 `mcp_servers` 表 —— P0-1-25 时这里写的是"属 P0-1-26"，
P0-1-26 落地时**改正**并同步翻转了 `verify-app.mjs` 里守着它 404 的断言）。

⚠️ P0-1-25 那句"本批没有写消息的端点 ⇒ `/active` 恒为无流（`streaming:false`）是预期行为"**到此作废**：

**① 权限：四族刻意各不相同（本批之后）** —— 判据仍是 §三 有没有 owner 列：

|------|---------|------|---------|

⇒ 给 ADMIN 开一个口子是**自己发明权限**，而且方向是隐私升级。

**② 端点的请求/响应增量**

| 端点 | 契约 |
|------|------|
| `GET /api/agents/:id/conversations` | offset/limit 分页（与其余列表同形）。排序见 ③。**刻意不过滤 `agents.deleted_at`**（软删 Agent 的会话是"只读**保留**"，历史要看得见），但"Agent 不存在"仍 **404**（回 `{items:[]}` 会让前端分不清"智能体没了"与"我还没聊过"——与文档列表同款）。 |
| `POST /api/conversations` | 请求体**只有** `{agentId}`；`userId` 取会话里的用户、**不接受请求体传入**（同 `createAgent` 的 `createdBy`）。成功一律 **200**（不引入 201，与其余建接口同口径）。校验**只有一条**：Agent 存在**且未软删**。⚠️ **刻意不校验**绑定模型可用性 / Provider 是否配 Key（那是"发消息"的前置，属 P0-1-26/27 的 424/409）—— 顺手加校验会让"模型停用后连自己的历史都进不去"。返回的 `topic` 与 `lastMessageAt` **都是 `null`**（本批没有自动命名；`03` §4.1 的首条消息创建流程属 P0-1-26/27）。 |
| `PATCH /api/conversations/:id` | 请求体**只有** `{topic}`，**非空字符串**（trim、≤255）—— **不是三态**：`null` 被拒（界面没有"清空标题"这个交互）。**不按 `status` 拦**（见 ⑦）。 |
| `DELETE /api/conversations/:id` | 响应 `{id, agentId, topic, deletedMessages}`。`messages` 由外键 **CASCADE** 连带清除；`deletedMessages` 是**同一个事务里"先数后删"**得出的（`03` §七 的确认框要"明示影响范围：将同时删除 N 条消息"；跨语句数会出现"数了 5 条、实际删了 6 条"的 TOCTOU）。删除后**清 `chat.active:{id}`**（失败只告警 —— 不删会积一批指向已删会话的键，而 `/active` 对已删会话是 404 ⇒ 没人能发现它们是垃圾）。 |
| `GET /api/conversations/:id/active` | 响应 = 快照三字段 + `streaming`；见 ⑤。 |

**③ 排序：`lastMessageAt desc` 且**新会话（`null`）排最前**** —— `nulls:'first'` **必须显式写**：
`conversations.last_message_at` 可空，**新建时就是 `null`**。PG 的 `DESC` 默认就是 `NULLS FIRST`，
但靠默认值等于把顺序语义寄存在数据库的实现细节上；这条错了的症状是"新建了会话却在侧栏看不见它"
（用户的第一反应是"新建没成功"）。`null` 之间再按 `createdAt desc`、`id desc` 兜底（确定性是分页的刚需）。
⚠️ 与 §4.4 的 `updatedAt desc`、§4.6 的 `createdAt desc` 都不同，理由在**触发源**：
会话的排序键是"**有没有人在说话**"，而不是"这行被改过没有"。

**④ `last_message_at` 的维护点：消息**落库**时，不是发起请求时**（`06` 的坑预判，本批结构性落地）：

- 唯一写入口是 `services/conversation.service.ts#touchConversation(db, conversationId, at)` ——
  P0-1-27 在"整条消息落库"那个事务里调它。签名收 `Pick<PrismaClientInstance,'conversation'>` 而**不是自己开事务**，
  **正是为了能被 `$transaction(async (tx) => …)` 直接传入**（否则"消息落库"与"活跃时间"会变成两次写入）。
- **"只前进不后退"用 CAS 表达**（`OR: [{ lastMessageAt: null }, { lastMessageAt: { lt: at } }]`），**不是"先读再比"**：
  后者在两处并发落库时会同时通过判断、**后到的旧值把新值盖回去**（时间倒流，会话在侧栏里"掉下去"）；
  单语句形式还天然幂等（重投同一个 job 不会把时间戳改坏）。
- ⚠️ 刻意**不顺手把 `status` 改回 `ACTIVE`**：`FINISHED` 是"Agent 被软删"留下的只读标记，
  "能不能再发消息"由 P0-1-26 的闸门判 —— 复活状态会让"只读保留"悄悄失效。
- **本批没有 HTTP 出口能验它**（没有写消息的端点），故它被做成一个可以单独调用的函数，由验收脚本直接调。

**⑤ `chat.active:{id}` 与 `/active` 读侧**：

- 键名由 `infra/redis.ts#chatActiveKey` 统一（`chat.active:${conversationId}`）。
  **写侧在 P0-1-26 已落地**（`orchestrator/sse.ts`；P0-1-25 时本节只写读侧、写侧列为后续批次 —— 原文保留以追溯）。
- **`streaming` 是派生的、不单独存**：**键在 ⇒ `streaming: true`** ⇒ "键在但 `streaming:false`"这种矛盾态**在形态上不可能出现**。
- 值坏（JSON 解析失败 / 字段类型不对）⇒ 走 `shared` 的 `parseActiveSnapshot` **逐字段降级**为全 `null` + warn，
  **永不 500**（断线重连路径上不能因为一个脏值把用户卡住）。
- **先查库、再查 Redis**：不是我的会话 / 不存在的会话一律 **404**，**不是**回 `{streaming:false}` ——
  后者会让前端把"会话被删了"当成"当前没在生成"，用户会盯着一个**永远不会有回复**的页面。
- 刻意**不为 Redis 故障做特殊兜底**：`requireAuth` 已保证这一刻 Redis 是通的（§十：Redis 故障 → 500 不放行），
  在这里再包一层只会掩盖真实故障。

**⑥ ⚠️「删除时异步清理 S3」在 P0-1 阶段是空操作（第三处临时边界，必须标出，不混进 ✅）**：
本阶段**确实没有**属于会话的对象 —— 产物在 `artifacts` 表（P0-3 的 TaskAgent 才用）、附件在 `files` 表（P1），
两张表都还不存在。故 `collectConversationObjectKeys` 返回 `[]`，`removeConversationObjects` 拿到空数组时
**连桶都不探**（与 `kb.service.ts`"没有文档就不碰 S3"同款 ⇒ 验收脚本因此**不需要 MinIO**）。
**接回点**：P0-3 只需在"收集"那一处加一句查询，删除路径本身不用改。

**⑦「只读」（`isConversationReadOnly`）的消费方是 P0-1-26/34**：
`FINISHED` 只表示"不能再产生消息"；**改名与删除刻意不按 `status` 拦** —— 用户需要能清理自己的历史，
"改个标题"跟"产生消息"是两回事；顺手加一条 `status === 'ACTIVE'` 才放行，
就把"删除一个已结束的会话"变成做不到的事（P0-1-11 的教训：自己发明约束会把合法操作挡在门外）。
**P0-1-26 落地了第一个消费方**：`POST /:id/chat` 对 `FINISHED` 会话回 **409**（走信封，见 ⑧），
这也是 P0-1-24 门槛④"写不进去"那一半的出口。

**⑧ SSE 出口的契约增量（P0-1-26 定案；`02` §五 的落地细则）**：

| 主题 | 定案 |
|------|------|
| 响应形态 | `200 text/event-stream`（`charset=utf-8`）；一帧 = `event:` + `data:` **两行** + 空行；**不写 `id:`**（不做重放，§5.2"事件即真相"）。 |
| 响应头禁缓冲 | 四行各有其用：`content-type: text/event-stream; charset=utf-8`（中文增量必须有明确编码）/ `cache-control: no-cache, no-transform`（挡中间层**合并小帧成大帧**）/ `x-accel-buffering: no`（nginx 系的应用侧开关，与 §十二 的 `proxy_buffering off` 双写）/ `connection: keep-alive`。⚠️ 还必须**显式 `flushHeaders()`** —— 否则客户端的 `fetch` 要等到第一帧（默认 20s 后的心跳）才 resolve。 |
| 心跳 | **无条件周期**（`SSE_PING_INTERVAL_SEC`，默认 20s），**不是"空闲期才发"**。理由：空闲态会随编排层演化而增加，而"空闲才发"要求每个等待点都记得重置计时器 ⇒ 把正确性寄托在"没漏掉"上。代价只是活跃时多几个几十字节的帧（前端对 `ping` 静默忽略）。副作用是好的：**这个周期同时是活跃锁的续期节拍**。 |
| 互斥锁 | `chat.active:{id}` 的写侧。**`SET … NX EX` 一步原子**（"先 EXISTS 再 SET"在并发下都会通过）；**TTL = 3 × 心跳周期且 ≥ 30s**（它是"进程被杀后这个会话多久能重新发消息"的**唯一上限**，正常路径靠 `finally` 主动释放）；**加锁无条件、释放按归属**（值里的 `startedAt` 是本次流的身份，直接 `DEL` 会把已属于下一个流的锁删掉 ⇒ 真的并发写同一份历史）。续期时 `EXPIRE` 返回 0 = 锁已丢 ⇒ **中断本流并以 `error` 收口**（不继续写 = 不和别人抢历史）。 |
| 停止键 | `chat.stop:{id}`，**TTL 60s**（`CHAT_STOP_TTL_SEC` 代码常量，不是 env）。`/stop` **只写键**（不做进程内注册表：多进程部署下注册表只有本进程看得见）；出口层用小周期轮询（心跳周期的 1/10，夹在 250ms–2s），发现即 `abort('user')`。键的存活期严格等于"有一个待消费的停止信号"：**新流启动时清 + 本条流收尾时清（在释放锁之前）**。 |
| 两类失败、两个出口 | **前置失败 → JSON 信封**：未登录 401 / 参数 400 / 会话不存在或不是我的 404 / 只读 409 / 缺凭据 424 / 绑定模型停用 409（主语是"**这个请求/目标**"）；**并发冲突 → 流内 `error{code:CONFLICT}`**（主语是"**这一轮生成**"，且 `03` §五 给它配了"消息流内错误卡" ⇒ 前端按单一渲染路径收口）。`/stop` 幂等：无流时 `200 {signaled:false}`。 |
| 空流（临时边界） | 本批的 producer 是**占位实现**：只发 `ping`、不落库、不自结束。它**不影响**本表的任何一条（通道 / 互斥 / 停止 / 心跳都已完整），编排循环属 **P0-1-27**，接回点是 `orchestrator/index.ts#resolveChatProducer()` **单点替换**。验收里有一条守门断言钉住"本批不该出现内容事件"。 |

**⑨ 消息落库形态与引用卡的契约增量（P0-1-27 定案；写入端本批落地，读取端 P0-1-28）**：

| 主题 | 定案 |
|------|------|
| `messages.content` 的形状 | `{ text: string; thinking?: string; citations?: CitationItem[] }`，收在 `shared/src/conversation.ts#messageContentSchema`。**`text` 必填**（可以是空串）—— 它是历史重建时**唯一**进入 LLM 上下文的部分（`chatContext.ts#selectHistoryMessages`），缺了键多轮对话就断了。`tool_calls` / `attachments` **本版本刻意不定型**（工具属 P0-2 / 附件属 P1，现在写进去只会是"猜的形状"）。⚠️ 该 schema **不是** `passthrough` 也**不是** `.strict()` ⇒ 未声明的键会被 **Zod 静默剥掉**（不报错），故"将来加字段必须同时回到 `shared` 加"（`verify:app` 有一条断言把这个坑本身钉住）。 |
| 空 `thinking` / 空 `citations` **不加键** | 省掉这个键表示"这一段本来就没有"，与"有但是空"在界面上是两件事（思考折叠区与引用区都是**有才出现**，`03` §五）。⚠️ 反过来 `text` **恒写**（哪怕是 `''`）：停止得很早的那一轮会留下"有 thinking 没 text"的助手行，历史重建时它被丢掉（一条空 `content` 的 assistant 消息会让严格的实现直接 400）。 |
| 助手消息**只在真有内容时才写** | `text` / `thinking` / `citations` 三者全空时不写助手行（否则界面上画出空气泡）。此时 `done.messageId` 为 **`null`**，语义正是"**这一轮没有产生可持久化的消息**"（§5.1 ④）。 |
| **引用卡 `items[]` 的形状只定义一次** | `shared/src/conversation.ts#citationItemSchema` = `{ docName, snippet, score }`，被**两个出口**共用：SSE 的 `citations` 事件与 `messages.content.citations`。两处各写一份的后果**没有编译期错误**、只有肉眼能发现：**流里看到的卡与刷新后恢复出来的卡长得不一样**（`03` §五 要求单一渲染路径）。`score` 取**融合分** `rrfScore`（§九"对外只给融合分"：`vectorScore` 与 `bigm_similarity` 量纲不可比）。 |
| 检索块的格式 | `知识库检索结果（每条的「来源」是文档名）：` + 每条 `N. 来源：{docName}` 换行 + **`snippet` 原样**。序号**从 1 连续**（跳号会让模型把两条认成同一条）；片段**不二次截断**（检索层已按 `SNIPPET_WINDOW_CHARS` 截过，编排层再截会让"卡片里显示的"与"模型看到的"不一样 —— 而卡片的意义就是让人核对模型看到了什么）。零命中时**写出明文**"（本次没有检索到与问题相关的知识库内容）"，**留白等于让模型自己决定有没有**。 |
| system prompt 的三段顺序 | 人格（`agents.system_prompt`；空白则回落 `DEFAULT_SYSTEM_PROMPT`——三态字段的"清空"是合法状态，不能变成"没有 system 消息"）→ **检索规则**（每一轮都注入，无论有没有命中）→ 检索块。顺序反过来会让"角色设定"被一大段资料冲淡；人格**逐字保留、不 `trim()`**（与 §4.4 的"`systemPrompt` 刻意不 trim"同口径）。 |
| 历史截断 | 取最近 **`rounds × 2`** 条（一轮 = 一问一答，`CONTEXT_ROUNDS=20`）；截断后**从 `user` 开始**（截点常落在助手回答中间，开头一条没有问题的回答会被模型当成"要继续写下去的上文"）；丢掉空文本助手行与 `SYSTEM` 行。⚠️ **不做 token 级裁剪**（见 §6.2 ⑧）。 |
| 多库命中的合并 | `rrfScore desc` + 同分按 `chunkId asc`（与 P0-1-20 检索层同款确定性口径；撞分很常见，没有 tie-break 会让引用卡在刷新前后换位置 ⇒ 用户以为"答案变了"）。**刻意不设条数上限**：每个库的 `topK` 是它自己的配置，在编排层再叠一个隐藏上限会造出"我配了 topK=10、进模型的却只有 5 条"这种**查不出来**的事（与 P0-1-23 同款判断）。 |
| 并发闸 | `CHATBOT_CONCURRENCY`（默认 50），**模块级单例**（每轮各造一个信号量等于没有闸门）。满 ⇒ 流内 `error{code:BUSY}`。粒度是"**一次生成**"而不是"一条流"—— SSE 通道本身（帧/心跳/锁）不占名额。 |

**⑩ 消息历史（P0-1-28 定案）**：`GET /api/conversations/:id/messages?beforeId=&limit=`，权限**仅创建者本人**
（`where:{id, userId}`，他人/不存在一律 **404**，连 ADMIN 也不给后门 —— 与 ① 同口径）。四条口径：

| 主题 | 定案 |
|------|------|
| 游标是**行 id**，不是时间戳 | `messages` 主键是 `(id, created_at)`，而**同一轮问答的两条消息在同一个事务里落库** ⇒ `created_at` 逐字相同。拿时间戳当游标会让并列的那条在翻页时**蒸发**（`01` §3.4「完整还原」直接破功）。条件写成 `(created_at, id)` 的字典序：`OR: [{createdAt:{lt: cursor.createdAt}}, {createdAt: cursor.createdAt, id:{lt: cursor.id}}]`。⚠️ 游标先按 `id + conversationId` 查出那一行，**查不到即 400**（`beforeId` 不属于本会话时**不能**当成"没有游标"—— 那会静默返回第一页，客户端陷入"永远在第一页"的死循环，而状态码全 200）。 |
| 分页取 `limit + 1` 条判 `hasMore` | `messages` 是**按月分区表**（14 个分区），`count` 要在每个分区上各跑一遍（本仓最贵的查询形态）。多取一条即可判"还有没有"，并且**天然**得到下一页游标 = **返回页的第一条**（`nextCursor`，SQL 是 `desc` 取，所以它就是"比这一页更早的最近一条"）。响应形状 `{ items, nextCursor, hasMore }`（`shared/src/envelope.ts#cursorPageOf`，本仓**唯一**游标分页；其余列表是 `offsetPageOf`）。 |
| `content` **原样透出**，读取端不解释 | `messageItemSchema.content` 是 `z.custom<unknown>((v) => v !== undefined)` ⇒ 存进去什么就吐什么，`tool_calls` / `attachments`（P0-2 / P1 才会写）**原样带出来**。⚠️ **不得**用 `messageContentSchema` 过滤：它是**写侧**的形状（只认 `text`/`thinking`/`citations`），过一遍会把未声明的键**静默剥掉** ⇒ 历史里 tool_calls 凭空消失而**没有任何报错**（`verify:conversations` 的 H 组有一条**反向对照**钉住这件事）。⚠️ 也不能写裸 `z.unknown()`：它**接受 `undefined`** ⇒ `JSON.stringify` 时**整个 `content` 键消失**（"消息没有正文"与"正文是 undefined"在线上无法区分）。 |
| 消息投影与排序 | `{ id, role, content, createdAt(ISO) }` —— **刻意不带** `tokensIn`/`tokensOut`/`conversationId`（token 计量属 **P1**，`02` §七 待决 4；会话 id 在路径里已有）。`role` 用 `MESSAGE_ROLES = ['USER','ASSISTANT','SYSTEM']`。排序常量 `MESSAGE_CHRONO_ORDER = [{createdAt:'desc'},{id:'desc'}]` 由 `conversation.service.ts` 导出，**历史分页与 §6.2 的上下文窗口共用同一份**（两处各写一份 `orderBy` 迟早分叉）。返回给客户端的 `items` 是**时间正序**（SQL 取 `desc` 后由 `toMessagePage` 反转）；`limit` 默认 **20**、上限 **100**（不设上限等于允许 `limit=100000` 拉爆分区表）。 |

**上传端点的请求形态与前置校验（P0-1-16 定案）**：

- `multipart/form-data`，**只接受一个文件字段 `file`**（字段名原表未定，本批定案：`UPLOAD_FILE_FIELD`）。缺文件 / 多文件 / 非 multipart 分别是 400 / 413 / 406，都有独立文案。响应 `{document, deduplicated}`：`deduplicated=true` 表示同库内 `content_hash` 已存在 ⇒ **不新建 documents 行**（覆盖重建的完整语义属 P0-1-19 的 `reupload`）。权限与知识库其余端点同口径：**登录即可，不是 ADMIN**。
- 上传**只做三件事**：前置校验 → 文件落 S3 → 建一条 `PARSING` 记录，**再加第四件：入队**（P0-1-17 起，`LPUSH pipeline:jobs`）。**这四件事是"同一件事"** —— 入队失败会把前面的登记整个回滚（删行 + 删对象），否则会留下一条"永远 `PARSING`、没有任何人消费、而重传又被判重命中跳过"的文档。**解析与入库是异步流水线**（P0-1-17 的 worker 消费队列），所以"传完立刻能检索"**不成立** —— 文档列表页必须对 `PARSING` 态显式提示「更新中，暂不参与检索」（`子方案①` §七）。
- 前置校验**四道**：① 扩展名白名单（`pdf/docx/md/txt`）② `.doc` 单独拦下并给可操作提示「请另存为 .docx 后重传」（混进"不支持的文件类型"等于什么都没说）③ 声明 MIME 与扩展名交叉校验（`application/octet-stream` 视为"未知"**放行**，否则 `curl -F` 这条最基本路径会被堵死）④ 大小 ≤ `UPLOAD_BODY_LIMIT`（由传输层给 413，不在业务层重复实现）。
- ⚠️ **本批在第三道之外补了「文件头魔数」比对**：MIME 是**客户端声明**，把 `a.txt` 改名成 `a.pdf` 后浏览器会老老实实声明 `application/pdf` —— 扩展名与 MIME 完全自洽，只靠交叉校验抓不到改名。真正能戳穿的是内容：PDF 须以 `%PDF-` 开头、docx 须是 ZIP 且包内含 `[Content_Types].xml`（否则"任意 zip 改名成 .docx"能过）、文本格式不得含 NUL 字节。代价是 4KB 的文件头副本（`HEAD_PROBE_BYTES`）。

**覆盖重建 / 重试 / 删除三条端点的契约增量（P0-1-19 定案）**：

| 端点 | 契约 |
|------|------|
| `POST .../documents/:docId/reupload` | `multipart/form-data`（与上传**同一个字段 `file`、同一段前置校验代码** —— 重建不能成为绕开校验的后门）。响应 `{document, unchanged}`：`unchanged=true` 表示**这一篇**的内容与库里一致 ⇒ **没落对象、没删 chunk、没入队**（提示文案走 `shared` 的 `REUPLOAD_UNCHANGED_HINT`）。字段名与上传的 `deduplicated` **刻意不同**：前者答"库里已有同样内容 ⇒ 没产生新文档"，后者答"这一篇没变 ⇒ 没跑流水线"，复用同一名字会让前端分不清"要不要刷新列表"。 |
| `POST .../documents/:docId/retry` | 无请求体，只重新入队。**`FAILED` 与 `PARSING` 都放行**（后者是"worker 崩了 / 入队丢了"的**恢复入口**，P0-1-17 就是照这个口径设计的）；`READY` 回 **409**（没有东西可重试，回 200 会让用户以为在重新处理）。响应 `{document}`，`status` 必为 `PARSING`、`errorMsg` 为 `null` —— **状态在端点里用 CAS 翻**（`updateMany where status='FAILED'`），交给 worker 翻会有一段"点了没反应"的空窗。 |
| `DELETE .../documents/:docId` | 清 DB 行（`chunks` 由外键 CASCADE）+ S3 原文件，响应 `{id, fileName, deletedChunks}`。**顺序是先 DB 后 S3**（与删库同款：S3 失败只告警，因为"文件还在、行没了"只是泄漏一点存储，反之会留下"行还在、文件没了"）。`deletedChunks` 是**删前数出来的**（删完就数不出来了），界面据此给提示。 |

> 三条端点**全部只需登录**（与知识库其余端点同口径，`03` §25）。**覆盖重建会换 S3 键并显式删掉旧对象**，否则对象会永久残留（行已指向新键，旧对象没人认领）。**`file_name` 一并更新**（对 `子方案①` §七 列清单的补全）：它还承担下载端点的 `Content-Disposition` 文件名，留着旧名就会出现"列表显示旧名、下载得到新内容"。

**检索端点的契约（P0-1-20 定案）**：

| 项 | 契约 |
|----|------|
| 请求 | `POST /api/knowledge-bases/:id/search`，body `{ query: string(1–1000，trim 后非空), topK?: 1–100, mode?: HYBRID\|VECTOR\|FULLTEXT }`。**只有这三项**：`mode`/`topK` 是"这次试查"的属性（可覆盖该库快照），而 `score`/`rrfK`/`weights` 是"这个库的检索口径"，**不可覆盖** —— 让一次点击就能改掉别人的召回率，比看不到更坏。 |
| 响应 | `{ items: RetrievalHit[], mode, topK, rrfK, candidatePool, elapsedMs, vectorPathSkipped, warnings }`，都是**生效值**的回显（`rrfScore` 的数值只有配上 `rrfK` 才可解释）。 |
| `items[]` | `{ chunkId, docId, docName, seq, page, headingPath, snippet, vectorScore, vectorRank, fulltextScore, fulltextRank, rrfScore, finalRank }` —— **六列分数/名次是"检索测试页"的要求**（`03` §4.3 的结果表要看到每一路各自的判断）；`§九` 的"对外只给融合分"指的是**引用卡**（F 包的 `citations` 事件），两者不冲突。 |
| `null` 的语义 | 某一路**没命中** ⇒ 该路的 `score`/`rank` 都是 `null`（**不是 0**）：RRF 的规则是"缺失即无贡献"，前端据此显示 `—`；显示 `0` 会让人以为"两路都算了，只是很低"。 |
| 参数来源 | `mode`/`topK`/`score`/`rrfK`/`weights` ← **该库的快照**（建库时来自环境默认值，此后按库独立可改）；`candidatePool = topK × CANDIDATE_POOL_FACTOR` ← 环境级（§十一 未把它定义为 KB 级参数）。 |
| 融合 | RRF（`子方案①` §6-2）：`w_v/(k+rank_v) + w_f/(k+rank_f)`，缺失一路记 0；排序 `rrfScore` 降序、**同分按 `chunkId` 升序**（uuid7 时间有序 ⇒ "先入库的优先"；确定性是刚需，否则同一 query 两次调用顺序不同会让分页与问题复现全部失去意义）。 |
| 全文路 | `content LIKE '%词%'` + `bigm_similarity`。query 预处理：剔标点（**含 `%` / `_` 这两个 LIKE 通配符**，否则"字面包含"会静默变成模式匹配）、**只剥句首/句尾**的提问脚手架、按码点截断 64 字符、有效字符 `< 2` 时整条路跳过并告警。⚠️ **只适合短查询**：它是子串匹配，自然语言长问句哪怕截断也几乎不可能连续出现在正文里（见 `06` P0-1-21 的坑预判）。 |
| 向量路 | `1 - (embedding <=> $1)`，候选池 `topK × CANDIDATE_POOL_FACTOR`，**相似度下限（`score`）只作用于这一路**（`bigm_similarity` 与 cosine 量纲不可比）。SQL **不加第二排序键**（`ORDER BY embedding <=> $1, id` 会让 HNSW 退化），tie-break 在 JS 侧做。 |
| 降级（`子方案①` §八） | 库快照的 `embedding_model` ≠ 当前 provider 的 `name()` ⇒ `HYBRID` **跳过向量路 + `warnings` 说明**（`vectorPathSkipped=true`）；`VECTOR` → **409**（没有可退的路，空结果会被读成"库里没有相关内容"）；`FULLTEXT` 不碰 embedding，不受影响。**"模型变更"（业务要重建）与"embedding 未就绪"（运维要修）两条原因分开报**。 |
| 权限 | **登录即可**（与知识库其余端点同口径）。 |

**列表 / 下载端点的契约（P0-1-21 定案）**：

| 端点 | 契约 |
|------|------|
| `GET /api/knowledge-bases/:id/documents` | 查询 `offset`/`limit`（默认 0/20，上限 100，与其余列表同口径）；响应 `{items, total, offset, limit}`，**每项与上传/重建响应里的 `document` 同一套投影**（`documentItemSchema` —— 同一份数据在多个出口出现不同形状是前端最容易踩的坑，验收有键集合断言）。排序 **`createdAt desc, id desc`**：⚠️ **刻意与其余三个列表相反** —— 文档是"边用边传"的，`asc` 会把刚上传的那篇压到最后一页、看起来像上传没成功；**不按 `updatedAt` 排序**（覆盖重建会改它，正在重建的文档会在翻页时"跳到最前面"）。**知识库不存在 → 404**（而不是空列表：`{items: []}` 会让前端分不清"库没了"与"库里没文档"）。 |
| `GET /api/knowledge-bases/:id/documents/:docId/download` | 成功时**返回字节流**（本仓唯一不套 JSON 信封的端点；失败**仍然**是标准信封 404/500 ⇒ 客户端要按状态码分支而不是永远 `json()`）。三个头部都由服务层给：`Content-Type` 按扩展名**唯一确定**（文本类型带 `charset=utf-8`）、`Content-Length` 取自 `statObject`、`Content-Disposition` 为 **RFC 6266/5987 双写**（`filename="<ASCII 回落>"` + `filename*=UTF-8''<百分号编码>`，中文名靠后者；CR/LF 一律剔除以防**响应头注入**，引号/反斜杠/路径分隔符替换）。⚠️ **先 `statObject` 再 `getObject`**：后者对不存在的键**不在 `await` 时抛错**（错误发生在读流时）⇒ 只调它的话响应头已经发出，客户端看到的是"下到一半断了"；先 `stat` 才能在发头前干净地回 404。**"行还在但对象没了" → 404 + 另一句文案**（"原始文件已不在存储中…请重新上传"）且**不动数据库**。 |

**两条界面规则也收在 `shared`**（`P0-1-21` 定案）：`DOCUMENT_PARSING_HINT`（"更新中，暂不参与检索"——
`§七` 的"先删后建"有一段检索空窗，不提示的话用户会以为"文档在、就是搜不到"是 bug）与
`isDocumentSearchable(status)`（`READY ⟺ 可检索`：`PARSING` 是我们还在干活、`FAILED` 才要人介入，
两者**不能混成一种"失败"样式**）。判据写成函数而不是让各处比较字面量：这条语义变过一次
（P0-1-17 时 `READY` 只是"解析完成"，P0-1-19 起才是"可检索"）。

> **P0-1-35 的契约零增量（前端落地回写）**：本批是**纯前端批次**，`02` 的契约**一个字节都没动** —— 无新增/改动端点、无新增环境变量、无新增数据列。本节因此只做一次**消费侧清点**（逐个核对了前端实际读的 `data` 形状，这是 P0-1-31 起的老坑：**错路径不报错、只给 `null`**）：
> - `GET /api/knowledge-bases` → `{items, total, …}`（**列表键** `['knowledge-bases']`）；`GET …/:id` → **裸 item**；`POST` 建库 → **裸 item**；`PATCH` → **裸 item**。
> - `POST …/:id/documents` → `{document, deduplicated}`（**字段名 `deduplicated`**）；`POST …/reupload` → `{document, unchanged}`（**`unchanged`，刻意与 `deduplicated` 不同名** —— 两者回答的是不同问题）；`POST …/retry` → `{document}`（`status` 必为 `PARSING`、`errorMsg` 为 `null`）；`DELETE …/documents/:docId` → `{id, fileName, deletedChunks}`。
> - `POST …/:id/search` → `{items, mode, topK, rrfK, candidatePool, elapsedMs, vectorPathSkipped, warnings}`（**都是生效值**）。
> - `GET …/documents/:docId/download` → **不是信封**（成功字节流、失败才是信封）⇒ 前端 `requestBlob` **按 `content-type` 是不是 `application/json` 分支**，而不是按状态码（这一步就是本批唯一需要"跨出 `unwrapEnvelope`"的地方）。
> - ⚠️ **`null` = 该路未命中，不是 0** 这条在界面上必须显形（显示 `—`）；**「命中库」这一列在界面上已不存在**（库是路径参数、恒等于当前库名）⇒ 检索结果表显示的是**「来源文档」**（有页码给页码、否则给块号）。

### 4.7 MCP 与凭据

| 方法 | 路径 | 说明 |
|------|------|------|
| GET/POST/PATCH/DELETE | /api/mcp/servers[…/:id] | 注册管理（全员） |
| POST | /api/mcp/servers/:id/test | 连通测试（含 tools/list 刷新缓存） |
| GET | /api/mcp/servers/:id/tools | 工具列表（不传 `refresh` = 纯读缓存、绝不联网；`?refresh=1` = 真拉并落库） |
| GET | /api/mcp/credentials | 我的凭据列表（含"哪些 server 未配置"） |
| PUT | /api/mcp/credentials/:serverId | 写入/更新我的凭据（值加密） |
| DELETE | /api/mcp/credentials/:serverId | 删除 |

> tool 缓存在 server 注册信息变更时自动失效；MCP tool `inputSchema` → OpenAI function 参数的转换规则见 §九。OAuth 2.1（授权码 + PKCE）为 **P1**：届时补充 `POST /api/mcp/servers/:id/authorize` 与 `GET /api/mcp/oauth/callback` 端点。

**契约增量 · 我的凭据（P0-2-4 定案）**

上表**七条现已全部落地**（凭据三条在 P0-2-4；它们的收窄不在角色上、在 `user_id` 上）。五条"落地时才定下来"的口径：

| # | 决定 | 理由（做错的症状） |
|---|------|------------------|
| ① | **`PUT` 是"合并"语义**：只动提交里出现的 key，**没提交的 key 逐字保留**；空串 = **清空该 key**；**清到一个不剩 ⇒ 整行删掉** | 与 P0-1 的 `components`（整体替换）**刻意相反**，分辨方式只有一句：**不可回填的字段只能合并**。值不下发（连掩码都没有）⇒ 前端无从回填 ⇒ 整体替换必然把用户没填的 key **静默清空**（他什么都没做，值却没了）。⚠️ 留一个 `values_enc:{}` 的空行会让"我有凭据"变成假话，故清空即删行 |
| ② | **`GET /api/mcp/credentials` 一次给两面、且刻意不分页**：`items`（每个 server × 我，含逐字段 `hasValue`）+ `unconfigured`（`configured:false` 的瘦投影：server 名 + 缺哪些 key） | `03` §4.5 是"按 server 分组的一张长表单"，而"未配置置顶提示"必须**跨全部 server** 成立 —— 一分页，用户翻到第 3 页时提示就凭空消失了。⚠️ 代价（响应随 server 数增长）写在契约注释里；同口径先例是 `/api/models/available`（同为"取全集"型端点） |
| ③ | **出参只有 `key` + `hasValue`**：没有值、**连掩码都没有** | 与 Provider Key 的 `apiKeyPreview` **刻意不同**：那是管理员配的一份、掩码用于"确认没配错"；这是每个人自己的令牌，下发掩码收益为零、风险是把它放进了一个更多人能读到的通道。**有进无出，连影子都不给** |
| ④ | **`DELETE` 本来就没配 ⇒ 404**（不是幂等 200）；**整个凭据路由里没有 403** | 它删的是"**我的那一份**"，"你没有可删的东西"比"删除成功"更准确（前端弹的是 Popconfirm，这正该是它说的话）。`PUT` 别人的 `serverId` **不是越权** —— 那台 server 上**我**的那份本来就可以写；路径里**没有凭据行 id**（行由 `(serverId, 我)` 推出）⇒ "能不能删别人的行"这个问题连入口都没有 |
| ⑤ | **`configured` 按当前模板逐 key 判**，与 `updatedAt`（有没有行）**是两个字段** | 合并语义 ⇒ 注册者后来给模板**新增** `required` 参数时，老用户的行还在、那个 key 却没有值；若用"表里有行 = 已配置"，界面显示 ✓、调用时才发现缺 key。反过来说：模板**没有必填项**时"从没写过"也是 `configured:true`（内网无鉴权 server 就属这类），把两者揉成一个字段会让"未配置置顶"在那些模板上永远点亮 |

**信封形态（凭据三条，逐个对齐用）**：`GET /` = **裸 `{items, unconfigured}`**（不分页、无 `total/offset/limit`）；`PUT /:serverId` = **裸 `McpCredentialItem`**；`DELETE /:serverId` = `{serverId, serverName}`（"删类多回 `{id,<name>}`"这一族的写法）。⚠️ 路径参数名是 **`:serverId`** 而不是 `:id` —— 凭据的主语是"我的这一份"，uuid 指向的是 server。

**契约增量 · MCP server 注册（P0-2-2 定案；P0-2-3 增补一条）**

⚠️ 上表四条 server 侧路由与三条凭据路由**现已全部落地**（凭据三条在 P0-2-4，见上一段）。这一段保留的是 server 侧的定案：五条"落地时才定下来"的口径 + 两条**已知边界**（SSRF 面、`auth_type` 接口留位）。

| # | 决定 | 理由（做错的症状） |
|---|------|------------------|
| ① | **权限 = 登录即可，且没有 owner 列收窄**（与 `/api/knowledge-bases` 同族；`created_by` 只作留痕） | 全员可注册是 `01` 决策 22 的直接推论。要做成"只有创建者能改/删"就得先改 `01`/`02`，**本批不自行发明权限模型**。验收里有两条反向守卫（另一个 MEMBER 能改、能删别人建的） |
| ② | `POST /api/mcp/servers` 回 **`{server, test}`**（不是 201、也不是"裸 item 多一个键"） | `01` §3.6 的「注册时连通测试」不能做成**注册前置**（坑预判 2），也不能让同一份数据有两种形状（前端两套渲染分支）。`test` 是一次 **best-effort** 探测结论，失败**只影响 `status`** |
| ③ | `POST /:id/test` **HTTP 恒 200**，结论在 `{ok:true,tools}` / `{ok:false,error}` 里（**两个分支互斥**，union 不是两个可选键） | "连不上"是一条**结论**，把上游抖动映射成 502 会让界面把一个可用信息渲染成错误（与 `/health` 恒 200 同源）。只有"server 不存在"才 404 —— 那是**请求本身**的问题 |
| ④ | 工具缓存失效判据 = **"真的变了"**：`endpoint_url` / `auth_type` / `credential_schema` 变了才清（`status` 回 `UNKNOWN`）；**只改 `name` 不清**；**原样提交不清**（键序无关比较） | 漏了前者 = "改了 endpoint，工具列表还是旧 server 的"（**纯静默**）；错判后者 = "每次保存工具数都归零"。⚠️ 这条缝隙是 **PG 的 jsonb 会重排键**撑开的，逐字比较必出假阳性 |
| ⑤ | 测试**失败时 `tool_cache` 一字不动**（只写 `status=ERROR`） | 上游抖一下就把上次成功拉到的工具列表清空，是"用户明明还能用却被我们清没了"的最坏形态 |

**信封形态（第五族，逐个对齐用）**：列表 `{items,total,offset,limit}`；`POST /` = `{server,test}`；`PATCH /:id` = **`{server,credentialSchemaImpact}`**（⚠️ **P0-2-2 时是裸 item，P0-2-3 改成复合响应** —— 见下面的增量段）；`DELETE /:id` = `{id,name}`；`POST /:id/test` = **恒 200** + `{ok,…}`；`GET /:id/tools` = **裸 `{tools,fetchedAt,cached}`**（`fetchedAt:null` = 从未成功拉过；`cached` 在本批恒等于 `fetchedAt !== null`，P0-2-5 加 `?refresh=1` 之后才会分叉）。`McpServerItem` 是**全端点唯一形状**，**不含 `oauthConfig`**（P1，恒 `null` 只会诱使前端写死分支）与**完整 `toolCache`**（列表页只要 `toolCount`）。

**⚠️ 已知边界（P0 不修）· `endpoint_url` 是一个 SSRF 面**：全员可注册 ⇒ **任何登录用户都能让后端去连任意地址**（打内网服务、探端口、读云元数据 `169.254.169.254`）。本阶段的处置**只有两条**：**校验 scheme（只接受 `http`/`https`）** + **把这条写在这里和 README**。真正的防护（出站 denylist / 代理 / 域名白名单）**属 P1**。⚠️ 这一条**必须留在文档里**，否则它就是一个没人知道的洞。

**⚠️ `auth_type` 是"接口留位、能力不做"**：列与取值域先建出来（P1 免得改表），但 **P0 只接受 `NONE`** —— 收到 `OAUTH` ⇒ **400 且文案指向 P1**（建与改两处都在写库之前拦）。理由与 P0-1-23 拒绝 `MCP` 绑定同源：存下一个 `OAUTH` 的 server 却发现没有授权端点，用户会以为它能用，真故障推迟到"调用时 401"才显形。

**契约增量 · 凭据参数模板（P0-2-3 定案）**

模板的形状与三条"按注入位置分判"的 `key` 约束见 **§9.4**（含协议线实测）；这里只记**接口口径**的三条：

| # | 决定 | 理由（做错的症状） |
|---|------|------------------|
| ① | `PATCH /api/mcp/servers/:id` 的响应从**裸 item** 改成 **`{server, credentialSchemaImpact}`** | 模板变更要带回一条"**本次请求特有**"的提示，而进 item 就破了"`McpServerItem` 是全端点唯一形状"（P0-2-2 决定 ② 的同一条理由）⇒ 只能走**复合响应**，与 `POST /` 的 `{server,test}` **同族**。⚠️ 这是本批唯一一次契约变更（消费方按 `data.server.*` / `data.credentialSchemaImpact` 取） |
| ② | `credentialSchemaImpact` **只提示、绝不自动清理**已存凭据；**`null` = 本次没有需要提示的影响**（含"没提交模板"与"提交了但等价"） | 自动删掉"已移除 key"的值会把"用户临时改错模板"变成**不可逆的数据丢失**，而他什么都没做。⚠️ `null` 与"三个数组都空"的形态**刻意合并成一个**（否则前端要为同一件事写两个分支） |
| ③ | `affectedCredentials` **在 P0-2-4 之前恒为 `null`**（**不填 `0`**） | `0` 会被读成"没有凭据受影响" —— 是一句关于**还不存在的功能**的断言，后端此刻根本没能力回答。**说不出来的数字宁可留白，也不要编一个**。⚠️ **接回点**：`verify:mcp-servers` 的 H1 有一条守着"它必须是 `null`"的断言，P0-2-4 建表后**翻转**并换成真数（数 `values` 里含 `removedKeys` 的行） |

⚠️ **与"缓存该不该清"是两个判据，别合并**：缓存按 `sameJson` 判"**模板整体**变没变"（**连 `label` 改了也清**），`credentialSchemaImpact` 按 `diffCredentialSchema` 判"**已存凭据会受什么影响**"（只有 key 级的增/删/换注入位置才算）。同一份输入得出**不同**结论是**对的**。

**契约增量 · 工具发现（P0-2-5 定案）**

`GET /api/mcp/servers/:id/tools` 的**请求**部分在后端历史上只有"读缓存"一种形态，本批起有了两种；响应形状**一个字没改**（`cached` 这个字段从 P0-2-2 就在契约里等这一天 —— 见下面 ②）。四条口径：

| # | 决定 | 理由（做错的症状） |
|---|------|------------------|
| ① | **`?refresh=1` 的三种出口**：拉到 ⇒ `cached:false`；拉不到但**有缓存** ⇒ **200** + `cached:true`；拉不到且**缓存也空** ⇒ **502** | 分界线是"**我们还能不能答出这个问题**"。第三种必须 502：那时唯一能给的成功形状是 `{tools:[]}`，而它与"这个 server 确实**没有**工具"**逐字一样** ⇒ 用户会去上游找一个**其实不存在**的配置问题。⚠️ 这与 `POST /:id/test` 恒 200 **不矛盾** —— 判据是"**响应形状里有没有『失败』的位置**"（`{ok,tools?,error?}` 有，`{tools,fetchedAt,cached}` 没有），不是"这个端点在哪"。**别把两条路由的出口『统一』起来**。详见 §9.6 ③ |
| ② | **不给响应加任何"这次刷新失败了"的字段** —— `cached:true` + 偏旧的 `fetchedAt` 就是全部信号 | 界面据此就能画"缓存于 X"；再加一个 `warning` 等于同一件事两个来源（迟早分叉）。**真正的失败原因进服务端日志**（`warn` 带 `error` 与旧 `fetchedAt`）—— 它对人有用、对界面无用 |
| ③ | **`refresh` 取值域收窄成白名单**（`1`/`0`/`true`/`false`，`true`/`false` 是给 `URLSearchParams` 用的），**拼错 ⇒ 400**（字段级 `path` = `querystring.refresh`） | ⚠️ **不能用 `z.coerce.boolean()`**：`Boolean('0') === true` ⇒ `?refresh=0` 判成"要刷新"，而**零症状**（用户以为关掉了，其实每次请求都联网打上游）。也不能放宽成"任意字符串"：`?refresh=yes` 静默等于不刷新（点了刷新看到旧列表）。**两种宽松写法都制造"看起来工作了"的假象** |
| ④ | **`tools/list` 不带任何用户凭据**，因此 `tool_cache` 是**每个 server 一份、全员共享**；需要鉴权的 server **如实报"本阶段不支持带用户凭据拉列表"** | 带上某个人的凭据会造出"**工具列表依赖谁先点过测试**"的诡异状态（A 点过测试后 B 才看得见工具）。⚠️ **文案要按 stage 分**：拉列表阶段的 401/403 不能说"请检查凭据"（那会把人引向一个**治不好的动作** —— 列表请求从来不带凭据）。详见 §9.6 ① |

**信封形态（本条路由，逐个对齐用）**：请求 `GET …/tools` 或 `GET …/tools?refresh=1`；响应**裸 `{tools, fetchedAt, cached}`**（**不变**）—— `fetchedAt:null` = 从未成功拉过；`cached` 的语义始终是"**这份列表来自 `tool_cache` 列**"（而不是本次实时拉取）。⚠️ 拉不到且无缓存时**没有成功信封**（502 走 §四 的统一错误信封）。

**`/health` 的语义（P0-1-4 定案）**：

- **HTTP 恒 200**，依赖状态放在响应体里：`data.status ∈ {ok, degraded}` + `data.checks[]`（每项含
  `target / ok / latencyMs / detail`）。理由：探活端点自身是「请求成功」——它确实给出了结论；把某个
  依赖抖动直接映射成 5xx 会让网关/负载均衡把**整个后端**摘掉（本机只停 Redis 时后端其实还能服务大部分接口）。
  若将来上 k8s 需要 status code 形式的 readiness，另加 `/health/ready`（返 503）更清楚，不把两种语义塞进同一端点。
- 每项探活**必须带超时**（`HEALTH_TIMEOUT_MS`，默认 2s），单项失败只降级、不整体报错：
  `detail` 要能直接告诉运维「为什么」（如 `connect ECONNREFUSED 127.0.0.1:16379`）。
- 推荐运维口径：`jq '.data.status'` 判整体；`jq '.data.checks[] | select(.ok==false)'` 定位到具体依赖。

## 五、SSE 协议（前后端唯一契约，双链路归一化）

`POST /api/conversations/:id/chat`，请求体 `{ content, attachmentFileIds?[] }`，响应 `text/event-stream`。

### 5.1 事件全集

| event | data | 说明 |
|-------|------|------|
| `delta` | `{ text }` | 助手回答文本增量 |
| `thinking` | `{ text }` | 思考过程增量（可折叠渲染） |
| `tool_call` | `{ callId, toolName, serverName, kind: MCP\|SANDBOX, status: RUNNING\|SUCCESS\|ERROR, inputSummary, output? }` | 工具调用卡片；同一 callId 多次推送 = 状态机流转 |
| `confirm` | `{ confirmId, toolName, inputSummary }` | elicitation：前端弹确认卡，用户答复走 `/confirm` 接口，流挂起等待 |
| `citations` | `{ items: [{ docName, snippet, score }] }` | 本轮知识库引用 |
| `artifact` | `{ artifactId, fileName, size, mime }` | TaskAgent 产出文件 |
| `queued` | `{ position }` | 沙箱并发满，排队中 |
| `ping` | `{ ts }` | 心跳（每 15–25s 一次，空闲期保活）；前端静默忽略；防止排队/确认挂起/长任务静默期被网关断连 |
| `done` | `{ messageId, finishReason: COMPLETE\|STOPPED\|ERROR, usage: { tokensIn, tokensOut } }` | 流结束 |
| `error` | `{ code, message }` | 错误（流终止） |

### 5.2 语义规则

- **事件即真相**：前端渲染只依赖事件流；持久化由后端在 `done` 时整条落库（含 tool_calls/citations/artifacts 结构），历史拉取直接读库，**不做 SSE 重放**
- **会话互斥**：Redis 锁 `chat.active:{conversationId}`；持锁期间同一会话再次发送返回 `error{code: CONFLICT}`（防双标签页并发写乱历史）
- **心跳**：空闲期（排队/confirm 挂起/引擎长静默）每 15–25s 推送 `ping`；部署前提：网关 `proxy_read_timeout ≥ 120s` 且关闭响应缓冲
- **停止**：`stop` 写 Redis key `chat.stop:{conversationId}`（TTL 60s），编排循环每个可中断点检查；中断后推送 `done{finishReason: STOPPED}`
- **confirm 挂起**：确认等待上限 120s，超时按取消处理
- **断线**：前端断线重连后先查 `/api/conversations/:id/active` 获取进度（在流/排队位次/当前工具），再调消息历史接口补齐（事件流不重放；历史不含进行中消息，进行中状态由 active 提供）
- **两条链路同构**：ChatBot 的 MCP 工具与 TaskAgent 的沙箱工具（bash/read/write 等）都映射为 `tool_call`（`kind` 区分）；引擎侧事件在编排层完成映射（详见子方案③）

> **P0-1-26 落地的细则**（锁的 TTL 与续期、按归属释放、停止键的三处清理、心跳为什么定成"**无条件周期**"、`CONFLICT` 为什么是流内事件而不是信封）集中在 **§4.5 ⑧**，本节只留协议语义。

### 6.1 LLM client 实现口径（`backend/src/llm/client.ts`，P0-1-12 起落地）

> 传输层只管"报文怎么发、差异怎么收敛、失败怎么归类"；**不碰数据库** ——
> Provider/模型 → 上游目标的解析（含解密 Key）在 `services/model.service.ts#resolveChatTarget()`。
> 这样这一层可以拿一个本地假上游独立验（`verify:llm`），不需要 PG/Redis。

| 项 | 口径 |
|----|------|
| 协议 | **按 Provider 的 `protocol` 分流**（P0-1-37）。默认 `OPENAI_COMPAT`：非流式 `POST {baseUrl}/chat/completions`（`stream:false`）；流式同一路径（`stream:true`），按 SSE 解析。三协议映射见下表 |
| 入口 | `chat()`（一次性，给工具循环/极小请求用）、`chatStream()`（增量回调，给 ChatBot）、`fetchRemoteModels()`（拉上游模型列表） |
| 认证 | `OPENAI_COMPAT` / `OPENAI_RESPONSES`：`Authorization: Bearer <解密后的明文 Key>`；`ANTHROPIC_MESSAGES`：`x-api-key` + `anthropic-version`（**不发 `Authorization`**）。**没配 Key 就不带鉴权头**（自建实现可能免鉴权），而不是带一个空 Bearer |
| 超时三级 | 到响应头 `LLM_REQUEST_TIMEOUT_MS`（流式收到头即撤 / 非流式覆盖全程）、流内空闲 `LLM_STREAM_IDLE_TIMEOUT_MS`（每收一块重置）、调用方 `abortSignal`（用户的"停止"）。前两者 → `UPSTREAM_TIMEOUT`(504)，第三个 → `LlmAbortError`（**不是故障**） |
| 结束原因 | 保留**上游原值**（`stop`/`length`/`tool_calls`/null）。归一化成 `COMPLETE\|STOPPED\|ERROR` 是 SSE 层（§5.1）的职责 —— 在这里归一化会丢掉 `length`（被 `max_tokens` 截断）这类的决策信息。⚠️ **P0-1-37 修订："原值"指协议内的原值，跨协议必须先归一到 OpenAI 词表**，见下 |
| usage | 有就收（`prompt_tokens`/`input_tokens` 两种命名都认）、没有就算了；**刻意不默认发 `stream_options.include_usage`**（见下） |

**三协议映射表**（P0-1-37；`backend/src/llm/protocol.ts` 是**唯一落点** —— 传输层只按它取路径/头/编解码）：

| 项 | `OPENAI_COMPAT`（默认） | `OPENAI_RESPONSES` | `ANTHROPIC_MESSAGES` |
|----|------|------|------|
| 对话路径 | `POST {baseUrl}/chat/completions` | `POST {baseUrl}/responses` | `POST {baseUrl}/messages` |
| 鉴权头 | `Authorization: Bearer` | `Authorization: Bearer` | `x-api-key` + `anthropic-version`（**不发 `Authorization`**） |
| 拉模型 | `GET {baseUrl}/models` | `GET {baseUrl}/models` | `GET {baseUrl}/models`（**同样要 `x-api-key`**） |
| 系统提示 | `messages[0].role = 'system'` | 顶层 `instructions` | 顶层 `system`（**`messages` 的 role 只认 user/assistant**） |
| 用户输入 | `messages[].content`（字符串） | `input`（消息数组） | `messages[].content`（字符串） |
| 输出上限 | `max_tokens`（可选） | `max_output_tokens` | `max_tokens`（**必填**；`maxTokens` 缺省时补常量 4096） |
| 流式开关 | `stream: true` | `stream: true` | `stream: true` |
| 非流式取文本 | `choices[0].message.content` | `output[].content[].text` | `content[]` 中 `type='text'` 的 `text` |
| 流式增量 | `choices[].delta.content` | `response.output_text.delta` 的 `delta` | `content_block_delta` 的 `delta.text` |
| 流结束信号 | `[DONE]` 哨兵或流自然结束 | `response.completed` 或流自然结束 | `message_stop` 或流自然结束 |
| 结束原因 | `choices[].finish_reason` | `response.completed.response.status` | `message_delta.delta.stop_reason` |
| usage | `prompt_tokens` / `completion_tokens` | `input_tokens` / `output_tokens` | `input_tokens` / `output_tokens`（`message_start` 与 `message_delta` 各给一半） |
| 错误帧 | `{error:{message}}`（200 里也可能藏） | `{error:{…}}` 或 `response.failed` | `event: error` + `error.message` |

⚠️ **三协议共用同一条"帧解析 → 增量回调 → 汇总"的外壳**：差别只在"这一帧取哪个字段"，所以落法是给外壳加一个**协议钩子**（`readStreamFrame`），而不是把 `chatStream` 抄三份 —— 抄三份等于把 P0-1-26 那批踩过的坑（背压 `waitDrain`、中断逐帧检查、末帧无空行）各养一套。

**三个文件的落点分工**（P0-1-37）：

| 文件 | 只负责 | **不许**出现 |
|------|--------|--------------|
| `llm/protocol.ts` | 路径 / 鉴权头 / 请求体字段名（`system` 放哪、上限字段叫什么）/ 报文解析 / 结束原因归一化 | 网络、计时、读流（它是纯函数层，可以脱开 HTTP 单测） |
| `llm/client.ts` | 发请求、读 SSE、三级超时、汇总、回调 | `if (protocol === …)`（出现就说明差异又摊回了外壳） |
| `llm/upstream.ts` | 看门狗 / 中断语义 / 状态码→502 映射 / 脱敏 / 通用 JSON 请求 | 任何协议字段名（它连 `choices` 都不认识） |

`LlmTarget` 因此多了一个 `protocol`（由 `resolveChatTarget()` 从 **Provider** 带出来，可选、缺省即默认协议 —— 于是 P0-1-37 之前的调用点一个字都不用改）；`fetchUpstreamJson` 多了一个 `headers` **整体覆盖**入参（不是"合并"：Anthropic 要的是**换掉** `Authorization` 而不是再加一个头）。

**差异收敛清单**（`06` P0-1-12 坑预判「不同 provider 的兼容性差异」的落点；每一条都有对应的验收用例钉着）：

1. **不发 `stream_options`**：这是 400 最常见的来源（不是所有网关都认这个字段），而 usage 只是锦上添花。真需要时应当做成 Provider 级开关，而不是默认发出去。
2. **不依赖 `[DONE]` 哨兵**：有的实现不发；流结束即结束。
3. **末帧可能没有结尾空行**：收尾时把残留缓冲也当作一帧处理，否则最后几个字会凭空消失。
4. **保活帧要跳过**：`choices: []`、只有 `role` 没有 `content` 的首帧、`:` 注释行（`keep-alive`）。注释行同时**重置流内空闲计时**，正是想要的语义。
5. **思考增量**：`reasoning_content`（DeepSeek 系）与 `reasoning` 两种写法都归到 `thinking`。
6. **`delta.content` 可能是数组**（多模态增量）：取其中文本 part 拼接。
7. **有的实现忽略 `stream: true`**：content-type 不是 `text/event-stream` 时按非流式解析，只回调一次 delta（并打 warn）。
8. **SSE 帧会被 TCP 切碎**：按行缓冲，与网络分片解耦（验收脚本会**故意**把一帧拆成两次 `write`）。
9. **畸形帧**：跳过并计数（`malformedFrames`）+ warn，不能因为一帧坏了丢掉整条回答。
10. **`200` 里藏 `{error}`**：显式判它并抛 502 —— 否则表现为"模型答了个空"，问题被推迟到很久以后。
11. **非 JSON 响应**：直接报"响应不是合法 JSON"并带上脱敏后的片段。
12. **Anthropic 的两条硬要求**（P0-1-37）：`system` **必须挪到顶层**（`messages[].role` 只认 `user`/`assistant`，混进去回 `unexpected role: system`），**`max_tokens` 必填**（OpenAI 可省略）—— 两条都是 400，而文案不会告诉你"该挪到顶层 / 该补一个上限"。
13. **Responses 的文本不在 `choices` 里**（P0-1-37）：非流式要读 `output[].content[]` 里 `type='text'` 的 `text`；`output_text` 是各家 SDK 的便捷字段，**HTTP 原生报文里不保证有** ⇒ 照 OpenAI 的老解析器打过去只会得到"上游响应里没有 `choices[0]`"。
14. **`rawFinishReason` 跨协议必须先归一化到 OpenAI 词表**（P0-1-37）：`chatBot`（§6.2 的留痕）用 `rawFinishReason !== 'stop'` 判"回答可能被截断"，而 Anthropic 原生是 `end_turn`、Responses 原生是 `completed` ⇒ 照原值透出去，**每一条正常回答都会打一条"可能被截断"的 warn**（观察面全是噪声，等于没有观察面）。映射：Anthropic `end_turn`/`stop_sequence`/`pause_turn`→`stop`、`max_tokens`→`length`、`tool_use`→`tool_calls`、`refusal`→`content_filter`；Responses `completed`→`stop`、`incomplete`→`length`（`incomplete_details.reason='content_filter'` 时→`content_filter`）。**未知取值原样透出**（不猜、不吞），判据落在 `llm/protocol.ts` 一处。
15. **`usage` 可能是"两个半份"**（P0-1-37）：Anthropic 的 `input_tokens` 在 `message_start`、`output_tokens` 在 `message_delta`，**且 `message_start` 那份是临时值**（形如 `{input_tokens:12, output_tokens:1}`）⇒ 合并规则必须是"非 `null` 字段覆盖"，且 `tokensTotal` 作为**从属量**在 `in`/`out` 都齐时按 `in+out` 重算（先到先得的 total 会让 `12+8=20` 报成 `13` —— 一个自相矛盾的 usage）。OpenAI 系一次给全且 `total = prompt + completion` 恒成立，故该规则对它们逐字等价。

**两条实现纪律**：

- **中断要在每一帧之前显式查一次信号**：一帧才几十字节，网关常把整个响应塞进一个 TCP 包，于是"abort 让网络读失败"根本不生效 —— 症状是"点了停止，回答还在往外冒"。
- **密钥零下发**（§九/§十 不变式）：明文 Key 只存在于进程内存；**任何**进日志或错误消息的上游响应片段都必须先脱敏（上游 401 的 body 常回显 `Authorization`，不脱敏等于借错误消息把 Key 漏出去）。日志只用 `describeTarget()`（id/名字/hasKey），绝不整体序列化 target。

### 6.2 编排循环实现口径（`backend/src/orchestrator/chatBot.ts`，P0-1-27 起落地）

§六 的 1~3 步与第 5 步在 P0-1-27 落地；第 4 步（工具循环）仍属 **P0-2**。文件分工刻意切成三块，
**判据是"能不能不依赖任何东西验"**（同 P0-1-18 给分块的定案）：

| 文件 | 内容 | 依赖 |
|------|------|------|
| `orchestrator/chatContext.ts` | system prompt 组装 / 检索块拼装 / 多库合并 / 引用卡 / 历史截断 / 落库形态（**全是纯函数**） | **零**（不 import `config`/`prisma`/日志）⇒ 断言进 `verify:app` 无依赖档 |
| `orchestrator/semaphore.ts` | 进程级并发闸（`tryAcquire` / `inFlight` / `limit`） | **零** ⇒ 同上 |
| `orchestrator/chatBot.ts` | 编排循环本体（读 agent/KB/历史、调检索、调上游、落库、打点） | 有（`config`/`prisma`/日志/上游）⇒ 归 `verify-chatbot` |

**九条口径**（都是"错了不会报错、只会静默做错事"的类型）：

① **并发闸满 ⇒ 流内 `error{code:BUSY}`，不是 429 JSON 信封。** 与 ⑧ 的 `CONFLICT` 同源判断：
分界线是**主语**。`BUSY`/`CONFLICT` 的主语是"**这一轮生成**"（客户端已经发起了对话 ⇒ 按单一渲染路径在
对话区收口），而 401/400/404/只读 409/424 的主语是"**这个请求/目标**"（换任何客户端都该先被拦下 ⇒ 信封）。
⇒ `assertConversationSendable` **刻意不含**并发闸（它是进程级信号量的产物）。
闸门**不排队**（`tryAcquire()` 满时**同步**返回 `null`）：ChatBot 这一侧没有 `queued` 的 UI，
顺手做排队只会造出"前端不知道该画什么"的中间态；`release` **幂等**（不幂等 ⇒ 计数减负 ⇒ 上限被悄悄放到无穷）。

② **未命中 KB ⇒ `citations` 事件一个都不发**（不是发 `items: []`）：前端按"有没有这个事件"决定要不要
画引用区（`03` §五），空事件会让它画一个**空卡**。这与 **prompt 层**的规则是 `01` 决策 12 的**两半**，
缺一半都是治表面（只做前一半 ⇒ 模型在正文里编造"根据《XX制度》"，界面上却没有卡可核对）。

③ **落库的判据是"这一轮真的发生过"，不是"成功了才写"**（`01` 决策 15「停止即中断，**已生成内容保留**」）：
中断（用户停止 / 客户端断开）**照样落库**（否则刷新后用户看到"我停了一下，问题没了"，而 `02` §5.2 的
断线恢复协议正是"拉历史补齐"）；上游故障时**已生成的内容也落库**再抛错。**唯一的例外是 `lock-lost`**
（那时可能已有另一个流在写同一份历史）。反之**前置失败（智能体没了 / 检索不可用）一个字都不落** ——
落库的单位是"一轮问答"，而这一轮没发生。**实现上刻意没有"是否落库"的标志位**：前置失败直接 `throw`，
能走到收尾分支的就是"真的发生过"的行 ⇒ **判据是控制流本身**。

④ **检索失败要整轮失败，不吞错。** 检索层把"搜不了"报成 409/500 而不是空结果（P0-1-20 定案：
"空结果会被读成'库里没有相关内容'，是一句假话"），本层原样透出。
⚠️ 逐库**各调一次** `searchKnowledgeBase` ⇒ 同一句 query 会被 embed 多次 —— 这是**刻意的**：
那条函数是"一次检索"的完整语义（读库配置 → 双路 → RRF），为省一次 embedding 绕过它（自己拼 SQL）
会让"检索口径"出现**第二个实现**；库的数量是个位数，代价可接受。

⑤ **帧透传要一条串行队列。** `chatStream` 的回调是**同步**的（`onDelta: (text) => void`），而 `emit`
是异步的（要过 schema 校验、还要在背压时等 `drain`）。`void emit(...)` 有两个真实后果：帧的**顺序**
不再有保证；emit 抛错会变成**没人接的 promise rejection**。故用一条 promise 链串起来 + 记下**首个错误**
（收尾时先判它，再判上游故障）。

⑥ **TTFT 在第一个 `delta` 上打点**（`02` §十三 是阶段一"首字 < 3s"的**唯一**测量依据，不能事后补）。
日志带 `ttftMs` / `historyMessages` / `citations`。上游 `finishReason` 不是 `stop`（如 `length` 被
`max_tokens` 截断）时契约里仍按 `COMPLETE` 收尾，但**必须打 warn 留痕** —— 否则"回答被腰斩"在服务端
没有任何线索（§6.1：归一化会丢掉这个决策信息）。

⑦ **`usage_records` 表在本版本不写**（属 **P1**：`01` 决策 20、§七 待决事项 4 已定案"首版只打日志"，
`schema.prisma` 里没有这张表）。本批做的是"计量**透传**"：`done.usage` 给前端 + 结束日志带
`tokensIn/tokensOut`。**接回点**：P1 建表后在落库那个事务里加一条 `usageRecord.create`。

⑧ **本版本刻意不做 token 级上下文裁剪**：`model.maxContext` 在库里但**没有可用的 tokenizer**
（embedding 用的是另一套模型）⇒ 按字符估算再裁会得到"看起来在保护上下文、实际按一个错误的折算率乱切"
的**假保护**，比"明确只按轮数裁"更坏。唯一的边界手段是轮数（`CONTEXT_ROUNDS`）。**留在待回补清单**。

⑨ **接回点兑现**：`orchestrator/index.ts#resolveChatProducer()` 从占位换成 `chatBotProducer`
（P0-1-26 的单点替换承诺），`routes/conversations.ts` **零改动** —— 唯一的接口增量是
`ChatProducerInput` 新增 `content: string`（占位 producer 只发 ping，确实不需要正文；编排循环需要它两次：
**检索 query** 与**落库正文**）。

### 6.3 工具循环实现口径（P0-2-8 落地）

代码落在 `orchestrator/chatBot.ts`（循环本体）+ `chatContext.ts`（工具结果 → 消息的**纯函数**）+
`llm/protocol.ts`（**三协议的差异收口**）+ `llm/client.ts`（分片累积）+ `services/mcpCall.service.ts`
（`resolveMcpToolCatalog` 组装工具表、`executeMcpToolCall` 执行一次调用）。**七条口径**：

① ⚠️ **流式 `tool_calls` 是"分片累积"的，绝不能在第一片解析。** OpenAI 的 `delta.tool_calls[]` 是
`index` + `id` + `function.name` + `function.arguments` **逐段到达**，`arguments` 在到达过程中是
**不完整的 JSON 字符串** ⇒ 第一片就 `JSON.parse` **不报错、只是解析出空参数**（模型看起来"调了个空工具"）。
正确形态：按 `index` 累积到**一个瞬时缓冲**里，**在 `finish_reason==='tool_calls'`（或流结束）后**才取
完整串去 `parseToolArguments()`。跨协议同理：Anthropic 的 `tool_use` 是 `content_block_start` +
`input_json_delta` 累积、Responses 是 `function_call` 的 `arguments` 增量 ⇒ **统一按同一个"累积"抽象做**，
落在 `protocol.ts` 的钩子里（**不在 `chatBot.ts` 里手拼**）。⚠️ 半成品**不外泄**：累积器是 `client.ts`
的局部变量，出口只给"已完整"的 `toolCalls`（越界/不完整的另走 `incompleteToolCalls` 计数告警）。

② ⚠️ **工具结果的报文形态跨协议全不同 ⇒ 编排层只吐协议无关的 `role:'tool'`。**
OpenAI 是 `role:'tool'` + `tool_call_id`；Responses 是顶层 `{type:'function_call_output', call_id}`；
Anthropic 是**用户消息里的 `tool_result` 块**（且有**角色必须交替**的硬要求 ⇒ 工具结果**合成一条
`user` 消息** + 相邻同角色合并）。编排层的 `buildToolResultMessages()` 只产
`{role:'tool', toolCallId, content, isError}`，**手拼报文一律归 `protocol.buildBody`** ——
否则"换了协议就调不动工具"，而 `verify:llm` **不会红**（它不跑编排循环）。

③ **工具失败 ≠ 这一轮失败**（`06` P0-2-8 门槛 2）。`isError:true` / 缺凭据 `424 NEED_CREDENTIAL` /
server 没了 `404` / 上游 `502`/`504` **全部**变成 `tool_call{ERROR}` 卡 + **把错误文本回填给模型**，
让模型自己决定怎么说。整轮失败会让用户只看到一张错误卡、**拿不到任何解释** —— 比"这一轮答得不好"更差，
也不是 `01` §3.6"失败错误可见"要的形态。**唯一的例外是中断**（`McpAbortError`）—— 那要真的停下来
（用户的「停止」**不是**工具失败）。

④ **"还允不允许要工具"的判据是"已执行了几轮"，不是"请求了几次"。** 到 `TOOL_LOOP_LIMIT`（=10）之后
**当轮就把 `tools` 撤掉** + 注入一条 `TOOL_LOOP_LIMIT_NOTICE`（`user` 角色，**只注一次**），
而不是等模型第 11 次要了再拒：撤掉省一次明知不会执行的上游往返，而且**只有"请求里没有 `tools` 字段"
才是真的禁工具** —— 只在提示里写"不许调"，模型仍可能吐一个工具名出来。那一刻**只能收尾**
（不能执行=突破上限、不能再提示=死循环），记一条 warn 留痕。

⑤ ⚠️ **`tool_calls` 还原成历史时必须"成对"。** 三协议都要求 `tool_calls` 与工具结果**成对**：
一条没有结果的调用是 **400**（Anthropic 的原文是 "tool_use ids were found without tool_result blocks"）。
而"工具跑到一半被停止 / 那一轮整体失败"正好会留下这种半截记录 ⇒ 历史还原时**整个工具段一起丢**
（只留正文），而不是留下一条会让**之后每一轮**都 400 的记录 —— 后者的症状是"这个会话从此再也发不出消息"，
且完全指不到历史里那一行（见 `chatContext.ts#selectHistoryMessages` ③④两条）。

⑥ **凭据的主语来自"当前会话"**（§9.3 不变式的落点）：`viewer.userId` 从 `conversations` 行**懒加载现查**
（只有真要执行工具时才查一次、查到就缓存），**不从请求体、不从路径、不顺着调用链传** ——
传一次就多一个"传错人"的机会，而现查的代价只有一次主键查询。

⑦ **落库的 `tool_calls` 与读取端共用同一个 schema**（`shared#toolCallRecordSchema`）：
助手消息 `content.tool_calls` 存**完整入参**（`arguments` 原样字符串），卡片的 `inputSummary` 只是**摘要**；
`inputSummary` 的"凭据形状遮值"（`looksLikeSensitiveKey`）是**尽力而为、不是安全边界** ——
真正的保证在另一条线上（**凭据从不下发给模型**，§九/§十 不变式）。工具结果**截断**用的是
`TOOL_RESULT_MAX_CHARS=8000`（常量），且**给模型的那份与给卡片看的那份是同一份**（同 P0-1-27 为引用
片段立的规矩）。
⚠️ **`arguments` 只进库、不上线，且这条不是靠 schema 自动挡住的**：`emit()` **序列化的是 `event`
原对象、不是 `parsed.data`**（zod 的 `strip` 只作用在 `parsed.data` 上）⇒ 构造 payload 时**不能把
`arguments` 混进去** —— 否则完整入参**原样上流**，而 `sseToolCallPayloadSchema` 的 `.omit()` 只是
**看起来**挡住了它（`safeParse` 不报错，因为未知键是"剥掉"而不是"拒绝"）。落法：`chatBot.ts` 里的
`base` 刻意**不含** `arguments`，完整入参只在落库那一份（`toolRecords.push`）上补。

> **本批的已知边界（别当 bug）**：· **危险判定已算出来但还没接线** —— `route.dangerous` 从 P0-2-9 起
> **已经是对的**（判定表见 §9.9），缺的只是"挂起等 `/confirm`"那一半（属 **P0-2-10**）⇒ 本版本
> **所有工具仍然直接执行、不弹确认卡**（别把"判定好了"读成"确认流做了"）；
> · **一轮里多个 `tool_calls` 按顺序执行**（不并行）；· 还原顺序是 `assistant{正文+toolCalls}` →
> `tool{结果}`，即"最终正文"排在工具结果**之前**（结构合法、语义略倒置 ⇒ 保真度折损，要修得先改成

## 八、embedding：双模式 provider

```ts
interface EmbeddingProvider {

  dim(): number;              // 1024（bge-m3）
  name(): string;             // 落库标记，用于换模型检测

// local：onnxruntime-node + bge-m3 int8 模型（挂载卷 /models/bge-m3-int8）
//        启动懒加载；批量推理；CPU 即可
// api：  OpenAI 兼容 POST {base_url}/embeddings
// 配置：EMBEDDING_MODE=local|api（api 时配 EMBEDDING_API_URL/KEY/MODEL）
```

- 换 embedding 模型 = `name()` 变化 → 所有 KB 标记"需重建"，检索时明确告警（旧向量维度不匹配直接跳过该库并提示）
- 维度变化时的重建路径：chunks_v2 新表 → 流水线双写 → 切换检索指向 → 弃旧表（见 §三分区说明与子方案①）
- 整库重建走流水线队列（P1）

### 8.1 实现口径（P0-1-13 落地）

代码：`backend/src/llm/embedding/{index,api,local,embedding.worker}.ts`；`index.ts` 是唯一入口
（`getEmbeddingProvider()` / `embeddingReadiness()` / `resetEmbeddingProvider()`）。

- **`name()` 的两种形态**：`api:<EMBEDDING_API_MODEL>`、`local:<模型目录名>`（如 `local:bge-m3-int8`）。
  同一个 model id 换 endpoint 视为同一模型（OpenAI 命名惯例：model id 就是身份）；换维度由
  `dim()` 与 `EMBEDDING_DIM` 的一致性单独守住。**就绪自检返回的 `name` 由 provider 自己给**，
  免得"自检里那个名字"与"实际落库的名字"不是同一个值。
- **`dim()` 恒返回配置维度**（`EMBEDDING_DIM`）：它是写 DDL/meta 的依据。上游/运行时**实际**返回的
  维度每次调用逐条校验，不符即报错（api → 502；local → 500），**绝不写库**——维度不对的向量
  事后无法分辨。
- **api 模式**：请求体只有 `{ model, input }`，**刻意不发** `encoding_format` / `dimensions` / `user`
  （与 §六.1 不发 `stream_options` 同因：都是 400 的常见来源）；批按 `EMBEDDING_BATCH_SIZE`（32）**串行**发
  （不裸 `Promise.all`：一份 5000 chunk 的文档会变成 157 个并发请求，上游限流当场打回）；
  响应四形态归一（`data[].embedding` 带/不带 `index`、`data` 放数组、ollama 的 `{embeddings}`），
  **有 `index` 就按它归位并要求是 `0..n-1` 的排列**（不归位会出现"第 3 段配了第 7 段的向量"）。
- **local 模式**：`worker_threads` 隔离 CPU 密集（§二），懒加载；**推理运行时（含分词）由
  `LOCAL_EMBEDDING_RUNTIME_MODULE` 注入**，契约是导出
  `createEmbedder({ modelPath, dim }) → { dim?, embed(texts), dispose?, describe? }`。
  为什么用注入而不是直接 `import('onnxruntime-node')`：bge-m3 的分词实现取决于最终拿到哪一份交付物
  （`06` §七 待决事项 2 未关闭），写死等于赌；而这个缝已经被验收脚本证明"能插上、且真的跑在独立线程里"。
  就绪自检三态（目录不存在 / 目录里没有 `.onnx` / 没配运行时模块）各给一条可执行文案，**在起线程之前**报错。
- **重试不在 provider 里**：`子方案①` §4-3 的"单批失败重试 2 次"属于流水线的任务级策略
  （P0-1-19：重试与"整篇 FAILED"是同一个决策），provider 只做单次调用 + 明确报错。
- **就绪判定分两级**（延续 §十一 的口径）：`config.ts` 只打 WARN（不拦启动）；
  `getEmbeddingProvider()` **取用时硬报错**并给全问题清单。

## 九、MCP 用户级凭据（核心定制点）

### 9.1 注册（注册者定义模板）

```json
// POST /api/mcp/servers
{
  "name": "内部工单平台",
  "endpointUrl": "https://ticket.internal/mcp",
  "authType": "NONE",
  "credentialSchema": [
    { "key": "X-User-Token", "label": "个人令牌",
      "type": "string", "inject": "HEADER" }      // HEADER | QUERY | BODY
  ]
}
```

### 9.2 用户填值（每用户一份）

```
PUT /api/mcp/credentials/:serverId
{ "values": { "X-User-Token": "我的token" } }
→ AES-256-GCM 加密后存 mcp_credentials（密钥来自环境变量）
```

### 9.3 调用时注入

```
编排器发起工具调用 → 取 (server, currentUser) 凭据
  ├─ 有：解密 → 按 inject 位置注入请求头/参数 → 执行
  └─ 无：tool_call{ERROR: "需先配置凭据"} → 前端卡片带"去配置"跳转
```

> ✅ **这条链路已在 P0-2-8 落地**（编排循环的工具循环，口径见 §6.3）：'有' 那一路 = `executeMcpToolCall`
> 走 `resolveMcpCallContext`（§9.8）执行；'无' 那一路不再是一句 `ERROR`，而是 `resolveMcpCallContext`
> 在发请求**之前**抛的 **`424 NEED_CREDENTIAL`**，被工具循环接住 ⇒ 变成 `tool_call{ERROR,
> errorCode:'NEED_CREDENTIAL'}` 卡片 + **错误文本回填给模型**（**不是**整轮失败，见 §6.3 ③）；
> 文案**点名缺哪几个 key**，"去配置"跳转由 `03` 的前端按 `errorCode` 决定。

**不变式**：凭据只在后端解密，永不下发前端；A 用户会话绝不使用 B 用户凭据。
> ✅ **P0-2-7 落地后这条是"结构性成立"的**（两道**独立**防线，见 §9.8）：
> ① 取凭据的查询范围固定在 `(serverId, userId)` 上（`viewer.userId` 只来自当前会话）；
> ② AAD 含 `userId`（§9.5 ①）⇒ 即使把 B 的密文粘到 A 的行上**也解不开**，解不开按"没值"处理。
> "两道都失效"需要同时改两处公式，而那个公式是**唯一实现**。

**inputSchema → OpenAI function 转换**：MCP tool 的 `inputSchema`（JSON Schema）直接映射为 function 参数 schema；工具名冲突时加前缀 `mcp_{serverSlug}_{toolName}`；转换逻辑集中在 MCPClient 层。
> ⚠️ **`serverSlug` 从哪来（P0-2-2 落地）**：`mcp_servers.slug`，由 `name` 派生（小写 ASCII、非字母数字折 `-`、截断 32、纯中文整串折空时回落 `server`）、**创建时生成后不再变**（改名不改 slug —— 它要进工具名，而工具名会进历史消息的 `content.tool_calls`）。派生函数 `slugifyServerName` / `uniqueSlug` 在 `shared/src/mcp.ts`（**纯函数、唯一实现**）。⚠️ 唯一性只是 **best-effort**（`slug` 列刻意不加唯一约束），**跨 server 的工具名冲突要在本层用"加序号"兜住**，别指望 slug 是唯一的。
### 9.4 注入位置的口径（P0-2-3 落地 · 含协议线实测）

> 模板形状（`{key,label,type,inject,required?,placeholder?}`）与"`key` **按注入位置分判**"的**唯一实现**在
> `shared/src/mcp.ts`（`credentialSchemaDeepIssues`，`credentialSchemaSchema.superRefine` 与独立入口
> `validateCredentialSchema` 共用它）；本节只记**为什么这么判**。⚠️ 凭据的**值**（`PUT` 写入 / 未配置清单）属 **P0-2-4**，本节只管**模板**。

三条规则都属于**"形状合法、注入出去一定出错"** —— 它们在模板层**都不报错**，要等到调用时，甚至只表现为"凭据没生效"⇒ 必须在**模板落地的那一刻**拦下来：

| `inject` | 落点 | `key` 的约束 | 违反的后果 |
|---|---|---|---|
| `HEADER` | 请求头 | 必须是合法 HTTP 头名（RFC 7230 的 `token`，用**正则**判，不是"不含空白"）；且**不得占用平台自己要发的头** | `X-User Token` / `X-User:Token` 会被 fetch/undici 拒绝或**静默截断**；占用平台头会覆盖掉平台的语义（见下） |
| `QUERY` | URL 查询串 | 不得含 `&` / `=` | 会把查询串切开，服务端收到的键名与模板里写的**不同** |
| `BODY` | 请求体**顶层** | 不得是 JSON-RPC 请求对象的保留成员（**按字面**比较 —— `Method` 不会覆盖 `method`） | 撞名会把报文语义毁掉（见 H3） |

**平台保留的请求头**（`HEADER` 不得占用，**按小写比较**——HTTP 头名不区分大小写）：
`accept` / `content-type` / `content-length` / `host` / `mcp-session-id` / `mcp-protocol-version`。
前四个是 HTTP 与 fetch 自身要用的；后两个属 **Streamable HTTP 传输层**（会话与协议协商）。
⚠️ 占用 `accept` 的后果**最隐蔽**：注入会覆盖掉"**回 JSON 还是回 SSE**"的协商头，症状是
"这个 server 的凭据一配上、工具就调不动了" —— 而报错会**指向上游**（`06` P0-2-7 坑预判 1）。

**JSON-RPC 请求对象的保留成员**：`jsonrpc` / `id` / `method` / `params`。
⚠️ 键名集合**只有这四个**：响应里的 `result` / `error` **不在其中**（我们发的是请求）。

**协议线实测（P0-2-3 探针，用例在 `verify-mcp-client` 的 H 组；被探方是**本仓的假 MCP server**，用裸
`fetch` 手写报文、刻意绕开 SDK）**：

| 问题 | 结论 | 取证 |
|---|---|---|
| 非保留的**顶层额外字段**，服务端认不认？ | **认，且完全不影响这次调用** ⇒ `BODY` 注入**在协议线上可行** | H1 |
| 塞进 `params.arguments` 呢？ | **污染工具入参**（凭据混进了工具自己的参数里，夹具把两者一起回显了） | H2 |
| 塞成 `params` 的**兄弟键**呢？ | **凭据等于白注**（服务端按工具契约只读 `name`/`arguments`，根本看不到它） | H2 |
| 与四个保留键**撞名**呢？ | 撞 `method` ⇒ 这次调用**变成另一次调用**；撞 `params` ⇒ 工具名丢了，服务端回 `-32602`；撞 `id` ⇒ 响应 id 被顶成凭据值并被**原样回显到线上**（关联被毁 **且** 凭据漏到链路上） | H3 |
| **拿什么去注入**？ | `StreamableHTTPClientTransport` 的 **`fetch` 选项**能同时改 URL / 请求头 / 报文体 ⇒ 三种位置**一个口子全包**，不必改 SDK、也不必为 `BODY` 造旁路 | H4 |

⚠️ **上面"顶层字段可行"是本仓假夹具的结论，不是规范的保证** —— 规范没有规定服务端**必须**忽略未知的
顶层成员。真正的兜底是 P0-2-7 落地后用**真 server** 复验一次；本探针的价值是把"该不该在模板层拒掉那四个键"
这类**必须现在就定**的事先定下来（答案：拒掉，因为撞名的后果是"毁报文 + 可能泄露凭据"）。

✅ **P0-2-7 已兑现这个接回点**：`McpClientOptions` 新增了 `fetch` 选项（并**删掉**了 P0-2-1 那个
`headers` 选项 —— 见 §9.8 ①），**注入中间件就落在那一个点上**（HEADER/QUERY/BODY 三种位置在同一个
`fetch` 里完成）。客户端层没有重构。

**模板变更只提示、不清理（P0-2-3）**：`PATCH /api/mcp/servers/:id` 的响应里带
`credentialSchemaImpact`（`removedKeys`/`addedKeys`/`retargetedKeys` + `affectedCredentials`）——
它**只说明"哪些参数被删/被加/被换了注入位置"，一个字都不动用户已填的凭据**（值没了是**不可逆**的，
而用户只是临时改错了模板）。⚠️ **`affectedCredentials` 在 P0-2-3 时恒为 `null`、P0-2-4 起是一个真数**
（表建好后"几条已存凭据受影响"就答得出来了 ⇒ `null` 从契约里去掉，不留"nullable 但恒有值"的死分支；
说出来的结论必须真，说不出来的才留白）。它只数 `removedKeys`（`addedKeys` 是"缺值"、
`retargetedKeys` 是"值还在、只是注入了别处"），且**不判解密**（键名不加密）。
⚠️ 它与"缓存该不该清"是**两个判据**：
缓存按 `sameJson` 判"模板**整体**变没变"（**连 `label` 改了也清**），impact 按 `diffCredentialSchema`
判"**已存凭据会受什么影响**"（只有 key 级的增/删/换注入位置才算）—— 同一份输入得出**不同**结论是对的。

### 9.5 凭据值的口径（P0-2-4 落地）

> 形状与判据的**唯一实现**在 `shared/src/mcp.ts`（`credentialValueKeys` / `missingRequiredCredentialKeys` /
> `isCredentialConfigured` / `mcpCredentialFieldSchema`）与 `mcpCredential.service.ts`
> （`mcpCredentialAad` / `listMyCredentials` / `putMyCredential` / `removeMyCredential` /
> `countAffectedCredentials`）；本节只记**为什么这么判**。接口口径（合并语义 / 两面清单 / 404 / 信封）
> 在 §4.7 的"契约增量 · 我的凭据"。

**① AAD = `mcp-credentials:{serverId}:{userId}.values_enc.{key}`（含 server + user + key，刻意不含行 id）**
—— 与 §10.2 的 `providerKeyAad`（含记录 id）**方向一致、组成不同**，差异有理由：
Provider 的 AAD 含 id ⇒ 加密只能发生在拿到 id 之后（建记录必须走事务）；凭据走 `upsert`，
**加密那一刻还没有行** ⇒ 归属用 `(server,user)` 这个唯一键（行 id 只是它的代理）。
少一段的效果是实打实的：**把 A 的密文粘到 B 的行上会解不开**（binding 层），
多带 `key` 则让值不能在**同一条记录的不同字段**之间搬运。

**② 读路径必须真解一次才判得出"有没有值"**（`hasValue` 的判据 = **这一格能不能解出来**）。
AAD 是**绑定**而不是**格式**：一段结构完全合法的 `v1.<iv>.<tag>.<ct>` 可能根本不属于这一格
（别处粘来的、主密钥换过）。⇒ "粘密文"这件事在 `GET` 上**立刻显形**（该参数显示未配置、可重填），
而不是拖到调用时才炸。解不开的处置固定三步：① 不进 `presentKeys`（⇒ `configured` 按模板重算）；
② 一条 `warn`（**只记 serverId/userId/key 名**）；③ **绝不 500** —— 主密钥轮换后整页崩掉是最坏的
形态，它会把"某人需要重填一个令牌"呈现成"这个系统坏了"。

**③ "有值" = 值是非空字符串**；**清空 = 把键删掉**。不是"键在=有值"：
`encryptSecret('')` 会得到 `v1.<iv>.<tag>.`（结构合法），若按"键在"判，清空过的参数会永远显示
"已配置"（界面上那个 ✓ 是骗人的）。⚠️ 因此 `PUT` 提交空串 ⇒ 删键；**清到一个不剩 ⇒ 整行删掉**
（留一个 `values_enc:{}` 的空行会让"我有凭据"变成假话）。

**④ `configured` 按**当前模板**逐 key 判（必填项齐不齐），与 `updatedAt`（有没有行）是两个字段。**
合并语义 ⇒ 注册者后来新增 `required` 参数时，老用户的行还在、那个 key 却没有值 ——
"表里有行 = 已配置"会让界面显示 ✓ 而调用时缺 key。反向：模板**没有必填项**时"从没写过"也是
`configured:true`（内网无鉴权的 server 就属这类）。

**⑤ 出参只有 `key` + `hasValue`，没有值、没有掩码。**（理由见 §4.7 契约增量 ③）
**⑥ 日志只写键名与真假，绝不整体序列化含值的对象**（§十三 的 `LOG_REDACT_PATHS` 已含
`values` / `valuesEnc` / `values_enc` 及其一级通配）；错误消息里也不能带值
（P0-1-12"借错误消息漏凭据"同款 —— 所以"参数不在模板里"报的是**键名**）。

### 9.6 工具列表与缓存（P0-2-5 落地）

> 形状与判据的唯一实现在 `shared/src/mcp.ts`（`mcpServerToolsQuerySchema` /
> `mcpServerToolsResultSchema`）与 `mcpServer.service.ts`（`refreshServerTools` / `readCachedTools` /
> `getMcpServerTools`）；解析层在 `mcp/toolCache.ts`。接口口径在 §4.7。本节只记**为什么这么判**。

**① `tools/list` **不带任何用户凭据**，于是 `tool_cache` 是"每个 server 一份、全员共享"。**
这条不是实现细节，是**一条产品级边界**：有些 MCP server 的 `tools/list` 也要求鉴权，本平台
**拉不到**那类 server 的工具列表。定案是"注册者视角"，绝不"顺手带上某个人的凭据"——
后者会造出"**工具列表依赖谁先点过测试**"的诡异状态（同一台 server，A 点过测试后 B 才看得见工具）。
⚠️ **文案要跟着这条走**：`tools/list` 阶段收到 401/403 时不能说"请检查凭据是否已配置且有效"
（那是**握手 / 调用工具**阶段的正确文案，因为那两个阶段真的会注入凭据），而要说
**"本阶段拉取工具列表不带任何用户凭据 ⇒ 平台当前不支持带用户凭据拉列表"**。
⇒ 实现上 `stage` 必须是**共享常量**（`mcp/errors.ts#MCP_STAGE_LIST_TOOLS`），
两处各写一份字符串就会让这条分支**静默失效**（退回那句误导人的话）。

**② 缓存的失效判据是"**真的变了**"，且它只认三列**（P0-2-2 定案，此处存档）：
`endpoint_url` / `auth_type` / `credential_schema` 变了才清（`tool_cache: NULL` + `status: UNKNOWN`）；
**只改 `name` 不清**（名字不参与连通，清了只会让用户白等一次重拉）；
**原样提交也不清** —— 判等必须**键序无关**（PG 的 `jsonb` 会重排对象键，逐字比较会把"没改"判成"改了"，
症状是"每次保存工具数都归零"）。⚠️ 与 `credentialSchemaImpact` **刻意是两个判据**（同一份输入两个结论是对的）：
缓存按"**模板整体**变没变"判（连 `label` 改了也清），impact 按"**已存凭据会受什么影响**"判。

**③ `?refresh=1` 与 `POST /:id/test` 都刷新缓存，但出口不同 —— 差别不在路由，在**响应形状里有没有"失败"的位置**。**

| 场景 | `POST /:id/test` | `GET /:id/tools?refresh=1` |
|------|------------------|---------------------------|
| 拉到 | 200 + `{ok:true,tools}` | 200 + 裸 `{tools,fetchedAt,cached:false}` |
| 拉不到、**有旧缓存** | 200 + `{ok:false,error}` | **200** + 裸 `{tools:旧, fetchedAt:旧, cached:true}` |
| 拉不到、**无缓存** | 200 + `{ok:false,error}` | **502**（统一信封） |

前两行是"**答得出来就答**"（连不上是一条**信息**，不是错误）；第三行是"**我们答不了这个问题**"——
唯一能返回的成功形状是 `{tools:[]}`，而它与"这个 server 确实没有工具"**逐字一样**，
用户会去上游找一个**其实不存在**的配置问题。⇒ **给不出的东西不要拿空值代替**。
⚠️ 因此**别把两条路由的出口"统一"起来**（`/health` 恒 200 是同一个道理的另一面）。

**④ `cached:true` 就是"你看到的不是刚拉的"的全部信号。** 契约里**刻意不加** `warning` 之类的字段：
`cached` + `fetchedAt` 两件事已经够界面画出"缓存于 X"，多一个字段等于同一件事两个来源（会分叉）。
真正的失败原因进**服务端日志**（`warn`，含 `error` 与旧 `fetchedAt`）——它对人有用，对界面无用。

**⑤ `refresh` 是白名单（`1`/`0`/`true`/`false`），拼错就 400。** 不能用 `z.coerce.boolean()`
（`Boolean('0') === true` ⇒ `?refresh=0` 变成"要刷新"，**零症状**：用户以为关掉了，其实每次请求都联网）；
也不能放宽成"任意字符串"（`?refresh=yes` 静默等于不刷新 ⇒ 点了刷新却看到旧列表）。

### 9.7 工具名与参数 schema 的转换口径（P0-2-6 落地）

> **唯一实现**：`backend/src/mcp/toolSchema.ts`（纯函数 `toOpenAiTools(server, tools, limit, taken?)` →
> `{ tools, routes, truncated }`）与 `shared/src/mcp.ts` 的四个常量（`MCP_TOOL_NAME_MAX` /
> `MCP_TOOL_NAME_PREFIX` / `MCP_TOOL_DESCRIPTION_MAX` / `MCP_TOOL_WRAPPER_KEY`）。
> **本步不改任何端点**（接口口径仍看 §4.7 / §九），消费方是 **P0-2-8** 的编排循环；本节只记**为什么这么转**。

**① 只做三件有理由的兼容处理，绝不"聪明地"裁剪 schema。**
① 剥 `$schema`（它只是"这份 schema 自己的方言声明"，对"参数长什么样"零信息量，而 OpenAI 的 `parameters`
位置不接受它）；② 缺 `type` 时补 `'object'`（缺 `type` 在 JSON Schema 语义里"什么都接受"，但 `parameters`
必须声明成 object）；③ 非 object 根包一层（见 ④）。
⚠️ **其余一律原样透出** —— `additionalProperties`（`false` 是**有约束力的**，不是元信息！）、`required`、
`items`、`enum`、`$ref` 一个不动；实现是**浅拷贝**（`{ ...schema }`），只删顶层 `$schema`、只补顶层 `type`。
理由（`06` P0-2-6 坑预判 1）：**丢掉的约束会让模型传错参数，而报错发生在服务端** —— 用户看到的是
"这个工具调用失败"，错因却在平台。

**② 工具名 = `mcp_{slug}_{toolName}`：过一遍 `[A-Za-z0-9_-]`（非法字符折成 `_`，不是删掉）、截断 64、撞名加序号。**
· 折而不是删：删掉会让 `a.b` 与 `ab` 同形（序号兜得住，但那是把"有区分度"的名字换成"靠顺序"的名字）；
· **不假设 `slug` 合法**：它来自库里的一列（历史行 / 手工改库 / 迁移都可能越界），`slugifyServerName`
  只保证"**创建那一刻**产出的值合法"⇒ 整串统一过一遍字符集；
· **截断与序号必须一起做**：只截断 ⇒ 两个长名字撞在一起、**后者静默覆盖前者**（模型永远调不到它）；
  只加序号 ⇒ 后缀被截掉等于没加。手法与 `shared#uniqueSlug` **逐字同款**（先按后缀长度截短 base）。
· ⚠️ **唯一性分两层**：单 server 内由本函数自增的集合保证；**跨 server 由调用方传入 `taken` 保证** ——
  slug 刻意不加唯一约束、纯中文名还会整串折成 `server` ⇒ **不同 server 天然会产出同名工具**。
  P0-2-8 拼多个 server 时必须**依次**把前一个的 `routes` 键喂给下一个（**顺序即正确性**）。

**③ 反向映射表（`routes`）只存 `toolName` + `serverId`，连 `slug` 都不存。**
它是"名字 → 工具"的**唯一事实来源**（模型回 `tool_calls` 时只给名字）。存 `serverId` 而不是 slug：
P0-2-7 要按 `(serverId, userId)` 取凭据、P0-2-8 要按 id 找 server —— 只给 slug 会让每个调用点
自己再查一次库。**不存 slug 本身也是刻意的**：只要表里有个"能反推出 server"的字段，就一定会有人
在编排层"从名字里 split"（而 slug 与 `toolName` 都常含 `_`，split 出来的十有八九是错的）。

**④ 非 object 根"包一层"是本层的一条已知边界（明知会失败也要包）。**
`type !== 'object'` **严格不等**才算非 object 根（`['object','null']` 这类**联合 type 也算** ——
OpenAI 的 `parameters` 不接受数组形式），处置是包成
`{ type:'object', properties:{ input: <原 schema> }, required:['input'] }`。
⚠️ **代价如实写在这里**：模型会传 `{ input: … }`，而那个工具真正想要的是**顶层标量** ⇒ 这次调用**必失败**。
之所以仍然包：包住至少保留了原始约束（模型看得到"这里要一个 string"）、用户在工具卡片里能看到真因
（"这工具的参数竟然不是对象"）并去修服务端；丢掉整个工具则只剩"它神秘消失"。
（`inputSchema` 连普通对象都不是时——`null` / 字符串 / 布尔——退回 `{ type:'object', properties:{} }`，
**不编造**内容。）

**⑤ `description` 兜底链 `description → title → ''`，按码点截断 `MCP_TOOL_DESCRIPTION_MAX`。**
用 `title` 兜底不算编造（它本来就是服务端给的**人读标题**），而"空 description"是**最贵**的一种省事
（模型对一个只有名字的工具几乎必然传错参数）。⚠️ 截断按码点（`[...raw]`）而不是 `String.prototype.slice`：
后者按 UTF-16 码元切、会把代理对劈成两半、产出非法字符串，而**这一层毫无报错**（P0-1-18）。

**⑥ `truncated` 与"告警"的分工，以及 `limit` 的兜底口径。**
超过 `MCP_TOOL_LIMIT` 时**截断**并返回 `{ total, kept }`，未截断时是 **`null`**（让"要不要告警"退化成
一个**真值判断**，而不是让每个调用点自己再比 `kept < total` —— 同一口径两处写法必有一处先腐烂）。
**告警的落点在调用方**（本模块零依赖、不 import 日志 ⇒ P0-2-8 打 `warn`）；但它**必须进返回值**，
因为"这个 server 的工具没全下发"界面那一侧也要能知道（不能像时间戳那样靠副作用）。
⚠️ `limit` 非有限值的兜底：**`NaN` ⇒ 0**（宁可全截断，也不静默全放行 —— "上下文被几十个工具的 schema
塞爆"是难查的一类问题）、**显式 `Infinity` ⇒ 不截断**（"无上限"是个合法的显式意图）。
`config.mcp.toolLimit` 本身已由 `intVar` 收在 1..512，这只是纯函数的自我保护。

### 9.8 注入端（P0-2-7 落地）

> 形状与判据的唯一实现：`backend/src/mcp/inject.ts`（**纯函数 + 一个 fetch 中间件**）与
> `backend/src/services/mcpCall.service.ts`（`resolveMcpCallContext`）；判据函数
> （`isValidHttpHeaderName` / `isReservedHeaderName` / `isReservedJsonRpcKey` / `hasQueryDelimiter`）
> 在 `shared/src/mcp.ts` —— **写端闸门（§9.4）与注入端共用同一份**。接口口径见 §4.7 / §九 9.3。

**① 三种注入位置**共用同一个口子**：transport 的 `fetch` 选项（H4 的兑现）。**
H4 问"拿什么去注入"，答案是 `StreamableHTTPClientTransport` 的 `fetch` —— 它**同时**能改 URL /
请求头 / 报文体 ⇒ HEADER / QUERY / BODY 一个口子全包。
⚠️ 因此 `McpClientOptions` **没有** `headers` 选项（P0-2-1 曾有一个、注释写着"凭据注入口"，P0-2-7 删掉了）：
留着它就是**第二条注入路径**，而两条路径在这一个点上打架的症状是"某个凭据时而生效、时而被顶掉"
—— 最难查的一类。要加静态头就写一个 `fetch` 包装。
⚠️ **注入是在 SDK 已拼好的 `Headers` 之上 `set`，不是替换**：SDK 传进来的那个 `Headers` 里装着
`mcp-session-id` / `mcp-protocol-version` / `accept` / `content-type`，整体替换会把会话与
**响应形态协商**一起搞坏（§9.4 表格最后一行）。

**② QUERY 注入**不需要**放弃连接复用（坑预判 2 的探针结论）。**
坑预判 2 的担心是"这一次调用的 endpoint 变了"⇒ 与连接复用冲突，预案是"QUERY 注入的 server
每次新建 transport"。**探针结论（读 SDK 1.30.1 源码 + 确定性核查）**：`send()` /
`terminateSession()` / `_startOrAuthSse()` 三处都是 `await (this._fetch ?? fetch)(this._url, init)` ——
**URL 是每次调用时现传给 fetch 的**（`_url` 本身整个会话不变）⇒ 把 query 拼在**每请求**的 URL 上安全，
会话与协议版本头都不受影响 ⇒ **那个代价没有发生**。

**③ 模板是唯一的路由表。** 注入**只遍历 `credential_schema`**、从不遍历"用户存了什么" ⇒
"模板里删掉的 key 不会被注入"**结构性成立**。这条让 §9.4 末尾那个"**只提示、绝不自动清理**"
（P0-2-3）与"注入正确"能**同时**成立 —— 不需要靠"清理过期值"来保证后者。
反面同样成立：用户填了、模板里没有的 key 也**绝不**注入（那正是 `PUT` 在写端就 400 的理由）。

**④ 注入端**必须再判一次**那三条判据，处置是"跳过 + 记账"而不是报错。**
读取端 `normalizeCredentialSchema` **刻意不跑语义层校验**（既不报错也不丢行 —— 丢了界面会凭空少一行，
而用户根本改不了那个事实）⇒ 库里**可能存着**"保留头名 / 非法头名 / 带 `&` `=` 的查询键 /
JSON-RPC 保留键"（P0-2-3 落地前的数据、手工改库的）。照注的三种后果**都比跳过更坏**：
占 `accept` ⇒ 顶掉响应形态协商头，症状**指向上游**；非法头名 / 头值带 CR/LF ⇒ `new Headers()` 直接抛；
撞 `method` / `id` ⇒ 毁报文，**甚至把凭据值原样回显到线上**（H3 实测）。
⇒ 跳过，并把 `{key, 注入位置, 理由}` 记进 `skipped` 回执（调用方打 `warn`）——
"这个参数没生效"于是变成**根因可见**的，而不是一句"调不动"。

**⑤ "没东西要注入"时一个字都不改。** 空注入 ⇒ `createCredentialFetch` **原样返回 baseFetch**
（同一个函数对象，不多套一层）；`applyQueryToUrl` / `applyBodyPatch` 在各自的输入为空时
**逐字返回入参**。理由：`new URL()` 往返会**规范化** URL（host 小写化、默认端口去掉…）⇒
"没注入任何东西的 server 的请求被悄悄改写"是最不该有的一类副作用（该节的两条判据各有一条断言盯着）。

**⑥ 未配齐 ⇒ 一个上游请求都不发。** `resolveMcpCallContext` 在 `new McpClient()` **之前**判
`missingRequiredCredentialKeys`（**按当前模板**逐 `required` 检查，**不是**"表里有没有行"），
缺任意一个 ⇒ **424 `NEED_CREDENTIAL`**，文案**点名缺哪几个 key**（上游 401 说不出这个）。
**解密失败走同一条路**（解不开的 key 不进 `values` ⇒ 若它是必填项，结论就是"需配置"）
⇒ 用户重填一次即自愈，**绝不 500**（同 §9.5 ②的降级口径）。
⚠️ 这里**只解一次**：`decryptCipherMap` 是解密循环的**唯一实现**，
§9.5 ② 的读路径与本节共用它。

**⑦ `secrets` 给的是"全部解密出来的明文"，不是"真的注出去的那几个"。**
它唯一用途是把**上游回显**里的凭据抹掉（上游 401 常把收到的 `Authorization` 原样回显）。
目的既然是"绝不让凭据进日志/错误消息"，那么**多抹一点是安全的、少抹一点是不可逆的** ——
`redactSecret` 自己会跳过过短的串，不会把正常文本误伤。被跳过的参数（④）**也在**这个数组里。

### 9.9 危险判定的口径（P0-2-9 落地 · ⚠️ **判定表本身就是契约**）

> 形状与判据的唯一实现：`backend/src/mcp/risk.ts`（纯函数 **`isDangerousTool(tool)`**；本模块只有一条
> `import type` ⇒ 真值表断言**不需要起任何依赖**）。判定结果由 `mcp/toolSchema.ts#toOpenAiTools` **算好**
> 挂在 `McpToolRoute.dangerous` 上 —— 编排层手上只有"模型回的工具名 + 那张映射表"，没有工具描述符，
> 现算就得再查一次库/缓存（多一次 round-trip + 一个"查到的那份与刚下发的那份不是同一份"的出错点）。
> 消费方是 **P0-2-10** 的确认流（`chatBot.ts` 工具循环里"取凭据 / 发 `RUNNING` 卡**之前**"那一处）。

**判定表**（只有 `readOnlyHint` / `destructiveHint` 参与，每个的取值域是 `{true, false, 缺失}`）：

| `readOnlyHint` | `destructiveHint` | 结论 | 理由 |
|---|---|---|---|
| 缺失 | 缺失 | **危险** | 保守：服务端**没说**它是只读的（MCP 里 `annotations` 是可选的 ⇒ 这是**常态**而非边角） |
| 缺失 | `false` | **危险** | `false` 只说"不是破坏性的"，推不出"只读"（可能是新增/追加） |
| 缺失 | `true` | **危险** | 明说破坏性 |
| `false` | 缺失 | **危险** | 明说"会写" |
| `false` | `false` | **危险** | 明说"会写、但不是破坏性的" —— **会写就够了**（保守） |
| `false` | `true` | **危险** | 明说"会写且破坏性" |
| `true` | 缺失 | **安全** | 服务端明确声明只读 |
| `true` | `false` | **安全** | 两个声明互相印证 |
| `true` | `true` | **危险** | **自相矛盾**的声明 ⇒ 保守取胜 |

等价的一句话判据：**`readOnlyHint === true` 且 `destructiveHint !== true` ⇒ 安全（直通）；
其余一切（含读不出注解）⇒ 危险（进 confirm）。**

**① ⚠️ `annotations` 是服务端"自报"的 —— 不是事实、也不可信。** 一个恶意（或只是粗糙）的 server
只要声明 `readOnlyHint: true`，它的删除操作就能绕过确认卡。**P0 的边界就到这里**（与 `01` 决策 22
"采用 tool annotations"一致）：平台侧"强制名单 / 按 `server + tool` 钉死的策略"属 **P1**。
⇒ 因此本机制做的事**不是**"识别危险工具"，而是"**在缺少可信信息时按危险处理**"。

**② ⚠️ 判定的输入是"这个工具"，不是"这个 server"。** 同一台 server 里既可能有只读查询、也可能有
删除操作（`06` P0-2-9 坑预判 2）⇒ 判定只能逐工具做。这也是结果挂在 `McpToolRoute`（**一行 = 一个工具**）
而不是 server 上的理由。

**③ ⚠️ `idempotentHint` / `openWorldHint` 刻意不进判定表**（规范里确实有它们）：
前者只说"同参数重复调用没有额外副作用"（**删两次**照样是破坏性的），后者只说"会与外部实体交互"
（一个只读的联网查询也是 `openWorldHint: true`）⇒ 两者都**推不出**"安全"，而本表的口径是
"拿不准就确认"。⇒ 对这两个 hint 本表是一条**显式的不变量**：它们取任何值都不改变结论。

**④ ⚠️ 严格 `=== true`，不做真值转换。** `"true"` / `1` / `"1"` / `{}` / `null` 一律按**缺失**处置
（契约里 `annotations` 是 `z.record(z.unknown())`，值可以是任何东西）。`Boolean(x)` / `x == true`
这类宽松写法会让一个**拼错类型的服务端**静默获得"只读"资格 —— 而症状正好是"确认卡该弹没弹"，
**唯一一种用户永远发现不了的故障**。

**⑤ 这个布尔**不是**"危险工具清单"。** 它返回 `true` 的含义是"**我们没有足够的可信信息放它过去**"，
不是"这个工具是破坏性的"。⇒ 界面上的"要不要提示"（P0-2-11）**不要复用**这一列（那是另一个判据）。

## 十、安全设计

| 项 | 方案 |
|----|------|
| 会话 | HttpOnly + SameSite=Lax Cookie + Redis 存储（登出即毁）；每请求校验 user.status（60s TTL 缓存），停用账号立即失效（实现口径见 §10.1） |
| 密码 | bcrypt(cost 12)；初始密码一次性展示 |
| 凭据/Provider Key | AES-256-GCM，主密钥仅环境变量注入 |
| HTML 产物预览 | 仅 sandbox iframe（无 script 权限）+ CSP，详见子方案④ |
| 文件下载 | 签名 URL + Content-Disposition: attachment |
| 沙箱 | **egress 白名单网络**（仅模型池出口；引擎须调 LLM，不能 network=none）、只读 rootfs、tmpfs 工作卷、mem/cpu 限额；需外网的工具走后端代理（P2 再议） |
| Docker socket | app 容器挂载 docker.sock 为**已知 trade-off**（等效宿主 root）；建议经 docker-socket-proxy 收敛暴露的 API 面 |
| 登录限速 | 同账号 5 次失败锁 10 分钟（Redis 计数键 `login-fail:{归一化用户名}`；第 6 次起 429 + `data.retryAfterSec`；**锁定判定在密码校验前**、**锁定后不再续期**、**登录成功即 DEL**；常量在 `infra/redis.ts` 的 `LOGIN_MAX_FAILURES`/`LOGIN_LOCK_TTL_SEC`，见 §4.1） |
| 越权 | 所有资源按 user_id/role 过滤；Agent 编删校验创建者（`(A)` 端点在路由层用 `requireAdmin`）；**admin 不能停用/降级/重置自己**（§4.2，防自锁） |
| 危险工具确认 | **由平台侧强制**（`01` 决策 22）：工具**没声明"只读"**（或声明了 `destructiveHint === true`）⇒ 走 confirm 卡，**不依赖 server 主动发起 elicitation**。⚠️ `annotations` 是**服务端自报、不可信** —— 声明 `readOnlyHint: true` 即可绕过确认 ⇒ **P0 的边界到此**，"平台强制名单 / 按 server+tool 的逐工具策略"属 **P1**。判定表见 §9.9 |

### 10.1 会话实现口径（P0-1-6 起落地）

> 实现：`backend/src/plugins/session.ts`（策略）+ `backend/src/infra/redis.ts`（存储原语）+ `backend/src/infra/crypto.ts`（密码与密文）。本小节只记**契约级**结论，代码注释里写"为什么"。

**Cookie**

| 项 | 取值 | 说明 |
|----|------|------|
| 名 | `doubulea_sid` | 常量，不做成环境变量（前后端各配一个名字会造成"登录成功仍显示未登录"） |
| 值 | 43 字符 base64url（32 字节 CSPRNG） | 会话令牌，**不签名** —— 身份真相在 Redis，签名不增加安全属性（详见 06 P0-1-6 落地要点 6） |
| 属性 | `HttpOnly` + `SameSite=Lax` + `Path=/` + `Max-Age=SESSION_TTL_HOURS` | 登出与登录必须用**同一份**选项，否则浏览器不覆盖旧 Cookie（症状：点了登出还是登录态） |
| `Secure` | 跟随 `SESSION_COOKIE_SECURE`，默认 = `NODE_ENV === 'production'` | 内网 HTTP 直连时必须显式置 `false`（否则浏览器丢弃 Cookie），生产置 false 会启动 WARN |

**Redis 键**

| 键 | 值 | TTL |
|----|----|-----|
| `session:{sid}` | `{userId, renewedAt}` | `SESSION_TTL_HOURS`（默认 12h）；**半衰期滑动续期**（已用掉一半才重写，避免每请求一次写） |
| `auth-user:{userId}` | `{id, username, role, status, mustChangePassword}`（**不含 `passwordHash`**） | `USER_STATUS_CACHE_TTL_SEC`（默认 60s） |

**失效语义（写侧责任）**：`user.status` 与角色变化**必须**由写侧调 `invalidateUserSnapshot(userId)` 主动失效缓存（P0-1-8 的启停 / 改角色 / 重置密码），否则最坏要等一个缓存窗口才生效；缓存只兜底"有人直接在库里改状态"的场景。该函数写失败**向上抛**（与"写缓存失败只告警"刻意相反）—— 失效是正确性要求，缓存只是性能优化。

**鉴权出口编码**（`requireAuth` 的四个结论，避免各处自行发明）：

| 情形 | 结果 |
|------|------|
| 无 Cookie | `401 UNAUTHORIZED`，**不访问 Redis**（匿名/探测请求不该打在依赖上） |
| 会话键不存在 / 已过期 / 用户已删 / `status=DISABLED` | `401`；**一律自毁**（删会话键 + 清 Cookie）；停用额外给出「账号已停用」文案 |
| 会话存储（Redis）不可用 | `500 INTERNAL` —— 依赖故障 ≠ 凭据不对；映射 401 会把在线用户全踢回登录页，运维也看不到 5xx |
| 已登录但非 ADMIN 访问 `(A)` 端点 | `403 FORBIDDEN` |

### 10.2 Provider Key 的存储口径（P0-1-10 起落地）

> 实现：`backend/src/services/model.service.ts`（唯一的读写点）+ `backend/src/infra/crypto.ts`（算法）。

| 项 | 取值 |
|----|------|
| 落库列 | `model_providers.api_key_enc`（`TEXT`，可为 `NULL` = 未配置） |
| 算法 | AES-256-GCM，密文形态 `v1.<iv:12B>.<tag:16B>.<ct>`，各段 base64url 无填充（§十） |
| AAD（附加认证数据） | `model-providers:{id}.api_key_enc` —— 由 `providerKeyAad()` 单点生成，写/读两侧共用 |
| 出口 | 只有 `hasKey` + `apiKeyPreview`（掩码）。**任何响应体都不含密文或明文** |

**三条要点**

1. **加密依赖 `id`，所以建 Provider 必须用事务**：`id` 由 Prisma 在 `create` 时按 `uuid(7)` 生成，
   而 AAD 里含 `id` —— 只能"先落一行拿 `id`，再用它加密写回"。若拆成两条独立语句，
   中间失败会留下"建好了但 Key 没写进去"的 Provider，而调用方看到失败会重试再建一个。
   PATCH 路径不需要事务（`id` 已知）。
2. **解密失败不掀桌**：主密钥换过/密文坏了时，`apiKeyPreview` 降级为 `****` 并留 warn，
   `hasKey` 仍为 `true` —— 语义准确（Key 还在，只是本进程解不开），且列表接口不会整页 500，
   管理员至少能看到"哪个 Provider 的 Key 坏了"。
3. **不要"防重解密"缓存**：`apiKeyPreview` 每次读都由服务端解密一次，成本可忽略（毫秒级），
   换来的是"读路径无副作用"（密文不会被读操作改写）与"换主密钥后立刻反映真实状态"。
   ⚠️ 反过来说：**PATCH 不传 `apiKey` 时必须一个字节都不写**，否则密文会被无谓重写
   （IV 变化 → 验收里"密文逐字不变"这条会失败）。

## 十二、部署形态

```
docker compose:
  app        （本后端 + 前端静态资源，单容器；挂 /var/run/docker.sock）
  postgres   （自建镜像：pgvector + pg_bigm；数据卷；pg_dump 定时备份 cron）
  redis      （数据卷；AOF everysec——重启不丢 session 与队列）
  minio      （数据卷）
  挂载卷：/models/bge-m3-int8（local embedding 模式时）
```

- app 容器需访问宿主 Docker daemon（沙箱调度）
- 网关/反向代理（如 nginx）：`proxy_read_timeout ≥ 120s` + `proxy_buffering off`（SSE 前提，配合 §五心跳）
- 无其他外部依赖；embedding 默认本地，纯内网可整体运行
- 升级：镜像替换 + Prisma migrate；回滚 = 回退镜像（schema 向前兼容一个版本）
