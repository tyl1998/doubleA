> 配套：`01-整体需求与实施步骤.md`（需求与决策基准）、`03-前端设计.md`。
> 技术结论：TypeScript / Node.js 单体。本文为自包含设计，不依赖任何既有系统。

## 一、技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| 运行时 | Node.js 22 + TypeScript 5 | 单语言栈；ACP 引擎适配器生态是 TS |
| Web 框架 | Fastify | 轻量、TS 原生、SSE/流式友好、插件体系够用不过度 |
| ORM | Prisma 7（Rust-free 客户端 + `@prisma/adapter-pg` 驱动适配器） | TS 生态最顺的 schema→类型链路；v7 起连接池改用底层 `pg`，与探活池同源，少一层黑盒（接入形态见 `06` §六 第 20 条） |
| 数据库 | PostgreSQL 16 + pgvector + pg_bigm | 业务数据 + 向量 + 中文全文一库承担（PG 内置 parser 不支持中文分词，以 bigram 补位；详见 §三/§十二） |
| 缓存/队列 | Redis 7 | 停止信号、会话、异步流水线队列（List/Stream） |
| 对象存储 | MinIO（S3 协议） | 原始文档 + 任务产物，文件不进库 |
| 容器调度 | dockerode（Docker SDK） | TaskAgent 沙箱生命周期 |
| MCP | 官方 TS SDK，协议 2025-06-18 | Streamable HTTP client、elicitation、OAuth 2.1 |
| LLM 接入 | OpenAI 兼容 client（自定义 baseURL） | 模型池全部走兼容协议，多 provider 零适配 |
| embedding | 双模式：onnxruntime-node（bge-m3 int8，默认）+ OpenAI 兼容 API | 配置切换，见第八节 |
| 文档解析 | unpdf（PDF）/ mammoth（**仅 docx**）/ 原生（md/txt） | .doc 不支持，上传时明确提示另存为 .docx |
| 校验 | Zod | 请求校验 + 共享类型 |
| 日志 | pino（结构化 JSON） | — |
| 工程形态 | pnpm monorepo（backend / frontend / shared） | DTO 一处定义前后端共用 |

## 二、架构总览

```
┌─────────────────────────────────────────────────────┐
│                  Fastify API 层                       │
│   路由 / 鉴权(Session) / Zod 校验 / SSE 出口          │
├─────────────────────────────────────────────────────┤
│                    服务层（领域）                      │
│  auth │ user │ model │ agent │ conversation │        │
│  knowledge │ mcp(+credentials) │ task │ file │ usage │
├─────────────────────────────────────────────────────┤
│                   编排层（核心）                       │
│  ChatBotOrchestrator：RAG 循环 + 工具调用循环          │
│  TaskAgentOrchestrator：沙箱管理 + ACP 桥接           │
│  SSE 归一化出口：两条链路 → 同一套事件                 │
├─────────────────────────────────────────────────────┤
│                  基础设施层                           │
│  LLMClient │ EmbeddingProvider │ MCPClient 池        │
│  DockerSandbox │ Pipeline Worker(文档流水线)          │
│  PG(Prisma) │ Redis │ S3 │ pino                     │
└─────────────────────────────────────────────────────┘
```

单体单进程；仅文档流水线 worker 作为**进程内异步任务**（Redis 队列驱动，不单独部署）。

流水线资源约束：并发上限 2（`PIPELINE_CONCURRENCY`），onnx 批量推理走 `worker_threads`，避免 CPU 密集任务（大 PDF 解析 / embedding 批量推理）阻塞在线请求；若仍出现明显争抢，演进路径为拆独立 worker 进程（Redis 队列协议不变）。

### 3.1 实现口径（P0-1-5 起，第一批 7 张表已落地）

> 已落地范围：`users` / `model_providers` / `models` / `agents` / `agent_components` /
> `conversations` / `messages`（见 `backend/prisma/schema.prisma` 与迁移 `0001_init`）。
> 其余表按 `06` 的批次顺序在 P0-1-14（知识库）与 P0-2/P0-3（MCP / 沙箱 / 产物）落地。

| 项 | 口径 | 理由 |
|----|------|------|
| 主键 | 一律 `uuid(7)`（Prisma `@default(uuid(7))` + `@db.Uuid`） | 时间有序 → 直接适配 `beforeId` 游标分页；不像自增键那样暴露业务量；不需要额外的分布式 id 方案 |
| 命名 | Prisma 侧 camelCase，库侧 snake_case（`@map`/`@@map`）；PG 枚举类型名亦 snake_case（`user_role` 等） | 与本节列名逐字对齐，`psql` 排查时不需心算转换 |
| 时间列 | `timestamptz(3)`；`created_at` 带 DB 默认 `CURRENT_TIMESTAMP`，`updated_at` 由 Prisma `@updatedAt` 维护（**无** DB 默认） | 分区按绝对时间切，必须带时区；毫秒精度足够，且与 JS `Date` 精度一致 |
| 外键删除 | `provider→models` 为 `CASCADE`（模型离开 provider 无意义）；`agents.model_id` / `agents.created_by` / `conversations.*` 为 `RESTRICT`（不允许被动消失）；`messages→conversations`、`agent_components→agents` 为 `CASCADE` | 「谁能带走谁」一次性写清楚，避免后续批次各自猜 |
| `agent_components.ref_id` | **多态外键，刻意不建 FK**（KNOWLEDGE→`knowledge_bases.id`，MCP→`mcp_servers.id`） | 一列不能同时指向两张表；引用完整性交服务层（`02` §4.4 的 PUT 全量替换），且两张目标表本批尚不存在 |
| `messages` 主键 | `(id, created_at)` 复合主键 | PG 硬性要求**分区键必须包含在主键/唯一约束内**。代价是 `findUnique` 要用复合键 `where: { id_createdAt: { id, createdAt } }`；业务上不亏 —— §4.5 的消息分页本来就带 `conversationId` 且按 `createdAt` 排序 |
| `messages` 索引 | `(conversation_id, created_at DESC)` 建在**父表**上一次 | 分区索引自动落每个分区，且**对后续 attach 的新分区同样生效**（已实测断言） |
| 分区窗口 | 迁移用 `ensure_messages_partition(月份)` 动态建「上个月 ~ 未来 12 个月」；续期脚本 `pnpm db:partitions`（幂等） | 写死日期会在窗口外用尽时让对话写不进去；向前留 1 个月覆盖数据回填/时钟偏差 |
| DEFAULT 分区 | **不建** | 它会把「新月份 attach 成正式分区」变成会失败的操作（分区约束被破坏时 PG 拒绝 attach，须停机搬数据），换来的是把"缺分区"从**立刻报错**（`no partition of relation "messages" found for row`）变成静默吞掉的假安全感 |
| `users.username` | 唯一但**大小写敏感** | 「登录时忽略大小写」由 P0-1-7 的服务层做归一（写入前统一小写），不引 `citext` 以免 Prisma 的 `@db.` 映射复杂化 |

分区说明：messages / usage_records 按月分区；**chunks 不分区**（分区表无法建全局 HNSW 索引，百万级以内单表 + HNSW 性能足够）。中文全文检索用 pg_bigm（bigram GIN，`LIKE '%词%'` 可走索引），不用 tsvector（PG 内置 parser 对中文无效）。换 embedding 模型的重建路径：新建 chunks_v2 → 流水线双写 → 切换检索指向 → 弃旧表（详见子方案①）。

> **`messages` 分区已落地（P0-1-5）**：`PARTITION BY RANGE (created_at)` + 复合主键 `(id, created_at)`，
> 分区由 `ensure_messages_partition(月份)` 动态建、由 `pnpm db:partitions` 续期，落地口径见 §3.1 表。
> Prisma 侧**照常当普通模型管理**（不启用 `experimental.externalTables`）—— 实测其内省能正确识别分区关系，
> `migrate dev` 不会重建该表，坑预判见 `06` §七 待决事项 1 的关闭记录。
> `usage_records` 到 P1 落地时按同一套路（分区键入主键 + 动态窗口 + 续期脚本）。

> **子方案①已完成**：`子方案/知识库流水线.md` 落实了本节的 DDL（含 `gin_bigm_ops` / HNSW 参数）、参数总表（chunk_size=512 **字符**、mode 三值枚举）、RRF 融合公式（k=60）、空文本检测阈值（50 字符）、覆盖重建"先删后建"语义与换模型重建五步路径。

## 四、API 设计

约定：`{ code, msg, data }` 包裹，`code=0` 成功（该格式适用于 JSON API，SSE 流与文件下载除外）；除登录外均需会话；`(A)` = 仅 ADMIN。列表分页：messages 用游标（`beforeId/limit`），其余列表 offset/limit（默认 20），小型选择器列表（模型/KB）可全量返回。

**错误出口的状态码（P0-1-4 定案）**：`code` 是唯一契约，HTTP 状态码是它的辅助信号，两条规则：

1. **领域错误**（`AppError`）→ 按 `shared/src/errors.ts` 的 `HTTP_STATUS_BY_ERROR_CODE` 出状态码（`VALIDATION`→400、`CONFLICT`→409、`NEED_CREDENTIAL`→424…）。
2. **框架错误**（Fastify 自己抛的）→ **保留其原始状态码**（415 不支持的媒体类型、413 请求体过大、408 超时…），只把 `code` 归类。把这些压成 400 会丢掉客户端的处理依据（前端要按 413 提示「文件太大」）。
   同时：**5xx 的原始 message 一律不透传**（可能是 SQL 片段/路径/堆栈），响应体只给通用文案，详情进日志（§十）。
3. **字段级明细**：校验失败时 `data.fields = [{path, message}]`，`path` 带请求部位前缀（`body.username` / `querystring.limit`），前端据此定位输入框。注意 Fastify 按 `params → body → querystring → headers` 顺序校验且**任一处失败即短路**，故一次响应只报得出第一处失败的部位。

**`/health` 的语义（P0-1-4 定案）**：

- **HTTP 恒 200**，依赖状态放在响应体里：`data.status ∈ {ok, degraded}` + `data.checks[]`（每项含
  `target / ok / latencyMs / detail`）。理由：探活端点自身是「请求成功」——它确实给出了结论；把某个
  依赖抖动直接映射成 5xx 会让网关/负载均衡把**整个后端**摘掉（本机只停 Redis 时后端其实还能服务大部分接口）。
  若将来上 k8s 需要 status code 形式的 readiness，另加 `/health/ready`（返 503）更清楚，不把两种语义塞进同一端点。
- 每项探活**必须带超时**（`HEALTH_TIMEOUT_MS`，默认 2s），单项失败只降级、不整体报错：
  `detail` 要能直接告诉运维「为什么」（如 `connect ECONNREFUSED 127.0.0.1:16379`）。
- 推荐运维口径：`jq '.data.status'` 判整体；`jq '.data.checks[] | select(.ok==false)'` 定位到具体依赖。

## 五、SSE 协议（前后端唯一契约，双链路归一化）

`POST /api/conversations/:id/chat`，请求体 `{ content, attachmentFileIds?[] }`，响应 `text/event-stream`。

### 5.1 事件全集

| event | data | 说明 |
|-------|------|------|
| `delta` | `{ text }` | 助手回答文本增量 |
| `thinking` | `{ text }` | 思考过程增量（可折叠渲染） |
| `tool_call` | `{ callId, toolName, serverName, kind: MCP\|SANDBOX, status: RUNNING\|SUCCESS\|ERROR, inputSummary, output? }` | 工具调用卡片；同一 callId 多次推送 = 状态机流转 |
| `confirm` | `{ confirmId, toolName, inputSummary }` | elicitation：前端弹确认卡，用户答复走 `/confirm` 接口，流挂起等待 |
| `citations` | `{ items: [{ docName, snippet, score }] }` | 本轮知识库引用 |
| `artifact` | `{ artifactId, fileName, size, mime }` | TaskAgent 产出文件 |
| `queued` | `{ position }` | 沙箱并发满，排队中 |
| `ping` | `{ ts }` | 心跳（每 15–25s 一次，空闲期保活）；前端静默忽略；防止排队/确认挂起/长任务静默期被网关断连 |
| `done` | `{ messageId, finishReason: COMPLETE\|STOPPED\|ERROR, usage: { tokensIn, tokensOut } }` | 流结束 |
| `error` | `{ code, message }` | 错误（流终止） |

### 5.2 语义规则

- **事件即真相**：前端渲染只依赖事件流；持久化由后端在 `done` 时整条落库（含 tool_calls/citations/artifacts 结构），历史拉取直接读库，**不做 SSE 重放**
- **会话互斥**：Redis 锁 `chat.active:{conversationId}`；持锁期间同一会话再次发送返回 `error{code: CONFLICT}`（防双标签页并发写乱历史）
- **心跳**：空闲期（排队/confirm 挂起/引擎长静默）每 15–25s 推送 `ping`；部署前提：网关 `proxy_read_timeout ≥ 120s` 且关闭响应缓冲
- **停止**：`stop` 写 Redis key `chat.stop:{conversationId}`（TTL 60s），编排循环每个可中断点检查；中断后推送 `done{finishReason: STOPPED}`
- **confirm 挂起**：确认等待上限 120s，超时按取消处理
- **断线**：前端断线重连后先查 `/api/conversations/:id/active` 获取进度（在流/排队位次/当前工具），再调消息历史接口补齐（事件流不重放；历史不含进行中消息，进行中状态由 active 提供）
- **两条链路同构**：ChatBot 的 MCP 工具与 TaskAgent 的沙箱工具（bash/read/write 等）都映射为 `tool_call`（`kind` 区分）；引擎侧事件在编排层完成映射（详见子方案③）

## 六、ChatBot 编排（编排器一）

```
入口：POST /chat（已建会话，type=CHATBOT）
 1. 并发闸：信号量（上限 50），满则 error{code: BUSY}；会话级互斥锁见 §5.2
 2. 组装上下文：
    system = agent.system_prompt
           + 检索块（绑定 KB 逐库混合检索：pg_bigm 全文 + 向量，RRF 融合，取 topK，
             拼"来源：文档名"前缀）
    history = 最近 20 轮 messages（含工具调用结构化还原）
    user    = content + 附件（图片→多模态 part；文本→解析后注入）
 3. LLM 流式调用（OpenAI 兼容，stream=true）
    → delta / thinking 持续透传
 4. 工具循环：LLM 返回 tool_call 时
    a. 该工具属于某 MCP server？
       - 危险判定：tool annotations 的 destructiveHint=true（或 readOnlyHint 缺失）
         → 平台强制走 confirm 流（不依赖 server 主动发起 elicitation）
       - 取当前用户凭据 → 注入（无凭据 → tool_call{ERROR, 需配置}）
       - elicitation 请求 → confirm 事件挂起 → /confirm 应答
         （P0 仅实现确认/取消二元语义，不做自由输入表单）
       - 执行 → tool_call{SUCCESS/ERROR} → 结果回填 LLM → 续流
    b. 循环上限 10 轮（防失控）
 5. done：整条消息落库 + usage_records 计量
```

## 七、TaskAgent 编排（编排器二，概要）

```
入口：POST /chat（type=TASK_AGENT）
 1. 沙箱获取：并发上限 10，满则 queued 排队（Redis 队列）
 2. 会话容器：dockerode 创建（镜像预构建：ACP 引擎 + 运行时）
    挂临时工作卷；网络为 **egress 白名单**（独立 bridge，仅放行模型池 baseURL 出口，
    iptables/代理实现——引擎运行必须调 LLM API，不能 network=none）；
    只读 rootfs、资源限额
 2.5 LLM 注入：agent.model_id → 解析 provider → 后端解密 API Key
    → 容器环境变量注入。Key 进入容器环境为已知暴露面：容器单会话独占 +
    无其他网络出口 + 会话结束即回收，风险可接受（详见子方案③）
 3. ACP 桥接：stdin/stdout JSON-RPC → 事件映射
    引擎 tool 事件  → tool_call{kind: SANDBOX}
    文件写入        → 结束时工作卷扫描 → artifact 事件
    引擎输出增量    → delta / thinking
    计量            → 引擎事件若携带 usage/成本信息则透传计量；
                      无则 usage_records 记条目（token 字段为空，按时长+轮次）
 4. 空闲 30min 回收；stop 信号 → 引擎中断 + 容器回收
```

细节（容器规格、镜像构建、ACP 事件映射表、产物扫描规则）见 `子方案/沙箱与引擎集成.md`。

## 九、MCP 用户级凭据（核心定制点）

### 9.1 注册（注册者定义模板）

```json
// POST /api/mcp/servers
{
  "name": "内部工单平台",
  "endpointUrl": "https://ticket.internal/mcp",
  "authType": "NONE",
  "credentialSchema": [
    { "key": "X-User-Token", "label": "个人令牌",
      "type": "string", "inject": "HEADER" }      // HEADER | QUERY | BODY
  ]
}
```

### 9.2 用户填值（每用户一份）

```
PUT /api/mcp/credentials/:serverId
{ "values": { "X-User-Token": "我的token" } }
→ AES-256-GCM 加密后存 mcp_credentials（密钥来自环境变量）
```

### 9.3 调用时注入

```
编排器发起工具调用 → 取 (server, currentUser) 凭据
  ├─ 有：解密 → 按 inject 位置注入请求头/参数 → 执行
  └─ 无：tool_call{ERROR: "需先配置凭据"} → 前端卡片带"去配置"跳转
```

**不变式**：凭据只在后端解密，永不下发前端；A 用户会话绝不使用 B 用户凭据。

**inputSchema → OpenAI function 转换**：MCP tool 的 `inputSchema`（JSON Schema）直接映射为 function 参数 schema；工具名冲突时加前缀 `mcp_{serverSlug}_{toolName}`；转换逻辑集中在 MCPClient 层。

## 十、安全设计

| 项 | 方案 |
|----|------|
| 会话 | HttpOnly + SameSite=Lax Cookie + Redis 存储（登出即毁）；每请求校验 user.status（60s TTL 缓存），停用账号立即失效 |
| 密码 | bcrypt(cost 12)；初始密码一次性展示 |
| 凭据/Provider Key | AES-256-GCM，主密钥仅环境变量注入 |
| HTML 产物预览 | 仅 sandbox iframe（无 script 权限）+ CSP，详见子方案④ |
| 文件下载 | 签名 URL + Content-Disposition: attachment |
| 沙箱 | **egress 白名单网络**（仅模型池出口；引擎须调 LLM，不能 network=none）、只读 rootfs、tmpfs 工作卷、mem/cpu 限额；需外网的工具走后端代理（P2 再议） |
| Docker socket | app 容器挂载 docker.sock 为**已知 trade-off**（等效宿主 root）；建议经 docker-socket-proxy 收敛暴露的 API 面 |
| 登录限速 | 同账号 5 次失败锁 10 分钟（Redis 计数） |
| 越权 | 所有资源按 user_id/role 过滤；Agent 编删校验创建者 |

## 十二、部署形态

```
docker compose:
  app        （本后端 + 前端静态资源，单容器；挂 /var/run/docker.sock）
  postgres   （自建镜像：pgvector + pg_bigm；数据卷；pg_dump 定时备份 cron）
  redis      （数据卷；AOF everysec——重启不丢 session 与队列）
  minio      （数据卷）
  挂载卷：/models/bge-m3-int8（local embedding 模式时）
```

- app 容器需访问宿主 Docker daemon（沙箱调度）
- 网关/反向代理（如 nginx）：`proxy_read_timeout ≥ 120s` + `proxy_buffering off`（SSE 前提，配合 §五心跳）
- 无其他外部依赖；embedding 默认本地，纯内网可整体运行
- 升级：镜像替换 + Prisma migrate；回滚 = 回退镜像（schema 向前兼容一个版本）
