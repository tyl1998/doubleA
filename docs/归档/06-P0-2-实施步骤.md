  **翻译成本仓的错误码 + 脱敏**（`backend/src/mcp/errors.ts`，与 `llm/upstream.ts` 同一层职责）。
  **这一层不认识数据库、不认识用户**（凭据经 `headers` 注入，解密与组装是 P0-2-7 的事）。

  ⚠️ **`toolSchema.ts` 不属本批**（`toOpenAiTools` 与工具名 token 化是 **P0-2-6** 的产出）：本批只把工具
  **原样**投影成 `McpToolDescriptor`，`inputSchema` 一个字都不动。
- **前置**：P0-1-38
- **验收门槛**（✅ 逐条有据，取证在 `verify:mcp-client` 的 A~G 组）：
  1. ✅ 握手成功时**记下协商后的协议版本**（≠ 我们请求的版本时**不报错但要留痕**，日志 + `client.protocolVersion` 双出口），
     工具列表形状正确（`name`/`description`/`inputSchema`/`annotations` 四键恒定存在，**缺失一律 `null`**）；
  2. ✅ `tools/call` 三种结果都能区分：**成功**（`content` 文本块，`isError:false`）/ **工具自身报错**（`isError:true`，**不是**传输失败，**不抛**）/ **传输失败**（超时/断连/非 2xx，**抛**）；
  3. ✅ **超时**（注入 500ms）在 2s 内返回且错误码是 `UPSTREAM_TIMEOUT`；**中断**（`AbortSignal`）实测 **151ms** 就停手（抛 `McpAbortError`，**不带**业务错误码）；
  4. ✅ **连不通要快失败**：DNS 失败（`ENOTFOUND`）/ 连接被拒（`ECONNREFUSED`）/ 非 MCP 端点（回 HTML）
     三种都给出可读原因（**不是**一句 `fetch failed`），且上游回显凭据时**消息里也没有凭据**（`sk-live-…` 被抹成 `****`）；
  5. ✅ **假上游侧取证**：握手请求带 `initialize`、`Accept` 同时含 `application/json` 与 `text/event-stream`、
     首包**不带** `mcp-protocol-version` 而协商后每条都带。
     ⚠️ **头名订正**：设计原文写的是 `MCP-Protocol-Version`，SDK 实际发的是**全小写** `mcp-protocol-version`
     （`_commonHeaders()`）—— 按实现口径记档，别照文档去断言大写形式。
- **坑预判（设计期识别；本批逐条证实/证伪）**：
  1. ✅ **证实**：Streamable HTTP 可能"回 JSON"也可能"回 SSE 流"（同一条 POST，服务端按 `Accept` 自选）⇒
     夹具**两种都能切**（`setResponseMode`），且 C 组对**两种形态各跑一遍**（C6 走 JSON、C5 走 SSE，
     连 `initialize`/`tools/list`/`tools/call` 三条都在各自的形态下记账）。
  2. ✅ **证实且更糟**：**会话是有状态的**。`initialize` 响应回 `Mcp-Session-Id`，后续每条都要带；
     不带的时服务端按规范回 **404** —— 而 404 与"路径写错"**同码**，`errors.ts` 的默认提示会把人
     引向 `endpoint_url`。⇒ 处置有两条：连接封装把 session id 收在传输层自己手里（`McpClient` 只暴露只读 getter），
     以及 **404 分支里加一条判据**（响应体提到 session ⇒ 改口说"多半是会话丢了"）—— 这条能加出来，
     正是因为夹具**回显了自己拒掉的那个 session id**。`close()` **先 `DELETE` 终止会话、再关传输**
     （`Client.close()` 自己不终止会话，不改的话服务端累积僵尸会话且我们零症状）。
  3. ✅ **证实**：协商后的版本**不等于**请求的版本。本批把它做成"**记下来但不用它做分支**"：
     `client.protocolVersion` 只服务日志与"恢复会话时补头"，没有任何 if/else 依赖它。
  4. ✅ **证实并改用 SDK 的能力**：SDK **自带** `RequestOptions.timeout`（超时抛 `McpError(-32001)`）
     ⇒ 我们**不再自建看门狗**，`AbortSignal` 只用于用户停止（P0-1-12 的"两个控制器"坑在本层结构性不成立）。
     ⚠️ 但实测发现一个**新坑**：SDK 的 `cancel()` 会把任意中断原因**包装成 `McpError(RequestTimeout)`**
     ⇒ "用户停止"和"真超时"**不能靠错误码区分**，必须由调用点把 `signal.aborted` 传下来。
  5. ✅ **证实**：出口一律显式投影（`McpToolDescriptor` / `McpToolResult`），SDK 对象一个都不外泄。
  6. ✅ **证实**：ESM-only —— 类型导入全用 `import type`，相对导入带 `.js`；
     `tsx` 直跑源码与 `tsc` 出 `dist` 两种形态**都真跑过**（后者就是 `verify:mcp-client` 的跑法）。
     另记一条：**`registerCapabilities()` 在 connect 之后调用会抛** ⇒ 能力声明只能在构造函数里做。
- **三条最值得记的落地要点**：
  1. **能力声明只在真有应答方时做**：传了 `onElicit` 才 `registerCapabilities({ elicitation: {} })`。
     声明了却答不出来，服务端会照发请求、我们静默失败 —— 比不声明**更难查**（E1 专门守这条）。
  2. **恢复会话要连带版本头**：跳过握手就没人告诉你协商结果，而规范要求后续每条都带
     `mcp-protocol-version`。`McpClientOptions.protocolVersion` 就是给这条用的（A5 取证：恢复不重发 `initialize`）。
  3. **本档不需要 PG / Redis**：客户端层不认识数据库 ⇒ `verify:mcp-client` 是本仓**第一档"只要 dist + `infra/.env`"**
     的第四档验收（`verify-llm` / `verify-chatbot` 那几档都必须起真库）。
- **取证方式**：第四档 —— 在本进程内起**假 MCP server**（`http.createServer` + 端口 0，记
  method/path/五个关键头/body），不用 `app.inject`、不连任何真 MCP 服务。
  ⚠️ 口径：**夹具假上游**档 ⇒ 只证明"契约与配置接对了"，**不等于**"真 MCP 服务那边一定对"。

#### P0-2-2 Server 注册 CRUD + 连通测试  `[✓]` 2026-09-24
- **内容**：`shared/src/mcp.ts`（server 的四段 schema + `McpServerItem` 投影）、
  `backend/src/services/mcpServer.service.ts`（列表 / 建 / 改 / 删 / **测试连通** / 工具列表读侧）、
  `backend/src/routes/mcpServers.ts`（六条路由，**只挂 `requireAuth`**）、`app.ts` 接线。
- **产出**：上述 + `backend/scripts/verify-mcp-servers.mjs`（新增档 `verify:mcp-servers`）、
  `verify-app.mjs` 新增一段（路由表 + 投影 + `credential_schema` 校验）。
- **前置**：P0-2-1
- **验收门槛**：
  1. **MEMBER 能建/能改/能删/能测**（**全员可注册**）—— 守门断言**必须用 MEMBER 跑通**，并用
     "能不能删掉**别人建的** server"做反向守卫（**能** —— 无 owner 收窄，这是刻意的，与 Agent 第三族相反）；
  2. `POST /:id/test` **恒 200** + `{ok:true, tools:[…]}` / `{ok:false, error:"…"}`，且**测试成功时顺手刷新 `tool_cache`**；
  3. 删除**被 Agent 绑定**的 server ⇒ **409**（判据 = 数 `agent_components`，与 P0-1-15 的删库守卫**同一处逻辑、同一段文案口径**）；
  4. 注册接口**不强制连通**：上游不通也允许注册成功（之后可以点测试）—— 理由见坑预判 2；
  5. `endpoint_url` 只接受 `http`/`https`（其它协议 400）；空串/超长 400；`created_by` 是**留痕**（不参与权限）。
- **坑预判**：
  1. ⚠️ **`endpoint_url` 是一个 SSRF 面**：**全员可注册 ⇒ 任何登录用户都能让后端去连任意地址**
     （打内网、探端口、读云元数据）。P0 的处置是**显式记为已知边界**（只校验 scheme + 在文档/README 写明），
     真正的防护（denylist / 出站代理 / 白名单）**属 P1**。⚠️ 这条**必须写进文档**，否则它是一条没人知道的洞。
  2. ⚠️ **"注册时连通测试"不能做成硬门槛**：`01` §3.6 的验收要点写的是"注册时连通测试"，但把它做成
     **注册前置**会让"上游临时抖动"变成"建不了 server"（用户没有别的入口），且**测试用谁的凭据**这个问题无解
     （刚注册时还没有人有凭据）⇒ 定案：**注册成功 + 响应带一次测试结果（best-effort）**，
     独立端点 `POST /:id/test` 才是正式入口。
  3. **注册信息变更要让工具缓存失效**（`endpoint_url` / `credential_schema` / `auth_type` 任一变）——
     漏了的症状是"改了 endpoint，工具列表还是旧 server 的"，**纯静默**。
  4. 与 P0-1-23 的接回点：**`assertComponentRefsBindable` 里的 `MCP` 分支**要从"一律 400"换成
     "查 `mcp_servers` 存在性"（**接口形态不变**）。⚠️ **同步要翻转 P0-1 留下的对偶断言**
     （`verify:agents` / `verify:agent-package` 里"含 MCP ⇒ 400 且文案指向 P0-2"）—— 这是
     §七"刻意未注册型断言的保质期"的第 N 次应用，**只有全量回归能抓到它**。
- **取证方式**：第二档（真 PG + Redis）+ 第四档（假 MCP server 提供 `tools/list`）；
  浏览器/curl 可跑路径进 `README`（**P0-2 的第一个命令行里程碑**）。
- **六条最值得记的落地要点**：
  1. **信封形态定为"第五族"，且与 P0-1 各族的差别要能一眼看出来**：列表 `{items,total,offset,limit}`、
     `PATCH` 是**裸 item**、`DELETE` 回 `{id,name}`、`GET /:id/tools` 是**裸 `{tools,fetchedAt,cached}`**、
     `POST /:id/test` **恒 200**。唯一"新"的一条是注册响应 **`{server,test}`**：
     `01` §3.6 的「注册时连通测试」既不能做成注册前置（坑预判 2），也不能做成"裸 item 多一个键"
     （同一份数据两种形状 = 前端两套渲染分支，P0-1-21 的教训）⇒ 拆成一个显式的复合响应，
     **`McpServerItem` 仍是全端点唯一形状**。⚠️ `oauthConfig`（P1）与**完整 `toolCache`** 刻意不进投影：
     前者恒 `null` 只会诱使前端写死分支，后者会让一次翻页变成几百 KB（列表页要的只是 `toolCount`）。
  2. ⚠️ **`tool_cache` 的失效判据是"真的变了"，不是"提交里带了"** —— 而这两者之间的缝隙
     **由 PG 的 jsonb 行为撑开**：PG 会把 jsonb 的键**按"长度 + 字节"重排**，于是"把库里读出来的
     模板原样提交回去"也会被逐字比较判成"变了" ⇒ 用户**每次保存都白清一次缓存**（工具数莫名归零，
     而且他会以为是那个 server 有问题）。故比较必须**键序无关**（`sameJson`，P0-1-27 `canonicalJson`
     的服务层版本 —— 那边比出假红，这边比出假阳性）。验收 F6 的第一条断言专门先证明
     "PG 确实重排了键"，否则那条"原样提交不清缓存"是**空转**的。
  3. **"清缓存"与"不清缓存"各有一半，且两条都是静默故障**：`endpointUrl` / `authType` /
     `credentialSchema` 变了 ⇒ **必须清**（漏了 = "改了 endpoint，工具列表还是旧 server 的"，界面上
     那个数字看着完全正常）；**只改 `name` ⇒ 不许清**（清了只会让用户白等一次重拉；`name` 不参与连通）。
     同理 **`POST /:id/test` 失败时只写 `status=ERROR`、`tool_cache` 一字不动** —— 上游抖一下就把
     上一次成功拉到的工具列表清空，是"用户明明还能用却被我们清没了"的最坏形态。
  4. **Prisma 对可空 jsonb 列要求显式区分"没有值"与"值是 jsonb null"**：清缓存必须写
     `Prisma.DbNull`（SQL `NULL`），写裸 `null` 会被类型系统拒绝（`TS2322`）。为此
     `backend/src/infra/prisma.ts` 把 `Prisma` 从**类型转发**改成**运行期转发**（业务代码仍然只 import
     本模块的约定不变）；读侧的判据随之定为 `parseToolCache(raw) === null ⇒ 没有缓存`。
     另有一条同类的读侧纪律：`tool_cache` 的坏数据**整体作废**、而 `credential_schema` 的坏条目
     **逐条过滤** —— 前者是"一次上游响应的快照"（留半份 = 模型能调到的工具少了几个，看不出来），
     后者要**下发给前端渲染表单**（丢一条比整个表单消失好）。**同一份 jsonb 两种降级策略**，
     差别写在两处的注释里，别互相照抄。
  5. **`slug` 是"创建时派生、之后不再变"**（它要进工具名前缀 `mcp_{slug}_{tool}`，P0-2-6）⇒
     `PATCH` 的契约里**根本没有这个字段**（传了会被 zod 静默剥掉，只剩它时等于"没改任何字段"⇒400）。
     派生函数是**纯函数**（`verify:app` 无需依赖即可断言），唯一性只是 **best-effort**、
     `slug` 列**刻意不加唯一约束**（并发的同名注册不该有一个 500）；`uniqueSlug` 加序号时会
     **先截短 base** —— 直接 `slice(0,32)` 会把 `-2` 截掉，两个 slug 又撞在一起。已知代价：
     **纯中文名会整串折成空串**、回落到 `server`，于是"验证 MCP-一号-x""验证 MCP-二号-x"这类名字
     **共用同一族 slug**（靠序号区分）—— 这是"slug 只认 ASCII（工具名限制）"的直接推论，
     验收 F1 因此换用专属的 ASCII 名字族，否则那条断言会依赖"前面跑过几条用例"。
  6. **接回 P0-1-23 的 `MCP` 分支，并同步翻转两处对偶断言**（坑预判 4 的落地）：
     `assertComponentRefsBindable` 从"一律 400 + 文案指向 P0-2"换成**存在性校验**
     （`NOT_FOUND` 404 + 文案带 id，接口形态不变）；`verify:agents` 与 `verify:agent-package` 里那两条
     "含 MCP ⇒ 400"的断言**同批翻转**，并**各补一条正面用例**（绑一个真实存在的 server ⇒ 200；
     解绑 ⇒ 详情立即只剩知识库那条）—— 只翻一半的话，"服务层把 MCP 一律 404"也能全绿。
     ⚠️ 这是 §七"刻意未注册型断言的保质期"的第 N 次发作（本批**又一次**证明：它只会被全量回归抓到）。
     同批还顺带修了一处**更早的历史欠账**：`verify:app` 里的 Provider 投影夹具停在 P0-1-37 之前
     （没有 `protocol`），"shared Provider 输出形态"那条**一直红着而没人看见**。
- **坑预判逐条落实**：① SSRF **只按"已知边界"处理**（校验 scheme + 写进 `02` §4.7 与 README），
  真正的防护属 P1；② 注册**不强制连通**（响应带 best-effort 的 `test`，探测失败只影响 `status`）；
  ③ 注册信息变更清缓存（见要点 2/3）；④ 接回点与对偶断言翻转（见要点 6）。
- **⚠️ 新增一条已知边界（本批实测）**：想造一个"连接被拒绝"的端点**不能用 `127.0.0.1:1`** ——
  端口 1 在 fetch 规范里属 **bad port**，undici 在**发包之前**就拒掉（原因链 `fetch failed ← bad port`），
  于是走不到 TCP、验不到「连接被拒绝」的翻译。正确做法是"起一个假 server 拿到端口再立刻关掉"。
  这条只影响验收脚本的夹具构造（已改），**不影响产品代码**；但它是"为什么必须真跑一遍"的又一个例子。

#### P0-2-3 凭据参数模板（`credential_schema`）  `[✓]` 2026-09-24
- **内容**：`credential_schema` 的契约与校验：`[{ key, label, type:'string', inject∈{HEADER,QUERY,BODY}, required?, placeholder? }]`；
  纯函数 `validateCredentialSchema`（key 合法性**按注入位置分**：HEADER 必须是合法头部名、QUERY 不能含 `&`/`=`）；
  纯函数 `diffCredentialSchema(old, new)`（算出"被移除/被新增/被改注入位置"的 key）；
  `PATCH /api/mcp/servers/:id` 的响应里带 `credentialSchemaImpact`（**只提示，不删任何已存凭据**）。
- **产出**：`shared/src/mcp.ts` 的 schema + **三个纯函数**（`validateCredentialSchema` / `diffCredentialSchema` /
  `credentialSchemaImpactOf`）+ `updateMcpServerResultSchema`；`mcpServer.service.ts` 的 `updateMcpServer`
  改为返回 `{server, credentialSchemaImpact}`；`verify-app.mjs` 新增"凭据模板契约"整段、
  `verify-mcp-servers.mjs` 新增 H 组、`verify-mcp-client.mjs` 新增 H 组（**BODY 注入的协议线探针**）。
- **前置**：P0-2-2
- **验收门槛**：
  1. 非法 `inject` 值 400；**同一模板内 `key` 重复 ⇒ 400 且字段级 `path` 指到 `['credentialSchema', 1, 'key']`**
     （`superRefine` + `addIssue({path})`，P0-1-23 的手法；`.refine()` 给不出 path）；
  2. HEADER 的 key 含空格/冒号 ⇒ 400；QUERY 的 key 含 `&`/`=` ⇒ 400；BODY 的 key 接受任意（但不得与 JSON-RPC 顶层键冲突，见坑预判 1）；
  3. 模板删掉一个 key 后再 PATCH ⇒ 响应含"**N 条已存凭据含已移除的参数**"的提示，且**库里那些凭据一字未动**（取证：`updated_at` 与密文逐字不变）。
- **坑预判**：
  1. ⚠️ **`inject: 'BODY'` 与 JSON-RPC 报文天然冲突** —— MCP 的一次 `tools/call` 的 body 是
     `{ jsonrpc, id, method, params }`，凭据能去的只有**顶层**（`params` 里是工具自己的入参，塞进去会污染工具参数）。
     但"顶层额外字段"**服务端认不认**取决于它的实现 ⇒ **必须先做探针**（假 MCP server 先按两种假设各接一次，
     看哪种真能读到），把结论写进 `02` §九。**这类冲突与 P0-1-19 的"文档 DDL 与不变式冲突"同源：
     先证伪再落笔，别按文档字面实现。**
  2. ⚠️ **模板变更的提示不能变成自动清理** —— 自动删掉"已移除 key"的值会让"用户临时改错模板"变成
     **不可逆的数据丢失**（用户没做任何操作，凭据没了）。⇒ **只提示**；真要清理由用户在凭据页自己点。
  3. **`type` 只支持 `string`**（`02` §九 原文如此）：P0 不做 number/boolean/file，写清接回点
     （在 `credentialValueSchema` 上按 `type` 分支即可，不影响别处）。
  4. 模板的**顺序即界面顺序**（数组，不是对象）：刻意保留顺序，因为界面按它排版；
     而"判等/比较"必须**按 key 集合**（改顺序不算改动 —— P0-1-23 第 ④ 条同源）。
- **取证方式**：三档一起 —— ① **无依赖**（`verify:app` **129 → 135 项**，新增"凭据模板契约"6 条，
  验字段级 `path`、数组级 `path`、独立入口、两个纯函数、响应形状）；② **第二档（真 PG + Redis）**
  （`verify:mcp-servers` **31 → 36 项**，新增 H 组 5 条）；③ **第四档（真 HTTP 假上游）**
  （`verify:mcp-client` **34 → 38 项**，新增 H 组 4 条 = BODY 注入的协议线探针）。
  ⚠️ 上游仍是**本仓夹具**（`fixtures/mcp-upstream.mjs`）⇒ 只证"契约与配置接对了"，
  **不等于**"真 MCP 服务那边一定对"。
- **六条最值得记的落地要点**：
  1. **"形状"与"语义"分两层，但两层只留一份实现**：形状（键齐不齐、长度、取值域）留在
     `credentialSchemaEntrySchema`；语义（`key` **按注入位置分判** + 同模板内判重）收进
     `credentialSchemaDeepIssues()` —— `credentialSchemaSchema` 的 `superRefine` 与**独立入口**
     `validateCredentialSchema` **都调它**（"同一口径两处各写一遍必有一处先腐烂"，即断言形态 ⑰）。
     独立入口存在的理由：调用方手里可能**只有一份 `unknown`**（从 jsonb 读出来的、将来别的非 HTTP 入口），
     不该被迫走 zod 上下文 ⇒ 那条路上要**自己两样都做**（形状 + 语义）；而 `superRefine` 那条路
     **只补语义**（形状由逐条 schema 与 `.max()` 报）—— 报两遍会让前端看到两行一模一样的红字。
     ⚠️ 判重是**跨行**的 ⇒ `superRefine` 必须挂在**数组**上（逐条 refine 看不到别的行）；过滤掉形状错的行
     之后**下标就没了** ⇒ 因此要显式带上原始 `index` 再传给语义层，否则字段级 `path` 会指到错误的行。
  2. ⚠️ **三条规则都属于"形状合法、注入出去一定出错"，所以必须在模板落地的那一刻拦**（这类错在模板层
     都不报，要等到调用时，甚至只表现为"凭据没生效"）：`HEADER` ⇒ 合法头名（RFC 7230 的 `token`
     **正则**，而不是"不含空白"这种粗略判据 —— `X-User Token` 与 `X-User:Token` 会被 fetch/undici
     直接拒绝或更糟地静默截断）+ **不得占用平台自己要发的头**；`QUERY` ⇒ 不含 `&`/`=`；
     `BODY` ⇒ 不得是 JSON-RPC 的保留键。⚠️ 占用 `accept` 的后果**最隐蔽**：注入会覆盖掉平台用来谈
     **响应形态**（回 JSON 还是回 SSE）的那个头，症状是"这个 server 的凭据一配上、工具就调不动了"，
     而报错指向上游（P0-2-7 坑预判 1）。
  3. ⚠️ **BODY 注入能不能做是探针问出来的，不是文档给的**（坑预判 1 的兑现，`verify:mcp-client` H 组）：
     ① **非保留的顶层额外字段能到达服务端、且完全不影响这次调用**（H1）⇒ BODY 注入**在协议线上可行**；
     ② 塞进 `params.arguments` 会**污染工具入参**（夹具把凭据一起回显了）、塞成 `params` 的兄弟键则
     **凭据等于白注**（H2）⇒ 这两条路都不可用；③ 与 `jsonrpc`/`id`/`method`/`params` **撞名会改掉报文语义**
     —— 撞 `method` ⇒ 这次调用变成另一次调用、撞 `params` ⇒ 工具名丢了服务端回 `-32602`、
     撞 `id` ⇒ 响应 id 被顶成凭据值并**把它回显到线上**（H3）⇒ 这四条必须在模板层拒掉。
     **结论已回写 `02` §九**。
  4. ⚠️ **"拿什么去注入"也在同一组里问了**（H4）：真 SDK 路径下 `StreamableHTTPClientTransport` 的
     **`fetch` 选项**能同时改 URL / 请求头 / 报文体 ⇒ **三种注入位置一个口子全包**，不必改 SDK、
     也不必为 BODY 单独造一条旁路。**`McpClient` 目前还没把这个选项透出来 —— 那就是 P0-2-7 的接回点**
     （加一个可选参数即可，客户端层不用重构）。这条比"到 P0-2-7 才发现接不上"便宜得多。
  5. ⚠️ **"缓存该不该清"与"该提示什么"是刻意分离的两个判据**（同一份输入得出**不同**结论是对的）：
     缓存用 `sameJson` 判"**模板整体**变没变"（**连 `label` 改了也清**）；`credentialSchemaImpact`
     用 `diffCredentialSchema` 判"**已存凭据会受什么影响**"（只有 key 级的**增 / 删 / 换注入位置**才算，
     只改 `label` ⇒ `null`）。合并它们会得到两种坏结果之一："改了个文案就弹一串无意义警告"，
     或者"清了缓存却什么都没提示"。`diffCredentialSchema` 自身另带两条口径：**只按 key 判**
     （`label`/`required`/`placeholder` 都不算改动）、**顺序不算改动**（P0-1-23 第 ④ 条同源）。
     验收 H2 就是**守这两个判据不合并**的那条（同一份输入、两个结论）。
  6. **`affectedCredentials` 本批刻意留白（恒 `null`），而 `null` 在这份契约里只有一个含义**：
     `null` = "本次没有任何需要提示的影响"（既包括**没提交模板**，也包括**提交了一份与当前等价的模板**）。
     ⚠️ 不填 `0` —— 那是"没有凭据受影响"这个**此刻无法作出的断言**（凭据表属 P0-2-4，后端根本没能力
     回答），编一个数字会被当成契约（P0-1-34/35 第 ⑦ 条"**给不出数字时宁可留白**"同源）。
     ⚠️ **接回点**：`verify:mcp-servers` 的 H1 里有一条**守着"它现在必须是 `null`"** 的断言，
     P0-2-4 建表后**翻转**它并换成真数（数 `values` 里含 `removedKeys` 的行）。
  7. **同一个东西的"读端"与"写端"是两个入口，职责不同、别互相替代**：写端闸门 = `credentialSchemaSchema`
     （zod，自带字段级 `path`）与 `validateCredentialSchema`（永不抛错的独立入口，适合非 HTTP 入口）；
     读端 = `normalizeCredentialSchema`（**逐条过滤、只求"能渲染"**）。⚠️ 读端**刻意不跑语义校验**：
     库里已存着"key 是个保留头名"的数据也照样要下发 —— 否则用户的表单会凭空少一行，而**那个事实他改不了**
     （与 P0-2-2 落下的"同一份 jsonb 两种降级策略"是同一条纪律的第二次应用）。
     **⚠️ 本批唯一一次契约变更要留痕**：`PATCH` 的响应从**裸 item** 变成 `{server, credentialSchemaImpact}`
     （与 `POST /` 的 `{server,test}` **同族**）—— 复合响应是唯一"既不污染 `McpServerItem` 这个
     全端点唯一形状、又能把本次请求特有的提示带回来"的写法（前提仍是那条：同一份数据**只有一种形状**）。
- **坑预判逐条落实**：① **成立，但边界比预判细得多** —— "BODY 与 JSON-RPC 冲突"确实存在（测出来是
  **四个键名**的冲突，撞上就毁报文），但**非保留的顶层额外字段是可行的**（H1 有协议线级取证）

- **落地要点**：
  1. ⚠️ **两个"唯一实现"分别落在两处、各有理由**：
     · `shared#isCredentialConfigured` / `missingRequiredCredentialKeys`（**判据**）——
       前端要按同一口径画 ✓ 与置顶提示，不能各写一份；
     · `mcpCredentialAad()`（**绑定公式**）—— 与 `model.service.ts#providerKeyAad` 同一条纪律：
       写与读（P0-2-7 的注入端）必须复用同一个函数，**改公式 = 库里密文全废**。
     ⚠️ AAD 含 `serverId + userId + key`、**刻意不含行 id**（与 Provider 的 AAD **相反**）：
     Provider 含 id ⇒ 加密只能发生在拿到 id 之后（建记录必须走事务）；凭据走 `upsert`，
     加密时**还没有行** ⇒ 归属用 `(server,user)` 这个唯一键（行 id 只是它的代理）。
  2. ⚠️ **`configured` 与 `updatedAt` 是两件事**（前者按模板算、后者是"有没有行"）：
     模板没有必填项时"从没写过"也是 `configured:true`（内网无鉴权的 server 就属这一类）。
     把两者混成一个字段会让"未配置置顶"在无必填项的模板上永远点亮。
  3. **`fields` 按模板投影，`hasValue` 的覆盖面是 `values` 的全部 key**：模板里被删掉的 key
     即使库里还有值也不出现在 `fields`（它已经不会被注入、界面不该拿它冒充可用参数），
     但那条值仍在库里等用户自己清（P0-2-3 定案"只提示、绝不自动清理"）。
  4. **"清到一个不剩 ⇒ 删行"**：留一个 `values:{}` 的空行会让"我有凭据"变成假话
     （`configured` 现在不依赖它，但下一个人会依赖）。**空串 = 删键**（不是存空密文 ——
     `encryptSecret('')` 得到的 `v1.iv.tag.` 结构完全合法，会让"已配置"永远为真）。
  5. **`DELETE` 本来就没配 ⇒ 404**（不是幂等 200）：它删的是"我的那一份"，
     "你没有可删的东西"比"删除成功"更准确。**整个凭据路由里没有 403** —— `PUT` 别人的
