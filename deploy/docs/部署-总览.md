# 部署包总览

这个目录是**分发包**：别人拿到它 + 镜像，改一个 `deploy.env` 就能起来，不需要源码、不需要 compose。

- 只想知道怎么启动 → 看对应平台的单页：`Linux.md` / `macOS.md` / `Windows.md`
- 想知道每个文件干什么、怎么打包给别人 → 就是本页

---

## 1. 三十秒上手

```bash
cd deploy
cp env/deploy.env.example deploy.env     # 然后改 4 个必填项
bash scripts/up.sh
```

浏览器打开 `http://<INSTANCE_IP>:8080`，账号 `admin`，初始密码在 `.generated/seed.log`。

必填的 4 项（`deploy.env` 里都标了 ★）：

| 项 | 怎么填 |
|---|---|
| `CREDENTIAL_MASTER_KEY` | `openssl rand -base64 32` 生成一次，**以后不能改** |
| `POSTGRES_PASSWORD` | 数据库密码（`MODE=all` 且 `MANAGE_INFRA=1` 时用于创建；否则就是连现有库的密码） |
| `S3_SECRET` | 对象存储密钥（同上规则） |
| `INSTANCE_IP` | 本机内网 IP。单机自测可以 `127.0.0.1`，多机必须填真实的 |

## 2. 目录结构

```
deploy/
├── deploy.env.example        ← 配置模板（复制成 deploy.env 后改）
├── deploy.env                ← 你的实际配置（不进 git）
├── .gitignore                ← 忽略 deploy.env 与 .generated/
│
├── env/
│   └── deploy.env.example    ← 模板本体（带全部注释说明）
│
├── docker/
│   ├── egress-proxy.mjs      ← 沙箱出网代理（零依赖，挂进 egress 容器）
│   └── sandbox-relay.mjs     ← 容器→后端 中转（macOS/Windows 需要）
│
├── scripts/
│   ├── _lib.sh               ← 公共函数（读配置/校验/探测），被下面几个 source
│   ├── up.sh                 ← ★ 启动（Linux / macOS）
│   ├── down.sh               ← 停止（Linux / macOS）
│   ├── status.sh             ← 看状态（Linux / macOS，只读）
│   ├── up.ps1                ← ★ 启动（Windows）
│   └── down.ps1              ← 停止（Windows）
│
├── docs/                     ← 你正在看的三份文档
│   ├── 部署-总览.md
│   ├── Linux.md
│   ├── macOS.md
│   └── Windows.md
│
└── .generated/               ← 运行时产物，不用管（不进 git）
    ├── seed.log              ← 首次初始化打印的账号初始密码
    ├── migrate.log           ← 迁移日志（失败时看这个）
    └── ...
```

**为什么只有一个 env**：仓库里的 `infra/` 按用途分了三四个 env（后端/网关/前端各一份）。
部署包里合并成 `deploy.env` 一份，脚本负责展开成各服务需要的值 —— 你只需要理解一份文件。

## 3. `deploy.env` 里的关键变量

分成 7 组，只有标 ★ 的必须改。

### ① 形态

| 变量 | 取值 | 含义 |
|---|---|---|
| `MODE` | `all` / `node` | `all` = 单机全套（后端+网关+前端）；`node` = 只加一台沙箱实例 |
| `IMAGE_SOURCE` | `registry` / `local` / `build` | 镜像从哪来（见第 4 节） |
| `IMAGE_REGISTRY` | 如 `ghcr.io/tyl1998` | `IMAGE_SOURCE=registry` 时用 |
| `IMAGE_TAG` | 默认 `2` | 镜像版本号 |
| `BACKEND_IMAGE` / `GATEWAY_IMAGE` / `FRONTEND_IMAGE` / `POSTGRES_IMAGE` | 完整镜像名 | **可选**：仓库地址不规整时逐个覆盖，设置后该镜像不吃 `IMAGE_REGISTRY`+`IMAGE_TAG` |
| `SRC_DIR` | 默认 `..` | `IMAGE_SOURCE=build` 时的源码根目录 |

### ② 本机身份

| 变量 | 含义 |
|---|---|
| `INSTANCE_IP` ★ | 别的机器要能访问到的地址（不能是 `127.0.0.1`） |
| `INSTANCE_ID` | 实例 id，多机时每台不同（`a`/`b`/`c`）。**同 id 两台会互相误杀** |
| `BACKEND_PORT` / `GATEWAY_PORT` / `FRONTEND_PORT` | 默认 `13000` / `13100` / `8080` |

### ③ 密钥与数据库 ★

| 变量 | 说明 |
|---|---|
| `CREDENTIAL_MASTER_KEY` | 32 字节 base64。**写入数据后不可更改**，否则已加密凭据全部解不开 |
| `POSTGRES_PASSWORD` / `S3_SECRET` | 数据库 / 对象存储密钥 |
| `POSTGRES_USER` / `POSTGRES_DB` / `S3_KEY` | 默认 `doubulea`，一般不用改 |

### ④ 基础服务地址

| 变量 | 说明 |
|---|---|
| `MANAGE_INFRA` | **默认 `0`**：本包**不创建也不停止** PG/Redis/MinIO，只连现有的（见第 5 节） |
| `REMOTE_PG_HOST` / `REMOTE_REDIS_HOST` / `REMOTE_S3_HOST` | 留空 = 用本机 `127.0.0.1` + 下面的端口；填了 = 连远端 |
| `POSTGRES_PORT` / `REDIS_PORT` / `MINIO_API_PORT` | 本机端口，默认 `15432` / `16379` / `19000` |

### ⑤ 首次初始化

| 变量 | 说明 |
|---|---|
| `SEED_ADMIN_USERNAME` / `SEED_ADMIN_PASSWORD` | 默认 `admin`，密码留空则随机生成并打印到 `.generated/seed.log` |
| `SEED_MEMBER_USERNAME` / `SEED_MEMBER_PASSWORD` | 同上，默认 `member` |

### ⑥ 沙箱

| 变量 | 说明 |
|---|---|
| `DOUBULEA_NODE_ROLE` | `chatbot` = 只做对话（不需要 Docker 权限，最省事）；`taskAgent` = 跑沙箱（默认） |
| `SANDBOX_IMAGE` / `SANDBOX_IMAGE_BASE` | 沙箱镜像 tag，与镜像构建时的版本线一致 |
| `DOCKER_SOCKET_GID` | 留空 = 脚本自动探测（**推荐留空**，见第 6 节） |
| `WORKSPACE_ROOT` | 工作区根目录，留空 = `$HOME/doubulea/workspaces` |
| `NODE_OPS_SECRET` | 多机跨实例运维用，所有机器填同一份；单机可留空 |
| `SANDBOX_NPM_REGISTRY` / `SANDBOX_APT_MIRROR` / `SANDBOX_APT_MIN_BPS` / `SANDBOX_NODE_DIST_MIRROR` / `SANDBOX_RUST_DIST_MIRROR` | 内网构建沙箱镜像时的换源。留空 = 官方源（内网通常至少要设前两个，否则 toolkit 会卡） |

### ⑦ 其它

`TZ`、`SESSION_TTL_HOURS`、`CHATBOT_CONCURRENCY`、`SANDBOX_CONCURRENCY`、`SANDBOX_CALLBACK_PORT` —— 都有默认值。

## 4. 镜像从哪来（三种方式）

部署包自己**不含镜像**，需要先让本机有镜像。

### 方式 A：从镜像仓库拉（`IMAGE_SOURCE=registry`）

```ini
IMAGE_SOURCE=registry
IMAGE_REGISTRY=ghcr.io/tyl1998
IMAGE_TAG=2
```

需要先登录（如果仓库是私有的）：`docker login ghcr.io`。

需要的镜像清单：

| 镜像 | 用途 | 必需 |
|---|---|---|
| `doubulea-backend:2` | 每台实例的后端 | ★ |
| `doubulea-gateway:2` | 路由网关（一台） | ★ |
| `doubulea-frontend:2` | 前端静态站点 | ★ |
| `doubulea/postgres:pg16-vector-bigm` | 数据库（含 pgvector + pg_bigm） | 仅 `MANAGE_INFRA=1` |
| `redis:7-alpine` / `minio/minio` | 依赖服务 | 仅 `MANAGE_INFRA=1` |
| `docker:27-cli` | 按需构建运行时用的 CLI | `taskAgent` |
| `node:22-bookworm-slim` | egress / relay 运行时 | `taskAgent` |
| `doubulea/sandbox-toolkit:8` | 沙箱默认镜像 | `taskAgent` |
| `doubulea/sandbox-base:6` | 构建 toolkit 时用 | 运行时不需要 |

### 方式 B：本地已有镜像（`IMAGE_SOURCE=local`）

先导入，再启动：

```bash
docker load -i backend.tar
docker load -i gateway.tar
docker load -i frontend.tar
```

```powershell
Get-ChildItem *.tar | ForEach-Object { docker load -i $_.FullName }
```

### 方式 C：从源码构建（`IMAGE_SOURCE=build`）

需要源码目录 + Node 22 + pnpm：

```bash
# 在源码根目录构建三个镜像（版本号从 infra/sandbox/versions.mjs 读，不要手敲 docker build）
pnpm backend:build-image
pnpm gateway:build
pnpm frontend:build-image
```

`SRC_DIR` 指向源码根（默认 `..`，即部署包上一级）。

> ⚠️ 多机部署时**必须把同一台构建出来的镜像分发到每台**（`docker save` + `docker load`，或推 registry）。
> 每台各自 build 会产生"同 tag 不同内容"的镜像，症状是只在某台上复现的怪问题。

### 打出分发包

给别人时这些**不要打进去**（含密钥/账号/本地状态）：

```bash
cd /path/to/repo
tar czf doubulea-deploy.tgz \
  --exclude='deploy/deploy.env' \
  --exclude='deploy/.generated' \
  deploy/
```

对方解压后：`cp env/deploy.env.example deploy.env` → 改 4 个必填 → `bash scripts/up.sh`。

镜像另外给（`docker save` 出来的 tar，或 registry 地址）。

## 4.1 两个启动入口的关系

仓库里有两个能起节点的入口，**都在用**，区别如下：

| | `infra/scripts/node-up.sh` | `deploy/scripts/up.sh` |
|---|---|---|
| 需要什么 | bash + 镜像 + 两份 env | 整个 `deploy/` 目录 |
| 配置文件 | `.env.node` + `.env.node.shared`（两份） | `deploy.env`（一份） |
| 起什么 | 后端 + docker-cli 侧车 + 命名卷 | 同上，且**可选**网关 / 前端 |
| 建表 / 种子 | 不做（依赖共用库已有表） | 做（`prisma migrate deploy` + seed） |
| 适用 | **新机器只有镜像**（从镜像里取出该脚本直接跑） | 主节点 / 有完整仓库 |

两者是**两份独立实现**：修一处不会自动同步到另一处。改 `docker run` 参数（socket gid、卷、侧车、
换源变量）时**两边都要看**。

## 5. `MANAGE_INFRA`：会不会碰基础服务

**默认 `0`，本包不碰 PG / Redis / MinIO。**

| 值 | 行为 | 用在哪 |
|---|---|---|
| `0`（默认） | 只探测端口能不能连，连不上就报错退出。**绝不** `stop` / `rm` / 创建容器 | 机器上已有 PG/Redis/MinIO（运维管、或另一个 compose 管） |
| `1` | 自己创建并管理（卷名带 `doubulea-deploy-` 前缀，与现有容器不重名） | 专用机器，从零开始 |

这条设计来自一次真实事故：早期版本在别人的机器上执行时把正在用的 PG/Redis/MinIO 停了。
现在 `MODE=all` 也不代表"我管基础服务"，两者是**独立**的开关。

`down.sh --all` 同理：`MANAGE_INFRA=0` 时只停应用容器，并明确打印"基础服务不归本包管"。

## 6. 两个平台差异（脚本已处理，这里只解释）

| 项 | Linux / macOS | Windows |
|---|---|---|
| 后端网络 | `--network host` | 发布端口 `-p 13000` / `-p 13001` |
| 访问宿主 Docker | 挂 `/var/run/docker.sock` | `DOCKER_HOST=tcp://host.docker.internal:2375` |
| socket 组 | `--group-add <gid>` | 不需要 |
| 沙箱回调 | listener 直连 | 经 `sandbox-relay` |
| 脚本 | `scripts/*.sh` | `scripts/*.ps1`（**只写 ASCII**，PowerShell 5.1 按 ANSI 读） |

### socket gid 为什么自动探测

容器内是 uid 10001，宿主 socket 通常是 `root:<group> 660`。gid 取错 → 后端访问 Docker 报
`permission denied` → 沙箱完全起不来，而 `/health` 仍然绿（容易误判）。

不同环境的 gid **不一样**：
- Linux（Docker Engine）：通常是 `999` 或 `0`
- macOS（OrbStack）：宿主 `stat` 是 `1`，但**容器内看到的是 `0`**

所以脚本不是简单 `stat` 宿主，而是让临时容器去 `stat` 挂进去的 socket，取**容器视角**的 gid。
一般不用手动设 `DOCKER_SOCKET_GID`；要覆盖再填。

## 7. 脚本命令速查

### Linux / macOS

| 命令 | 作用 |
|---|---|
| `bash scripts/up.sh` | 启动（幂等：已在跑就跳过） |
| `bash scripts/up.sh --force` | 强制重建容器（换了镜像 tag 后用） |
| `bash scripts/up.sh --no-build` | `IMAGE_SOURCE=build` 时跳过构建 |
| `bash scripts/up.sh --reset-db` | ⚠️ 删数据重建（仅 `MANAGE_INFRA=1`） |
| `bash scripts/down.sh` | 停应用容器 |
| `bash scripts/down.sh --all` | 连基础服务一起停（仅 `MANAGE_INFRA=1` 生效） |
| `bash scripts/down.sh --purge` | ⚠️ 连数据卷一起删 |
| `bash scripts/status.sh` | 看容器状态 + 健康检查 + 网关视角的实例列表 |

### Windows

| 命令 | 作用 |
|---|---|
| `powershell -ExecutionPolicy Bypass -File scripts\up.ps1` | 启动 |
| `... -File scripts\up.ps1 -Force` | 强制重建 |
| `... -File scripts\up.ps1 -NoBuild` | 跳过构建 |
| `... -File scripts\up.ps1 -ResetDb` | ⚠️ 删数据重建 |
| `powershell -ExecutionPolicy Bypass -File scripts\down.ps1` | 停止 |
| `... -File scripts\down.ps1 -All` / `-Purge` | 同 Linux 的 `--all` / `--purge` |

`up.sh` 执行顺序（每步都会打印 `[OK]` / `[--]`）：

1. 校验配置 → 2. 检查/拉取镜像 → 3. 探测基础服务（或创建，见 `MANAGE_INFRA`）
→ 4. `prisma migrate deploy` → 5. 种子账号 → 6. 后端 → 7. 沙箱侧车/egress/relay
→ 8. 网关 → 9. 前端 → 10. 汇总（地址 + 账号位置）

## 8. 常见问题

| 症状 | 原因 | 解决 |
|---|---|---|
| `配置不完整` | 4 个必填没改 | 按提示填，密钥用 `openssl rand -base64 32` |
| `连不上 PG 127.0.0.1:15432` | `MANAGE_INFRA=0` 且本机没有 PG | 填 `REMOTE_PG_HOST`，或改 `MANAGE_INFRA=1` 自建 |
| 登录返回 `上游实例不可达` | 网关找不到后端 | `docker logs doubulea-gateway`；确认后端 `/health` 正常 |
| 实例自检 `docker` 项红 | socket gid 错 | 先清空 `DOCKER_SOCKET_GID` 让脚本自动探测 |
| `port is already allocated` | 端口被占 | 改 `deploy.env` 里的端口，不要动别的容器 |
| 沙箱自检缺 `toolkitImage` | 没构建沙箱镜像 | `pnpm sandbox:build`（源码）或导入 `sandbox-toolkit` |
| 网关反复 502 | 上游地址是本机的 127.0.0.1 | 单机时脚本用 `host.docker.internal`，别手改成 `127.0.0.1` |
