# 分角色部署：A 前端 / B 后端 / C 基础服务 / D 网关

本文回答一个具体的部署问题：**把前端、后端、基础服务各放一台机器，网关再单独一台，怎么起。**
仓库里原有的部署文档没有这一形态（`Linux.md` 等讲的是 `MODE=all` 单机全套与 `MODE=node` 加沙箱实例），
所以这一页把它补齐。

> ⚠️ **"分角色"与"放几台后端"是两件正交的事**，别把它当成"只能一台后端"：
>
> - **角色**：前端 / 后端 / 基础服务 / 网关 四类组件各放哪台机器；
> - **规模**：**后端角色可以有多台**（B1、B2、…），网关天然支持 —— `ROUTER_UPSTREAMS` 就是
>   **逗号分隔的多台地址表**（`backend/src/router/config.ts:12`），与自动发现取并集，按会话粘性路由。
>
> 所以「A 前端 / B1、B2… 后端 / C 基础服务 / D 网关」是一种合法且推荐的组合：
> 每加一台后端就是**照着第四节在新机器上再来一遍**（实例 `id` 换一个、地址填自己的 IP），
> 再把它加进 `ROUTER_UPSTREAMS`（或开着自动发现让它自己注册）。**前端（A）与网关（D）都不用动。**
>
> 单台后端时，网关的粘性路由与负载感知**退化为直转**（无损，只是用不上）—— 是同一套配置的退化情形，
> 不是另一种部署方式。

> ⚠️ **先分清仓库里的三种部署形态**（与上面"分角色"是另一维度，别混）：
>
> | 形态 | 说的是什么 | 在哪 |
> |---|---|---|
> | **单机全套** | 一台机器跑后端 + 网关 + 前端 + 基础服务（`deploy.env` 的 `MODE=all`） | `deploy/docs/部署-总览.md`、`Linux.md` |
> | **分角色（本文）** | 前端 / 后端 / 基础服务 / 网关 分别落到不同机器（后端可 1~N 台） | 本文件 |
> | **多实例扩容** | 同一套角色拓扑下**追加后端实例**（P1-14 的"多机"） | `docs/子方案/沙箱多机部署.md` 路线 A |

## 一、拓扑与端口

```
浏览器
  │  http://<A_IP>:8080
  ▼
机器 A  前端    doubulea-frontend（nginx：托管 SPA + 反代 /api、/health）
  │  http://<D_IP>:13100
  ▼
机器 D  网关    doubulea-gateway（唯一入口；按会话粘性把 /api 分给下面的后端）
  │  http://<B1_IP>:13000 / <B2_IP>:13000 / …     ← ROUTER_UPSTREAMS 是**多台列表**
  ├──────────────┐
  ▼              ▼
机器 B1 后端     机器 B2 后端   doubulea-backend（network=host + 挂 docker.sock ⇒ 各自起沙箱）
  │              │
  └──────┬───────┘   PG 5432 / Redis 6379 / MinIO 9000（**共用** C 这一套）
         ▼
机器 C  基础服务  PostgreSQL(pgvector+pg_bigm) / Redis / MinIO
```

后端角色**可以是一台，也可以是多台**（B1 / B2 / …）：每台后端只跑自己的沙箱，
共用 C 的 PG/Redis/MinIO，由 D 按会话粘性路由。下面各节以 **单台 B** 为主线，
加第二台就是"重复第四节、换个实例 id 与 IP、再把地址加进网关"（见 §八）。

| 机器 | 角色 | 镜像 | 端口 | 需要 docker.sock |
|---|---|---|---|---|
| A | 前端静态站点 | `doubulea-frontend:<ver>` | `8080 → 80` | 否 |
| B1 / B2 / … | 业务后端 + 沙箱宿主（**可多台**） | `doubulea-backend:<ver>` | `13000`（host 网络）、出口② `13001` | **是** |
| C | PG / Redis / MinIO（**后端们共用**） | `doubulea/postgres:pg16-vector-bigm`、`redis:7-alpine`、`minio/minio` | `5432` / `6379` / `9000`（控制台 `9001`） | 否 |
| D | 路由网关 | `doubulea-gateway:<ver>` | `13100` | 否 |

**为什么网关单独一台（D）**：网关的**代码默认端口就是 13000**（`backend/src/router/config.ts`：
`ROUTER_PORT` 默认 13000），而业务后端的 `BACKEND_PORT` 默认也是 13000。同机跑两者在 macOS 上会因
host 网络与端口转发争用而失败 —— 所以仓库把网关的推荐值定成 **13100**
（`infra/router/.env.router.example` 与 `infra/router/docker-compose.router.yml` 文件头都写了这一条，
并注明"不要用 13000"）。**放到 D 则连这个冲突都不存在**（D 与各后端不同宿主，互不抢口）。

**接线方向（防火墙按这些放）**：

- `浏览器 → A:8080`
- `A → D:13100`
- `D → 每台 B:13000`（转发）与 `D → C:6379`（读会话目录 `sandbox:owner:*` / `sandbox:instance:*`）
- `每台 B → C:5432 / 6379 / 9000`
- `每台 B → 模型上游 / 公网`（沙箱出网，经**各自本机**的 egress 容器）

浏览器**不直连** B 与 D。

## 二、镜像：一台构建、分发到各台

各角色机器都不应该各自 `docker build`（会产生"同 tag 不同内容"的镜像）。**在一台构建机上**打齐：

```bash
pnpm backend:build-image -- --save backend.tar     # doubulea-backend:<ver>
pnpm gateway:build       -- --save gateway.tar     # doubulea-gateway:<ver>
pnpm frontend:build-image -- --save frontend.tar   # doubulea-frontend:<ver>

# 自建 PG（pgvector + pg_bigm）——官方 pgvector 镜像不含 pg_bigm，必须用这一个
docker build -t doubulea/postgres:pg16-vector-bigm infra/postgres
docker save doubulea/postgres:pg16-vector-bigm -o postgres.tar
docker save redis:7-alpine minio/minio -o basics.tar
```

```bash
# 分发（或改成推私有 registry）
scp backend.tar  user@<B_IP>:~
scp gateway.tar  user@<D_IP>:~
scp frontend.tar user@<A_IP>:~
scp postgres.tar basics.tar user@<C_IP>:~
```

```bash
# 各台 load
docker load -i backend.tar      # B 上
docker load -i gateway.tar      # D 上
docker load -i frontend.tar     # A 上
docker load -i postgres.tar && docker load -i basics.tar   # C 上
```

> 镜像 tag 的唯一来源是 `infra/sandbox/versions.mjs`（`backend:2` / `gateway:2` / `frontend:2`），
> **不要手敲 `docker build`**。改了镜像内容要 +1 层版本号。

## 三、机器 C：基础服务（先起它）

C 上放 PG / Redis / MinIO。用仓库的 compose（只含这三个有状态服务，不含应用）：

```bash
git clone <仓库地址> doubleA && cd doubleA
cp infra/.env.example infra/.env
vi infra/.env     # ★ POSTGRES_PASSWORD / MINIO_ROOT_USER / MINIO_ROOT_PASSWORD；端口默认 5432/6379/9000
bash infra/scripts/dev-up.sh      # 建 PG 镜像（首次编译 pg_bigm）→ up → 等健康 → 验收扩展
# 或：pnpm infra:up
```

- ⚠️ **PG 必须是 `doubulea/postgres:pg16-vector-bigm`**：中文全文检索依赖 pg_bigm，官方
  `pgvector/pgvector` 镜像里没有它（`docs/01` 决策 11）。compose 里的 `build:` 就是为这个。
  若已在构建机打好该镜像，C 上 `docker load` 后 `dev-up.sh --no-build` 可直接跳过编译。
- `dev-up.sh` 收尾会自动跑 `pg-verify.mjs` 验收 `vector` + `pg_bigm` 真可用。
- **S3 bucket 不用手建**：后端首次上传/写对象时会 `ensureBucket`（见 `backend/src/infra/s3.ts`）。
- C 的 `infra/.env` 只管：两组密码（`POSTGRES_PASSWORD` / `MINIO_ROOT_PASSWORD`）、宿主端口、TZ。
  `DATABASE_URL` / `REDIS_URL` / `CREDENTIAL_MASTER_KEY` 这些应用变量 C 上**没人读**（C 不跑应用），
  照样例默认即可 —— 真正生效的是各后端的 `.env.node.shared` 里那几行。
- ⚠️ `POSTGRES_PASSWORD` 与 `MINIO_ROOT_PASSWORD` 要记牢 —— 每台后端的 `.env.node.shared` 里
  `DATABASE_URL` 的密码段、`S3_SECRET` 都必须与它们一致（**多台后端共用这一套**）。
- ⚠️ **多台后端共用 C 的这一套 PG / Redis / MinIO**：数据库/对象存储是共享的（迁移只跑一次，
  见 §4.2），Redis 也是共享的（会话目录、实例注册、队列都在里面）——**不要给每台后端配各自的 Redis**。

开放端口（对**每台后端**与网关 D）：

```bash
# 例（ufw）；按实际网段收敛，不要把 5432/6379/9000 暴露到公网
sudo ufw allow from <B1_IP> to any port 5432,6379,9000 proto tcp
sudo ufw allow from <B2_IP> to any port 5432,6379,9000 proto tcp   # 第二台后端照加
sudo ufw allow from <D_IP>  to any port 6379 proto tcp             # 网关只要 Redis
```

> ⚠️ **C 的 Redis 最好只服务本套部署**：自动发现靠它读 `sandbox:instance:*`。若同一 Redis 上还有
> 其它实例 / 同事 dev 写进去的 `sandbox:instance:*`，网关会把那些地址也当上游（症状：一半 `/api` 502）。
> 这种共享场景改用 `ROUTER_DISCOVERY_SEC=0` + 静态 `ROUTER_UPSTREAMS` 全列表（见 §五）。

## 四、机器 B：后端 + 沙箱（每台后端都照此节做一遍）

B 是**一台**后端实例，也是沙箱宿主（`network_mode: host` + 挂 `/var/run/docker.sock`，
在 B 本机起兄弟容器）。要第二台就整节照做，只改下面标出的**实例唯一项**（`SANDBOX_INSTANCE_ID` /
`ADVERTISE_ADDR` / IP）。

**前置**：B 上要有仓库源码目录（下面用的 `infra/router/docker-compose.host.yml` 引用了仓库内路径：
`egress` 服务挂载 `../scripts/egress-proxy.mjs`、`backend` 组件的 `build.context` 是仓库根）。
镜像本身已从构建机分发过来，所以这步**只需要源码、不需要在 B 上装 Node / pnpm**。
（`deploy/` 分发包也能起后端，见 §七末。可以只分发 `deploy/` 目录、不带源码。）

### 4.1 两份 env

B 需要两份 env（与 `infra/router/docker-compose.host.yml` 配套）：

`infra/router/.env.node`（本机身份，每台不同）——从 `.env.node.example` 复制：

```ini
SANDBOX_INSTANCE_ID=b
SANDBOX_INSTANCE_ADVERTISE_ADDR=<B_IP>:13000   # 网关据此回连 B
BACKEND_IMAGE=doubulea-backend:2
SHARED_ENV_FILE=./.env.node.shared
WORKSPACE_ROOT=/var/lib/doubulea/workspaces     # 宿主绝对路径，须可写
BACKEND_PORT=13000
DOCKER_SOCKET_GID=<stat -c %g /var/run/docker.sock>   # Linux 通常是 999 或 0
EGRESS_IMAGE=node:22-bookworm-slim
EGRESS_DOCKER_BIN=/usr/bin/docker
```

`infra/router/.env.node.shared`（业务变量，指向 C）——从 `.env.node.shared` 那份改地址：

```ini
DATABASE_URL=postgresql://doubulea:<pw>@<C_IP>:5432/doubulea?schema=public
REDIS_URL=redis://<C_IP>:6379
S3_ENDPOINT=http://<C_IP>:9000
S3_KEY=doubulea
S3_SECRET=<与 C 的 MINIO_ROOT_PASSWORD 一致>
S3_BUCKET=doubulea

CREDENTIAL_MASTER_KEY=<各台同一份，openssl rand -base64 32>
SANDBOX_IMAGE=doubulea/sandbox-toolkit:8
SANDBOX_IMAGE_BASE=doubulea/sandbox-base:6
SANDBOX_EGRESS_PROXY_URL=http://doubulea-egress:3128
SANDBOX_EGRESS_ALLOW_HOSTS=*
SESSION_TTL_HOURS=12
SANDBOX_CONCURRENCY=10
SANDBOX_IDLE_TTL_MIN=30
SANDBOX_CALLBACK_PORT=13001
CHATBOT_CONCURRENCY=50
```

> ⚠️ **Linux 上不要设 `SANDBOX_LISTEN_HOST` 与 `SANDBOX_BACKEND_URL`**。
> 仓库里那份 `.env.node.shared`（153，macOS）把它们设成了 `0.0.0.0` 与
> `http://doubulea-sandbox-relay:13001` —— 那是"后端与 Docker 不同宿主"（macOS/OrbStack）的走法，
> 靠一个 relay 中转容器。**Linux 上后端与 Docker 同宿主，两者都留空/删掉**：
> listener 会自己绑沙箱网桥网关地址，`compose` 里也没有 relay 服务，照抄 macOS 那份会让出口② 找不到中转。

> ⚠️ **HTTP 直连必须关掉 Cookie 的 Secure 位**（未配 TLS 时）。后端 `NODE_ENV=production` 时
> `SESSION_COOKIE_SECURE` 默认 `true`，浏览器会**直接丢弃**这枚 Cookie，症状是"登录成功却立刻未登录"。
> 把这一行加进 `.env.node.shared`（`env_file` 会把整份文件的键都灌进容器）：
>
> ```ini
> SESSION_COOKIE_SECURE=false
> ```
>
> 想彻底消掉这个口子：在 A 或更外层终结 TLS（HTTPS），然后保持 `true`。
> ⚠️ 已知缺口：`deploy/` 分发包的 `up.sh` 用的是写死的 `-e` 列表，**没有透传** `SESSION_COOKIE_SECURE`
> ⇒ 走 `deploy/` 起后端时无法关掉它（见本文件 §七）。

### 4.2 建表 + 种子（**起后端之前**跑一次）

`MODE=node` / compose 形态都**不负责建表**（只有单机 `MODE=all` 才跑）。表必须先由 C 的库存好，
否则后端起来后任何写操作都会 `no partition of relation "messages" found for row`。用后端镜像里的
Prisma 跑（不需要在 B 上装 Node）：

```bash
# ① 迁移（只应用，不做 diff）
docker run --rm --network host \
  -e DATABASE_URL="postgresql://doubulea:<pw>@<C_IP>:5432/doubulea?schema=public" \
  -e TZ=Asia/Shanghai \
  --entrypoint sh doubulea-backend:2 -lc \
  'cd /app/backend && /app/node_modules/.bin/prisma migrate deploy'

# ② 种子：建第一个 ADMIN + 一个 MEMBER（幂等，已存在则跳过、绝不改密码）
#    ⚠️ seed 要过 config 校验 ⇒ 必须带齐 DATABASE_URL / REDIS_URL / S3_* / CREDENTIAL_MASTER_KEY
docker run --rm --network host \
  -e DATABASE_URL="postgresql://doubulea:<pw>@<C_IP>:5432/doubulea?schema=public" \
  -e REDIS_URL="redis://<C_IP>:6379" \
  -e S3_ENDPOINT="http://<C_IP>:9000" -e S3_KEY=doubulea -e S3_SECRET=<pw> -e S3_BUCKET=doubulea \
  -e CREDENTIAL_MASTER_KEY=<同一份主密钥> \
  -e TZ=Asia/Shanghai \
  --entrypoint sh doubulea-backend:2 -lc \
  'node /app/backend/dist/backend/prisma/seed.js'
```

**记下种子打印的 admin 初始密码**（只打印这一次），首次登录后必须改密（首登改密闸门，
ADMIN 也不例外）。忘掉就 `SEED_RESET_PASSWORD=1` 重发（需要一份能在宿主跑的源码环境）。

> 迁移自带初始分区窗口（上月 ~ 未来 12 个月）。到期前要续期，用运维/cron 在能连库的地方跑：
>
> ```bash
> docker run --rm --network host -e DATABASE_URL="..." --entrypoint sh doubulea-backend:2 -lc \
>   'cd /app/backend && /app/node_modules/.bin/prisma db execute --file prisma/sql/ensure_messages_partitions.sql \
>    && /app/node_modules/.bin/prisma db execute --file prisma/sql/ensure_usage_records_partitions.sql'
> ```

### 4.3 起后端（+ egress）

```bash
# ① 后端（会一并带出 docker-cli 侧车）
docker compose -f infra/router/docker-compose.host.yml \
  --env-file infra/router/.env.node up -d backend

# ② egress（★ 必须在后端起来、doubulea-sandbox 网出现之后再起）
docker compose -f infra/router/docker-compose.host.yml \
  --env-file infra/router/.env.node up -d egress
```

> ⚠️ **两步不能合成一条 `up -d`**：`docker-compose.host.yml` 只声明了 `backend depends_on docker-cli`，
> **没有** `egress depends_on backend`（沙箱网是**后端运行期**建的，compose 表达不了这个依赖）。
> 直接 `up -d`（不带服务名）会两个容器同时起 ⇒ egress 在前 300 秒里等不到 `doubulea-sandbox` 网，
> 沙箱出网就断了。

egress 容器自己的启动脚本会等 `doubulea-sandbox` 网出现再接上（最多等 ~5 分钟）：

- `docker-cli` 侧车把 Linux 版 `docker` 二进制复制进命名卷（容器里没有 CLI，按需构建运行时要用）。
- 想收窄出网（不用 `EGRESS_ALLOW=*`）：改用 `bash infra/scripts/egress-up.sh --daemon`
  （读平台 `egress_policy` 表 + 模型池主机）。

自检（在 B 上）：

```bash
curl -s --noproxy '*' http://127.0.0.1:13000/health     # 期望 PG / Redis / S3 全 ok
docker logs --tail 50 doubulea-backend
```

**只做对话、不跑沙箱（chatbot 档位）**：把 `infra/router/docker-compose.host.chatbot.yml`
**叠加**上去 —— 它会摘掉 socket / `egress` / `docker-cli` 侧车 / socket 补组：

```bash
docker compose -f infra/router/docker-compose.host.yml \
               -f infra/router/docker-compose.host.chatbot.yml \
               --env-file infra/router/.env.node up -d backend
```

> 这条路线**不需要** `DOCKER_SOCKET_GID`（覆盖文件已把它从 backend 上摘掉），一条命令即可，
> 且不再需要起 `egress`。档位判据见 `backend/src/sandbox/roleOverride.ts`：`chatbot` ⇒
> 不建容器、不登记实例、不进实例列表。
> 若走 `deploy/scripts/up.sh` 那条路线，则直接在 `.env.node.shared` 里设 `DOUBULEA_NODE_ROLE=chatbot`
> （它按档位跳过 egress / relay / 侧车），不必用这个覆盖文件。

## 五、机器 D：网关（唯一入口）

网关是**无状态小进程**，只要 Redis + 各实例地址，**不挂 docker.sock**。
（也可用 `infra/router/docker-compose.router.yml`，这里给等价的 `docker run`，D 上不必放仓库。）

```bash
docker run -d --name doubulea-router --restart unless-stopped \
  -e DOUBULEA_SANDBOX_ROLE=router \
  -e NODE_ENV=production -e LOG_PRETTY=false \
  -e ROUTER_PORT=13100 \
  -e ROUTER_UPSTREAMS=<B1_IP>:13000,<B2_IP>:13000 \
  -e ROUTER_DISCOVERY_SEC=10 \
  -e REDIS_URL=redis://<C_IP>:6379 \
  -p 13100:13100 \
  doubulea-gateway:2
```

逐项理由：

| 键 | 值 | 为什么 |
|---|---|---|
| `DOUBULEA_SANDBOX_ROLE` | `router` | **必须显式写**：不写时"配了 `SANDBOX_IMAGE` 且本机能拿到 Docker 才算宿主"，而网关没有 docker.sock ⇒ 会把自己登记进实例表、自动发现把自己当上游（回环）。写了就明确是非宿主。 |
| `ROUTER_UPSTREAMS` | `<B1_IP>:13000,<B2_IP>:13000` | 静态上游表（**逗号分隔的多台**，`config.ts:12`）。单台后端就写一行。它是"种子"，与自动发现取并集。 |
| `ROUTER_DISCOVERY_SEC` | `10` | 自动发现轮询间隔（秒），**默认行为**：扫 Redis 的 `sandbox:instance:*` 动态补上游。多台后端时最省心（新实例自注册）。`0` = 只用静态表。 |
| `REDIS_URL` | 指向 C | 网关读会话目录 `sandbox:owner:*`（决定粘性路由到哪台）与 `sandbox:instance:*`（自动发现）。 |
| `ROUTER_PORT` | `13100` | **不要用 13000**（那是各后端的端口）。 |

**单台 vs 多台**：

- 只 1 台后端（B1）：`ROUTER_UPSTREAMS=<B1_IP>:13000`，`ROUTER_DISCOVERY_SEC` 填 `0` 或 `10` 都行
  （一台时两者等价，`0` 更简单）。
- 多台后端（B1、B2…）：**必须**让网关知道全部地址 —— 两个办法二选一或并用：
  1. **静态**：`ROUTER_UPSTREAMS` 把它们**全列出来**（`b1:13000,b2:13000`）；
  2. **自动发现**（推荐）：`ROUTER_DISCOVERY_SEC=10` ⇒ 各后端启动后把自己的心跳注册进共享 Redis，
     网关自动扫到；`ROUTER_UPSTREAMS` 只当种子（留一台或留空皆可，但不能**又空又关发现**——
     `config.ts:207` 会大声报错）。
- ⚠️ **自动发现的前提**：C 的 Redis **只服务本套部署**。若该 Redis 被别人共用、里面有无关的
  `sandbox:instance:*`，自动发现会把它们当成上游（症状：一半 `/api` 502）。这种共享场景才需要
  `ROUTER_DISCOVERY_SEC=0` + 静态全列表。

⚠️ 网关是**新增单点**：真生产要 ≥2 副本 + 前置 LB；当前按 1 副本部署（多副本编排见
`docs/子方案/沙箱多机部署.md` §八·补）。

自检：

```bash
curl -s --noproxy '*' http://127.0.0.1:13100/health
# 期望 upstreams 里出现**全部**后端地址（静态 ∪ 已发现的）；多台时都应在
```

## 六、机器 A：前端

A 只托管静态产物，并把 `/api`、`/health` 反代到**网关 D**（不是后端）。

```bash
docker run -d --name doubulea-frontend --restart unless-stopped \
  -e ROUTER_UPSTREAM=http://<D_IP>:13100 \
  -e CLIENT_MAX_BODY_MB=100 \
  -p 8080:80 \
  doubulea-frontend:2
```

> ⚠️ `ROUTER_UPSTREAM` 要填**网关**地址（写成 `http://<D_IP>:13100` 即可，容器入口脚本会把
> scheme 折算成 nginx `upstream` 需要的 `host:port`）。填成某台后端会绕过网关 —— 单后端时看不出
> 问题，但一旦后端超过一台就丢粘性与负载感知（会话会打到"没有这个沙箱"的那台）。

浏览器：`http://<A_IP>:8080`，账号 `admin` + §4.2 种子脚本打印的初始密码。

同一份也可以用仓库 compose（`infra/frontend/docker-compose.yml`）：

```bash
cp infra/frontend/.env.frontend.example infra/frontend/.env.frontend  # 改 ROUTER_UPSTREAM / FRONTEND_PORT
docker compose -f infra/frontend/docker-compose.yml --env-file infra/frontend/.env.frontend up -d
```

## 七、这套形态下的已知边界与坑

| 现象 | 原因 | 处置 |
|---|---|---|
| `登录成功却立刻未登录` | 生产默认 `SESSION_COOKIE_SECURE=true`，而访问是 HTTP ⇒ 浏览器丢弃 Cookie | 后端 env（`.env.node.shared` 或 `deploy.env`）里设 `SESSION_COOKIE_SECURE=false`（两条启动路线都已透传该键）；或在外层终结 TLS |
| 后端起来后写入报 `no partition of relation "messages" found for row` | 没跑迁移（`MODE=node`/compose 不建表） | 先跑 §4.2 的 `migrate deploy`（迁移会顺带建到未来 12 个月的分区） |
| 沙箱起不来、`/health` 仍绿 | `DOCKER_SOCKET_GID` 不对（容器内 uid 10001 vs 宿主 socket 660） | 用**容器视角**取 gid（`deploy/scripts/_lib.sh#detect_socket_gid` 的做法），别直接用宿主 `stat`；或让脚本自动探测。忘设时 `up` 会报 `unable to find group DOUBULEA_GID_UNSET` |
| 只做对话、不跑沙箱 | 需要 chatbot 档位（不建容器、不需要 socket/egress） | 用 `docker-compose.host.chatbot.yml` 叠加（见 §4.3）；`deploy/` 路线则设 `DOUBULEA_NODE_ROLE=chatbot` |
| 出口② 不通、容器里 `git`/`workspace` 代理全 404 | 在 Linux 上误留了 macOS 的 `SANDBOX_BACKEND_URL=http://doubulea-sandbox-relay:13001` | Linux 上删掉 `SANDBOX_LISTEN_HOST` 与 `SANDBOX_BACKEND_URL` |
| 一半 `/api` 502（多台后端时） | 有后端没进网关的上游表：既没写进 `ROUTER_UPSTREAMS`、也没被自动发现扫到 | 加进 `ROUTER_UPSTREAMS`，或确认该实例已注册进共享 Redis 且 `ROUTER_DISCOVERY_SEC>0` |
| 一半 `/api` 502（共用 Redis 时） | C 的 Redis 里有**无关**的 `sandbox:instance:*`，被自动发现当成了上游 | 改用 `ROUTER_DISCOVERY_SEC=0` + 静态 `ROUTER_UPSTREAMS` 全列表；或给这套部署一个独占 Redis |
| egress 报接不上沙箱网 | egress 先于后端启动（网是后端运行期建的） | 先起 backend 再起 egress |
| 各台镜像内容不一致 | 各台各自 `docker build` | 一台构建 → `--save` 分发 → `docker load`（或推 registry） |
| 生产日志刷 `CORS_ORIGINS 未设置` WARN | A 的 nginx 是同源反代，后端看不到 Origin 白名单需求 | 可忽略；想消掉就把 `CORS_ORIGINS=http://<A_IP>:8080` 写进后端 env（已透传） |
| 分区写不进去（跨月后） | 迁移建的初始窗口只有上月 ~ 未来 12 个月 | 到期前 cron 跑 §4.2 的两条 `ensure_*_partitions.sql` |
| 实例名冲突拒启 | `SANDBOX_INSTANCE_ID` 与共享 Redis 里在线实例重名 | 每台唯一（`b`/`c`/`d`…）；同 id 两台会对账互相误杀 |

> ⚠️ **`deploy/` 分发包路线的差异**：`bash deploy/scripts/up.sh --env … --shared …` 也接受
> 这两份 env（会合成一份临时 `deploy.env`，`MODE=node`），可用来起**后端**。但注意：
> ① 它 **不做建表**（仍需 §4.2）；② 它**只起后端 + 沙箱侧车**，不起网关/前端（那是 `MODE=all` 那台的事）。
> 现在 `SESSION_COOKIE_SECURE` / `CORS_ORIGINS` 已透传（本仓已修），HTTP 直连时把
> `SESSION_COOKIE_SECURE=false` 写进 `.env.node.shared` 即可。
> 两条路线（`infra/router/` compose 与 `deploy/` 脚本）**都对**，按团队习惯选一条，别混着用。

## 八、加第二台后端（与"多实例扩容"衔接）

本文的 B 就是**第一个后端实例**。按 P1-14 加第二、第三台后端（把沙箱分散到多台 Docker 宿主）：

1. 新机器上**重复 §四**：镜像 `docker load` → 两份 env 里改
   `SANDBOX_INSTANCE_ID`（`b`→`c`…，**每台唯一**）与 `SANDBOX_INSTANCE_ADVERTISE_ADDR`（填自己的 IP）；
   共用 C 的 PG/Redis/MinIO（**同一套**，目录与队列都在里面）；
2. 新实例**不必再跑迁移**（§4.2 只在新库上跑一次，库是共用的）；
3. 让网关 D 认识它 —— 二选一（见 §五"单台 vs 多台"）：
   - 静态：`ROUTER_UPSTREAMS` 追加 `,<B2_IP>:13000`（改完重启网关容器）；
   - 自动发现（推荐）：网关已设 `ROUTER_DISCOVERY_SEC=10`，新后端启动后心跳自注册，**网关不用重启**；
4. **A（前端）与 D 的接线不变** —— 前端仍只连一个同源 `/api`，后端台数对它透明。

⚠️ 加实例时最容易漏的一步：**新实例的 IP 必须能被 D 与其它后端访问到**（`ADVERTISE_ADDR` 用内网 IP，
不能写 `127.0.0.1`；否则网关回连/路由会打到它自己）。

详见 `docs/子方案/沙箱多机部署.md`（路线 A：每机一实例 + 按会话粘性路由）。
