## 坑 1：`06` 的坑预判"注意路由注册顺序"是错的（说明 → 求证 → 改结论）

**原文**（`06` P0-1-11 坑预判）：

> 全员可读接口与 `(A)` 管理接口同路径 → 用方法+查询参数分流，注意路由注册顺序

**先花两条命令求证**（`06` §六 的纪律：坑预判可能本身是错的），探针脚本用 `find-my-way` 的真实行为：

```js
// 探针 1：同路径同方法注册两次
app.get('/api/models', handlerA)
app.get('/api/models', handlerB)     // → ?
// 探针 2：静态段 vs 参数段
app.get('/api/models/:id', paramHandler)
app.get('/api/models/available', staticHandler)
```

**实测输出**：

```
✅ 同路径两个 GET 在注册期就失败： FST_ERR_DUPLICATED_ROUTE | Method 'GET' already declared for route '/api/models'
静态段优先？ 200 {"hit":"static"}
```

**结论（与坑预判不同）**：

- 坑预判担心的"注册顺序"**根本不是问题** —— `find-my-way` 静态段优先，`/api/models/available`
  不会被 `/api/models/:id` 抢先匹配（本项目在 `:id` 上只注册了 `PATCH`/`DELETE`，连冲突都没有）。
- 真正会炸的是"同路径注册两个 GET"，而且**炸在启动期**（进程起不来），不是请求期。也就是说
  "用方法+查询参数分流"**做不到**（`GET /api/models` 只能有一个 handler）。
- 所以**必须拆路径**。反过来，"注册顺序"这条在 verify 里也不该写成断言 ——
  真正值得断言的是"两条 GET 路径各自是真路由、且 `GET /api/models/:id` 不存在"。
  `verify-app.mjs` 里已按这个写（用 `app.hasRoute` + 匿名请求的 401/404 取证）。

> 教训：**"注意顺序"这类模糊预判，要么证伪、要么补上可执行的形态**。写成"注意顺序"等于没写 ——
> 照着做也躲不开真正的失败模式。

## 坑 2：两套投影**按角色分**会违反自家验收门槛（本批最要紧的一条）

`02` §4.3 原表把两个用途写在同一条 `GET /api/models` 上：

| 用途 | 谁用 | 需要什么 |
|------|------|---------|
| 管理列表 | `/admin/models` 管理页（ADMIN） | 看得见 `enabled=false` 的、要分页、要 `agentCount` |
| 全员可选列表 | `03` §4.2 智能体编辑页的模型下拉 | **只含"能用的"**、精简投影 |

**第一条看起来可行的方案是"按角色决定返回哪套投影"。它错得很隐蔽**：

`03` §4.2 的智能体编辑页用同一份列表渲染下拉，而 **ADMIN 也要建智能体**。按角色分 ⇒
ADMIN 拿到的是"管理投影" ⇒ **ADMIN 的模型下拉里会出现 `enabled=false` 的模型** ⇒
直接违反 `01` §3.2 的验收要点「无效模型创建 Agent 时不可选」。同一份代码，换个身份就违反自己的门槛。

**最终方案：按用途分路径，与身份无关。**

| 端点 | 权限 | 投影 |
|------|------|------|
| `GET /api/models` | 仅 ADMIN | `ModelItem`（含 `enabled`/`agentCount`/`providerEnabled`） |
| `GET /api/models/available?type=` | 登录即可 | `ModelOption`（无 `enabled`、无 `agentCount`、无时间戳） |

这与 `/api/users`、`/api/model-providers` 的摆法一致：资源根的 `(A)` CRUD 在根路径，
"视图型"的子集走子路径。`03` §116 的 `GET /api/models?type=CHAT` 已同步改为
`GET /api/models/available?type=CHAT`。

**验收怎么钉死这件事**：`verify-models.mjs` 里有一条用例**用 ADMIN 身份**打 `available`，
断言它同样看不到停用项；另有一条断言两套投影的键集合互不串味（可选项里不得出现
`enabled`/`agentCount`/`createdAt`/`updatedAt`，且响应体字符串级不含 `agentCount`）。

> 教训：**"按调用者身份给不同投影"看着省一个路径，实际把权限逻辑和展示逻辑搅在一起** ——
> 而且最容易漏掉的就是"管理员也是普通用户"这一半。

## 坑 3：zod v3 的 `required_error` 与 `errorMap` **互斥，且在模块加载期抛错**

第一版把"必填"和"取值非法"两条文案都写在一个字段上：

```ts
type: z.enum(MODEL_TYPES, {
  required_error: `type 必填（${MODEL_TYPES.join('/')}）…`,
  errorMap: () => ({ message: `type 只能是 ${MODEL_TYPES.join('/')}` }),
})
```

**现象**：`pnpm -r build` 与 `pnpm -r typecheck` **全绿**；一跑 `verify:app` 进程就死：

```
Error: Can't use "invalid_type_error" or "required_error" in conjunction with custom error map.
    at Module.createZodEnum (.../zod/v3/types.js:3027:12)
    at file:///.../shared/dist/model.js:129:17
```

两个要点：

1. 它是**模块加载期** `throw`（构造 schema 时就抛），不是校验期 —— 所以表现是"整个进程
   import 就死"，错误信息里指向的是 zod 内部，不看堆栈很难联想到是 schema 定义写错。
2. **`typecheck` 完全查不出来**（是运行期约束，不是类型约束）。

**对策**：删掉 `required_error`，把"必填"文案交给 `errorMap` 分派：

```ts
type: z.enum(MODEL_TYPES, {
  errorMap: (issue) =>
    issue.code === 'invalid_type'
      ? { message: `type 必填（${MODEL_TYPES.join('/')}）：这个端点只用来填"选模型"的下拉` }
      : { message: `type 只能是 ${MODEL_TYPES.join('/')}` },
})
```

并加一条断言守住它（`verify-app.mjs`）：缺 `?type=` 时，`data.fields` 里
`querystring.type` 的 **message 必须含「必填」** —— 否则"必填语义被降级成通用类型错误"这种
退化不会被发现；大小写写错时则必须提示合法取值 `CHAT/EMBEDDING`。

> 教训：**schema 定义层的 API 误用，`typecheck` 是拦不住的**。所以"契约类断言"必须真跑一次
> import + 一次 `safeParse`，不能只靠构建通过。

## 坑 4：`available` 的 `type` 必须**必填**（不是可选）

`available` 的唯一用途是填"选模型"的下拉（`03` §4.2）。对话模型与向量模型**不可互换**：

- 若 `type` 有默认值（比如默认 `CHAT`），那么"忘了传"的调用方会拿到一堆 CHAT 模型；
  若它拿去填向量库（P0-1-13 的 embedding 配置），**不会报任何错**，只会在检索时表现为
  "结果莫名其妙" —— 静默产生垃圾向量的典型路径。
- 必填 + 400 把这件事变成"配置时就知道"。

断言：`listAvailableModelsQuerySchema.safeParse({})` 必须失败，且 HTTP 层返回 400 +
`querystring.type` 明细（校验先于鉴权，所以匿名请求也能验）。

## 坑 5：**Provider 停用** ⇒ 其模型也不可选

`01` §3.2 只有一句「无效模型创建 Agent 时不可选」，落地时容易只对应到 `models.enabled`。
但"用不了"还有另一种形态：**`model_providers.enabled = false`**。

只筛 `models.enabled` 的后果：可选列表里给出一个"能选、能建 Agent、**一发消息就失败**"的模型
—— 比不显示它更坑（用户会以为是自己配错了 Agent）。

**对策**：`where: { type, enabled: true, provider: { enabled: true } }`，三个条件缺一不可。
`verify-models.mjs` 有一条专门用例：停用 Provider → 模型从可选列表消失，**且模型自身的
`enabled` 不被动过**（"停用 Provider"不等于"停用模型"，两者拆开才能只恢复一半），
`providerEnabled` 在管理投影里如实反映。

## 坑 6：`providerId` 要**放进** PATCH 契约（为了能显式报错）

模型"迁移到另一个 Provider"是**不支持**的（会静默改变"已绑定 Agent 走的是哪个上游"）。
但实现上有两条路：

| 做法 | 行为 | 问题 |
|------|------|------|
| 字段**不在** schema 里 | zod 默认剥掉多余键 → `{providerId: 别的}` 返回 **200**，什么都没改 | 调用方以为迁移成功了 —— 静默 no-op |
| 字段**在** schema 里，服务层比对 | 值不同 → **409** 并给可执行文案；同值放行（幂等） | 多几行代码，但意图可见 |

选后者。同值放行是为了前端的"整表单提交"（没改的字段原样送上来）不该失败 ——
与 P0-1-10「改 type 时同值放行」同一口径。

顺带被这条钉住的另一件事：**未知键不会静默通过**。`updateModelBodySchema.safeParse({foo: 1})`
必须失败 —— 剥掉 `foo` 之后没有任何字段，于是命中 `.refine(至少给一个字段)`。
这样 `{"foo": 1}` 不会返回 200 让人误以为改成功了。

## 坑 7：`@@unique` 含 `type` ⇒ 同名不同 type **必须放行**

`models` 的唯一键是 `(provider_id, model_name, type)`。`schema.prisma` 的注释已经写明理由：

> 带 `type` 是因为同一型号名可能既提供 chat 又提供 embedding（如 bge 系列的兼容端点），
> 不带 type 会把这种合法情况误判成重复。

所以服务层**刻意不校验**「`models.type` 必须等于 `model_providers.type`」——
那属于自己发明约束，会把合法配置挡在门外。
`verify-models.mjs` 有一条用例专门证明"同一个型号名换 `type` 建第二条 → 200 放行"。

> 这条值得单独记：**唯一索引的列集合就是业务规则的表达**，加校验前先读索引。

## 坑 8：清理段用 `delete` 会污染断言输出

第一版清理写成"逐个 `prisma.model.delete({ where: { id } })` + `.catch(() => undefined)`"。
问题：用例自己删过的记录也在清单里，于是清理阶段会为每一条不存在的记录触发 `P2025`，
而 **Prisma 的查询日志会把整个堆栈打到 stdout**：

```
{"level":"error",...,"target":"model.delete","msg":"\nInvalid `prisma.model.delete()` invocation:\n...No record was found for a delete."}
```

`.catch()` 吞掉的是异常，**吞不掉已打出的日志** —— 而验收脚本的 stdout 就是断言结果本身
（`06` §六 的"收敛脚本自身日志"纪律）。

**对策**：清理一律用 `deleteMany({ where: { ... } })`（返回 count，空删不抛），
清理阶段的"目标已经不在"变成正常情况。

## 坑 9：`model_name` 拒**内部空白**

`modelName` 是**上游真实型号名**，会原样放进请求体的 `model` 字段。上游 model id 从不含空格
（`gpt-4o-mini` / `text-embedding-3-small` / `us.anthropic.claude-3-5-sonnet` / `bge-m3` / `qwen2.5:7b`），
而"从文档粘过来"最常见的脏数据是**尾随空格/换行**（`trim` 就够）。

- 尾随的 → `trim` 吃掉（不打扰用户）；
- **内部的** → 直接拒（`/^\S+$/`）。放行下去只会在**第一次调用上游时**变成一个 404/400，
  排查成本远高于现在就告诉管理员"这个型号名不对"。

`label`（别名）不设这条限制 —— 它是给人看的，可以中文、可以带空格。
