# 问题记录 — P1-17 模型流静默卡住（TaskAgent 一轮"卡约 6 分钟"）

> 批次：P1-17（补充修订）
> 日期：2026-10-15
> 关联：`docs/06-实施计划.md` §五 P1-17（补充块）/ §六 施工纪律 3；`docs/子方案/沙箱与引擎集成.md` §四 3（出口①）
> 定位：本文件记录"真跑暴露的一处静默卡死"的现象、定位过程、根因与修法。计划文件只留一行指针。

---

## 现象

用户在平台里发一条指令（"demo 下的 test_case 新增了一个 debug 文件。你在里面帮我新增一个 py 文件吧"）后，
**界面一直转圈、约 6 分钟没有任何新内容**，随后答案一次性全部出现。用户报告原话："中间 agent 的回复有一个很大时间卡住了"。

## 定位过程（全部落在可复现的证据上）

1. **平台侧**：`TaskAgent 本轮结束` 的 `durationMs=477445`、**`ttftMs=468241`**（首字延迟 ≈ 整轮耗时）、`rounds=11`、`toolCalls=18`。
   ⇒ "卡"发生在**第一个正文 token 之前**，且几乎占满整轮。
2. **后端日志空窗**：其间只有 60s 一次的维护日志，该 `requestId` 从 16:57:28 到 17:03:32 **一条都没有**。
   ⇒ 模型请求不在后端这条链上，而在**容器内的 pi 引擎**里（引擎直连 `baseUrl`）。
3. **容器日志**（`docker logs <engine-container>`）——决定性证据：

   ```
   16:57:23.346  {"type":"turn_start"}
   16:57:28.438  {"type":"message_start", ..., "stopReason":"pending"}     ← 响应头到了
                 ⋯⋯ 静默 355.7s（引擎零事件）⋯⋯
   17:03:24.180  {"type":"message_end", "stopReason":"error", "errorMessage":"terminated"}  ← 对端断开
   17:03:24.187  {"type":"auto_retry_start","attempt":1,"maxAttempts":3,"delayMs":2000,"errorMessage":"terminated"}
   17:03:26.190  {"type":"agent_start"} / {"type":"turn_start"}            ← 引擎自动重试
   17:03:41.470  {"type":"auto_retry_end","success":true,"attempt":1}      ← 重试一次即成功
   ```

   ⇒ **上游"回了响应头、正文 356s 一个字节都没有"，随后被对端掐断**；引擎自己的 `auto_retry` 重发
   **那一次 provider 请求**后成功。也就是说：不是平台坏了，是**没人在这条链上给"流空闲"设判据**。

## 根因

整条链上三处都不管"隧道建成后的静默"：

| 处 | 现状 | 为什么没兜住 |
|----|------|--------------|
| `LLM_REQUEST_TIMEOUT_MS=30000` | 「到响应头」上限 | 头 16:57:28 就到了 ⇒ 不生效 |
| `LLM_STREAM_IDLE_TIMEOUT_MS=120000` | 后端自己调 LLM 的路径（ChatBot） | TaskAgent 的模型调用在**容器内的 pi 引擎**里 ⇒ 管不到 |
| 出网代理 `egress-proxy.mjs` | 隧道建成后 `setTimeout(0)` | 原注释即"不对已建立的隧道设 idle 超时"（怕误杀慢响应） |

## 修法（**分相位**：只有"等模型"算静默异常）

> 判据要点：正常模型流会**持续吐 delta**（一次真跑里 `thinking_delta 549 + text_delta 106`）；
> 而工具相位（`bash` 跑 npm/pytest）**本来就可能长时间零输出** ⇒ 两者必须用不同规则，否则必然误杀。

1. **出网代理（快速自愈，不动引擎）**：策略文件增 `modelHosts`（模型池主机），代理对**这些目标**在隧道
   建成后保留一个空闲上限 `EGRESS_MODEL_IDLE_TIMEOUT_MS`（默认 180s；0 = 关），静默到上限即**掐断** ⇒
   容器里的引擎收到流错误 ⇒ **引擎自己的 `auto_retry` 只重发那一次 provider 请求**（不重跑整轮工具）。
   非模型目标（registry / git）仍 `setTimeout(0)`。
2. **平台可见性（不中止）**：`taskAgent.ts` 增**模型相位静默看门狗** —— `turn_start` / `message_start{role:assistant}`
   起算"等模型"相位，`tool_execution_*` / `turn_end` / `agent_*` 离开该相位；处于该相位且
   `MODEL_SILENCE_NOTICE_MS=60s` 无任何引擎事件 ⇒ 推一条 `status` 帧。
3. ⚠️ **平台侧刻意不做 abort/重试**：平台只能整轮重发，那会把这一轮已经跑过的工具再跑一遍（本例里文件已写完）
   —— 粒度不对；粒度正确的重试只有引擎能做（它是 per-provider-request 的）。

## 施工中抓到的坑（写下来是因为**纯读代码看不出来**）**坑 1 — idle 回调接到 `fail()` 上 = 永不生效**：初版把空闲回调写成 `fail('模型流空闲超时')`，而 `fail()` 的
`settled` 守卫在 `upstream.on('connect')` 那一刻**已经置 true**（原设计里 `fail` 只服务"建连期失败"）⇒
回调被静默吞掉、隧道永不掐断。**新冒烟 `pnpm egress:idle-smoke` 当场抓到**（命中组 `closedMs≈∞` 而非 ≈idle），
改法是在回调里直接销毁两个 socket（并打 `CUT` 日志 + 审计）。

**坑 2 — 相位判据不能用"整轮静默"**：`turn_start` 之后的同一个 turn 里**也会跑工具**（工具调用→工具结果→`turn_end`）；
若按"整轮静默"判死，长 `npm ci` / `pytest` 会被误判成卡死。故必须显式维护"是否在等模型"。

**坑 3 — 重启代理时撞出两个 bash 3.2 兼容 bug（与本次改动无关，属 P1-16a 起的潜伏问题）**：
本机 `bash` = macOS 自带 **3.2.57**（`/bin/bash`），两条老写法在它上面会直接报错退出，导致
`bash infra/scripts/egress-up.sh` 起不来：

| 位置 | 症状 | 修法 |
|------|------|------|
| `egress-up.sh#csv_to_array`（原 `eval "$name=(\"\${out[@]}\")"`） | 空数组 + `set -u` ⇒ `out[@]: unbound variable`（`.env` 没配 `SANDBOX_EGRESS_REGISTRY_HOSTS`/`GIT_HOSTS` 时必现） | 用 `[ "${#out[@]}" -gt 0 ]` 分两支：非空 `eval` 展开，空则 `eval "$name=()"` |
| `egress-down.sh:48` `（pid $WATCH_PID）` | `$VAR` **紧跟全角字符** ⇒ bash 3.2 把多字节字符首字节当成变量名的一部分 ⇒ `WATCH_PID?: unbound variable` | 写成 `${WATCH_PID}`（变量名用花括号界定） |

⚠️ 同类的**仍潜伏**（本次未改，超出范围）：`dev-stop.sh:95` 的 `（$portpids）` 与 `:139` 的 `$pid，`
—— 同样是 `$VAR` 紧跟全角标点。修法同上（补花括号）。
为什么之前没炸：跑着的代理容器是 **2026-10-13** 建的（早于 P1-16a 引入 `csv_to_array`），
且 `--daemon` 的同步进程早已死掉（`.pids/egress-watch.pid` 里留着死 pid）⇒ 两条路径都没被走到。

## 自证与真跑

- 自证：`pnpm -r typecheck`（三包 Done，Node 22）+ 改动文件 `eslint` + `pnpm check:batch` +
  `pnpm egress:regression`（16/0）+ **`pnpm egress:idle-smoke` 通过**（命中 `modelHosts` ⇒ 静默 1500ms 后掐断，
  实测 1504ms；不在名单 ⇒ 静默 6s 仍保持）。
- **真跑取证留给用户**：`bash infra/scripts/egress-up.sh --daemon`（**代理进程需重启才加载新代码/新 env**）⇒
  再遇上游静默应在 ≤180s 掐断并由引擎自动重试；界面静默 ≥60s 应出现"上游模型已 Ns 无响应…"。
