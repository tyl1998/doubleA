## 坑 1 ⚠️ 权限第四族：给"顺手加个后门"留出的是隐私事故，不是便利

**现象**：`06` / `02` 在 P0-1-25 之前只写了**三族**权限口径，且文件里有专门的"三族对照表"：

| 资源 | owner 列 | 权限 |
|------|---------|------|
| `/api/users`、`/api/model-providers`、`/api/models` | 无 | ADMIN |
| `/api/models/available`、`/api/knowledge-bases/*` | 无 | 登录即可 |
| `/api/agents` | `created_by` | 建/看登录即可；编/删 = 创建者 + ADMIN |

会话是本批第一次出现的、**有 owner 列（`user_id`）且 owner 就是唯一有权者**的资源。
照抄邻居必然出错：抄知识库 → 任何登录用户都能读别人的聊天记录；抄智能体 → 加个 `|| role === 'ADMIN'` 就变成
"管理员可读全站私聊"。

**根因**：`01`/`02`/`03` **没有一处**说管理员要能看别人的会话 —— 给 ADMIN 开口子属于**自己发明权限**，
而且方向是"读别人的私密对话"。这不是"多一个便利"，是**隐私升级**。

**对策**：把"越权实现"做成**写不出来**，而不是靠注释劝：

```ts
// services/conversation.service.ts
/**
 * 调用者 —— **只有 `id`，刻意没有 `role`**。
 * 与 `AgentViewer`（`{ id, role }`）的差别不是省事：那个资源要按角色判权，这个资源**不该按角色判**
 * —— 少一个字段，就越权实现无处落脚。
 */
export interface ConversationViewer {
  id: string
}
```

外加两条结构约束：

1. **判据不写成函数** —— 本文件**没有** `canEditConversation`，判据就是 `where: { id, userId: viewer.id }`。
   它只有"是不是你的"这一种答案，落在查询条件里比落在一个布尔函数里更难写错（也不存在"判了但顺序反了"）。
2. **别人的会话与不存在的 id 返回同一个 404**（不是 403）—— 403 等于**确认这个 id 有效**，
   而会话 id 不出现在任何对他人可见的列表里，**藏得住**。

**原始输出**：

```text
── C 权限：**仅创建者本人**（他人 404 · ADMIN 也 404 · 本人 200） ──
   三族以外还有第四族：会话。`conversations.user_id` 是唯一判据 —— 连 ADMIN 也没有后门
  [PASS] 他人读/改/删 → 404；**ADMIN 也 404**；本人 → 200（三个方向都验，只验一路会漏）
```

**⚠️ 顺带记一条验收纪律**：这一组**必须三个方向都验**（他人 404 **且** ADMIN 404 **且** 本人 200）。
只验"他人 404"的话，一个"仅创建者 + ADMIN"的实现会全绿 —— 而它正是本批**刻意不做**的那个（P0-1-22/23 的同款反向守卫）。

## 坑 2 ⚠️ 一条"没有 HTTP 出口"的口径：`last_message_at` 的维护时点

**现象**：`06` 的坑预判原文是「`last_message_at` 在消息落库时更新，而非在发起请求时（否则停止后仍算活跃）」。
但本批**没有写消息的端点**（`POST /:id/chat` 属 P0-1-26）⇒ 这个时点在本批**没有任何 HTTP 出口能验**。

在"发起请求时"更新的实现，症状写在用户看得见的地方：一个**点了停止**（或上游报错、或断线）的会话
仍然会被算成"刚刚活跃"、被顶到侧栏最前，而它其实**一条新消息都没有**。

**根因**：这是一条"只在下游批次才被消费"的口径。若本批不处理，P0-1-27 会各自实现一遍
（"消息落库"与"更新活跃时间"变成两次写入），同一口径复制成两份 —— 而后一份大概率会丢掉"只前进不后退"。

**对策**：把它做成**一个可以单独调用的函数**，由验收脚本直接调。

```ts
export type ConversationTouchClient = Pick<PrismaClientInstance, 'conversation'>

export async function touchConversation(
  db: ConversationTouchClient, conversationId: string, at: Date,
): Promise<boolean> {
  const result = await db.conversation.updateMany({
    where: { id: conversationId, OR: [{ lastMessageAt: null }, { lastMessageAt: { lt: at } }] },
    data: { lastMessageAt: at },
  })
  return result.count > 0
}
```

三处刻意：

1. **签名收 `Pick<PrismaClientInstance,'conversation'>` 而不是自己开事务** ——
   **正是为了能被 P0-1-27 的 `$transaction(async (tx) => …)` 直接传入**（"整条消息落库 + 更新活跃时间"必须同一事务）。
2. **"只前进不后退"用 CAS 表达**（`OR: [null, { lt: at }]`）而不是"先读再比"：
   后者在两处并发落库时会**同时通过判断**、**后到的旧值把新值盖回去**（时间倒流，会话在侧栏里"掉下去"）；
   单语句形式还天然幂等（重投同一个 job 不会把时间戳改坏）。
3. **刻意不顺手把 `status` 改回 `ACTIVE`** —— `FINISHED` 是"Agent 被软删"留下的只读标记，
   在这里复活状态会让 P0-1-24 门槛④ 的"只读保留"**悄悄失效**。

**原始输出**：

```text
── G `touchConversation`：`last_message_at` 的"只前进不后退"（给 P0-1-27 用） ──
   本批没有写消息的端点 ⇒ 这个时点（`06` 的坑预判）只能在这一档钉；含"能在事务里用"
  [PASS] `null` → 设值；更早的 → 不动（返回 false，库里逐字不变）；更晚的 → 前进
  [PASS] ⚠️ 能在**事务里**调用（P0-1-27 是"整条消息落库 + 更新活跃时间"同一事务）
```

## 坑 3 ⚠️ `nulls:'first'` 必须显式写：错了的症状是"新建了会话却看不见它"

**现象**：`conversations.last_message_at` 可空，**且新建时就是 `null`**（没有自动命名、没有首条消息）。
排序口径是"按最近活跃倒序" ⇒ 新会话要排**最前**。

PG 的 `ORDER BY … DESC` 默认就是 `NULLS FIRST`，所以一个**漏写 `nulls` 的实现本机全绿**，
看起来完全正常 —— 直到有人把 PG 版本/方言换掉，或者加了别的排序键。

**根因**：靠（未写出的）数据库默认值，等于把**顺序语义寄存在数据库的实现细节上**。
而这条错了的症状对用户极不友好：**新建了会话，侧栏里看不见它** —— 用户的第一反应是"新建没成功"，
第二反应是"这软件坏了"，**排查方向完全指反**。

**对策**：显式写，并配一条专门的断言（新会话必须出现在第一条）：

```ts
orderBy: [
  { lastMessageAt: { sort: 'desc', nulls: 'first' } },   // ← 必须显式
  { createdAt: 'desc' },                                  // null 之间再兜底
  { id: 'desc' },                                         // 确定性是分页的刚需
],
```

**另一处刻意**：`toItem` 里 `lastMessageAt: row.lastMessageAt === null ? null : …` ——
**不回落到 `createdAt`**：那会让"还没消息"与"刚发了消息"在界面上无法区分，而"最后活跃时间"正是侧栏唯一要显示的东西。
另外这个排序与 §4.4 的 `updatedAt desc`、§4.6 的 `createdAt desc` **都不同**，理由在**触发源**：
会话的排序键是"**有没有人在说话**"，不是"这行被改过没有"（文档的 `updated_at` 会被后台流水线改，会污染排序）。

**原始输出**：

```text
── B 列表按最近活跃排序（含"新会话排最前"与分页） ──
   排序 `lastMessageAt desc, nulls:'first', createdAt desc, id desc`
  [PASS] 新会话（`lastMessageAt = null`）**排最前**；再按"最近活跃"倒序；分页三件套齐全
```

## 坑 4 ⚠️ `streaming` 是派生的：让矛盾态**在形态上不可能出现**

**现象**：`/active` 要回四件套（是否在流 / 排队位次 / 当前工具 / 起始时间）。最直觉的写法是
把这四个字段一起存进 Redis，读的时候整个取回来 —— 于是"键在但 `streaming:false`"或
"键没了但 `queuedPosition:3`"这类**自相矛盾**的状态**在形态上是可表达的**，
而它们一旦出现，前端的重连逻辑会走进死路。

**根因**：`streaming` 与"键在不在"是**同一件事**，被当成两个独立字段存就会漂移。

**对策**：`streaming` **不存**，由键的存在性派生；值里的细节走永不抛错的 `parseActiveSnapshot`。

```ts
const raw = await getRedis().get(chatActiveKey(id))
if (raw === null) return { streaming: false, ...EMPTY_ACTIVE_SNAPSHOT }
const snapshot = parseActiveSnapshot(raw)   // 逐字段降级，永不抛错
return { streaming: true, ...snapshot }
```

另外两条：

- **先查库、再查 Redis**：不是我的会话 / 不存在的会话一律 **404**，**不是**回 `{streaming:false}` ——
  后者会让前端把"会话被删了"当成"当前没在生成"，用户会盯着一个**永远不会有回复**的页面。
- **不为 Redis 故障做特殊兜底**：`requireAuth` 已经保证这一刻 Redis 是通的（`02` §十：Redis 故障 → 500 不放行），
  在这里再包一层只会**掩盖真实故障**。

**原始输出**：

```text
── F `/active` 读侧（`02` §5.2 断线重连） ──
   无流恒为 `{streaming:false, …null}`；键在 ⇒ streaming=true（**派生**）；值坏降级不 500
  [PASS] 无流：恒为 `{streaming:false, queuedPosition:null, currentTool:null, startedAt:null}`
  [PASS] 有流：键在 ⇒ `streaming:true` 且"排队位次 / 当前工具"回显（**值坏也只降级、不 500**）
  [PASS] 纯函数 `parseActiveSnapshot`：合法值逐字保留，各种脏值**逐字段**降级且永不抛错
```

⚠️ **本批的 `/active` 恒为无流**（写侧 `chat.active:{id}` 属 P0-1-26）⇒ 验收里的"有流"分支
只能由脚本**直接往那个键里写一份快照**来验（等价取证，已在脚本里注明）。README 的已知边界也写了这一条。

## 坑 5 ⚠️ 自己写出来的假断言：`JSON.stringify` 比对象会被**键序**咬

**现象**：F 组一开始全红，报的是"响应与预期不等"，而打印出来的两个对象**看起来一模一样**。

```text
[FAIL] 有流：键在 ⇒ `streaming:true` …
       实际 {"queuedPosition":1,"currentTool":"search","startedAt":"…","streaming":true}
       预期 {"streaming":true,"queuedPosition":1,"currentTool":"search","startedAt":"…"}
```

**根因**：`conversationActiveSchema = conversationActiveSnapshotSchema.extend({ streaming })`
—— zod 的 `.extend()` 把新键**追加在末尾**，而预期值是手写的、把 `streaming` 写在了最前。
`JSON.stringify` 是**键序敏感**的 ⇒ 内容相同、顺序不同就被判不等。

**对策**：加一个**键序无关**的深比较助手，并把脚本里所有对象比较都换成它（值比较仍走 `assertEqual`）：

```js
/** 深比较但**忽略键序**（zod `.extend()` 会把新键追加到末尾，用 JSON.stringify 比会假红） */
function assertSameObject(actual, expected, label) { … }
```

⚠️ 这是**断言自己写错**，不是实现问题 —— 与 P0-1-20 的两个假失败是同一族
（"假红比假绿好，但它会浪费一轮排查"). 留档的价值：**下次加 `.extend()` 字段时不用重新踩一遍**。

## 坑 6 收尾时的两个自伤：变量改名漏一处 + 模板字符串拼接

**现象**：两个都是**脚本自己**的错，都把验收卡在"跑不起来"上：

1. `ReferenceError: touchedActiveKeys is not defined` —— 我把某个 `Set` 从 `touchedActiveKeys` 改名为
   `activeKeysWritten`，`replace_all` 之外的**一处**漏了（第 226 行）。
2. `verify-agent-package.mjs` 的 `SyntaxError: missing ) after argument list` —— 结论行的
   `console.log` 模板字符串里有一处 `+` 续行写坏（在长文本里极难肉眼定位）。

**根因**：改名与长模板串都是"**改一处、看另一处**"的活。前者靠 `tsc`/断言抓不到（脚本是 `.mjs`、没类型检查），
后者要等**解析期**才炸且报错位置在长串尾部。

**对策**：

- 脚本改名后用 `grep -n '<旧名>'` 复核一遍（**改名必须留一次搜索**，这条已在 P0-1-23/24 出现过多回）。
- 长结论串**不要用 `+` 续行**：拆成多个 `console.log`，或用模板字符串内的换行。分段比"一根长绳"更难拼错，
  而且报错位置更有信息量。

⚠️ 这两条都不是项目的坑，但**每次收尾都会遇到**（本批各花了一轮），值得记在这里提醒下一个人：
**`verify:*` 脚本本身没有类型检查，改它等于在没有安全网的地方动刀**。

## 坑 7 ⚠️ 全量回归抓到一条**上一批留下的陈旧断言**（本批最值钱的一条）

**现象**：三档"本批相关"的脚本全绿之后跑全量回归，`verify-agents` 红了：

```text
── F 组 · 路由表：六条已注册，P1 / P0-1-25 的刻意不存在 ──
  [FAIL] 六条路由都在，且"尚未做"的两条一律 404（不提前注册）
         会话列表属 P0-1-25：期望 false，实际 true
```

**根因**：`verify-agents.mjs` 里那条"**刻意未注册**"的断言（P0-1-22 写下、P0-1-24 沿用）：

```js
assertEqual(app.hasRoute({ method: 'GET', url: '/api/agents/:id/conversations' }), false, '会话列表属 P0-1-25')
```

它当时的**作用是好的** —— 挡住"顺手把下一批的活提前做了"。但它是一条**有保质期的断言**：
本批落地那条路由之后，它就从"守门"变成了"陈旧"，而**它报的红不是回归，是"该翻转了"**。

**为什么只有全量回归能抓到**：本批我改了三处脚本（新增 `verify-conversations`、扩 `verify-app` 第 25 节、
回补 `verify-agent-package` 的 R4），这三处全绿；而**`verify-agents` 不在"本批相关"的清单里**，
它属于"上一批的档"。只跑本批相关的档 ⇒ 这条永远发现不了（它会一直红到某个未来批次，或者更糟：
被下一个人当成"已知问题"忽略过去）。

**对策**：

1. **翻转断言并保留"翻转痕迹"**（与本批在 `verify-app.mjs` 里做的一致）——
   `false → true`，注释写明"P0-1-24 时这里是 `false`，P0-1-25 落地后翻转"，`it` 标题也从
   "六条路由"改成"七条路由（含 P0-1-25 的会话列表），仅'复制'是 P1"：

```js
// ⚠️ 同上：P0-1-24 时这里写的是 `false`（"会话列表属 P0-1-25"）；P0-1-25 落地后翻转为 `true`
assertEqual(app.hasRoute({ method: 'GET', url: '/api/agents/:id/conversations' }), true, '会话列表（P0-1-25 已落地）')
```

2. **一条"不存在的 agent 一律 404"的断言不用改** —— 路由存在与"不存在的 id 回 404"是两件事，
   那条断言在翻转之后**依然成立**（而且现在真的走到了新路由里）。

**复跑输出**：

```text
── F 组 · 路由表：七条已注册（含 P0-1-25 的会话列表），仅"复制"（P1）刻意不存在 ──
  [PASS] 七条路由都在（含 P0-1-25 的会话列表），仅"复制"是 P1；不存在的 agent 一律 404

✅ P0-1-22/23 智能体验收通过：35 项全通过
```

**📌 留给后面批次的规矩（建议写进施工清单）**：**"刻意未注册"型断言是有保质期的** ——
凡断言里出现"属 P0-1-XX（未来批次）"，那个批次落地时**必须**回来翻转它。本批在 `verify-app.mjs`
与 `verify-agents.mjs` 各翻了一条（`PUT …/components` 是 P0-1-23 那次翻的，本批翻会话列表这条）。
**加一条"收尾时必须跑全量回归"的硬理由就在这里**：本批相关的三档全绿而 `verify-agents` 红，
说明"只跑相关的"会漏掉**由本批引起、但不落在本批脚本里**的断言。
