## 坑 1 — 种子脚本的「幂等」是安全属性

**现象**：设计种子脚本时最容易写成"每次都把 admin 密码设成固定值"（对开发方便）。
**根因**：`pnpm db:seed` 会被反复执行 —— `db:deploy` 之后、重装环境、CI 起库、别人接手你的库。
若每次都覆盖密码，**已经自己改过密码的人会在下一次 seed 后突然登录不上**，
而症状（401）与"密码记错了"完全一样，是最难查的一类假故障。
**对策**（`prisma/seed.ts`）：

- 默认：`findUnique` → 存在则**跳过并明确打印"已存在（密码未改动）"**（什么都不写）；
- 覆盖密码必须显式：`SEED_RESET_PASSWORD=1`（同时把该账号打回**首登改密态**，
  语义等价于 admin 点了"重置密码"）；
- 并发竞态：还带一个 `P2002` 兜底（两个进程同时 seed 时当作"已存在"）。
- 验收侧用**密码哈希逐字比对**证明这一条（不是只看 stdout）：
  第二次 seed 后 `password_hash` 必须与第一次完全一致。

**顺带一条**：这个脚本必须**先有鸡还是先有蛋**地存在 —— `POST /api/users` 要求调用者是 ADMIN，
而系统里第一个 ADMIN 没有别的地方生成。README「怎么拿到第一个账号」指的就是它。

## 坑 2 — 种子脚本的 console 不是"漏了 logger"

**现象**：`pnpm lint` 报 `no-console`。业务代码禁 console 是本仓铁律（`02` §十三：日志必须走 pino，
否则没有 requestId、没有脱敏）。
**根因**：种子脚本是 **CLI**，stdout 就是它的接口；初始密码的**唯一交付通道**就是那一次打印。
**对策**：`eslint.config.mjs` 的脚本 override 里加上 `**/prisma/seed.ts`（与 `**/scripts/**`、
`*.config.*` 同一档），注释写明"它不是在记日志，而是在交付一次性凭据"。
**安全侧并未放松**：密码只打到终端、不写日志文件；
`infra/logger.ts` 的 `LOG_REDACT_PATHS` 早就有 `initialPassword`（P0-1-8 加的），
"顺手 log 整个响应/对象"仍会被打码。

## 坑 3 — 种子脚本会被编译进 `dist`（好事，但有前提）

**发现**：`backend/tsconfig.json` 的 `include` 是 `["src/**/*.ts", "prisma.config.ts", "prisma/**/*.ts"]`，
而 `rootDir` 是 monorepo 根 → `prisma/seed.ts` 的产物是 `backend/dist/backend/prisma/seed.js`。
**为什么是好事**：

1. `verify-e2e.mjs` 可以直接 `spawn(node, ['dist/backend/prisma/seed.js'])` 来验种子脚本 ——
   不必依赖"tsx 怎么被调用"这种细节，验的也正好是**构建产物**（CI 会跑的那份）；
2. `pnpm -r typecheck` 天然覆盖它（strict + `noUncheckedIndexedAccess` 全开），
   不会出现"脚本不在类型检查范围内"的盲区。
**前提**：正因为要编译，`prisma/seed.ts` 里不能写只在 tsx 下成立的东西
（例如依赖 tsx 的路径别名、或指望 `.ts` 后缀被解析）。本脚本只用了 `.js` 后缀的相对导入，
与其它 src 文件一致。

## 坑 4 — 「端到端」的关键是换掉传输层

**背景**：P0-1-6/7/8 的四个验收脚本全部走 `app.inject`（Fastify 内部请求生命周期）。
它快、不占端口、能进 CI，但**跳过了 HTTP 传输层**：`Set-Cookie` 的序列化、Cookie 回传、
连接复用、`bodyLimit`、真实的 JSON 编解码都在那一层。
**对策**：本批的 `verify-e2e.mjs`

- `spawn(process.execPath, ['dist/backend/src/index.js'], { env: { BACKEND_PORT: <独立端口> } })` 起**真实进程**；
- 用 `fetch` 打 `http://127.0.0.1:<port>`，**手写 Cookie 罐**（只认 `doubulea_sid`，
  从 `getSetCookie()` 读、空值即清），全程不使用任何测试后门；
- 起服务前先探端口（见坑 5），起来后轮询 `/health` 直到 200（20s 上限），
  失败时把子进程日志一起打出来。

**价值**：本脚本能跑通 ⇔ **用户照着 README 敲 curl 也能跑通**（本批另用一份 14 步 curl 走查独立验证了这一点，
见验收记录 §3）。实测两种方式的行为**完全一致**（包括 403 文案、429 文案与 `data.retryAfterSec`），
说明 inject 那几条契约没白写 —— 但这是**验出来的**，不是假设出来的。

## 坑 5 — 子进程端口：起来之前先探一次

**现象（预判）**：端口被别的进程占着时，`listen` 会失败，但脚本的"等服务就绪"轮询会
**成功打到那个陌生服务上**（因为 TCP 是通的），症状变成一堆莫名其妙的 404/401。
**对策**：起进程前先 `fetch(/health)`：

- 有应答 → 明确报错并提示换端口（`E2E_PORT=13098 pnpm verify:e2e`）；
- 连不上 → 才是预期（端口空闲），继续 spawn。
另外默认端口取 **13099** 而不是 13000 —— 用户本机很可能正开着 dev 服务，
验收脚本不该去抢他正在看的那个端口。

## 坑 6 — `UID` 是 shell 的只读内置变量

**现象**（真机走查脚本里踩到）：`UID=$(curl … | python3 …)` 报 `UID: readonly variable`，
赋值失败但脚本继续跑 → 后续 `PATCH /api/users/` 带空 id → 400「用户 ID 不是合法 UUID」。
**根因**：`UID`/`EUID`/`PPID`/`SECONDS` 等在 bash 里是特殊/只读变量。
**对策**：业务变量改名（`TARGET_ID`）。写 shell 时先避让这一组名字。
**副产物**：这次失败的绝对值不大，但它演示了一个更普遍的风险 ——
**"脚本没报错"不等于"请求是对的"**；所以每个请求都断言了 HTTP 码与信封 `code`，
而不是只看 `curl` 有没有输出。

## 坑 7 — Node `fetch` 的多条 `Set-Cookie`

**结论**：`response.headers.getSetCookie()`（Node 18.14+ / 本机 22）才拿到**数组**；
`headers.get('set-cookie')` 会把多条合并成一条字符串（逗号分隔），
在"登录下发会话 Cookie + 清 Cookie"这类场景下会解析错。
本脚本的 Cookie 罐只认 `doubulea_sid` 且把空值当"清除"，因此登出路径也一并覆盖。

## 坑 8 — 「跑完干净」要写成断言

**对策**：`verify-e2e.mjs` 的清理不是 finally 里的"尽力而为"，而是：

1. 正常路径显式调 `cleanupTemporaryData()`（停服务 → 清 Redis → 按 **`verify-e2e-` 前缀**删账号）；
2. 紧接着**一条断言**：残留账号数 0、每个用过的用户名 `login-fail:*` 不存在、
   每个用过的 sid 的 `session:*` 不存在；
3. `finally` 里再调一次（幂等），覆盖异常路径。
**为什么按前缀而不是按内存清单**：跑到一半崩了，内存清单就丢了 —— 前缀清扫能把上一轮的残骸一起收掉。
（P0-1-7 的教训：清理范围要枚举全，包括"顺手创建的"键。）

## 坑 9（口径）— 门槛 3 的"业务 API"本仓还没有

`docs/06` P0-1-9 门槛 3 写的是"改密后可正常访问业务 API"，但**本仓此刻没有 MEMBER 可用的业务接口** ——
`/api/agents` 是 E 包（P0-1-22~24）的产出。若照字面找一个"业务 API"，只能拿到一个永远 403 的路径。
**对策**：用 **403 的文案**区分两条本质不同的 403：

- 改密前：`首次登录必须修改密码后才能使用其他功能`（闸门，`plugins/session.ts#installPasswordChangeGate`）；
- 改密后：`该操作仅限管理员`（权限，`requireAdmin`）。

断言"改密后 msg 必须**不再**含'修改密码'、且含'仅限管理员'"，等价于"闸门已放行 + 权限判定生效"。
等 E 包有了 `/api/agents`，这条可以升级成"直接 200"。

## 坑 10（流程）— 手工走查会留下"不可用状态"

**现象**：为了让用户拿到已知密码，先 `SEED_RESET_PASSWORD=1 SEED_ADMIN_PASSWORD=… pnpm db:seed`；
但 curl 走查第 ⑤ 步会把 admin 的密码改成 `…-Changed-2026` 并置 `mustChangePassword=false`。
**若就此收工，用户拿到的是一份"密码已不是我告诉你的那个"的环境**。
**对策**：走查脚本跑完必须**复位**：

```bash
SEED_RESET_PASSWORD=1 SEED_ADMIN_PASSWORD='…' SEED_MEMBER_PASSWORD='…' pnpm db:seed
```

同时删掉走查期间建的 `curl-member`、清掉 Redis 里的会话键与失败计数
（`member` 在走查第 ⑪ 步被刷到锁定）。
**验收**：`select username, role, status, must_change_password from users` → 只剩 `admin`(ADMIN,t) / `member`(MEMBER,t)；
`redis-cli --scan` → 空。
