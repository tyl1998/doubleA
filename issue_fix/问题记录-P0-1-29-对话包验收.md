## 坑 1 ⚠️ 引用片段**不是**整块正文 —— 别把"夹具碰巧成立"当契约

**现象**：R1 的引用卡断言一跑就红：

```
AssertionError: 期望 "…整块 chunk 正文…"
                  实际 "…（只到窗口边界的那一段）"
```

而报告里两串**看着几乎一模一样**（前缀相同），差异在末尾。

**根因**：上一批（P0-1-27）的夹具里，那块 chunk 的正文**比引用窗口短** ⇒ `buildSnippet()` 取
"围绕字面命中的 ±80 码点"时**恰好**能取到整块 ⇒ 那时写 `snippet === chunk.content` 是对的。
本批换成**三篇真 PDF**（正文更长）之后窗口开始生效，同一条断言立刻失败 ——
**上一批的写法不是契约，只是那批数据恰好落在窗口内**。

**对策**：把断言改成**真实契约的三条**（缺一不可）：

```js
// 1. 片段必须是原文的子串（引用卡的全部意义就是"让人核对模型看到了什么"）
assert(chunkText.includes(snippet), '片段必须 ⊆ 原文')
// 2. 必须命中查询词（否则"截到一段无关的话"也能过）
assertIncludes(snippet, 命中的词)
// 3. 不得超出窗口上界（用 shared 导出的常量，别写字面量）
assert([...snippet].length <= SNIPPET_WINDOW_CHARS + 2, '不超窗口上界')
```

**判据**：`SNIPPET_WINDOW_CHARS` 从 `@doubulea/shared` 导入（**不写死 80**）；
三条里第 1 条是"引用的语义"，第 2 条是"引用不是随便一段"，第 3 条是"实现没越界"。

## 坑 2 ⚠️ 「被拒的那一轮不落库」只对了一半（**绑库**的 Agent 会多一条空正文的助手消息）

**现象**：R4 的收尾断言从「1 条」改成「2 条」才对：

```
AssertionError: 期望 1 条用户消息，实际 2 条
  [{role:'USER',text:'占住这个会话'}, {role:'ASSISTANT',text:'',citations:[…]}]
```

**根因**：第一条流用的是**绑了知识库**的 Agent ⇒ **检索跑在 LLM 之前**，`citations` 事件在
`stall` 开始之前**就已经发出去了**。于是哪怕上游一个字都没吐，这一轮也**真的发生过** ⇒
按 `chatBot.ts#persistRoundQuietly` 的判据（`hasAssistantContent = 正文!=='' || 思考!=='' || citations.length>0`）
必须落一条**只带引用卡、正文为空**的助手消息。

**⚠️ 与 P0-1-27 的 D 组不矛盾**：那一档断言的是"被拒那轮**只落用户消息**"，因为它的用法是
**不绑库**的 Agent（没有引用卡）⇒ 两档都没错，缺的是"**绑库时多一条引用卡**"这一半。

**对策**：断言写成完整的四条，并把"被拒的那一句"单独钉住：

```js
assertEqual(rows.length, 2, '用户消息 + 只带引用卡的助手消息')
assertEqual(rows[0].role, 'USER')
assertEqual(rows[0].content.text, '占住这个会话', '⚠️ 被拒的那一句不得出现在历史里')
assertEqual(rows[1].role, 'ASSISTANT')
assertEqual(rows[1].content.text, '', '正文为空（上游一个字都没吐）')
assert(rows[1].content.citations.length >= 1, '但要带引用卡')
```

**判据**：这条同时守住三件事 —— ① 被拒的请求**没有自己的历史**（`content.text` 是有意设计的不同字符串）；
② 已发生的那一轮**不因为"没回答"被丢掉**；③ 引用卡是**真产出**（长度 ≥ 1，不是空数组占位）。

## 坑 3 ⚠️ 历史里"第几条"数错位置（被中断的那半条是 `rows[1]`，不是 `rows[3]`）

**现象**：R2 断言失败，报"被中断的那轮不含第 1 段"。

**根因**：消息是**成对**的（USER, ASSISTANT, USER, ASSISTANT…）。R2 的会话是
`[提问1, 被停掉的半条回答, 追问2, 追问2的回答]` ⇒ 被中断的内容在 **`rows[1]`**；
原稿写的 `rows[3]` 拿到的是**追问的回答**（它当然不含第 1 段）。

**对策**：断言固定成下表并加注释说明"为什么是第 2 条"：

```js
assertEqual(rows.length, 4)
assertEqual(rows.map(r => r.role).join(','), 'USER,ASSISTANT,USER,ASSISTANT', '成对且正序')
assertEqual(rows[0].content.text, QUERY, '第一轮提问')
assertIncludes(rows[1].content.text, '第1段。')          // ← 被中断的那条
assert(rows[1].content.text.length < longPieces.join('').length, '确实被截断了')
```

**判据**：`rows.length === 4` **加上**"成对正序"的组合串断言 —— 后者能一次抓住"漏了一条"与"顺序错"。

## 坑 4 ⚠️ 密码字母表的**注释与常量不一致** ⇒ 验收约 1/4 概率**随机红**

**现象**：R1 偶发失败（三次里红一次），报"初始密码含易混字符"：

```
AssertionError: 初始密码不得含易混字符，实际 hV3G83CdDNEdqEiNoQ   ← 含小写 o
```

**根因**：`backend/src/infra/crypto.ts` 的**注释**写"剔除 `0/O/o`、`1/l/I`"，而
`PASSWORD_ALPHABET` 常量其实**保留小写 `o`**（`o` 与 `0` 不像，与 `O` 也不像 —— 真正的易混字符是
`0` 与 `O`、`1` 与 `l` 与 `I`）。注释写错后，验收里的 `!/[0Oo1lI]/.test(initialPassword)`
把**合法的 `o` 也算成违规** ⇒ 18 位密码里出现 `o` 的概率约 **1/4**。

**对策**（两处缺一不可）：
1. 断言改成**与常量同源**的口径：`!/[01IlO]/.test(initialPassword)`，长度取 `INITIAL_PASSWORD_LENGTH`；
2. **订正注释**，并把这条写进注释里留痕：`📌 P0-1-29 收尾时订正`。

**📌 更值钱的一条**：R7 的"证据①"**一度也写了同一个正则** —— 同一件事在两处各写一遍，
**必有一处先腐烂**（本批就是 R7 那处先烂，R1 那处跟着红）。处置是**删掉重复写法**，
只留一处并与常量同源。

**判据**：新档**连跑 3 次全绿**才算通过 —— 这种"随机红"跑一次绿**证明不了什么**。

## 坑 5 ⚠️ 证据必须在断言**之前**收集（否则一个失败被放大成两个）

**现象**：R1 一红，R7 跟着报 `期望 401 实际 undefined`。

**根因**：`evidence.chosenPasswordLoginStatus` 的赋值写在 R1 的断言**之后**
⇒ R1 抛错时它还是 `undefined`，被 R7 当成"实测值"去比。

**对策**：把"给后面几组当证据用"的采集动作**排在断言之前**（`await` 拿到响应就存）。

**判据**：**先手动把 R1 打红一次**，看 R7 报的是不是它自己的结论 —— 若跟着 `undefined`，
就是采集顺序的问题，不是数据的问题。

## 坑 6 ⚠️ 门槛⑦「全程无手工干预数据」**不能写成"我们没插 SQL"**（那是恒真的废断言）

**现象**：门槛原文是一句**意图**，不是一句可断言的话。照字面写 `assert(!usedRawSql)` 永远通过 ——
脚本里当然没有那句 SQL。

**对策**：拆成**四条"只有服务端能产生"的证据** + 一份**端点台账**：

| # | 证据 | 为什么只有服务端能产生 |
|---|------|----------------------|
| ① | 拿本脚本**自选**的密码登这个新号 ⇒ **401**；拿 `POST /api/users` 回的 `initialPassword` ⇒ **200**（且长度 = `INITIAL_PASSWORD_LENGTH`） | 密码是服务端生成的；手改过库或"密码写死"的实现过不了这一对 |
| ② | 三篇 PDF 各自的 chunk 正文里含**各自的特征短语**，且列表端点报的 `chunkCount` **== `chunks` 表实际行数** | 正文只可能来自我们上传的字节；块数是"接口不能谎报"的那条（P0-1-19 明令） |
| ③ | 助手消息正文 **== 事件流收到的增量拼接**（逐字） | 它是服务端流式产出的，手写不出来 |
| ④ | `agent.createdBy` **== 会话里的用户 id** | 由服务端从会话取，客户端**提交不了**这个字段 |

外加**端点台账**（本档共 95 个请求、去重 23 个端点）打印出来，供人核对"整条链只用产品端点"。

**唯一直接写库的地方**是**自举管理员**（第一个账号没有 HTTP 出口能创建 —— 建号本身就要 ADMIN 登录），
这一点在文件头写明，**不藏**。

**判据**：四条都断言 + 台账打印；`✅ R7｜全程无手工干预数据（四条"只有服务端能产生"的证据 + 端点台账）`。

## 定型决定（实现期定的口径，不是坑）

| # | 决定 | 理由 |
|---|------|------|
| 1 | **包级脚本只跑"串起来还成不成立"**，不重复四档的细粒度断言 | 帧格式/锁归属/游标边界…由 `verify:chat-stream`/`verify:chatbot`/`verify:conversations` 各自守着；本档只问"一个新建的账号能不能自己把这条链走完" |
| 2 | 注入 **`CHATBOT_CONCURRENCY=2`**（而不是 1）来验门槛④ | 门槛④ 要的是**会话互斥**（`CONFLICT`）。若闸门设 1，两条流会先撞**进程级并发闸**拿到 `BUSY` —— 两个错误码长得像、根因完全不同（`BUSY` 已由 `verify:chatbot` 的 D 组单独覆盖）。**注入值要选得让被测的那条路径真的被走到** |
| 3 | 端口 **13096**、`SSE_PING_INTERVAL_SEC=1`、`PIPELINE_QUEUE_KEY=verify:chat-package:jobs:${suffix}` | 与用户 dev 的 13000、另两档的 13097/13098 全部错开；随机队列键避开开发队列 |
| 4 | R1 的 3 篇 PDF 用 **ASCII 夹具** | 本仓 `makePdf` 走 Helvetica 内置字体 + latin1 字节（P0-1-16 定案），**装不下中文** —— 不是"PDF 只支持英文"；真中文 PDF 由 `verify:documents` 的 A 组单独验 |
| 5 | **三处"部分完成"在结论表单列、不混进 ✅** | R3 只到 HTTP 层（浏览器渲染属 P0-1-32~34）、R1 用 ASCII 夹具、R6 的 TTFT 是**链路值**不是模型值（上游是本地假夹具，证明的是"打点存在 + 口径正确 + 全链路无隐藏等待"） |
| 6 | 收尾清 **7 张表 + 4 个键族**并**断言残留为零** | 含 `login-fail:{username}` 登录失败计数键 —— 它是登录限速（P0-1-7）的计数，忘了清会让下一次跑那条账号的用例带着上一档的失败次数 |
| 7 | 长会话**真发 25 轮**（不用"直接造历史"冒充） | 门槛⑤ 的语义是"连问很多轮不报错"，造出来的历史验不到"第 N 轮请求本身会怎么样"（例如提示词组装、TTFT 打点） |
