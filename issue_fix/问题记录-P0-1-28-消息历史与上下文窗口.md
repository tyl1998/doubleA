## 坑 1 ⚠️ 游标必须是**行 id**，不能是时间戳（否则并列的那条会蒸发）

**现象**：翻页时**少一条消息**。没有报错、状态码 200、界面只是"少了一条"，用户与开发者都不会
第一反应怀疑分页。

**根因**：`messages` 的表定义是 **`PRIMARY KEY (id, created_at)`**（分区表的约束要求分区键进主键，
见 P0-1-5），而**同一轮问答的 USER 与 ASSISTANT 两条消息是在同一个事务里落的库** ⇒ 它们的
`created_at` **逐字相同**（同一个 `now()`）。于是：

- 若游标是"时间戳 < cursor"：那一对里**只有第一条**会被下一页返回，第二条被跳过；
- 时间戳是**离散**的，而消息是**成对**出现的 —— 这不是概率问题，是每次都发生。

**对策**：游标的语义定为**二元组 `(created_at, id)` 的字典序**，曲线是"严格更早"：

```ts
// backend/src/services/conversation.service.ts#listMessages
where: before === null
  ? { conversationId: target.id }
  : {
      conversationId: target.id,
      OR: [
        { createdAt: { lt: before.createdAt } },
        { createdAt: before.createdAt, id: { lt: before.id } },   // 同一毫秒内按 id 继续往前
      ],
    }
```

对外的 `beforeId` 只是**行 id**（客户端不需要知道时间戳），服务端先按
`{id: beforeId, conversationId}` 把那一行查出来拿到 `(createdAt, id)`。

**判据**（两条，缺一不可）：
1. **一次性探针**先证 PG/Prisma 真的接受 `id: { lt: '<uuid>' }`（`id` 列是 `@db.Uuid`，
   Prisma 的类型推断要能把它当 uuid 比较，而不是当字符串）—— 这条**必须真跑**，因为"看起来
   能编过"与"运行时 PG 收不收"是两件事（P0-1-15 的"参数方向写反"就是同类）；
2. H 组的"**同毫秒四条**"用例：故意把四条消息写成**完全相同**的 `created_at`，逐页翻完，
   断言**一条不漏**。⚠️ 这条用例不能用"自然写入的两条"来替代 —— 那两条的 `created_at`
   只**碰巧**相同，夹具一旦变慢就悄悄失效（假绿）。

## 坑 2 ⚠️ `beforeId` 不属于本会话时必须 **400**，不能当"没有游标"

**现象**：客户端拿着一个**别的会话**（或已删除）的消息 id 来翻页 ⇒ 接口**静默返回第一页**，
客户端把"第一页"当"下一页"追加在下面 ⇒ 消息**反复出现**，而**状态码全 200、日志里什么都没有**。
如果客户端是按游标自觉循环拉取，就是**无限循环**。

**根因**：把"游标查不到"与"没有游标"混成一条路。前者是**客户端给了错东西**（可行动的错误），
后者是**合法的首页请求** —— 两者的正确响应完全不同。

**对策**：`beforeId` 存在时先查
`{ id: beforeId, conversationId: target.id }`，查不到直接
`AppError.validation('beforeId 不是该会话的消息（游标无效）')`（400，走信封）；
只有"没传 `beforeId`"才是首页。

**判据**：四类 400 各一条 —— ① 同会话但**不存在**的 id、② **他人会话**里真实存在的 id、
③ 非 UUID 形态（这条由 schema 拦，走框架的 400）、④ `limit` 越界（0 / 101 / 非数字）。
⚠️ ② 特别重要：它证明校验里**带了 `conversationId`**（只查 `{id}` 的实现会放行，然后按别人的
游标去翻自己的页 —— 结果同样是静默错页，而不是报错）。

## 坑 3 ⚠️ `content` 的 zod 写法两个陷阱：一个编译报错、一个**静默丢键**

**现象 A（会在 `tsc` 时报错，属好消息）**：`z.unknown().refine(...)` 的推断类型是 `{} | null`，
与 service 返回的 `unknown` **不兼容** ⇒ `src/services/conversation.service.ts(522,5)` 报类型错。
`refine` 会把 `unknown` "收窄"成它认为可赋值的形状，而 `{} | null` 正好排除了
`string`/`number`/`boolean` 这些**基本类型**。

**现象 B（更危险，**不报错**）**：裸 `z.unknown()` **接受 `undefined`** ⇒ 序列化时
`JSON.stringify({content: undefined})` 会**把整个键丢掉** ⇒ 线上"这条消息没有 `content` 键"
与"`content` 是 `undefined`"无法区分。而"少一个键"在下游（`03` 的渲染路径）就是要处理的分支。

**对策**：用 `z.custom<unknown>()` 显式给回 `unknown`，并把"不接受 `undefined`"写成守卫：

```ts
// shared/src/conversation.ts#messageItemSchema
content: z.custom<unknown>((value) => value !== undefined, {
  message: '消息必须有 content',
}),
```

**判据**：`verify:app` 里那两条 —— ① `messageItemSchema.safeParse({content: undefined})`
必须**失败**；② 键集合恰好是 `{id, role, content, createdAt}`（**不多不少**）。

## 坑 4 ⚠️ 读取端**不许**用 `messageContentSchema` 过滤 `content`

**现象**：历史里的 `tool_calls` / `attachments` **凭空消失**，没有报错、没有告警、日志干净。
P0-1 阶段它们本来就还没人写，所以**本批验不出来**；而这正是它危险的地方 —— 它会**在 P0-2 上线那天**
才暴露，而且那时会被当成"工具记错了"而不是"读取端把键剥了"。

**根因**：`messageContentSchema`（P0-1-27 建的）是**写侧**形状：只声明
`{text, thinking?, citations?}`，而 Zod 的对象默认**剥掉未声明的键**（既不报错也不保留）。
拿它去"校验"读回来的历史，等于把**将来才有的字段**提前删掉。

**对策**：
- 读取端**完全不过滤**：`messageItemSchema.content` 是 `z.custom<unknown>` ⇒ 存进去什么就吐什么；
- 在 `shared/src/conversation.ts` 的文件头补第 ⑥ 条，把"读侧不解释 `content`"写成显式口径；
- 在 `messageContentSchema` 的注释里订正：**它只服务写侧**，读侧不用它。

**判据**：**反向对照**（`verify:conversations` H 组）—— 直接落一行
`content = {text, tool_calls: [...]}`，然后：
① 过 `messageContentSchema` ⇒ **掉键**（`tool_calls` 不在结果里）；
② 过端点 ⇒ **键还在**。
两条一起断言才有判别力：只断言 ② 时，一个"恰好没过滤"的实现也能过；
只断言 ① 时，验的是 schema 而不是端点。

## 坑 5 ⚠️ 排序口径必须**同源** + 换端点会连带打红旧断言

**5.1 排序同源**：历史分页与"上下文窗口的最近 N 轮"（`chatBot.ts`）是**同一个语义**
（时间上的最近 N 条），区别只在"取多少"与"给谁看"。两处各写一份 `orderBy` 字面量，会在
"哪天有人改了一处"时**静默分叉**：界面上历史顺序与模型看到的历史顺序不一致，且**没有任何报错**
（P0-1-27 那条"多库合并 tie-break"的同类）。
⇒ 常量由 service 导出、编排侧 `import`：

```ts
// backend/src/services/conversation.service.ts
export const MESSAGE_CHRONO_ORDER = [{ createdAt: 'desc' }, { id: 'desc' }] as const
// chatBot.ts:  orderBy: [...MESSAGE_CHRONO_ORDER]
```

⚠️ `id` 作为副键是**必需**的（不只是好看）：同毫秒并列时没有副键，两次查询的顺序可以不同 ⇒
"上下文窗口"与"历史分页"在并列处给出不同顺序。

**5.2 连带影响（本批第二次遇到"旧档因为本批落地而红"）**：`verify-chatbot` 的取历史从
"直接读库"改成"真打 `GET /:id/messages`"之后，那条"**tokens_in / tokens_out 已落库**"的断言
立刻红（`实际 undefined`）—— 因为 `messageItemSchema` **刻意不带** token 计量（属 P1，
`02` §七 待决 4）。
**处置**：那条断言改回**直接读库**（并加注释说明"这是路径依赖旧写法、换端点后立刻红"），
而不是把 token 加进消息投影（那会**为了让断言通过而改产品契约**）。
📌 判据：**换取数路径时要逐条过一遍旧断言"它验的是数据还是形状"** —— 验形状的会红，
验数据的不会；红的那条要么改路径、要么改断言，**但绝不能改产品契约去迁就断言**。

## 坑 6 ⚠️ 跨档 flake：`verify-retrieval` 的"逐条对照"在并列段上是一次**抛硬币**

**现象**：P0-1-28 的全量回归**首跑**，`verify-retrieval`（P0-1-20 的档）
**1 项失败 / 26 项通过**：

```
[FAIL] 向量路的名次与分数 == 独立复算的 `<=>` SQL（逐条对照）
       第 3 条的块 id（名次应与独立 SQL 一致）：期望 "01a0c85f-cec8-…"，实际 "01a0c85f-ceb5-…"
```

而**单独重跑这一档立刻 27/27 全绿**（试了两次都绿）—— 典型的**假红**，
但它会**污染每一批的收尾**（收尾必须全量回归，每次都有约 50% 的概率看到它红一次）。

**根因链**（三环，缺一不可）：

1. 本档的假 embedding 上游是**词面重叠型**（`semanticVectorFor`：把 2-gram 哈希到维度上再归一化）
   ⇒ 与 query **没有共同 bigram** 的对照块，余弦相似度**恰好是 0**（不是"很小"）；
2. 测试夹具里有**多块**对照块（考勤 / 休假 / 长篇），它们的相似度**同为 0** ⇒ **并列**；
3. 实现（`services/retrieval.ts`）**刻意**不在 SQL 里加第二排序键 —— 加了会让 HNSW
   退化成"索引扫描 + 显式排序"，P0-1-14 的索引取证就白做了 ⇒ tie-break 落在 **JS 的
   `stableOrder`（score 降 + id 升）**；
   而**验收脚本的独立复算 SQL 少了这个副键**（`ORDER BY c.embedding <=> $1`）
   ⇒ 并列段的先后**由 PG 的不稳定快排决定** ⇒ 两份"应该相同"的列表在并列段上随机不同。

**对策**：两份独立复算 SQL 各补 `, c.id`（**镜像实现的 tie-break 口径**）：

```sql
-- 向量路
ORDER BY c.embedding <=> ${literal}::vector, c.id
-- 全文路（en) 同款：ORDER BY score DESC, c.id
```

⚠️ **不动被测代码** —— 产品侧的 tie-break 是**有理由的**（HNSW），要改的是**对照条件不等价**。
⚠️ `uuid` 的 PG 比较是**无符号字节序**，而 `id::text` 是定宽小写十六进制 ⇒ 与 JS 的字符串 `<`
**同序**，所以两边可以逐条对齐（这不是巧合，是能写下来的依据）。

**判据**：修完连跑两次都 27/27（`/tmp/rerun-retrieval.log`）。
📌 **判据本身**：**"两份查询只在某个并列段上不一致" ⇒ 先怀疑对照条件不等价，别急着改断言**
（把断言放宽成"集合相同"也能"修好"，但那会把"实现真的排序错了"一起放过）。
📌 **另记一条边界**（属可接受，不修）：候选池的**池边界**上并列的取舍仍由 PG 决定
（内部 SQL 是 `ORDER BY 距离 LIMIT pool`，没有副键）—— 只有当**并列条数 > 池容量**时才会有
不可判的子集选择；本档池 20 ≫ 块 4，碰不到。记在这里是为了下一个人见到它时知道**这是已知的**，
而不是新 bug（要根治得改索引策略，属性能与正确性的交易，不在 P0-1 范围）。

## 坑 7 结构决定：分页用"多取一条"，**不做总数**

**现象/理由**：`messages` 是**按月分区表**（14 个分区），`count(*)` 要在**每个分区上各跑一遍**
再合并 —— 本仓最贵的查询形态。前端要的是"还有没有更早的"与"下一页从哪儿开始"，
**都不需要总数**。

**对策**：`take: limit + 1`。多出来的那一条**只用来判 `hasMore`，不进 `items`**；
`nextCursor` = **返回页的第一条**（SQL 是 `desc` 取的，所以第一条就是"更早那侧的最近一条"），
`hasMore === false` 时为 `null`（**不给一个再翻一次会返回空页的游标**）。
响应形状走 `shared/src/envelope.ts#cursorPageOf`（本仓**唯一**游标分页；
其余列表是 `offsetPageOf`）—— ⚠️ 分页响应**没有 `total`**，这条要写进文档，否则前端会去找它。

**落地形态**：`toMessagePage(rows, limit)` 是**纯函数**（切片 → 判 `hasMore` → **倒序** → 映射 ISO 时间），
所以它能进**无依赖档**（`verify:app`）。六条断言：

1. 多取的那一条**不进** `items`（且 `hasMore === true`）；
2. 取满且无更多 ⇒ `hasMore === false` 且 `nextCursor === null`；
3. 两页拼接**不重不漏**（**集合双向相同 + 顺序逐条**——只比集合会放过"顺序反了"）；
4. 同毫秒两条**不被吞**（纯函数层面的对照，与坑 1 的端到端用例互补）；
5. 空输入 ⇒ `{items: [], hasMore: false, nextCursor: null}`；
6. 排序常量与编排侧**同源**（同一份导出）。

**判据**：`verify:app` 第 25·b 节；`verify:conversations` 的"25 条翻页"端到端用例
（真翻页 + 用**库里独立复算的正序列表**逐条比 + 自证不变式"两页拼接 == 全集"）。

## 定型决定（实现期定的口径，不是坑）

| # | 决定 | 理由 |
|---|------|------|
| 1 | `limit` 默认 **20**、上限 **100**，且是**代码常量**（不进 env） | 上限不设 ⇒ 允许 `limit=100000` 一次拉爆分区表；默认值写进 schema（`.default(20)`）而不是在 service 里兜底 ⇒ 校验与文档同源 |
| 2 | 路由**只挂 `requireAuth`**，权限判据是 `where: {id, userId}` | 会话是"仅本人"的资源（`02` §4.5 ①）：**403 等于确认 id 有效** ⇒ 他人/不存在/ADMIN 看别人**一律 404**；判据落在查询条件里 ⇒ 越权**写不出来** |
| 3 | 投影是 `{id, role, content, createdAt(ISO)}`，**刻意不带** `tokensIn/tokensOut/conversationId` | token 计量属 **P1**（`02` §七 待决 4）；会话 id 在路径里已有。⚠️ 与坑 5.2 是同一件事的两面：**为了断言好看而把 P1 的字段提前塞进投影**是本仓明确拒绝的做法 |
| 4 | `items` 返回**时间正序**（SQL 取 `desc` 后由纯函数反转） | 界面从上到下就是时间顺序（`03` §五）；让前端自己 `reverse()` 会把"顺序"分散到两处实现 |
| 5 | `MESSAGE_ROLES` 由 `shared` 导出（`['USER','ASSISTANT','SYSTEM']`） | 前端要按角色渲染不同气泡，枚举只能有一处 |
| 6 | 只读会话（`FINISHED`）的**历史照常可读** | "只读"的判据是**不能再产生消息**（P0-1-26 的闸门），而不是"不能看"；软删 Agent 之后用户最需要的恰恰是**把自己问过的东西翻回来**（P0-1-22 的"只读保留"就是为这个） |
