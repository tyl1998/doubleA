| # | 发现 | 严重度 | 状态 |
|---|------|--------|------|

## 复核方法（真跑）

在 `doubulea/sandbox-toolkit`（pi `0.87.1`，Node 22）容器里：

1. 挂载真实 `infra/sandbox/base/pi-agent/extensions/workspace`（`-e /probe/workspace/index.ts`）；
2. 注 `DOUBULEA_WORKSPACE_MEDIATION=1` + `SANDBOX_BACKEND_URL`/`SANDBOX_TOKEN`；
3. 起一个**假上游**（OpenAI `chat/completions` 的 SSE + 假 `/api/sandbox/workspace/*`），第一轮返回一个 `write`（后复跑 `edit`）工具调用、第二轮收尾；
4. `pi --print --mode json --no-approve --provider doubulea --model doubulea/probe-model "…"`。

**三条结论**：

| 结论 | 证据 |
|------|------|
| 同名覆盖**生效** | 发给 LLM 的请求体 `tools[]` 里 `read`/`write`/`edit` 是**本扩展**的定义（中文 description；`edit` schema = `{path, edits:[{oldText,newText}]}`），不是内置 |
| 写走 **CAS** | 假代理收到 `POST /api/sandbox/workspace/edit`，体 = `{path, edits:[{oldText:"human",newText:"agent"}], baseVersion:3}`（`baseVersion` 先经一次 `read` 取到） |
| 冲突**回喂模型** | `CONFLICT` 被 `throw` 成**失败工具结果**；下一次 LLM 请求的 messages 里含 `"文件已被修改（当前 v4），请重新读取后再写。…"` |

（另：`read`/`write` 的入参与内置**逐字一致**，无需改。）

## 发现 1 — 镜像里没有扩展（本批最贵）

**现象**：在宿主 `doubulea/sandbox-toolkit:5` 里 `ls /opt/pi/agent/extensions/` **只有 `mcp-bridge`**，`workspace/index.ts` 不存在 ⇒ `exec pi` 压根不加载它。

**根因**：P2 改了 `infra/sandbox/base/Dockerfile`（`COPY pi-agent/ …` + `test -f …/workspace/index.ts` 断言）并新增了 `infra/sandbox/base/pi-agent/extensions/workspace/`，**但没动 `infra/sandbox/versions.mjs`**（`BASE_LAYER_VERSION`/`TOOLKIT_LAYER_VERSION` 仍是 `5`）。于是宿主上那份旧 tag 的镜像永远不会被重建 —— 症状正**是 `versions.mjs` 文件头反复警告的"静默故障"**：Code 模式打开、agent 的文件写却完全没走中介，而后端日志里一条错都没有。

**修法**：`versions.mjs` 两个层版本 `5 → 6`，并**重建镜像**。本批已跑：

```
pnpm sandbox:build -- --registry https://registry.npmmirror.com
# → doubulea/sandbox-base:6 / doubulea/sandbox-toolkit:6（toolkit 依赖自检全过）
```

并把 `infra/.env` 改指 `:6`（`SANDBOX_IMAGE=doubulea/sandbox-toolkit:6` / `SANDBOX_IMAGE_BASE=doubulea/sandbox-base:6`）。**验证**：`docker run --entrypoint sh doubulea/sandbox-toolkit:6 -c 'ls /opt/pi/agent/extensions/'` 现在同时列出 `mcp-bridge` 与 `workspace`；并用 `:6`（内建扩展、无 `-e` 挂载）复跑复核，扩展加载 / 覆盖生效 / `edits[]` 走 CAS / 冲突回喂全部一致。

## 发现 2 — `edit` 形状与 pin 不一致

**内置 `0.87.1` 的 `edit`**（`dist/core/tools/edit.js`）：

```ts
editSchema = Type.Object({
  path: Type.String(…),
  edits: Type.Array(Type.Object({ oldText: Type.String(…), newText: Type.String(…) })),
})
```

**我们的旧形**：`{ path, old_string, new_string, replace_all? }`。因为我们是**同名覆盖**，发给模型的是**我们的** schema，所以调用本身自洽；但模型（尤其 Opus / GLM 系）对 pi 的 `edits[]` 有强先验，会给 `edits` 而不是 `old_string` ⇒ 在 schema 校验这一步就失败。

**修法**：全面对齐 `edits[]`。

- 扩展侧：`edit` 的 `parameters` 改 `{path, edits:[{oldText,newText}]}`，并加 `prepareArguments` 兼容 shim（`edits` 是 JSON 字符串 / 单个对象 / 旧 `old_string+new_string` 都归一，照抄内置口径）。
- 后端侧：`backend/src/workspace/edit.ts` 新增 **`applyWorkspaceEdits`（原子多改）** —— 每处 `oldText` 对着**原文件**唯一匹配、两两不重叠，任一处不满足**整次拒绝**（不做"改了一半"）；`workspace/proxy.ts` 的 `edit` 端点请求体改 `{path, edits[], baseVersion?}`（旧 `oldString/newString/replaceAll` 仍兼容）。`applyWorkspaceEdit`（旧单处）保留给兼容路径与既有自证。

## 发现 3 — 覆盖会抹掉内置工具的提示贡献

**现象**：只覆盖 `write` 时，系统提示 `<tools>` 段里 **`write` 行消失**（只剩 `read`/`bash`/`edit`）。

**根因**：内置工具在系统提示里的条目（`promptSnippet`）与用法提示（`promptGuidelines`）**由工具定义本身携带**；同名覆盖把整个定义替换掉，这两项若不给就是"无"。pi 的 `ToolDefinition` 明确有 `promptSnippet?`/`promptGuidelines?`/`constrainedSampling?` 字段。

**修法**：三个覆盖工具都补 `promptSnippet` + `promptGuidelines`（照内置抄、按我们的版本语义措辞）+ `constrainedSampling: { type: 'json_schema', strict: 'prefer' }`。复核后 `<tools>` 里 `read`/`edit`/`write` 行**全部回来**。

## 边界

- 层版本升 `6` 后**必须重建镜像并改 `.env`**，否则宿主仍跑 `:5`（无扩展）。
- `read` 仍返回原文（未复刻内置的行号 / 截断提示）；`edit` 已对齐，`write` 的"自动建父目录"由后端 CAS / 配额兜。
- 覆盖内置工具 = 承担其全部语义：`promptSnippet`/`guidelines` 照抄，但**不**复刻内置 `renderCall`/`renderResult`（RPC 模式无 UI，不构成问题）。
- 多机粘性（R9）仍属剩余清单。
