## 坑 1 ⚠️ 整体替换的「删除」与「校验」谁先谁后：写反了会删光旧数据再报错

**问题**：整体替换的直觉写法是"**先清空、再写入**"：

```ts
// ✗ 错的顺序
await db.$transaction(async (tx) => {
  await tx.agentComponent.deleteMany({ where: { agentId: id } })      // 先删
  await assertComponentRefsBindable(desired)                          // 后校验 ← 太晚
  await tx.agentComponent.createMany({ data: ... })
})
```

当 `desired` 里有一个**不存在的知识库**时，请求会回 404（看起来"被正确拒绝了"），
但**旧绑定已经被删干净**。用户看到的是"保存失败"，而库里那几条绑定没了 ——
他没有任何理由去检查绑定，只会以为"刚才那次保存真的没生效"。等到某次对话检索不到内容，
或某个知识库突然删得掉了，才以完全无关的症状暴露出来。

**根因**：`deleteMany` 与 `createMany` 在同一个事务里，但**校验不是事务的一部分**，
它在代码里的位置就决定了"失败时回滚到哪个状态"。校验放在删除之后 ⇒ 回滚的粒度只能覆盖
"删除 + 部分写入"，而**删除本身已经发生了**（事务回滚要靠抛错，而抛错点在校验处，
此时同一事务里的删除**会**被回滚 —— ⚠️ 这句话对"校验在同一个 `$transaction` 回调里"成立，
对**校验在事务之前/之后**不成立。而直觉写法里 `assert...` 往往被写在事务**外**或事务内的
`deleteMany` 之后却不抛回滚，两种都会留下"删了没建"或"删了才报错"的状态）。

**对策**：**校验整体前置到任何写操作之前**，并且把它写进注释当作本端点的第一条口径：

```ts
const desired = [...input.components].sort(compareComponents)
await assertComponentRefsBindable(desired)     // ① 校验：一个字都不写
const current = await componentsOf(id)
if (!sameComponentSet(current, desired)) {     // ② 集合没变就连事务都不开
  await db.$transaction(async (tx) => { … })   // ③ 只有确定要改才删+建
}
```

**取证方式**（`verify-agents` H 组第 3 条）：断言**旧行的 `id` 逐字不变**，而不是看状态码。
`agent_components.id` 是 `uuid(7)`、由 Prisma 在插入时生成 ⇒ "重写了一遍但内容相同"也会换 id，
所以"id 不变"同时排除了"先删后建"与"删了没建"。这是 `06` P0-1-19 那条
「要证明某件事**没发生**，必须用**删得掉证据**的方式」的第三次应用（P0-1-21 的 R4 是第二次）。

```text
[PASS] ⚠️ 校验失败时**旧绑定逐字不变**（校验必须在删除之前）+ MCP 引用被明确拒绝
```

> 通用教训：**"全量替换"类端点里，校验的位置就是正确性的一部分**。
> 凡是"先清空再重建"的实现，都要问一句"重建失败时，清空要不要回滚"——
> 而能让这个问题的答案是"是"的最简写法，就是**别在失败之前动手**。

## 坑 2 ⚠️ 计划文档要求"绑定多 KB + **多 MCP**"，但 `mcp_servers` 表要到 P0-2 才建

**现象**：`docs/06` P0-1-23 的验收原文写「绑定多 KB + 多 MCP 后详情完整回显」，
P0-1-24（本包的验收门槛）第 2 条写「绑定 2 个知识库 + **1 个 MCP server**」。
但 `agent_components.ref_id` 的 MCP 一侧指向 **`mcp_servers`**，而该表 `02` §3.1 已明确
**属 P0-2**（`06` 第 893 行起：`P0-2-1` MCP client 底座、`P0-2-11` MCP 管理页）。
也就是说：**P0-1 阶段没有任何路径能创建出一个 MCP server**，也就没有任何路径能拿到一个真实 `refId`。

**为什么不能"先收下、等 P0-2 再收拾"**：`ref_id` 是**多态外键、刻意没有 FK**
（`02` §3.1：一列不能同时指向两张表），所以数据库**不会拦**任何一个 uuid；
而界面在 P0-2 之前根本没有 server 列表，用户**看不见**这些绑定、也**改不掉**它们。
留下的就是 `kb.service.ts` 文件头 ④ 定性的那类数据 ——
"Agent 说绑着某物、那个物已经不存在"，症状要到检索时才炸、且查不出来。

**对策**：**在 P0-1 阶段明确拒绝 MCP 引用**（400 + 可执行文案），并在文档里把口径变更写清：

```
400 VALIDATION
msg: MCP 服务器功能尚未开放（P0-2 才提供注册与绑定）：本次提交里有 N 条 MCP 绑定，请先移除
```

- `docs/06` P0-1-23 新增「**口径变更**」段：写明理由、影响（P0-1-24 的验收门槛第 2 条
  与 P0-1-35 的界面）与 **P0-2 的接回方式**（同一处 `assertComponentRefsBindable`
  从"无条件拒绝"换成"存在性校验"，**接口形态不变**）；
- `docs/06` P0-1-24 的验收门槛第 2 条**同步改写**为可执行版本（MCP 那半由 P0-2 接回）；
- README「智能体专项边界」写进"含 MCP → 400 是**预期行为**"；
- `verify-agents` H 组有一条断言**同时**盯住两件事：状态码 400 + 文案里出现 `P0-2`
  （**断言文案指向哪一步**，而不是只断言"被拒"—— 否则将来有人把拒绝改成 500，
  或者把文案换成"参数不合法"，用户就不知道自己在等哪个版本）。

```text
[PASS] ⚠️ 校验失败时**旧绑定逐字不变**（校验必须在删除之前）+ MCP 引用被明确拒绝
```

> 通用教训：**"表还不存在"的关联对象，不要用"先写进去"来假装功能已实现**。
> 这类决定要在文档里留一句"将来怎么接回来"，否则 P0-2 会在两个地方各猜一次。

## 坑 3 `.refine()` 与 `superRefine`：同类校验，一个给不出 `path`、一个给得出

**背景**：P0-1-22 在"空 body"那条上踩过 `.refine()` —— 它失败时 `issue.path` 是**空串**，
于是那条错误是"表单级"而非"字段级"，前端挂不到任何输入框上（验收只能遍历 `data.fields[].message`）。

**本批的同类需求**：整体替换的 payload 里**重复项**（同一对 `componentType + refId` 出现两次）
必须在写库前拒掉 —— `agent_components` 上有 `@@unique([agentId, componentType, refId])`，
放过去就是 P2002 → **500**，而"提交了一份带重复项的集合"本就是调用方的 bug
（多选框选不出重复值），说清楚比悄悄去重好：**悄悄去重会让"我提交的 ≠ 我拿到响应的"变成查不出来的事**。

**对策**：用 `.superRefine()` + `ctx.addIssue({ path: ['components', index, 'refId'] })`
给出**真正的下标**（实测 `path = ['components', 1, 'refId']`），前端能精确高亮到那一行：

```ts
.superRefine((body, ctx) => {
  const seen = new Set<string>()
  body.components.forEach((item, index) => {
    const key = `${item.componentType}:${item.refId}`
    if (seen.has(key)) {
      ctx.addIssue({ code: z.ZodIssueCode.custom, path: ['components', index, 'refId'], message: '…' })
      return
    }
    seen.add(key)
  })
})
```

**两档验收都钉了这条**，而且**刻意放在一起对照**（无依赖档里就是一行之隔）：

```text
（verify-app 第 24 节）
[PASS] 组件绑定 body 契约（P0-1-23）：`components` 必填、重复项给**真 path**（与 `.refine()` 的空 path 对照）

（verify-agents H 组）
[PASS] 请求体形态：`components` 必填、重复项 **path 精确到下标**、坏枚举/坏 uuid 各 400
```

> 通用教训：**要"按字段报错"，就得用能给 `path` 的 API**。`.refine()` 只适合"整个表单级"的规则
> （如"至少给一个字段"），一旦想指到某一行/某一项，必须 `superRefine` + `addIssue({ path })`。

## 坑 4 集合类接口的两条静默口径：**省略是否等于清空**、**相同集合要不要写库**

**4-a 语义设计**：`components` **必填**，清空必须显式传 `[]`。

若把"省略"当作"清空"，`03` §4.2 第 5 条的保存流程（`PATCH` + `PUT` **串行**）里
某次忘了带字段，就会**静默解绑所有知识库**，而界面显示"保存成功"。
这与 `guideQuestions` 用 `[]` 表达清空是同一套口径：**清空只有一种写法**（P0-1-22 已写过这条）。
验收断言同时盯文案（`含"空数组"`）与路径（`body.components`）。

**4-b 幂等设计**：**集合相同就不写库**。

保存按钮每次都发 `PUT`（整表单提交），若每次都 `deleteMany + createMany`，
`agent_components.id` / `created_at` 会被**无谓刷新** —— P0-1-10 已经为这类"看不见的改写"立过规矩
（"带随机 IV 的密文逐字不变"）。判等刻意做成**集合语义**（`componentType + refId` 组成键），
于是"只换了提交顺序"不算改动。验收用"**换顺序再提交一次**"取证，断言行的 `id` 逐字不变：

```text
[PASS] 幂等：重复提交同一份绑定（**换顺序**再提交）→ 行的 `id` 逐字不变
```

顺带：`createMany({ skipDuplicates: true })`（`ON CONFLICT DO NOTHING`）**只兜并发** —— 双击时
两个相同 `PUT` 会在插入上撞唯一索引，跳过即得正确结果，不会把一次双击变成 500。
payload **内**的重复项已由 schema 拦住，所以这个"跳过"不会掩盖调用方 bug。

**4-c 另一条反向的连带效应**：整体替换的语义包含"**清掉不在提交集合里的行**"。
`ref_id` 没有 FK ⇒ 手工 `INSERT` 一条绑定是完全合法的（P0-1-22 的验收脚本就这么造过 MCP 行），
这些"历史遗留"会在用户**下次保存组件绑定**时被清干净。验收专门造了两条脏行（一条别的知识库、一条 MCP）来验：

```text
[PASS] 整体替换会清掉**不在提交集合里的手工脏行**（"提交什么，库里就有什么"）
```
