## 坑 1：手写 DDL 被 Prisma 判成"多余对象"并生成 `DROP INDEX`（本批最大坑，且不在预判里）

**怎么发现的**：做完 schema 与迁移后，按 P0-1-5 的纪律跑一次反向探针 —— 加一个**一次性模型**（`ZzzProbe`）
再跑 `migrate dev --create-only`，看 Prisma 会为"别的改动"生成什么：

```
$ pnpm --filter @doubulea/backend exec prisma migrate dev --create-only --name probe
-- DropIndex
DROP INDEX "idx_chunks_bigram";

-- DropIndex
DROP INDEX "idx_chunks_embedding";
```

**根因**：Prisma 把"库里存在但 schema 里没有"的索引统一视作**漂移**，并在下一次迁移里清掉。
`0002_knowledge` 里的两条手写索引在 schema 里"没有对应声明"（Prisma 表达不了），于是被打成多余对象。

**为什么 P0-1-5 的结论会误导人**：P0-1-5 的 `messages` 分区探针结论是"Prisma 能正确识别分区、不会重建它"，
当时顺势记成了"Prisma 会跳过它不认识的东西"。**这两件事的机制不同**：

| 对象 | Prisma 的行为 | 后果 |
|------|---------------|------|
| `messages_2026_01` 之类的**分区子表** | **跳过**（识别为分区，不纳入漂移） | 无 |
| 手写的**索引**（HNSW / `gin_bigm_ops`） | **当作漂移，生成 `DROP`** | 静默丢索引 |

⇒ **无法用一条"Prisma 对未知对象很宽容"的经验概括两类对象**。每引入一类新的"schema 表达不了的对象"
（分区、特殊索引、触发器、视图、自定义类型…）都要**单独做一次反向探针**，不能沿用上一个的结论。

**后果的严重性**：这次是 `chunks` 的两个检索索引。如果放任，**P0-2 加 MCP 相关表时**（任何 schema 改动都会触发）
两条索引会被静默删除 —— 表还在、数据还在、代码照跑，只有"检索悄悄退化成全表扫描"。
这类问题在开发期（表小人少）几乎不可见，正是最该被守门的一类。

**对策（两条路不同）**：

1. **`idx_chunks_bigram`（GIN）—— 在 schema 里声明**（Prisma 能表达，就不需要藏）：

   ```prisma
   @@index([content(ops: raw("gin_bigm_ops"))], type: Gin, map: "idx_chunks_bigram")
   ```

   三个参数**都不是可选的**，实测各缺一个的后果：
   - 缺 `ops` ⇒ 生成默认算子类，与手写 DDL 不一致 → diff 不为 0；
   - 缺 `type: Gin` ⇒ 按 **btree** 生成（Prisma 的默认索引类型）；
   - 缺 `map` ⇒ 每次 diff 都想把索引改名为 `chunks_content_idx`。

2. **`idx_chunks_embedding`（HNSW）—— 藏进"部分索引"这一类**：
   Prisma 7.10.0 **没有** `Hnsw` 索引类型（`type: Hnsw` 直接报 `Unknown index type`），
   也没有 `WITH (m, ef_construction)` 的语法位置 ⇒ 只能手写 DDL，于是必须让它不被 diff 看见。

   实测的"藏身"判据：

   ```
   反手建 普通 btree 索引（不在 schema）      → 立即 DROP INDEX
   反手建 表达式索引（不在 schema）           → 立即 DROP INDEX
   反手建 部分索引（带 WHERE 谓词）           → Prisma 一条 diff 都不出   ← 唯一安全
   ```

   **注意"表达式索引也会被 DROP"这一条**：它说明 Prisma 的漂移识别是**读 `pg_index` 的**（不只看列），
   所以"藏"不能靠"Prisma 读不懂表达式"，只能靠"**Prisma 不看带谓词的索引**"这个特定行为。

   写成：

   ```sql
   CREATE INDEX "idx_chunks_embedding" ON "chunks"
       USING hnsw ("embedding" vector_cosine_ops)
       WITH (m = 16, ef_construction = 64)
       WHERE "kb_id" IS NOT NULL;
   ```

   `WHERE kb_id IS NOT NULL` **不是业务过滤**（`kb_id` 是 NOT NULL 列，谓词恒真）⇒
   索引覆盖全部行，**内容与全量 HNSW 完全等价**（已断言取证）。

**代价与守门**（必须说清，因为这两个机制一旦失效是**静默**的）：

- 代价：规划器只在查询**能推出该谓词**时才用这条索引。而向量路本来就必须按库收窄
  （`子方案①` §6-1「绑定某 Agent 的每个库各查一次」，`WHERE kb_id = $2 ORDER BY embedding <=> $1`），
  `kb_id = $2` 蕴含 `kb_id IS NOT NULL` ⇒ 照常走索引。
  **已额外探针取证 `kb_id = ANY(...)` 与 `kb_id IN (...)` 也蕴含**（P0-1-20 多库检索形状）：
  ```
  Index Scan using idx_chunks_embedding on chunks
    Filter: (kb_id = ANY ('{…}'::uuid[]))
  ```
- 守门：`verify:knowledge` 三条断言盯着 —— ① `migrate diff --exit-code` 必须为 **0**；
  ② HNSW 的 `pg_index.indpred` 仍等于 `(kb_id IS NOT NULL)`；③ 两条路 `EXPLAIN` 真的命中各自索引。
  **换 Prisma / PG 版本前先重跑这三条**（与 P0-1-5 的"升级前重跑分区探针"同一纪律）。

## 坑 2（预判证伪）：`USING gin (content)` 不是静默建错，而是直接报错

**`06` P0-1-14 的坑预判原文**：「建索引必须显式写 `gin_bigm_ops`，用默认 `gin` 会**建错算子类且不报错**」。

**实测**（PG 16.15 + pg_bigm 1.2）：

```
ERROR:  data type text has no default operator class for access method "gin"
HINT:   You must specify an operator class for the index or define a default operator class for the data type.
```

⇒ 它会**在建索引时立刻失败**，而不是"静默建成一个错的"。同时取证了机制：

```
gin_bigm_ops(default=false)
```

即 `pg_bigm` 提供的 `gin_bigm_ops` **刻意没有**把自己设成 `text` 的默认 GIN 算子类
（因为 `text` 上可以装多个 GIN 算子类，官方不替用户选）。

**所以真实的风险变了**：不是"静默建错"，而是"**报错文案里不含 `gin_bigm_ops`，容易被误读成 `pg_bigm` 没编进镜像**"
（本仓的 PG 镜像是源码编译 pg_bigm 的，团队对"没编进去"本来就敏感，正好会往那个方向猜）。
把这条写清楚，能省下一次"去查 Dockerfile"的误判。

**因此验收不止断言"索引存在"**，而是三层：
① `pg_indexes.indexdef` 逐字含 `gin_bigm_ops`；② 断言 `text` 确实**没有**默认 GIN 算子类（机制取证）；
③ `EXPLAIN` 中文 `LIKE '%中文%'` 真能命中这条 GIN（**存在 ≠ 可用**）。

**教训**：`06` 的坑预判是"设计期写的可能性"，不是"事实"。花几条 SQL 把它证伪/证实，
结论写回 `06` 与这里 —— 这条已经写进 `docs/06` P0-1-14 的坑预判段（标注"经实测部分不成立"）。

## 决定 1：主键口径统一 `uuid(7)`，改掉 `子方案①` §4-4 的 `bigserial` 草稿

**背景**：`子方案①` §4-4 的 DDL 草稿给三张表的主键写的是 `bigserial`；
而 `docs/02` §3.1 早已定案全仓「一律 `uuid(7)`」。两份文档对**同一条 DDL**给出不同口径 = 文档腐烂。

**判据（哪个该改）**：`agent_components.ref_id` 在 P0-1-5 已经落成 `UUID` 列。
它的语义是"指向被挂载对象（含知识库）的 id" ⇒ **将来要指向 `knowledge_bases.id`**。
若知识库主键是 `bigserial`，那条外键永远指不上。⇒ 以 `02` §3.1 为准，改 `子方案①` §4-4。

**代价（必须提前知道）**：`@default(uuid(7))` 是**客户端**默认值、不进 DDL（P0-1-5 的函数型默认值口径），
所以 `chunks.id` 由客户端生成 ⇒ **P0-1-19 手写 `INSERT ... SELECT unnest(...)` 必须自带 id 数组**
（不能用 `RETURNING id` 反过来拿，因为要一次插一批）。已写进 `docs/06` P0-1-19 的坑预判。

## 决定 2：`knowledge_bases.embedding_model` 定为 NOT NULL

**依据**：它是 `子方案①` §八「换 embedding 模型的重建路径」的**判据** —— 建库时快照
`EmbeddingProvider.name()`（`api:<模型名>` / `local:<目录名>`），入库/检索时比对是否漂移。
`02` §三 只写了列名、未标可空，按其用途应是 NOT NULL（可空则判据失去意义）。

**副作用（刻意保留）**：`EmbeddingProvider` 的取值依赖 provider **已就绪**
（`config.embedding.apiReady=false` 时 `getEmbeddingProvider()` 会硬报错）。
⇒ **本机 `.env` 的"`EMBEDDING_MODE=api` 三项空"状态下，P0-1-15 建库会直接失败**。
这是刻意的（那样建出来的库不可能完成入库，早失败比晚失败好），但 **P0-1-15 的验收要先备好 embedding 配置或假上游**。
已写进 `docs/06` P0-1-15 的前置说明。

## 给下一个人（或下一批）的三句话

1. **动 `chunks` 相关 schema 前**，先跑一次 `migrate dev --create-only` 看有没有 `DROP INDEX` —— 两条守门断言
   都在 `verify:knowledge` 里，跑一遍比读这段字快。
2. **升级 Prisma / PG 前**，先重跑 `pnpm verify:knowledge`（尤其 `migrate diff --exit-code` 那一条）与 `pnpm verify:db`。
3. **要在 `chunks` 上再加"Prisma 表达不了的索引/对象"**，别照抄这两条 —— 先做一次反向探针，
   确认它属于"被跳过"（分区）还是"被 DROP"（索引）还是"被忽略"（部分索引）哪一类。
