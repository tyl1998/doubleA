## 0. 一句话结论

**本批把"一个注册者定义的参数模板，怎么算合法、改了它该提示谁"这两件事钉成了可断言的契约。**

> `shared/src/mcp.ts` 仍是**契约唯一落点**：形状留在 `credentialSchemaEntrySchema`，
> **语义层（`key` 按注入位置分判 + 同模板内判重）只有一份实现** `credentialSchemaDeepIssues()`；
> 写端两个入口（zod 的 `superRefine` 与**永不抛错的独立函数**）调它，读端另有一个
> `normalizeCredentialSchema`（逐条过滤、只求能渲染）。
>
> `backend/src/services/mcpServer.service.ts` 的 `updateMcpServer` 只多做一件事：
> **把"这次模板变更会影响什么"如实带回去，然后一个字都不动用户的凭据**。

**四条坑里最值钱的一条是"BODY 注入能不能做 —— 是探出来的，不是读文档读出来的"**（§3）：
一次探针同时定下了"BODY 可行""两条不可用""哪四个键必须拒"和"P0-2-7 拿什么去注入"。
**最容易被合并掉的一条是"'缓存该不该清'与'该提示什么'是两个判据"**（§4）——
合并的两种坏结果都很安静。

## 2. ⚠️ 坑一：三条规则都属于**"形状合法、但注入出去一定出错"**

这是本批的**设计起点**：这三条错**在模板层一个都不会报** —— 要等到真正调用时，
甚至只表现为"凭据没生效"（用户会以为是凭据填错了）。

| `inject` | 落点 | `key` 的约束 | 违反的后果 |
|---|---|---|---|
| `HEADER` | 请求头 | 合法 HTTP 头名（RFC 7230 的 `token`，**用正则判**，不是"不含空白"）+ **不得占用平台自己要发的头** | `X-User Token` / `X-User:Token` 会被 fetch/undici 拒绝或**静默截断**；占用平台头见下 |
| `QUERY` | URL 查询串 | 不得含 `&` / `=` | 把查询串切开 ⇒ 服务端收到的**键名与模板里写的不同** |
| `BODY` | 请求体**顶层** | 不得是 JSON-RPC 的保留成员（**按字面**比较） | 撞名会毁掉报文语义（见 §3 的 H3） |

**平台保留的请求头**（按**小写**比较 —— HTTP 头名不区分大小写）：
`accept` / `content-type` / `content-length` / `host` / `mcp-session-id` / `mcp-protocol-version`。
前四个是 HTTP 与 fetch 自己用的；后两个属 **Streamable HTTP 传输层**（会话与协议协商）。

> ⚠️ **占用 `accept` 的后果最隐蔽**：注入会覆盖掉"**回 JSON 还是回 SSE**"的协商头。
> 症状是"这个 server 的凭据一配上、工具就调不动了"，而**报错会指向上游**（`06` P0-2-7 坑预判 1）。

**JSON-RPC 请求对象的保留成员**：`jsonrpc` / `id` / `method` / `params`。
⚠️ 键名集合**只有这四个** —— 响应里的 `result`/`error` **不在其中**（我们发的是**请求**）。

### 2.1 为什么"判重"必须挂在整个数组上

`superRefine` 挂在**数组**上而不是每条上 —— 判重是**跨行**的，逐条 refine 看不到别的行。
⚠️ 由此带出一个**容易写错**的点：形状错的行会被过滤掉，**过滤之后下标就没了** ⇒
语义层必须显式收 `{index, entry}[]`（把**原始下标**一起传下去），否则字段级 `path` 会指到错误的行。

### 2.2 为什么"形状"与"语义"分开、却只留一份实现

- **形状**（键齐不齐、长度、取值域）留在 `credentialSchemaEntrySchema`（zod）；
- **语义**（三条按位置的 `key` 规则 + 同模板内判重）收进 `credentialSchemaDeepIssues()`。

两条路径都调它：`credentialSchemaSchema.superRefine`（**只补语义** —— 形状由逐条 schema 与
`.max()` 报，报两遍会让前端看到两行一模一样的红字）与**独立入口** `validateCredentialSchema`
（**形状 + 语义两样都做、永不抛错**，给"手上只有一份 `unknown`"的调用方用）。

> 这是断言形态 ⑰（"同一口径在两处各写一遍，必有一处先腐烂"）的**预防性处置**：
> 本批的 `key` 规则有 3 条 × 3 个位置，写两份几乎必然会分叉。

## 3. ⚠️ 坑二：BODY 注入的**协议线探针**（P0-2-3 坑预判 1 的兑现）

`06` 的坑预判原文是"`inject: 'BODY'` 与 JSON-RPC 报文天然冲突"，并要求**先做探针、再落笔**。
探针放在 `verify-mcp-client` 的 **H 组**（那里已经有一个"真 HTTP 假上游 + 记账"的夹具），
用**裸 `fetch` 手写报文**、刻意绕开 SDK —— 因为 SDK 的 `callTool` 根本没有"往报文里加顶层字段"的参数
（**这本身就是 H4 要证的结论**）。

| 问题 | 结论 | 取证 |
|------|------|------|
| 非保留的**顶层额外字段**，服务端认不认？ | **认，且完全不影响这次调用** ⇒ `BODY` 注入**在协议线上可行** | H1 |
| 塞进 `params.arguments` 呢？ | **污染工具入参** —— 凭据混进了工具自己的参数里（夹具把两者一起回显了） | H2 |
| 塞成 `params` 的**兄弟键**呢？ | **凭据等于白注** —— 服务端按工具契约只读 `name`/`arguments`，根本看不到它 | H2 |
| 与四个保留键**撞名**呢？ | 撞 `method` ⇒ 这次调用**变成另一次调用**（服务端回了 `tools/list`）；撞 `params` ⇒ 工具名丢了、服务端回 `-32602`；撞 `id` ⇒ 响应 id 被顶成凭据值并被**原样回显到线上**（关联被毁 **且** 凭据漏到链路上） | H3 |
| **拿什么去注入**？ | `StreamableHTTPClientTransport` 的 **`fetch` 选项**能同时改 URL / 请求头 / 报文体 ⇒ 三种位置**一个口子全包**，不必改 SDK、也不必为 `BODY` 造旁路 | H4 |

> **坑预判的结论因此被改写**：不是"BODY 不能用"，而是"**四个键名**不能用"⇒ 处置落在
> 模板层的 `MCP_JSONRPC_RESERVED_KEYS` 校验上，而不是"禁掉 BODY 这个选项"。
> 这类"先证伪再落笔"的做法从 P0-1-14 起就是本仓的规矩。

**P0-2-7 的接回点（H4 的产物）**：`McpClient` 目前**没有**把 transport 的 `fetch` 选项透出来
⇒ **加一个可选参数即可**（客户端层不用重构），注入中间件就落在那**一个点**上
（HEADER/QUERY/BODY 三种位置在同一个 `fetch` 里完成，`verify:mcp-client` H4 已演示过完整形态）。

> ⚠️ **这条结论只对本仓夹具成立**：规范**没有**规定服务端必须忽略未知的顶层成员。
> 本档的价值是把"该不该在模板层拒掉那四个键"这类**必须现在就定**的事先定下来；
> 真正的兜底是 **P0-2-7 落地后用真 server 复验一次**（已写进 `docs/02` §9.4）。

## 4. ⚠️ 坑三："**缓存该不该清**"与"**该提示什么**"是两个判据

这两个问题的输入是同一份（旧模板、新模板），但**结论可以不同，而且不同才是对的**：

| 判据 | 实现 | 问的是什么 | 只改 `label` 时 |
|------|------|-----------|----------------|
| 缓存该不该清 | `sameJson`（**整体**比较） | 模板**整体**变没变 | **要清**（模板确实变了，缓存里的工具列表按旧模板谈的） |
| 该提示什么 | `diffCredentialSchema`（**key 级**） | **已存凭据会受什么影响** | **不提示**（`label` 是文案，值还是注到同一个 header 上） |

合并的两种坏结果都很安静：
- 合并到"整体" ⇒ **改个文案就弹一串"某某参数受影响"的无意义警告**（用户会开始忽略这些提示）；
- 合并到"key 级" ⇒ **改了模板却不提示**（值悄悄不再被注入，而用户以为还在用）。

`diffCredentialSchema` 自身还带两条口径：**只按 key 判**（`label`/`required`/`placeholder` 都不算改动）、
**顺序不算改动**（模板是数组、顺序即界面顺序，但"换了个位置"不该被报成增删 —— P0-1-23 第 ④ 条同源）。
⚠️ 判重与判差异都用 key 的**字面**：把 `Token` 改名成 `token` 会被如实报成"移除 + 新增"——
那正是要让用户看到的（他改的确实是一个"新键"）。代价是 HTTP 头名的大小写变体本阶段不拦（已注明）。

**验收 H2 就是守这两个判据不合并的那条**：同一份输入（只改 `label`）⇒ 断言
`credentialSchemaImpact === null` **且** `toolCount === 0`（缓存照清）。

## 5. ⚠️ 坑四：`affectedCredentials` **刻意留白**（恒 `null`，不填 `0`）

`credentialSchemaImpact` 有四个键，其中 `affectedCredentials`（"值里含被移除 key 的凭据条数"）
在本批**恒为 `null`** —— 因为 `mcp_credentials` 表要到 **P0-2-4** 才建，
**后端此刻没有能力回答这个问题**。

> 填 `0` 的后果：它会成为一句"**没有凭据受影响**"的断言，而这句断言此刻**无法作出**。
> 界面会照它显示"0 条受影响"，用户会相信一个我们编出来的数字。
> （与 P0-1-34/35 第 ⑦ 条"**给不出数字时宁可留白**"同源。）

⚠️ **`null` 在这份契约里只有一个含义**："本次没有任何需要提示的影响" —— 既包括**没提交模板**，
也包括**提交了一份与当前等价的模板**。让"三个数组都空"的形态也在线上出现，前端就得多写一个
`length === 0` 的分支，而那条分支与 `null` 分支做的事一模一样（P0-1-21 的"同一份数据两种形状"）。

⚠️ **接回点**：`verify:mcp-servers` 的 **H1 里有一条守着"它现在必须是 `null`"的断言**，
P0-2-4 建表后**翻转**它并换成真数（数 `values` 里含 `removedKeys` 的行）。
`credentialSchemaImpactOf` 里的那一行是 `affectedCredentials` 的**唯一赋值点**。

## 6. 坑预判逐条落实

## 8. 本批的取证方式与边界（诚实标出）

**能证的**：
- 模板的**形状与语义规则**逐条有断言（无依赖档，`verify:app`）；
- `PATCH` 的**影响提示**在真库里跑通（有 PG + Redis 档）：删/增/换位置分类正确、
  **只提示不清理**（库里模板一字不多不少）、**两个判据不合并**（H2）；
- **BODY 注入在协议线上可行、两条替代落点不可用、四个键必须拒**、以及
  **`fetch` 选项是三种注入位置的统一口子**（假上游档，H1~H4）。

**不能证的（别当已验过）**：
1. ⚠️ **H 组探针的被探方是本仓的假 MCP server** ⇒ 它证明的是"**我们发出去的报文**能被一个
   按规范实现的 server 正确处理"，**不等于**"真 MCP 服务端也忽略未知顶层成员"
   （规范没这么要求）。⇒ **P0-2-7 要用真 server 复验一次**。

## 9. 一句话给下一个动这一块的人

> **`credential_schema` 的两半不要混**：**模板**（注册者定义的，可以整体覆盖、本次会回带
> `credentialSchemaImpact`）属**本批**；**值**（每用户一份、加密存储、绝不下发）属 **P0-2-4**。
> 改模板时**只允许提示** —— 自动清理会把"用户临时改错模板"变成**不可逆的数据丢失**，
> 而他什么都没做。
>
> 动 **P0-2-7（凭据注入）**时：注入口子已经探好了（transport 的 `fetch` 选项，H4 有完整演示），
> **BODY 只能注到报文顶层、且必须避开那四个保留键**（否则会毁掉这次调用、甚至把凭据回显到线上）；
> HEADER **不得占用平台自发的六个头**（尤其 `accept` —— 它决定"回 JSON 还是回 SSE"）。
>
> 动 **P0-2-4（凭据表）**时记得三件事：① 建 `mcp_credentials` 表（一批一张迁移）；
> ② 把 `credentialSchemaImpactOf` 里那行 `affectedCredentials: null` 换成真数、
> **并翻转 `verify:mcp-servers` H1 守着 `null` 的那条断言**；③ 写入/清理由**用户自己点**，
> 不因为模板变了就替他删。
