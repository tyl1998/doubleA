## 坑 1 ⚠️ 断言"每条的向量分都 > 0"是**假失败**：正交向量的余弦相似度**恰好是 0**

**现象**（首轮 `verify:retrieval` 的输出，逐字）：

```
[FAIL] **VECTOR 模式：含关键词的那一块排第一**（向量路是一路真检索，不是摆设）
       向量分应为正数：{"chunkId":"01a0c77c-301e-72a0-…","docName":"考勤管理.txt",…,"vectorScore":0,"vectorRank":3,…}
```

**根因**：`vectorScore = 1 - (embedding <=> query)`。两个向量**正交**时余弦距离恰为 `1`，
于是相似度**恰好是 `0`** —— 这是合法且有意义的取值（"这一块与 query 毫无共同 2-gram"），
不是"没算出来"（那是 `null`）。我把它写成了 `> 0`，于是在"某一块与 query 完全不相关"时假失败。

**对策**：把断言改成**想验的那件事** —— "含关键词的那一块必须**严格更近**"
（`items[0].vectorScore` 严格大于其余每一条）。这比 `> 0` 强得多，而且不会误伤正交。
另外把 `null`（未命中/未运行）与 `0`（命中但正交）的区分写进契约注释与 `verify:app` 的断言。

> 这类"断言自己写错、却看起来像被测代码坏了"的失败是 P0-1-17/18/19 记过的同一族（第 ⑥⑦ 种形态），
> 报错信息一律指不到自己头上。**判据：先把期望值在两个方向各算一遍，再写断言。**

## 坑 2 ⚠️ "长 query 截断到 64 字符后仍应命中"——这个前提本身就是错的

**现象**（同一轮输出）：

```
[FAIL] 长 query 截断到 64 字符（全文路；向量路不受影响）
        截断到 64 字符后仍应命中（关键词在前 64 字符内）：期望 1，实际 0
```

**根因**：我用 `'出差住宿标准的相关规定到底是怎么写的呢'.repeat(8)` 拼了一个长 query，
以为"前 64 字符含关键词 ⇒ 截断后能字面命中"。**错**：全文路是
`content LIKE '%<needle>%'`，要求 needle **整段连续出现**在正文里 —— 截断只保证
"模式串不长"，**不保证**那 64 个字符连续存在于任何一块正文中。自然语言问句几乎必然不连续。

**这同时是一条产品级的边界**（不是 bug、也不是本批的实现问题）：**`FULLTEXT` 模式只适合短查询**。
已写进 `子方案①` §6-1 的落地口径、`06` P0-1-21 的坑预判、README 的"检索专项边界"。

**对策**（把用例改成"命中只能由那次截断解释"）：

1. 从**长正文里取一段 64 字符的业务内子串**（夹具的填充句刻意不含标点，否则会被预处理剔掉而对不上），
   后面拼一段长后缀 ⇒ 整条 query 远长于 64；
2. 先用**不截断**的独立 SQL 复算一次，断言 `count = 0`（证明"整条 query 必然命不中"）；
3. 再打端点，断言命中 1 条且是那一篇 ⇒ **命中只能来自截断**。

## 坑 3 ⚠️ 文档里的 RRF 示例数值是错的（0.0323 → 实测 **0.0320**）

**现象**：`子方案①` §6-2 写"只在单路拿到第 1 名（0.0164）会输给两路都排中游的（向量第 1 + 全文第 4 = **0.0323**）"。
按公式 `1/(60+1) + 1/(60+4) = 0.016393 + 0.015625 = 0.032018` ⇒ 应是 **0.0320**。

**根因**：`06` 的坑预判原文就点过这件事（"RRF 示例数值算一遍再写进文档（参考项目踩过：文档里的数值要实测）"），
但那条提醒一直躺在文档里没被执行。文档里的数字**看着无害**，实际会被下一个人当"实测值"引用
（本批的引用示例 JSON 里也抄了这个数）。

**对策**：① 订正 `子方案①` §6-2 并补一张四情形数值表（两路都第 1 = 0.0328 / 向量 1 + 全文 4 = 0.0320 /
单路第 1 = 0.0164 / 单路第 3 = 0.0159）；② 把这三个数值写成 `verify:app` 的断言
（`rrfScoreOf(...).toFixed(4)`）—— **文档与代码从此互为守门**：谁改了公式，断言先红。

## 坑 4 ⚠️ `§6-1` 的"去停用词"照字面实现会**降低**命中率

**问题**：`§6-1` 原文是"query 去停用词、去标点后作为 LIKE 子串"。但 LIKE 要的是**连续子串**：

```
正文：出差住宿标准为每晚上限 500 元
query：报销的标准是多少  --(按字删停用词)-->  报销标准   ⇒ 正文里没有"报销标准"这四个连续字 ⇒ 命中不了
query：报销的标准是多少  --(只剥首尾脚手架)--> 报销的标准 ⇒ 与正文的"报销的标准"一致 ⇒ 命中
```

**对策**（收窄，并回写文档）：**只剥句首/句尾的提问脚手架**（"请问…是多少"这类，本来就只在两端），
剔标点（全部），中间的停用词**一律保留**；并显式**不剥否定词**（"不含税"→"含税"是**语义反转**，
比召回率低严重得多）。验收有"中间的『的』必须保留"的专门断言。

## 坑 5 ⚠️ `%` 与 `_` 是 LIKE 的通配符：不剔除 = 静默从"字面匹配"变成"模式匹配"

**问题**：全文路的 SQL 是 `content LIKE '%' || $1 || '%'`。若 needle 里留着 `%`，
`query = 5%0` 会变成 `LIKE '%5%0%'` ⇒ 命中"5 … 0"这种毫不相关的内容（还会命中一大片）。

**对策**：query 预处理里剔的是 `[\p{P}\p{S}\p{C}\s]`，而 `%`/`_` 都是 `\p{P}` ⇒
**顺手解决，且不需要再叠一层 LIKE 转义**（多一层转义就多一处会漏的地方；转义写错时同样静默）。

**验收的判别式**（关键在构造）：造一块正文**同时含 `5` 与 `0`、但两者永不相邻**：
`%` 被剔除 ⇒ needle = `50` ⇒ 0 条；`%` 当通配符 ⇒ 1 条。**两种实现的期望值不同，断言才有判别力**
（若正文里含 `50`，两种实现都命中，那条用例就是白测的）。

## 坑 6 `score`（相似度下限）只作用于向量路，且过滤放在候选池**之后**

- `bigm_similarity` 与 cosine 的量纲、分布都不同，给全文路套同一个阈值是**两套量纲混用**；
- 过滤放在 `LIMIT` 之后与之前**等价**（距离单调 ⇒ "最近的 N 条里过线的" = "过线的里面最近的 N 条"），
  但放后面能少传一份 20KB 的向量字面量（1024 维的 `[0.1,0.2,…]`）。

验收用 `score=1` 取证（只有与 query 完全同向的向量能过 ⇒ 本用例一条不剩），
并断言 `vectorPathSkipped === false`（是"跑了但被下限过滤"，不是"没跑"）。

## 坑 7 ⚠️ `ORDER BY embedding <=> $1, id` 会让 HNSW **退化** ⇒ tie-break 必须在 JS 侧做

**问题**：为了让"同一 query 两次调用名次一致"，最自然的写法是给 SQL 加第二排序键。但
**HNSW 只支持单键距离排序** —— 加了第二键就变成"索引扫描 + 显式排序"（大表上直接退化成 seq scan + sort），
P0-1-14 那三条 EXPLAIN 守门断言也就白做了（索引还在，只是不再被用）。

**对策**：SQL 保持 `§6-1` 的单键形状；**取回候选池之后**在 JS 里按 `(score, id)` 稳定排序
（`stableOrder()`）。`fuseRrf` 的同分也按 `chunkId` 升序 —— uuid(7) 时间有序 ⇒ 等价于"先入库的优先"，
不引入文档没有的业务偏好。验收有一条"同分结果与输入顺序无关"的确定性断言。

> 边界说明：池的**边界处**若出现完全同距的两行，取哪一行仍是 PG 的自由（`LIMIT` 之前无法确定），
> 这是"平局本来就没有正确答案"的自然结果，不做过度设计。

## 其它值得记一笔的

### ① 假 embedding 上游新增了**可选**的 `semantic: true`（词面重叠型向量）

P0-1-19 留下的夹具是**哈希噪声**向量（两条文本的余弦相似度恒在 0 附近）⇒ 向量路**排序**在任何
语料上都等价于随机排序。"链路通了"能验，"含关键词的那一块排第一"**验不到**。

新增 `semanticVectorFor()`：把文本切成**字符 2-gram**，每个 gram 哈希到一维并置 1，最后 L2 归一化。
于是"query 的 2-gram 都在这一块里" ⇒ 余弦 ≈ `sqrt(|q|/|块|)`（实测：8 个 2-gram 的 query 对约 55 字的块
≈ 0.38，对不相关块 ≈ 0.05 以下）。

**默认仍是哈希噪声**（`options.semantic !== true` 时走老路）—— 不改既有脚本已断言的向量性质
（`verify:ingest` 的"同一文本距离为 0 / 最近邻是它自己"两条照旧通过）。

> ⚠️ **这条断言的边界必须说清**：它是**字面重叠**型向量，不是真语义。所以
> "向量路命中了含关键词的块"在这个夹具下证明的是**链路正确**（query 向量 → `<=>` 距离 → 名次 → 融合），
> **不证明模型的语义质量** —— 后者要真 embedding 模型（`06` §七 待决事项 2）。

### ② "与独立 SQL 等价"是本批最重要的一条验收手法

只断言"返回非空 + 有六列分数"，一个把 `ORDER BY seq` 当排序的假实现**照样全绿**
（分数可以随便填、名次也自洽）。本批的做法是：脚本**独立跑一遍同形状 SQL**（不经任何业务代码），
逐条比对 `chunkId` 名次与分数：

```
向量路：SELECT id, (1 - (embedding <=> $1))::float8 FROM chunks WHERE kb_id = $2 AND embedding IS NOT NULL ORDER BY embedding <=> $1 LIMIT pool
全文路：SELECT id, bigm_similarity(content, $1)::float8 FROM chunks WHERE kb_id = $2 AND content LIKE '%'||$1||'%' ORDER BY score DESC LIMIT pool
```

这条同时证明了**用的是 bigm**（不是别的东西排的序）—— 比"返回非空"强得多。

### ③ 检索测试页的"可覆盖"与"不可覆盖"是刻意的

`topK`/`mode` 可在单次请求里覆盖（试查页要"同一 query 试三种模式"，每次去 PATCH 库配置会**污染**别人
的检索口径），且有一条断言证明**覆盖不落库**；`score`/`rrfK`/`weights` **不可覆盖** —— 它们是
"这个库的检索口径"，让一次点击就能改掉别人的召回率，比看不到更坏。

### ④ 引用片段"不加工"是硬要求，不是风格问题

`§六` 的示例 JSON 里写着 `"……出差住宿标准为……"`，而 `§九` 要求"不加工、不摘要"，
验收又要求"片段与原文一致可核对" —— 三者里**省略号是唯一可以去掉的**：带了省略号的字符串
**不再是原文的子串**，那条验收就永远做不成。故后端只给原始窗口，省略号归前端（展示层）。

### ⑤ 本批的时间分配（给下批一个预期）

"写实现"大概占四成，**其余六成在验收脚本与文档订正上**：两个假失败（坑 1/2）各花了来回一轮，
文档里有三处口径/数值需要动手改（坑 3/4 + 响应示例）。这与前几批的体感一致 ——
**验收脚本写不动的批次，等于没验**。

## 遗留 / 下批提醒

1. **这不是浏览器可端测的里程碑**：列表/下载端点是 P0-1-21、界面是 P0-1-30。
   但 **API 级"上传 → 入库 → 检索"已经整条打通**（`curl POST .../search` 能拿到双路分数与 RRF 名次）。
2. **手工跑检索要先配好 `EMBEDDING_*`**（要算 query 向量）：本机 `.env` 三项为空时 `HYBRID` 会
   降级为纯全文并给 warning，`VECTOR` 报 500。零配置的完整跑法是 `pnpm verify:retrieval`。
3. `chunks.meta.embeddingName` 目前**只写不读**（`§八` 的换模型重建要靠它分辨"哪些行是旧模型产的"）
   —— 那是 P1「重建索引」的输入，本批只在**库级**（`knowledge_bases.embedding_model`）做了探测。
4. 跨库检索（`kb_id = ANY($2)` 的形状）**SQL 已就位**，但本批的端点只查一个库；
   F 包的对话编排要一次查 Agent 绑定的多个库时，只需改调用方（`searchKnowledgeBase` 目前收单个 `kbId`，
   届时按"以哪个库的 `retrievalConfig` 为准"补一条口径）。
5. `candidatePool` 目前是 `topK × CANDIDATE_POOL_FACTOR`（环境级）。若将来发现"多库检索时候选池太小"，
   先改那个环境变量 —— 别顺手把它塞进 `retrieval_config`（那是 KB 级快照，语义不同）。
