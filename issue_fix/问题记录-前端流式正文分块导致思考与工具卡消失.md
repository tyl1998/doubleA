> 批次：P1-21 前端长会话内存优化（P3 回退 + 贴底跟随修订）
> 日期：2026-10-24
> 关联：`docs/子方案/前端长会话内存优化.md` §P3；`docs/06-实施计划.md` §五 P1-21「同批另含」；
>      `docs/03-前端设计.md` §4.1「贴底跟随」
> 定位：本文件记录"内存优化 P3 引入的两处可见缺陷"的现象、根因与修法。子方案与计划文件只留指针。
> 症状一（思考 / 工具卡**消失**）：回退 P3 分块；症状二（**输出完不定位到文末**）：补晚一拍贴底跟随。

---

## 现象（用户报）

发起一轮聊天后，**模型开始返回正文的那一刻**：

1. 思考块与工具卡**整批消失**；
2. 等正文"回归"（收尾）时它们又出现；
3. 视口被带到**开头**，而不是停在尾部（贴底跟随失效）。

## 根因（纯读代码即可定位，无需起浏览器）

内存优化 P3 把流式正文切成"稳定前缀 + 尾巴"两段渲染（`AssistantMarkdown`），而**内联条目
（思考块 / 工具卡）只在解析时被插**（`remarkInlineBlocks` 是一个 remark 插件）：

- 前缀用 `stablePlugins = [remarkGfm]` 解析 —— **不带**条目；
- 尾巴短时按**纯文本** `<div className="md md--tail">` 渲染 —— **根本不解析**。

于是正文一旦开始到达（`text !== ''` ⇒ `tail !== ''`），两条分支都不插条目 ⇒ 思考与工具卡
**整批消失**，直到 `streaming` 变 `false` 走整篇解析才回来。同时纯文本尾巴没有 `.md` 的块级
排版（段落/列表/代码块），内容高度骤降 ⇒ 滚动容器的 `scrollTop` 被钳在旧值、贴底跟随的
`pinnedRef` 也已在高度变化中失效 ⇒ **视口停在开头**。

**关键结论：这个优化并没有真正省下解析。** `react-markdown@10` 的同步 `Markdown` 组件
（`node_modules/react-markdown/lib/index.js` 的 `export function Markdown(options)`）**没有任何
memo**：每次调用都 `createProcessor → parse → runSync` 整篇。所以"把哪一段交给它"不改变
"父组件每帧重渲染 ⇒ 每帧全量解析"这一事实 —— 分块只带来了缺陷，没带来收益。

## 修法（2026-10-24 定案：回退分块）

1. `AssistantMarkdown`：删掉 `streaming` 入参、`streamingMarkdownChunks` / `shouldParseTail` 与
   两段渲染分支，恢复"**与历史消息逐字同款：整篇解析一次**"单棵元素树。
2. 删除 `frontend/src/features/chat/markdownChunks.ts` 与 `frontend/scripts/verify-markdown-chunks.mjs`，
   并从 `frontend/package.json` 去掉 `verify:markdown-chunks`。
3. `AssistantMessage` 不再传 `streaming`（`streamingThinkingIndex` 保留：它决定"哪一段思考仍在
   生成"，与分块无关）。
4. 剩余的内存收益**不依赖 P3**：P2 的组件 `memo`（`AssistantMessage` / `ThinkingBlock` /
   `ToolCard` …）与 P5a 的渲染窗口（`messageWindow.ts`）照旧生效。

## 为什么不去"按边界拆分条目"（另一条路的取舍）

理论上可以按 `stable` 边界把条目拆开（落在前缀的进前缀解析、落在尾巴的进尾巴解析，纯文本分支
也渲染落在尾巴里的条目）。但：① 它要改 `insertInlineEntries` 的偏移口径（尾巴内的偏移需减去
边界），复杂度落在**已经出过一次错**的那处逻辑上；② 它仍**省不下解析**（见上），只是把
"条目消失"这一个症状绕过去 —— 用复杂度换一个不存在的收益，不成立。

## 追加：同批的第二个症状「输出完之后没有定位到文末」（2026-10-24）

回退分块后，用户报告**另一条**症状仍在：正文**输出完之后**视口没有停在文末。

**根因**：同一批内存优化给 `.msg` 加了 `content-visibility: auto` +
`contain-intrinsic-size: auto 220px`（`app.css`）。`auto` 关键字让那个估高**按元素**记住
上一次实测值 —— 而一轮收尾时，流式气泡被**落库版本换掉**（React key 由 `stream:assistant`
换成真实消息 id ⇒ 卸载重挂，见 `roundReducer.ts#roundToViews`）。新元素**没有**记忆尺寸，
先按兜底的 `220px` 参与布局；而"贴底跟随"的 effect 依赖 `[messages]`，只在这次提交跑**一次**：

- 这一次读到的 `scrollHeight` 可能是**偏小的估算值** ⇒ 视口停在文末**之上**；
- 浏览器随后把新元素真的排出来（`content-visibility` 的渲染比该提交晚一拍）内容变高，
  但 `messages` 不再变化 ⇒ **没有第二次 pin** ⇒ 停在半途。

流式**期间**不犯这个毛病，正是因为它每一帧都换 `messages` ⇒ 每帧都 pin，估算误差被下一帧
纠正掉（收尾之后没有"下一帧"了）。

**修法**：在"贴底跟随"里补一个 `ResizeObserver` 盯**内容列**（`.stream__inner`，即
`frame.firstElementChild`）—— 每次真实变高都回调（含"估算 → 实测"那一次），回调跑在**布局之后、
绘制之前** ⇒ 在那里改 `scrollTop` 不会闪。判据仍只有 `pinnedRef`（用户贴底才跟随；主动上翻
不打断）。观察器只在节点真的换掉时重建（避免流式每帧 churn），三态切走或卸载时断开。

**为什么不用 `useLayoutEffect` / rAF 补一次**：那只是把"猜第几拍"换个地方写死，仍然赌
`content-visibility` 的实测在同一帧完成；`ResizeObserver` 直接以"尺寸真的变了"为准，不猜。
