## 坑 1 ⚠️ `§4-4` 的 `INSERT ... SELECT unnest(...)` 与 `uuid(7)` 只能有一个赢

**现象（写代码时发现的）**

`§4-4` 给的写入语句是：

```sql
INSERT INTO chunks (id, doc_id, kb_id, seq, content, meta)
SELECT ... FROM unnest($1::uuid[], $2::uuid[], ...)
```

它要求调用方**自带 id 数组**。但 `chunks.id` 的口径是 `uuid(7)`（`02` §3.1），
而 P0-1-16 已经为这件事踩过一次并**定案"不手搓 uuid7"**：`crypto.randomUUID({ version: 7 })`
在 Node 22.22 上**静默返回 v4**（不抛错、形态合法，只有版本位是 4，`@types/node` 的类型里
还没有 `version` 字段，`as` 强转把谎说圆了）。

于是"自带 id 数组"这句话等于要求**第二个 uuid7 实现**，而 `uuid(7)` 在本仓**只有 Prisma 的
`@default(uuid(7))` 一个来源**（它是客户端侧默认值 —— P0-1-14 实测过：函数型默认值不进 DDL）。

**根因**

Prisma 的客户端侧默认值只在走 Prisma 的写入路径（`create` / `createMany`）时才被赋值。
"手写 INSERT" 与 "让 Prisma 生成 id" 是两条互斥的路。

**对策**

改成三步、同一事务：

```
① DELETE FROM chunks WHERE doc_id = $1                      -- 先删后建（§七 的取舍）
② prisma.chunk.createManyAndReturn(...)                     -- id 由 @default(uuid(7)) 生成
③ UPDATE chunks AS c SET embedding = v.emb::vector          -- 手写 SQL 回填向量
     FROM unnest($1::uuid[], $2::text[]) AS v(id, emb)
   WHERE c.id = v.id
```

- 用 `createManyAndReturn` 拿回 id（返回顺序**无承诺** ⇒ 按 `seq` 归位，`seq` 是文档内唯一序号）；
- 向量用**文本数组** `'[0.1,0.2,…]'` 传参再 `::vector` 转换，**不是** `vector[]` ——
  后者要求驱动层认识 pgvector 类型，而 `text::vector` 是官方路径（P0-1-20 的 `embedding <=> $1` 同款）；
- 每批 200 行（`CHUNK_WRITE_BATCH`）：一条 SQL 的体量合理，也避开参数长度限制。

**验收怎么抓住它**：加了一条 **"id 的版本位必须是 7"**（`id.split('-')[2][0] === '7'`）。
这条是**唯一**能抓住"某天有人换回自搓 id"的东西 —— 手搓出来的 uuid 不会报错，只是版本位不同。

实测原始输出（探针 `probe-writer.mjs`，只读验证，未入库）：

```
inserted = 3
seq=0 idVersion=7 hasVec=true dist=0.3200 meta={"page": null, "headingPath": [], "embeddingName": "api:probe-model"}
seq=1 idVersion=7 hasVec=true dist=0.0000 meta={"page": null, "headingPath": ["探针标题"], "embeddingName": "api:probe-model"}
seq=2 idVersion=7 hasVec=true dist=0.3663 meta={"page": null, "headingPath": ["探针标题"], "embeddingName": "api:probe-model"}
维度检查: [ { d: 1024 } ]
第二次写入 inserted = 2 库内行数 = 2      ← 先删后建：3 条 → 2 条，无孤儿
残留文档行 = 0
```

> `dist=0.0000` 是"拿自己那条的向量去查"，说明 `<=>` 与 `::vector` 都工作正常。

## 坑 2 ⚠️ `§七` 的 `UPDATE` 列清单漏了 `file_name`

**现象**

按 `§七` 的清单实现完覆盖重建后，验收里一条"校验失败不应改动文件名"报出：

```
校验失败不应改动文件名：期望 "报销制度-v2.txt"，实际 "报销制度.txt"
```

——即**第二次**重建（内容变了）之后，`documents.file_name` 还是**第一次**上传时的名字。

**根因**

`§七` 写的是 `UPDATE documents SET status='PARSING', error_msg=NULL, content_hash=<new>,
file_key=<new>, chunk_count=0` —— 列清单里**没有 `file_name`**。但它在本仓承担两个职责：

1. 列表页的展示名；
2. **P0-1-21 下载端点的 `Content-Disposition` 文件名**（`document.service.ts` 文件头写明
   "让 `documents.file_name` 承担展示与下载命名"）。

旧名字留下来就会**说谎**：用户把《旧制度.docx》换成《新制度.docx》之后，列表永远显示旧名，
而下载下来的字节是新文件、名字却是旧的（`file_key` 里不带原名，事后无从分辨）。

**对策**

重建时**一并更新 `file_name`**，并把这处偏离写进 `docs/06` 落地要点 8 与 `子方案①` §七 的落地口径。

**为什么必须偏离而不是留着**：用户**没有任何别的入口**改名 —— "删除重传"是唯一的路，
而那会丢掉文档 id（决策 13 要保的正是 id 稳定："引用与 `agent_components.ref_id` 的绑定都不受影响"）。

## 坑 3 上传与重建的"入队失败"补偿能力**不对称**，而且不能装作对称

**现象 / 决策**

上传时入队失败可以**整次回滚**（删行 + 删对象）—— 因为行是它刚建的（P0-1-17 的
`rollbackRegistration`）。很自然会想给重建也写一个"回滚"。

但重建**做不到**：旧 chunk 一旦 `DELETE` 就回不来，旧 S3 对象也可能已经删掉。
"装作回滚成功"（返回 500 且说"什么都没变"）会让用户以为旧内容还在 —— 那是最坏的一种谎。

**对策**

重建的入队失败如实报告，并**指向可用的恢复手段**：

```
内容已替换成功，但任务入队失败（队列不可用）。该文档暂时停在「处理中」且内容尚未入库，
请稍后在该文档上点「重试」；原因：…
```

这条同时**反向决定**了 `retry` 的状态口径（见坑 4）。

**顺带一处刻意的换序**：旧 S3 对象在**"改行之后、入队之前"**删。
放在入队之后的话，"入队失败提前返回"会把清理一并跳过 ⇒ 泄漏一个对象
（此时 `documents.file_key` 已指向新对象，旧对象**已经是孤儿**，没有任何人会再来清理它）。

## 坑 4 `retry` 必须**放行 `PARSING`**，否则"卡住的文档"永远没有出路

**现象 / 决策**

第一版把 `retry` 写成"`PARSING` 就 409（正在处理中）"。这是错的：

P0-1-17 的失败处置里明确写过一种状态 —— **worker 读行/写状态本身失败（PG 挂了）、
worker 崩在中途、或者这一次"入队成功但改行失败"** —— 都会让文档停在 `PARSING` 且
**队列里没有活的任务**。文档卡在那里，靠的就是"重投同一个 job"恢复。
若 `retry` 因为"看起来正在处理"而 409，这些文档**没有任何出路**（重传会被判重命中跳过）。

**对策**

| 当前状态 | `retry` 的行为 |
|----------|---------------|
| `FAILED` | 放行。**并在端点里就把状态 CAS 翻成 `PARSING` 且清 `error_msg`** —— 交给 worker 翻的话，用户点完按钮会有一段"点了没反应"的空窗，看起来像没生效 |
| `PARSING` | **放行**（恢复入口，同上）。CAS 的 `where status='FAILED'` 自然不匹配，状态保持 `PARSING` |
| `READY` | **409**「该文档已是就绪状态，无需重试」。不是"没有必要"，而是"没有东西可重试"：入队也会被 worker 的幂等第 ④ 道跳过，回 200 会让用户以为在重新处理却看不到任何变化 |

验收把三条都钉住了（并顺带验了"跨库 docId → 404"，避免用 `docId` 探测别人库里有什么）。

## 坑 5 embedding 的重试粒度是"**批**"，而 provider 看不到"批"

**现象**

`§4-3` 要求"单批失败重试 2 次（指数退避 1s/3s）"，但 `EmbeddingProvider.embed(texts)` 内部
**自己**会按 `batchSize` 循环切批、逐批发请求 —— 它看到的永远是"一次调用"。
在 provider 外面重试，重试的是**整篇**（可能是 10 批），语义与"单批"不符；
而且失败一次要重跑前面已经成功的批次，白白放大上游压力。

**对策**

由流水线侧（`pipeline/index/writer.ts` 的 `embedChunks()`）**先按 `EMBEDDING_BATCH_SIZE` 把文本切好、
每次只喂一批**（provider 的内部循环于是只跑一轮），重试的边界才与"批"对齐。

**一批最终仍失败 ⇒ 整篇 `FAILED`**（不做"跳过这批继续"）：跳过会留下"有块没向量"的坏数据 ——
那些 chunk 在检索里**永远排不上号**（`<=>` 对 NULL 是 NULL），而界面上一切正常。
这种"看不见的缺失"比整篇失败难查得多，而整篇失败**可见且可重试**。

**验收怎么抓**：D 组把假上游 toggle 成 500，然后断言 worker 失败后 `error_msg` 含
「文本向量化失败（已重试 2 次）」**且上游被调用 ≥ 3 次**（1 次原始 + 2 次重试）
—— 只断言"失败了"是验不出"重试真的发生了"的。

## 坑 6 ⚠️ 新加的验收夹具被 P0-1-18 的内容门槛判死（自己记过的坑，还是踩了）

**现象**

`verify-ingest.mjs` 首跑：**16 条断言失败**，从 B 组到 F 组全线飘红。查库看原因：

```
解析结果内容过少（有效字符 48，不足 50 个），疑似扫描件或空白文档；…
```

—— 夹具文本只有 **48** 个有效字符，低于 `EMPTY_TEXT_THRESHOLD`（默认 50）⇒ 每篇文档都在 ④ 就被拦，
于是"chunk 有没有落库""重建有没有换内容"这些断言全部失去前提。

**根因**

**给流水线加"内容质量门槛"之后，任何"要让文档走到 READY"的夹具都必须先过门槛。**
这条正是 P0-1-18 记下的（"新增的空文本门槛把两处旧夹具判死"），这次换了个方向又撞上：
不是"旧夹具被门槛判死"，而是**新写的夹具**没算字数。

**对策**

- 夹具函数旁写明"长度必须超过 `EMPTY_TEXT_THRESHOLD`"，并用**一眼能数清**的方式造长
  （`notice()` 现在是 ~95 个有效字符：一段制度描述 + 一段交通费规则）；
- 顺带保持"控制在 512 字以内 ⇒ 恰好 1 块"，让"块正文 === 原文""近邻查询命中的就是它自己"
  这类断言仍然**逐字确定**；
- 把这条教训补进批次施工技能的收尾清单（"本批若加了新的拒绝条件，跑一遍全部既有验收档并逐条确认失败原因"）
  —— 这次之所以能快速定位，正是因为那条清单已经在用。

**踩坑的额外收益**：修好之后首跑即 22/23，唯一剩下的失败就是坑 2（`file_name`），
说明"夹具太短"这一个原因确实解释得通全部 16 条 —— 也就没有被掩盖的第二层问题。

## 其它值得记一笔的

### ① 阶段数组买到的东西兑现了：插 ⑥⑦ 时 `worker.ts` **一行未改**

P0-1-18 插入 ④⑤ 时只改了 `JOB_DOCUMENT_SELECT`（多带 KB 的分块参数，属"阶段间的数据契约"）；
本批插入 ⑥⑦ 时连它都没动 —— `chunks` / `vectors` / `embeddingName` 全在上下文里流转。
机制（并发闸、四道幂等、CAS 写状态、失败翻译）三批下来**一次未改**，而这正是风险最高的那段代码。

### ② `READY` 的语义到本批才完整，且它是**可验证**的

`READY = 可检索` 的定义落成三条可断言的等式：
`documents.chunk_count === count(*) WHERE doc_id = ?`、`chunks.embedding IS NOT NULL`（无例外）、
`vector_dims(embedding) === EMBEDDING_DIM`。三条一起才是"这篇文档能被检索到"。

### ③ "跳过"类断言必须用**删得掉证据**的方式

`content_hash` 相同时的三个"没做"（不落对象、不删 chunk、不入队），如果只断言"内容还在"，
那么"重写了一遍但结果相同"的实现照样通过。故用：

| 要证明的"没做" | 断言 |
|---------------|------|
| 没删/没重建 chunk | **chunk 行 id 逐字不变**（重写过就会换新 id） |
| 没写库 | 文档 `updated_at` 逐字不变 |
| 没落对象 | `kb/{kbId}/` 下的对象数不变 |
| 没入队 | 队列深度 0 |

### ④ 假 embedding 上游做成了可复用的夹具

`scripts/fixtures/embedding-upstream.mjs`：真 HTTP 服务 + 记录每个请求 + `setFailing(bool)` 运行期开关。
`verify:pipeline` 与 `verify:ingest` 共用它（前者是因为 P0-1-19 起 ⑥ 会真的调用 embedding，
不接上所有"走到 READY"的用例都会红）。**必须在 `await import(backend)` 之前**设好
`EMBEDDING_API_URL` —— 配置在模块加载期只读一次。

### ⑤ 本机跑验收要补 PATH（记一笔，免得下次又困惑）

`docker` 不在本机默认 PATH 里（OrbStack 装在 `~/.orbstack/bin`）⇒ `pnpm infra:up` 会报
"Docker engine 不可达"。处置：`export PATH="$HOME/.orbstack/bin:$PATH"` 再跑。

## 坑预判取证

`docs/06` P0-1-19 的坑预判原文：**"「先删后建」有检索空窗（`子方案①` §七 的刻意取舍）
→ 文档列表页必须在 PARSING 态显式提示「更新中，暂不参与检索」"**。

⚠️ **成立**，且本批把它拆成两半处理：

1. **空窗本身**（后端这半，本批已做）：`reupload` 在改行的事务里就删掉旧 chunk
   ⇒ 窗口 = 一次流水线耗时；响应里 `status` 立刻是 `PARSING`、`chunkCount` 立刻归 0、
   `updatedAt` 变化 —— **界面据此就足以显示"更新中"**，不必等任何额外接口。
   验收把这三点都断言了（"重建响应"那一条）。
2. **提示那条**（前端那半）**属 P0-1-21**，故已**写进 `docs/06` P0-1-21 的坑预判**并标注"必做"：
   列表端点必须把 `PARSING` 显示成「更新中，暂不参与检索」，且 `PARSING` 与 `FAILED`
   不能用同一个样式（前者是"我们还在干活"、后者才要人介入）。

**同时被验收排除的另一种实现**（`§七` 拒绝的"双份共存再切换"）：B 组断言
**旧 chunk 的 id 一个不剩**，并且**全库查孤儿**（`LEFT JOIN documents ... WHERE d.id IS NULL`）必须为 0
—— 双写实现会留下旧 id，先删后建漏删会留下孤儿，两条各抓一种。

## 遗留 / 下批提醒

- **P0-1-20 直接接上**：`chunks` 表已经有内容与向量，双路检索的两条 SQL 可以照着写
  （向量路 `1 - (embedding <=> $1)`、全文路 `content LIKE '%词%'` + `bigm_similarity`；
  候选池 `topK * CANDIDATE_POOL_FACTOR`；`mode` 三值分流；RRF `k=60`）。
  ⚠️ 坑预判提醒：**必测 `mode=FULLTEXT` 单独跑中文 query** —— 返回空说明 pg_bigm 索引没被用上。
- **`meta.embeddingName` 已经每行都存**：`§八` 的"换模型检测"可以在 P0-1-20 之后真正派上用场
  （筛出"哪些行是旧模型产的"）。
- **P0-1-21 必须先做列表页那条提示**（`PARSING` → 「更新中，暂不参与检索」），
  否则"重建期间搜不到"会被当成 bug；另：`PARSING` 与 `FAILED` 的样式必须分开。
- **本批仍不是可端测里程碑**：`READY` 已经真的等于"可检索"，但**检索端点本身**（P0-1-20）
  与列表/下载端点（P0-1-21）还没有 —— 手动能做的只有"查库看 `chunk_count` 与 `chunks` 行"。
- **手动端测前必须配好 embedding**：`infra/.env` 的 `EMBEDDING_*` 三项是空的，
  不配的话每篇文档都会在 ⑥ 变成 FAILED（`error_msg` 是「文本向量化失败（已重试 2 次）…」）。
  验收脚本自己起了假上游，所以脚本能跑不代表手动能跑 —— 这一条已写进 README 的手工端测 ⑩。
