## 0. 一句话结论

本批两个真 bug 都属**同一类**：**"不报错、只是内容多一点/少一点"**。

它们不是"写错了"那种一眼可见的错误，而是"看起来完全正常"的静默偏差 —— 所以本批真正的产出不只是代码，还有一条**断言纪律**：

> **这一层的断言必须落在字面量上。**
> 只断言"能解析出事件"是**弱断言** —— 下面 ①② 两个 bug 都能从那类断言底下走过去。

## 1. ⚠️ 帧的中间态跨 `push()` 丢失 ⇒ 事件名丢失、整帧被静默忽略（验收脚本抓到的真 bug ①）

### 现象

验收档 A 组一上来就红：

```
A2  ❌ payload 原文：期望 "{\"text\":\"a\"}"，实际 "\n{\"text\":\"a\"}"
C2  ❌ 切点在 13 时：期望 "delta,done"，实际 "done"
C3  ❌ 逐字节喂入：返回 []
```

C2 是**切点全扫描**（`for (let cut = 1; cut < bytes.length; cut += 1)`），只在其中一个切点失败 —— 也就是说，**这条 bug 需要 TCP 恰好在某个换行之后分段才会显形**。

### 根因

`SseFrameParser.push()` 里，"正在攒的那一帧"原本是**函数局部变量**：

```ts
push(chunk: string): RawSseFrame[] {
  let current: PartialSseFrame | undefined   // ← 局部
  ...
}
```

一帧的三行（`event:` / `data:` / 空行）落在**三次 `push`** 里时，第二次 `push` 进来时 `current` 已经是 `undefined`：

- 后到的 `data:` 行以「还没有 `event`」的状态**开了一个新帧** ⇒ 帧的事件名丢了；
- 空行到达时收口出来的那一帧，事件名是规范默认值 `message` ⇒ 前端按名字分派时**不认识它** ⇒ 整帧被当"未知事件"忽略。

**症状**：回答里偶尔少一段。少的那一段只在"TCP 恰好在换行后分段"时出现 ⇒ 复现概率极低、看着像模型随机抽风。

### 修复

把中间态提为**实例字段** `#current`（生命周期与 parser 一致，而不是与一次 `push` 一致），空行收口后清空。现由三条断言按住：A2（切两段）、**C2（切点全扫描）**、**C3（逐字节喂入）**。

### 为什么手点浏览器碰不到

要手点复现，得让 TCP 恰好把 `event:` 行和 `data:` 行分成两个包 —— 本机走 loopback 时基本不会发生。**这类 bug 只能靠"按任意切点喂字节"的自动化断言抓。**

## 2. ⚠️ 单行 `data:` 凭空多一个前导换行（验收脚本抓到的真 bug ②）

### 现象

与 ① 同一条 A2 断言（它同时按住两件事）：`frame.data` 与原始报文**逐字**比对时，每一帧都多了一个 `\n`：

```
期望 "{\"text\":\"a\"}"   实际 "\n{\"text\":\"a\"}"
```

### 根因

中间态用**空串**表示"还没有见过 `data:` 行"：

```ts
data: string = ''                                  // ← 缺席 = 空串
current.data = current.data + '\n' + value          // ← 于是首个 data: 也走拼接
```

首个 `data:` 行于是拼成了 `'' + '\n' + value` ⇒ 每帧多一个前导换行。

### 为什么这个 bug 被完全掩盖

**`JSON.parse` 容忍前导空白** —— `'\n{"text":"a"}'` 解析结果与 `'{"text":"a"}'` 一模一样。

⇒ 脚本一路绿、界面完全正常，**只有把 `frame.data` 与原始文本逐字比对才看得见**。这条直接印证了 §0 的断言纪律：如果 A 组只写 `assertEqual(parsed.kind, 'event')`，② 会活到线上。

### 修复

用 `data?: string` 明确区分两种状态，并把这个区分写进类型注释：

```ts
interface PartialSseFrame {
  event: string
  data?: string      // undefined = 还没见过 `data:` 行；'' = 见过，但值是空的
}
```

### 顺带修掉的一处"不可达分支"

`parseSseFrame` 里的 `empty` 分支原本**永远进不去** —— `{ event: 'ping', data: '' }` 会掉进 JSON 解析失败、被报成 `invalid`。加了 `if (frame.data === '') return { kind: 'empty' }` 才让它真的可达（B 组断言因此才立得住）。

### 一个必须记住的相邻陷阱

事件**名**（`event:` 行）的"缺席"与 `data` 相反：SSE 规范规定**省略时默认 `message`**。所以：

- `data` 的缺席 ⇒ 用 `undefined` 表示（**不能**用空串，否则就是本 bug）；
- `event` 的缺席 ⇒ 用**规范默认值 `message`** 补齐。

两者口径**刻意不同**，写的时候不能"为了对称"统一成一种。

## 3. ⚠️ `MessageList` 自己又包了一层 `.stream`（端测抓到的结构缺陷）

### 现象

浏览器端测时顺手量了一下 DOM：

```js
document.querySelectorAll('.stream').length   // → 2
```

`ChatPage` 已经用 `StreamFrame` 提供了滚动容器 `.stream`，而 `MessageList` 内部**又包了一层**同名的 `<div className="stream"><div className="stream__inner">`。

### 为什么危险

- `padding` 被**叠加两层**（视觉上内边距比设计大一倍，但不报错）；
- 多出一个**嵌套滚动容器** —— 在特定内容高度下会出现"内层可滚、外层不动"的诡异滚动行为；
- **没有任何报错**，typecheck / lint / 构建全绿，只有数 `.stream` 的个数才看得见。

### 修复

`MessageList` 改为返回 `<>{messages.map(...)}</>`（`<>` fragment），滚动容器**只由页面持有**。并把这条写进 `docs/03` §4.1 增量：

> `.stream` 容器**只能有一层**，`padding` 与滚动都归它。

### 教训

"组件自己包一层容器"在单测里看不出来，在静态检查里也看不出来 —— 只能靠**在真 DOM 上量结构**。这类"结构上错了但不报错"的缺陷，是浏览器端测相对验收脚本的**独占价值**。

## 4. ⚠️ 贴底跟随的判据写在 effect 里 ⇒ 永远判成"用户不在底部"（端测抓到的交互缺陷）

### 现象

流式回答在**视口外**一帧帧长出来，滚动条纹丝不动。实测数据：

```
gap（距底部距离）: 595 → 629   （一路上涨）
scrollTop:        纹丝不动
```

### 根因

第一版把"用户是否贴着底部"写在 effect 里**现算**：

```ts
useEffect(() => {
  const frame = frameRef.current
  const nearBottom = frame.scrollHeight - frame.scrollTop - frame.clientHeight < 120  // ← 错在这里
  if (nearBottom) frame.scrollTop = frame.scrollHeight
}, [messages])
```

顺序错了：**effect 跑在内容已经长高之后**。此刻量到的"距底部距离"已经被新内容撑大 ⇒ 永远 > 阈值 ⇒ 永远判成"用户不在底部"。

"用户本来在底部"这件事，在 DOM 更新之后已经**不可考**。

### 修复

判据必须在**用户滚动时**记录（内容长高不触发 `scroll` 事件，所以这个记录天然保持的是"长高之前"的值）：

```ts
const pinnedRef = useRef(true)
const handleNearBottom = useCallback((nearBottom: boolean) => {
  pinnedRef.current = nearBottom                       // ← 只在 scroll 事件里写
}, [])

useEffect(() => {
  const frame = frameRef.current
  if (frame === null) return
  if (pinnedRef.current) frame.scrollTop = frame.scrollHeight   // ← 只读，不现算
}, [messages])
```

`StreamFrame` 上挂 `onScroll` 上报（阈值 120px：程序化滚到底后距离是 0，用户手动滚到底也能落进容差）。

### 教训

**"用 DOM 的当前状态描述 DOM 变化之前的事实"是行不通的。** 凡是"用户意图"类的判据（是否贴底、是否聚焦、是否手动改过），都必须在**用户事件**里记录，effect 只读不猜。

## 5. 验收档的取证手法（可复用，建议后续前端批次照用）

### 5.1 用加载器钩子 shim `import.meta.env` —— **不为测试方便去改产品代码**

`api/client.ts` 里读了 `import.meta.env.VITE_API_BASE_URL`（Vite 的 define，node 里不存在）⇒ 直接 `node --import tsx` 跑会 `TypeError`。

诱惑很大："把那个常量抽成参数/加个默认值" —— 但那是**为了测试而改生产代码**，会把测试的便利泄漏成产品的形状。

本档的做法是**只对该文件**注册一个加载器钩子，把 `import.meta.env` 文本替换成 `({})`（等价于 Vite 的 define 结果）：

```js
register(`data:text/javascript,${encodeURIComponent(VITE_ENV_SHIM)}`, import.meta.url)
```

```js
const VITE_ENV_SHIM = `export async function load(url, context, nextLoad) {
  if (!url.endsWith('/api/client.ts')) return nextLoad(url, context)
  const loaded = await nextLoad(url, context)
  const source = loaded.source.toString().replaceAll('import.meta.env', '({})')
  return { ...loaded, source, shortCircuit: true }
}`
```

**产品代码零改动。**

### 5.2 边界要"穷举"，不能"抽样"

C 组用两种互补方式按住解码边界：

- **C2 切点全扫描**：`for (let cut = 1; cut < bytes.length; cut += 1)` —— 对一条真流量的**每一个字节位置**都切一刀；
- **C3 逐字节喂入的差分**：一次喂 1 字节，结果必须与一次喂完**逐字相同**。

这两条才是 bug ① 的杀手。抽 2~3 个切点会**恰好错过**切点 13。

### 5.3 "静默忽略"要用**同一对象引用**证明，不能只断言"看起来没变"

坑预判原文是"`ping` 误当数据渲染会让消息流出现空条目"。要证明它被静默忽略，弱断言是 `assertDeepEqual(before, after)`（两个**不同但相等**的对象也能过）。本档用 `Object.is`：

```js
assertSameRef(reduceRound(state, pingEvent), state)   // ← 必须是同一个引用 ⇒ 连重渲染都没有
```

store 层再验一次（G3）。**"返回同一个引用"是比"值相等"强得多的性质** —— 它同时证明了"没有产生新对象"，也就是"不会触发重渲染"。

### 5.4 jsonb 往返的值必须**键序无关**地比

从 `GET /messages` 取回的历史里，结构化字段（引用卡等）是**经 PG jsonb 往返**过的，而 **PG 会重排 jsonb 的键序** ⇒ 直接 `assertDeepEqual` 会出**假红**。

本档统一走 `canonical()`（递归按键名排序后序列化）再比 —— 与既有批次同一手法。

### 5.5 B 组遍历事件全集 ⇒ 将来加事件会红

B 组**遍历 `SSE_EVENT_NAMES`** 断言"每种事件都有样本"⇒ 将来 `shared/src/sse.ts` 加了事件却忘了在验收档补样本，脚本会**主动报红**（而不是悄悄少验一种）。这是把"守门"写进脚本的例子。

## 6. 环境与工具杂项

- **zsh 的 `nomatch` 让全量回归"没跑"**：`rm -f /tmp/P0-1-32-*.fail.log` 在无匹配时会让**整条命令失败**（`(eval):1: no matches found`），而它后面跟着的是回归本体 ⇒ 后台任务 1 秒就"完成"，日志里只有前端那一段。**去掉通配、只 `rm -f` 一个确定存在的文件名**再跑。
- **`pnpm db:seed` / `pnpm -r build` 撞"安全删除守卫"**：
  - `generated/prisma … doesn't look like a generated Prisma Client` ⇒ 上一次并行 `build` 的 `prisma generate` 被拦在中途，产物只剩一半。修：`rm -rf backend/generated/prisma && pnpm --filter @doubulea/backend db:generate`。
  - vite dev 起不来：`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":109,…deps"}`（vite 打印 "Re-optimizing dependencies because lockfile has changed"）⇒ 修：`rm -rf frontend/node_modules/.vite`（**不要**让 vite 自己去删）。
- **`127.0.0.1:5174` 打不通（`http=000`）**：vite 绑的是 `localhost`（IPv6）⇒ 端测地址必须写 `http://localhost:5174/`。
- **后端重启 ⇒ Cookie 失效**（会话存 Redis、启动时清）⇒ 重新登录并重抓 cookie jar；**同时要把 Provider 的 `baseUrl` 重新 PATCH 到新上游端口**（`serve-upstreams` 每次起的端口可能不同）。
- **`agent-browser screenshot` 的路径是位置参数**：`agent-browser screenshot /tmp/x.png`（写成 `--path X` 会报 `Element not found`）。
- **`agent-browser eval` 共享作用域**：同名 `const` 二次声明会 `Identifier 'f' has already been declared` ⇒ 一律用 IIFE `(()=>{…})()` 包起来。
- **`curl` 打 localhost 必带 `--noproxy '*'`**，否则本地代理环境下 `http=000`。
- **pino 彩色输出混有 ANSI 转义** ⇒ `grep` 可能匹配不到；用 `sed -n 'X,Yp'` 取行再过滤更可靠。
- **macOS `grep` 不支持 BRE 的 `\|`** 且**静默返回空**（和"没匹配"长得一样）⇒ 多模式检索一律 `grep -E`。本批在数包进度时踩过一次。

## 8. 本批**没**覆盖到的（别当全批验收）

- **`verify:chat-sse` 是无依赖档**：验的是解析 / 归约 / UI 映射的**纯逻辑**，跑不了**真 TCP 的时间轴**（心跳、互斥锁、`done` 时序、响应头禁缓冲）⇒ 那些属 `pnpm verify:chat-stream` / `verify:chatbot`。
- **React 渲染与交互**（七种卡片长什么样、思考块折叠动画）⇒ 只由浏览器端测覆盖。
- **输入区完整状态机 / 停止按钮 / 断线黄条** ⇒ **P0-1-33**。本批只做"流式中禁用发送"这条**防并发的必要最小集**（不做的话用户点两下就吃 `CONFLICT`）。
- **会话侧栏**（新建 / 切换 / 重命名 / 删除）⇒ **P0-1-34**。本批只能经 URL 进某个会话，从列表页进来永远是**新会话态**。
- **`tool_call` / `confirm` / `artifact` 三种卡片组件已就位但暂无数据源**（工具调用与产物属 P0-3，`queued` 属沙箱并发闸）⇒ 本批实测只覆盖 4 种卡片 + 错误卡。
- **打包产物**：本档与端测跑的都是**源码**，不经 vite ⇒ 体积/分包问题属 **P0-1-36**（本批实测单块已在 vite 告警线附近）。
