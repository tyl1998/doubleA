# 问题记录 — 本页自己刚跑完的一轮被显示成"另一窗口正在生成"

> 日期：2026-10-25
> 关联：`docs/06-实施计划.md` §六 施工纪律 3；`docs/03-前端设计.md` §五 的 `done` 行 / §4.1 输入区状态机、
> `docs/02-后端设计.md` §5.2（`chat.active:{id}` 锁与 `/active`）；`issue_fix/问题记录-P1-22-外部调用显示为定时任务.md`（同族）
> 定位：本文件记录"回答刚返回、界面却弹出『正在生成』"的现象、根因与修法。计划文件只留一行指针。

---

## 现象

用户在本页发一条消息，回答已经完整显示出来（`done` 已落库、消息流里就是完整正文），但紧接着：

1. 页面头部弹出一枚标签「**另一窗口正在生成**」（`ChatPage#serverRunLabel`）；
2. 消息流末尾补出一行「另一个窗口正在生成这一轮」（`AssistantMessage#serverRunStatusText`）；
3. 输入区被判成忙碌：主按钮 `正在生成…` 且禁用、`canSend:false`（`composerState` 的 `serverRunning` 分支）。

三处通常持续到下一次 `/active` 轮询回来才消失（有流在跑时 2s 一拍，全空闲 10s 一拍）。

## 根因

`serverRun`（"服务端这一刻在跑这个会话"，判据是 Redis 的 `chat.active:{id}` 锁）与 `rounds`
（"本页画得出这一轮"，判据是本页那条 SSE 事件流）是**两个来源**，而本页自己发起的那一轮会**同时**
写进两者，收尾时却只丢了一边：

| 时刻 | `rounds[id]` | `serverRun[id]` |
|------|--------------|-----------------|
| `begin`（开一轮） | 有（streaming） | 有（`chatStream.ts#begin` 一并写入 + `runOrigins='UI'`） |
| `done` 到手 + 让位 effect `reset` | **无** | **仍在** ⇒ 空窗 |

- `begin` 写 `serverRun[id]` 是**对的**（2026-10-21 用户报过"切走再切回，A 变成可继续"），但那些行的
  注释写着"它的收口与清除统一走 `noteServerRun(false)`，见 `useChatStream` 的 `finally`" ——
  **那个调用从来不存在**（全仓只有 `ChatPage.tsx` 与 `useConversationActiveWatch.ts` 会写 `noteServerRun`）。
  注释与实现已漂移，于是本页这一轮只能等 `/active` 轮询来收。
- `done` 一到手，`ChatPage` 的让位 effect 立刻 `reset(conversationId)`（历史已重取到位，流式版本必须丢，
  否则同一条消息渲染两遍）⇒ `round === null && serverRun[id] !== undefined` 必然成立
  （`ChatPage.tsx#serverRunning`）⇒ 三处"正在生成"文案同时亮起。
- 文案把它说成「另一窗口」是**第二层错**：`UI` 取值域的含义是"平台界面"，**包含本窗口**
  （`shared/src/conversation.ts#CONVERSATION_RUN_ORIGINS`）。这与 P1-22 修的"外部调用被说成定时任务"
  是同一类错：来源粒度不足以区分"我这一轮"与"别的界面那一轮"。

结论：**锁的结论没错（那一刻确实还持着），错在本页没在收口时按归属收掉自己那一格**，
于是把"我自己刚跑完"渲染成了"别人还在跑"。

## 修法（本页自己那一轮，由本页自己收）

1. **store 新增 `releaseOwnRun(conversationId)`**（`stores/chatStream.ts`）：本页自己发起的那一轮**收到
   终帧后**调用，收掉 `serverRun` / `runOrigins` 两格。判据用 `runOrigins === 'UI'`
   （**不是**比 `startedAt`）：`begin` 写的是**客户端**时刻，而 `/active` 轮询会把同一格覆写成
   **服务端**时刻（`streamChatReply` 自己的 `startedAt`）⇒ 比等永远不相等、会静默失效。
2. **调用点**：`useChatStream#performStream` 的 `finally`，且**只在 `terminated`（收到 `done`/`error`）时**调。
   - 收到终帧 ⇒ 这一轮在服务端已经收尾（`orchestrator/sse.ts` 的 `finally` 就在 `done` 之后释放锁），
     本地清不必再等下一次轮询；
   - 没收到终帧（断线 / 用户 abort）⇒ **不清**：那把锁还在不在只有 `/active` 知道，本页不许猜
     （与"没落库就不说落库"同一纪律）。
3. **按归属，不是无条件删**：`releaseOwnRun` 在 `runOrigins` 不是 `'UI'` 时**空转**。否则"我刚跑完"
   会把**外部调用 / 定时任务**那一轮的灯一起灭掉 —— 同一条纪律见后端 `releaseConversationLock`
   的"按归属释放"。
4. **顺手修一处同族孤儿键**：`stoppedLocally` 原先只清 `serverRun`、留下 `runOrigins`，与它自己的
   注释（"两处一起清"）矛盾；已改成两格一起清，且空转时返回同一 `state` 引用（零重渲染）。
5. **文案不动**：合法场景仍在（窗口 B 看窗口 A 发起的轮次，`UI` 说"另一窗口"是对的）⇒
   修因不修文，不去把 `UI` 的中性措辞改成"本窗口"。

## 已知边界（写在 `useChatStream#performStream` 的注释里）

终帧写出去与锁释放是同一个 handler 里紧邻的两步，客户端可能在锁真正删掉前几毫秒就清了本地这一格 ——
这期间的发送由后端的 `CONFLICT` 兜底，窗口与引入前同量级。
