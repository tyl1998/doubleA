## 坑 1 ⚠️ `crypto.randomUUID({ version: 7 })` 静默返回 v4（本批唯一的真 bug，且**不报错**）

**现象**

上传接口 10 条用例全 500。日志里的错误是断言侧的（`docId[14] !== '7'`），服务端本身**没有任何异常**：

```
[FAIL] 上传 md：200 + status=PARSING ...
       期望 200，实际 500
```

**定位过程**

写验收脚本时顺手加了一条"docId 必须是 uuid7"的断言（`02` §3.1 定案：全库主键一律 `uuid(7)`）。
如果没有这条断言，这个 bug 会**一路溜到线上** —— 因为：

**根因**

```bash
$ node -e "const {randomUUID}=require('node:crypto'); const v=randomUUID({version:7}); console.log(v, v[14])"
9470d1f2-d92d-4bb0-b0e3-6de8464c5653 4      # ← 期望 7
```

- Node **22.22.2** 的 `crypto.randomUUID` **不认识 `version` 选项**，传了就**当作没传**，返回 v4。
- 它**不抛错、不警告**，返回值是一个**形态完全合法**的 UUID（正则、长度、段数全对）。
- 真正让这个 bug "看起来能写"的是**类型缺口**：`@types/node@22.20.4` 的 `RandomUUIDOptions`
  里**没有 `version` 字段**，当初是靠一个 `as` 强转绕过去的 —— 类型系统在此处**恰好替运行时说了谎**。
  也就是说：`tsc` 报错 → 加 `as` → 编译通过 → 运行时静默降级，三步都不像有问题。

**对策**

**彻底放弃手搓 uuid7**（不换 `uuid` 包、不自己拼 v7 时间戳）：

- `documents.create` **不带 `id`** —— `schema.prisma` 的 `@default(uuid(7))` 才是唯一事实来源
  （它是 Prisma **客户端**赋的值，P0-1-14 已定案，见 `issue_fix/问题记录-P0-1-14` 的"函数型默认值不在 DB 层"）。
- S3 键中段改用**普通 `randomUUID()`**（v4）：那一段**与 docId 无关**，
  本就不需要是 uuid7 —— 当初想让它也是 v7 只是"顺手"，而顺手正是坑的来源。
  现形态：`kb/{kbId}/{randomUUID()}/source.{ext}`。

**留痕**：`document.service.ts` 的文件头把这段原样写下来了，避免下一个人（或下一批）再"顺手"一次。

## 坑 2 ⚠️ 「改名绕过」只能靠**文件头**拦下，MIME 交叉校验抓不到

**现象**

按 `子方案①` §4-1 的字面实现（扩展名白名单 + `.doc` 专拦 + MIME × 扩展名交叉校验 + 大小），
把 `a.txt` 改名成 `a.pdf` 上传 —— **一路绿灯入库**。

**根因**

MIME 是**客户端声明**。改名之后浏览器（和 curl）会老老实实声明 `application/pdf`：

```
扩展名 = pdf          ← 白名单通过
声明 MIME = application/pdf   ← 与扩展名一致，交叉校验通过
内容 = "这是一个纯文本文件"      ← 没人看
```

第三道校验的**前提**是"客户端会诚实声明"，而改名恰恰打破了这个前提。
换句话说：这一道能抓"用户选错文件"，**抓不到"用户（或攻击者）改了名字"**。

**对策**

在四道之外补第四道：**读文件头字节**（`HEAD_PROBE_BYTES = 4096`），命中签名即比对扩展名：

| 内容 | 签名 | 允许的扩展名 |
|------|------|--------------|
| PDF | `%PDF-` | `pdf` |
| ZIP（docx/xlsx/pptx 同族） | `PK\x03\x04` / `PK\x05\x06` / `PK\x07\x08` | `docx`（**还要再过一道**，见下） |
| 旧版 Word（OLE2 复合文档） | `D0 CF 11 E0 A1 B1 1A E1` | 无（提示另存为 `.docx`） |
| RTF | `{\rtf` | 无 |
| 图片 | `\x89PNG` / `\xFF\xD8\xFF` / `GIF8` / `BM`+保留位 / `RIFF`+`WEBP` | 无 |
| 文本 | （无签名） | `md` / `txt`，且**不得含 NUL** |

两个**容易漏**的子分支（都是写完第一版才发现的）：

1. **任意 zip 改名成 `.docx` 能过 ZIP 签名** —— OOXML 就是 ZIP，所以 `PK\x03\x04` 通过之后
   必须再看**包内是否含 `[Content_Types].xml`**（`looksLikeOoxml()`）。否则 xlsx/pptx 甚至普通
   压缩包都能混进 docx 解析器。
2. **BMP 只认 `BM` 会把文本误判成图片** —— `"BMW 2026 年度报告"` 以 `BM` 开头，会被判成"图片型
   文档"并给出误导文案。补验 BMP 头第 6~9 字节的保留字段恒为 0（真实 BMP 必为 0），误判率压到可忽略。

**为什么不做"内容嗅探/纯文本启发式"**：判定的目标是"用户能不能自己解决"，不是"内容分类"。
上表的失败模式是**明确的**（内容不符），且文案能直接指向动作："请确认文件没有被改名，或改用
正确的文件格式"。

## 坑 3 编码嗅探：必须做，但**不需要 iconv**；前提是 `fatal: true`

**`06` 的原坑预判**：`TXT 编码嗅探 —— GBK 文件用 UTF-8 解出乱码但不报错，必须显式嗅探 + iconv 兜底`

**实测订正**：

- 「必须显式嗅探」**成立**，而且是本批点名的验收项（`[PASS] ⚠️ TXT(GBK)：编码嗅探出 gbk 且中文不乱码`）。
- 「iconv 兜底」**不必要**：Node 自带 ICU 就支持 `new TextDecoder('gbk')`，**零新增依赖**。
- **真正的关键**在另一个地方：严格 UTF-8 判定必须带 `fatal: true`。

```js
// ❌ 不带 fatal：GBK 字节被**静默**解成 U+FFFD，不抛错 ⇒ "嗅探"永远嗅不出东西
new TextDecoder('utf-8').decode(gbkBytes)          // '����'  （不抛错！）

// ✅ 带 fatal：解不了就抛，嗅探才有真假之分
new TextDecoder('utf-8', { fatal: true }).decode(gbkBytes)   // throws TypeError
```

**最终口径**（`pipeline/parse/txt.ts#decodeTextBuffer`）：BOM（UTF-8/UTF-16）→ 严格 UTF-8 →
GBK。失败兜底时给**可读的**报错，而不是返回一堆替换字符。

## 坑 5 `unpdf` 没有 `destroy()`，只有 `cleanup()`

**现象**：按 pdfjs 的习惯写 `pdf.destroy()` → 运行时报 not a function。

**对策**：真正的释放点是 **`pdf.loadingTask.destroy()`**，放在 `finally` 里。
另两条踩到的细节：

- `extractText(pdf, { mergePages: false })` 才拿得到**逐页**数组（`mergePages` 默认 `true`
  会把整篇拼成一坨，页码就无从谈起）。
- **空白页给 0 个 block，但 `pageCount` 照记**：否则下游（P0-1-18 的空文本检测）分不清
  "扫描件"和"空文件"—— 两者的失败原因文案完全不同。

## 坑 6 ⚠️ 手写的类型声明被 `.gitignore` 静默吞掉（**提交前才发现的第二个真问题**）

**现象**

`tsc` 全绿、`pnpm -r typecheck` 全绿、`pnpm -r build` 全绿 —— 但 `git status` 里**找不到**
`backend/src/types/mammoth.d.ts`。它不是"没创建"，而是被忽略了：

```
$ git check-ignore -v backend/src/types/mammoth.d.ts
.gitignore:19:**/src/**/*.d.ts    backend/src/types/mammoth.d.ts
```

**根因**

`.gitignore` 第 17~20 行有一组**编译残留防护**（P0-1-1 踩过：tsc 因 `rootDir`/`outDir` 配错把
`.js`/`.d.ts` 写回源码目录）：

```
**/src/**/*.js
**/src/**/*.js.map
**/src/**/*.d.ts        ← 这一条把手写的 mammoth.d.ts 一起吃了
**/src/**/*.d.ts.map
!**/src/**/*.d.mts      ← 已有的一个例外（.d.mts 用 negate 放行）
```

这类规则的失败方式是**最坏的一种**：本机全绿（文件确实在磁盘上），只有 **CI / 新克隆的仓库**才会
在 `pnpm -r typecheck` 时炸 `TS7016: Could not find a declaration file for module 'mammoth'` ——
而 CI 是最后一道关，反馈最晚。

**对策**

按既有惯例加一条 negate，并顺手把"这个目录是手写的"写成约定（否则下一个人会往这里扔 tsc 产物）：

```gitignore
# 例外：**手写的环境声明**（不是 tsc 产物）。约定 `backend/src/types/` 只放手写声明 ——
# 目前只有 `mammoth.d.ts`（该包既不带类型、也没有 `@types/mammoth`，P0-1-16）。
# ⚠️ 若哪天 tsc 真把产物写进这个目录，说明 `rootDir`/`outDir` 配错了，**别用 gitignore 掩盖**。
!backend/src/types/**/*.d.ts
```

**为什么不用"把声明文件挪到 `src` 外面"**：`tsconfig.json` 的 `include` 是 `src/**/*`，
挪出去要额外配 `typeRoots`/`include`，而 negate 只动一行、语义也更直白。

**可复用的检查**：**新增任何非 `.ts` 的源文件（`.d.ts` / `.json` / fixture）后，`git status` 必须看得见它。**
一条命令：`git check-ignore -v <path>`（打印命中的规则；命中 negate 即未被忽略）。

## 其它值得记一笔的

### ① 上传**刻意不做同步解析**

上传 = 前置校验 → 落 S3 → 建 `PARSING` 行。**响应里 `status` 恒为 `PARSING`**。
理由：同步解析会让 P0-1-17 退化成"把已经做完的事再异步做一遍"，而且队列/幂等/重试
会在两处各有一套入口。

**副作用（要主动告诉用户）**：本批**不是可端测里程碑** —— 传完没有下游消费，
也没有列表端点能看进度（P0-1-21）。所以"四格式各传 1 篇均能解析出文本 + meta"这条验收
在 `verify:documents` 的 **C 组**用**模块级真跑夹具**来验，而不是"上传后等 READY"。

### ② 「两道 bodyLimit」不要混成一个

- 全局 JSON `bodyLimit` 收回 **1MB**（`JSON_BODY_LIMIT_BYTES`）—— 原先是 `UPLOAD_BODY_LIMIT`，
  那会让**每个** JSON 接口都能收 100MB。
- 上传的 `UPLOAD_BODY_LIMIT` **只挂在**上传路由上（route-level `bodyLimit`）。
- 插件侧 `limits.fileSize`（管文件字段）与路由 `bodyLimit`（管整个请求体）**两道都要**。

### ③ multipart 的错误码要显式登记

`@fastify/multipart` 用 `fastify-plugin` 包裹 ⇒ 装饰器落在**根实例**上。它抛的是
Fastify 世界的错误码（`FST_REQ_FILE_TOO_LARGE` 等），`errorHandler` 对框架错误
**优先用 `statusCode`**（P0-1-4 定案），所以 413 不会被压成 400 —— 这一点在验收里
有一条专门的断言盯着（`[PASS] 超过 UPLOAD_BODY_LIMIT（注入 8KB，传 20KB）→ 413，状态码不被压成 400`）。

### ④ 判重是「按库」的，且 DB 写失败要补偿删 S3

- `content_hash`（sha256 十六进制）判重**限定在同一个 kb 内**；跨库同内容**不**判重
  （两条各有一个断言）。命中即返回已有那条 + `deduplicated: true`，**不新建行**。
- 顺序是 **S3 先写、DB 后写**，所以 DB 失败（FK 失败 / 库被并发删掉）时**必须补偿
  `removeQuietly`**，否则留下孤儿对象。
- `ensureBucket` 在写入前兜底建桶（P0-1-4 的 `s3.ts` 只做探活，没有建桶能力）。

### ⑤ 验收脚本的"注入小值"手法

`UPLOAD_BODY_LIMIT=8KB` 是**脚本内先写 `process.env` 再动态 `import`** 得到的 ——
因为配置在模块加载期只读一次（P0-1-13 的 D 组用过同样的手法，那次还特意用了子进程）。
取 8KB 而不是 1KB：**docx 夹具本身约 2.9KB**，上限必须高于所有正常夹具，否则正常用例会先红。
