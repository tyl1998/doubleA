## 坑 1 ⚠️⚠️ `#waitDrain()` 永久挂住 ⇒ 活跃流锁不释放（本批最严重）

**现象**：浏览器里关掉标签页之后，**同一个会话在 30s 内一直报 `CONFLICT`**，
像是"锁泄漏"。日志里还有一行很扎眼的 Node 警告：

```text
(node:xxxxx) MaxListenersExceededWarning: Possible EventEmitter memory leak detected.
11 close listeners added to [Socket]. Use emitter.setMaxListeners() to increase limit
```

**根因**：背压等待写成了"等两个**将来**事件里先到的那个"：

```ts
// ❌ 错的写法
await new Promise<void>((done) => {
  this.#raw.once('drain', done)
  this.#raw.once('close', done)   // ← 客户端**已经断开**时，close 早就发生过了
})
```

`once` 注册的是**将来**的事件。客户端断开时 `close` **已经触发完毕**，
再 `once('close')` 永远等不到 ⇒ 这个 `await` **永久挂住** ⇒ `streamChatReply` 的收尾回不来
⇒ `finally` 走不到 ⇒ **锁一直不释放，直到 3 个心跳周期的 TTL**。
而每次心跳又往同一个 socket 上再挂一个**永不触发**的 `close` 监听器 —— 于是有了那行
`11 close listeners`（心跳数一多就不断累加）。

**为什么极具欺骗性**：症状（"关掉页面后一直 CONFLICT"）**看起来**像锁没被释放，
排查方向会指向 `releaseConversationLock` / 键 TTL / 归属判断 —— 而真正卡住的是
**收尾根本没执行到**。`MaxListenersExceededWarning` 是唯一指向正确方向的线索。

**为什么只有真 HTTP 抓得到**：`app.inject()` 不会真的建立/断开 socket，
`reply.raw` 是一个 mock ⇒ **这条路径在 inject 下根本不进入**。

**对策**：把"事件已经过去了"变成**同步可见的判据**，并把"没人读了"这条路顺手封掉：

```ts
// ✅ 先问"现在是不是已经不能写了"，再谈等 drain
#waitDrain(): Promise<void> {
  if (this.#raw.destroyed || this.#raw.writableEnded) return Promise.resolve()   // ← 同步可见
  return new Promise((resolve) => { const done = () => { off('drain', done); off('close', done); resolve() }; … })
}

// ✅ 客户端走了 ⇒ 后续 emit 不必再试写一个已销毁的 socket
abort(reason) { if (reason === 'client') this.#closed = true; … }
emit(…) { if (this.#closed || this.#raw.destroyed) return; … }
```

**原始输出**（D 组）：

```text
── D 断线释放锁（`02` §5.2：断线重连先查 `/active`；这里验"断开即解锁"这一半） ──
  [PASS] 客户端断开（abort fetch）→ 3s 内锁被释放（不必等 TTL）
  [PASS] 断线之后**马上**能重新发消息（拿到锁 → 200 + 心跳）
```

> 📌 **排查手法留档**：为了确认"不是 Fastify 的锅"，我写了两个最小探针脚本 ——
> `/tmp/probe-sse-close.mjs`（裸 Node `http`）与 `/tmp/probe-sse-fastify.mjs`（Fastify + hijack），
> 都打印了 `close` 触发的时机。两个都**正常触发** ⇒ 排除框架，把问题锁在**我们自己的时序**上。
> 这类"先证伪嫌疑对象"的探针比反复读代码快得多。

## 坑 2 ⚠️ `lock-lost` 不能靠 producer 的返回值判断：**正常返回 ≠ 正常结束**

**现象**：锁在生成过程中被外部清掉（进程被杀、运维误删、TTL 到）时，验收收到的是
`done{finishReason:STOPPED}` —— 前端会把它渲染成"**你点了停止**"。

**根因**：`producer` 是"等 abort"的占位实现，锁丢了它**压根没察觉**，返回得**干干净净**。
出口层按"producer 正常返回 ⇒ 发 `done`"这条直觉写，就把"服务端状态异常、零产出"
**伪装成了用户主动停止**（`01` 决策 15 的反面：用户什么都没做，界面却说他停了）。

**对策**：**出口层是唯一的收口决策点** —— producer 返回后**再看一眼 `stopReason`**：

```ts
await producer({ channel, signal })
if (channel.stopReason === 'lock-lost') throw new ChatStoppedError('lock-lost', LOCK_LOST_MESSAGE)
```

一句话：**producer 只负责"生产"，"这一轮算怎么结束"由出口层说了算**。

**原始输出**（E 组）：

```text
── E 锁被清掉时**必须用 error 收口**（而不是假装"已停止"） ──
  [PASS] 锁被人清掉 → 2~3s 内收到 `error`（INTERNAL），而不是 `done{STOPPED}`
  [PASS] 清理回收：`releaseConversationLock` 对"已经没有的键"是安全的（下一次开流不受影响）
```

## 坑 3 ⚠️ 停止键的生命周期：**清键的位置是正确性的一部分**

**现象**：点了 `/stop` 之后流正常结束了，但**紧接着新开的那条流被"秒停"** ——
进来的第一件事就是读到上一轮残留的停止信号。

**根因**：`chat.stop:{id}` 只在"新流启动时清"没有用 —— **收尾不清**，
键就要靠 TTL（60s）自己过期，而这 60s 内的任何一次新发送都会被误停。

**对策**：清键做成**三道**，其中"收尾时清"必须是**释放锁之前**：

| 时机 | 挡的是什么 |
|------|-----------|
| 新流启动时清 | **第二道防线**：进程被杀、键来不及清的那种残留 |
| 通道轮询时消费 | 正常路径（读到即删） |
| **收尾时清**（`finally`，**在 `releaseConversationLock` 之前**） | 停止信号与流结束几乎同时到达的那种竞态 |

⚠️ **顺序的理由**：收尾那一刻**锁还在我们手上** ⇒ 这个会话**不可能**有别的流在跑
⇒ 那个键**只可能是写给我们的**；挪到释放锁之后，就可能和新流的 `/stop` **抢键**
（把新流刚拿到的停止信号删掉，症状是"点了停止但停不下来"）。
这与 P0-1-23「**校验必须排在删除之前**」是同一类事：**顺序即正确性**。

**原始输出**（C 组）：

```text
── C 停止（`02` §5.2：`chat.stop:{id}` TTL 60s，编排循环在可中断点检查） ──
  [PASS] `POST /:id/stop` → `{signaled:true}`（真的有流收到了信号）
  [PASS] 5s 内收到 `done{finishReason:STOPPED}`，且它**是最后一个事件**
  [PASS] 停止之后：`/active` 回到 `streaming:false`，两个 Redis 键都不残留
  [PASS] 再停一次 → `{signaled:false}`（流已经结束，幂等）
  [PASS] 停止信号不残留：紧接着新开一条流，它**不会被上一轮的停止键秒停**
```

## 坑 4 ⚠️ CONFLICT 是**流内 `error` 事件**，不是 409 信封（契约错配，实现时先写错）

**现象**：初版按"**没 hijack 就走信封**"这条自洽的规则，把并发冲突写成了
`409 CONFLICT` JSON 信封 —— 代码读起来毫无问题。回写文档时发现**四处**都写的是流内事件：

| 出处 | 原文 |
|------|------|
| `docs/02` §4.5 / §5.2 | 同会话重复发送 → 流内 `error{code:CONFLICT}` |
| `docs/03` §五 | 前端按**单一渲染路径**处理：错误 toast + **消息流内错误卡** + 释放输入区 |
| `docs/06` P0-1-26 验收原文 | "同会话并发发送第二次得 `error{code:CONFLICT}`" |

其中 `03` §五 还**给它配了具体 UI**（消息流内错误卡）—— 信封形态的响应根本走不到那条渲染路径。

**根因**：判断"该走信封还是事件"时用了**错误的判据**。
直觉的判据是"**能不能在写帧之前判定**"（能 ⇒ 信封），但这个判据与本批架构无关：
`/chat` 的 handler 里**所有**闸门都在写帧之前。真正的判据是**主语**：

| 主语 | 例子 | 出口 | 理由 |
|------|------|------|------|
| "**这个请求 / 目标**" | 401 未登录、400 非法 body、404 会话不是我的、只读 409、424 没配 Key、模型停用 409 | **JSON 信封** | 换**任何**客户端都该在发起前被拦下 ⇒ 与"这一轮生成"无关 |
| "**这一轮生成**" | 同会话已有流 → `CONFLICT` | **流内 `error` 事件** | 客户端**已经发起了对话** ⇒ 前端在对话区按单一渲染路径收口 |

**对策**：加一个专门的 "只写一帧然后结束" 的出口，并把这个分界线写进
`shared/src/sse.ts` 与 `routes/conversations.ts` 的文件头（**契约的注释与实现必须同源**）：

```ts
/** 并发冲突的出口：HTTP 200 + text/event-stream，**只写一帧 `error` 事件**然后结束 */
async function writeSseErrorReply(reply: FastifyReply, payload: SseErrorPayload): Promise<void> {
  reply.hijack()
  reply.raw.writeHead(200, SSE_RESPONSE_HEADERS)
  reply.raw.flushHeaders()
  reply.raw.write(serializeSseFrame({ name: 'error', data: payload }))
  reply.raw.end()
}
```

**原始输出**（B 组）：

```text
── B 会话互斥（`02` §5.2：持锁期间同一会话再次发送 → 流内 `error{code:CONFLICT}`） ──
  [PASS] 同会话并发发送 → `error{code:CONFLICT}` 事件（`02` §5.2 的会话互斥）
  [PASS] 被拒之后**第一条流仍在跑**（锁没被误释放）+ 仍有心跳
  [PASS] 会话是"仅本人"：他人打同一个会话的 chat / stop 都 404（不是 403）
  [PASS] `/stop` 是幂等的：**当前没有流的会话** → 200 + `signaled:false`（不是 4xx）
```

**⚠️ 与 F 组的一条呼应**：只读会话（Agent 被软删 → `FINISHED`）打 `/chat` 得的是
**409 信封**（主语是"这个会话"），而**并发冲突得的是事件**（主语是"这一轮生成"）。
两者状态码相近、出口完全不同 —— 这正是"分界线是主语"的意义。
`verify-agent-package.mjs` 的 R4 因此**额外断言它"不是 event-stream"**。

## 坑 5 测试脚本自身的三个伤（**这一批的假绿最贵**）

### 5.1 `waitUntil` 漏 `await` —— 一条**假绿**的断言，掩盖了坑 1

```js
// ❌ 谓词是 async 时，Promise 对象恒为 truthy ⇒ 等待立即"通过"
async function waitUntil(predicate, …) { if (predicate()) return true; … }
```

所有 `/active` 轮询都是 async 谓词 ⇒ **每一次等待都瞬间返回 true**。
于是"等锁被释放"这条断言**从来没有真的等过** —— 它在坑 1 存在时也全绿。
修法是 `if (await predicate())`。

⚠️ **教训**：这类 bug 的形态是"**测试脚手架比被测代码更容易错，而且错了是假绿**"。
它和 P0-1-25 的坑 5（`JSON.stringify` 键序假红）是同一族的两个方向 ——
**假红浪费一轮排查，假绿会让你把 bug 交出去**。

### 5.2 逐帧列表用 `assertSameSet` ⇒ 抛错后**级联 409**

```js
assertSameSet(frames.map((f) => f.event), ['ping'], …)
// 实际拿到 ['ping','ping','ping'] ≠ ['ping'] ⇒ 抛错 ⇒ 下一行 reopened.abort() 不执行
// ⇒ 那条流继续占着锁 ⇒ 后面所有用例连锁 409
```

**对策**：新增 `assertOnlyEvents(frames, expected, label)`（**去重后**再比），
并把"开流"的用例统一收进 `waitIdle()`（显式等 `/active` 的 `streaming:false`）+ `try/finally` 兜底 `abort()`。
**一条断言失败不该让后续用例一起红** —— 那不是"发现了更多 bug"，那是**噪音**。

### 5.3 模板字符串里嵌反引号 ⇒ `SyntaxError`

结论行的模板串里写了 `` （`orchestrator/index.ts`） `` ⇒ 反引号嵌套直接把脚本**在解析期**打死，
报错位置还在长串的尾部。与 P0-1-25 坑 6「长结论串不要用 `+` 续行」同源：
**`verify:*` 脚本没有类型检查，改它等于在没有安全网的地方动刀**。

## 取证手法留档：`flushHeaders()` 必须"可测量"，不能只"看得见"

`docs/02` §五 只说"响应头要禁缓冲"。但如果**不显式调 `flushHeaders()`**，
客户端的 `fetch` 要等到**第一次 `write()`** 才 resolve —— 本批默认 20s 后的第一个心跳
⇒ 症状是"**前端以为请求没发出去**"（用户看到的是转圈，而不是"在生成"）。

只断言"首帧比请求晚 > 400ms"是**证明不了**头早到的（头也可能是跟着首帧一起到的）。
验收把它做成**两条合起来**：

```text
[PASS] 响应头**立刻**到达（而不是等到第一帧）—— 这是在钉 `flushHeaders()`
[PASS] 心跳**按间隔**到达（1s 一次；太勤或太慢都算错）
```

具体测法：记录 `requestedAt`，拿到响应头时打 `headersAt`，收到首帧时打 `firstFrameAt`：

- `headersAt - requestedAt < 600ms` ⇒ 头是**立刻**冲出去的；
- `firstFrameAt - headersAt > 400ms` ⇒ 首帧**确实晚于**头（两者是分开的两次 flush）。
