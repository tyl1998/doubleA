## 坑 1 — 「不泄露账号是否存在」必须用**耗时**取证，不能只看文案

**背景**：`01` §3.1 的验收要点原文是「错误提示明确；连续失败限速」，而 `06` P0-1-7 的验收写的是
「错误密码提示明确且**不泄露账号是否存在**」。把文案对齐是直觉动作：

```ts
if (user === null || !passwordOk) throw AppError.unauthorized('用户名或密码错误')
```

**问题**：这段代码在"账号不存在"时**根本没跑 bcrypt**，直接返回。于是：

| 场景 | 是否跑 bcrypt | 实测耗时 |
|------|---------------|----------|
| 账号存在、密码错 | 是（cost 12） | **235ms** |
| 账号不存在 | 否 | **0ms** |

调用方只要量一下响应时间，就能把一个用户名"是不是真账号"筛出来 —— **文案一模一样，但这条验收条款已经被违反了**，
而且从代码上看不出任何毛病。

**对策**：

```ts
// 账号不存在时喂一个结构合法的常量摘要：同样跑满一次 cost 12，两条路径耗时一致
const passwordOk = await verifyPassword(input.password, user?.passwordHash ?? DUMMY_PASSWORD_HASH)
```

`DUMMY_PASSWORD_HASH` 是 P0-1-6 就备下的（当时记录过"bcrypt 对非法摘要 compare 立刻返回 false"那个坑），
本批正式用上。**验收加两条断言**：

1. 两条路径的**中位数都 > 100ms**（证明真的跑了 bcrypt，而不是走了短路分支）；
2. 两者中位数**差 < 150ms**（阈值放宽到 150ms 是因为机器抖动/连接首建都有几十毫秒噪声）。

实测输出：`中位数耗时：账号存在 235ms / 不存在 236ms`。

> **可复用的教训**：「不泄露是否存在」这类条款，**必须有一条"看时间"的断言**。
> 只断言 `msg` 与 `code` 的验收是"假通过"——它保证的只是文案，不是信息量。

## 坑 2 — 停用账号的报错时机：在**密码正确之后**才说"已停用"

**两难**：

- 一律不报（哪怕是密码对的用户）→ 被停用的同事以为是自己密码记错，反复重试，把失败计数刷满被锁，
  然后来问"我密码明明是对的为什么登不进去"。
- 一律报 → 拿一个用户名 + 任意密码就能试出"这个账号存在且被停用"，等于把坑 1 的成果抵消掉。

**对策**：把状态检查放在**密码校验成功之后**。

```ts
const passwordOk = await verifyPassword(...)
if (user === null || !passwordOk) { /* 累加计数 + 通用文案「用户名或密码错误」 */ }
await clearLoginFailures(username)          // 凭据正确 → 清计数
if (user.status !== UserStatus.ACTIVE) throw AppError.unauthorized('账号已停用，请联系管理员')
```

两条断言分别在"密码错"与"密码对"下各验一次：
`停用账号：密码错时仍只得到通用文案` / `停用账号：密码对时明确告知已停用`。

## 坑 3 — 限速：三个顺序细节，写错就变成"锁不住"或"自伤"

`02` §十 只写了一句「同账号 5 次失败锁 10 分钟（Redis 计数）」。落到代码里有三处必须想清楚：

**① 锁定判定必须在密码校验之前。** 否则锁定期内**正确密码**仍会登进去，"锁定"就没意义了。
→ 断言：`锁定期间正确密码也被拒（429）`。

**② 锁定之后不能再续期 TTL。** 第一直觉是"每次失败都 `EXPIRE 600`"，但那样：
攻击者（或就是本人）每几十秒试一次，锁就永远不到期 —— 顺带把账号永久锁死，成了自伤式 DoS。
→ 实现：只在**未达上限**时 `EXPIRE`；达上限后不再碰 TTL。

```ts
const failures = await redis.incr(key)
if (failures <= LOGIN_MAX_FAILURES) await redis.expire(key, LOGIN_LOCK_TTL_SEC)
```
→ 断言：`锁的剩余时间不应被新尝试延长：600s → 600s`。

**③ 登录成功即 `DEL` 计数键**（本批的坑预判）。不清的话"错 4 次 → 成功 → 再错 1 次"就会被锁，
与用户直觉不符。→ 断言设计得很讲究：错 4 次 → 成功 → **再错 5 次都必须是 401**（第 6 次才 429）。
若没清计数，第 2 次就会 429 —— 这条断言能精确区分两种实现。

**另外两个刻意的选择**：

- **计数键按用户名（归一化后）而不是 userId**：不存在的用户名也会累加，
  避免"同一个用户名试几次看会不会被锁"反推出账号是否存在（与坑 1 同源）。
- **第 6 次才锁**（不是第 5 次）：`01` §五 门槛 5 的口径是「连续 5 次错误 → 第 6 次返回已锁定」，
  所以第 5 次仍是普通的 401。`verify:auth` 逐次断言了这 6 次的差别。

**429 而不是 401**：这不是"凭据不对"，而是"现在不允许再试"；响应带 `data.retryAfterSec` 供前端倒计时。

## 坑 4 — 首登闸门：挂根级 `preHandler`、白名单逐条写、不依附 `requireAuth`

`02` §4.1 的注记是「`must_change_password=true` 时除 `/auth/{password,me,logout}` 全 403」。
三个实现选择都值得记下来：

**① 挂根级 `preHandler`，而不是逐个业务路由挂。** 作用对象是"所有业务路由，包括将来才写的那些"。
逐个去挂**迟早会漏一个**，而漏掉的那个恰好就是缺口 —— 这类缺陷不会报错，只会让人以为"已经拦住了"。
→ 断言：一个**不挂任何鉴权钩子**的公共 `/api/**` 路由，首登用户访问同样 403。
这条断言是"闸门在根上"的取证：如果闸门挂在 requireAuth 里或挂在那条路由上，这条就会是 200。

**② 白名单逐条显式列出，不用 `/api/auth/**` 前缀匹配。** 前缀匹配的语义是"认证端点全部放行"，
将来新增认证端点（如 P1 的 SSO 回调）会**默认放行**；逐条列出则是"新增端点默认拦住"。
安全默认值应该是后者。

**③ 无 Cookie / 会话无效 / 账号停用时，闸门直接放行**，把结论留给 `requireAuth`。
两处都处理会让错误原因含糊（403 还是 401 取决于钩子顺序），而且**无 Cookie 时闸门若不早退，
匿名请求也会去查 Redis** —— CI 里没有 Redis，那条断言就会从 200 变 500。
→ `verify:app` 里的断言 `/api/** 的公共路由在无 Cookie 时仍是 200` 就是"匿名请求不碰会话存储"的取证，
且**在有/无依赖两种模式下都成立**。

## 坑 5 — 改密后必须主动失效快照缓存（否则"改密没生效"）

P0-1-6 已经立了规矩：**写侧必须调 `invalidateUserSnapshot`**。本批是它的第一个真实调用方。

不调的后果很具体：首登用户改完密码后，`auth-user:{userId}` 里还留着 `mustChangePassword: true`，
**闸门会继续 403，最长 60s**。用户视角就是"我明明改成功了，还是进不去"。
→ 验收里有一条专门的断言：改密成功 → **紧接着**（同一秒内）访问业务接口 → 必须是 200。

> 顺带确认了"改密不吊销其它会话"是**刻意**的：`01` §五 门槛 3 要求的正是"改密成功后可以正常访问业务 API"，
> 把当前会话也踢掉反而违背门槛。要"改密即踢掉其它设备"需要按 userId 反查会话集合（P0-1-6 没建这个索引），
> 留到有真实需求时再说。

## 坑 6 — Prisma 的「函数型默认值」不在 DB 层（手测第一步就撞上）

**现象**：想手工造一个账号做 curl 手测，直接 psql 插入：

```
ERROR: null value in column "id" of relation "users" violates not-null constraint
DETAIL: Failing row contains (null, manual-p017, $2b$12$SpFg…, 手测账号, MEMBER, ACTIVE, t, …, null).
```

翻迁移里的 DDL 才明白：

```sql
"id" UUID NOT NULL,                                    -- ← 没有 DEFAULT
"role" "user_role" NOT NULL DEFAULT 'MEMBER',          -- ← 有 DEFAULT
"created_at" TIMESTAMPTZ(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
"updated_at" TIMESTAMPTZ(3) NOT NULL,                  -- ← 没有 DEFAULT
```

**根因**：Prisma 的两类默认值落点不同 ——

| Prisma 写法 | 谁赋值 | DB 里有 DEFAULT 吗 |
|-------------|--------|--------------------|
| `@default(MEMBER)` / `@default(true)`（字面量） | DB | ✅ 有 |
| `@default(now())` | DB | ✅ 有（`CURRENT_TIMESTAMP`） |
| **`@default(uuid(7))`** | **Prisma 客户端** | ❌ **没有** |
| **`@updatedAt`** | **Prisma 客户端** | ❌ **没有** |

**对策**：手工造数据一律走 `pnpm db:studio` / Prisma 客户端（本批的手测改成用 Prisma 建号后一次通过）。
写进 README 的端点小节，避免下一个人再撞。P0-1-9 的 seed 用 Prisma，不受影响。

## 坑 7 — `verify:*` 脚本要先构建 `shared`

**现象**：给 `shared/src/auth.ts` 加了新导出后直接 `pnpm verify:app`：

```
import { AppError, PASSWORD_MAX_BYTES, … } from '@doubulea/shared';
SyntaxError: The requested module '@doubulea/shared' does not provide an export named 'PASSWORD_MAX_BYTES'
```

看着像写完就错，其实只是 `shared/dist` 还是旧的。

**根因**：`tsconfig.base.json` 的 `paths` 把 `@doubulea/shared` 指向**源码**，但那**只影响类型解析**；
tsc 产物里仍然是 `import '@doubulea/shared'`，运行期由 `node_modules` → `shared/dist` 解析。
也就是说：**后端 dist 的运行依赖 `shared/dist` 这个构建产物**（`pnpm start:backend` 同理）。

**对策**：四个 verify 脚本前置新增的 `build:shared`（= `pnpm --filter @doubulea/shared build`，
从子包目录调用同样成立）。代价约 1 秒，换来"单包跑脚本也不会踩到构建产物过期"。
（CI 不受影响：它先 `pnpm -r build`，顺序已由 workspace 拓扑保证。）

## 坑 8 — 验收脚本的"自清理"要连**顺手创建的键**一起管，且必须复核

第一次跑 `verify:auth` 后复核残留：

```bash
$ redis-cli --scan --pattern '*'
login-fail:no-such-user-yueriu          ← ⚠️ 残留
```

这个键不是给自建用户建的 —— 是"**故意不存在的用户名**"那条用例触发的
（失败计数键按被尝试的用户名建）。TTL 到了会自己消失，但"跑完即干净"是上一批立下的规矩。
→ 对策：把 `missingUsername` 也纳入 `finally` 的清理列表；再复核 `users` 与 Redis 均为空。
**顺带把这条补进技能里的「写验收脚本的三条常规」**：自造数据要**枚举全部**会创建的键，并实测复核。

### 5. 还没验的（明确的边界）

- **`/api/agents` 的 403**：`06` P0-1-7 验收里写的是"首登账号访问 `/api/agents` 得 403"，
  但 `/api/agents` 要到 P0-1-22 才存在。本批用探针路由 `/api/__t/business`（挂 `requireAuth`）
  与 `/api/__t/public`（不挂钩子）代替，**结论等价**（闸门在根上，与具体路由无关）。
- **限速的"10 分钟"时长本身**：验了锁定与"不被续期"、以及 `retryAfterSec` 落在 `(0, 600]`，
  但没有真等 10 分钟看它自动解锁（机制上等价于 Redis 键过期，已在 P0-1-6 的验收里覆盖）。
- **多实例部署下的限速**：计数在 Redis 里，多实例共享是对的；但没做多实例实测（本机只有单实例）。
- **改密后"其它设备"的会话**：刻意保留（见坑 5 的说明），因此也没有"其它设备被踢"的断言。
- **前端**：登录页/改密页是 P0-1-30 的产出；本批只保证接口契约（`shared/src/auth.ts` 的 schema
  就是给前端表单校验用的）。
