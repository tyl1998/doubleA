## 坑 1 — pnpm 12.4.2 不再读取 `.npmrc`

**现象**：把 `link-workspace-packages=true`、`node-linker=hoisted`、`strict-peer-dependencies=false`
等写进根 `.npmrc`，`pnpm install` 与 `pnpm config list` 均**完全无视**。

**定位过程**：

```
pnpm config list
→ 输出里只有 registry / allowBuilds / packages，
  自建 .npmrc 的键（link-workspace-packages 等）一个都没有
```

**根因**：pnpm 12.x 起，**配置的唯一入口是 `pnpm-workspace.yaml`**，`.npmrc` 仅保留
registry / auth 等 npm 兼容项（本项目 `.npmrc` 里只有注释，实际配置已外移）。

**结论**：
- 所有 pnpm 设置（`nodeLinker` / `resolutionMode` / `linkWorkspacePackages` …）写入
  `pnpm-workspace.yaml`，键名用 **camelCase**。
- `.npmrc` 只留说明性注释，避免后人再往里加设置而白费功夫。

## 坑 2 — 未授权的依赖构建脚本会让 `install` 直接失败

**现象**：

```
Error: ERR_PNPM_IGNORED_BUILDS
  ╰─▶ Ignored build scripts: esbuild@0.21.5
```

`install` 以退出码 1 结束（**是错误，不是警告**），依赖没有装完。

**试过但无效**：
- `.npmrc` 写 `onlyBuiltDependencies[]=esbuild` → 因坑 1 被无视；
- 命令行 `--config.strictDepBuilds=false` → 无效；
- 命令行 `--config.dangerouslyAllowAllBuilds=true` → 无效；
- `pnpm-workspace.yaml` 写标准键 `onlyBuiltDependencies: [esbuild]` → `pnpm config list`
  **能读到**，但 install 阶段仍不放行。

**根因**：pnpm 12.4.2 实际采纳的键是 **`allowBuilds`（映射形态）**：

```yaml
allowBuilds:
  esbuild: true
```

**旁证**：`node_modules/.modules.yaml` 里对应的字段是 `"allowBuilds": {}`，
且 `install` 在缺失配置时会**自动把占位符写回** `pnpm-workspace.yaml`（`set this to true or false`）。

**结论**：新增需 postinstall 的原生依赖（如 P0-1-13 的 `onnxruntime-node`）时，
必须在 `pnpm-workspace.yaml` 的 `allowBuilds` 下加 `包名: true`，否则 install 直接失败。

## 坑 3（最关键）— pnpm 目录符号链接**静默失败**

**现象**：`pnpm install` 报「成功」，但构建时报：

```
Error: Cannot find module 'E:\doubuleA\shared\node_modules\typescript\bin\tsc'
Error: Cannot find module '@doubulea/shared'
```

**排查过程**：

1. 包内 `node_modules` 下确实有 `typescript` 目录，但 `readdirSync` 返回 **0 项**；
2. `lstatSync().isSymbolicLink()` 为 `false` —— **不是链接，是空目录**；
3. 手工 `fs.symlinkSync(target, p, 'junction')` → **成功**，能读到内容；
4. 手工 `fs.symlinkSync(target, p, 'dir')` → **不抛错**，但只得到 **0 项空目录**；
5. 手动删除该空目录时还报 `EPERM`（真实 symlink 残留需更高权限）。

**根因**：Windows 创建**真正的符号链接**需要「开发者模式」或管理员权限。
权限不足时 Node 的 `symlink(…, 'dir')` **不报错**，留下空目录；pnpm 对此不告警。
本机未开启开发者模式 → pnpm 的每一种 layout（isolated / hoisted）都拿不到可用链接。

**这解释了为什么 `store`（`node_modules/.pnpm/*`）内容完整、`install` 却「成功」** ——
真正失败的是最后一跳「store → 各包 node_modules」的链接注入。

**解决方案（三层，缺一不可）**：

1. **`nodeLinker: hoisted`**（`pnpm-workspace.yaml`）
   依赖扁平提升到根 `node_modules`，不做逐包链接。`typescript` / `zod` / `react` /
   `vite` 等**第三方包**由此正常解析。
   注意：hoisted 布局下各包**不再有**自己的 `node_modules`，`pnpm run` 靠解析
   `node_modules/.bin`，仍然可用。

2. **根 `tsconfig.base.json` 的 `paths` 指向 shared 源码**
   ```json
   "paths": { "@doubulea/shared": ["./shared/src/index.ts"] }
   ```
   让 **TS 不需要任何符号链接**即可解析该包。
   ⚠️ 副作用：shared 源码进入各包编译程序，故 `backend/tsconfig.json` 必须把
   `rootDir` 设为 `"../"`（而非 `./src`），否则报
   `TS6059: File '.../shared/src/index.ts' is not under 'rootDir'`。
   产物路径随之变为 `backend/dist/backend/src/index.js`，`start` 脚本已同步。

3. **`frontend/vite.config.ts` 的 `resolve.alias`**
   TS 的 `paths` 只管类型，**不管 Rollup 打包**。不加 alias 会在打包期报
   `Rollup failed to resolve import "@doubulea/shared"`。
   别名同样指向 `../shared/src/index.ts`（Vite 一并编译进产物，符合
   「编译期内联、运行期零耦合」的定位）。

4. **`infra/scripts/link-workspace.mjs` + 根 `prepare` 脚本**
   上面三条解决了 TS 与打包，但**运行期** Node 仍需按 `exports` 解析该包
   （hoisted 布局下 `@doubulea/shared` 不会自动提升到根 `node_modules`，
   因为 workspace 包**不参与 hoist**）。
   该脚本在 `prepare`（`pnpm install` 后自动触发）中把
   `backend|frontend/node_modules/@doubulea/shared` 的空目录**替换为 junction**
   （junction 不需要开发者模式）。脚本对已有效的链接会跳过，在正常环境无副作用。

**教训（写进施工纪律）**：
> **`install` 报成功 ≠ 依赖可用。** 每批次动完依赖后，必须跑一次
> `pnpm -r typecheck && pnpm -r build` 才算验证通过；
> 出现 `Cannot find module` 时**先查 `node_modules` 里的目录是不是空的**。

## 坑 4 — 根 `clean` 脚本自我递归

**现象**：

```
$ pnpm -r clean   ← 被重复打印约 50 次
'pnpm' 不是内部或外部命令
```

**根因**：根 `package.json` 的 `"clean": "pnpm -r clean"`，
经 `pnpm -r` 递归到各包后，执行的是**各包自己的 `clean`**；
但当从根直接 `pnpm clean` 时，`-r` 会再次匹配到根，形成自我递归。

**结论**：改为不依赖同名脚本的写法，直接递归 exec：

```json
"clean": "pnpm -r --no-bail exec node -e \"require('node:fs').rmSync('dist',{recursive:true,force:true})\""
```

## 坑 5 — tsc 产物写回 `src/`，且 `.gitignore` 当时未覆盖

**现象**：P0-1-1 收尾检查文件树时，发现 `shared/src/` 下混入了
`envelope.js` / `errors.d.ts` / `*.js.map` 等 **12 个编译产物**，与源码平级。

**根因**：排查 `rootDir`/`outDir` 冲突的过程中，中途的 tsconfig 版本让 tsc
把产物写在了 `src` 旁边。当时 `.gitignore` 只忽略了 `dist/`，这些文件不会被排除。
虽然最终配置已修正（产物正确落 `dist/`），但这些残留是**已发生的事实**。

**解决**：
1. 清理 `shared/src` 下全部 `.js` / `.d.ts` / `*.map`（12 个），确认只剩 3 个 `.ts`；
2. `.gitignore` 补编译残留防护，避免同类问题再次被提交：

```gitignore
**/src/**/*.js
**/src/**/*.js.map
**/src/**/*.d.ts
**/src/**/*.d.ts.map
!**/src/**/*.d.mts
```

**教训**：改 `rootDir`/`outDir` 后要**复查源码目录是否干净**，
不能只看构建是否报错 —— tsc 往源码目录写产物是**不报错**的。

## 遗留与后续注意

1. **`--force` 在本机极易失败**：它会尝试 swap 已有的每个目录，Windows 常报
   `failed to remove existing directory ... 拒绝访问 (os error 5)`，
   且**每次卡在不同的目录**。清理后应**优先跑普通 `pnpm install`**；
   确需重建时先清空 `node_modules` 再装，不要反复 `--force`。
2. **不要手工删各包 `node_modules`**：删掉后 `pnpm install` 会认为
   「Already up to date」而不重建链接（`prepare` 脚本可兜底修复）。
3. 若将来 CI（Linux）或本机开启开发者模式，可去掉 `nodeLinker: hoisted`
   与 `link-workspace.mjs`，切回 pnpm 默认的严格隔离布局，**代码无需改动**。
4. `--force` 阶段曾残留大量 `*_pacquet-stage_*` 中间目录，已清理；
   若再出现，可安全删除。
