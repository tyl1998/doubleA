# 问题记录 · P1-18 · 迁移"就地改"未落库导致 500 INTERNAL

> 批次：P1-18（资产共享与用户组标签）
> 日期：2026-10-16
> 现象：前端拿到 `{"code":"INTERNAL","msg":"服务内部错误"}`（HTTP 500）；`/api/model-providers`、`/api/user-groups`、`/api/agents` 等页面报错。

## 1. 现象与取证

`.dev-logs/backend.log` 里两条 `PrismaClientKnownRequestError`（P2022 / P2021）：

```
The column `model_providers.credential_mode` does not exist in the current database.
→ db.modelProvider.findMany()   (services/model.service.ts:231)
The table `public.user_groups` does not exist in the current database.
→ db.userGroup.findMany()       (services/userGroup.service.ts:66)
```

## 2. 根因

P1-18 按设计（`06` §五·补 P1-18 / `子方案⑧` §5.2）**在未提交的同名迁移 `20261016120000_asset_acl` 上就地改**（把 P1-13 的可见性初版扩成 P1-18 的最终形态）。

但**该迁移在本机 dev 库上早已被 P1-13 应用过一次**（`_prisma_migrations` 里已有记录）。就地改文件**不会**把新增对象带进这个已应用的库 ⇒ Prisma 客户端按新 schema 查询、库里却没有 `credential_mode` / `user_groups` 等对象 ⇒ 500。

校验和证据：库里记录的 checksum 是**改前**文件的 `8871bc99…`，而磁盘上已是改后文件 `3c8a389b…`。

> 教训：**"就地改未提交迁移"只对"尚未应用过该迁移的库"成立**。本机 dev 库已经应用过 ⇒ 需要一次**修复**（对已应用的库补齐 delta），而不是重跑迁移。

## 3. 修复（数据保留，不清库）

① 用 Prisma 自己算 delta（比手写可靠）：
```bash
cd backend
pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script
```
只保留 **P1-18 相关**语句（剔除其中与 P1-16a 的 `egress_scope` 重排噪音，见 §5），存成 `/tmp/p18_repair.sql`，内容即：`CREATE TYPE audience_subject_type / provider_credential_mode` + `ALTER TYPE asset_visibility ADD VALUE 'SHARED'` + `ALTER TABLE model_providers ADD COLUMN credential_mode …` + `DROP TABLE provider_shares` + `CREATE TABLE agent_audiences / user_groups / user_group_members / provider_user_credentials` + 索引与外键。

② 应用到 dev 库（`provider_shares` 当时 0 行，DROP 无数据损失）：
```bash
docker exec -i doubulea-postgres psql -U doubulea -d doubulea -v ON_ERROR_STOP=1 < /tmp/p18_repair.sql
```

③ **刷新已应用迁移的记录校验和**，让"库里记录"与"磁盘文件"一致：
```sql
UPDATE _prisma_migrations
   SET checksum = '3c8a389bdeb4c7ee82471f40cb6c5f92a38c4d3e7910402c19f6a5150223225d'
 WHERE migration_name = '20261016120000_asset_acl';
```
（该 sha256 = 改后 `migration.sql` 的 `shasum -a 256`。）

## 4. 验证

- `prisma migrate status` → **Database schema is up to date!**
- 对象核对：`agent_audiences / user_groups / user_group_members / provider_user_credentials` 存在、`provider_shares` 已删、`asset_visibility = {PUBLIC,PRIVATE,SHARED}`、`model_providers.credential_mode` 存在。
- 直接跑服务层（tsx，ADMIN 视角）：`listModelProviders`（读 `credentialMode`）✅ / `listUserGroups` ✅ / `listAgents`（读 `audiences` + 解析 viewer 组）✅ —— 三条原报错路径全部恢复。
- `curl /health` → 200；未登录访问两个端点 → **401**（不再是 500）。

## 5. 遗留（**非本批**，不修）

`prisma migrate diff` 仍会报一处**与 P1-16a 有关**的既有噪音（下 enum 值重排 + `egress_policy.id SET DEFAULT 'default'`）：
```
ALTER TABLE "egress_policy" ALTER COLUMN "id" SET DEFAULT 'default';
BEGIN; CREATE TYPE "egress_scope_new" … RENAME … COMMIT;
```
这是 Prisma 对"枚举值顺序"的已知改法，**语义上是 no-op**，`migrate status` 判为 up to date。它**不是 P1-18 引入**，故本批不触碰（动了反而可能波及出网策略）。留给 P1-16 相关批次决定是否收口。

## 6. 对新机器的口径（无需任何手工修复）

- **全新库 / 其他开发机**：`pnpm db:deploy`（`prisma migrate deploy`）会**从头**应用改后的 `20261016120000_asset_acl` ⇒ 一次得到完整 P1-18 schema，**不需要**本文 §3 的修复。
- 本文 §3 只针对"**已经应用过改前版本**的既有库"（本机 dev 库）。
- ⚠️ 副作用（无害）：本机 dev 库的 `asset_visibility` 取值顺序是 `{PUBLIC,PRIVATE,SHARED}`（`ADD VALUE` 追加），而迁移文件里是 `{PRIVATE,SHARED,PUBLIC}`。Prisma 不依赖枚举顺序，`ORDER BY`/比较语义不受影响。
