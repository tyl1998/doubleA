## 0. 一句话结论

**本批的价值一半在新代码，一半在"把协议差异关进一个文件"。**

> 新增的 `backend/src/llm/protocol.ts` 是路径 / 鉴权头 / 报文 / 结束原因归一化的**唯一落点**；
> `client.ts` 仍然是"读流 / 计时 / 汇总 / 回调"那条**不认识任何协议字段名**的外壳；
> `upstream.ts`（看门狗 / 中断 / 状态码映射 / 脱敏）**一行没动协议相关的逻辑**。

而**两个真缺陷都不是演练**，是验收档先红、再修、再绿：

| # | 缺陷 | 谁抓出来的 | 症状为什么难发现 |
|---|------|-----------|-----------------|
| 1 | `mergeUsage` 让"先到的 `total`"活了下来（期望 20、实测 13） | **本批新写的** `verify:llm` **C 组** | 数字看着像个正常数字；只有拿 `in`+`out` 去反算才看得出矛盾 |
| 2 | `buildProviderUpdateBody` 把 `protocol: undefined` 当成一次改动 | **P0-1-36 就有的** `verify:admin-ui` **D4/D5/E2** | "没改也要发一次 `PATCH {}`" 被契约打成 400；typecheck/lint 全绿 |

## 1. 架构决定：**一条外壳 + 一个协议钩子**

三种协议（`OPENAI_COMPAT` / `OPENAI_RESPONSES` / `ANTHROPIC_MESSAGES`）的差异**全部**可以归到六个点上：

| 差异面 | OpenAI 兼容（默认） | OpenAI Responses | Anthropic Messages |
|--------|--------------------|------------------|--------------------|
| 对话路径 | `POST {baseUrl}/chat/completions` | `POST {baseUrl}/responses` | `POST {baseUrl}/messages` |
| 鉴权头 | `Authorization: Bearer <key>` | 同左 | `x-api-key: <key>` + **`anthropic-version: 2023-06-01`**（**不带 `Authorization`**） |
| system 的位置 | `messages[0].role === 'system'` | 顶层 `instructions` | 顶层 `system` |
| 输出上限字段 | `max_tokens`（可选） | `max_output_tokens` | `max_tokens`（**必填** ⇒ 缺省兜 `4096`） |
| 增量文本在哪 | `choices[].delta.content` | `response.output_text.delta` 事件 | `content_block_delta` 且 `delta.type === 'text_delta'` |
| 结束信号 | `data: [DONE]` | **`response.completed` 事件** | **`event: message_stop`** |
| 结束原因词表 | `stop`/`length`/`tool_calls`/`content_filter` | `response.status` = `completed`/`incomplete` | `end_turn`/`stop_sequence`/`max_tokens`/`tool_use`/`refusal`/`pause_turn` |

于是钩子的形状就是：

```ts
interface ChatProtocol {
  id; label
  chatPath; modelsPath
  headers(endpoint, opts): Record<string, string>
  buildBody(input): unknown
  isDoneSentinel(eventName, data): boolean
  readNonStream(payload): { text, rawFinishReason, usage }
  readStreamFrame(eventName, data): DecodedFrame | null
}
```

**为什么值得为它单开一个文件**：这七行差异**任何一处泄漏到外面**，都会让"与协议无关"的层开始认识协议名 ——
而那一层的职责（超时、中断、状态码、脱敏）本来是**三种协议共用同一份**的。泄漏的症状全部是静默的（见 §2~§5）。

## 2. ⚠️ 坑一：鉴权头是"换"不是"加"

**直觉写法**：`fetchUpstreamJson` 里 `headers: { ...upstreamHeaders(endpoint, opts), ...request.headers }`。

**为什么是错的**：那样一来，Anthropic 的请求会同时带 `Authorization: Bearer` **和** `x-api-key` ——
而要让"带不带 `Authorization`"变成可配置的，`upstream.ts` 就被迫**认识协议名**，
它现在的四个职责（看门狗 / 中断 / 状态码映射 / 脱敏）本来是**完全与协议无关**的。

**定案**：`UpstreamJsonRequest.headers` 是**整体覆盖**语义 —— 钩子给了就用钩子那份，没给才走默认：

```ts
headers: request.headers ?? upstreamHeaders(endpoint, { json: ... })
```

**取证**：假上游侧记录 `authorization` 与 `x-api-key` 两个头，C 组里有一条硬断言 ——
Anthropic 那条路上 **`authorization === null`**（不是"值不同"，是**根本没这个头**）。

> 通则：**"可选覆盖"与"合并"是两种语义**。当被合并的两份来自"与协议无关的默认"和"与协议有关的定制"时，
> 合并会把"定制"的边界抹掉，让默认那份的键泄漏进不该有它的请求里。

## 3. ⚠️ 坑二：`rawFinishReason` 必须先**归一化到 OpenAI 词表**

`client.ts` 把每一帧的结束原因透出成 `rawFinishReason`，而 `orchestrator/chatBot.ts` 里有一条判据：

```ts
if (rawFinishReason !== 'stop' /* … */) { logger.warn('可能被截断') }
```

这条判据是 **P0-1-12 为 OpenAI 词表写的**。如果 Anthropic 原生值直通 ——
每一条**正常结束**的回答都会拿到 `end_turn`（≠ `stop`）⇒ **每条回答都打一条 warn**。

**为什么这条最贵**：它不是功能坏，是**日志噪音**；而噪音会让"真的被截断"那条 warn 淹掉。
而且它**只在接真 Anthropic 上游时才出现**，夹具假上游如果只测"能不能解析出文本"是照不到它的。

**定案**：在 `protocol.ts` 里做一次显式映射，**归一化的位置就在协议层**（离开这层就是 OpenAI 词表）：

```
end_turn → stop      stop_sequence → stop    pause_turn → stop
max_tokens → length  tool_use → tool_calls   refusal → content_filter
completed → stop     incomplete → length（含 content_filter 时 → content_filter）
```

**取证**：`verify:llm` 的 C 组是**纯逻辑**断言（不经过任何 HTTP），逐条比对映射表 ——
这类"词表归一化"只有纯函数档能穷举得干净。

## 4. ⚠️ 坑三（真 bug）：`usage` 是**两半合并**，`total` 必须是**从属量**

### 现象

Anthropic 的流式把用量**拆在两处**：

- `message_start` ⇒ `message.usage.input_tokens`（**此刻 `output_tokens` 还是 0**）
- `message_delta` ⇒ `usage.output_tokens`

而 `message_start` 里那份 `usage` 常常还带一个 `total` 之类的**临时汇总值**（本仓夹具给的是 13）。

### 第一版实现（错的）

```ts
// 逐字段：先到先得
const tokensTotal = incoming.tokensTotal ?? previous?.tokensTotal ?? null
```

⇒ 先到的 `13` 活了下来，**并且因为后面那次没有 `total`，它永远不被覆盖**。
验收 C 组那条断言"两半齐了 ⇒ 补算 `total`，期望 20、实际 13"当场红。

### 定案

```ts
const tokensIn  = incoming.tokensIn  ?? previous?.tokensIn  ?? null
const tokensOut = incoming.tokensOut ?? previous?.tokensOut ?? null
const explicitTotal = incoming.tokensTotal ?? previous?.tokensTotal ?? null
const tokensTotal = tokensIn !== null && tokensOut !== null ? tokensIn + tokensOut : explicitTotal
//                     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 齐了就自己算，不看上游给的那份
```

### 为什么这条必须写进文档

`total` 是**从属量**（`in + out`），不是**独立观测量**。
一旦把上游某半截报文里的 `total` 当成权威值，**任何按 `total` 计费/统计的报表都会少算** ——
而少算的数值**看起来完全合理**（13 也是个正常的 token 数），没有任何异常信号。

> 口径：**能由别的字段推出来的量，不要采信上游在"半截报文"里给的值。**

## 5. ⚠️ 坑四（真 bug）：前端 `undefined` 会被判成"改了一次"

### 现象

`buildProviderUpdateBody` 的职责是"**什么也没改就 `return null`**"（P0-1-36 定的：无改动**不发请求**，
否则每次都刷 `updated_at` 搅乱排序）。它的判据长这样：

```ts
if (values.protocol !== provider.protocol) body.protocol = values.protocol
```

新增 `protocol` 之后，`values.protocol` 在"编辑表单还没初始化/老数据"时会是 `undefined`，
而 `undefined !== 'OPENAI_COMPAT'` **恒为真** ⇒ 请求体里多出一个 `protocol: undefined` ⇒
`Object.keys(body).length === 0` 这条"零改动"判据**失效** ⇒ 一次空 `PATCH {}` 被契约打成 **400**。

**它为什么是"真发现的"而不是推演出来的**：P0-1-36 就存在的 **D4 / D5 / E2** 三条用例（"无改动 ⇒ 不发请求"）
在加完 `protocol` 后**当场变红** —— 这三条守的正是这个行为，而它们当时还没有任何协议概念。

### 定案

```ts
// ⚠️ 显式判 undefined（三态）：不判的话 `undefined !== 'OPENAI_COMPAT'` 被判成一次改动
if (values.protocol !== undefined && values.protocol !== provider.protocol) body.protocol = values.protocol
```

并补 **K7** 把"`undefined` 不算改动"钉成一条**常驻断言**（否则下一个人重构时又会踩）。

> 通则：**三态字段（不带 / `null` / 值）在"比较是否变化"时必须先判 `undefined`。**
> 这条与"Key 三态"是同一个家族，区别是 Key 那处是**请求体形状**错，这处是**"要不要发请求"**错。

## 6. 兼容性是怎么做到的：**可选字段 + 一处回落**

```ts
interface LlmTarget { /* … */ protocol?: UpstreamProtocol }   // 可选
export function protocolOf(id?: string) { return PROTOCOLS[id ?? ''] ?? PROTOCOLS[DEFAULT_UPSTREAM_PROTOCOL] }
```

- **读**：`chat()` / `chatStream()` / `fetchRemoteModels()` 都走 `protocolOf(target.protocol)`；不传 ⇒ 默认协议。
- **数据库**：`protocol` 列 `NOT NULL DEFAULT 'OPENAI_COMPAT'` ⇒ 迁移后**既有行行为逐个不变**（已 `select` 取证）。
- **未知协议名**：**回落到默认协议，不抛错**（`docs/02` 已写明这条口径）—— 数据库里不该出现的值不应该变成 500。

**结果**：P0-1-37 之前的**所有调用点与验收脚本一个字都没改**，`verify:llm` 原有 22 项**一条未改也全绿**。
这条是"可加性改造"的验收标准：**旧档不改也过**。

## 7. `EMBEDDING` + 非默认协议为什么拦在**服务层**

- 用户明确的是"**只做 CHAT**"，embedding 仍然只有 OpenAI 兼容一套。
- 这条约束**跨两个入口**（`createModelProvider` / `updateModelProvider`），而且 update 要看的是
  **合并后的最终生效值**（只改一半时另一半得拿库里的现值比）⇒ 校验点只能在服务层。
- 判据落在 `shared`（`protocolAllowedForType(type, protocol)`，**唯一实现**），错误形状与其他校验失败一致：
  顶层 `msg` = 「请求参数校验失败」，字段级 `data.fields = [{ path: 'body.protocol', message }]`。

**注意一处刻意的"没有做"**：`update` 上**没有**加"改 `protocol` 要先解绑 Agent"之类的 409 守卫 ——
`protocol` 不是 Agent 绑定的判据（绑的是 `model_id`），加一条**自己发明的约束**是 P0-1-11 记过的老坑。

## 9. 三条「施工时才发现」

| # | 事 | 归类 |
|---|----|------|
| ① | `readNonStream` 要求 Responses 的 `output[]` **非空**是**解析前提** | **用例写错**（不是实现的问题）—— 最早那条用例喂了 `{ status: 'incomplete', output: [] }`，实现抛"上游响应里没有 output[]"，是正确的 |
| ② | 协议名查表必须**回落**而不是抛错 | 与 §6 同一条；未知值只可能来自手工改库 |
| ③ | Anthropic 的 `GET /models` **同样要带 `x-api-key`** | `fetchRemoteModels` 的 404 文案**按协议分支**（Anthropic 那条点明"要带上 `x-api-key`"），否则用户会照着 OpenAI 的文案去查 `Authorization` |

另有一处**脚本自身的伤**（`verify-llm.mjs`）：`const DECODE_CTX = { … apiKey: SECRET_KEY }` 写在 `SECRET_KEY`
声明之前 ⇒ `Cannot access 'SECRET_KEY' before initialization`（TDZ）。改成**函数** `decodeCtx()` 即可 ——
**常量对象在模块顶层引用后面才声明的常量**是这类脚本最常见的自伤。

## 11. 一句话给下一个动这一块的人

> **要加第四种协议，只改 `protocol.ts` 一个文件。**
> 如果你发现自己在 `client.ts` / `upstream.ts` / `service` 里写下了某个协议特有的字段名或头名，
