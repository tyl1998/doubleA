## 坑 1 — 「响应体不含密码」的检查要分两层

**背景**：验收条款是「建号返回体含初始密码、再次查询列表**不含**密码」。
写断言时很自然地把所有"敏感字样"列成一张清单去搜响应体：

```js
const PASSWORD_TRACES = ['passwordHash', 'password_hash', 'initialPassword', '$2b$', PASSWORD]
```

**问题**：`initialPassword` 在建号/重置密码的响应里**本来就是该出现的字段名**
（`{"user":{…},"initialPassword":"nHKqC7u7bwQUDbZFme"}`）。把它放进"任何响应都不许出现"的清单里，
**正确实现会被判失败**；而如果把清单删干净，又漏掉了"列表里出现 initialPassword 字段"这种真问题。

**对策**：按"信息在哪一层"拆成两条检查：

| 检查 | 清单 | 适用范围 |
|------|------|----------|
| 值 / 哈希 | `passwordHash`、`password_hash`、`$2b$`、已知明文密码 | **所有**响应 |
| 字段名 | `initialPassword` | **列表/详情类**响应（建号/重置那一次除外） |

```js
const PASSWORD_TRACES = ['passwordHash', 'password_hash', '$2b$', PASSWORD]   // 不含键名
// 列表额外要求这个键也不出现
assert(response.body.includes('initialPassword') === false, '列表响应里出现了 initialPassword 字段')
```

> **可复用的教训**：写"泄露检查"时先分清**要拦的是值还是字段名**。
> 把两者混在一张清单里，得到的不是更严格的验收，而是**自相矛盾**的验收
> —— 它会在正确实现上报错，然后被人"顺手放宽"到失去意义。

## 坑 2 — 重置密码必须清登录失败计数

**场景**：某同事连错 5 次密码被锁 10 分钟，来找管理员。管理员点"重置密码"，把新初始密码发给他。
**如果重置不清计数**：他拿着新密码登录 → 仍然 `429 账号已锁定，请 10 分钟后重试`
→ 他会认为"重置没生效"，再来一轮沟通。而这**恰恰是重置密码最常见的触发场景**。

**对策**：`resetUserPassword` 里做三件事（缺一个都会让这个功能名不副实）：

1. `invalidateUserSnapshot(userId)` —— 否则该用户**在线的**会话不会被首登闸门拦住（最长 60s 空档）；
2. `clearLoginFailures(username)` —— 让"因被锁而重置"的人立刻能登进来；
3. 不吊销其已有会话（没有按用户反查会话的索引，P0-1-6 的取舍）—— 配合第 1 条后，那些会话会立刻被闸门赶到改密页。

验收里的原话断言：

```
[PASS] 重置密码会**清掉登录失败计数**：连错 5 次被锁的号，重置后能立刻用新密码登录
```

> 这类"文档没写但语义上必需"的连带动作，是**从使用场景倒推**出来的 —— 读需求文档读不出来，
> 只有把"谁会在什么情况下点这个按钮"走一遍才会浮现。

## 坑 3 — Prisma 的唯一冲突：要两道，且用错误码而不是 `instanceof`

**两个问题叠在一起**：

**① 只做预检有并发窗口。** `findUnique` 查到没有 → 另一个请求同时插入 → `create` 撞唯一约束。
只写预检的话，第二个请求拿到的是 **500**（未分类的 Prisma 错误），而不是应有的 `409 用户名已存在`。

**② `instanceof` 判定不可靠。** Prisma 7 的错误类从生成物的**内部路径**导出，monorepo 里
"两份类对象"会让 `instanceof PrismaClientKnownRequestError` 悄悄变成 `false`
（而且它是"漏判"而不是"错判"，最难发现）。错误码字符串是稳定的对外契约。

**对策**：

```ts
function hasPrismaCode(error, code) {                  // 鸭子类型
  return typeof error === 'object' && error !== null && error.code === code
}
const isUniqueViolation = (e) => hasPrismaCode(e, 'P2002')   // 唯一约束
const isRecordNotFound = (e) => hasPrismaCode(e, 'P2025')    // update 未命中

// 先查一次（给出可读结论）+ create 上 catch（并发兜底）
if (await db.user.findUnique(...)) throw AppError.conflict(`用户名已存在：${username}`)
try { created = await db.user.create(...) }
catch (error) { if (isUniqueViolation(error)) throw AppError.conflict(...); throw error }
```

认不出来的错误**原样抛出**（errorHandler → 500 + 完整日志），不吞错。

**实测**：`Verify-Users-Created-X` 与 `verify-users-created-x` 都返回 409 —— 归一化真的生效了
（否则会插进两条看起来"不同名"的记录，而它们其实指向同一个人）。

## 坑 4 — 分页的两条硬要求：稳定排序 + `total` 与数据同快照

**① 排序必须稳定。** 只按 `username` 排时，若两个用户的 username 排序相等（本项目 username 唯一，
所以这在当前表结构下不会发生），或将来加了别的排序键，`offset` 分页就会在翻页时重复/漏项。
统一写成 `orderBy: [{ username: 'asc' }, { id: 'asc' }]` —— **主键兜底**是分页的通用保险。

**② `total` 与当页数据要来自同一快照。** 分成两次独立查询时，中间有其他写入就会
"总数与列表对不上"，分页器会显示 3 页但只有 2 页有数据。用一次事务：

```ts
const [rows, total] = await db.$transaction([
  db.user.findMany({ select: USER_LIST_SELECT, orderBy: […], skip, take }),
  db.user.count(),
])
```

**另一条同源纪律**：`USER_LIST_SELECT` 是**列表/建号/重置共用的一份字段白名单**，
集中在一处的意义是——将来给 `users` 加列时，只有"确实该下发"的列才会被加进来，
不会因为某处顺手 `include: true` 就把 `password_hash` 带出去（`02` §十 不变式）。

## 坑 5 — 「不能操作自己」放哪一层、边界到哪

**坑预判只说了**「不能停用/降级自己（防 admin 自锁）」。落地时有三个必须自己想清楚的判断：

**① 放服务层，不放路由层。** 这条约束需要知道"**谁**在操作**谁**"（同一个 admin 对别人可以做、
对自己不行）—— 它是业务规则而不是鉴权规则。路由层的 `requireAdmin` 只回答"你是不是管理员"。
放在服务层还有个好处：脚本/内部调用同样受约束。

**② 返回 `409 CONFLICT` 而不是 `400 VALIDATION`。** 请求本身完全合法（`{status:'DISABLED'}` 没问题），
冲突在于"目标是你自己"这个**状态关系**。`400` 会引导前端去标红某个输入框，而这里没有那个输入框。

**③ 边界扩到"重置自己"（本批扩充，非坑预判原文）。** 停用/降级会真的锁死账号；
重置自己不会锁死，但会让一枚**只在响应里闪一次**的新初始密码出现在浏览器里，
而本人本来就有 `/api/auth/password` 可自助改密 —— 少一条可能把密码弄丢的路径。
三条合并成一句可读的话：「不能修改自己的状态或角色（否则可能把自己锁在外面）」/
「不能重置自己的密码，请用「修改密码」自助改密」。

验收断言里还特意加了一条"被拒之后操作者本人仍然可用" —— 这才是这条约束存在的意义，
只断言 409 是验不出"防自锁"的。

## 坑 6 — 首登闸门会拦住"首登态的 admin"调 `/api/users`

P0-1-7 的闸门白名单只有 `/api/auth/{login,logout,me,password}`，`/api/users` **不在其中**。
于是：**一个刚建出来的 admin（`mustChangePassword=true`）在改密之前是建不了号的**。

这不是 bug，但它有两个实际影响，都必须提前知道：

1. **P0-1-9 的 seed 顺序**：`06` 写的是"造一个 admin（**首登改密态**）" —— 那么门槛 1
   「admin 建号 → 返回初始密码」的**第一步必须是让这个 admin 先改密**，否则他建号会吃 403。
   （这恰好也是门槛 1 里"用户用初始密码登录成功且被强制跳改密"的同一条链路。）
2. **验收脚本的数据准备**：`verify-users.mjs` 里的"操作者"账号必须建为**非首登态**
   （`mustChangePassword: false`），否则整批断言会全线 403 —— 这类失败看着像"接口坏了"，
   实际是测试夹具没准备好。

真机演示里这步是显式走出来的（见下方验收记录 ①②③）。

## 坑 7 — 建号返回 `200` 而不是 `201`

`POST /api/users` 成功了，语义上"创建了一个资源"，REST 惯例是 `201 Created`。
本项目**刻意不引入**：`02` §四 已定「`code` 是唯一契约，HTTP 状态码是它的辅助信号」，
成功侧同理统一 `200` + `code=0`。

代价是"少了一点 REST 味道"，收益是**前端只有一条成功分支**（不必为 201 单独处理），
与既有 4 个端点（login/logout/me/password 都是 200）也一致。记在这里，免得下批或前端以为是漏了。
