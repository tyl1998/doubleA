## 坑 1 — pg_bigm 没有二进制包，只剩源码编译

**排查过程（排除了两条路）**：

```bash
# ① Debian 官方源（bookworm / bookworm-updates / security）
apt-cache search bigm
→ 只有 r-cran-bigmemory / r-cran-bigmemory.sri（R 语言包，与 PG 无关）

# ② PGDG 源（apt.postgresql.org）
curl -fsS .../dists/bookworm-pgdg/Release   → HTTP 200（源可达、可 update）
apt-get update                              → Hit:4 http://apt.postgresql.org/pub/repos/apt bookworm-pgdg InRelease
apt-cache pkgnames | grep -i bigm           → 同样只有 r-cran-bigmemory*
apt-cache policy postgresql-16-pg-bigm      → （空，包不存在）
```

**结论**：PGDG **确实没有** `pg_bigm` 的二进制包。`06` §P0-1-2 坑预判里
「失败则评估 `zhparser` 替代」**不需要走了** —— 源码编译是唯一且可行的路径。

**顺带发现（优化点）**：`pgvector/pgvector:pg16` 基础镜像**自带 PGDG 源**，
所以 `postgresql-server-dev-16` 不装源就能直接装。Dockerfile 里**刻意不加 PGDG**，
省一次 apt 往返。

## 坑 2 — pg_bigm 的 GitHub tag 不是 `v1.2`

**现象**：按直觉拼 `.../archive/refs/tags/v1.2.tar.gz` → **404**，
且四个镜像源全部 404（说明不是网络问题，是 tag 不存在）。

**根因**：pg_bigm 的 tag **带日期后缀**：

```bash
curl -fsSL https://api.github.com/repos/pgbigm/pg_bigm/tags
→ v1.2-20250903   ← 最新
  v1.2-20240606
  v1.2-20200228
  v1.2-20191003
  ...
```

**解决**：Dockerfile 拆成三个 ARG，避免每次改 tag 都要改 URL 拼接：

```dockerfile
ARG PG_BIGM_VERSION=1.2
ARG PG_BIGM_RELEASE=20250903
ARG PG_BIGM_TAG=v${PG_BIGM_VERSION}-${PG_BIGM_RELEASE}
```

**同时注意**：GitHub archive 解压后的目录名是 **`pg_bigm-1.2-20250903`**
（去掉 `v` 前缀），不等于 `${PG_BIGM_TAG}`。Dockerfile 里用 `cd pg_bigm-*`
通配规避，避免日后改 tag 时再踩。

## 坑 3 — Docker Hub 镜像加速器不可靠

**现象**：

```
docker pull pgvector/pgvector:pg16
→ failed to resolve reference "docker.io/pgvector/pgvector:pg16":
  unexpected status from HEAD request to https://docker.xuanyuan.me/... : 403 Forbidden
```

**本机配置的加速器**（`docker info` 输出）：

```
docker.1ms.run, docker.xuanyuan.me, docker.m.daocloud.io,
hub-mirror.c.163.com, dockerproxy.com
```

**排查**：`docker.xuanyuan.me` 稳定 403。逐个直连其余四个拉 `minio/minio` 也**全部失败**
（网络/限流问题，非配置错误）。

**两个绕过办法**：

1. **重试官方源** —— `pgvector/pgvector:pg16` 重试后成功（621MB 落地）。
   说明 403 是**间歇性**的，多试一次往往就过。
2. **本地已有等价镜像时直接打 tag** —— MinIO 本机已有
   `quay.io/minio/minio:latest`（quay 是 MinIO 的官方发布源，镜像内容一致）：

## 坑 4（最关键）— PowerShell 5.1 把 Go 模板 `'{{...}}'` 当脚本块

**现象**：`dev-up.ps1` 直接语法错误，整个脚本无法加载：

```
所在位置 dev-up.ps1:90 字符: 50
+  $state = (& docker inspect --format '{{if .State.Health}}{{.S ...
+                                   ~
if 语句中的"if"后面缺少"("。
"end"后面缺少语句块。
```

**根因**：Windows PowerShell **5.1** 的解析器会把 `{{` 视为**嵌套脚本块起始符**。
即使整段在单引号里，`--format '{{if ...}}'` 这种「命令参数 + 双花括号」
组合仍会被提前分词，导致解析器在 `{{if` 处尝试按 `if` 语句解析。

**解决**：Go 模板**先赋值给变量**，再传参：

```powershell
# ❌ 直接内联 → 语法错误
$state = (& docker inspect --format '{{if .State.Health}}...{{end}}' $cid)

# ✅ 放变量 → 正常
$HealthFormat = '{{if .State.Health}}{{.State.Health.Status}}{{else}}{{.State.Status}}{{end}}'
$state = (& docker inspect --format $HealthFormat $cid)
```

**波及**：`dev-up.ps1` 里**所有** Go 模板都要这样处理，包括看起来无害的
`'{{.Server.Version}}'`（本身没有 `if`，但同属该模式，统一改掉以免后人踩）。

## 坑 5 — `.ps1` 没有 BOM 时按系统 ANSI 读取

**现象**：坑 4 修完之后**报错位置变了、还是同一类错误**：

```
CAUGHT: 所在位置 dev-up.ps1:83 字符: 74
+ ... 蹇呴』鏀捐繘**鍙橀噺**鍐嶄紶缁?docker inspect銆?#    鐩存帴鍐呰仈 `--format '{{if .State. ...
```

中文注释显示为乱码（`蹇呴』鏀捐繘` = 「必须放进」的 GBK 误读），
并且**乱码后的注释里仍有 `{{if ...}}` 字样**，于是触发与坑 4 相同的语法错误。

**根因**：**Windows PowerShell 5.1 在文件没有 UTF-8 BOM 时，
按系统 ANSI 代码页（本机 CP936/GBK）读取 `.ps1`**。
本仓库文件统一 UTF-8 **无 BOM**（`.editorconfig` 也是这个约定），
于是中文注释被逐字节误读。

**解决（选了方案 B）**：

- 方案 A：给 `.ps1` 加 UTF-8 BOM —— 但会破坏仓库「统一无 BOM」的约定，
  且 `git` diff 会显示奇怪的首行变更；
- **方案 B（采用）：`.ps1` 脚本内容全部改为纯 ASCII**（注释用英文），
  彻底绕开编码问题。脚本本来就是给本机用的运维工具，英文注释不影响可读性，
  也保证在任何代码页的机器上行为一致。

**教训**：写 PowerShell 脚本时，**要么纯 ASCII，要么显式带 BOM**，
不要写「无 BOM + 非 ASCII」。这一条对后续所有 `.ps1` 都适用
（`06` §六 施工纪律已回写）。

## 坑 6 — `psql -c` 多语句 + `TEMP TABLE` 跨会话

`pg-verify.mjs` 首版有 4 项失败，全部是**脚本自身**的问题，不是环境问题。

**6.1 多语句输出会带上命令标签**

```bash
psql -t -A -c "CREATE TABLE t(...); INSERT INTO t VALUES(1); SELECT count(*) FROM t;"
→ CREATE TABLE        ← 命令标签也打出来了
  INSERT 0 3
  1                   ← 这才是想要的结果
```

`-t -A` 压不住命令标签。若断言直接解析整串 stdout → `Number("CREATE TABLE\n...")` = `NaN`。

**解决**：加 `-q`（quiet）抑制命令标签；且**只取最后一行**作为结果。

**6.2 `TEMP TABLE` 是会话级的，跨 `psql` 调用必丢**

```bash
psql -c "CREATE TEMP TABLE t(...)"      # 会话 1
psql -c "SELECT * FROM t"               # 会话 2 → ERROR: relation "t" does not exist
```

每次 `docker compose exec psql` 都是**新会话**，临时表不会留存。

**解决**：把 DDL 与校验查询**合并到同一次 `psql` 调用**里（用 `;` 串联），
配合 6.1 的「取最后一行」拿到干净结果。

**6.3 扩展的 GUC 只在库被载入本会话后才注册**

```bash
psql -c "SELECT current_setting('pg_bigm.similarity_limit', true);"
→ (空 / NULL)
```

必须先在本会话调用过一次 bigm 函数，`pg_bigm.*` 参数才可见：

```bash
psql -c "SELECT bigm_similarity('abc','ab'); SELECT current_setting('pg_bigm.similarity_limit', true);"
→ 0.5
  0.3     ← 真实默认值
```

**教训**：写「SQL 可用性自检脚本」时，别把 DDL 与校验拆成两次调用，
也别假设扩展 GUC 一连接就能读。这两条已写进 `pg-verify.mjs` 文件头注释。

## 遗留与后续注意

1. **镜像瘦身已把 `pg_config` 一并删掉**（随 `postgresql-server-dev-16`）。
   运行期不需要，但**若将来要多阶段编译别的扩展，别在这之后调用 `pg_config`**。
2. **`initdb` 脚本只在空数据卷首次初始化时执行**。在已有数据的卷上补装扩展
   需要手工 `CREATE EXTENSION`（`pg-verify.mjs` 里已用 `IF NOT EXISTS` 兜底）。
3. **生产形态（app 入 compose + pg_dump 定时备份 cron）尚未落地** ——
   `02` §十二 描述的是生产编排，本步只做开发依赖（见 compose 文件头说明），
   到 P0-3 收尾时补。
4. **模型卷 `/models/bge-m3-int8` 未挂载** —— 属于 P0-1-13（embedding 双模式），
   本步不需要；届时回到 compose 加挂载。
5. 若 CI（Linux）能用官方源正常拉取，`infra/postgres/Dockerfile` 无需改动；
   镜像加速器问题只影响本机拉基础镜像，不影响构建。
