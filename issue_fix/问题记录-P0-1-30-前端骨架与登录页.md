## 1. `client.ts#isEnvelope` 把**所有错误响应**都判成畸形信封

### 现象
未登录时打开 `/`，页面永远停在 `读取登录态 · /api/auth/me`（`BootScreen`），不跳到登录页。网络面板里 `/api/auth/me` 已经是 401，响应也确实是统一信封。

### 根因
`Envelope<unknown>` 的 `code` 是 `0 | ErrorCode`：成功态是**数字 0**，失败态是**字符串错误码**（如 `'UNAUTHORIZED'`）。`isEnvelope()` 里只判断了 `typeof candidate['code'] === 'number'`，于是每个失败响应都被判成"不符合统一信封约定"，统一改写成 `INTERNAL` 错误后抛出。

`fetchCurrentUser()` 只把 `ApiError.isUnauthorized`（即 `code === 'UNAUTHORIZED'`）收敛成 `null`，但现在 code 变成了 `INTERNAL`，于是它继续上抛；而 `useCurrentUser` 的 `retry: false` 让它进入 `isError`，`data` 保持 `undefined`。

### 修复
`isEnvelope` 改为同时接受 `number` 和 `string`：

```ts
const code = candidate['code']
return (
  (typeof code === 'number' || typeof code === 'string') &&
  typeof candidate['msg'] === 'string' &&
  'data' in candidate
)
```

### 教训
信封的 `code` 是**两种类型**；写类型守卫时如果只考虑其中一种，会把另一类全部误判。这类 bug 在命令行验收里看不出来（`curl` 看到的是正确的 JSON），只有前端解析逻辑会错。

## 2. `RequireAuth` 没有处理 `useCurrentUser` 的 error 状态

### 现象
在 bug 1 存在时，页面永远停在 `BootScreen`。即使 bug 1 修复后，如果 `/api/auth/me` 因为后端没起、代理串错、网络断开等原因报错，页面仍会卡在"读取登录态"。

### 根因
`RequireAuth` 的判断只有三态：`isPending || user === undefined` → `BootScreen`；`user === null` → 跳登录页；否则放行。它没有处理 `isError`。**而 error 时 `data` 也是 `undefined`**，于是 guards 把它当成"还在问"，永远显示等待页。

### 修复
把 error 态提前，渲染一个可重试的 `SessionErrorScreen`：

- `isError` → 显示 `SessionErrorScreen`（带"重试"按钮，`refetch()` 触发）
- `isPending || user === undefined` → `BootScreen`
- 其余按原逻辑走

### 教训
TanStack Query 的五态（`pending`/`success`/`error`/fetchStatus 等）必须显式分支。`data === undefined` 同时对应"还没问到"和"问失败了"，不能只靠 `undefined` 判断。

## 3. `/health` 在 vite dev 期间没被代理到后端

### 现象
登录页左侧识别板的"服务"一行永远显示 **"服务信息未取到（/health 未响应）"**。网络面板里 `/health` 是 HTTP 200，但响应体是 `index.html`（vite 的 SPA 兜底）。

### 根因
`vite.config.ts` 的 proxy 只配置了 `/api`，但后端 `/health` **不带 `/api` 前缀**（`docs/02` §四 端点表）。请求打到 vite 自己身上，vite 作为 SPA 服务器回了 `index.html`，前端 `response.json()` 解析失败，抛出内部错误。

### 修复
在 `vite.config.ts` 的 `proxy` 里新增一条 `/health` 规则，与 `/api` 指向同一个目标。

### 教训
"请求是绿的（200）"不等于"请求打到了后端"。代理遗漏会让症状非常安静，因为浏览器拿不到错误码，只看到"数据没取到"。端测时必须看响应体，不能只看状态码。

## 4. 前端 dev 端口会**静默顺延**

### 现象
vite 默认 5173。本机 5173 常被另一个项目（`apitest-server`）占用，于是 vite 会**自动递增**到 5174，但启动日志里只会轻轻带过一句 `Port 5173 is in use, trying another one...`。结果：README、`docs/02` 的 `CORS_ORIGINS` 示例、验收脚本里的 `http://localhost:5174` 都默认你会落在 5174，而有时你其实落在 5173。

### 修复
`frontend/vite.config.ts` 把 dev 端口**钉死**在 5174，并加 `strictPort: true`：

```ts
server: {
  port: 5174,
  strictPort: true,
  // ...
}
```

端口被占时直接报错退出，不再静默顺延。5174 与 `docs/02`、`README`、`verify-app.mjs` 里的示例保持一致。

### 教训
"自动顺延"对单体项目友好，对**多项目共用的本机环境**是灾难：同一仓库在不同机器/不同启动顺序上跑在不同端口，文档里的地址就不可信了。宁可起不来报错，也别让它"看起来起来了"。

## 5. 端测时 `pnpm dev:backend` 后台任务被 kill

### 现象
用 `run_in_background` 启动的 `pnpm dev:backend` 后台任务在运行一段时间后状态变为 `failed`，13000 上的监听消失。用 `nohup`/`setsid` 等常规脱壳方式在本机沙箱里也不稳定（日志为空、端口未监听）。

### 处置
本批次端测中，重新通过 `run_in_background` 启动后端；每次执行验证前重新 `curl /health` 确认，必要时重启。后台任务特性本身不是前端代码缺陷，已记录在本文件提醒后续批次：浏览器端测前要确认 13000 真在监听。

## 6. 其他小修

- `styles/app.css` 里 `BootScreen.tsx` 引用的 `.boot` 类原本不存在，导致首帧等待页没有居中布局。补齐了 `.boot`/`.boot__line`/`.boot__box`/`.boot__title`/`.boot__lead`。
- `theme.ts` 里 `Tag: { defaultBorderColor: ... }` 是 AntD 5 `Tag` 不存在的组件 token，tsc 报错。移除该字段并加注释说明：Tag 边框色实际取自全局 `colorBorder`；后续页面真正渲染 Tag 时若需对齐原型更浅的 `--rule`，应在 `styles/app.css` 里补一条 `.ant-tag { border-color: var(--rule) }`。
