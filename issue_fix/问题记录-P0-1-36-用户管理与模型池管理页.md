## 1. ✅ 挂起项闭环之一：`manualChunks`（P0-1-32/34/35 连续挂了三批）

### 挂起的原因

包 G 从 P0-1-32 起每批的版本记录都写着同一句：
「前端产物 1xxx.xx kB，仍超 vite 500KB 告警线 ⇒ 与 `manualChunks` 一起留给 P0-1-36」。
到 P0-1-35 时单块已经 **1413.78 kB**（gzip 445.37 kB）。

### ⚠️ 三轮才找到唯一能过的分组

`manualChunks` 的坑不是"写不出来"，而是**分组落进循环依赖**，而 vite 给的报错只有 `Circular chunk: A -> B -> A`
（它不告诉你哪条 import 造成的）：

| 尝试 | 分组 | 结果 |
|------|------|------|
| 第 1 版 | `react`（react/react-dom/react-router-dom）+ `antd`+rc 一起 | `Circular chunk: vendor -> react -> vendor` |
| 第 2 版 | `antd`（核心）与 `rc`+`@ant-design/*` 分两组 | `Circular chunk: antd -> rc -> antd` |
| **最终** | `antd` = **只有 `antd` 一个包名**；`rc` = `rc-*` + `@rc-component/*` + `@ant-design/*` **同组** | **零告警** |

根因：`antd` 与 rc 系经 `@ant-design/cssinjs-utils` → `rc-util` **互相依赖**，拆开必然成环；
`react` 与 `vendor` 之间也有互相引用（`@babel/runtime` 这类运行时垫片被两边都用到）。

最终分组（`frontend/vite.config.ts`）：

```
react    ← react / react-dom / react-router-dom
antd     ← antd（**只这一个包名**）
rc       ← rc-* / @rc-component/* / @ant-design/*   （必须同组，否则成环）
markdown ← react-markdown / remark-* / micromark* / mdast-*
state    ← zustand / @tanstack/react-query
vendor   ← 其余（@babel/runtime / dayjs / classnames …）
```

⚠️ **`packageNameOf()` 必须用 `lastIndexOf('node_modules/')`** —— pnpm 的路径里会出现**嵌套** `node_modules`
（`.../node_modules/.pnpm/antd@5/node_modules/antd/...`），用 `indexOf` 取到的是 `.pnpm` 那一层，
包名会变成 `.pnpm` 之类 ⇒ 全部落进 `vendor`，而**构建照样成功**（症状只是"分了组但没人认识这些组"）。

### ⚠️ 诚实口径：拆包**不是"总量变小"**

| | 拆分前 | 拆分后 |
|---|---|---|
| 最大单块 | **1413.78 kB**（`index`，超 vite 500 kB 线 ⇒ **告警**） | **450.77 kB**（`antd` ⇒ **告警消失**） |
| 七块 raw 合计 | 1413.78 kB | **1460.38 kB**（**+46.60 kB**） |
| gzip 合计 | 445.37 kB | **456.01 kB**（**+10.64 kB**） |

**总量反而涨了** —— 跨块重复的运行时与包装代码是拆包的固有过路费。真正换到的是**缓存粒度**：
改业务代码只失效 `index`（168.04 kB / gzip 58.33 kB）这一片，
`antd`（450.77）+ `rc`（393.57）+ `markdown`（114.35）这些不常动的部分**留在浏览器缓存里**。

> 📌 **教训**：文档里写"做了拆包优化"必须跟上这几个数字，否则它会被读成"体积优化"，
> 而下一个人的合理推论是"再拆细一点还能更小" —— 那就走进死胡同了。

### 最终产物（`pnpm --filter @doubulea/frontend build`，零告警）

```
dist/assets/state-*.js       3.06 kB │ gzip:   1.45 kB
dist/assets/markdown-*.js  114.35 kB │ gzip:  32.76 kB
dist/assets/vendor-*.js    162.75 kB │ gzip:  48.20 kB
dist/assets/react-*.js     167.84 kB │ gzip:  54.55 kB
dist/assets/index-*.js     168.04 kB │ gzip:  58.33 kB
dist/assets/rc-*.js        393.57 kB │ gzip: 135.11 kB
dist/assets/antd-*.js      450.77 kB │ gzip: 125.61 kB
✓ built in 2.76s
```

## 2. ✅ 挂起项闭环之二：语法高亮 —— 本批的结论是**不做**

P0-1-32 在 `03` §4.1 里记了一条"已记录差异"：助手正文的代码块**暂缓语法高亮**，留到 P0-1-36 定夺。
本批给出结论：**不做**，理由三条（写进了 `features/chat/AssistantMarkdown.tsx` 的文件头）：

1. `01` §五 阶段一出口验收**不含**这一项（它是体验项，不是功能项）；
2. 它要再引一套高亮依赖（`shiki` / `prism` 这级别的体积），换来的是观感；
3. **接回点是一个组件的 `<code>` 渲染分支** —— 日后想加随时能加，**不需要改数据流**。

> 📌 **这是一条"主动的不做"，不是"漏做"**：有理由、有接回点、有落档。
> 与"暂时先这样"的区别就在于，下一个人看到它时知道**这是决定，不是欠账**。

## 3. ⚠️ 新识别风险一：Key 掩码被回填进编辑表单 ⇒ 用户把掩码当新 Key 存进去

### 现象（如果照直觉实现）

Provider 列表要显示"这个 Provider 配没配 Key"，接口回的是 `hasKey` + `apiKeyPreview`（形如 `sk-****abcd`）。
编辑弹窗的直觉写法是"把这条记录填进表单" —— 于是 Key 输入框里出现 `sk-****abcd`。
用户改完名字点保存 ⇒ 请求体里带着 `apiKey: 'sk-****abcd'` ⇒ **后端照存**（它有长度、非空、完全合法）
⇒ 下一次真的去调这个 Provider 时，用的 Key 是那串掩码 ⇒ **401**。

### 为什么"不报错"这件事最贵

- 保存那一刻**一切都是绿的**（200 + "保存成功"）；
- 掩码看起来就像个 Key（`sk-` 开头）；
- 真正炸的时候（调用上游 401）已经隔了好几屏，很难联想到"三天前改了个名字"。

### 处置（两边各一半，缺一不可）

**① 表单初值 `apiKey` 恒为空串**（`providerEditValuesOf()`）——
"Key 有进无出"在界面侧的**落地点就是这一行**。J4 / D8 两条断言从源码与纯函数两侧守它。

**② 三态意图由纯函数判**（`providerKeyIntent`）：

| 表单状态 | 意图 | 请求体 |
|---|---|---|
| 输入框有值 | `set` | `apiKey: <trim 后的值>`（**输入优先**，哪怕同时点了「清除 Key」） |
| 输入框空 + 勾了「清除 Key」 | `clear` | `apiKey: null` |
| 输入框空 + 没勾 | `keep` | **不带 `apiKey` 这个键** |

⚠️ **注意 `clear` 与 `keep` 的区别是"带不带这个键"**：空串在契约层是**非法值（400）**，
所以"留空"无论如何都不能原样发出去 —— 它必须被翻译成"不带键"或"显式 `null`"。
D4/D5/D6 三条断言分别钉住这三态。

## 4. ⚠️ 新识别风险二：模型池的第三条缓存键漏失效 ⇒ 智能体编辑页的下拉永远是旧的

### 现象

模型池页面写操作（建/改/删 Provider、建/改/删模型）之后要刷新三处视图：

```
['admin','model-providers']     ← 本页 Provider 表
['admin','models']              ← 本页模型表
['models','available','CHAT']   ← **智能体编辑页的模型下拉**（跨页共享，本批之外）
```

前两个在写模型池时"顺手就会想到"，第三个**不在本页** ⇒ 极容易漏。

### 症状

改了模型池（比如停用一个模型），回到智能体编辑页 —— 下拉里**还是有它**，选中保存 ⇒ 后端 409/业务错误。
中间**没有任何报错、没有黄条**，用户只会觉得"这软件有毛病"。

### 处置

三条键的失效**收进一个函数**：`api/modelPool.ts#invalidateModelPoolViews(queryClient)`，
六个写操作调用点全部走它。J5 断言"这个函数里三个键都在"。

> 这里不是"写两处"，而是"**该写三处却只写了两处**" —— 同样是靠"把判断收进一处"来防：

## 5. 顺手收敛：`isTypedConfirmMatch`（第四个消费方出现时合并）

P0-1-31（智能体）、P0-1-34（会话）、P0-1-35（知识库）各自写了一遍"输入名称/词逐字确认"的判断。
本批的 Provider 删除**也要一份** —— 第四个消费方。此时不收，就是第四份拷贝。

处置：抽到 `app/confirm.ts`：

```ts
export function isTypedConfirmMatch(typed: string, expected: string): boolean {
  return typed === expected
}
```

四处（会话 / 智能体 / 知识库 / Provider）全部改为委托。
⚠️ **它刻意不做 `trim`**（"多一个空格也不算"是这四处的共同口径，也是那条"逐字"的全部意义）。
J1 断言定义**全仓恰好一处**、J2 断言四个消费方**都在委托**（不是各自实现）。

> 📌 这里有个反直觉点值得记：这个函数**只有一行**，所以很容易觉得"抽出来没意义"。
> 但它的价值不在实现，而在**判据的唯一性** —— 删掉 `trim` 那天，只需要改一处。

## 6. 十条交互规范落实（`03` §七）—— 三处对原表的收窄

逐条落实记录见 `docs/03` §七「P0-1-36 落地增量」。这里只记**三处与 `03` 原表的差异**，
它们的共同点是**"照着原表写会写出错的东西"**：

| # | `03` §七 原文 | 本批实际做法 | 为什么 |
|---|---|---|---|
| 1 | 表格规范含"删除放最后" | **用户列表没有删除项**（三件操作：编辑/停用启用/重置密码） | `P0-1-9` **只给了启停、没有 `DELETE /api/users/:id`** ⇒ 摆一个点下去必失败的入口，比没有入口更糟（**没有能力就不摆入口**） |
| 2 | 表格规范允许排序 | **模型表一个 `sorter` 都没挂** | 该表用 `rowSpan` 合并同 Provider 的行；挂 `sorter` 会让同 Provider **不再相邻** ⇒ 合并立刻变错（行高串位、数据错位），而**代码不报错** |
| 3 | 键盘约定：`Esc` 关闭弹窗与抽屉 | **`InitialPasswordModal` 刻意不响应 `Esc`** | 这是新账号密码**唯一一次**明文出现；误触关掉就永久拿不回来（`closable`/`maskClosable`/`keyboard` 全 `false`） |

> 📌 三处的共同模式：**"通用规范"落到具体页面时，要先问一句"这个页面的数据允许我这么做吗"**。
> 表里那一栏在别的页面都对，只在"数据源不支持某个能力"或"某个能力会破坏本页的另一个不变量"时错。

## 7. 其余值得记的口径（简）

- **"不能操作自己"的判据是"是不是自己"（id 相同），不是"是不是 ADMIN"** —— 第一个 ADMIN 停不动自己、
  却能停**另一个** ADMIN，这是**正确行为**（同 `P0-1-8`：防自锁只针对自己）。UI 层对着 `/api/auth/me`
  把三件事（停用/降级/重置自己密码）分别禁用 + 给理由，而不是让用户点下去吃一个 409。
- **"什么也没改 ⇒ 不发请求"只许一处来源**：三个 `build*Body()` 在无改动时返回 `null`。
  ⚠️ 必须**逐字段比较** —— 不能靠"用户有没有敲键盘"，更不能"反正后端幂等、发了也没事"
  （后者会每次刷新 `updated_at`，把列表排序搅乱）。
- **三态字段要能表达"清空"**：`maxContext` 清空输入框 = `null`（不限制），与"没动这个字段"是两件事；
  清空要**显式发 `null`**（同 P0-1-35 的 `description`）。
- **删除 Provider 弹窗只报"将同时删除 N 个模型"**（N 来自列表行数），**不报智能体引用数** ——
  那个数在 Provider 端点上**拿不到**。这是同一原则的**第三次应用**（P0-1-34 删会话给不出消息条数、
  P0-1-35 不显示全库 chunk 总数）：**"界面上有数字" ≠ "能拿到这个数字"**。
- **一次性密码的复制文本要带账号**（两行：用户名 + 初始密码）—— 只给密码，转交时对方不知道该配哪个号；
  C4 断言这一点。
- **`maxContext` 的界面上限（1 ~ 1000 万）与 `shared` 的 `maxContextSchema` 同源**（F1 断言），
  不在这里手写第二份数字。
