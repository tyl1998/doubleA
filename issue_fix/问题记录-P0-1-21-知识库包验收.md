## 坑 1 ⚠️ "前面每一档都绿"不等于"串起来还成立"：R4 的"检索返回 v2"必须**换真端点重验**

**问题**：P0-1-19 验收 B 组那条"覆盖重建后检索返回 v2"的原始写法是 ——
用 `<=>` 近邻 SQL 直接问库（"拿 v2 块自己的向量查，最近邻是它自己"），并在注释里写明
**"P0-1-20 才有检索端点"**。这在当时是**诚实的等价取证**，但它证明的是"向量与内容是对应的"，
而不是"检索端点会返回 v2"。

**更隐蔽的一层**：本批第一版把这条重写成"检索命中的那块**正文里含 `v2` 标记**"。
这依然是**弱断言** —— 一个"新旧两份 chunk 都留着"的坏实现（双写没删旧、或 `DELETE` 漏了）
照样会让 v2 的块被搜到并含 `v2` 字样，那条断言全绿。

**对策**：改成**方向相反的一对**断言：

1. **新关键词命中 1 条**，且命中的 `chunkId` **必须在"重建之后写入的那一批 id"集合里**
   （拿重建前后两次 `chunkRowsOf()` 的 id 集合对照）；
2. **v1 的关键词查不到（0 条）** —— 这一条才真正排掉"新旧共存"。

顺带把 `v2` 的正文写成"删掉了 v1 的第二句"，让"旧内容不在索引里"这件事在**内容层面**也成立。

> 通用教训：**凡是"换了新版本"的验收，都要有一条"旧版本查不到了"的断言**。
> 只验"新的在"是无法区分"替换"与"追加"的 —— 这与 P0-1-19 记过的"删得掉证据"是同一族。

## 坑 2 ⚠️ `getObject` 对不存在的键**不在 `await` 时抛错**（错误发生在读流时）

**问题**：下载端点最自然的写法是

```ts
const body = await s3.getObject(bucket, key)   // ← 不存在的键这里**不会**抛
reply.header(...).send(body)
```

`getObject` 返回的是一个 `Readable`，`NoSuchKey` 是在**读这个流的时候**才发生的。于是：
响应头（含 `200`）已经发出去了，流一读就炸 ⇒ 客户端看到的是"下载到一半断了"，
而不是"这个文件不存在"。**这类错误最难查**：日志里是一条流错误，用户描述是"下载坏了"。

**对策**：**先 `statObject` 再 `getObject`**：

```ts
const stat = await s3.statObject(bucket, key)  // ← 这里抛 NoSuchKey，可以干净地回 404
...
const body = await s3.getObject(bucket, key)
```

代价是两次往返，换来的是"最常见的失败（对象没了）能回一个干净的 404 信封" + 顺手拿到
`Content-Length`。判定"对象不存在"写了一个 `isNoSuchKey()`：看 `code` 之外**再兜一层 message**
（自建 MinIO 回 `NoSuchKey`，某些 S3 兼容实现回 `NotFound`/`NoSuchBucket`；
`instanceof` 跨包不可靠，与 `hasPrismaCode` 同款）。

⚠️ **边界如实写在注释里**：`stat` 与 `get` 之间仍有 TOCTOU 窗口（对象在这两步之间被删），
那时流会报错、而响应头已经发出 ⇒ **只能断流**。流式响应的这个固有边界**不假装能回 JSON**。

## 坑 3 ⚠️ 下载是**唯一不返回 `ok()` 信封**的端点 —— 不显式说明就会被下一个照抄的人包起来

**问题**：本仓其余所有端点都返回 `{code, msg, data}`。下载成功时返回的是**字节流**，
如果它也被包进信封，客户端拿到的会是"一个 JSON 文件"（而且"下载下来的文件打不开"这种现象
很容易被归咎到存储或编码上）。

**对策**：三处显式写清 ——
① 路由注释里写"成功回字节流、**失败仍然是标准信封**（404/500 是 JSON）⇒ 客户端要按状态码分支"；
② `02` §4.6 的契约表里标注；
③ README 手工端测 ⑬ 里写"这是唯一不套信封的端点"。

**验收**：`verify-documents` 的 G 组同时断言"成功时 `content-type` 是文件的类型（不是
`application/json`）"与"失败时是 JSON 信封（`response.json().msg` 可读）"—— **两侧都断言**，
才能守住"失败也走信封"这条。

## 坑 4 ⚠️ `Content-Disposition` 是纯函数，但**错了不会报错**：中文名、头注入、RFC 5987 的四个字符

三件互相独立的事挤在同一个头部里，写错的症状都只是"另存为的文件名不对"（或者更糟）：

| 事 | 写错的后果 | 对策 |
|----|-----------|------|
| 只给 `filename="..."`（不给 `filename*`） | 中文名变 `______.pdf`（ASCII 回落规则生效） | **RFC 6266 双写**：`filename="<ASCII 回落>"; filename*=UTF-8''<百分号编码>` |
| CR/LF 不剔除 | **响应头注入**（`a\r\nX-Evil: 1` 能加出一个新头部 → 响应拆分） | 控制字符**删掉**（不是转义 —— CR/LF 在头部里没有正当用途）；引号/反斜杠/路径分隔符替换成 `_` |
| 只依赖 `encodeURIComponent` | `'` `(` `)` `*` 这四个字符**不会被转义**，而 RFC 5987 的 `attr-char` **不含**它们 ⇒ 头部在某些客户端上解析失败 | 编码后再补一轮 `['()*] → %XX` |

**验收**：五组边界全在**无依赖档**（`verify-app` 第 23 节）：中文名可 `decodeURIComponent` 还原、
ASCII 回落**逐字期望值**（`报销制度（2026版）.pdf` → `_____2026__.pdf`，即"非 ASCII→`_`、ASCII 原样"）、
空名回落 `document.bin`、注入用例**必须单行**、路径分隔符不残留、四个特殊字符被编码后仍能解回原名。

> 为什么把它们放进"无依赖档"：这些规则**不依赖任何外部件**，而且是"错了不会 400、只会静默错"的
> 典型 —— 与 P0-1-18 把分块策略做成纯函数是同一条理由。

## 坑 5 两条**产品口径**要在文档里，而不是只在代码注释里

- **列表排序 `createdAt desc`（刻意与 `/api/users`、`/api/models`、`/api/knowledge-bases` 相反）**：
  文档是"边用边传"的，`asc` 会把刚上传的那篇压到最后一页 ⇒ 用户以为"上传没成功"（而它其实在 `PARSING`）。
  **不按 `updatedAt` 排**：覆盖重建会改它，一篇正在重建的文档会在用户翻页的过程中"跳到最前面"，
  看起来像列表自己在动。
- **库不存在 → 404 而不是空列表**：`{items: [], total: 0}` 会让前端分不清"库没了"（该跳回列表页）
  与"库里没文档"（该显示上传引导）。

两条都写进了 `02` §4.6 的契约表与 `verify-documents` 的断言（"库不存在 404"那条断言的名字里
就写着"不是空列表"）。**只写在代码注释里的口径，下一个人会按"直觉"改回去。**

## 坑 6 `PARSING` 的提示不是"提示文案"问题，而是**判据归属**问题

`06` P0-1-19 的坑预判写的是"列表端点必须把 `PARSING` 显示成「更新中，暂不参与检索」"。
本批落地时发现：真正要收在 `shared` 的**有两样东西**，而不只是一句话 ——

1. `DOCUMENT_PARSING_HINT`：用户看得见的那句话（前后端共用，免得两边各写一遍然后漂）；
2. `isDocumentSearchable(status)`：**"能不能被检索到"的判据**。它是 `READY`，
   但这条语义**变过一次**（P0-1-17 时 `READY` 只是"解析完成"，P0-1-19 起才是"可检索"）——
   因此不能让它退化成散落各处的 `status === 'READY'` 字面量比较。

并且断言里显式钉了一条**否定**：这句提示里**不能出现"失败"**（`PARSING` 是我们还在干活、
`FAILED` 才要人介入，两者混成一种样式会让用户去重试一件正在正常进行的事）。
