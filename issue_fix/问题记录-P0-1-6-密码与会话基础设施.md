## 坑 1 — bcrypt 对非法摘要的 `compare` 立刻返回 false，等时比较静默失效

**现象（实测）**：想给 `DUMMY_PASSWORD_HASH` 找一个"已知不可能匹配"的常量，第一版随手写了

```ts
export const DUMMY_PASSWORD_HASH = '$2b$12$0BQ9YF3S4S1oQ7wQ0iW3F.PnP1Zk5n7M6pJ0Ccz1Y6yRk7Qxk8yGe'
```

跑一下最小验证才发现问题：

```bash
$ node -e "require('bcrypt').compare('wrong', '<合法摘要>').then(r => ...)"
compare(valid, wrong)         = false  225ms     ← 正常：跑完了 cost 12
compare(invalid-hash, wrong)  = false    0ms     ← ⚠️ 立刻返回，压根没跑 bcrypt
```

**根因**：bcrypt 会先看摘要的前缀/长度等结构。结构不合法时它**不抛错、也不计算**，
直接返回 `false`。于是那句"用常量摘要跑一次以对齐耗时"完全没发生 ——
**账号不存在**（不跑 bcrypt，0ms）与**账号存在但密码错**（跑 bcrypt，225ms）的耗时依旧差 200ms 以上。

**为什么危险**：这个缺陷**没有任何报错**。它不会让任何功能坏掉，只会让
`01`/P0-1-7 验收里的「错误密码提示明确且**不泄露账号是否存在**」悄悄变成假命题 ——
靠"看代码/看功能"永远发现不了，只能靠实测耗时。

**对策**：

1. 常量改为 `bcrypt.hash(随机串, 12)` 的**真实产物**（本仓用的是 `$2b$12$zdC1OsUBJBssxoQb.pWB8.5zDJN1iF24HCU5a1Nqy3/pUgi65oM4W`），并注明"必须是结构合法的摘要，否则等时比较失效"。
2. `verify:app` 增加断言守住它的形态：`startsWith('$2b$12$')`、长度 60、对空串与自身都返回 `false`。
3. 顺手确证了另一条边界：**摘要本身损坏时 `verifyPassword` 返回 `false` 而不是抛错** ——
   库里若存了脏数据，让登录以"密码错误"结束好过 500（后者会把"数据坏了"包装成服务故障）。

## 坑 2 — bcrypt 静默截断 72 字节

**现象**：`bcrypt.hash('a'.repeat(72) + 'x', 12)` 与 `bcrypt.hash('a'.repeat(72) + 'y', 12)` 的校验结果相同 ——
第 73 个字符起被忽略。

**为什么本项目的概率不低**：密码是**中文**输入的场合，一个字符 3 字节，
`'中'.repeat(25)` 就已经 75 字节。用户在密码框里贴一句中文短语就可能踩上，
而且现象是"后半段随便改都还能登录"，属于不会有人举报、但说不清的那类问题。

**对策**（两条刻意相反的处理）：

- **写入侧严**：`hashPassword` 按 `Buffer.byteLength` 判断，> 72 字节直接抛 `RangeError`，
  消息里点明上限与"bcrypt 会静默忽略超出部分"。让密码策略在路由层显式解决。
- **校验侧松**：`verifyPassword` **不做**长度判断 —— 否则超长输入的登录会与"密码错误"
  走不同分支（报 RangeError → 500），等于从报错形态泄露了密码长度特征。

## 坑 3 — 原生依赖不一定需要编译器（bcrypt 自带 prebuilds）

**结论先写**：`bcrypt@6.0.0` 的 `scripts.install` 是 `node-gyp-build`，**但包里自带 `prebuilds/`**：

```
package/prebuilds/darwin-arm64/bcrypt.node      package/prebuilds/win32-x64/bcrypt.node
package/prebuilds/linux-x64/bcrypt.glibc.node   package/prebuilds/linux-x64/bcrypt.musl.node
（共 9 个平台文件）
```

`node-gyp-build` 只负责把对应平台的那个 `.node` 挑出来，**不触发编译**，
所以「双平台（Windows 施工机 + macOS）都得装 C++ 工具链」这个担心不成立。
但仍**必须登记 `allowBuilds`** —— 未登记会以 `ERR_PNPM_IGNORED_BUILDS` **报错退出**
（与 `esbuild`/`prisma` 同款机制，见 `docs/06` §六 第 22 条）。

**验证手法（值得复用）**：判断一个包要不要登记、要不要编译器，不要靠猜 ——
`npm pack <pkg>@<ver>` 解开看 `scripts.install` 与有没有 `prebuilds/`：

```bash
$ npm pack bcrypt@6.0.0 && tar -tzf bcrypt-6.0.0.tgz | grep -i prebuild
```

装完的实测：`node_modules/bcrypt install$ node-gyp-build` → `Done`（无编译输出），
`hashPassword` cost 12 本机耗时 **≈225ms**。

## 坑 4 — `Packages: +6 -72` 不是依赖树坏了

**现象**：`pnpm --filter @doubulea/backend add bcrypt @fastify/cookie` 成功，但汇总行是
`Packages: +6 -72`；随后每次 `pnpm install` 仍打印 `Packages: -72`。

## 坑 5 — `@fastify/cookie` 取不到 `CookieSerializeOptions` 这个名字

**现象**：按习惯写

```ts
import cookie from '@fastify/cookie'
const OPTIONS = { … } as const satisfies Partial<cookie.CookieSerializeOptions>
//                                        ~~~~~~~~~~~~~~~~~~~~~~~~~~~~  TS2503: Cannot find namespace 'cookie'
```

**根因**：该包（v11.1.2，`"type": "commonjs"`、无 `exports` 字段）用的是 `export = fastifyCookie`
形态 —— 类型定义在 `fastifyCookie` **命名空间**里，默认 import 拿到的是值而不是命名空间，
所以 `cookie.XxxType` 这种写法不成立。

**对策**：类型从它自己给 `reply.setCookie` 声明的参数上取，既绕开命名空间，又让 `satisfies`
真的生效（属性名写错会在编译期报错）：

```ts
type SessionCookieOptions = NonNullable<Parameters<FastifyReply['setCookie']>[2]>
const SESSION_COOKIE_OPTIONS = { path: '/', httpOnly: true, sameSite: 'lax', secure: … } as const satisfies Partial<SessionCookieOptions>
```

## 坑 6 — `decorateRequest`/`decorate` 不能走 `register`

**现象**：把会话装饰器写成 `app.register(sessionPlugin)` 时，`app.requireAuth` 在根作用域
路由上不存在（报 `requireAuth is not a function` 或被 Fastify 判为未装饰）。

**根因**：Fastify 的 **封装（encapsulation）** 边界 —— 经 `register` 装载的插件里做的装饰，
只对该插件**子树**可见。这与 P0-1-4 撞过的 `setErrorHandler` 是同一个机制。

**对策**：`installSession(app)` 直接调用，内部只把 `@fastify/cookie` 交给 `register`：

```ts
export function installSession(app: FastifyInstance): void {
  void app.register(cookie, { hook: 'onRequest' })   // 插件 → 队列（ready() 时装载，早于路由 preHandler）
  app.decorateRequest('auth', null)                  // 装饰器 → 必须直接调用（根作用域）
  app.decorate('requireAuth', requireAuth)
  app.decorate('requireAdmin', requireAdmin)
}
```

**顺带记两条**：① `decorateRequest` 的默认值用 `null` 而不是 `undefined`（`request.auth === null`
才有明确语义）；② `@fastify/cookie` 用 `hook: 'onRequest'` 解析，因为 `requireAuth` 是
`preHandler`，晚于 `onRequest`。

## 坑 7 — 会话令牌「不需要签名」

**背景**：`02` §十 写的是「HttpOnly + SameSite=Lax Cookie + Redis 存储」，没提签名。
写代码时的直觉是"Cookie 里的令牌当然要签名/加密"，容易自己加上一道。

**想清楚后的结论**：签名能证明的只有"这串没被客户端改过"。而本项目的判定逻辑是
`session:{sid}` 这个 **Redis 键是否存在** —— 客户端把值改成一个无对应键的随机串，
结果一样是"无会话"。所以签名**不增加任何安全属性**，只多出一个需要轮转的密钥
（以及"密钥一换，所有在线用户被踢"的运维负担）。

**真正需要的是熵**：令牌是 `randomBytes(32).toString('base64url')`（256 bit，43 字符），
暴力猜中的概率可忽略。**这一点写进注释**，免得后人"顺手加强度"。

## 坑 8 — 60s 缓存窗口的验收陷阱（坑预判的正面落地 + 两次踩到）

`06` 的坑预判写的是「60s 缓存的失效窗口与『立即失效』验收口径冲突 → 停用操作**主动删缓存**」。
本批把这句话落成两件事，并**在验收脚本里两次踩到它**：

**踩法一（脚本自身）**：写入 `DUMMY` 之外的"停用后立即断言 401"用例时，
`prisma.user.delete()` 之后**立刻**打请求 —— 拿到的是 **200**。原因是快照缓存
（`auth-user:{userId}`）里还留着那位用户"存在且 ACTIVE"的记录，窗口没过就命中缓存。
**结论：验收用例必须与缓存窗口对齐**（要么先失效缓存，要么等过窗口）。

**踩法二（区分两条路径）**：最终把验收拆成两条**互补**用例，恰好把机制讲清楚：

| 用例 | 操作 | 期望 | 说明 |
|------|------|------|------|
| 主动失效 | 停用 + `invalidateUserSnapshot(userId)` | **下一个请求就 401** | P0-1-8 的启停/改角色/重置密码**必须**这么写 |
| 兜底窗口 | 停用但**不**失效缓存 | 窗口内仍 200 → 窗口过后 401 | 缓存只兜底"有人直接在库里改状态" |

脚本把 `USER_STATUS_CACHE_TTL_SEC` 压到 1s（配置项，机制与生产 60s 完全相同），
否则这条用例要跑一分钟。**这两条同时存在**才是完整结论：只验"立即 401"会掩盖
"写侧忘了失效"的回归（那时表现是"偶尔还能用一会儿"），只验"等窗口"又会放过性能与体验问题。

**连带的两个设计取舍**（都写进代码注释与 `02` §10.1）：

- `invalidateUserSnapshot` 写失败**向上抛**，而 `writeUserSnapshot` 失败**只告警** ——
  失效是正确性要求，缓存只是性能优化；反过来会让写侧以为"已经立即生效"。
- 快照缓存存的是**整份用户信息**（`id/username/role/status/mustChangePassword`）而不是只存
  `status`：`role` 是 `requireAdmin` 用的、`mustChangePassword` 是 P0-1-7 首登闸门用的 ——
  只缓存 status 的话其余字段每请求仍要回库，等于没缓存。

## 坑 9 — 「会话存储不可用」= 500，不是 401

**要定的是什么**：Redis 挂掉时，一个带着有效 Cookie 的请求该得到什么？

**选择 500（`INTERNAL`）**，理由三条：

1. **语义**：这是"服务端此刻给不出结论"，不是"你的凭据不对"。映射成 401 等于对用户撒谎。
2. **后果**：401 会让**所有在线用户**被前端踢回登录页（还以为自己会话过期），
   而他们重新登录也登不进去（Redis 还是挂的）—— 把依赖事故放大成全员登不进去。
3. **可观测**：运维只会在日志里看到 401（正常的鉴权拒绝），而不是 5xx，
   容易把依赖事故当鉴权问题去查。

**配套的一条**：「无 Cookie」这一条路径**刻意不碰 Redis**，直接 401。
理由：匿名/探测请求不该打在依赖上（也避免了"Redis 挂了导致匿名请求也 500"的放大）。
这条在 `verify:app` 的两种模式下都有断言：本机（依赖在线）→ 401；CI（依赖不可达）→ 401。

**另外**：鉴权失败时一律**自毁会话**（删 Redis 键 + 清 Cookie）—— 会话不存在/过期、
用户已删、`status=DISABLED` 三种情况都如此。客户端那枚 Cookie 已经没有意义，
留着只会让每个请求重复走一遍失败路径。
