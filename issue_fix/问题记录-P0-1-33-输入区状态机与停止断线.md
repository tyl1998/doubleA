## 0. 一句话结论

本批的头号风险**不是**"按钮点不亮"，而是**两个"看不出在动"的空窗**：

> 按下发送到这一轮真正建立之间（`sending`）、点过停止到收到收口之间（`stopping`）——
> **这两段时间在界面上长得和 `idle` / `streaming` 一模一样，但对"能不能再发一条"的答案完全相反。**

把它们并进相邻状态，得到的不是"少一个状态"，而是两个具体事故（见 §1）。
其余四条（停止时序、失败分两个通道、黄条住 store、对齐判据）都是**顺序即正确性**类的结论。

## 1. ⚠️ `sending` 窗口并进 `idle` ⇒ 按两次回车建出两个会话（本批最大的坑）

### 现象

`submit()` 的第一版：

```ts
const text = draft.trim()
if (text === '' || streaming) return
setDraft('')                    // ← React 状态更新是异步的：这一次 render 里 draft 仍是旧值
const outcome = await send(text)
```

从"按下发送"到 `useChatStream` 把这一轮写进 store 之间，要做两件事：**（首条消息时）创建会话** +
**建立流**。这段窗口里 `round === null` ⇒ 按三态机（`idle`/`streaming`/`confirm`）判定，它就是 `idle` ⇒
发送按钮**是亮的**、`Enter` **是通的**。

于是：用户连按两次回车（或手快点两下）⇒ 第二次进入时 `draft` 还没被清空（`setDraft('')` 要到下一次
render 才生效）⇒ **同一句话发两遍**，而且首条消息时**建出两个会话**。

### 根因

把"没有进行中的轮次"当成了"空闲"。但"空闲"的完整含义是
**"现在按发送，会且只会产生一轮新的"**——`sending` 窗口不满足：此时再发一次，产生的是**第二轮**（或第二个会话）。

### 修复

状态机落成**五态**，把空窗显式建出来（`features/chat/composerState.ts`）：

| 状态 | 含义 | 发送 |
|------|------|------|
| `idle` | 没有进行中的轮次，且没有正在建立/收尾的 | ✅ |
| `sending` | 按下发送 → store 里出现这一轮之间（建会话 + 建流） | ❌ |
| `streaming` | 这一轮在生成中 | ❌（**输入不禁、只禁发送** — `03` §4.1 原文） |
| `stopping` | 点过停止，正在等 `done{STOPPED}` 的窗口 | ❌ |
| `confirm` | 有工具确认卡待处理 | ❌（**输入也锁** — `03` §4.1 原文） |

优先级 `confirm > stopping > streaming > sending > idle`：**顺序即正确性**，四条都有真实错法
（例如把 `stopping` 排在 `streaming` 后面 ⇒ 停止窗口里按钮显示回「停止」⇒ 用户以为没点上而反复点）。

### 为什么不能靠"防抖 / 禁用 500ms"绕过

那样是把正确性寄存在时序上：网络慢时窗口更长，禁用时间还是不够。**状态是唯一的事实来源**，
窗口由事件驱动关闭（`send()` 一返回就退出 `sending`），与时序无关。

## 2. ⚠️ `/stop` 的响应 schema 被重复定义了一份（`tsc` 当场拦下）

### 现象

本批第一次给前端加 `/stop` 的类型，顺手在 `shared/src/conversation.ts` 写了：

```ts
export const stopConversationResultSchema = z.object({ id: z.string().uuid(), signaled: z.boolean() })
export type StopConversationResult = z.infer<typeof stopConversationResultSchema>
```

`pnpm -r typecheck` 立刻红：

```
error TS2308: Module './sse' has already exported a member named 'stopConversationResultSchema'.
               Consider explicitly re-exporting to resolve the ambiguity.
```

### 根因

`shared/src/sse.ts` **在 P0-1-26 就已经定义过同一份**（停止是 SSE 出口层的能力，写在那里很自然）。
本批是它**第一个前端消费方**，于是产生了"第二个使用方"的错觉 —— 实际上使用方多了不等于该有第二份定义。

### 修复

删掉 `conversation.ts` 里的那一份，前端 `request<StopConversationResult>()` 的泛型直接从 `@doubulea/shared`
取（`sse.ts` 里已有的）。**净新增契约 0 处。**

### 可复用的教训

> **「同一口径两处各写一遍」在 TS 里通常能被 `TS2308` 抓到，但只在"同名字导出"时。**
> 名字不同、形状相同的重复（如 P0-1-29 那次）编译器抓不到 —— 只能靠"同一件事只写一份"的纪律。

## 3. ⚠️ 停止时序：`03` §4.1 原文漏了"`POST /stop` 自身失败"这一路

### `03` §4.1 原文（五行）

```
点停止 → POST /stop → 等 done{STOPPED} 收口 → 5s 未收口才 abort fetch → 随后拉历史对齐
```

### 缺的一路

`POST /stop` **自己**可能失败（会话被别人删了 404 / 网络断了 / 未登录过期 401）。按原文照做，
结果是：**没等到 `POST` 的响应就不进入 5s 窗口**（不知道窗口该不该开），按钮停在「停止中的…」
⇒ 用户看到的是一个**点了没反应的按钮**，而且这一轮还在服务端继续生成。

### 定案（本批补，并写进 `03` §4.1 落地增量）

`stopController.ts` 把它做成**第四条路径**，与另外三条并列：

| 路径 | 触发 | 动作 |
|------|------|------|
| `settled` | 窗口内等到 `done{STOPPED}` | 对齐，**不 abort** |
| `settled-locally` | 5s 未收口 | **abort** 兜底 + 客户端侧标"已停止" + 对齐 |
| `stop-request-failed` | `POST /stop` 返回失败 | **不等窗口**，直接 abort + 对齐 |
| `nothing-to-stop` / `already-running` | 幂等 | 不重复 POST（`signaled:false` 也照样走窗口） |

理由：**"点了没反应的按钮"比"提前丢掉尾巴"更坏** —— 后者用户至少看到内容停了；前者用户不知道
该继续等还是重试。而 `POST /stop` 失败时，服务端**本来就已经**可能收不到停止信号了（`signaled`
的价值只在于文案），所以主动 abort 是唯一能立刻恢复可用状态的动作。

### 可复用的教训

> **文档写的时序是"主路"，不是"全部路径"。** 落地时必须问一句：**这一步自己失败了怎么办？**
> 答案通常就是核心状态机的第 N+1 条分支（对照 P0-1-25 的"流刚好结束"竞态）。

## 4. ⚠️ 断线黄条必须住在 store 里、不能挂在轮次上

### 一个反直觉的顺序问题

点黄条 = **对齐历史**，而对齐的结论之一就是"服务端存下来了 ⇒ **丢掉流式轮次**"。
若黄条的数据挂在轮次上（`round.disconnect`），那它会在**用户点它的同一瞬间**随轮次一起消失：

```
用户点黄条 → align() → 条数 +1 → 丢轮次 → round = null → 黄条跟着没了
```

用户看到的是"我点了一下，提示没了"—— **但到底对齐了没有、对齐成了什么，页面上没有任何证据。**

### 定案

黄条状态（`{ reason, extra }`）放进 `stores/chatStream.ts`，**与轮次的生命周期解耦**：

- 轮次该丢就丢（避免同一轮渲染两遍）；
- 黄条**留到调用方显式清**（`align()` 成功返回后清）⇒ "对齐完成"这个动作有可见的收尾。

### 形态

黄条是**整条可点的 `<button>`**（不是 `<div onClick>`）—— 键盘可达、`aria` 语义正确，且 `:disabled`
在 `aligning` 期间真的挡住重复点击。CSS 侧要**把浏览器给按钮的默认外观全部抹平**，否则它会显示成
一个圆角小按钮而不是通栏提示条（`.banner` 一节，无 `.ant-*` 选择器 ⇒ 按 P0-1-31 定案**不需要**
`:root` 前缀）。

## 5. 失败分两个通道：`errorSource` 落在轮次上

P0-1-32 只有"服务端流内 `error`"一个入口，本批多了两个客户端侧入口（读流失败 / 连接中断 /
停止超时），于是必须回答：**它们该不该弹 toast？**

| `errorSource` | 来源 | 出口 |
|---------------|------|------|
| `'server'` | 流内 `error` 事件（含 `CONFLICT`） | **toast + 消息流内错误卡**（`03` §五 原文） |
| `'client'` | 读流失败 / 连接中断 / 停止超时 | 错误卡 + **顶部黄条**，**不弹 toast** |

理由：`'client'` 的黄条自带一句**可操作**的"点此对齐"；再叠一个 toast 说明同一件事，会把用户
的注意力从"点哪儿"引到"又报错了"。**三处同时喊同一件事，等于哪一处都没说清。**

## 6. 「点击黄条对齐」的判据 = 助手消息条数有没有增加

对齐本身只是"重拉历史"（`useConversationMessages` 的 `invalidate` + `refetch`），但拉回来之后必须回答：
**本地那份流式版本还要不要？**

- 服务端**存了**（助手消息条数 +1）⇒ **丢掉**本地流式版本（否则同一轮渲染两遍 —— 一遍来自流、
  一遍来自历史）；
- 服务端**没存**（条数不变）⇒ **保留**（本地那份是唯一副本，丢掉就是内容真的没了）。

`done` 那条路仍走 P0-1-32 的 `done.messageId` **精确**让位（比"条数"更准，因为 `done` 一定带 id）。
两条规则分工写在 `ChatPage.tsx` 文件头：**有 id 用 id，没 id 用条数**。

⚠️ 顺带定案：**没落库的轮次（`persisted === false`）永远不丢** —— 它本来就不在历史里。

## 7. 验收档本批新增了什么（H / I / J 三组）

| 组 | 守什么 | 条数 | 关键取巧 |
|----|--------|------|----------|
| **H** 输入区状态机 | 五态都可达 / `label === state` / 占位符与提示行两两不同 / **只有 `idle` 能发送** / 键盘判据（`Enter` 发、`Shift+Enter` 换行、**`isComposing` 一律不发**） | 9 | "五个状态的集合语义"用**排序后比**（`06` §六 第 ⑤ 条），不依赖枚举顺序 |
| **I** 停止时序 | 四条路径各一条 / **窗口注入 30ms** 真跑到超时分支 / 幂等重复点不重复 POST | 8 | 窗口是**注入参数** ⇒ 不用等 5 秒，也不用读代码相信代码 |
| **J** 文案与对齐 | `CONFLICT` 短句是后端原文**子串**（跨包一致性）/ **同一句文案在 `frontend/src` 里只有一处**（P0-1-29 的 ⑰ 号教训）/ 对齐判据（条数 ±1 ⇒ 丢或留） | 5 | J4 用**全目录扫描**数出现次数，某个组件里再抄一份立刻红 |

**J4 的写法值得复用**：它不 grep 某个文件，而是 `readdirSync('../src/', { recursive: true })`
把全部 `.ts/.tsx/.css` 读进来数这句文案的出现次数，断言**恰好 1 处、且必须在 `streamErrors.ts`**。
"同一口径两处各写一遍"这类问题只有这种写法抓得到。

## 8. 本批**没**覆盖到的（别当全批验收）

- ⚠️ **浏览器里的三条验收路径由用户人工端测**（本批不做智能体侧端测，用户 2026-09-23 定案）：
  ① 停止后可直接追问、不丢已生成内容；② 同标签页重复发送出现专用 toast；③ 断线黄条点击后历史与后端一致。
  跑法与观察点见 `README`「浏览器端测 · 对话」**㉖~㉛**。
- `verify:chat-sse` 是**无依赖档**（不起浏览器、不起真后端）⇒ 它只证明"状态转移与契约接对了"，
  **不等于**"界面上一定对"。真后端的 `/stop` 行为归 `pnpm verify:chat-stream`。
- 本档**验不了** React 渲染（黄条/按钮长什么样、点下去视觉反馈）⇒ 只能人工端测。
- `/active` 的两个进度字段（`queuedPosition` / `currentTool`）在 P0 阶段**没有产生方**（沙箱属 P0-3）
  ⇒ "恢复进度视图"的完整形态等 P0-3，本批文案会退化成"服务端仍在生成这一轮"。
