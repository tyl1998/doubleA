## 坑 1 ⚠️ PDF 夹具的单行文本超出页面宽度 ⇒ pdf.js **静默截断**

**现象**

写 `verify:pipeline` 的 H 组时，用 `fixtures.makePdf([['第一页：' + '丙'.repeat(390)]])` 造了一份"422 字的、
2 页、每页一块"的 PDF，准备断言"跨页的块页码分别是 1 和 2"。结果解析出来的文本只有 **3 个字符**：

```
pdf chars= 4 pageCount= 2 blocks= [{"len":3,"page":1},{"len":3,"page":2}]
```

换成 ASCII 也一样 —— 每页只析出 85 个字符，而且**截在半个单词上**：

```
block0 len = 85
block0 text = "alpha sentence 1. alpha sentence 2. alpha sentence 3. alpha sentence 4. alpha sentenc"
```

**根因**

夹具的 PDF 把整段文本写在**一条 `Tj`** 里（`makePdf` 的 `pages: string[][]` 是"每页若干行"，
我误当成了"每页若干段"）。561 个字以 14pt Helvetica 排出来宽约 4400pt，而 `MediaBox` 只有 612pt 宽 ——
**超出部分在页外**，而 pdf.js 的文本提取**只返回页面框内的文本**。于是内容被无声裁掉，且看起来像是
"pdf.js 有 bug"或"夹具的 `/Length` 算错了"。

验证（同一份夹具，只有"行数与行长"不同）：

```
lines=1  expected chars=23   actual=23
lines=2  expected chars=47   actual=47
...
lines=30 expected chars=740  actual=740     ← 多行（每行 20 余字）完全正常
single long line, expected=1000 actual=78    ← 单行 1000 字被裁到 78
```

**对策**

1. 夹具的"页"要按**能放进纸面的行**给：`makePdf` 的每个元素是**一行**，行宽别超过页宽
   （612pt / 14pt ≈ 70~80 个 ASCII 字符；中文更少）。本批 H 组的做法是每页 20 行 × 36 字。
2. 断言前先打印一次 `parsed.meta.charCount` 与 `parsed.blocks` 的 `(len, page)` ——
   "解析出来的东西"与"我造的东西"对不上时，**先怀疑夹具**，别去改被测代码。
3. ⚠️ 这条与 P0-1-16 的 `makeBlankPdf` **不冲突**：扫描件夹具本来就是"有页面、没有文本层"，
   它的 0 字符是**测出来的真相**；这里被裁的是"我明明写了字却读不到"的假数据。

> 附注：这不是实现问题，但**会让人把排查方向搞反**（去怀疑分块或空文本检测）。它同时也是
> `docs/06` 该批"PDF 页码 meta 取块起点所在页"那条断言可信的前提 —— 所以记在这里。

## 坑 2 ⚠️ 新增的空文本门槛，把 P0-1-17 留下的两处夹具"判死"了

**现象**

加完 ④ 空文本检测（阈值 50）后首跑 `verify:pipeline`，C 组的"四格式全部 READY"与 F 组的"重投救回 READY"
**双双失败**。查库看原因：

```
制度.docx  chars= 20   ← 「报销制度」+ 一句话
巡检.txt   chars= 29   ← makeTxtUtf8()
F 组 PDF   chars= 43   ← 「Retry Policy」+ 一句话
```

三份都低于 50 个有效字符 ⇒ 被判 "疑似扫描件或空白文档"。**这是刻意的行为变化，不是回归** ——
但如果不留档，下一个人看到"夹具这样写"会以为这就是规范，或者反过来把新门槛当成 bug。

**根因**

P0-1-17 选定这几个夹具时，流水线**只到解析**（没有任何"内容质量"的门槛），于是"能解析出东西"就够用。
P0-1-18 引入门槛后，"夹具的资格"变了 —— 而夹具的**意图**（"四格式都能端到端走通"）没变。

**对策**

1. **把夹具写长，别改断言**：C 组的 docx 加到一个标题 + 三段各 30 余字（~80 字），txt 换成三行巡检记录
   （~70 字），F 组的 PDF 加一行（~70 字）。断言与意图都保持不变。
2. 在夹具旁**写明"为什么这么长"**（脚本里已经写了注释）：否则下次有人"顺手精简"就会再踩一次。
3. **"太短会被拦"这件事由 H 组专门验**（阈值边界那一对用例），**不混进 C 组** ——
   一个用例只该有一个失败理由。
4. 需要**真跑默认阶段**的新用例，内容一律给足；只在 D/E 组当"幂等靶子"的短文档不受影响
   （那两组注入的是慢速假阶段，根本不跑 ④⑤）。`uploadFresh()` 的注释里已写明这一点。

## 坑 3 切片单位必须是**码点**：`text.slice()` 会劈开代理对，而且**本层毫无报错**

**现象**

`fixed` 的定长滑窗最自然的写法是 `text.slice(start, start + size)`。对纯中文/ASCII 完全正确，
但对 emoji 就会产出**非法字符串**（半个代理对 = 一个孤立的 surrogate），而这一步**不抛任何错** ——
要等 embedding 拿到它才炸（报的还是上游/模型的错）。中文场景里 emoji 并不罕见（用户文档里的 ✅😀📌）。

**根因**

`'😀'.length === 2`：UTF-16 长度 ≠ 字符数。`chunk_size` 的单位按 `子方案①` §二 B8 定案是**字符**，
所以下标就不能用 UTF-16 长度来算。

**对策**

- `chunk/strategy.ts` 里所有切片一律建在 `[...text]` 的**码点数组**上（`cutPoint` 返回的也是码点下标），
  整条链上没有一处 `text.slice()`。文档注释里写明"这是唯一一处用了慢写法的地方，刻意"。
- 验收分两层：`verify:app` 的"600 个 emoji 按 `fixed` 切，每块逐码点都是 `😀`"（外加断言长度分别是
  512/152，证明是**按码点**算的而不是碰巧没劈开）；`verify:pipeline` 的 H 组则用真字节断言"每块都是
  原文的逐字子串"。
- ⚠️ 顺带一个"断言怎么写"的教训：第一版探针写的是 `/^😀+$/.test(content)`，它**必然失败** ——
  不带 `u` 标志的正则里 `😀` 是两个码元、`+` 只重复低位代理，连不上一串 emoji。
  正确写法是 `[...content].every((ch) => ch === '😀')`。**断言自己写错时，报错看起来像被测代码坏了。**

## 坑 4 Section 必须按"**连续**同名标题"切，不能按 `headingPath` 分组

**现象**

按 `headingPath` 做 Map 分组（"同名标题归一堆"）的实现，在文档里出现两个 `## 考勤`（中间隔着 `## 报销`）
时会把两段考勤**并成一个 Section** ⇒ chunk 顺序变成 `考勤, 考勤, 报销`，与原文的
`考勤, 报销, 考勤` 不一致。

**根因**

Map 分组只看了"标题名"，没看"位置"。而文档里同名标题出现多次是常态（"注意事项"、"其他"）。

**对策**

只比较"与上一段的标题路径是否相同"：不同就开新 Section。这样 Section 序列天然是原文的**连续划分**，
于是还有一个免费的强不变式 —— **所有 Section 的文本按序拼起来逐字等于 `parsed.text`**。
验收用 `考勤/报销/考勤` 三段断言标题路径**随原文顺序**。

**为什么这个错很难发现**：命中检索后读到的片段**通顺**，只是"位置不对"；而位置不对在一份没有页码、
没有行号的文本里根本看不出来。这类"静默错序"是分块层最贵的一种 bug。

## 坑 5 「回退到最近的句末边界」需要一个**下界**，否则会切出碎块

**现象**

严格照 §4-2 字面实现（"累到 `chunk_size` → 回退到最近的句末边界"）时，遇到长表格转文本、
无标点的 OCR 残留这类内容：整段可能几百字才有一个句号，于是"最近的边界"会退到很靠前的位置，
切出几十字的块 —— 与 `chunk_min`（避免碎片块）的意图**正好相反**。

**根因**

"最近"是**距离最近**，不是"离目标位置最近"。文档没写"找不到边界怎么办"，也没写下界。

**对策**

搜索下界取 `chunk_min`：若最近的边界落在 `chunk_min` 之前，说明这一段几乎没有句读，
**按长度硬切在 `chunk_size`** 反而更好。复用 `chunk_min` 而不是另发明一个阈值 —— 它本来就是"碎块"的判据。
（`docs/子方案/知识库流水线.md` §4-2 的落地口径表已回写这一条。）

## 坑 6 ⚠️ `chunk_count` **不能**在"只算了块"的时候就写

**现象 / 决策**

本批把块切出来了，`ctx.chunks` 里有 2 条、日志里也打了 `chunks: 2`。**顺手**写进
`documents.chunk_count` 看着很自然（"数据不就在手上吗"），但那是错的：

- `schema.prisma` 对 `chunk_count` 的定义是"**已入库**的 chunk 数"；
- 本批**没有**写 `chunks` 表（⑥ embedding 与 ⑦ 入库属 P0-1-19）。

写了它就会造出一个最难查的假象：**接口说这篇有 2 块、检索却什么都搜不到**（因为库里根本没有 chunk）。
而且 P0-1-19 还得回头把它改成"其实没入库"，等于给下一批埋一个必须修的 bug。

**对策**

- `chunkStage` **不写** `ctx.chunkCount`（`PipelineContext.chunkCount` 的注释写明"只有真的落库之后才可以写"）；
  worker 那边 `chunkCount: ctx.chunkCount ?? 0` 保持原样。
- 于是 `READY` 的语义是"解析与分块都过了"，**仍不是"可检索"** —— 这个中间态是**刻意暴露**出来的。
- "切了几块"改为**进日志**（`log.debug({ chunks })`）+ 由验收在**模块级**观测（见下一条），
  两条路都不依赖那个列。
- 验收同时断言两面：READY 文档的 `chunk_count === 0` **且** `chunks` 表里该文档 0 行。

## 坑 7 「产物不落库」的东西怎么验：走**模块级**，但必须喂真字节

**问题**

`docs/06` 的验收原句是"传 200 字短通知 → 恰好 1 个 chunk"。本批**没有任何 HTTP 响应**能看到"切了几块"
（不落库、也没有列表端点）。只跑纯函数会漏掉"阶段真的接到了解析结果"这半件事。

**对策**

`verify-pipeline.mjs` 加 `runStagesOnDocument(docId)`：从库里取行 + 从 S3 取对象，构造出与 worker
**同形**的 `ctx`，然后跑**同一条** `defaultPipelineStages`。它验的仍是真字节、真解析器、真分块，
只是换了个调用入口 —— 与 P0-1-16 处理"解析结果"的手法同源。

额外收益：它返回 `{ ctx, error }` 而**不抛**，"在哪一步失败"于是也成了可断言的东西 ——
H 组"④ 拦在 ⑤ 之前"就是用 `ctx.chunks === undefined && ctx.parsed !== undefined` 取证的。

**注意**：这个助手要用 `normalizeRetrievalConfig(row.kb.retrievalConfig)` 自己补默认值（不能 `??'hybrid'`），
否则它就成了一条"与生产不同的读法"。

## 其它值得记一笔的

### ① 分块模块**不 import `config`**，所以它的验收能进 CI

`pipeline/chunk/*` 全是纯函数、不读环境变量、不打日志 ⇒ `verify:app`（无依赖档）能直接 import 它。
这不是巧合而是**刻意**：分块是"给定字节 → 给定块"的确定性变换，让它的验收被 PG/Redis/MinIO 绑住
是没必要的代价。十条断言（小文档特例、句末回退、逐字子串、重叠、尾块合并、滑窗、码点、页码、
顺序、策略回落）全在 `verify:app` 里。

### ② `chunk_min` 是**代码常量**，不是环境变量

`子方案①` §十一 的"本方案新增"配置表里**没有** `CHUNK_MIN_DEFAULT`，`knowledge_bases` 也没有对应列。
凭空加一个环境变量属于**自己发明契约**（本项目明令禁止）。故落成有名字的导出常量
`DEFAULT_CHUNK_MIN_CHARS = 50`，让验收能断言它；要让它可配，先改 §二/§十一 与 schema，再回来改代码。

### ③ 空文本检测的四条口径

| 议题 | 定案 | 为什么 |
|------|------|--------|
| 判据位置 | **解析之后**（独立阶段 ④） | 上传时无从知道内容量（8MB 的 PDF 可能只有 47 字） |
| 判据粒度 | **全文有效字符总量**，不按页 | 封面/目录页本身近乎空白，按页判会大面积误杀（§五 明文） |
| 文案数字 | 取**实测** `charCount` 与**当前**阈值 | 阈值可配；写死 50 会让用户按错数字重传 |
| 边界 | `<` 不是 `<=`（恰好达标通过） | 验收用"恰好 = 阈值通过 / 少一个失败"一对断言守住，且用例按**当前阈值**生成 |
| 失败后 | **保留原文件** | 用户要能下载回去核对"我传的是不是扫描件" |

### ④ 阶段顺序：④ 必须排在 ⑤ 之前

反过来的话扫描件会先被切一遍再判失败（白干），而且"chunk 数为 0 却报句子级错误"会把排查方向带偏。
验收用**产物的缺席**取证（比"读代码看顺序"强）。

## 坑预判取证

`docs/06` P0-1-18 的坑预判原文：**"`chunk_size=512` 是字符不是 token（B8 定案），不要用 tokenizer 计数；
中文 1 字符 1 长度，`[...text].length` 才是正确计数（避免 emoji 代理对）"**。

⚠️ **成立**，且本批把它变成了两条硬的实现与断言：

1. 实现侧：`chunk/strategy.ts` 的**所有**切片都建在 `[...text]` 的码点数组上（`cutPoint`/`tailByCodePoint`/
   `blockSpans` 的下标全是码点）。整条链上没有一处 `text.slice()`。
2. 断言侧：`verify:app` 里"600 个 emoji 按 `fixed` 切 → 块长 512/152，且每块**逐码点**都是 `😀`"。
   （只断言长度会漏掉"碰巧没劈开"，只断言内容又看不出长度是按码点算的 —— 两条一起才守得住。）

**实测补充的两条（预判里没有的）**：

- **PDF 夹具必须折行**（见坑 1）：单条超长 `Tj` 超出 `MediaBox` 时 pdf.js **静默截断**
  （单行 1000 字实测只析出 78 字；561 字析出 85 字且截在半个单词上）。多行（每行 20 余字）时
  提取完全正常。⇒ 用它断言"分块边界/阈值"前，先确认解析出来的字符数与预期一致。
- **emoji 的"正则断言"本身会写错**（见坑 3 末段）：`/^😀+$/` 在不带 `u` 标志时**必然失败**
  （`+` 只重复低位代理）。要用 `[...content].every(...)` 这种按码点的写法。
  **断言写错时报的错看起来像被测代码坏了** —— 这类问题的排查成本最高。
